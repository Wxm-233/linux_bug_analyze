# 新·论文思路梳理

# 待解决的问题

## Linux如何兼容多架构

Linux不是为每个架构维护独立内核，而是采用“公共内核主体层\+架构层”的方式，两层各实现架构/非架构功能：

- 架构功能指用于处理不同处理器架构差异的功能，如启动、异常处理、页表、内存屏障等。

- 非架构功能指用于提供Linux通用内核服务的功能，如调度、内存管理、文件系统等。非架构功能主要使用不依赖架构的数据结构和算法，需要调用架构功能以实现功能。

实现这两种功能的代码被称作**架构/非架构（公共层）代码**。非架构功能提供服务和抽象，架构功能提供实现与适配。非架构功能会调用架构功能。

两层代码各有一部分**边界代码**，对架构层调用其提供的功能，也要向上为公共层提供功能接口。一旦边界代码内的两类代码在适配上出现了问题，其不仅在架构/公共层间沿调用路径**纵向**出现，也会在不同的架构间**横向**传递。

## 本文要解决的问题

本文要回答的是：Linux内核中，公共层代码在适配多个架构时，通常会出现什么问题，根因是什么，问题在横向（多个架构间）和纵向（架构/非架构）间的传播情况如何，如何修复以解决问题？

# 已有方法的不足

现有工作在分析内核功能可变性、API演化、架构一致性方面已有相关研究，但是对多架构兼容性的两方向错误的研究还不够深入：

- **纵向：现有工作大多关注边界代码在哪，且它们是否可被正确配置和编译，还没有对边界代码内两侧（即公共层和架构层）对硬件行为的理解是否一致有足够的分析。**如配置项分析可以发现某个架构选项是否会启用相应代码；调用图和架构恢复方法可以发现公共代码是否调用了架构实现；编译器也可以检查函数参数、类型和符号是否匹配。然而这些方法通常无法判断边界代码所要求的语义是否真的由该架构实现提供。

- **横向：已有工作较少关注一项架构相关修复如何经由边界代码影响其他架构。**在修复某架构的错误时，有时需要修改边界代码，边界代码修补不当可能会在其它架构上出现新错误，增加开发成本（尤其是某些错误不会在合入时立即暴露，而是过了很长时间才被发现），现有工作忽略了对这一跨架构错误情况的研究。

**边界两侧的架构和非架构代码隐含的架构语义，它们在哪些情况下没有被接口、能力描述或测试明确表达。** 这正是触发架构特定错误的来源。

# 核心观察

我们的核心观察是，**Linux中的边界代码是否可明确表达并处理各个架构不同的硬件语义，以支持多架构。**

## 兼容多架构的问题

公共层与架构实现之间通过边界代码实现控制流或数据流上的关联，如公共代码调用架构代码里的函数或方法，或读写架构代码里定义的变量或数据结构。公共部分依赖的语义必须由架构实现保证；架构实现的关键能力和限制，必须被公共代码识别并正确处理。

**然而现有Linux开发规范或开发工具没有保证边界代码两侧对硬件行为的语义理解一致。**如编译器和构建系统通常能够检查函数类型、符号可见性和配置条件，却难以检查接口是否完整表达了中断投递、地址转换、DMA 一致性、缓存维护、内存顺序或权限隔离等架构语义。

因此当边界代码中，公共层部分隐含的架构语义，和其调用的架构层部分所隐含的语义不一致时，出现失配。硬件能力无法被正确表示或使用，从而带来以下错误。

## 错误类型

由此带来以下两种错误：

**隐式语义假设错误。**公共代码与某一架构实现共同执行时，暴露出两侧语义未对齐。例如公共内存管理代码默认某种页表、TLB、cache、一致性或内存顺序行为，而该假设只在部分架构成立。

**跨架构回归。**修复或优化目标架构 A 时修改了公共代码，忽略了 B 架构原有的限制或能力，使原本正常的架构 B 出现功能错误、性能回归或语义变化。

## 出现问题的原因

**出现语义失配，是因为Linux想用一套公共内核支持多种架构，但很多公共功能在真正实现时，公共层的逻辑被大量复用，但又允许底层硬件有不同的行为。**

在内核长期增量演化中，开发者较容易抽取不同架构之间表面相同的控制流、数据结构或资源管理方式，却未必能同时将仍然存在的语义差异明确写入接口。已有公共抽象也往往由历史硬件和既有使用场景逐步形成；当新架构或新平台能力具有不同的资源拓扑、同步要求或隔离边界时，旧抽象可能包含只对部分既有架构成立的隐含假定。

若这种假定没有被重构为明确的接口契约、能力描述或测试义务，便可能先在某一架构上形成纵向兼容缺陷，或在后续修补中演化为横向的跨架构回归。

然而在内核代码长期增量演化中，开发者只考虑到不同架构下控制流或数据流上的共同部分，却容易忽略不同架构之间可能存在的语义差异；此外，公共层抽象往往由历史硬件和使用场景逐步演化而来。若新功能具有不同的资源拓扑或语义约束，既有抽象可能隐含只对部分已支持架构成立的假设。

# 修复的必要性

设边界代码中，非架构部分要求的语义为R，架构部分支持的语义为G，在R=G时，两侧代码的语义才是适配的，否则便出现了语义失配。此时公共代码额外依赖某项未被架构实现保证的行为，当特定架构、设备或执行条件触发该行为时，错误便会暴露；若公共代码不能识别处理架构侧代码的关键能力和限制，错误也会暴露。

问题在于，边界代码有时只表达了调用什么函数或资源，却没有表达该函数必须保证什么，满足什么规范。于是，公共代码可能隐含依赖某项语义d，但开发者在编写边界代码时忽略了d。当旧架构恰好提供d时，问题不会出现；新架构不提供d时，公共路径便会发生纵向兼容缺陷；类似地，若开发者为了架构A修改公共代码，使其开始依赖新的语义d\_A，但没有检查架构B是否也能保证d\_A，这一修改便可能形成横向的跨架构回归。

因此，修复应当实现将原本隐含的语义d显式写入边界代码中。修复后，公共代码只能依赖接口声明的保证；每个架构的实现也必须明确表明自己是否能够提供这些保证。**这样，原本隐藏在代码路径中的语义假设转化为可构建和检查的条件，从而修复这两类错误。**

- 对纵向错误而言，目标架构若不满足公共代码的语义要求，就不能再静默接入该路径；问题会在实现或测试接口时暴露。

- 对横向错误而言，公共接口一旦改变，所有实现该接口的架构都成为明确的影响范围；维护者必须检查它们是否仍满足新契约，而不是等回归在某个架构上偶然暴露。

## 断言

设计可构建和检查的条件有多种方式，断言是一种最重要的方式，因此一种可能的设计方向是：**架构接口断言化**。Linux内核当中已经在锁、类型约束和硬件描述等方面大量使用了这种思想。有些地方的断言使用还和我们的场景很相似：

例如，`lockdep_assert_held()` 断言表达“调用此函数时，必须持有某把锁”，违反时发出警告。[Linux文档](https://docs.kernel.org/locking/lockdep-design.html)指出：它尤其适合发现回调场景中上层假定锁仍被持有、下层却擅自释放并重新获取锁的情况。这个结构与本文的问题非常接近，即两侧代码都能调用成功，但对接口语义的理解不同。

再例如，[Sparse](https://www.kernel.org/doc/html/v4.9/dev-tools/sparse.html)的`__must_hold`、`__acquires`和`__releases`则把锁的进入/退出条件写入函数声明，使静态分析器能够检查调用路径是否满足这些条件。

再者，设备树binding除了规定硬件是否存在，还规定资源数量、顺序、兼容型号和对象关系，并通过 `dt_binding_check`、`dtbs_check` 验证。[Linux开发规范](https://docs.kernel.org/devicetree/bindings/writing-bindings.html)已经要求binding尽量完整，即使当前驱动尚未使用某项硬件能力，这一特性或许可以用在边界代码的开发中。

**但并不是所有的语义都可以转化为断言，因为很多语义并不是某一时刻可计算的布尔条件。**因此除了断言，某些语义信息还需要由类型、能力描述、回归测试等来验证。

- 如果一个语义性质需要跨时间、跨CPU或设备等才能判断，那么它可能不适合使用断言。如“所有 CPU 最终都会退出旧页表”，断言只能检测一次执行是否正常，无法检测未来的执行都满足这个性质。不过maintainer一般会要求开发者将这些性质以注释的方式写在代码中以方便审查，这为我们开发其它的验证方式提供了便利。

通过调研分析已有的补丁，我们认为残缺的语义信息一般从以下几个方面联合获得，而非只通过某一方面：

- 文字材料。包括注释（例：9bcac97dc42d2f4da8229d18feb0fe2b1ce523a2）、内核文档、硬件手册、架构指令集文档等。

- 人类讨论。包括用户与开发者的邮件往来等。

- 内核已有的代码实现。包括①接口本身的实现；②调用接口的代码的特征；③接口使用的数据结构的定义

- 内核实际运行时的结果反馈，如日志（这更多适用于修复而不是预防）；编译错误等

- 其它架构的相同功能的实现方式。

最大的一个问题是，为修复或避免跨架构错误所需的语义信息并不集中在某一个地方，而是分布在各处。需要结合在一起才能给出相对完善的上下文信息。

语义源也会出错，不同来源的语义信息有可能会冲突。比如14bce187d1600710623d81888da3501bbc470ba2这个提交，改动前的DTB解析函数和实际应修改的语义完全相反。一旦参考了这些代码，有可能对语义信息的分析造成误导。

想到的方法：使用大模型调取并阅读这些东西，提取生成候选语义。需要引入判别器，分析哪个语义适合应用在补丁中。

计划：检查LLM生成的修补措施是否能够正确生成以下内容。如果使用多源证据能显著提高语义和修复方式的判断准确率，那么这个修复的novelty就成立。断言、接口扩展和边界迁移都是该语义重建结果导出的不同修复策略。

- 缺失或冲突的语义是什么；

- 它的触发条件、架构/设备/配置范围是什么；

- 哪些证据支持、哪些证据反驳该结论；

- 应修改边界接口中的公共层还是架构层；

- 修改后应采用何种验证手段。

## 边界代码迁移

好的边界代码里，对于可能影响正确性的关键语义信息，两侧代码都能回答：①谁提供和消费语义；②语义作用的对象和范围，不支持时的回退策略；③语义正确性的检查条件。

如果以上有其中一条无法满足，即关键语义既无法在当前边界被表达，也无法通过合适的静态、运行期或测试机制被验证，则考虑这段代码还是否适合作为边界代码出现。**因为断言不一定能完全满足以上三条，所以断言可以作为判断边界代码是否适合保留的标准之一，更合适的方法是用多个方法，覆盖上面三个条件，进行联合判断。**

具体迁移谁，怎么迁移，还需要再深入地考虑。

- 如何提交断言，可以作为新意和研究方法

- 是否有架构层/公共层边界不合适的情况？某函数不合适，用另一个函数才可以更好地使用断言，是否使用断言可以考虑作为一种判断的标准

# 方法

可参考ICSE'26上关于Linux内核并发缺陷研究的论文《A Comprehensive Study of Concurrency Bugs in the Linux Kernel》的研究方法：

- 从 Linux 主线内核的提交开始（一般得是5年），以关键词（在我们的场景下可以是architecture, RISC\-V等架构名称等）筛出候选提交。

- 将候选提交随机排序，两名研究者分别检查提交说明、代码补丁以及相关缺陷报告或邮件讨论；有分歧时再讨论取得一致意见，最终确认一部分真实跨架构缺陷。这篇文章真实缺陷有200个，我们或许可以收集数量级差不多的。

- 对每个缺陷人工标注四方面信息：触发条件、根因与缺陷模式、发现方式、修复方式。

- 再把这些缺陷与一般内核缺陷比较，例如缺陷从引入到修复经历多久、补丁改动多少函数和代码块、涉及架构和触发原因等。

- 分析错误的补丁，提出修复方案。
