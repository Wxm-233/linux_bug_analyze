# 跨架构语义问题的初步 Pattern 与系统层机制总结

整理日期：2026年9月15日。依据本项目已有源码复核、历史修复对照和原型实验。

## 一、当前可以得出的核心结论

目前已形成13条源码案例记录，其中9项开展了不同层级的原型验证；后续对8条新增提交进行了小批复核，并在其中一条调度拓扑案例上补充了契约迁移实验。这些材料支持一个初步观察：

**公共接口的函数签名和数据类型，往往没有充分表达平台实现所依赖的参数来源、表示方式、能力条件和有效时机。当这些隐含条件发生变化，原本在一种配置下正确的代码，可能在另一种架构、ABI、页大小、设备或固件条件下产生错误。**

因此，系统层的研究重点可以放在：将隐含假设转成显式、可检查的接口契约，在数据消费前和状态转换过程中验证，并用跨配置测试检查修复覆盖范围。

本文所说的“防止跨架构逃逸”，是指防止缺陷因架构或配置差异而漏过检查、进入后续运行阶段。当前案例包含功能、兼容性、能力属性和状态转换问题，不能全部计为已确认安全漏洞；也不能把所有跨层问题都解释成已有完整证据的“修复架构A，导致架构B回归”。

## 二、四类初步 Pattern

### P1：默认配置下成立的参数关系，被当成普遍成立

代表案例包括Btrfs、mlx5 SHAMPO和fbnic。

- **Btrfs：** 挂载选项在实际扇区大小就绪前，使用临时4096值裁剪。虽然最终几何参数被更新，已经裁剪的选项却不会自动恢复。
- **fbnic：** 设备按4K片段处理系统页。4K页只执行一次循环，掩盖了输出描述符指针未推进的问题；更大页需要多个片段，错误才暴露。
- **mlx5：** 页大小、MTU和每个工作请求所需报头数量之间的关系，在64K页及较大MTU条件下不再满足原先假设。该项目前以源码分析为主。

共同点不是“大页一定有问题”，而是**参数是否真实就绪，以及分配、索引、编码和释放是否使用一致的几何关系**。

对应机制：区分默认参数与已验证参数；集中派生布局；检查非零、整除、容量、步长及片段覆盖；测试必须包含超过单次循环的输入，不能只验证默认4K配置。

### P2：相同类型或地址，隐藏了不同的数据表示

代表案例包括NUMA compat位图、perf配置union和s390回溯。

- **NUMA：** 32位用户位图与64位内核位图在访问宽度和大端字序上存在差异。转换位置及入口包装器决定了实际行为，不能直接以某个辅助函数的结果替代完整入口结论。
- **perf：** 将所有数值统一写入union的u64成员，再按bool、int或u32成员读取。在小端下部分输入看似正确，在大端下非零值解释错误。
- **s390回溯：** 相同的栈指针数值类型不代表相同的起始帧语义；消费者还依赖调用约定和帧基准。该项尚未做原型。

共同点是**表示信息在跨接口传递中被丢失，消费者按自己的假设解释数据**。

对应机制：显式携带ABI、字宽、格式、单位或有效成员标签；通过统一构造和转换接口完成规范化；验证“写入类型—有效成员—消费类型”的一致性。不能将所有表示问题都简化为字节交换。

### P3：最终状态正确，但消费时点或转换过程不正确

代表案例包括s390拓扑、ARM SMMU以及新增的调度拓扑上下文案例。

- **s390拓扑：** CPU启动通知发生时，公共层需要的拓扑尚未更新。修复不仅要提前更新，还要以prepared状态识别尚未online的CPU。
- **ARM SMMU：** 域切换的最终状态正确，并不保证设备可观察到的中间状态满足访问约束。
- **新增调度拓扑案例：** 回调依赖残留的全局NUMA层级，导致消费者取得错误掩码；修复改为显式传入本次调用的层级上下文。

共同点是**消费者需要的是“此刻与本次操作对应的有效状态”，而不是某个最终会正确或之前曾正确的状态**。

对应机制：显式状态机、通知前置条件、操作级上下文和全过程不变量；同时检查失败恢复与重新加入流程。仅加锁、检查最终结果或提前调用一次更新函数，都不必然解决语义问题。

### P4：统一逻辑掩盖了底层能力及其适用条件

代表案例包括VT-d、ACPI、parisc和fw_devlink。

- **VT-d：** 不同分页模式对权限的表达能力不同，不能把一种模式的限制无条件套用到另一种模式。
- **ACPI：** CPU条目存在、启用和可上线是不同概念；能力判断依赖正确的规范来源、版本和兼容环境。
- **parisc：** 架构启动时无条件清除稳定属性，与后续拓扑策略不一致。
- **fw_devlink：** 公共依赖建链依赖固件节点表示的完整性，这一条件在特定平台未必成立。该项尚未做原型。

共同点是**用架构名称、默认值或统一分支，替代了具体资源的实际能力**。

对应机制：按设备、模式和版本表达能力，并记录来源；区分“未知”“不支持”和“已确认支持”；检查请求能否被正确实现；由具体契约规定拒绝、协商或兼容回退，不能对所有情况一律拒绝，也不能静默改变请求语义。

## 三、贯穿各类问题的共性：修复没有覆盖完整语义依赖

ACPI历史中出现过只修LAPIC而遗漏x2APIC、依据错误版本信息判断能力等问题。s390拓扑实验中，“只改顺序”和“只改掩码”两种人工不完整修复均未通过。

NUMA的深化实验进一步说明：原来在小输入范围内通过的修复，在更大声明范围下仍可能不满足契约。后续索引修正解决了部分问题，但本实验仍保留4组部分compat字宽输入的不一致，尚需核实实际接口约定。

因此，应建立一份**语义影响清单**：

| 需要记录的内容 | 要回答的问题 |
|---|---|
| 提供者与消费者 | 谁产生数据或能力，谁依赖它？ |
| 表示及来源 | 数值采用什么ABI、单位、格式，来自何处？ |
| 适用条件 | 哪些模式、版本、配置下成立？ |
| 状态与时序 | 何时可消费，哪些中间状态允许出现？ |
| 等价入口 | 哪些入口、回调或架构实现消费同一语义？ |
| 失败行为 | 不支持或条件不满足时应如何处理？ |
| 验收反例 | 哪个输入能区分旧实现、完整修复和不完整修复？ |

这份清单初期可以由源码复核构建，静态分析和模型辅助查找线索；目前尚未实现自动完整提取，不能宣称已经获得完整依赖闭包。

## 四、系统层机制如何落地

建议形成“**契约表达—边界检查—转换过程约束—跨配置回归**”四个环节。

| 环节 | 可落实的措施 | 预期拦截的问题 | 当前状态 |
|---|---|---|---|
| 契约表达 | 带表示信息的参数、按模式描述的能力、显式调用上下文 | 默认值冒充能力、类型相同但含义不同、残留全局状态 | 已有案例及历史修复支持，未实现统一框架 |
| 边界检查 | 消费前检查参数就绪、访问范围、布局覆盖和请求可表示性 | 提前消费、按错误字宽读取、遗漏片段、权限表达失配 | 已有多个源码及内核原型 |
| 过程约束 | 状态机、通知前置条件、中间状态检查及失败恢复 | 最终正确但通知时错误、转换中短暂违约 | 已有拓扑与SMMU原型，真实并发和设备证据不足 |
| 回归集成 | 按受影响能力组合运行旧／新／不完整修复对照 | 只修一个入口、只测一种配置、边界修复不完整 | 已有局部矩阵，尚未接入统一CI门禁 |

测试维度应由契约决定。例如：表示类覆盖字宽×字节序×输入边界，几何类覆盖系统页×设备粒度，能力类覆盖版本×模式，生命周期类覆盖通知前后×失败恢复。并不要求所有维度做无差别笛卡尔积；优先选择能区分错误实现的最小反例及正常对照。

这些机制的研究价值在于，把发现时机前移到接口交接和回归检查阶段。现阶段验证的是若干历史实现与契约的符合性，还没有证明一套已部署机制能够普遍防止跨架构问题。

## 五、已有实验能支持到什么程度

| 原型 | 主要结果 | 证据限制 |
|---|---|---|
| Btrfs | 每版18场景，旧版5组违约，修复版全部通过 | 源码数据依赖投影，未真实挂载 |
| fbnic | 每版18场景，旧版12组违约，修复版全部通过 | 描述符函数执行；大页支持配置有范围限制，未运行网卡 |
| parisc | 每版14场景，旧版10组违约，修复版全部通过 | 拓扑策略一致性，未测量物理时钟同步 |
| VT-d | 真实内核页表检查：旧版11通过／3失败，修复版14通过 | 未验证设备DMA和硬件IOTLB |
| ARM SMMU | 每版14场景，旧版5组违约，修复版0组 | 硬件和锁等使用替身，未验证设备可见并发 |
| ACPI | 八场景分别执行旧／新策略，共16次启动；旧策略4项预期失败，新策略24项检查通过 | 固定内核上的判定策略对照；固件输入和环境条件受控，未物理热插拔 |
| NUMA | 初步辅助函数矩阵修复版通过；深化入口链每版32组，旧版27通过、统一入口20通过、回放后续修正28通过 | 真实保护页、历史入口转换链，但策略末端及部分接口是替身；剩余4组待核实 |
| perf | 每版每架构12场景；旧版小端全通过、大端5组失败，修复版均通过 | 真实s390x用户态模拟执行，未运行完整perf环形缓冲区测试 |
| s390拓扑 | 每版每架构12序列；旧版均在契约检查失败，完整修复通过，两种不完整修复失败 | 真实掩码函数与生命周期投影，未运行内核通知链 |
| 新样本契约迁移 | 显式NUMA层级上下文：每版8组，旧函数4组错误，修复后全部通过 | 新案例上的人工契约实例化，不是自动发现或完整调度器运行 |

八条新增提交的模型对照中，一条契约相关案例被保留；六条普通对照被模型排除，其中一条因材料截断被程序保守保留；一条范围争议项被排除。该组规模小且非随机，只能说明本轮表现，不能作为整体准确率或机制泛化能力的证明。

## 六、下一阶段应优先验证什么

1. **先核实NUMA剩余4组不一致。** 检查真实ABI存储约定、入口路径和支持配置，确定是实验契约过严、测试环境差异，还是仍需进一步追踪的实现问题。保留失败结果，不通过修改预期追求全通过。
2. **推进一个代表案例到完整运行链。** NUMA补真实内核入口，或拓扑补真实通知链；用实际消费结果检验切片结论。不要仅扩充相似参数数量。
3. **固定规则，扩大独立验证。** 增加未参与契约设计的案例和正常对照，分别记录模型原始判断、程序处理、源码复核及运行结果，并请领域人员确认争议项。
4. **评估机制本身。** 衡量它能拦住哪些原始错误和不完整修复、会拒绝多少正常配置、带来多少复核与运行开销，再决定哪些检查适合成为开发期或运行期机制。

### 可用于汇报的概括

目前我们通过小批样本源码分析和原型验证，初步归纳出参数与粒度、数据表示、生命周期和能力表达四类语义问题。它们的共同点是公共接口未充分表达平台实现必须满足的条件，使同一代码在不同配置下产生不一致行为。针对这些问题，可以在公共层与平台实现的交接处引入显式契约，检查参数就绪、表示转换、能力适用范围和消费时序，并通过跨配置反例及不完整修复对照验证覆盖。已有实验支持部分契约具有区分正确与错误实现的能力，但尚未形成统一防护系统，也未证明其普遍泛化效果。下一阶段重点是补足真实调用链验证、核实剩余边界问题，并用独立样本评估机制的有效性与代价。
