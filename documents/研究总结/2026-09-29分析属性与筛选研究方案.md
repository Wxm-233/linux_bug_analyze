# 分析属性与筛选研究方案（待确认）

日期：2026-09-29。依据项目代码、组内沟通及已有实验说明整理。

状态：这是设计与实验计划，不是已实现功能或实验结论。研究范围和 RISC-V 反事实口径待用户确认；暂不修改正式分析协议、筛选阈值，也不启动付费调用。

## 1. 研究目标与已有基础

目标不是只缩短 LLM 筛选时间，而是用有限预算找到可复核的架构相关缺陷，并说明其产生、传播和修复机制。

已有能力应复用：

- `screen_fast.py`：并发、分级材料、累计预算、断点缓存、保守排除保护。无需另建初筛器。
- `semantic_signals.py`：根据提交说明及实际变更检测语义线索。当前规则仍要求说明命中关键词，尚不能解决完全缺少文字线索的情况。
- `prepare_review.py`：从详细报告提取初步人工复核清单；尚未直接覆盖新初筛结果和原正则未选中的提交。
- schema v4 详细分析：保留七项通用性质，作为辅助标签；新增架构因果信息应成为主要案例描述。

两项待确认口径：

1. 建议正式跨架构案例要求有架构语义依赖的证据。ABI、页大小、设备、固件等差异可成为该依赖的表现，但不是只要出现这些差异就自动纳入；纯配置差异暂保留待定。
2. 建议 RISC-V 反事实分为“保留现有公共逻辑，仅运行 RISC-V”和“进一步移除已证明仅其他架构需要的公共逻辑”。不把两种操作混为一谈。

## 2. 报告新增属性

新增内容同时进入机器读 JSON 和程序渲染的报告，CSV 提供可筛选列。先服务详细分析，不把全部长字段塞进短判定，避免初筛成本再次增长。

以下字段名称是建议值，正式 schema 在口径确认后确定。

| 用户要求 | 建议记录 | 判定约束 |
|---|---|---|
| 是否由某架构引入 | `architecture_origin`：yes/no/unknown/not_applicable、来源架构、引入提交、原因和证据 | 指为某架构需求/限制引入的改动导致该缺陷；不等于提交修改了 arch/，也不等于最先在哪个架构发现 |
| 为什么影响其他架构 | `cross_arch_impact`：是否有证据、受影响架构、共享行为及失配解释 | 纯纵向问题可无已知其他受影响架构，不强迫模型编造横向回归 |
| 通过什么路径传播 | `propagation_path`：有序的函数/接口/状态/配置步骤及证据 | 区分运行期数据/控制/状态依赖与提交历史中的共享行为变化；不假定 CPU A 在运行期调用 CPU B |
| 只保留 RISC-V 后是否仍有影响 | `riscv_counterfactual`：场景、yes/no/unknown/not_applicable、条件和依据 | 固定缺陷版本、触发条件及干预操作；区分源码推断与实际验证 |
| 触发错误的架构 | `trigger_architectures`：数组、条件及证据 | 复用架构规范名，支持多个架构；不能用正文架构词汇或现有 related_architectures 直接替代 |
| 触发错误的子系统 | `trigger_subsystems`：主子系统及其他涉及子系统、依据 | 主子系统便于统计，其他涉及项可多选；不把修复文件所在目录直接当作故障触发位置 |
| 横向还是纵向 | `propagation_direction`：vertical/horizontal/both/neither/unknown | 允许两者兼有，不能用“没看到横向证据”推导为纵向，也不能与初筛字段默默矛盾 |
| 架构侧还是公共侧产生 | `defect_origin_side`：architecture/common/both/unknown/not_applicable | 记录错误假设或实现的来源，不等同于修复侧，也不等同于最终崩溃位置；只有关系已知、无法归责时用 unknown 并解释边界失配 |
| 引入—发现—修复时间 | `lifecycle`：事件、时间、来源、已知精度和派生间隔 | 不让模型猜日期；缺失为 null；间隔由程序计算 |

每项保留依据和未知说明。空架构数组结合显式状态解释为未知或不适用，不默认为“所有架构”。

原有 `semantic_origin_architectures` 表达语义需求来源，并不自动证明某次改动引入缺陷；两者有关联但不能机械复制。原有“应修改的层次”也不能替代“错误产生侧”。

子系统第一版采用小型统一词表，例如 mm、scheduler、irq、iommu、virtualization、filesystem、network、driver、firmware、arch_core、tooling、other、unknown，并保留原始具体名称供复核。该词表是项目分类，不声称是 Linux 唯一官方划分。

### 2.1 RISC-V 反事实

两种推荐场景均针对同一个有缺陷的基线：

- 场景 A：保留公共代码和相关资源语义，只考察 RISC-V 的适用运行路径。禁用其他架构不意味着历史上为其他架构加入的公共逻辑消失。
- 场景 B：在 A 的基础上，移除有证据表明仅为其他架构所需的公共语义，同时维持 RISC-V 必需功能。必须指出具体可移除的逻辑，不能用“重写后就没问题”作为答案。

若该版本不支持 RISC-V，或涉及的硬件/配置不适用于 RISC-V，明确记录不适用；若无法确定支持范围，记录未知。不能凭移植后的想象执行路径填 yes/no。

### 2.2 生命周期

当前代码的 `CommitInfo.date` 来自作者日期 `%ad`；Fixes 材料未附日期，邮件材料也未系统保留日期。因此需要补证据提取，而不是只改提示词。

推荐定义：

- 引入：有证据支持的引入提交的 Git committer 时间。保留作者时间供审计；committer 时间只是提交时间代理，不宣称等于进入 Linus 主线的实际合并时间或首次发生错误时间。
- 发现：当前材料中最早可核实的缺陷报告/邮件所记载时间。报告中若明确记述更早的发现日期，另存该事件及出处；不能将“最早找到的公开报告”冒充真正首次发现。
- 修复：所分析修复提交的 committer 时间。一个问题有多次修复时保留修复链，不能默认第一条补丁完整解决了问题。
- 计算：分别计算“引入提交至首次已知报告”和“首次已知报告至本次修复提交”的天数；若发现事件有直接证据，再单独报告真实发现事件口径。
- 缺少报告时间时，两个报告相关间隔为 null；可另统计引入至修复，不能拆分猜测。多个引入候选未裁定时也不硬选最早日期。
- 时间顺序矛盾、精度不足或来源范围不同的记录标记待复核，不生成负数年龄或用绝对值掩盖问题。

汇总给出有效样本数、缺失数及口径；所有缺失值不得当作 0。保留旧 `date` 语义，新增事件字段，避免悄悄改变已有时间统计。

### 2.3 模型与人工结论分离

模型提出上述属性；独立的人工复核层保存确认/否定/待定、依据、复核人和日期，可覆盖个别字段但不抹掉模型原始结果。`needs_review=false` 不等于人工确认。

先按提交输出，人工复核时可指定 `case_id` 归并同一缺陷的多次修复。提交数、确认缺陷数分别统计。跨架构、跨子系统多标签计数不得直接当作互斥类别比例。

新字段采用固定键和显式 unknown/null，不把缺失信息强行补成否定。这个设计参考了 OpenAI Docs 对必填键和可空值的输出约束说明，但本项目继续保留现有兼容接口及应用侧校验，不假定服务端提供原生 Structured Outputs。[输出约束文档](https://developers.openai.com/api/docs/guides/structured-outputs)

## 3. Challenge–Solution：跨架构因果线索稀疏下的预算受限检索

### Challenge

跨架构缺陷的触发架构、需求来源和传播范围可能分散在修复提交、引入提交及公共接口实现中，单条提交说明不一定直接描述这些关系。架构关键词还可能来自署名、文件路径或无关对照，而关键词少的公共层改动可能具有重要影响。因此，提高关键词阈值虽然减少调用量，却可能系统性遗漏最值得研究的隐式语义失配；仅提高并发则不能减少总分析工作量。

这段描述是待用真实案例检验的研究假设，不能仅凭导师举例就断言其频率很高。

### Solution（拟议）

构建一个保留审计信息的候选排序方法，联合使用字段化文本证据、公共/架构边界改动线索及有限的提交历史关联。在固定分析预算下，优先检查高分候选，同时为低分和原规则未命中的提交保留随机探索额度；用独立人工复核样本衡量发现收益和遗漏风险。分数控制检查顺序，不直接证明缺陷相关性，也不把暂未检查的提交标为不相关。

潜在贡献是：是否能找回“文字线索弱、边界语义影响强”的跨架构案例，以及是否在相同成本下发现更多经确认的缺陷。不是声称发明关键词加权或主动学习。ASReview 已研究基于人工反馈的筛选优先级与主动学习，且指出错误率评估仍需要额外标注；其结果不能直接当作 Linux 提交上的效果。[ASReview 原始论文，2021](https://www.nature.com/articles/s42256-020-00287-7)

### 3.1 关键词打分的最小改进版

推荐先实现可解释的离线规则分数，不立即训练复杂模型：

1. **按字段区分。** 标题、说明正文、实际代码改动、文件路径分别计分。架构词不从署名邮箱、维护者地址或 URL 域名中获取；Fixes/Closes 等结构信息另行保留。
2. **重复命中封顶。** 同一语义特征反复出现不无限加分，减少长提交和大补丁的优势。
3. **区分强弱线索。** 单独出现 ARM、IRQ、DMA 只给弱权重；差异描述、回归后果、接口契约变化给更高优先级。修复信号是加分，不是必需门槛，避免遗漏普通功能改动中引入的错误。
4. **加入交互线索。** 例如“表示差异说明 + 实际转换代码改动”“公共路径改动 + 能力检查变化”。不要求同时改 arch/ 和公共目录，也不要求提到两个架构。
5. **为弱文字线索保留独立通道。** 在一部分文字低分提交中检查能力位、转换、回调、配置保护等改动；否则完全依赖文字命中后才读 diff，会重复原有盲点。源码匹配仍只是启发式线索，不是语义证明。
6. **有限历史补充。** 优先查显式 Fixes 关系及相关提交说明，记录是否新增架构和共享接口线索。只做有限跳数，不立即建设全内核调用图；没有 Fixes 的提交仍保留探索机会。
7. **多样性和探索。** 每批为低分、不同子系统及机制线索保留名额，避免高分队列长期被同一类修改占据。架构未知不能被排除在配额之外。

示意得分：文本信号 + 边界改动信号 + 历史关联信号 + 信号交互。先登记规则、权重、封顶方式及版本，调参后在冻结的另一批样本上验证；该得分不是相关概率。

第一版不需要大模型生成得分，也不需要再换一个模型。元数据扫描和历史读取使用本地 Git；较贵的 diff/历史检查按阶段缓存，同时统计本地预处理成本。不能靠先对所有提交调用 LLM 再评分来声称减少调用。

### 3.2 避免把历史知识当作预测能力

Fixes 指向的修复关系只能在相关修复提交已存在时使用。第一轮将目标限定为“对截止日期前已存在的提交做回顾性缺陷案例检索”，不声称在引入时预测了未来漏洞。若以后评估提交时检测，则必须只允许使用当时可获得的历史。

引入—修复链和同一缺陷的多个提交应分组划分开发/验证集，避免两边共享同一案例。统计发现收益时同时报告提交数和去重案例数。

### 3.3 能够写进论文的条件

必须出现独立样本支持，例如：

- 有可核实的相关提交在文本打分中低分，但被边界/历史线索提升并确认；具体指出原方法漏看了什么。
- 相同请求/token 或复核预算下，改进方法发现更多真实案例，而不仅是得到更多模型 related。
- 移除源码或历史特征后收益下降，说明提升不是仅增加了随机检查数量。
- 公开未找回的类型及证据不足的限制。没有收益时如实报告，不把工程完成包装成研究有效性。

## 4. 服务器试验计划

### A. 先跑离线审计，不调用模型

冻结 Linux ref 的完整 hash、时间范围、规则版本和随机种子；保存全范围提交清单，而不只保存旧规则选中的 45,575 条。

输出：每条提交的字段命中、特征贡献和分数、旧规则是否选中、分层规模、缺失材料与解析错误、候选重叠率、本地处理耗时。旧审计文件只能统计大类规则及命中字段；重新提取提交才能分析具体命中片段。

产物建议为 `manifest.json`、`features.jsonl`、`ranking.csv`、`audit_summary.json`。这些文件名是拟议接口，目前没有对应新增命令；脚本实施后再给出服务器运行命令。

### B. 有限人工标注，先检验方案是否值得继续

建议起步分两批各 100 条，实际规模依人工时间调整：

- 开发批：用于修正词表和权重。
- 独立验证批：规则固定后使用，不再据此调整并在同一批报告成功。

覆盖旧候选的高/中/低分、文本和源码信号分歧项、原规则未选中项；配额取决于 A 的总体分布。每个随机层记录总体数量、样本数和入选概率。已有源码案例用于功能回归，不混作全新独立样本。

第一轮样本用于可行性判断，不能据此保证高召回率。若正例太少，应扩大随机验证样本或收窄并声明研究范围，而不是只追加高分正例后宣称总体有效。

人工尽量先看原始材料、再看模型标签。证据不足保留待定；抽样双人检查和分歧裁定，不能把模型一致性当作独立真值。

### C. 对照与指标

在同一份已标注验证池上比较：随机顺序、关键词分数、字段/交互改进分数、再加入边界/历史线索的分数。比较对象、预算和候选范围保持可比；多次随机种子报告波动。

- 离线：前 K 条中的确认相关提交数、去重案例数，以及低关键词正例的找回情况。池内 recall@K 只有在该验证池标签完整时计算，并明确不是两年总体召回率。
- 端到端：通过现有短判定后最终找到的确认案例数、错误排除的人工正例、待定/失败数；记录输入/输出 token、请求数和人工耗时。
- 补充总体盲点检查：原规则未选中层和低分层随机抽查中的相关比例、样本量及不确定性。不能把被排除集合中的正例比例直接称为全部缺陷的漏报率。
- 成本同时包含多阶段扩充、重试和不同实验目录的累计消耗。先离线比较排序，再对小批样本运行短判定，不默认批准每种方案各跑一轮全量模型。

未给出允许的漏报风险、独立人工标签和验证结果之前，不启用自动硬排除，也不制定“连续若干条负例就停止且已经找全”的保证。

## 5. 建议实施顺序与验收

1. 确认研究范围与 RISC-V 场景；按上面的代理口径处理日期，未知不补造。
2. 扩展详细分析模型、协议、渲染和 CSV/JSON 汇总；新增结构化字段模块，与通用七项性质分开。计划升级详细报告 schema，使用新输出目录，不覆盖旧实验。
3. 补充 Git 事件日期及本地邮件日期证据；日期间隔由程序计算。测试未知、缺字段、时间矛盾、多架构/多子系统、横向纵向并存及无横向影响的合法情况。
4. 在现有复核清单上接入短判定的成功/待定/失败和原规则未选中样本；支持独立人工结论与确认案例统计，保留模型原始结果。
5. 提供纯离线的特征审计、排序和冻结抽样脚本，由用户在服务器运行 A；据分布确定 B 的人工配额。
6. 根据独立验证结果决定是否值得增加历史/源码特征，是否安排 C 的小批付费试验。初筛的并发、预算和证据保护继续复用，暂不改变模型及现有筛选标签的含义。

当前不需要全量重跑、部署新模型或开展完整内核硬件实验。优先把报告口径、人工证据和离线排序实验接通，再决定研究方法是否有效。
