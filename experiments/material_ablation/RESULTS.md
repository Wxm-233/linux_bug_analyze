# DeepSeek 短判定材料压缩对照（2026-09-23）

目标是缩短模型判断时间与 token，同时保留研究所需的跨架构语义案例。先从已完成的第一批 275 条中冻结 80 条挑战集：高 30、中 25、低 15、旧规则未入选两层各 5；其中包含此前逐条源码抽查的 26 条。按旧模型标签选入相关 22、不确定 24、不相关 34，故这组样本专门用于发现判断变化，**不是总体相关率估计**。模型均为 `DeepSeek-V4.1-Flash`、4 并发、同一完整提交；三种新配置各有独立输出目录、最多 130 次请求和 600,000 token 预算。实际均完整处理 80 条、无待处理项。

| --- | ---: | ---: | ---: | ---: | ---: |

第一批原配置的 80 条是从 275 条混合并发运行的账本中提取的，**没有这 80 条单独运行的墙上时间**。三个新配置的模型阶段分别用时约 83.5、53.7、54.3 秒，受服务端负载和顺序影响，不能由此计算相对原配置的端到端提速。命令在模型阶段计时前还会读取 Git 提交、补丁并计算 patch-id；这些时间也未计入表中。token 差异是真实账本读数，但模型输出具有随机性且每配置只运行一次，标签变化不能全部因果归于所删材料。

逐条看变化后，当前三个方案都不适合替代默认配置：

- 去掉研究文档和简版摘要确实节省约一半 token，但分别改变 26、17 条标签。两者均把原判相关的 RISC-V XIP/alternative 配置案例 `c80ee64a8020` 改判不相关；此案例是否纳入研究范围尚未由领域人员裁定。两者都将先前源码抽查支持排除的 perf powerpc 新增解析案例 `06dd4c5a561c` 判为相关，简版摘要还把单驱动位图容量问题 `359414b33e00` 判为相关，显示排除边界不稳定。
- 首轮压缩补丁上下文只省 5.14% token，却有 11 条原保留项变不相关。尤其 `12aab25ca56e` 的提交说明明确说 Device MMIO 访问顺序违背软件与驱动依赖的保证，原配置和助手源码复核均保留，关键片段版却以“仅是单架构硬件勘误、公共代码无隐含依赖”为由排除。已知 IIO 字节序案例 `81d5a5366d3c` 在去文档/简版摘要配置中由原配置的漏保变为相关，但在关键片段版中仍被排除；不能因某一个案例被纠正就忽略其他错漏。
- 简版摘要仍将 SCMI 无完成中断能力描述 `0c5453bf8437` 由不确定改判不相关；这类 binding/能力描述本就需领域人员裁定范围。相关、待定和误保同时变化，不能只用整体保留数衡量质量。

**决策：不改变正式短判定默认上下文和补丁材料，也不在这些压缩配置上继续付费测试 8 并发。** 原计划把并发试验放在材料质量没有明显退步之后；关键片段版已发生源码抽查支持的漏保，而上下文版标签漂移与误保明显，前提未满足。现有实验选项留在 CLI 中便于复核，默认值保持原配置；不能把这些输出混入正式筛选结果或据单次对照宣称模型准确率变化。下一步需要领域人员先裁定架构内部能力限制、测试/文档和准备性改动的范围，并建立独立、人工标注的验证集，再决定是否以输入压缩换取成本下降。

复现文件位于 Git 忽略目录 `analysis_out/material-ablation-20260923/`：`manifest.json`、`sample80.txt`、三个配置的逐条结果和 `usage.json`、`comparison.json`、`label_changes.tsv`。冻结和比较脚本为 [freeze.py](freeze.py)、[compare.py](compare.py)，简版研究摘要见 [compact_context.md](compact_context.md)。运行时使用新的输出目录及对应 `--context-mode task-only`、`--context-file` 或 `--material-mode key-hunks`；三者均未更改原配置默认值，也未调用 GLM/Gemini 或生成完整分析报告。
