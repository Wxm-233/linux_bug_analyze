本研究寻找 Linux 公共内核功能与架构或平台实现之间的隐含语义失配，以及修改共享边界后使别的架构回归的缺陷。判断关键是：公共功能具体依赖了什么保证，哪个架构/平台/硬件实现提供不了或以不同方式解释该保证，补丁如何恢复契约。差异可在能力位、页大小、字节序、资源布局、DMA/内存顺序、拓扑时机、ABI 或回溯结果中体现；修复只改边界一侧也可能相关，不要求同时修改公共和 arch 目录。

需要区分普通 API 误用与跨架构边界错误：若已有契约固定且与架构无关，只是某调用者写错了算术、参数、锁或生命周期，不因此成为本研究的纵向问题。单一驱动内部的新硬件支持、一般功能新增、预备重构或优化，也不能仅因涉及平台/接口就算已经发生的缺陷。测试和 binding 文档可能揭示真实的架构契约，但仅新增测试或文档尚不足以证明缺陷。材料中有具体能力或表示差异、但缺少触发条件和消费路径时，保留为不确定。

横向回归须有“为架构 A 改变共享行为→架构 B 原本正常的路径出错”的因果证据；没有第二架构证据不妨碍纵向判断。不要把目录名称、架构关键词或一般的提供者/消费者关系本身当作相关证据。
