# 约定级建模试点二：“KVM代客户机写内存必须标脏”

## 这一轮要回答什么

试点一证明“先列位置、再逐位置核对”能覆盖已知违反，但没有找到新问题。试点二换一条更可能发现问题的约定，检验这个方法能否找出新问题。

- **约定D**：KVM不经过客户机的二级页表映射、直接替客户机写客户机内存时，必须把被写的页（按**客户机页号**）在内存槽中标为脏；否则热迁移时会漏拷这些页。
- 判据：`criteria.md`（SHA `b2d98b73…`）。全部为人工阅读，不调用模型，不构建内核。

## 第一步：实现位置的分类与清单

**先核实公共写入函数**（终点版本`virt/kvm/kvm_main.c`）：
- `__kvm_write_guest_page`和`kvm_write_guest_offset_cached`都在写后调用`mark_page_dirty_in_slot`，所以`kvm_vcpu_write_guest`、`kvm_write_guest`等都会自动标脏；
- `kvm_vcpu_unmap`在解除映射时也会标脏。

因此只有**直接写**（W类）需要调用者自己标脏：先取得客户机内存的宿主机地址，再用`put_user`、`copy_to_user`等写入。

**RISC-V KVM（终点版本）的全部代写位置**：在`arch/riscv/kvm/*.c`中检索地址获取函数与写入函数，共命中约40处，逐个阅读后：
- 绝大多数是ioctl把数据拷给用户态（`copy_to_user(uaddr, …)`、`put_user(reg, uindices)`），写的不是客户机内存，不适用；
- `mmu.c`中的两处标脏，是客户机自己经映射写入时，缺页处理代为记录，不属于“代写”；
- `vcpu_exit.c`的`gfn_to_hva_memslot_prot`和`vcpu_sbi_system.c`的`kvm_vcpu_gfn_to_hva_prot`只是查地址、做检查，不写入，不适用。

真正代写客户机内存的有5处：

| 位置 | 方式 | 结论 |
| --- | --- | --- |
| `vcpu_pmu.c` 464、527、731行：PMU快照与事件信息写回 | H类，`kvm_vcpu_write_guest` | 满足 |
| `vcpu_sbi_sta.c` 113行：steal time区域清零 | H类，`kvm_vcpu_write_guest` | 满足 |
| `vcpu_sbi_sta.c` 47–78行：记录steal time | W类：`kvm_vcpu_gfn_to_hva`取地址后`put_user`三次，最后`kvm_vcpu_mark_page_dirty(vcpu, gfn)`，`gfn`由客户机地址算出；第一次写失败时提前返回，此时尚未写入任何内容 | 满足 |

## 第二步：已知违反的覆盖

按事先写定的条件检索`v5.0..df2908090cda`：改动`arch/`、带`Fixes:`、说明涉及脏页、改动中有`mark_page_dirty`。

**实现修正**：第一次检索时，`-G`的写法带上了改动行开头的`+`号，而`-G`匹配的是改动行的内容本身，所以结果为空。修正后重跑，判据未改。

检索到2条，读后都属于约定D被违反：

| 修复 | 内容 | 位置类型 |
| --- | --- | --- |
| s390 `898885477e0f` | 适配器中断的指示位直接写入后，标脏时传了宿主机地址算出的页号，而不是客户机页号；`mark_page_dirty_in_slot`找不到内存槽时静默不做事 | W类，标脏的对象错了 |
| x86 `910c57dfa4d1` | 模拟原子指令时，KVM经宿主机地址做cmpxchg写客户机内存，没有标脏；标脏还必须放在判断成功与否之前，因为失败时也会写回旧值 | W类，漏标 |

**覆盖2/2。** 按事先标准，方法有效，但只有2个已知违反，样本很小。

这两条还给RISC-V的核对补充了两个细节：标脏要用**客户机页号**；**写失败也要标脏**（如果确实写过）。RISC-V的steal time两点都满足。

## 第三步：结果

RISC-V的5处代写全部满足约定D。**按事先标准，“能找到新问题”为0。**

**旁证（事后观察，不计入判定）**：RISC-V在2026年3月的修复`fa9681ed`，要求经`KVM_SET_ONE_REG`设置的steal time共享内存地址按64字节对齐。修复前，若用户态设了一个靠近页末的不对齐地址，steal time结构就会跨页，而代码只按第一个页号取地址和标脏，第二个页既写错位置，也不会被标脏。这个历史问题与约定D相邻：代写的范围必须落在被标脏的页内。

## 两个试点合起来看

| | 试点一（脏页记录期间页粒度） | 试点二（代写须标脏） |
| --- | --- | --- |
| 实现位置 | 4个，沿公共钩子和参照架构的缺页处理列出 | 5处，沿公共写入函数和直接写的方式列出 |
| 已知违反的覆盖 | 5/5（留出2/2） | 2/2 |
| RISC-V当前代码 | 全部满足 | 全部满足 |

- **方法的覆盖面得到两次验证**：只要位置列全，已知的违反都落在清单里。上一轮单位置规则漏掉的，正是清单中的其他位置。
- **这两条约定上，RISC-V当前没有问题。** 两个试点都没有找到新问题，原因可能是：这两条约定都已经被其他架构“踩过坑”，RISC-V的实现较新，也修过同类问题（试点一中的两次修复，以及上面的旁证）。
- **下一步要找新问题**，应该选RISC-V实现较新、其他架构也刚出过问题的约定，也就是机制目录中M8（落后于参照对象的演进）与M10交叉的地方。这与案例分析中“参照对象的同名函数后来又修过什么”的检测思路一致。

## 统计

不调用模型；构建0；新确认缺陷0；新疑点0。
