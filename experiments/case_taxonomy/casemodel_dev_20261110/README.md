# 用例模型（casemodel_dev_20261110）

## 这一轮要回答什么

前三轮里，静态分析已经把测试引到了有问题的地方，但动态检出始终只有 A310、A171 两条。A101、A181、B467 都卡在构造不出合法的输入：
- 随机 flags 很少合法；
- `msghdr`、`perf_event_attr` 这类结构体参数只能靠随机缓冲区碰运气；
- 需要先建资源的参数（IPC 标识符、定时器、aio 上下文）几乎总是无效。

这一轮加入三项通用的用例模型改进，判据 `criteria.md` 在实现之前写定：

| 编号 | 改进 | 做法（举例） |
| --- | --- | --- |
| C1 | 结构化参数 | 参数指向结构体时，用 libclang 读出每个架构上的布局，再按布局填：<br>· 指针字段指向子缓冲区（`msghdr.msg_iov` → 一个 `iovec`）；<br>· 长度字段填子缓冲区长度（`msg_controllen`）；<br>· 名为 `size` 的字段填结构体大小（`perf_event_attr.size`）；<br>· 其他字段默认 0，随机改 1～2 个 |
| C2 | 取值词表 | 从静态事实里收集每个参数被怎样比较：`==` 的常量、`switch` 的 `case` 值、`&` 掩码的位。例如 `futex` 的 `op` 收到全部 17～18 个命令值 |
| C3 | 资源准备 | `msqid` 先 `msgget`，`timer_id` 先 `timer_create`，`ctx_id` 先 `io_setup`；新增 epoll、timerfd、signalfd、inotify、pidfd、perf 软件事件等 fd；每个用例后清理 IPC |

三组同预算（1000 用例 × 3 种子），都用 C1–C3：
- **G0m**：均匀分配；
- **G2m**：上一轮排序后的前 40 个系统调用；
- **G3m**：前 40 个系统调用，加提示。

## 我做了什么

1. **执行器 v2**（`harness/sh_init2.c`，由 `patch_exec.py` 对上一版打补丁，我自己写）：
   - 用例行末尾可以带结构化缓冲区的定义；
   - 新增记号 `t:<k>`、`x:<资源>`，以及 7 种新 fd；
   - 结构化缓冲区和子缓冲区都参与观测。
   
   自测 19 条（期望先写在 `harness/selftest/expected.md`），三个架构全部符合。例如结构化的 `recvmsg` 三个架构都收到 16 字节、控制缓冲区都改写 48 个位置。

   - 1 个是 `msgrcv` 以前阻塞在前面用例残留的消息队列上，现在每个用例后清理 IPC，它不再阻塞。
   
   判据写的“完全相同”过严，经你同意写修订 2，按修订后的口径回归通过。
3. **静态侧**：抽取器补记 `switch`（`static/extract3.py`），重抽 6 棵树；写结构体布局探测 `static/layouts.py`（每组约 56～59 个根类型，找到 47～51 个）和词表 `static/hints4.py`、`static/vocab.py`（覆盖约 300 个系统调用、700 多个参数）。
4. **生成与运行**：`gen/generate_m.py`，每组约 8300～8500 个用例，其中约 1800～2200 个带结构化参数；23 个内核各跑 3 次，共 69 次，用时 16 分钟，全部完整。

（表中数字是检出该缺陷的种子数。）

- **A181 第一次被检出**（G2m 种子 1，用例 3179）：
  - 用例：`recvmsg(udgram, 结构化 msghdr, 4)`，`msg_iov` 指向一个 `iovec`，`msg_control` 指向一块起点错开 1 字节的缓冲区；
  - 结果：修复前 riscv 的控制缓冲区被改写了 12 个位置，修复后和两个参照都是 9 个；
  - 解释：这正是 A181 的症状，地址不对齐时 `put_user` 写错了 `cmsg_len`。修复前后的内核只差这一个修复提交。
- **A101**（G2m 种子 2）：
  - 一个用例和第一轮相同，是区间模板的 mmap 暴露的；
  - 另一个是 `mmap`：修复前在找空闲区间时就返回 ENOMEM，修复后和参照走到映射类型检查，返回 EINVAL。
- **G0m 第一次检出了东西**（A171，2 个种子；第一轮 G0 是 0），说明用例模型本身有作用。
- **按事先写定的参考线，“用例模型有增益”不成立**：参考线要求 G3m 合计大于 G3r 的 6，并且新检出一条缺陷、至少 2 个种子。G3m 正好是 6；新检出的 A101、A181 都出现在 G2m，而且各只有 1 个种子。

### 当前版本：19 个与众不同的聚类，疑似失配 0 个（`manual_review_current.json`）
- **测试自身问题 11 个**：
  - 10 个是同一个原因：通用取值里的小整数（0x10000、0x2003a、0x400009 等）当作地址用时，在 riscv 上正好落在静态测试程序的映像里（riscv 加载于 0x10000，arm64、x86 加载于 0x400000），一边可读，一边未映射；
  - 1 个是 `get_robust_list` 写回地址；
- **环境/能力 4 个**：cpumask 大小 3 个；`F_GETOWNER_UIDS` 需要 `CHECKPOINT_RESTORE` 1 个；
- **riscv 合法差异 2 个**：sv57 地址空间更大、调用号位宽；
- **判断不了 2 个**：rseq；`CLOCK_BOOTTIME_ALARM`（推测 QEMU riscv 机器缺 RTC，未验证）。

## 看出的几点

1. **用例模型确实打开了新的缺陷。** A181 卡了四轮，靠结构化参数第一次被检出；G0m 也第一次有了检出。这说明瓶颈判断是对的。
2. **但随机组合多个条件，命中概率是相乘的。**
   - A181：`recvmsg` 的 139 个用例里，fd 恰好是带控制消息的数据报套接字的只有 3 个（fd 有 17 种）；
   - B467：要 `size` 正确、只改 `type`、`group_fd` 为 −1、flags 为 0 同时成立，概率太低。
   
   下一步应该改成**“合法基础用例＋单点变异”**：每个系统调用先有一个各参数都取最常见合法值的基础用例（fd 取与该调用匹配的类型、结构体各字段合法、flags 为 0），然后每次只改一个参数或一个字段。
3. **提示（G3m）这次没有比只定向（G2m）更好**：G3m 每个种子都检出 A310、A171，但新缺陷都出在 G2m。提示取值占用了一半概率，挤掉了用例模型的取值。两者怎么配额，需要专门设计，而不是简单地各取 1/2。
4. **测试程序的加载地址应该在三个架构上统一**：例如把 riscv 的静态程序也链接到 0x400000，或者全部改成位置无关加载。这能一次消掉一大类“测试自身问题”。

## 局限

- 开发集，数字很小；A101、A181 各只在 1 个种子里出现，可能是偶然。
- A181 的检出用例是全 0 填充，与我事先写的关键条件不符。我没有改条件，如实记录。
- 结构体逻辑按 riscv 布局决定；内嵌结构体、数组、位域字段不填（例如 `recvmmsg` 的消息头内嵌在 `mmsghdr` 里，没被填写）。
- 前几轮的 B467 诊断条件里，“pid 为 −1 且 cpu 为 0”这一支因为 32 位的 −1 没处理而永远匹配不上；只影响诊断计数，不影响检出判定。本轮已修正。
- 本轮没有新建内核。
