# 32个分歧的规则裁定（裁定前写定，2026-10-29）

用户授权“按规则裁定”。规则如下：

1. 同一迁移中的不同错误按指南记“部分”；
2. function_graph_enter系列按“同一修复驱动的逐架构转换”记“是”；
3. 其余8对逐条写理由。

裁定后由用户抽查。裁定者为Claude，同时也是两位标注者之一，这一点在论文中如实写明。

## 规则1：否↔部分的13对 → 部分

S013、S019、S052、S054、S060、S069、S076、S090、S097、S098、S099、S101、S102

这一组是两位标注者在“相关但不是同一缺陷”与“无关”之间的分歧。按授权规则统一记“部分”。以下三对**建议抽查**：

- **S090**：A标部分、B标否。B的理由是s390原本已有锁，T只是把锁移交给公共层，比较有说服力。
- **S102**：T只删除riscv的一条过时注释，不是缺陷修复。
- **S076**：B自己也说明是保守地标为部分，没有证明MIPS受同一回归影响。

## 规则2：function_graph_enter系列11对 → 是

S022—S032：各架构的prepare_ftrace_return逐个改用function_graph_enter()，属于同一修复驱动的逐架构转换。

## 其余8对：逐条裁定

| 编号 | A | B | 裁定 | 理由 |
| --- | --- | --- | --- | --- |
| S037 | 是 | 部分 | **是** | 两者都删除泄露内核地址的日志（x86 realmode trampoline与arm64 vDSO），标题都是“不要泄露内核地址”，属于同一信息泄露问题在不同架构上的修复，而不只是清理 |
| S041 | 是 | 部分 | **是** | T明确沿用arm64的做法删除ARM vDSO的地址日志，与S是同一问题 |
| S047 | 是 | 部分 | **部分** | S加入的是mmap锁断言，并没有在其他架构补锁；openrisc页表遍历缺锁是原有问题，被S的断言暴露。T不是S本身漏掉的那一处，按“从引入点出发”规则不记“是” |
| S067 | 是 | 部分 | **是** | 两者针对同一条要求：BPF_PSEUDO_FUNC的地址只在额外遍历中才确定，JIT必须保证它在最终代码中正确（arm64用固定长度，powerpc在额外遍历中重生成）。补救方式随架构不同，要求相同 |
| S075 | 是 | 部分 | **是** | 同S067：powerpc与riscv对同一条BPF_PSEUDO_FUNC地址要求的各自补救 |
| S091 | 是 | 部分 | **是** | 公共层改动后，high_memory须由架构正确设置；x86-32恢复早期初始化，s390设为直接映射的末端，是同一要求在两个架构上的满足 |
| S033 | 否 | 是 | **是** | S为无PCI配置提供了通用的pcibios_penalize_isa_irq桩，T删除h8300与之冲突的本地定义，正是S的通用化在h8300上漏做的适配。A当初看漏了这一联系 |
| S073 | 否 | 是 | **部分** | S修的是在follow_pte前完整校验VMA（s390），T修的是没有VMA时遍历内核页表须持写锁（riscv与pagewalk）。两者都关乎页表遍历的安全，但不是同一项修复 |
