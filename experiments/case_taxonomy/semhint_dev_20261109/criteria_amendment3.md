# 修订 3：实现细节（生成正式用例之前写定）

2026-11-09 19:50，Claude。此时已完成：6 棵树中部分的静态抽取、A101 组的提示合成（我看过它的统计：326 个入口、129 个系统调用有提示点、mmap 没有提示点）、执行器自测（只用手写的 31 个自测用例）。**还没有生成正式用例，没有在任何被测内核上运行正式用例。**

1. **系统调用号**（第五节“全集 U”）：各架构的编号取自三个交叉工具链的 `<asm/unistd.h>`（系统调用号是稳定的 ABI，同名调用编号不随版本变化）。工具链头文件比被测内核旧，个别新调用（如 `mseal`、`setxattrat` 系列）没有编号，这些调用不进 U，逐个列在 `gen/cases_<组>.json` 的 `excluded.no_number` 里。
2. **用例独立性**（第五节“彼此独立”、第六节“重建 /tmp/f、/tmp/d”）：执行器在每个用例之前把 `/tmp` 换成一个新的空 tmpfs，再由子进程重建 `/tmp/f`、`/tmp/d`。这比判据字面更严，目的是不让上一个用例建的文件影响下一个。SysV IPC、密钥环等内核全局对象无法这样清理，作为局限写进 README。
3. **守卫的“错误出口”**（第 4.2 节）：实现为 then 分支含 `goto`，或其记号中出现“`-` 后接 E 开头的全大写标识符”（覆盖 `return -EINVAL`、`err = -EINVAL`、`return ERR_PTR(-EINVAL)` 等写法）。
4. **执行器**由 Codex 按我的规格编写（`harness/`），自测由我补做。Codex 在写自测时被 OpenAI 的安全过滤中断，没有参与生成和判定。我对它的代码做了两处修改：上面第 2 条，以及 `parse_log.py` 对单个用例准备失败只记录、不使整份日志作废。
5. **内核崩溃**：判据没有规定。若某次运行在中途出现内核崩溃（日志里没有 `@@SH END`），我记录最后一个完成的用例编号，把它的下一个用例记为“导致崩溃”，从再下一个用例起续跑，三次运行都这样处理；“导致崩溃”作为一种结果参与比较。

其余判据不变。
