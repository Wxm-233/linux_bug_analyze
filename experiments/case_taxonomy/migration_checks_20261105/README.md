# 由程序执行迁移的两项检查

## 这一轮要回答什么

历史回放实验（`replay_migration_20261105/`）发现：
- 迁移补丁的主要错误是**漏改一部分**和**照搬了在目标架构上前提不成立的做法**；
- 把两项检查写进提示，模型不照做；
- 迁移后的模型审查能发现漏改（9/13），但照搬前提一类完全发现不了（0/7）。

本轮把两项检查改由程序执行，再把程序的标记和收集到的目标架构事实交给模型审查（第3版，L3），看能发现多少。

**性质说明**：检查是看了这批补丁的错误之后设计的，在这批补丁上的结果是**调参，不是独立评估**。为减少过拟合，每项检查都按机制写成通用规则，并用42个真实补丁作阴性对照。

| 文件 | 说明 | SHA |
| --- | --- | --- |
| `criteria.md` | 判据，实现之前写定 | `9e99693c…` |

## 程序检查了什么

| 检查 | 内容 |
| --- | --- |
| C1a 构建条目 | 新增或改名的源文件，所在目录的Makefile中有没有对应的`.o`，旧名是否还留着 |
| C1b 签名变化后的调用点 | 函数参数个数改了，仍按旧个数调用它的位置 |
| C1c 替换不彻底 | 补丁把`旧函数(实参)`改成`新函数(实参)`，别处还剩`旧函数(同样实参)` |
| C1d 参照覆盖 | 参照补丁改了的函数，目标架构有同名函数而补丁没改；或参照新增了覆盖公共`__weak`默认实现的函数，目标架构没有 |
| C2a 分配与释放配对 | 补丁新增的释放调用，与同一对象的分配调用是否配对（例如`kvcalloc`要配`kvfree`） |
| C2b 接口签名 | 定义的函数与公共代码中的声明，返回类型、参数个数是否一致；公共代码中没有任何声明的`arch_*`钩子 |
| C2c 目标架构事实 | 不判断真假，只收集：C2a找到的分配语句、新调用的公共函数的原型、新用到的结构成员的定义 |

## 结果

### 1. 程序检查

| | 修法“部分/不同”的20个生成补丁中指出了出错原因 | 漏改 | 照搬前提 |
| --- | ---: | ---: | ---: |
| 程序检查 | 9 | 6/13 | **3/7** |

- **查出的**：
  - A028两个补丁没加进Makefile的新文件、仍引用旧名的`.o`（C1a）；
  - A018没跟着改的5个调用处（C1b）；
  - A103、A104、L121中参照改了、补丁没改的函数（C1d）；
  - **L147两个补丁“用`kfree`释放`kvcalloc`分配的内存”**（C2a）；
  - **L132把钩子写成`void`，而公共代码声明为`int __must_check`，并定义了公共代码中已不存在的`arch_unprotect_bpf_trampoline`**（C2b）。
- **没查出的**：
  - V011漏改的`cond_resched_lock(&gstage->kvm->mmu_lock)`，与补丁中替换的写法不同，按文字匹配找不到；
  - A025、A109漏掉的内容与参照补丁的函数名对不上；
  - L128的`char`/`short`符号扩展、A060的做法差异，通用规则表达不了。
- **阴性对照（42个真实补丁）**：13条标记，全部不成立，平均每个补丁0.31条，超过0.2的参考线，记为“误报过多”。来源：
  - C1d的“同名函数没改”太宽，8条（参照补丁顺带改的函数，目标架构不一定要改）；
  - C2b把`__must_check`、`__no_sanitize_address`等属性当成了返回类型，3条；
  - C1c把函数改名误当成替换，1条；
  - C2b把汇编调用的内部函数当成“没有声明的钩子”，1条。

  在42个生成补丁上，同类不成立标记共7条。

### 2. 模型审查第3版（L3，42次调用）

| | L2（回放实验） | **L3（加程序检查结果与事实）** |
| --- | ---: | ---: |
| 修法“部分/不同”的补丁中指出出错原因 | 9/20（45%） | **11/20（55%）** |
| 其中漏改 | 9/13 | 8/13 |
| 其中照搬前提 | 0/7 | **3/7** |
| 修法“同”的22个补丁上的不成立标记 | 2条（事后更正后） | 0条（另有1条三点合写、其中一点不成立） |
| 修法“部分/不同”的补丁上的不成立标记 | 0条 | 1条 |

- 按参考线：
  - **“前提事实有帮助”达到**（0/7 → 3/7）：L147两个补丁都引用了程序给出的`ctx.offset = kvcalloc(…)`，L132引用了公共声明`int __must_check`；
  - **“程序检查有帮助”没有达到**：55%低于60%的参考线。
- **少了一个**：L121（条件S）的补丁是空的，L2指出了，L3没有报告任何问题。
- **没有因为程序的误报而多报**：程序在生成补丁上给出的7条不成立标记（如A060的`flush_tlb_kernel_range`、L132的`arch_alloc_bpf_trampoline`），L3都没有采纳，只有一条与程序标记无关的不成立问题。
- **仍然查不出的**：L128（`char`/`short`）、A060（做法完全不同）、A025、A109的漏改。这几类需要的事实，程序目前给不出来：参照补丁之外还有哪些情况要处理、目标架构的真实修法是什么。

### 3. 对上一轮的一处更正

回放实验中，我把检测对A103（条件S）报出的第2条“漏了`bpf_jit_inlines_helper_call()`的改动”判为不成立，理由是真实补丁也没有加。这是错的：真实补丁在该函数中加了`BPF_FUNC_get_smp_processor_id`。生成补丁本身写了这一改动，但hunk头没有行号，应用后没有落进去，所以对应用后的代码该条成立。L2在修法“同”的补丁上的不成立标记因此由3条改为2条。详见`l3_judgement.json`。

## 看出的几点（只作描述）

- **由程序收集目标架构的事实，能让模型发现照搬前提不成立的问题**：这一类从0/7提高到3/7，而且三个都是程序直接给出了关键事实（分配方式、公共声明）。这与第一部分复核中的经验一致：模型的判断上限取决于它能看到哪些事实。
- **程序检查本身已能查出近一半的问题，但误报过多**：最主要的误报来源是“参照补丁改了同名函数、目标没改”这一项。下一步可以只在参照补丁的核心改动（与说明中的问题直接相关的函数）上做这项检查，并修正属性解析。
- **两者的结合比各自都好**：程序标记加模型审查，查出11/20；程序单独9/20，模型单独9/20。而且模型没有照搬程序的误报。
- **剩下的问题需要另一类事实**：参照补丁本身就不完整，或者目标架构的正确做法和参照不同。这已经超出“迁移检查”能给的事实，需要从目标架构的历史修复或其他架构的同类修复中找依据。

## 局限

- 检查是看了这批补丁之后设计的，结果不是独立评估；独立评估要等新的回放样本。
- 核对由我一人完成。
- 每个补丁只审查一次。
