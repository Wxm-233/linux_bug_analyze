# 方法M4设计登记：程序定位变化点＋模型写要求＋事实判定（设计，实现前写定）

2026-10-28。用户选择“Model + program facts”，要求先登记设计。**本文件只登记设计与验证计划，不含实现，不调用模型，不选样本。**

## 1. 动机（来自已有结果）

- E1（模型自由提候选）：die、shmem回放断在E1；补提供者定义（M1）后模型看到了信息仍选别的接口——瓶颈是**开放式候选选择**。
- E4（程序检查族）：评价集C的5个跨架构真修复全部漏检，分属五种机制（配置开关行为、修复新增钩子、运行时值对上限、预定义宏对Kconfig、字长）——瓶颈是**模板覆盖面**。
- 事实层与核心在已知缺陷上有判别力（宏来源、取值、优化后行为、Kbuild适用性）。

M4的分工：**程序决定“看哪里”和“能用什么事实”，模型只决定“这里要求什么”，判定由程序完成**。

## 2. 程序：变化点枚举（site enumeration）

对修复触及的每个非`arch/`、非`tools/`/`scripts/`/`samples/`的`.c`消费者文件，在父版的追踪上下文（x86_64、arm64、s390 defconfig＋守卫配置，同M1/M2）上，枚举以下五类**变化点**，每个变化点记位置（文件:行范围）与类型：

| 类型 | 程序判据 | 对应的已知漏检 |
| --- | --- | --- |
| V1 架构相关宏使用 | 消费者使用的宏，其展开链在追踪上下文间来源或文本不同（M1 `select`） | die、shmem |
| V2 架构/特性条件块 | 预处理条件含`CONFIG_<ARCH>`（如`CONFIG_S390`、`CONFIG_X86`）、`__HAVE_ARCH_*`/`ARCH_HAS_*`、编译器架构预定义宏（`__x86_64__`、`__i386__`、`__aarch64__`…）、`BITS_PER_LONG`、`CONFIG_64BIT` | s04、s15、s18 |
| V3 架构相关函数调用 | 调用的函数在追踪上下文间定义来源不同（`static inline`定义所在头文件不同，或某上下文仅有声明） | s07类钩子 |
| V4 几何/上限比较 | 代码中含比较运算的表达式，一侧含以`_ORDER/_SHIFT/_SIZE/_NR`结尾或含`MAX/LIMIT`的宏，另一侧为变量或另一宏 | shmem、s10 |
| V5 架构名分支 | `IS_ENABLED(CONFIG_<ARCH>)`等C层判断（非预处理） | s01 |

每个文件按类型优先级与出现次数截取至多16个变化点；超出记截断数。变化点枚举只用父版源码与追踪，不看修复。

## 3. 程序：每个变化点的事实词表

沿用已有查询（`macro_defined`、`macro_provided`、`macro_value`、`returns_only_zero`、`object_defines_token`、`kbuild_selected`），新增一种：

- **`expr_value(expr)`**：用取值探针（M2已实现的“编译`return (expr);`读优化后GIMPLE”）求变化点相关常量表达式在每个上下文的值，例如`IS_ENABLED(CONFIG_S390)`、`BITS_PER_LONG`、`MAX_ORDER`、`sizeof(long)`。非常量不答。

每个变化点由程序生成事实名与含义（值盲：给模型的是事实名、含义、类型，以及该点在各追踪上下文的**定义原文**，不给判定结果）。

## 4. 模型：为变化点写要求

- 每个样本1次调用（Kimi-K3.1-Pro-HighSpeed，参数同前，无自动重试）。输入：消费者代码中各变化点前后各20行、各上下文的相关定义原文（同M1格式）、每个变化点的事实词表。
- 任务：对每个变化点，判断是否存在“消费者对提供者/配置的隐含要求”；有则只用给定事实名写出`scope`与`relation`（v2 DSL，必要条件或完整），并给一句理由；无则写`none`。不得引用词表外的事实。
- 不提示任何缺陷、修复或标签；不给出“哪个上下文违反”。

## 5. 判定与复核

- 程序在父/修两版、7个判定上下文（同附录2 D）求事实并判定；scope另加`kbuild_selected`（同M3a）。模型的要求属`model_proposal`，核心判“不足”，须研究者复核后才判满足/违反；复核在方法输出保存之后、读修复内容之前，仅依据代码与要求本身判断忠实性（同前E1复核口径）。
- 观察分类与(a)—(d)复核、主线标注同附录2/3。

## 6. 验证计划（分三步，均须用户逐步同意）

1. **覆盖检查（只程序，不调用模型）**：在开发用例上检查变化点是否覆盖修复所针对的位置——die、shmem、s04、评价集C的s01、s07、s10、s15、s18（均已接触，只作开发）。事先不写命中预期，只报告每例是否有变化点落在修复改动的父版行±5行内及其类型。s07的钩子由修复新增，预期覆盖不到（其父版行为点可能落入V3或不落入）。
2. **开发回放（调用模型）**：在上述8个开发用例上各调用1次，报告模型是否为覆盖到的变化点写出“修复后满足、父版违反”的要求。开发用例结果不计评价。
3. **评价**：冻结方法后，从后备池按M3修正选样规则、新种子抽取未接触的评价集D（20个＋正常对照），每样本1次调用；同时以同一输入运行E1自由候选作基线（每样本1次）。报告命中、误报代理、复核成本与基线对比。

预算：步骤2约8次调用；步骤3约40次调用（M4与E1基线各20）。付费调用须用户在各步骤启动时另行授权。

## 7. 已知风险

- 变化点数量与质量决定上限：V1/V3在大文件中可能很多，截断会漏；V2/V5只看语法形态。
- 模型看到各上下文定义原文，可能“猜出”违反方，这本身是方法的一部分，但须报告复核前后的差异。
- s07这类“修复新增的钩子”在父版没有变化点，M4同样无法覆盖，记为结构局限。
