## 规则（简述）

**“不能睡眠”的场合**：
- A：RISC-V函数内的关中断、raw自旋锁、自旋锁、禁抢占区间；
- B：异常向量表中的陷入处理函数在开中断之前的部分；
- C：作为`stop_machine`或跨核调用回调的函数；
- D：公共代码在原子区间里调用的RISC-V钩子。

**“可能睡眠”的操作**：
- 互斥锁、等待、用户内存访问、`GFP_KERNEL`分配等；
- 跨核调用并等待，只在“硬”原子上下文（关中断、raw自旋锁、陷入入口）中计入；
- 沿调用链最多往下看3层；
- PREEMPT_RT下会睡眠的普通自旋锁，单独标为`rt`类。

**不可插桩约定**：
- N1：公共代码中的`noinstr`函数调用了RISC-V函数，而参照架构的同名函数标了`__always_inline`或`noinstr`；
- N2：RISC-V的`noinstr`函数调用了可插桩的函数。

**修订1**：在第一遍57个标记的基础上，修改了以下几处，标记降到27个：
- 持锁或禁抢占时的跨核调用不算违规；
- 早期启动（`__init`函数中的区间）不作为来源；
- 不沿入口框架函数往下查；
- 忽略`mm/highmem.c`；
- 排除循环宏被误识别成函数的情况；
- N1要求参照架构的证据。

整个检查约10秒完成。

## 结果

**开发集**（只用于调试）：M5两条中命中A344（未对齐陷入中关着中断访问用户内存）。A327属于早期启动，按判据不在范围内。

**测试集**（冻结后只算一次，`scores_test.json`）：

| | 结果 |
| --- | --- |
| 测试集M5命中（/6） | **2**：A118、A175 |
| 测试集全部命中（/51） | 3：A118、A175、A202 |
| 标记总数 | 27 |

**命中的原因是否一致**（第一标注人核对）：
- **A118，一致。** 标记指出`die()`在关中断的陷入处理中获取普通`spinlock_t`，PREEMPT_RT下会睡眠；真实修复（`6a97f4118ac0`）正是把它改成raw锁。
- **A175，部分一致。** 标记指向同一批陷入处理函数、同一类问题：关中断时获取RT下会睡眠的锁。但具体路径是`die()`，而真实修复说的是用户态陷入中的`force_sig_fault()`，修法是开中断。
- **A202，不一致。** 标记是noinstr约定问题，真实修复是对非当前任务的栈关闭KASAN检查，两者只是落在同一函数上。

**人工核对**（全部27个标记，`manual_review.json`）：

| 归类 | 标记数 | 对应的不同问题 |
| --- | ---: | --- |
| (a) 疑似真问题 | 14 | **3个**：<br>① `die()`在关中断的陷入处理中拿`spinlock_t`，9个标记，上游已修，即A118；<br>② 未对齐陷入中关着中断访问用户内存，4个标记，上游已修，即A158、A344；<br>③ `machine_shutdown`关着中断调用可能睡眠的函数，1个标记，本项目已在QEMU中确认 |
| (b) 不是 | 4 | 例如`console_unblank`在oops期间不会拿锁；`flush_tlb_all`在只有一个CPU在线时走本地路径；ftrace只有在允许睡眠时才调用`cond_resched` |
| (c) 判断不了 | 9 | 主要是noinstr约定类，例如`regs_irqs_disabled`在x86上是`__always_inline`，RISC-V后来也改成了`__always_inline`，但那次修改没有`Fixes:`标签 |

**之后是否被修**（参考，按行范围对应，`later_fixed.json`）：
- 被标记的函数中，5/14（36%）之后被`Fixes:`提交改过；
- 未标记函数的抽样中，这个比例是35/200（18%）；
- Fisher p=0.15，差异不显著。

**按判据判定**：
- 测试集M5命中2条，要求不少于3条，**未达到**；
- 人工核对(a)类占52%，要求不低于25%，满足。
- 两条须同时满足，所以**本轮未达到成功标准**。

## 事后分析（只作描述，不计入指标）

1. **A158其实被标出来了，但没算上。**
   - 修复改动的`handle_scalar_misaligned_load`，是在快照`v6.12`之后才由重构改名得来的；在`v6.12`中这段代码叫`handle_misaligned_load`。
   - 检查器的标记9、11、13、15正指向它：关中断时访问用户内存。
   - 判据规定按函数名对应，所以不计。如果按行范围对应，测试集M5会是3/6。这与机制扫描轮得出的教训相同：**事后评估应该按行范围对应，不能按函数名**。
2. **A122的漏报是区间配对造成的。**
   - `kfence_guarded_free`在第519行拿raw锁，在第526行一个提前返回的分支里释放，第541行调用`kfence_protect`时锁还拿着。
   - 检查器按“第一个释放”配对，区间在526行就结束了。需要按分支分析锁的持有状态。
3. **公共代码中的缺陷不在本轮范围内。** B558（每任务的栈偏移）和B580（ACPI LPI函数缺`__cpuidle`）都在公共代码中，检查器只看RISC-V函数和RISC-V钩子。
4. **同一问题被重复标出。** 14个(a)类标记只对应3个问题。今后应按“问题”合并报告，例如“`die()`在陷入中被调用”只报一次。

## 结论

- 按判据，**未达到成功标准**：测试集M5命中2/6，要求3/6。
- 但这是迄今第一个在测试集M5正例上有命中的方法，而且标记的精确度高（52%为真问题），不需要调用模型。
- 改进方向（未执行）：
  - 评估改为按行范围对应；
  - 区间配对改为按分支跟踪锁的持有状态，即处理提前返回的释放；
  - 同一问题合并报告；
  - 把检查范围扩展到RISC-V实际使用的公共代码路径，例如`drivers/acpi/`中的空闲状态处理。
