# 静态分析器统一框架方案（unified_20261119）

2026-11-19，Claude。用户：“先整理统一框架吧”。本文只是方案，还没有写代码。

## 一、为什么要统一

现在有 9 个检查引擎，每个都有自己的一套读入、解析、判定和输出：

| 引擎 | 目录 | 检查什么 |
|---|---|---|
| P1 | `reachgap_20261116` 等 | 公共代码用 `pmd_leaf`、`pte_dirty` 这类接口前，没先确认页表项在位 |
| XV | `xvdom_20261116`、`xvlift_20261116` | 同上，按各架构的编码差异排序，并上提到辅助函数 |
| ORD | `orddom_20261116` | 页大小推出的 order 超过页缓存上限 |
| WT | `widthtrunc3_20261117` | 32 位架构上的位宽截断 |
| TLB | `tlbhook2_20261117` | 改了页表后该刷 TLB/缓存却没刷 |
| CTX | `ctxeff3_20261118` | 原子或关中断上下文里调用了会睡眠、会发 IPI 的架构实现 |
| WK | `weakov2_20261118` | 覆盖实现在某些路径上跳过了通用实现的工作 |
| XA | `xvatom2_20261119` | 页表接口的原子性层级不一致；少数架构断言表项在位 |

最近几轮的做法是看一个漏报、写一条专门的规则。结果是：
- 开发样本总能抓到，但独立召回很难验证（weakov2 挖不到第二个同类缺陷）；
- 每加一类缺陷就要新写一个引擎，代码不复用；
- 三类检查（类型一致性、实现一致性、调用上下文）只是事后贴的标签，代码里没有对应的结构。

## 二、统一模型：接口契约

所有引擎其实在回答同一个问题：

> 公共代码调用一个架构接口时，对它有所期待；某个架构**实际生效的实现**，是否满足这个期待？

把“期待”写成**接口契约**，分三部分：

| 部分 | 含义 | 例子 |
|---|---|---|
| 值 | 参数和返回值的类型、位宽、取值范围、编码 | `unsigned long` 在 32 位架构上只有 32 位；`__ffs(0)` 的结果 |
| 前置条件与效果 | 调用前必须满足什么；调用后保证发生了什么 | 传入的项必须在位；返回时 CPU 设备已注销；页表项已原子地清空 |
| 上下文 | 能在什么上下文里调用；会不会睡眠、发 IPI、用 SIMD | 关中断时不能调用会发 IPI 并等待的实现 |

三类检查正好对应三部分：
- **类型一致性检查**：比较“值”；
- **实现一致性检查**：比较“前置条件与效果”；
- **调用上下文检查**：比较“上下文”。

契约从三个来源推断：
1. 通用实现（`__weak` 函数、`__HAVE_ARCH_*` 保护的通用定义）；
2. 多数架构的实现；
3. 公共调用方的用法：调用前做了什么检查，调用后假设了什么。

## 三、四个统一的部件

### 部件 1：接口表

自动找出所有“架构可以提供自己实现”的接口：
- 非 arch 代码里的 `__weak` 函数；
- `include/linux` 和 `include/asm-generic` 里被 `#ifndef __HAVE_ARCH_X` 或 `#ifndef x` 保护的通用定义；
- 公共代码调用、而定义只在 `arch/*/` 里的函数（架构钩子）。

每个接口记下：名字、通用定义（如果有）、哪些架构有自己的定义。

### 部件 2：实际生效的实现

对每个（接口，架构）组合：
- 架构有自己的定义就取它，没有就取通用定义；
- 结合 Kconfig 判断这个接口在这个架构上是否在用，以及在哪些配置下生效。

现成部件：xvatom 的 `Defs.effective`、archsig 的 Kconfig 可行性判断。

### 部件 3：属性摘要

对每个实际生效的实现，算出一组属性。沿调用往下追，只追和接口参数有关的调用：

| 属性 | 属于 | 现在在哪个引擎里 |
|---|---|---|
| 每条路径上都调用的效果函数；只在部分路径上调用的效果函数及条件 | 前置条件与效果 | weakov 的 `cond_map`、`missing_paths` |
| 对参数的断言、对参数的提前返回 | 前置条件 | xvatom 规则 B、ctxeff3 的 H1 |
| 作用在参数上的原子操作 | 效果的属性 | xvatom2 的参数追踪 |
| 刷 TLB/缓存这类副作用 | 效果 | tlbhook2 |
| 会睡眠、会发 IPI、要求 SIMD 可用 | 上下文 | ctxeff 的效果计算 |
| 返回值、参数的位宽和取值范围 | 值 | widthtrunc3、orddom |
| 对各类非在位项的读值 | 值 | encrank 的编码探针 |

### 部件 4：调用方摘要

对公共代码里每个调用点：
- 调用前已经确认了什么（在位守卫、宏守卫、配置守卫）；
- 调用时所处的上下文（持锁、关中断、单 CPU）；
- 调用后用了什么（是否检查返回值、是否假设效果已发生、接着做了哪些清理）。

现成部件：P1 的守卫分析、ctxeff 的上下文区间和传播、weakov 的“忽略返回值”判断。

## 四、五种比较方式

所有引擎的判定都可以写成下面几种比较之一。新的缺陷类型，多数情况下只需要在属性表里加一种属性，不用新写引擎。

| 比较方式 | 含义 | 已有的例子 |
|---|---|---|
| 横向少数派 | 同一接口，少数架构的属性和多数不同 | XV 的编码差异、xvatom 规则 B、CTX 的少数派标记 |
| 覆盖 vs 通用 | 覆盖实现缺了通用实现在每条路径上都有的属性 | weakov |
| 同族层级 | 同一架构内，同一族不同层级（pte/pmd/pud）的属性不一致 | xvatom 规则 A |
| 调用方 vs 实现 | 调用方假设的属性，某个架构的实现不提供；或者实现要求的前置条件，调用方不保证 | P1、TLB、CTX、xvatom 规则 B 的排序 |
| 提交级差分 | 一个提交前后，上面任一比较的结果新出现 | 提交级模式（7 个引擎） |

## 五、现有引擎怎么放进来

| 引擎 | 属性 | 比较方式 | 检查类 |
|---|---|---|---|
| WT | 位宽 | 调用方 vs 实现（运算对位宽的假设） | 类型一致性 |
| ORD | 取值范围 | 调用方 vs 实现 | 类型一致性 |
| P1 | 前置条件（在位） | 调用方 vs 实现 | 实现一致性 |
| XV | 对非在位项的读值 | 横向少数派 + 调用方 vs 实现 | 实现一致性 |
| TLB | 效果（刷 TLB/缓存） | 横向少数派 + 调用方 vs 实现 | 实现一致性 |
| WK | 效果（每条路径） | 覆盖 vs 通用 | 实现一致性 |
| XA-A | 效果的属性（原子） | 同族层级 | 实现一致性 |
| XA-B | 前置条件（断言） | 横向少数派 | 实现一致性 |
| CTX | 上下文（睡眠、IPI） | 调用方 vs 实现 | 调用上下文 |

## 六、实施步骤

1. **接口表和实际生效的实现**：从 xvatom、archsig 抽出来，做成独立模块；在主线上统计接口数、覆盖情况，人工抽查 20 个是否正确。
2. **属性摘要**：先做四种已有属性（每条路径的效果、参数断言、作用在参数上的原子操作、睡眠/IPI），代码从 weakov、xvatom2、ctxeff 搬过来，统一成“属性提取函数”。
3. **比较方式**：实现横向少数派、覆盖 vs 通用、同族层级三种，输出统一格式：接口、架构、属性、比较方式、证据链、检查类。
4. **对照**：用统一版本重跑 WK、XA 的开发样本，要求结果一致。之后再逐步迁移 CTX、TLB、P1。
5. **新的留出集**：从没读过的历史修复里另抽一批，用统一版本测召回。重点看**没有专门规则、靠通用属性加比较方式就能抓到的缺陷**有多少，这才是统一框架的价值所在。

前三步约 1～2 轮，第四步视迁移范围而定，第五步需要一轮标注（可以请 Codex 做第二标注人）。

## 七、取舍和风险

- **不保证召回马上提高**：统一首先解决的是“规则零散、不能复用、说不清和三类检查的关系”。召回能否提高，要看第五步。
- **通用属性比专门规则更粗**：比如“作用在参数上的原子操作”比“取出并清空必须原子”宽，噪声可能变大，需要排序和少数派阈值来控制。
- **迁移成本**：P1、XV 这条线积累了很多专门处理（返回值摘要、goto 标签、死分支），全部搬进来工作量大。建议先迁移结构简单的 WK、XA、CTX，P1/XV 暂时作为外挂引擎保留。
- **论文表述**：统一后，可以直接用“接口契约的三个部分 → 三类检查”来组织方法章节，比现在按引擎罗列更清楚。
