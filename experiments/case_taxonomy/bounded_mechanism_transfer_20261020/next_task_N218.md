# 下一项 N2.18：把部分正确候选变成有边界的身份集合检查

本计划依据 N2.17 已保存的父版预测、随后开放的历史修复及研究侧复核制定，属于已读案例开发，不能称未见样本验证。执行前仍需固定具体输入、源码提取位置及检查表达式；列明两版相同的枚举次序、进入时各 mask/引导 CPU 状态与观察点，不根据输出调整输入或契约。

## 目的

回答一个有限问题：模型已指出 SPARC 将 CPU 数量改写成连续编号的风险，能否将这条线索转换成带选择范围和阶段的可执行检查，并避免“全部 present 必须 possible”等过强要求？这连接 N1 的条件化要求与 N2 的有区分力对照；不以增加通用解析能力或再次改提示词作为结果。

## 连续完成的研究小闭环

1. **先核数值和阶段。** 只读 G 已固定父/子版的 `init/main.c`、`kernel/smp.c`，以及子版 `arch/sparc/kernel/prom_64.c`、`arch/sparc/kernel/smp_64.c`，至多六份新增完整源文件。定位 `nr_cpu_ids` 在相关阶段的数量限制、最大编号界限及公共 bringup 的使用关系。已有八文件和原始回答不变；找不到的调用、配置和实际路径保留未知，不再追辅助函数树。
2. **登记有限契约。** 明确固件身份集合、实际选择集合、数量限制、位图容量及观察阶段。候选方向是“不得引入未提供的 CPU 身份；限制数量时保留被选择的原编号；无数量截断时保留原集合”。这些是待源码审查的研究者精化，不能记作模型已经自动输出的正式契约，也不预设启动 CPU 的额外要求已证。
3. **做源语义最小对照。** 对照单元须包含旧版“`record_one_cpu`登记真实编号＋随后`smp_fill_in_cpu_possible_map`重建前缀”和修复版“`record_one_cpu`登记时限数量＋不再重建”的完整变化。后一个整理函数在修复中已删除，不能虚构同名旧/修函数两体。现存原函数正文逐字提取，使用相同枚举输入；API替身的位图容量、计数/遍历有效位域及阶段语义先固定，不手工改写循环或删除分支，也不只比较两个抽象循环。事先固定不超过十二个版本/输入组合，重点是同数量的连续与稀疏编号，以及有数量限制时的边界。报告机器的 0/2 编号与人为构造边界分列；替身位图执行不是实际固件、内核启动或合法硬件配置证明。
4. **核检查是否有用。** 分开报告旧/修复行为、研究者条件检查及模型原始过强谓词的结果。无警告、程序返回成功或普通连续输入通过，不作为整体契约正确。当前提不足，检查保持不足；不为得到通过结果回填配置、修改原答案或补选样本。
5. **收束。** 给出可复用的“架构提供身份→数量/编号转换→公共逐位消费”检查关系及其证据边界。若不能建立有依据的阶段契约，保存失败并停止，不扩展前端。后续独立同机制问题与同用途正常对照仍须另选、隔离和冻结，不能用本例开发结果替代。
