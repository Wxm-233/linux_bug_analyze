## G：关键原因已提出，完整条件仍不能直接接受

**G 原答已在父版 R1 中提出修复的关键原因。** 原答不仅提到 possible/present，还明确指出按 `weight` 重建连续前缀、固件 ID 可稀疏、`{0,2}` 被改成 `{0,1}`、公共资源分配与 `cpu_up` 会消费该结果。其列出的 sun4u/非 hypervisor、SMP 条件，以及固件输入、`nr_cpu_ids` 时点和启动顺序未知，也与冻结 oracle 的主要证据缺口一致。因此可以报告“父版模型提出与历史修复一致的关键转换线索”，不能把该线索全记作读修复后的研究者发现。

但这是局部因果线索的符合，不是完整契约正确：

- R1 与 T1 要求所有 present 都在 possible、相关编号均小于当时的 `nr_cpu_ids`，缺少实际选择范围和观察阶段。修复 diff 在 `record_one_cpu` 里仍先无条件置 present，再按 `num_possible_cpus() < nr_cpu_ids` 决定是否置 possible。存在数量截断且 present 保留未选条目的条件时，修复流程也可能不满足原来的全量包含谓词。因此“所有发现 CPU 都必须进入 possible”不能替代“被选中 CPU 保留真实身份”。这没有独立证明某一实际配置一定如此，仍须补齐数值与阶段链。
- `nr_cpu_ids` 在特定位置究竟作为数量限额、还是已按最大 CPU 编号形成的有效位界限，原答未证明。把同一个数在不同时点的用途直接合并为 `cpumask_last(present) < nr_cpu_ids`，不能得到可执行真值。
- architecture_paths[0] 的“只有当 OF 集合为连续前缀才满足”依赖 `P_before=Q_before`、完整写入者、取 weight 的有效位范围、上限和观察时点。一般地，旧函数输出的是 `Q_after=[0,k)`，`k=min(weight(Q_before),nr_cpu_ids_at_that_time)`；检查 `P_before⊆Q_after` 的直接条件是这些 present 成员都落在该前缀内。未证明前提时，“稀疏”本身不够作为完整充分触发条件，“致密”也不是跨所有阶段和上限的满足保证。
- T1 把公共 `cpu_up` 的拒绝消息列为足以否定要求的证据，仍过宽。拒绝一个合法被禁用或未选中的 CPU 不必是提供者违约；要绑定应被选中的同一 CPU、合法活动配置、错误状态来源及路径，才能形成因果结论。
- ARM64 原答称“合法对照”，同时把相应 architecture_path 标为 `insufficient`，并承认其他写入与调用顺序未知。应保留局部同用途构造的比较价值，不能升级为整体正常真值或独立正常样本。

G 的 R2/R3 还包含编号传送范围、哨兵和其他字段来源等候选，它们没有因为 R1 命中历史修复而一并获得正确性。冻结 oracle 只确认此修复的身份/数量转换机制及公共用途，并未建立这些额外候选的新缺陷真值。

## H：一般拓扑关系未覆盖本次修复的模式/策略关系

H 原答 R1 为 CLS⊆MC，R2 为同层掩码划分，R3 为 numa-in-package 拓扑替换与初始化的时序；架构路径主要区分 Intel、AMD/Hygon 和 SNC/COD。它确实把架构提供者连接到公共调度域，但没有提出 hybrid 模式下 CLS 组容量会干扰 CPU priority 选择的关系。整份原答没有 hybrid/混合核/异构核分析，也没有将 CPU 优先级和是否保留 CLS 进行条件化对照。

冻结 oracle 认为本修复的直接机制是特定硬件模式下的策略兼容：真实缓存组关系可以正确，选择它作为调度层级仍可能不符合混合 CPU 的优先级政策。因此父子包含、同层划分、来源初始化都可能成立而问题仍在；它们的检查通过不能充当此次历史问题的检出。原答并未覆盖该关系，不应把 Intel/AMD 来源区别、某个 topology WARN 或词法调用顺序当作等价命中。

这可以作为固定 H 尝试的目标关系未提出与开发迁移局限报告，不能据此算正式独立跨 ISA 漏检率。H 本就有方法开发接触，范围属于同 ISA 型号/配置策略辅助；hybrid 必须严格按优先级的具体政策由修复说明明确，当前包也没有完整任务选择/运行证据。README 没有把其他 H 候选叫作新缺陷，这一点正确。
