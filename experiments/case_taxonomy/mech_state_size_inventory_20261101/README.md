# 大页“表项状态—大小来源”机制：案例清点与划分

## 这一轮要回答什么

下一轮拟做的试点，是把“表项状态—大小来源”写成带架构适用条件和保证来源的规则，冻结后在没参与设计的案例上评价。本轮只回答**这个试点做不做得成**：独立的历史实例有多少，扣掉已用于设计的还剩多少，正常对照有多少。

**机制**：处理大页的代码根据某个页表项的**内容**推出映射大小或表项个数，而这个表项可能不在内存中（空项、swap项、迁移项、标记项），这时推出的大小是错的。只有把大小编码在表项内容里的架构才适用，例如RISC-V的NAPOT位、arm64的连续位。

## 结果

### 1. 历史实例

`v4.0..df2908090cda`中，改动大页相关架构文件、说明里涉及大小或状态、并有缺陷证据的提交共68条。逐条阅读后：M（机制实例）7条，R（相关但不是这个机制）28条，N（无关）33条。

7条M合成3组：

| 组 | 提交 | 内容 | 划分 |
| --- | --- | --- | --- |
| A | `935d4f0c`（公共）、`6f1bace9`（arm64）、`1de195dd`（RISC-V） | 写入swap项或标记项时，从表项内容推大小 | 开发集：含`1de195dd`，此前各轮已用过 |
| B | `02410ac7`（公共）、`49c87f76`（arm64）、`83d78ac6`（RISC-V） | 读出并清空不在内存的表项时，从表项内容推个数 | 开发集：含`49c87f76`和`83d78ac6` |
| C | `20156ce2`（arm64，2016） | 写入时目标位置还是空项，按“空项”推出个数为1 | **留出集** |

R类中有不少是“与状态有关但不涉及大小”（如LoongArch把无效PMD误读成swap项），或“与大小有关但不是状态造成的”（如地址不对齐时取错大小）。

### 2. 正常对照（终点版本）

逐个阅读大小编码在表项中的架构（arm64、RISC-V、sparc64、powerpc 8xx），列出所有“用表项内容决定大小或是否连续”的位置，共18处：

| 分类 | 个数 | 例子 |
| --- | ---: | --- |
| G-本地：先判断在内存 | 3 | RISC-V、arm64的`huge_ptep_get` |
| G-调用者：调用者只传在内存的表项 | 5 | `huge_ptep_set_wrprotect`只在复制页表的“在内存”分支调用 |
| G-其他来源：大小来自参数或大页类型 | 4 | arm64的`huge_pte_clear`、`huge_ptep_get_and_clear` |
| U 未知 | 3 | sparc64两处、powerpc 8xx一处 |
| **疑似违反** | 2 | RISC-V的`huge_ptep_get_and_clear`、`huge_pte_clear` |

另有6个架构的大页大小由页表层级或固定配置决定，机制不适用：s390、x86、LoongArch、MIPS、parisc、powerpc book3s。

### 3. 按事先标准的判定

留出集只有1组（C），正常对照12处。按判据，**留出组≤1，应换机制**：这一机制没有足够的独立历史实例做冻结后的评价。

事后补查（看过归类之后做的，不计入判定）：用更宽的说明关键词检索，又找到arm64 2017年一组可能的同机制提交（`30f3ac00`、`9386fac3`、`7868a208`，为连续大页支持swap项），它们没有缺陷证据，不在原规则内。即便算上，留出组也只有2组，仍不够定量评价。

## 阅读中发现的疑点（读代码所得，未运行）

**RISC-V的B组修复可能不完整。**

- arm64的`49c87f76`把`huge_ptep_get_and_clear`中“按表项内容判断是不是连续页”的门槛`if (!pte_cont(orig_pte))`**整个删掉了**，直接用调用者给的大小。
- RISC-V的`83d78ac6`照着arm64修（说明里写“同样适用于RISC-V”），但**只把个数改成用大小参数，`if (!pte_napot(...))`这道门槛保留了下来**，`huge_pte_clear`也一样。
- RISC-V的swap项编码（`arch/riscv/include/asm/pgtable.h`中`__swp_entry`）不会带NAPOT位，所以不在内存的表项永远过不了这道门槛，只清掉一组里的第一个表项。也就是说，`83d78ac6`声称修复的情形（表项不在内存）实际上没有被修到。
- 写入一侧没有这个问题：`set_huge_pte_at`对不在内存的表项会按大小参数写满整组（`1de195dd`修的）。于是写16个、清1个，留下15个残留项。
- 会走到这里的公共路径（`mm/hugetlb.c`终点版本）：
  - 解除映射时，不在内存的表项走`huge_pte_clear`（约5264行）；
  - `mremap`移动大页时走`huge_ptep_get_and_clear`（约5101行）；
  - 解除uffd写保护标记时也走`huge_pte_clear`（约6603行）。
- RISC-V会出现的不在内存的大页表项：大页迁移项（RISC-V选了`ARCH_ENABLE_HUGEPAGE_MIGRATION`，`ce68c035`之后NAPOT大小也支持迁移）、`UFFDIO_POISON`写入的中毒标记、uffd写保护标记。

**可能的后果**：64KB的NAPOT大页被`UFFDIO_POISON`标记后解除映射，同一页表页里留下15个中毒标记；之后在这个地址上建立普通映射并访问第2到16个4KB页时，会被当作中毒页收到SIGBUS，正确行为是读到零页。这是推测，**必须运行验证**，sh那次的教训说明读代码可能漏看条件。

这个疑点本身说明了机制的用法：它不是靠“和arm64比较步骤”找到的，arm64和RISC-V这两个函数在步骤特征上都“有大小参数”。它是按“这条要求在什么状态下必须成立、门槛用的是什么信息”去读，才看出来的。

其他记录：sparc64的大页代码完全从表项内容推大小、忽略大小参数，对中毒标记会推出8KB并触发一次内核警告；但写入和清除都只处理一项，前后一致，危害不明，归为U。powerpc 8xx一处需要细读，不在RISC-V重点内。

## 统计

不调用模型；构建0；新确认缺陷0；新疑点1条（RISC-V，待运行验证），只记录、不对外报告。

## 后续

上面的疑点已在QEMU上运行验证，**成立**：原版内核上，被写成中毒标记的64KB NAPOT大页在解除映射或`mremap`后，第2到16个4KB页残留标记、读时收到SIGBUS；只去掉`pte_napot`门槛的对照内核上全部读到零。详见`../riscv_napot_clear_verify_20261101/README.md`。
