# 大页“表项状态—大小来源”机制：案例清点与划分（判据，实现前写定）

## 这一轮要回答什么

下一轮拟做的试点是：把“表项状态—大小来源”这一机制写成带架构适用条件和保证来源的规则，冻结后在未参与设计的案例上评价。本轮只回答**试点做不做得成**：

1. 这一机制在各架构的历史修复中有多少个独立实例（按根因和传播链分组）；
2. 扣掉已经用于设计的实例后，留出集还剩多少；
3. 有多少可作正常对照的位置（要求成立且有明确保证来源，或机制不适用）。

本轮只读代码和提交记录，不构建内核，不调用模型，不写检查程序。

## 机制定义

**M（表项状态—大小来源）**：处理大页映射的代码，根据某个页表项的**内容**推出映射的大小或表项个数；而这个表项在该调用路径上可能处于不携带大小信息的状态（不在内存：空项、swap项、迁移项、硬件中毒项、标记项等），此时推出的大小是错的。

- **架构适用条件**：只有把大页大小（或连续表项个数）编码在表项内容里的架构，才可能有这个问题，例如RISC-V的NAPOT位、arm64的连续位。大小只由页表层级决定的实现，不适用。
- **保证来源**：函数自己先判断表项在内存；调用者只传入在内存的表项；或者改为用调用者给出的大小参数、VMA等内容以外的来源。

   - 或者改动`include/linux/hugetlb.h`、`include/asm-generic/hugetlb.h`、`mm/hugetlb.c`之一，**同时**改动`arch/`下的文件（公共约定连带架构修改的情况）。
2. 提交说明（标题加正文）匹配（不区分大小写）：`present|swap|migrat|hwpoison|poison|marker|contig|napot|cont_pte|num_contig|ncontig|nr_ptes|page size|pgsize|huge.?page size|\bsz\b|size`。

## 二、逐条阅读归类（人工，记录理由）

对每条候选读提交说明和改动，归为一类：

| 类 | 含义 |
| --- | --- |
| **M** | 机制实例：修复前，代码从表项内容推大小或个数，而该表项可能不在内存中（或因其他状态不携带大小）；修复改变了大小来源（改用大小参数、VMA等），或在推大小前加入状态判断，或给公共接口加大小参数以使架构能这样做 |
| **R** | 相关但不是M：同样与大页大小或表项个数有关，但错因不是“表项状态使内容不可信”，例如地址对齐、个数算错、刷新步长、编译错误 |
| **N** | 无关 |

归类时同时记录：架构、函数、修复前的大小来源、修复后的大小来源、提交说明中提到的引起修复的表项状态。

**分组**：同一根因的修复，以及沿同一传播链的修复（公共接口加参数及各架构随之的修改；一个架构修复后另一个架构引用它所做的同类修复）合成一组。分组依据是提交说明中的引用（`Fixes:`、提交号、“similar to”“same as”等）和改动内容；依据要写明。

## 三、开发集与留出集

- **开发集**：本项目此前已用于机制分析或规则设计的实例所在的组。已知包括：RISC-V `1de195dd`、`83d78ac6`，arm64 `49c87f76`（方向4第二轮的独立参照）。与它们同组的实例一并划入开发集。
- **留出集**：其余M组。
- 同一组不能拆到两边。

## 四、正常对照

在终点版本`df2908090cda`上，对**大小编码在表项内容中**的每个架构，研究者阅读其大页实现，列出所有“从表项内容推大小或个数”的位置（消费点），每处按以下分类，并写明依据（代码位置）：

| 类 | 含义 |
| --- | --- |
| **G-本地** | 同一函数在推大小之前已判断表项在内存 |
| **G-调用者** | 所有直接调用者都只传入在内存的表项（列出调用者及其依据） |
| **G-其他来源** | 实际使用的大小来自内容以外（参数、VMA、层级），内容只用于其他目的 |
| **U 未知** | 找不到足够证据（例如调用者经函数指针分派、或某调用者的状态无法确定） |

另外，大小只由页表层级决定的架构记为“机制不适用”的对照，只列架构和依据，不逐处列出。

`U`类不作为正常样本，只计数。被M实例修复过的函数，修复后的写法作为“修复后满足”的对照单独列出。

## 五、判断标准（事先写定）

- **可做定量试点**：留出集中M组 ≥ 4，且正常对照（G三类之和）≥ 5。
- **只能做描述性试点**：留出M组为2到3，或正常对照少于5。这时逐例报告，不给比率。
- **换机制**：留出M组 ≤ 1。
