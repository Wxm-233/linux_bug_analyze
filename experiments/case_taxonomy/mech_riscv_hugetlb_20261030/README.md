# 方向4：RISC-V大页接口家族深挖（第一轮）

## 这一轮要回答什么

前几轮里，RISC-V的历史修复明显集中在大页上。这一轮按研究目标，从已确认的修复出发：

1. 先读懂每个修复，归纳出背后的机制；
2. 再按机制写出检查，看能不能在修复之前把问题标出来；
3. 最后把检查用在当前代码上，看会标出多少条，人工核对。

**事先提出的机制假设**：

- RISC-V的NAPOT大页和arm64的连续页一样，都是用一组连续的页表项共同表示一个大页。公共大页代码给架构留了一批可覆盖的钩子，默认实现是按“一个大页一个表项”写的。所以，**arm64因为连续页而覆盖了的钩子，RISC-V多半也要覆盖**。
- 第二类机制是“读出并清空”这类操作必须是原子的。

## 第一部分：18个已确认修复的归因

范围是v4.15以来带`Fixes:`、改动RISC-V大页相关代码的修复。

| 类别 | 个数 | 例子 |
| --- | ---: | --- |
| **多表项大页的默认实现不适用** | 4 | `huge_ptep_get`：默认只读一个表项，NAPOT要合并整组表项的脏位和访问位；`hugetlb_mask_last_page`、`arch_hugetlb_migration_supported`：默认实现不认识NAPOT的大小；`pte_leaf_size`：默认返回一个页的大小 |
| **原子性要求未满足** | 1 | `pudp_huge_get_and_clear`：默认实现先读后清，改为原子交换 |
| 公共约定改变 | 2 | `set_huge_pte_at`、`huge_ptep_get_and_clear`：公共修复给它们加了页大小参数，各架构同步修改 |
| RISC-V自身逻辑错误 | 6 | 其中4个是RISC-V自己的NAPOT实现写错了。例如修改NAPOT表项前没有先整体清空并刷新TLB（RISC-V规范要求这样做，相当于arm64的“先断后建”）；处理不在内存中的表项时，取错了表项个数 |
| 其他 | 5 | 3个编译错误；`arch_clear_hugepage_flags`（RISC-V用页标志管理指令缓存，分配大页时要清掉，原因与多表项无关）；`pmdp_collapse_flush`（RISC-V的TLB刷新语义不同） |

## 第二部分：检查与回溯

- **检查A**：公共代码允许架构覆盖的大页钩子中，arm64覆盖了、RISC-V没有覆盖的那些。
- **检查B**：RISC-V上实际生效的“读出并清空”类函数里，有没有原子交换。

| 案例 | 机制 | 修复前的父版本上是否被标出 | 父版本上标记总数 |
| --- | --- | --- | ---: |
| `arch_hugetlb_migration_supported` | 多表项 | 是 | 4 |
| `hugetlb_mask_last_page` | 多表项 | 是 | 5 |
| `huge_ptep_get` | 多表项 | 是 | 5 |
| `pudp_huge_get_and_clear` | 原子性 | 是 | 5 |
| `pte_leaf_size` | 多表项 | **否**：这个钩子定义在`include/linux/pgtable.h`，不在检查A规定的大页头文件里 | — |

- 两类机制的5个案例中，4个在修复之前就会被标出，而且每次只标出4到5条，人工完全看得过来。
- 另外，归为“其他”的`arch_clear_hugepage_flags`也会被检查A在修复前标出。这说明“参照arm64找该覆盖未覆盖的钩子”的适用面，比“多表项”这个机制更宽。

## 第三部分：当前代码（终点版本）

检查A标出3条，检查B标出4条，共7条，研究者逐条核对，**都不是问题**：

| 标记 | 核对结论 |
| --- | --- |
| `flush_hugetlb_tlb_range`（A） | RISC-V的`flush_tlb_range`内部已经按NAPOT规则处理了大页的刷新步长 |
| `huge_ptep_modify_prot_start/commit`（A） | arm64覆盖它们，只是为了绕开自家一款CPU的硬件勘误（2645198）；公共默认实现直接调用RISC-V已支持NAPOT的函数 |
| `huge_ptep_get_and_clear`及3个`*_get_and_clear_full`（B） | 它们只是调用`ptep_get_and_clear`等函数的薄包装，被调函数在RISC-V上用了`xchg`。检查B只看函数体里有没有原子操作，没有跟进被调函数，因此误报 |

## 结论（按事先标准）

| 标准 | 结果 | 是否满足 |
| --- | --- | --- |
| 机制成立：已确认案例中至少一半属于两类机制 | 5/18（28%） | **不满足** |
| 检查有指导作用：两类案例中至少一半能在修复前标出，且当前标记不超过15条 | 4/5；当前7条 | 满足 |

- **检查本身有用**：“参照arm64找RISC-V该覆盖而未覆盖的大页钩子”在历史上能提前标出4到5个真问题，每次只标出几条。当前代码上没有新的疑似问题，说明这一类问题在大页家族里基本已经补齐了。
- **但这两类机制只解释了不到三成的大页修复。** 最常见的是RISC-V**已经覆盖了钩子、但自己的NAPOT实现没写对**，例如：
  - 修改前没先清空并刷新TLB；
  - 写保护时逐项改写，而不是整组处理；
  - 处理不在内存中的表项时取错了个数。

### 事后观察（看过结果之后，未登记）

- 如果按“与NAPOT有关”来归，18个修复中有10个相关：4个默认实现不适用、4个RISC-V自身的NAPOT实现错误、2个由此引起的编译错误。
- RISC-V自身NAPOT实现的那几个错误，arm64的连续页实现在对应的地方本来就是正确的写法：先整体清空并刷新再写入，整组处理写保护。也就是说，这类错误同样可以“参照arm64”，只不过要比较的是**实现步骤**，而不只是“有没有覆盖钩子”。

## 可能的下一步（未登记）

1. 把“参照arm64”从“有没有覆盖”扩展到“实现步骤是否一致”：对RISC-V和arm64中处理多表项大页的同名函数，比较关键步骤，例如是否先清空并刷新、是否整组处理、是否区分在内存与不在内存的表项。用这一轮的4个“RISC-V自身NAPOT错误”做回溯检验。
2. 把检查A的钩子范围扩大到`include/linux/pgtable.h`中与大页、连续页相关的钩子，补上`pte_leaf_size`这类遗漏。
3. 检查B改为跟进一层被调函数，消除包装函数的误报。
