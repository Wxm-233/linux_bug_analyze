## 结论

- “模型读修复→写受限正则→程序实例化”在两种设定下都是负结果：
  - P1（同作者兄弟）：M5 25%，同文件基线47.5%；
  - P1′（严格跨架构缺陷兄弟）：M5 30%，跨架构同路径基线52%。

  失败模式一致：模型写的正则贴合种子修复的表面写法，换了架构就匹配不上。
- 这轮有一个可报告的经验事实：**跨架构缺陷兄弟高度集中在各架构的平行文件里**，仅靠“同一相对路径＋同名函数＋标识符重叠”这一结构基线，就能在前20中找回约一半。
- 如果继续B方向，更合理的分工是由结构对应（B3）生成小候选集，再让模型或程序逐个判断“是否存在同一问题”，而不是让模型写全局搜索的正则。不过这50对已被用来分析失败，只能作为开发集。要做独立检验，需要新的留出样本，例如把范围再往前扩，或换配对来源。
- 来源B的构造缺陷（S多为引入点）须在后续任何登记中修正：要么要求S本身也是修复（S自带`Fixes:`），要么把“从引入点找漏改的使用方”作为另一种任务单独设计。
