# 判据：补老版本构建（ecbuild_20261122）

2026-11-22，Claude。用户：“先补老版本构建”。接第五轮（`ecprot_20261122`）：规则 4 没起作用，主因是老版本 PMD/PUD 级可比的构建太少。写于修改和运行之前（v5.18 上为查原因重建过一次变体，结果只用于诊断）。

## 一、诊断（已查清，不是编译器版本问题）

| 现象 | 原因 |
|---|---|
| powerpc 6 个构建、s390 在 v6.x 及以前 `prepare` 失败 | 卡在 `vdso_prepare`：老内核用编译器驱动链接 vdso，需要 `<三元组>-ld`，WSL 没有；s390 的 vdso 把 `-fPIC` 直接传给链接器，ld.lld 不认 |
| v5.10 几乎全部失败（`-mcmodel=medany`、`power8`、`-mabi`、未知寄存器名） | 老内核由 `CROSS_COMPILE` 推出 clang 的 `--target`，没设时 clang 按宿主 x86 编译 |
| v5.18 的 i386_pae 变体没有 PAE | 老 Kconfig 里 `X86_PAE` 依赖 `HIGHMEM64G`，用 df 的配置 `olddefconfig` 后被关掉（第四、五轮该版本 i386_pae 的数据实际是非 PAE） |
| 老版本 x86_64 全部“依赖运行时” | `_static_cpu_has(X86_FEATURE_LA57)` 为真的分支上 `MAX_PHYSMEM_BITS` 不是常量，整次求值放弃；合并时这个空分支让所有组合都不一致 |
| v6.2、v6.4 的 loongarch `olddefconfig` 失败 | 待查（可能是该版本 clang 不支持 LoongArch） |

## 二、修正（只改构建与运行基础设施，引擎判定规则不变）

1. **工具链**：所有构建传 `CROSS_COMPILE=<该架构的三元组>-` 和 `LLVM_IAS=1`；PATH 前加一个替身目录，内有各三元组的 `<三元组>-ld`（调用 ld.lld，并去掉 GNU ld 专有、ld.lld 不认的 `-fPIC`）。只用于 vdso 等驱动链接，`mm/memory.o` 的编译命令照旧来自 clang。
2. **身份选项核对**：每个构建定一组“身份选项”（决定该构建是什么的选项，取自 df2908090cda 的配置）：i386_pae 的 `X86_PAE`、arm_lpae 的 `ARM_LPAE`、mips32xpa 的 `XPA`、ppc44x 的 `44x`、ppc8xx 的 `PPC_8xx`、ppc64e 的 `PPC_BOOK3E_64`、ppc32s 的 `PPC_BOOK3S_32`、ppc64le/ppc64le_hash 的 `PPC_BOOK3S_64`（ppc64le_hash 另要求 `PPC_RADIX_MMU` 关闭）、rv32_abi 的 `32BIT`、各 64 位构建的 `64BIT`。`olddefconfig` 后缺身份选项时，按已知的老 Kconfig 依赖补一次（目前只有 `X86_PAE` ← `HIGHMEM64G`），再缺就把该构建记为“配置不符”、不参加。
3. **运行时分支合并**：某个运行时取值组合上整次求值失败（常量算不出），这个组合不参加合并；只有在实际算出结果的组合之间才判“依赖运行时”。df2908090cda 上若没有整次失败的组合，结果不变（会核对）。
4. loongarch 老版本失败查明原因；修不了的如实记录。
