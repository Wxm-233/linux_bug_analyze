# 架构准备期限与公共消费者：候选检查卡

2026-10-15，R5已读s390/x86案例的机制开发。承接[五输入反例](../claude_contract_resume_20261015/README.md)。原历史运行、原C、模型旧AST及旧Claude账本保留；本轮不新增案例、构建或内核启动，R3继续暂缓。

## 本轮回答的问题

检查应围绕“架构提供者是否在同一公共消费期限前，为同一对象提供了符合用途的状态”，而不是统一要求CPU先online，或仅搜索一次准备函数。x86允许未online的CPU先建立拓扑；旧s390以online为准备资格，而公共通知在online之前。因此，架构之间合法的准备方式不同，共同消费者的期限却相同。

具体到这个已读消费者，需要分别核对：有效配置和路径、目标组身份、self成员关系、初始rq状态、非singleton路径的其他leader，以及安装后的组内一致性。self只是带前提的必要窄候选；无WARN和整个过程正确均不能由它单独推出。详见[逐条件语义复核](semantic_review.md)。

## 检查卡及程序的范围

[检查卡](contract_card.json)为研究者综合，不是Kimi自动生成。它把源码、运行、研究侧推断等来源分开，保留当前证据缺口。[程序](check_contract.py)执行显式登记的窄关系及证据门控；不自动理解任意C，也不自动证明整条架构准备链。配置、身份与路径等前提仍需要有依据的复核。

同一结果分别报告窄关系、伴随条件和整条路径结论。既有五输入只回放原结果，未重跑C：仅其他成员的singleton可无WARN却缺self；含self的多成员组仍可缺leader。缺初始化只使该初始化条件不足，不抹掉已有的独立成员关系求值；同样，一个局部关系成立不能让其他条件一起通过。

[25项离线测试](test_contract.py)通过，[独立复核](independent_review.md)未发现本轮局部范围内的阻断问题。[回放结果](gate_results.json)全部保留精确消费和整条路径`insufficient`；测试通过仅说明门控按登记条件工作，不是25个案例或检测准确率。初稿必需引用组可被自报删空的问题已经改为固定schema并补测。

历史四格的mask仅在`local_irq_save`之前非原子采样，不能移作原循环精确读取值；真正原消费为集合遍历及后续weight/leader/安装/解锁。卡片保持这一区别，不把实际锁调用计数解释为整个区间的完整快照。精确读取、其他writer、真实SMT与重入/并发仍未证明。
