## 这说明什么

1. **这种写法的跨架构缺陷在历史上非常少。** 就我们定义的这种形态而言，近五年公共代码里只出现了 X1 一次。纵向信号能抓住 X1，但用来发现缺陷的覆盖面很窄。
2. **师兄结论第 18 条点出了更常见的情况。** “缺失的操作没有对应语句”：公共层根本没写某项检查或某项工作，而不是先写了、再用开关跳过。这种情况在补丁里的表现是“新增了一个检查或一项工作”，而不是“删掉了一个开关赋值”。按我们现在的形态，从修复补丁里是筛不出来的。
3. **结合前面各轮**：横向比对噪声大，纵向开关形态覆盖窄。静态分析单靠“代码形态”来定位效果依赖，两头都有困难。

## 下一步可以考虑的（还没做）

1. **换一种筛法找样本**：按修复补丁“在公共代码里新增了对架构接口结果的检查”或“新增了一项本该由架构做的工作”来筛（例如新增 `if (!arch_xxx(...))`，或者在调用架构接口之后新增清零、刷新、初始化）。这更接近师兄第 18 条，样本可能多一些，可以用来回答“依赖缺失”通常长什么样。
2. **把检查放到动态阶段**：师兄结论最后一条说静态太重的检查放到动态阶段。纵向信号给出的“资源 + 性质”数量已经很少，可以直接交给动态阶段按性质验证，而不是继续在静态上追求精度。这需要 ACTOR 记录器，见 `../actor_eval_20261113/README.md`。
