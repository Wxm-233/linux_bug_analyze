## 2. B3命中由什么决定

| 分层 | 开发集（命中/对数） | 留出集（命中/对数） |
| --- | ---: | ---: |
| 全部 | 26/50（52%） | 5/22（23%） |

| 目标不在同相对目录 | **0/14** | **0/14** |

- **B3只在目标位于平行实现目录（同相对目录）时起作用**。在这一层里，两组命中率接近（72%与62%）；不在这一层的，两组都是0。
- **两组差距主要来自构成**：目标在同相对目录的比例，开发集为36/50（72%），留出集只有8/22（36%）；同相对路径的比例分别为48%与9%。

## 3. 构成差异从何而来

| 候选解释 | 结果 |
| --- | --- |
| 代码年代 | 留出集中早于v4.19与之后的各11对，同相对目录都是4/11，**与年代无关** |
| 开发集隔离排除了共用X的家族 | 开发集中共用X的24对同相对目录为15，单独X的26对为21，单独X反而更多，**解释不了** |
| 兄弟质量 | 留出集“否”13对中只有4对在同相对目录，开发集“否”9对中有7对；留出集的“否”更多、更分散（不同子系统的无关修复），**与构成差异一致** |
| 来源 | 留出集全部为来源A；开发集来源A为21/31在同相对目录，来源B为15/19 |

最可能的原因是：以“共同引入提交”配对时，很多T只是修了同一引入提交带来的另一个问题。这类对在留出集中占多数，而且分散在不同子系统。这是对数据集质量的判断，不是对B3的判断。

## 4. 结论

- B3的表现不是“不稳定”，而是**有条件**：当跨架构兄弟位于平行实现目录时，结构对应在前20中找回约三分之二（两组分别为72%与62%，事后分层）；不在平行目录时完全找不到。
- 以`Fixes:`自动配对得到的兄弟对，真兄弟只占少数（盲核“是”分别为8/20与7/22），配对噪声是两组结果差异的主要来源。之前的整体召回（52%、23%）都混入了这一噪声。
- 数据集还有具体缺陷：重复提交，以及函数名识别把`__attribute__`、`switch`当作函数名。后续使用前须修正，并对兄弟关系做人工过滤。
- 这些结论都在看过数据之后得出，样本也小，论文中只能作为事后分析报告。
