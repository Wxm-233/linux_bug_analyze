# N2.18 CPU 身份集合与数量限制的有限对照

2026-10-21。本轮围绕已读 SPARC 案例完成一个小闭环：核对启动阶段，把模型的部分正确线索精化成有条件的身份检查，再执行原函数的旧/修复对照。**只检查数量时，旧版六组均通过；检查身份后，旧版四组不满足限定要求，修复版六组均满足。模型原始条件又会对部分修复版状态报警，表明选择范围与阶段不能省略。**

这是同一项已知历史案例上的开发验证，不是十二项缺陷、两个架构的实际启动或独立检出率。没有新增付费模型分析。

## 依据和执行单元

沿用 N2.17 的 G：父版 `95706e717c4f55ca62025c151451ccc28863d085`、修复 `98937707fea8375e8acea0aaa0b68a956dd52719`。本轮仅新增六份预先指定原文：两版本各自的 `init/main.c`、`kernel/smp.c`，以及修复版 `prom_64.c`、`smp_64.c`。每份与本地 Git blob 对应，没有 fetch 或追辅助源码树。

源码确认：公共启动先执行 `boot_cpu_init`、`setup_arch`，再执行 `setup_nr_cpu_ids`；SPARC 的 `setup_arch` 在早期解析参数。`nr_cpus` 先限制数量，后来的 `setup_nr_cpu_ids` 根据 possible 中最大编号加一重定界。`maxcpus` 是另一项激活数量控制，不应与之混用。完整 paging→OF 枚举调用链、实际配置和设备树仍未获得，不能据局部调用解释所有启动情况。

原函数正文按已登记行范围逐字提取：父版是 `record_one_cpu` 枚举真实编号后调用 `smp_fill_in_cpu_possible_map` 重建前缀；修复版是枚举时限制数量、保留真实编号，不再调用已删除的整理函数。两版随后使用同一份原始 `setup_nr_cpu_ids` 函数体。四段原文与两份生成单元经过执行前复核；没有为了宿主编译删除分支、改写循环或制造同名修复函数。

## 固定前提与研究者检查

只投影 `CONFIG_SMP`、非 FORCE、`NR_CPUS=8`、64位字、引导 CPU 0 已在 possible/present 的情况。每次新进程从同样状态开始，按固定顺序输入编号；枚举、位图 API 和设备树由显式替身提供，不是实际 SPARC 固件或完整 Linux API。此分支的 `num_possible_cpus` 使用 `small_cpumask_bits=NR_CPUS=8`，不能错误地只数早期限额 L 位。

观察点分为架构整理后、公共重定界前，以及公共重定界后。online、CPU 上线、锁、分配和并发均未模拟。公共头还指出一般只保证 `<nr_cpu_ids` 位有效，所以早期高位操作在本轮只能评价为限定源码投影，不能证明相应中间状态是普遍合法的 API 用法或合法内核配置。多字/动态位图分支没有覆盖。

研究者依据接口身份含义精化的关系是：输出不应凭空制造 CPU 身份；在本投影的限制下选择数量正确；没有数量截断时保留全部输入身份。first-L 只作实现诊断，不是普适规范。原模型的全部 present 都必须 possible、最大 present 编号小于当前 nr_cpu_ids 等谓词单独计算，没有作为真值标准。

这一原始身份子集关系仅适用于本 SPARC 路径把 cpuid 直接作为公共位索引的命名空间。ARM64 可以通过显式硬件→逻辑映射合法使用另一组编号；可复用检查应比较映射后身份，不能要求跨架构原值相同。

## 十二组实际结果

每行含旧/修复各一次运行；L 是早期选择数量限制，不随后续 nr_cpu_ids 回写改变。

| 输入编号顺序 | L | 旧版 possible | 修复版 possible | 旧/修身份关系 | 修复版 nr_cpu_ids 前→后 |
|---|---:|---|---|---|---|
| 0,1 | 2 | 0,1 | 0,1 | 满足 / 满足 | 2→2 |
| 0,1 | 8 | 0,1 | 0,1 | 满足 / 满足 | 8→2 |
| 0,2 | 2 | 0,1 | 0,2 | 不满足 / 满足 | 2→3 |
| 0,2 | 8 | 0,1 | 0,2 | 不满足 / 满足 | 8→3 |
| 0,2,4 | 2 | 0,1 | 0,2 | 不满足 / 满足 | 2→3 |
| 0,2,4 | 8 | 0,1,2 | 0,2,4 | 不满足 / 满足 | 8→5 |

0/2 是历史报告提及的编号形状，本轮没有复现该机器；0/1 是构造的连续对照，0/2/4 是构造边界，不是另两项历史缺陷。两次宿主 GCC 13.3.0 编译与十二次执行均首次返回 0，没有修源或重试；返回 0 只说明替身运行完成。数量性质两版均六组通过，不能据此认为成员身份正确。

修复版原模型组合谓词在早期两组为假，重定界后一组为假：0/2、L=2 的编号上界随阶段改变；0/2/4、L=2 中 CPU4 仍为 present，但没有被选入 possible。相对本轮已审的条件关系，这些是原谓词过强/阶段不当的警示，不是新修复缺陷或总体误报率。

另外复用已有运行，比较将编号 1 改为 2 后输出能否对应变化：两个 L 下旧版均不保持、修复版均保持。这是四项关系求值，**没有额外启动、运行或案例**。它也不证明任意编号重命名在真实硬件上合法。

## 研究含义与未完成项

这条机制更具体地说明“数据表示不一致”：架构原始编号可稀疏，代码却把数量解释为连续身份；公共代码按位消费，因此数量看似正确仍可能指向错误对象。默认连续输入可掩盖问题。系统层检查应连接提供者命名空间/映射、选择范围、变换效果和消费阶段，而不是统一检查一个数量、原始值相等或调用存在。

本轮精化关系是研究者在已看修复后建立的，程序只按登记关系评价有限原始观测，没有自动从新源码推导整个契约，也没有运行正式契约核心或自动配置选择器。不能据此确认 N1/N2 创新或跨案例泛化。实际合法配置、完整启动链、另一架构的同用途正常性、宏/底层位操作完整实现与物理 CPU 状态仍未证。

执行前语义/API、方法及执行后结果分别由助手角色复核，不是专家金标准。编译警告保留：父版原形参未用及 int/unsigned 比较，修复版原形参未用；没有 GCC 编译错误。WSL 提示的 stderr 采用替代解码，原始非 UTF-8 字节未保留，不称日志原字节完整，也未为此重跑。核心结论依赖完整 ASCII JSON stdout 与逐字源单元。
