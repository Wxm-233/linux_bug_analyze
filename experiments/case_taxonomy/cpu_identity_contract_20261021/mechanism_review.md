# N2.18 实际 12 组源码投影的机制复核

本复核只读 `experiment_pre.json`、`execution_gate.json`、`execution.json`、`results.json` 和已审的固定源／方法说明；没有重跑、采新源码、调用模型或修改原结果。`source_phase_review.md` 中 I1–I6 是先前提出的**备选矩阵**，不是本次执行。正式矩阵只有 `NR_CPUS=8`、`BITS_PER_LONG=64`、引导 CPU 0 初态、升序枚举 `dense_01`／`reported_ids_02`／`boundary_024`，各以早期上限 L=2/8 跑父、修两版，共 12 个版本/输入组合；多字位图、反序、重复或另一种配置没有覆盖。两份宿主 C 单元编译返回 0，12 次投影进程返回 0；这不是两版内核编译或实际 SPARC 启动。

## 此次真正区分出的关系

在相同 8 位 API 摘要和固定初态下，连续 `{0,1}` 四组父／修均输出 possible `{0,1}`。稀疏 `{0,2}` 在 L=2 和 L=8 时，父版都把 possible 变为 `{0,1}`，修复版保留 `{0,2}`；L=8 这一对尤其不依赖早期小上限，高 ID 2 仍在早期 `nr_cpu_ids=8` 内。构造 `{0,2,4}` 在 L=2 时父版 `{0,1}`、修复版 `{0,2}`，L=8 时父版 `{0,1,2}`、修复版 `{0,2,4}`。它只验证了**本投影中**修复前后“身份位被连续前缀替换／保留”的有限源效果，以及早期上限和后期最高置位上界的不同角色：如修复版 `{0,2}`、L=2 在公共重定界前 `nr_cpu_ids=2`，后为 3，mask 本身未变。研究者登记的三项条件关系给出父版 2 满足/4 违反、修复版 6 满足/0 违反；这是同一个已知案例的 12 次条件对照，不是 6 个缺陷，也不是系统范围的正确性证明。

**数量检查不足以发现该问题。** 12 组的 `weight(possible)=min(weight(已提供身份集合),L)` 均成立；父版把 `{0,2}` 改成 `{0,1}` 仍是两个 CPU，把 `{0,2,4}` 改成 `{0,1,2}` 仍是三个。损坏发生在身份对应关系，必须追踪集合成员以及“是否引入未提供 ID／无截断时是否保留原 ID”。复用 dense→sparse 的编号重命名对照在两种 L 下均为父版不交换、修复版交换，说明连续前缀重写依赖编号形状；它只重用原 12 次观察，不是新增样本或硬件上合法的任意重命名保证。

## 原模型谓词为何不能直接作为真值

`experiment_pre.json` 把原模型的 `present⊆possible`、boot0 在 possible、`max(present)<当前 nr_cpu_ids` 以及合取式与研究者条件要求**分开**。修复版 `{0,2}`、L=2 在重定界前因最高 present ID 2 不小于早期名额 2 而使合取式为假，重定界后上界 3 才为真；这是时点含义变了，并非 mask 被修补。修复版 `{0,2,4}`、L=2 在两个时点合取式都为假：修复路径把所有受理 ID 记为 present，却只选择两个 possible 身份，未选中的 4 不须在本次**条件性选择策略**下被强制 possible。boot0 一项在所有输入中由初态保证，没有区分力。故修复版合取式执行前 4 真/2 假、执行后 5 真/1 假不能报成“修复仍有两处／一处漏洞”。“截断合法”仅指登记的数量/阶段投影允许选择子集；本包没有证明这些输入属于真实 SPARC 的合法配置或全部内核 cpumask 使用前提。头文件一般说只依赖 `nr_cpu_ids` 内的位，尤其 L=2 时的高编号暂态仍是明确未证。通用 `maxcpus` 管激活数，不能拿它或最终 `nr_cpu_ids` 来倒填早期选择集合。

## 对跨架构机制的支持及缺口

本案例的源级支持是：SPARC OF 回调把固件 `cpuid` 直接用作 CPU mask 位，旧后处理却把“几个 CPU”误当“哪些 CPU”；公共 `cpumask` 的位位置表达逻辑 CPU 身份，`for_each_possible_cpu` 按这些位消费，SPARC 的 IRQ 栈／per-CPU 初始化因而接收被改写的集合。这为“架构提供的身份表示 → 数量/编号转换 → 公共按 ID 消费”的检查机制提供一个已知案例开发证据。它尚未证明真实固件顺序、`paging_init` 到 OF 枚举的全链、配置合法性、实际 CPU 在线结果或跨架构检出率。公共 `bringup_nonboot_cpus` 的已读串行分支用 present mask，不能把本次 possible 差异直接等同于其实际 bringup 决策或硬件失败。

另一个架构可以合法先将硬件 ID 映射为新的**逻辑** CPU ID；已读 ARM64 父版就有逻辑映射再设置 possible 的路径。因此不应把本次 SPARC 的 `possible⊆raw_firmware_ids` 无条件套到 ARM64。可迁移的检查应先确定各架构的映射、选择阶段及共同消费者使用的逻辑 ID 命名空间，再核“所选逻辑身份没有凭空产生／被静默替换”，并保留数量限制下未入选 present 的条件分支。ARM64 先前源码已曝光，且同用途正常运行未证，本次没有做第二架构配对。

下一项有研究增益的直接延续是：**先冻结这套提供者映射—选择集合—公共消费的条件协议，再用一个未参与规则开发的同机制案例和同用途正常实现作隔离对照**；无资格或证据不足仍计入预定分母。不要继续在 G 的已知输入上扩充替身来宣称泛化。
