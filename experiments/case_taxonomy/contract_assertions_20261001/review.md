# 从字段线索到自动生成的条件检查

日期：2026-10-01。研究任务是检验共性机制能否指导自动检查。本轮只使用已读历史材料和合成边界输入，没有新的独立留出、付费模型调用或确认缺陷数量增长。

## 本轮做了什么

新增 `../contract_assertion_generator.py`，接收上一轮单修订提取器的报告及其同版源码，重新计算并核对报告，再把完整、简单、定宽端序结构体生成最小 C 检查。当前支持直接局部对象、直接主机成员来源、16/32/64 位 LE/BE 字段、已绑定的原样复制链；整个载荷所有字段都必须有证据。缺字段、未知布局、重复来源、复杂声明、packing 上下文和篡改的报告/发射计划拒判。

生成计划保存原声明、原赋值、源码引用、来源类型、schema、适用条件及完整验证输入。实际生产者函数保留原始赋值；参考转换和逐字段漏转换是单列的对照，不替换实际生产者。消费者从实际写出的字节解码。Python 另以输入值、位宽和条件性格式计算字节与解码结果，避免只读取生成 C 的 pass 标签。

条件检查的准确写法为：

```text
bytes = P_original(v)
decode_C(bytes) == v
bytes == bytes_required_by_independent_format(v)  # 仅在格式有独立依据时
```

同版 `__le`/`__be` 字段可作为本轮原型的条件性 schema，但不凭字段名称认证外部设备协议。源成员实际数值、opcode 格式、完整预处理和运行路径仍须独立补证。生成器不自动修改内核、不自动加转换。

## 自动生成检查的运行结果

正式运行保存在 `final_run_01/`；`pilot_01/` 是开发过程输出，不作为锁定代码的最终运行证明。正式执行前后四个运行代码哈希一致，生成器 SHA-256 为 `84a0cb6c034ca1f885141ff331e831ea4d55fc92c20c2b0ff10280cf6a09433c`。

历史开发输入为 HCI 父版 `cef456cd354ef485f12d57000c455e83e416a2b6` 与修复版 `727ea61a5028f8ac96f75ab34cb1b56e63fd9227`。程序自动从两版各生成一个两字段载荷检查，分别在 x86_64 GCC 原生小端及 s390x GCC/QEMU 用户态大端运行。每字段使用两组非零不对称值和零值；下面仅统计非零活动字段检查，分母不是缺陷数量。

| 生产者变体 | 小端：不符/4 项 | 大端：不符/4 项 |
| --- | --- | --- |
| 父版原始两字段主机赋值 | 0/4 | 4/4 |
| 修复版原始两字段匹配转换 | 0/4 | 0/4 |
| 参考完整转换，两份计划分别运行 | 各 0/4 | 各 0/4 |
| 仅漏改 tx_len，两份计划分别运行 | 各 0/4 | 各 2/4 |
| 仅漏改 tx_time，两份计划分别运行 | 各 0/4 | 各 2/4 |

每个“版本×目标”有 48 个字段结果，四次共 192 行；其中含非活动字段零值与活动零值，不能把 192 行称作 192 个案例。Python 核对全部实际字节、解码值、输入、矩阵覆盖、pass 标签及字段偏移范围。GCC 声明图核对生成翻译单元内的实际生产者、目标字段和来源声明；不证明原内核完整翻译单元的同名绑定或配置可达性。普通 GCC 也不会验证端序 typedef 语义。

这些结果说明：在已提供的条件性 schema 和主机数值输入下，自动生成的检查能区分已知原始写法、完整转换与漏改字段；默认小端环境和零值可能掩盖相同问题。没有据此声称发现新的缺陷或已建立通用检测。

## 独立审计与检查自身的边界

17 项生成器测试通过。独立审计的 19 个有限探针符合预期，详见 `audit/code_audit.md`。审计找出并收束两类布局遗漏：外部 packing pragma 丢失，以及源码重定义 `__packed` 后被固定桩替换。最终程序遇到这两类已知上下文拒判；未读头文件中的任意预处理上下文仍不由本原型认证。

审计使用不同字段名的混合 LE16/BE32/LE64 载荷：原始主机赋值在小端 27 个字段结果中 2 项不符，在大端 27 项中 4 项不符；匹配转换两端各 27 项全部符合。Python 独立字节核验一致，64 位高位输入和本机 UBSan 未报运行错误。多变体共 540 行只是合成机制检查。零初始化及来源结构投影是原型措施；padding 不参与格式 oracle，不证明原历史对象或驱动行为。

## 为什么仅检查往返还不够

`paired_domain/` 从已读内部 coredump 的同版写读源码建立证据卡，并自动生成 16/32/64 位 × host/le/be 写读域的对照。只有 32 位旧 host/host 和新 le/le 两组关联该历史源码，其他域和宽度为合成对照。

每目标 81 行常规矩阵，两个目标共 162 行；同域 host/host、le/le、be/be 均还原原值。54 行非零输入每目标有 24 行预期混域失配，不能当成 24 个历史错误。原 coredump 消费者拒绝零值，矩阵中的零只是数值控制，不是完整初始化通过。

另有每目标一个共同错误变异：声称 BE/BE，但写读两端都执行 LE。它能读回原值，往返等式通过；独立格式核验拒绝实际字节和读端解释。由此可见，两端共享同一错误可能掩盖问题。系统检查应分别确认写出格式与实际读端，不能让两端相互背书。

内部同主机 host/host 的旧写读本来数值自洽，不能仅看到复制主机整数就要求固定小端。其未对齐指针、别名、生命周期与队列行为未由本轮 memcpy 投影证明，也未将该历史改动纳入新的确认核心样本。

## 对老师两个问题的进展

“怎样自动提取应该添加的检查”：本轮已经把受限的源码证据自动转成可执行条件检查，并加入不完整修复、布局拒判、独立字节 oracle。检查不是只根据修复补丁形状手写，但仍限于支持的简单字段/复制结构，真正独立同机制阳性与正常留出验证未完成。

“接口理解不同时以什么为准”：内部数据以同版、同模式实际消费者及来源链为依据；固定格式接口还需独立的版本化格式约束。源码声明与外部规范或运行模式冲突时先记为契约待决，不能按架构数量投票或强制统一端序。HCI 当前只达到条件性源码 schema，本轮没有新取得外部协议或设备执行证明。

下一步先补一项载荷的源数值、具体 opcode/读端及适用配置证据，建立“依据已证/条件性/不足/冲突”门控；再冻结至多两项新的同机制输入和有限选样池。没有合适材料时如实停在范围限制，不继续无限扩池。旧固定 12 条仍为 6/5/1；C1–C4、D2 通用泛化、D3 全部接口裁定、D4 NUMA 边界仍未完成。
