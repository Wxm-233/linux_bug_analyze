## 发现并已收束的布局问题

- 父执行者发现原结构体外的 `#pragma pack` 上下文会在片段复制中丢失。本审计独立 GCC 证实：16/32 位混合结构在 pack(1) 下大小为 6、第二字段偏移为 2；丢掉上下文后大小为 8、偏移为 4。
- 本审计发现已知 `__packed` 宏重定义也会被替换：源码把它定义为 aligned(16)，生成器却固定定义为 packed。独立 GCC 对照的原大小为 16、投影大小为 6；第二字段偏移分别为 4、2。该证明使用缩小有效 C，不是对已修改初读版本反复运行。
- 最终生成器对所读文件中的 packing pragma 和已知 `__packed` define/undef 保守拒判，两项探针均返回 refused。不扩展宏展开器，不认定未读头文件上下文已被证明。

布局证明源和命令见 `layout_context_proof.c`、`mixed_layout_proof.c` 与最终 C 运行 JSON。另核对三字段 plain/packed 结构：大小 16/14，第二字段偏移 4/2，第三字段偏移 8/6。padding 没有进入字段表示 oracle；生成程序的零初始化是缩小原型措施，并非原历史代码的行为证明。

## 断言没有通过同时改写两端而恒真

合成 payload 使用不同字段名：`small:__le16`、`medium:__be32`、`large:__le64`；源为对应位宽的主机成员，三字段全部覆盖，来源映射互不重复。实际生产者函数保留已复核原始赋值，reference/逐字段不完整转换是另列人工对照。消费者从生产者复制出的实际字节解码，Python 再按注入输入值独立计算 `to_bytes/from_bytes`，没有从 C 的 expected_value 或 pass 标签反推预期结果。

| 实际生产者 | 小端 GCC 原型 | 大端 s390x/QEMU 用户态原型 |
| --- | --- | --- |
| 三字段均直接写主机值 | 27 项字段检查中 2 项不符，来自非零 BE32 字段。 | 27 项中 4 项不符，来自非零 LE16/LE64 字段。 |
| 三字段匹配转换 | 27 项均相符。 | 27 项均相符。 |

reference 两端均相符；不完整转换在与漏转换字段相反的主机端序出现不符，在本机同端序或零值下可被掩盖。64 位输入包括高位非零的 `0xd6a57c3f1298b40e`；本机 GCC UBSan 没有运行错误。解码最大移位为 56，不发生 64 位移位。完整检查的是三字段的具体字节和数值，不检查 padding 或外部命令格式。
