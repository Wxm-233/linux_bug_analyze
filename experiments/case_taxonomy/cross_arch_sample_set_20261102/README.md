## 观察（只作描述）

1. **跨架构缺陷约占四分之一**（24.3%），与此前121条单函数修复中的21%相近。
2. **其他架构在修复时多半已经是对的**：134条中92条为S1。也就是说，多数跨架构缺陷在出现时，“参照对象”里已经有正确写法——这正是“对照参照对象做检查”能起作用的前提，也给同名函数跟随、约定级列点等方法提供了可评估的空间。
3. **一般缺陷类也大量跨架构**：M7有24条、M6有5条是跨架构的（例如KVM客户机可控下标的推测越界防护，arm64、x86早已做）。所以M6、M7虽是“一般缺陷类”，在跨架构样本中不能直接排除。
4. **M2只有1条**（A143，NAPOT不在内存表项），说明此前大页实验所依赖的机制在近期修复中占比很小；样本集的主体是M8、M7、M10、M1。
5. **掩盖方式判断不了的多达55条**，多数是提交说明只说了怎么修，没说为什么别处没出事。这一字段的证据较弱，使用时应注意。

## 标注过程的说明与局限

- 标注由研究者一人完成，逐条阅读提交说明和改动（超过60行的读统计和相关部分）。**第二人复核尚未做**：已按判据抽好40条（`second_sample.json`，不含标签），需要用户确定第二人；没有第二人的，作为局限写明。
- 跨架构条目的对应物位置，大多在修复前一版用`git grep`核实过；少数（如提交说明中直接点名的arm64、x86修复）依据提交说明。
- 机制只给一个主机制。约定：参照对象在RISC-V派生之后又改进、RISC-V未跟上的，或公共接口变化未跟上的，记M8；否则记内容上的机制（M1–M7、M9、M10），“参照对象早已改好”放在掩盖方式4中记录。
- 标注期间没有运行任何检测方法。
- 同一补丁出现两次的（如A149/A150、A188/A197、A190/A191、B444/B445），各按一条计。

- 按修订1的参考线，C/R一致性记为“中等”。抽样是C、R各20条的分层抽样，kappa不代表全体样本上的一致性。

**这次复核暴露的两点**

1. **X1用得太多。** 第一遍常把RISC-V自有代码里的一般缺陷（竞争、初始化时序、笔误）记成X1，而规则是“先按内容”。现有X1共123条（全部为R），不影响C/R和测试集，但影响R类的机制分布。若要用R类的机制分布，需要按内容规则重查。
2. **修订2第3条“调用上下文”的写法可被读成任何公共API误用都算共享约定**（如B464）。建议补一句：共享约定须是“各架构各自实现的那一方”所承担的要求，调用方误用公共API不算。
