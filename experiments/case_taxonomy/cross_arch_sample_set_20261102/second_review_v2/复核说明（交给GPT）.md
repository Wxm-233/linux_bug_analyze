# 复核任务说明

你是第二标注人。请独立阅读40条Linux内核修复提交（与上一批不同），对每一条判断两件事：

1. 它属于哪一类**缺陷机制**（只选一个主机制）；
2. 它是不是**跨架构缺陷**（C或R）。

材料在`全部40条材料.txt`（也按条拆在`材料/`文件夹中），每条包括提交说明、改动统计和改动内容（最多200行）。请把结果填进`answers_template.csv`。

请只根据材料和你对Linux内核的了解独立判断，不要去查这些提交在网上的讨论或别人的分类。

---

## 一、背景

我们研究的是“跨架构缺陷”：同一条要求由多个架构或公共代码共同承担，在别的架构上没问题（或被掩盖），在RISC-V上出了错。这40条都是2023年到2026年间Linux内核中与RISC-V有关的修复，内核版本范围是v6.6之后。

---

## 二、机制分类（每条只选一个主机制）

| 代号 | 名称 | 含义 | 例子 |
| --- | --- | --- | --- |
| M1 | 默认假设不适用 | 公共代码的默认实现或通用辅助函数，按“大多数架构”的表示方式写，RISC-V的表示方式不同 | 公共代码默认一个大页只对应一个页表项，而某些架构用多个页表项拼成一个大页 |
| M2 | 页表项状态与信息来源不符 | 从页表项内容里读大小、分组、物理页号等，但这个页表项此时可能不在内存（空、swap、迁移等），内容里没有这些信息 | 对不在内存的大页表项用`pte_napot()`判断大小 |
| M3 | 修改映射或代码的步骤 | 修改正在使用或多项组成的映射时须按顺序：先清空、刷新TLB、再写入，整组一起改；改写代码后须维护指令缓存 | 修改由多项组成的映射前没先清空并刷新TLB |
| M4 | 原子性与内存顺序 | “读出再修改”须原子；弱内存模型下发布数据前须有屏障 | 先读后清代替原子交换；完全有序的原子操作漏了屏障 |
| M5 | 执行上下文 | 关中断、异常入口、NMI、单步、关抢占等上下文中的限制，例如不能睡眠、不能被插桩、不能迁移CPU | NMI中取普通自旋锁；单步窗口中再次触发探测 |
| M6 | 资源生命周期与出错路径（一般缺陷类） | 漏释放、重复释放、释放后使用、出错路径没清理、状态未初始化 | 内存泄漏、`of_node_put`遗漏、空指针 |
| M7 | 边界、宽度、对齐（一般缺陷类） | 差一、整数宽度、符号扩展、溢出、对齐、随配置变化的上限 | 32位上`1UL`不够宽；下标越界 |
| M8 | 落后于参照对象的演进 | RISC-V的实现源自参照对象（其他架构的代码或公共约定）的旧版本，参照对象后来的修补或改法没有同步；公共接口改了、RISC-V没跟上也属于这一类 | 公共代码新增了一种返回值、要求各架构处理，RISC-V没处理；arm64早已修好的问题RISC-V照旧 |
| M9 | 特性与配置条件 | 默认假定某个ISA扩展、固件功能、编译器能力或Kconfig组合存在或不存在；替代补丁、能力检查错误 | 未开某选项时编译失败；依赖了可选扩展却没检查 |
| M10 | 同一约定、各自实现、条件或顺序不一致 | 一条公共约定（系统调用ABI、KVM接口、信号语义、公共代码调用的钩子等）由各架构各自实现，接口本身没变，但RISC-V在判断条件或步骤顺序上与其他架构不同 | 系统调用号为-1时其他架构返回`-ENOSYS`，RISC-V不返回；恢复状态的先后顺序与arm64不同 |
| X1 | RISC-V自身逻辑 | 只与RISC-V自己的规范、协议或功能有关，没有其他架构或公共代码共同承担的对应要求 | SBI调用返回码、AIA中断控制器寄存器语义、RISC-V指令解码 |
| X2 | 其他 | 笔误、注释、日志、文档、纯重构、编译告警、测试或工具代码，或者“修复”并不改变行为 | 拼写、删无用代码、sparse告警 |

**选择规则（按顺序判定，先按内容，后按传播）**
1. **M8只用于两种情形**：
   - (a) 公共接口或语义发生了变化（例如公共代码新加了要求、改了参数含义），RISC-V没有跟着改；
   - (b) RISC-V的代码照着参照对象写成，而参照对象的修复**晚于**RISC-V代码写成的时间。
   - 如果参照对象在RISC-V代码写成之前就已经是对的（RISC-V照抄时漏了，或者另写时没照着做），**不选M8**，按内容归类。
   - 判断不了先后的，按内容归类。
   - 缺陷就在公共代码本身（不是RISC-V没跟上），也不选M8，按内容归类。
2. **M10与M7**：修复改变的是数值的宽度、符号扩展、边界或对齐的，选M7；改变的是判断条件或步骤顺序的，选M10。
3. **M1与M6、M7**：根源是公共代码对表示方式的假设在RISC-V上不成立的，选M1，即使表现为空指针或越界。
4. **M9与X1**：只有缺陷来自“假定某个扩展、固件功能、编译器能力或配置组合存在或不存在”时选M9；RISC-V特有设备或固件接口的默认行为问题选X1。
5. M6、M7是一般缺陷类，但只要内容符合，照样选它们。

## 三、跨架构判断（C或R）

记为**C（跨架构）**，必须同时满足下面五条：

1. **有对应物**：被违反的那条要求，也由其他架构或公共代码承担。对应物分三种：
   - **K1 公共约定的另一种实现**：公共代码调用、各架构各自实现的钩子或接口，例如`huge_ptep_get_and_clear`、`machine_shutdown`、系统调用ABI、KVM接口；
   - **K2 其他架构的同类实现**：没有公共钩子，但其他架构有做同一件事的代码，例如各自的BPF JIT、页表遍历、异常入口处理；
   - **K3 公共代码本身**：问题就在公共代码里，在RISC-V上暴露。
2. **能指出对应物的具体位置**：至少写出一处其他架构或公共代码中对应的文件（尽量写到函数）。只凭“别的架构大概也有类似代码”不算。
3. **被违反的要求是“共享约定”，不能只是通用编程正确性。**
   - 共享约定指：公共接口或钩子的语义（参数、返回值、调用上下文、调用顺序）；公共代码对架构的假设；同一硬件或软件机制在各架构上都必须遵守的具体规则（例如“改写代码后须维护指令缓存”“释放页表后须刷新TLB”“NMI上下文中不能取普通锁”）。
   - 以下**通用编程正确性**本身不算共享约定：下标或长度差一、空指针未判断、资源泄漏、变量未初始化、错误码不对、笔误。除非这个错误只因为RISC-V与其他架构的差异（表示方式、宽度、调用约定等）才出现。
4. **K2必须指出其他架构中处理“同一个具体条件”的代码**，而不只是一个做类似事情的函数。写法为“文件:函数（处理了什么条件）”。例如“`arch/arm64/kernel/syscall.c:el0_svc_common`（系统调用号为-1时把x0置为-ENOSYS）”可以；“x86也有ptrace实现”不可以。
5. **K1必须写出公共钩子或接口名，以及被违反的那条语义；K3必须指出公共代码中做出错误假设的位置。**

不满足的记为**R（仅RISC-V）**。

**注意**
- “别的架构修过同名函数”只是一种证据，不是必要条件。即使其他架构从没出过问题，只要满足上面五条，就记C。
- 第3、4条拿不准的，记R，并在理由中说明。
- 纯笔误、注释、测试代码等X2类，一般记R。
- 你看不到内核源码，“对应物位置”请凭你对内核的了解写；拿不准时写你认为最可能的位置，并在理由中注明“未核实”。

## 四、答题表怎么填

打开`answers_template.csv`，每行一条，前三列（序号、编号、提交）已填好，请填后五列：

| 列 | 填什么 |
| --- | --- |
| 机制 | M1–M10、X1、X2之一，只填代号 |

请保持40行、顺序不变，不要改动前三列。输出时请给出完整的CSV文本（UTF-8，带表头），方便直接保存。

如果一次处理不完，可以分批（例如每批10条），但每批都按同一份说明判断。
