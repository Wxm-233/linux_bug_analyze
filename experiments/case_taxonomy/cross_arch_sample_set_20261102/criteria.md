# 跨架构缺陷样本集（判据，实现前写定）

## 这一轮要回答什么

复核实验（`mixed_sample_replication_20261102/`）的样本按“有修复记录”抽取，多数不是跨架构缺陷，检验不了跨架构机制本身。要回答“机制能否指导检测”，需要一套**以已确认的跨架构缺陷为主**的样本，供后续各种检测方法（约定级列点、同名函数跟随、机制目录加模型等）共同评估。

本轮只建样本集：确定范围，逐条标注，冻结标签，划分开发集与测试集。**不评估任何检测方法**，不调用模型。

## 一、样本来源

范围统一为`v6.6..df2908090cda`中带`Fixes:`的非合并提交。

| 来源 | 规则 | 规模（写判据前已数过，只数个数，未读内容） |
| --- | --- | --- |
| **A RISC-V架构代码的修复** | 改动`arch/riscv/`，排除只改`arch/riscv/boot/dts/`（设备树）的提交 | 401个（含dts为453个） |
| **B 公共层或驱动中与RISC-V有关的修复** | 不改`arch/riscv/`，提交说明中出现`riscv`或`RISC-V`（不区分大小写，含`risc-v`） | 202个（其中标题中出现的88个） |

B类用来覆盖研究重点“公共层到RISC-V”：问题在公共代码或驱动里，但在RISC-V上暴露或由RISC-V报告。B类中提交说明只是顺带提到RISC-V（例如测试平台列表、抄送名单），与问题本身无关的，标为“无关”，不进入样本集。

## 二、“跨架构缺陷”的定义

一个修复记为**跨架构（C）**，必须同时满足：

1. **有对应物**：被违反的要求，也由其他架构或公共代码承担。对应物分三种：
   - **K1 公共约定的另一种实现**：公共代码调用、各架构各自实现的钩子或接口（如`huge_ptep_get_and_clear`、`machine_shutdown`、系统调用ABI、KVM接口）；
   - **K2 其他架构的同类实现**：没有公共钩子，但其他架构有做同一件事的代码（如各自的BPF JIT、kexec段装载、crashkernel预留）；
   - **K3 公共代码本身**：问题就在公共代码里，在RISC-V上暴露（主要来自B类）。
2. **能指出对应物的具体位置**：写出修复前一版（`修复^`）中对应物所在的文件和函数，至少一处。**只凭“别的架构大概也有类似代码”不算。**

不满足的，记为**R（仅RISC-V）**。

另外对每条C类记录：

- **对应物在修复时的状态**：
  - S1 其他架构当时已经正确；
  - S2 其他架构也有同样问题（同时或之后才修）；
  - S3 其他架构没有这个功能或这条路径；
  - S0 判断不了。
- **为什么在别处没暴露、或在RISC-V上长期没发现**（对应“五种被掩盖的情况”）：1 表示方式不同；2 出问题的状态在某些架构上走不到；3 执行环境遮住了后果；4 别的架构早已改好；5 修复只移植了一半；0 判断不了。

**避免循环论证**：“别的架构修过同名函数”只是S1或掩盖方式4的一种证据，**不是**进入样本集的条件。进入样本集只看上面两条（有对应物、能指出位置）。这样之后评估“同名函数跟随”时，它的查全率才有意义。

## 三、逐条标注的内容

| 字段 | 内容 | 谁来填 |
| --- | --- | --- |
| 提交、日期、标题、`Fixes:`指向的提交 | — | 程序 |
| 引入问题的提交是否改动了`arch/riscv/` | 用来区分“公共层改动引发”与“RISC-V自身引入” | 程序 |
| 改动的文件、函数、行数 | 按改动行所在函数确定 | 程序 |
| 机制 | 按`catalog_v2.md`归为M1–M10、X1、X2之一；一条只给一个主机制 | 研究者 |
| 跨架构 | C或R | 研究者 |
| 对应物 | 种类（K1/K2/K3）与位置 | 研究者（仅C） |
| 状态与掩盖方式 | S0–S3；0–5 | 研究者（仅C） |
| 附加标记 | **构建错误**（只修编译、链接错误，编译器本身就能发现）；**非C代码**（只改汇编、Kconfig、Makefile、链接脚本）；**无关**（B类中与RISC-V无关） | 研究者 |
| 理由 | 一句话 | 研究者 |

- 研究者逐条阅读提交说明和改动。改动超过60行的，读改动统计和与问题有关的部分，并在理由中注明。
- 此前已标注的121个单函数修复（`mech_catalog_validation_20261102/labels.py`），按第二版目录**重新核对**：原标签保留，改动的逐条记录原因（预计主要是X1改为M10）。

## 四、开发集与测试集

此前几轮已经看过一部分修复，并据此改写了M8、提出了M10。如果用它们评估检测方法，结果会偏乐观。所以：

- **开发集**：
  - 此前标注过的121个单函数修复；
  - 案例分析、M8传播链、M10三个案例、约定级试点中用过的修复；
  - 程序按提交号列出，不靠记忆。
- **测试集**：其余全部。
- **规则**：
  - 检测方法只能在开发集上设计和调整；
  - 每种方法在测试集上只运行一次，运行前写定判据；
  - 本项目自己发现的两个缺陷（NAPOT清除、`machine_shutdown`）不在上述范围内（没有上游修复），单独作为特别样本，不计入统计。

## 五、标签的冻结与复核

- 全部标注完成后，记录`labels.json`的SHA，此后不再修改。确有错误的，另写修订文件说明，原文件保留。
- **标注期间不运行任何检测方法**，不看任何检测方法对这些提交的输出。
- **第二人复核**：从全部C类中随机抽20条、R类中随机抽20条（`random.Random(20261102)`），由第二人独立标注“C或R”和“机制”，计算一致率和kappa。人选待用户确定；没有第二人的，如实注明“单人标注”，作为局限。

## 七、之后怎么用（本轮不做，各自另写判据）

- 对每条C类，用程序取出修复前、修复后的代码，作为“有bug/已修复”配对；
- 各检测方法在测试集上比较：修复前能否标出，修复后会不会误报；
- “同名函数跟随”的查全率上限，就是S1中“其他架构先修过同名函数”的比例。
