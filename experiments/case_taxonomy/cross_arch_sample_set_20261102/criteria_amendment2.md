# 判据修订2：收紧“跨架构”和机制边界（复查标签之前写定）

## 为什么改

第二标注人复核（`agreement.json`、`adjudication.json`）发现两处定义太松：

1. **K2“其他架构的同类实现”太宽**：只要别的架构有做类似事情的函数就能算C，结果下标越界、空指针、驱动自身逻辑也能算跨架构。9条C/R分歧中有6条出在这里。
2. **机制边界不清**：M8与M10、M10与M7、M1与M6、X1与M9。

本修订只改判定规则，不改样本范围。已冻结的`labels.json`和修订1不动，按本修订复查后的结果另存为第二版标签。

## 一、跨架构（C）的收紧规则

原定义两条（有对应物、能指出位置）保留，再加三条，**全部满足才记C**：

3. **被违反的要求必须是“共享约定”，不能只是通用编程正确性。**
   - 共享约定指：公共接口或钩子的语义（参数、返回值、调用上下文、调用顺序）；公共代码对架构的假设；同一硬件或软件机制在各架构上都必须遵守的具体规则（例如“改写代码后须维护指令缓存”“释放页表须刷新TLB”“关中断时不能睡眠”“客户机可控下标须防推测越界”）。
   - 以下**通用编程正确性**本身不算共享约定：下标或长度差一、空指针未判断、资源泄漏、变量未初始化、错误码不对、笔误。除非这个错误只因RISC-V与其他架构的差异（表示方式、宽度、调用约定等）才出现。
4. **K2必须指出其他架构中处理“同一个具体条件”的代码**，而不只是一个做类似事情的函数。写法为“文件:函数（处理了什么条件）”，并在修复前一版用`git grep`核实。例如“arm64 `vgic_get_irq`对客户机给出的中断号做`array_index_nospec`”可以；“x86也有PMU读取函数”不可以。
5. **K1必须写出公共钩子或接口名，以及被违反的那条语义**；K3必须指出公共代码中做出错误假设的位置。

不满足3–5条的，改记R。

## 二、机制边界的规则

按以下顺序判定，**先按内容，后按传播**：

1. **M8只用于两种情形**：
   - (a) 公共接口或语义发生了变化（通常`Fixes:`指向的是公共代码的提交），RISC-V没有跟着改；
   - (b) RISC-V的代码派生自参照对象，而参照对象的修复**晚于**派生。
   - 若参照对象在RISC-V代码写成之前就已经是对的，按内容归类（M1–M7、M9、M10），并把掩盖方式记为4（别的架构早已改好）或5（只移植了一半）。
   - 判断不了先后的，按内容归类。
2. **M10与M7**：修复改变的是**数值的宽度、符号扩展、边界或对齐**的，记M7；改变的是**判断条件或步骤顺序**的，记M10。
3. **M1与M6、M7**：缺陷的根源是公共代码对表示方式的假设在RISC-V上不成立的，记M1，即使表现为空指针或越界。
4. **M9与X1**：只有当缺陷来自“假定某个扩展、固件功能、编译器能力或配置组合存在或不存在”时记M9；RISC-V特有设备或固件接口的默认行为问题记X1。

## 三、怎样复查

- 对修订1之后的全部跨架构条目（136条）逐条按第一节复查，不满足的改为R并写明原因。
- 对全部M8条目按第二节第1条复查先后，必要时查参照修复与RISC-V代码的日期。
- R条目中，只复查第二标注人记为C的条目（按新规则是否成立）；其余R条目不因本修订改为C。
- 结果另存为`labels_v2.json`，并列出每条改动的原因；统计与参考线按原判据重新计算。
