## 第三轮结论（6 个构建）

- **六个构建、五种位布局，三条义务全部成立**。在合法域（类型 0～MAX_SWAPFILES-1，偏移 1～2^K-1）上，对所有取值逐位证明：
  - O1：编码后的页表项既不会被当成有效映射，也不会被当成空项；
  - O2：编码本身不占用会被清掉的标志位；
  - O3：读回来的类型和偏移与写入时逐位相同。
- **编码容量是我们自己推出来的**（不用内核的探测值），然后和内核的探测值对账，六个构建都一致：riscv64 52 位、x86_64 50 位、arm64 50 位、i386 PAE 26 位、i386 非 PAE 23 位、rv32 20 位。
- **与编译器对账：每个构建 33 个具体值（6 组输入 × 5 个量，加 3 个常量）全部一致，0 处不一致**，满足“至少两种布局各 ≥ 6 组”的门槛。
- **没有发现编解码违反**。这在预期之内：这几种编码都是移位、掩码、取反，上游也有构建期检查（`MAX_SWAPFILES_CHECK`）。
- **原生测试退化得到编译器确认**：在真实 x86_64 构建上，clang 把 `debug_vm_pgtable.c:1229` 的表达式折叠成常数 **0**；其余五个构建上它都等于“探测值 - 1”，也就是本意要测的最大偏移。所以第 2 天的发现不再只靠照抄宏的小程序。

## 一、方法

- **逐位符号位向量**（`swapsym.py`）：每一位是常量 0/1、某个输入（t 或 o）的第 i 位（可带取反），或者来历不明的未知位。按位运算、常数移位、截断、零扩展、符号扩展都逐位精确；加减乘只在两边都是常数时才计算。把它装进第 1 天修正过的页表求值器（`toolfix_20261121/evalpg.py`，只导入，没有修改），在真实构建上对合成函数求值。
- **真假判断带上输入域**：要判断一个条件（例如 `pte_none`）是否恒假，就看“相关位全为 0”在域内能否满足。每一位只能是常量或输入位，再加上 o ≥ 1、t ≤ MAX-1 两个约束，可以精确判定；判不了的记“未知”，不当作成立。
- **输入域**：t 的低 5 位自由，并且 t ≤ MAX_SWAPFILES-1（MAX_SWAPFILES 从各构建求出：arm64 是 27，其余是 28）；o ≥ 1，只有低 K 位自由。K = min(32, K_enc)，其中 32 来自交换区头部的 32 位 `last_page`，K_enc 是编码容量。
- **编码容量 K_enc**：让 o 取公共偏移的全部位宽（64 位上 58 位，32 位上 26 位），跳过 present/none 判断直接解码（和 `generic_max_swapfile_size` 一样），数从第 0 位起有多少位能原样读回。
- **对账**：用该构建的编译参数，让 clang `-O2` 把 `C_i(void) { return S_xxx(具体 t, 具体 o); }` 编成 LLVM IR，读出折叠后的返回常数，与符号结果代入同一组值的预测逐个比较。6 组输入是 (0,1)、(1,2)、(MAX-1,1)、(MAX-1,2^K-1)、(MAX/2,2^(K-1))、(3,0x2345 与 2^K-1 相与)。

## 二、校准

`calib_sym.json`：18 个 8 位表达式（按位运算、取反、各种移位、有符号右移、符号扩展、截断，以及 x86 那种“取反、左移、右移”组合），与 clang 编译后对 256 个输入的具体结果逐个比较，**0 处矛盾**。比较类运算在输入不定时给出“未知位”，不会给出错误的确定值。

第一次运行时 `!x` 报 1 处矛盾，原因是校准也套用了“o ≥ 1”的域约束，把 x = 0 排除了。校准改为不加这条约束后为 0。这是校准设置的问题，不是运算错误。

## 四、原生测试的退化（第 2 天发现，本轮确认）

- `mm/debug_vm_pgtable.c:1229`：`max_swap_offset = swp_offset(softleaf_from_pte(softleaf_to_pte(swp_entry(0, ~0UL))))`，然后用 `swp_entry(MAX_SWAPFILES - 1, max_swap_offset)` 作为所有交换项测试的唯一输入。
- x86_64 上类型 0、偏移全 1 编码后整个页表项是 0，`softleaf_from_pte` 判为空项，`max_swap_offset` 就成了 0。**clang 在真实 x86_64 构建上把这个表达式折叠成 0**（`sym_x86_64.json` 中 `C_S_dbg`），与符号求值一致。
- 其余五个构建上都等于探测值 - 1。i386 PAE 也取反，但 32 位上公共偏移只有 26 位，取反后高位仍是 1，所以不受影响。
- 后果：在 x86_64 上，`pte_swap_tests`、`pte_swap_exclusive_tests`、`pte_swap_soft_dirty_tests` 测的都是偏移 0。真实交换里不会出现偏移 0（第 0 槽是交换区头部），偏移位全是 1（取反后）的情况也就没测到。
- 引入：`a3a3e215c9c1`（v6.19-rc1）。同一个提交在 `generic_max_swapfile_size()` 里手工绕开了同样的问题，测试这一处没有。本地最新主线 `65e4fd942f72`（11-19）上仍是这样。
- 可能的修法（没写补丁）：照 `generic_max_swapfile_size()` 的做法手工解码，或者直接改用 `generic_max_swapfile_size() - 1`。
- **没有登记、没有对外报告**，由用户决定。

## 五、局限

- 只覆盖普通交换项和这五种布局。迁移项、设备私有项、hwpoison、marker 以及 PMD 级的编码没有检查。
- 偏移域按交换区头部封顶在 2^32-1。如果将来交换区格式允许更大的偏移，64 位架构上需要按 K_enc 再证一次（逐位结果显示，在 K_enc 以内同样成立，但这一点没有单独记录为结论）。
- O1 用的是各架构自己的 `pte_present`、`pte_none`。如果某个架构另有“看起来像交换项”的判断（例如 `is_swap_pte` 的变体），没有覆盖。
