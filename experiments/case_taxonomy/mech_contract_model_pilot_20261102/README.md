# 约定级建模试点：“脏页记录期间只能按页粒度映射”

## 这一轮要回答什么

上一轮发现M10规则只覆盖约定的一个实现位置，泛化不了。本轮试点“约定级建模”：先列出一条约定在各架构上的**全部实现位置**，再在RISC-V上逐个位置核对。

- **约定C**：内存槽开启脏页记录期间，二级页表映射只能是页粒度；开启记录时、清除记录时已经存在的大页，要么整块写保护、之后再拆，要么直接拆成页。
- 判据：`criteria.md`（SHA `97827477…`）。全部为人工阅读，不调用模型，不构建内核。

## 第一步：实现位置清单

**来源**：
- 公共代码`virt/kvm/kvm_main.c`中与脏页记录有关的架构钩子：`kvm_arch_commit_memory_region`、`kvm_arch_mmu_enable_log_dirty_pt_masked`（取记录、清除记录、脏页环复位都会调用）、`kvm_arch_sync_dirty_log`；
- 加上arm64、x86缺页处理中与映射大小有关的位置。

| 位置 | 公共调用点 | arm64怎样满足 | x86怎样满足 |
| --- | --- | --- | --- |
| P1 开启记录（提交内存槽） | `kvm_commit_memory_region` → `kvm_arch_commit_memory_region` | 除“手动保护并初始全置位”模式外，对整个内存槽写保护，可选主动拆分 | `kvm_mmu_slot_apply_flags`：写保护，可选主动拆分 |
| P2 清除记录、取记录、脏页环复位 | `kvm_arch_mmu_enable_log_dirty_pt_masked` | 对指定页写保护；初始全置位模式下拆分覆盖这些页的大页 | 写保护包括大页；拆分范围须向大页边界取整（`1aa4bb91`修的就是这里的差一错误） |
| P3 缺页时决定映射大小 | 各架构缺页处理 | `memslot_is_logging()`为真时，`max_map_size`为页大小 | 脏页跟踪开启时，最大映射级别为4K |
| P4 记录期间，缺页落在已有大页上（写或非写） | 各架构缺页处理 | 按页重新映射并拆块；拆分需要预先补充页表缓存（`56fd1fc5`），并且要在MMU写锁下进行（`f587661f`） | 以页级表项替换大页 |

**不属于约定C、但相关的位置**（记录，不核对）：
- 关闭记录后恢复大页：属于性能，不是约定；
- 硬件脏页同步`kvm_arch_sync_dirty_log`：RISC-V为空实现；
- 更大的约定“每一次写入都要被记录”：例如KVM代替客户机写内存时要标脏（x86 `910c57df`）。它与C是同一目标下的另一组实现位置。

## 第三步：RISC-V逐个位置核对（终点版本）

| 位置 | RISC-V实现 | 结论 |
| --- | --- | --- |
| P1 | `kvm_arch_commit_memory_region`（`arch/riscv/kvm/mmu.c`约239–256行）：初始全置位模式直接返回，否则`mmu_wp_memory_region`，可选`mmu_split_memory_region` | 满足 |
| P2 | `kvm_arch_mmu_enable_log_dirty_pt_masked`（约160–183行）：`kvm_riscv_gstage_wp_pt_masked`遇到大页时整块写保护（`clear_huge_mask`）；初始全置位且开启主动拆分时，`mmu_split_huge_pages`从按PMD对齐的起点逐块拆，没有x86那种差一错误 | 满足 |
| P3 | `kvm_riscv_mmu_map`：开启记录时`vma_pagesize = PAGE_SIZE`；hugetlb也在这一判断之后；THP调整只在`!logging`下进行（`b342166c`之后） | 满足 |
| P4（写缺页快速路径） | `kvm_riscv_mmu_dirty_log_write_fault_fast`（2026年5月新增）：只处理页级表项（`ptep_level`不为0就退出），大页交给慢路径 | 满足 |
| P4（慢路径） | `kvm_riscv_gstage_map_page`：发现更高层的叶子就调用`kvm_riscv_gstage_split_huge`拆到页级；在进入映射前无条件补充页表缓存；拆分在`mmu_lock`写锁下进行；非写缺页时只映射为只读页 | 满足 |

**RISC-V的4个位置全部满足约定C，没有发现违反。**

- arm64那两条留出违反（缓存补充、加锁），RISC-V的写法天然不会犯：缓存无条件补充，拆分本来就在写锁下。这说明逐位置核对不仅能发现问题，也能**有依据地排除**：别的架构出过的问题，在RISC-V上不适用。
- RISC-V在这条约定上的两个历史违反（P2、P3）都已经修好。

## 判定

- **约定级建模有效**：已知违反覆盖5/5，其中留出2/2；清单中有3个位置是上一轮规则没有检查的。
- **对RISC-V**：全部位置核对完毕，没有新的疑似问题。

## 解读

1. **“先列位置”解决了上一轮的漏报问题**：约定的违反分散在P2、P3、P4三个位置，只要清单完整，每一条都落在某个位置上。
2. **列位置的方法可以机械化**：
   - 公共接口部分：沿公共代码中与这条约定相关的架构钩子去找；
   - 缺页处理部分：要靠参照架构的实现来提示。
   这一步可以交给模型提出候选位置，再由人或规则确认。
3. **逐位置核对，要回答的仍是“保证来源”**：在每个位置上，RISC-V靠什么满足约定（函数、条件、锁、缓存补充）。这就是M2规则里的“适用条件加保证来源”，现在推广到了约定的每个实现位置。
4. **代价**：本轮是一条约定的人工试点，读了约20个函数。推广到更多约定，需要把“列位置”和“逐位置核对”都做成半自动。

## 统计

不调用模型；构建0；新确认缺陷0；新疑点0。
