# 多样化的基础用例（diverse_dev_20261110）

## 这一轮要回答什么

上一轮（`mix_dev_20261110`）的混合生成得到了历轮最好的一组（G2x 确认合计 9），但 A101 时有时无，A181 没有检出。原因是基础用例离多条件状态太远：
- 每个系统调用只试 48 个候选，`mmap`、`recvmsg` 都没找到合法的基础用例；
- 每个系统调用只留前 2 个基础用例，往往是同一类 fd。

这一轮只改基础用例的来源和挑选，其余与上一轮完全相同（判据 `criteria.md` 在实现之前写定）：
- 校准候选从 48 个加到 128 个，前 48 个与之前完全相同（已逐个核对），在统一加载地址后重新校准；
- 每个系统调用最多留 6 个合法基础用例，优先取“fd 类型、资源、路径、是否结构化”这一签名互不相同的。

- **G3d 第一次在一组里检出了全部 5 条缺陷。**
- **A181 第一次在 2 个种子中检出**（G3d 种子 2、3）：合法基础用例本身就是“数据报套接字＋结构化 msghdr＋错开的控制缓冲区”，变异只改了无关的 `msg_flags` 字段，触发条件就保住了。
- **A101 的原始症状第一次出现**（用例 4321）：从新的合法 `mmap` 基础用例出发，只改了一处，用区间模板占住提示地址。修复前返回 ENOMEM，修复后和参照都另找位置映射成功，正是修复说明描述的症状。
- **按事先写定的参考线（某组 4 条缺陷各 ≥2 种子），“多样基础用例有增益”不成立**：G3d 是 3 条（A310、A171、A181），A101、B467 各只有 1 个种子。
- 41 个检出用例全部确认（`confirm.json`）。我事先写的 A101 关键条件仍然过窄（要求 flags 的映射类型为 1 或 2、长度 ≥ 地址），检出的 3 个用例都不满足它，如实记录。

## 看出的几点

1. **基础用例的质量直接决定多条件缺陷能否被触发。** `mmap`、`recvmsg` 一旦有了合法基础用例，A101 的原始症状和 A181 只差一处改动，就都出现了。
2. **单个缺陷在 3 个种子里的稳定性仍然有限。** 每组 1000 个用例分到约 40 个目标系统调用上，每个只有二十几个用例，A101、B467 这类只在一个系统调用、一个参数或字段上触发的缺陷，有一个种子没撞上也正常。要稳定，要么增大预算，要么让变异位置偏向“提示点相关的参数和字段”。
3. **噪声已经降到很低**：当前版本只有 10 个与众不同的聚类，全部能解释，没有测试自身的问题。比较和剔除这一侧已经比较成熟。

## 局限

- 开发集，数字小，而且我读过这 5 条缺陷的修复说明；
- 多样性签名只看 fd、资源、路径和是否结构化，不看 flags 等标量；
- 本轮没有新建内核。
