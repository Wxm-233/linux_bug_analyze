## 实际完成了什么

[新版程序](context_binding.py)不要求模型抄写完整函数，而从同一request的完整源码片段恢复作用域、参数和局部别名；原模型引用与程序扩展原文分别保存。实际路径为：

`S_core 5753–5794函数／cpu参数 → 5755局部smt_mask → 5760调用实参／形参 → S_locks 240–248 → 246内容遍历`。

这是一个受限的完整函数、局部路径和单调用边识别器，不是通用C解析、全程序别名分析或并发证明。未知中间语句、分支、未展开任意调用以及影响cpu／alias的写入均保守拒判。独立审查发现原版本漏掉前缀、位复合和下标等写法，已补拒判并测试；当前实际片段没有这些写法，原两组结果未改变。`cpu_rq`、`local_irq_save`只作为标注的局部helper假设，不声称完整纯度已证明。

| 结论层次 | 本轮结果 | 必须保留的限制 |
| --- | --- | --- |
| 原引用所属函数与参数 | 两组都能自动恢复完整上下文及显式实参／形参连接 | 扩展证据来自程序，不冒充模型原引用 |
| 模型原5755锚点 | 仍为取得指针；两组原位置求值均insufficient | 没有该精确时刻的独立内容观测 |
| 程序另提的内容消费位置 | 识别sched_core_lock中的掩码遍历 | 不是静默改写模型consumer或模型已自动选点 |
| 归档实际采样 | 在local_irq_save之前采样内容，非遍历时刻原子快照 | 原位置、精确遍历值、全区间稳定及并发均未证明 |
| 原AST在另列采样点的事后诊断值 | 两组均旧s390为false，其余三格true | 不是原锚点验证、新运行、新缺陷或独立泛化 |

结果分别见[配对诊断来源](pair_context.json)、[去架构正式来源](ablated_context.json)。配对仍来自上阶段的posthoc诊断正文，不变成正式协议通过；去架构仍保留local_candidate。两组的原AST／polarity／consumer不变。值从已核对的原始mask成员计算，不读旧status／predicates或oracle作答案。

继承归档基础检查中的`same_mask_until_first_consumer`只表示若干离散采样相等，不能解释为连续稳定。多字段非原子读取，计数发生在真实锁完成后，打印发生于unlock后；同对象也不等于内容在整个时间区间不变。详见[源码／观测独立复核](source_consumption_review.md)、[原始摘录](consumption_evidence.json)和[实现独立复核](implementation_review.md)。

## 对跨架构机制的推进

本轮把一个候选检查拆为三个可核对部分：**公共消费者需要什么状态 → 架构提供者在什么资格和阶段准备状态 → 程序能在哪个真实内容使用／观测位置检查。**

同CPU、同getter和显式参数映射可以支持受限静态连接；是否按时满足要求，还需要架构准备资格、有效配置、初值和消费阶段证据。s390的online资格及较晚准备、x86的通知前准备仍是本例的重要差异；当前代码／归档支持限定首次启动解释，不覆盖真实SMT、热插拔重入或并发。

旧候选的必要性理由仍需修正：leader查找跳过当前CPU，后续安装循环才处理它；weight==1不是非空断言，也不能单独证明唯一成员就是目标CPU。成员条件只是必要窄候选，不能验证完整兄弟集合或leader有效性。这些是研究侧源码复核，不能登记成这轮Claude已自行修正。
