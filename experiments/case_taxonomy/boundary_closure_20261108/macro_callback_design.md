# 我怎样补宏和回调，哪些地方仍保留整块代码

## 宏：记录外层使用，再追候选定义

宏是预处理器在编译前替换的代码。比如当前内核的 `pfn_to_page(pfn)` 经 `__pfn_to_page` 使用架构定义的 `vmemmap`，但旧枚举表只看到了外层使用。A058 改的正是 `vmemmap`。我在当前 `mm/sparse.c` 的一个既有编译命令上验证：libclang 的详细预处理记录没有一条 `vmemmap` 展开记录；沿宏定义的 token（名字、标点等词法单元）追依赖后，15 处所选外层使用能走到它。证据是 `real_prototype_result.json` 与 `evidence/prototype/A058_macro_dependencies.json`。

因此，**单靠 libclang 的详细预处理记录不能恢复完整的嵌套展开链**。我仍用它取得当前编译单元可见的宏定义、外层展开、定义位置及活动条件分支；另运行同一参数的 `clang -E -dD`，保存宏定义和 `#undef` 轨迹。这是现有工具可以做到的小原型，不需要安装软件或修改内核。

原型输出的是“可能依赖”，不是精确的预处理展开。它做以下几件事：

1. 以定义文件、行列、USR 区分宏的多个版本；从外层调用的被引用定义出发，按替换体的名字继续追内层宏，并记录可能引用的函数、对象和类型定义。
2. 宏形参先排除为普通全局名字，避免把 `PARAM(INNER)` 的形参误连到全局 `INNER` 宏。形参代入、实参再次展开尚未完整实现，所以整个外层调用及其定义仍是待分析区域。
3. 重定义、`#undef` 与定义先后不按“最终名字表”任选一个。原型保留候选定义并标出绑定未知。`#` 字符串化、`##` 拼接、递归抑制、无法定位的标识符、字段/类型解释等也保留整个外层及可达定义区域。条件不活动的源码不能借此算成活动边界。
4. 精确的下一步应接 Clang 前端的 `PPCallbacks`（预处理事件回调）或等价的带位置/实参/禁用集的预处理器接口，在每次展开时保存实际环境、参数替换及生成 token 的来源。`-E -dD` 有定义轨迹，但会丢掉嵌套展开的来源链；它本身不能替代这个事件接口。本轮没有实现或安装前端插件。

A081 也有实际证据：当前被选中编译单元的7处外层 `arch_xchg*` 使用能沿候选依赖到 `__arch_xchg_masked`，libclang 没有直接暴露后者的展开。它是宏，不能假装是普通C直接被调函数。A081补丁同时改了外层接口，所以样本匹配第二版已命中这条；恢复内层依赖是新增的实现区域，不是又新增一条样本命中。

## 回调：同型目标全保留，初始化器另记确证引用

回调指通过函数指针间接调用函数。例如 `ops.run(x)` 的 `run` 是一个函数指针字段；仅看直接调用表，会漏掉它可能调用的实现。描述表同样如此：一个数组可以把编号和处理函数放在同一条初始化器里。

我的原型从所有输入编译单元收集函数定义/外部声明、函数指针类型、间接调用、表初始化器、运行时赋值和强制类型转换。类型先消除 typedef 别名并忽略按值参数的顶层 const；参数、返回值与可变参数等用规范类型比较。同型函数全部保留，不按“有没有被取地址”再删候选；未原型化函数保守纳入相应返回类型组。两个文件里的同名 static 函数用定义位置区分，可以同时成为保守候选。

指定字段的 ops 初始化和按顺序排列的描述表都单独保存实际的函数引用，包括对象位置、目标定义位置、指定/顺序形式。这里能确认“初始化器引用了这个函数”；本轮还没有实现表元素、字段、索引与运行时指针流的精确配对，不能把它当作这个调用点唯一可达目标。

所有间接调用都保留包含它的整个函数区域。其他TU未扫描、外部声明没有定义、运行时赋值、函数指针转换、通过整数/union/内存写入指针、汇编和ABI等仍可能补入目标；类型组不能封闭这些来源。强制转换的确证初始化目标即使签名不同也保留，另记待分析原因。候选组是C规范类型近似，无法处理的类型/转换/调用约定必须借由待分析区域继续处理，不能宣称全内核不漏。

## 我实际验证了什么

- 自测期望先写在 `prototype_src/expected.json`，后来补充的保守区域期望在 `expected_extra.json`。两个夹具TU验证17项：嵌套对象/函数宏、参数遮蔽和代入未知、字符串化/拼接、重定义/undef、递归、ops指定初始化、描述表顺序初始化、同型/异型候选、同名static、运行时赋值、转换和未扫描TU。
- 4个间接调用各保留5个同型定义；4个初始化对象的真实引用集合逐个相同；1处运行时赋值与1处转换均有明确待分析记录。
- 分批扫描器只在同一小夹具上跑过：先1个TU，再续跑1个TU，最后汇总。两个批次与摘要绑定；4个调用的类型候选仍与预先写的集合相同。压缩模式保存每TU宏定义图一次，9个外层使用全部保留待分析区域，避免为每个调用复制整张依赖图。
- 真实内核只验证A058和A081对应的两个既有编译命令；修改原型后各重跑一次，共4次真实TU解析。未解析整个内核，未把这些定点结果追加进完整运行时池或修改75条/77条样本数字。

## 交给Claude怎样跑

`prototype_batch.sh <arch> --limit 8` 每次前台处理8个C单元，重复同一命令直到打印complete。`--profile <配置名>` 使用已由本轮构建脚本生成成功标记的新配置。输出在本轮 `prototype_scan/<输入名称>/<摘要>/`，包括每TU压缩证据、预处理轨迹及输入摘要；已有失败记录会拒绝继续，不能跳过失败单元。明确的scripts/tools宿主单元和mod.c元数据单列排除，其他生成运行代码保留。这个路径规则仍不是完整的宿主分类器。

三个旧配置各自扫描完后，运行 `run.sh prototype_summary.py <arch>`，按类型组汇总函数目标、去重间接调用和初始化器。新配置要带同样的 `--profile`。每个调用仍保留整个所属函数的未知区域，不因全量输入扫描完就把运行时指针来源算成已封闭。

这里的全量命令采集的是宏/回调原型证据，**还没有把新配置的所有边界引用重扫、运行时池合并、宏/回调闭包和样本匹配接成一个统一工具**。不要用旧 `enumerate.py` 的defconfig硬编码直接扫描新配置，也不要改旧结果。精确PP事件、字段/索引/跨TU指针流、上下文/段属性、隐含ABI和内存模型仍是后续工作。全量原型输出规模、耗时和候选数量本轮均为null。
