# 两项父版模型结果与冻结组件试用的解释

2026-10-17。主分析为Windows原生Claude Code 2.1.301＋AWS-Claude-Opus-5.5，父版结果先保存，随后才读取两项修复材料。以下为研究侧后验复核，不回写原模型回答或父版结果。

## 交付与可采用结论分开

两项均exit0、非空final、返回型号一致、仅观察到end_turn，没有refusal。本轮两项分别119.422秒和109.359秒；这是两个顶层CLI任务，不保证只有两次底层推理。客户端可见token分别168353、119316，合计287669；保守预占合计400000，内部恢复和实际账单仍未知，两者不能相加。本轮证明两项新任务可以交付，不能据此证明所有长分析都稳定。

外层JSON/schema/list初检均通过；`parent_component_results.json`中的`protocol_parse=pass`只表示这一层，不是完整claim协议或语义通过。六项原始局部声明均保留，没有补字段或重试。

## 原样程序核对的边界

共十个去重函数定位请求：九个取得完整函数，一项旧定位器不支持`void __init early_identify_cpu`这种声明形态。实际函数在原文件中存在，不能写成Git源码缺失。九函数中，局部源码组件四项支持、五项不足；前向组件一项支持、五项保留边界、三项不足。均为语法结构，不证明实际守卫、效果或可达性。

六项模型声明全部为`insufficient`。五项首先被定位失败或函数子集限制挡住，一项被return中的嵌套调用挡住。这不等于六项声明为假，也不构成检测漏报率。此外，五项把`first`或`branch`放在`target`内，和检查器要求的根层字段不符；提示只给了自然语言描述，没有清楚的根层JSON示例，也应承担接口不明确的责任。此结构问题是附加诊断，没有移动字段后重算“通过”。

A的原函数包含预处理分支、未提供的类型等上下文；没有删`#if`、补临时类型或剪掉循环让它通过。B的前向组件可取得一个注册函数的结构备选，但条件内调用仍是不透明守卫，不自动成为已执行的独立调用事件。没有实际预处理profile、原语审核摘要、对象和消费证据，其他三个组件不被伪装成已端到端执行。

## A的语义复核

模型提出CPUID特性位在地址位宽读取前可见，以及TME位宽调整两个候选，同时承认缺定义、实际消费和第二CPU架构。它没有提出此次修复重点涉及的“CPUID可见范围准备应赶在依赖高叶的拓扑评估之前”关系。输入有晚解锁与先评估的调用线索，但没有拓扑消费者定义，因此本轮不能分离材料不完整与模型遗漏各自的贡献，更不能据此算正式召回率。

修复说明报告：某些Intel CPU的BIOS限制CPUID到叶2，旧拓扑重复求值曾掩盖晚准备，新的一次求值暴露问题。可见diff将解锁移入两个识别入口，位于取得厂商之后、采能力之前。这里不能要求所有CPUID读取前都已解锁：早期厂商和型号识别本身要先读CPUID。义务应绑定“依赖解锁结果的消费”，而不是某个同名函数或所有读取。

此项保留为单ISA厂商/型号条件下的准备机制辅助材料。第二ISA、共同Linux消费者的传播及实际受限运行均未建立，不纳入本轮核心跨CPU架构独立正例。

## B的语义复核

模型正确区分了设备能力、CPU选择与CPU架构差异，也没有认定实际违约。它提出注册前准备CPU状态和IRQ的用途要求，但把“首次实际使用前”直接推进为“perf注册发布前”的期限，仍需公共perf语义与调用环境证明。CPUHP头文件说明多实例状态创建不执行启动回调，add_instance才调用，不能将前者当准备已经发生。

可见修订将驱动自管cpumask/CPUHP迁移改为声明system-wide scope。IRQ注册仍在PMU注册之后，因此不能将模型的IRQ顺序候选解释成此提交已经证实并修复的根因；这也不独立证明该候选一定是假。公共perf的scope消费者和实际配置不在包内，清理标题及作者说明都不能成为同用途正常真值。

B保留为版本变化下责任从驱动移向公共层的边界材料：检查义务必须跟随当前接口分工，不能机械要求保留旧CPU字段。但本轮尚未核实公共层是否满足替代义务，正常对照仍未建立。其他顺带模型建议未扩展为新问题调查。
