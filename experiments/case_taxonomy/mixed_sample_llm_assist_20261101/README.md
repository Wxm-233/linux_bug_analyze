# 混合样本上的分类效果：规则、模型、规则加模型

## 这一轮要回答什么

用户建议：把有bug和没bug的函数混在一起，用自动检查分类，看效果；并且必须加入大模型辅助判断。本轮比较三种做法：

| 做法 | 内容 |
| --- | --- |
| R 只用规则 | 上一轮写成的“表项状态—大小来源”自动检查 |
| L 只用模型 | DeepSeek-V4.1-Flash-1017，看函数代码及同文件被调函数，判断有无bug并引用行号 |
| RL 规则加模型 | 在L的输入上，加机制目录（9类跨架构缺陷机制）和规则检查结果，其余完全相同 |

| 文件 | 说明 | SHA |
| --- | --- | --- |
| `criteria.md` | 判据，实现前写定 | `f5789c1a…` |
| `catalog.md` | 交给模型的机制目录（M1–M9） | `1887b626…` |
| `criteria_amendment.md` | 修订1：重跑被截断的调用（看分类结果之前写定） | `69dbde4b…` |
| `interim.md` | 第一次运行的中间记录 | — |
| `select_samples.py` → `samples.json` | 机械抽样与规则结果 | `96995ad1…` → `36e8848e…` |
| `build_prompts.py` → `prompt_index.json` | 提示词 | `286a8c95…` → `3e52507f…` |
| `run_calls.py`、`run_rerun.py`、`rerun_index.json` | 两次运行 | 见`criteria_sha256.txt`；日志`run_calls.log`、`run_rerun.log` |
| `score.py` → `scores.json`、`predictions.json` | 评分 | `5ff46509…` → `1c4d297e…`、`17c2e22e…` |

模型输出在`模型调用测试/2026-11-01/mixed_20261101/`（第一次）和`mixed_20261101_rerun/`（重跑）。

## 样本

- **有bug，30个**：`v6.6`到终点之间，修复只改动RISC-V一个函数的提交中，取修复前的版本。共453个修复提交，符合条件的121个，从中随机抽30个：2026年3月以后的15个，更早的15个。
- **修复后的版本，30个**：与上面一一配对，最难区分。
- **两年多未改动的函数，30个**：全部来自有bug样本所在的文件。
- **特别样本2个**：本项目确认的`huge_pte_clear`缺陷，以及打了补丁的版本。单独报告。

样本涉及KVM、陷入处理、kexec、CPU特性探测、内存缺页等，大部分**不在**大页代码里。

**标签噪声**：以`Fixes:`标签为准，个别“修复”很弱，例如`do_trap`只改了日志级别；修复后的版本也可能还有别的问题。

## 运行情况（如实记录）

- **第一次运行**：204次调用，输出上限16384。155次被截断，截断部分全是模型内部推理，没有答案，所以没有作结论（见`interim.md`）。
- **修订1**：经用户同意，把155次在新目录中重跑，上限65536，其余不变。146次给出答案，9次仍被截断或出错。
- **合计**：359次调用，约874万token。主样本最终无结果：L 5个，RL 3个，按判据计为无bug。
- 输出文件中没有出现密钥。

### 按事先标准的判定

RL的F1比L高0.116（≥0.10），配对区分率也比L高（10对8）。**判定为“RL有增益”。**

## 解读

1. **增益主要来自机制目录，而不是规则结果。** 这一轮的规则只覆盖大页的一种机制，90个主样本里规则一个都没标出，所以RL比L多出来的只有机制目录。机制目录的作用是：
   - **少误报**：未改动函数的误报从13降到8；
   - **多找到**：多找到4个bug，L只多找到1个。

   这说明：**已提炼的跨架构缺陷机制，作为检查清单交给模型，能提高自动检测的效果**。这正是研究目标要验证的“机制能否指导检测”。
2. **只用规则的覆盖面很窄**，这在预期之内：一个机制只能管一类缺陷。用户的判断是对的：只靠写死的规则判断不了全部bug。
3. **模型很难区分修复前后的版本**：30对中，L有7对、RL有8对是两个版本都判有bug。也就是说，模型常常不是发现了“那个”bug，而是在代码里找出了别的可疑之处。
4. **误报仍然很多**：RL判为有bug的36个里有18个是错的。不能直接拿去报告，必须再经过人工或运行验证。
5. **样本量小**：90个样本上，F1差0.116，只相当于几个样本的差别。这个结论需要在更大的样本上复核。

## 误报中的值得注意的条目（读代码所得，未运行）

两种做法在30个未改动函数上，合计判了15个有bug，研究者只深入核对了两条：

| 函数 | 模型的说法 | 核对结果 |
| --- | --- | --- |
| `kvm/aia_imsic.c` `imsic_vsfile_cleanup` | `memset`只清了一个元素 | **误报**：`swfile`是结构体指针，`sizeof(*swfile)`是整个结构体 |
| `kernel/machine_kexec.c` `machine_shutdown`（L和RL都标了） | 先`local_irq_disable()`，再调用`smp_shutdown_nonboot_cpus()`，后者会睡眠 | **疑似真问题**：`smp_shutdown_nonboot_cpus`先`cpu_maps_update_begin()`（互斥锁），再逐个下线CPU，会等待。arm64的同名函数不关中断；`kernel_kexec()`调用它时中断是开着的。属于机制目录中的M5（执行上下文）。**只记录，不对外报告，需要运行验证**（例如开启`CONFIG_DEBUG_ATOMIC_SLEEP`，在QEMU中走kexec重启） |

其余13条（例如`get_break_insn_length`按4字节读取压缩指令、`imsic_vsfile_rw`在原子上下文中等待跨核调用）没有逐条核实，归为判断不了(c)。

## 统计

规则调用0；模型调用359次（DeepSeek-V4.1-Flash-1017，约874万token）；构建0；新确认缺陷0；新疑点1条（RISC-V `machine_shutdown`，待运行验证）。
