# “参照对象的同名函数后来又修过什么”：候选与人工核对

## 这一轮要回答什么

案例分析发现，M8的实质多为“RISC-V落后于参照对象的演进”。本轮把“同名函数被别的架构修过、RISC-V之后没改”的思路，扩大到近两年arm64、x86、LoongArch的全部修复，看会给出多少候选、人工核对后有多少是真问题。

## 候选

- 在`v6.12..df2908090cda`中，arm64、x86、LoongArch带`Fixes:`的修复共2352个；
- 其中改动的函数在RISC-V中有同名定义，并且RISC-V的这个函数在参照修复之后没有改过的，共**114条**（80个不同函数）：arm64 51条、LoongArch 38条、x86 28条。

## 人工核对（随机抽30条，涉及26个不同的参照修复）

| 归类 | 条数 | 说明 |
| --- | ---: | --- |
| (a) RISC-V疑似有同样的问题 | 2（同一个参照修复） | 见下 |
| (c) 判断不了 | 3（同一个参照修复） | 无效的大页叶子映射 |
| (b) 没有 | 25 | 见下 |

**(a) 内存热插拔时页表分配失败直接崩溃**（参照：arm64 `bfc184cb1ba7`）
- arm64的问题：热插拔内存时，`arch_add_memory`调用早期启动用的建页表函数，其中的分配器在失败时`BUG_ON`；内存极度紧张时会直接让系统崩溃。arm64把它改成了返回`-ENOMEM`。
- RISC-V：`arch_add_memory`调用`create_linear_mapping_range`，后者没有返回值，用的是“后期”页表分配器`alloc_pte_late`、`alloc_pmd_late`等，这些函数在分配失败时都`BUG_ON`。**写法与arm64修复前相同。**
- **机制**：M8，落后于参照对象的演进。这段代码原本只在早期启动时使用，后来被内存热插拔复用；arm64随之修改了，RISC-V还没有。
- **为什么还没暴露**：只有在内存热插拔、而且内存极度紧张时才会触发，很少见。
- **影响**：可靠性问题，系统直接崩溃，而不是热插拔失败。只记录，不对外报告。

**(c) 无效的大页叶子映射**（参照：arm64 `15bfba1ad77f`）
- arm64的问题：线性映射中的大页表项被清除“有效位”后，很多代码不能正确处理。
- RISC-V：修改线性映射前会先拆大页；而且RISC-V的`pmd_present`把读写执行权限位也算作“存在”，所以清除存在位的PMD大页表项仍会被识别为叶子，arm64的问题在这一级不会出现。PUD一级没有细查，但没有找到会让对齐的1GB整段失效的调用者。归为判断不了。

**(b) 25条没有问题的**，原因大致四类：
- **RISC-V本来就写对了**：例如kexec段拷贝区分内核指针和用户指针；BPF trampoline按`round_up(arg_size, 8) / 8`计算128位参数；用户态中断控制器注入的中断也能唤醒WFI；
- **RISC-V用的是公共实现**，问题已在公共代码中修好：compat `ftruncate64`；
- **只与参照架构的硬件或特有机制有关**：arm64 MTE、计数器寄存器，x86 SMI、`cpa_lock`；
- **新功能、优化、改名、删除冗余代码**，或者RISC-V不支持的功能（RV32 JIT不支持子程序尾调用）。

## 结论

- **命中率**：30条中2条为(a)，按不同的参照修复算是1/26。上一轮“同一触发提交”规则的7条候选中有1条(a)。两者都在“每二三十条中有一条”的量级，只作描述。
- **这种做法能找到真问题，但噪声大**：大多数候选是新功能、优化，或只与参照架构硬件有关的修改，人工排除它们不难，但量大。
- **改进方向**：
  - 先按提交说明区分“修复”与“优化或新功能”，再按“是否只涉及参照架构特有的硬件或功能”过滤，可以去掉大部分(b)；这一步适合交给模型，而且只需读提交说明；
  - 对剩下的候选，再按机制目录逐条核对RISC-V的同名函数。
- **方法上的意义**：这次找到的(a)类，正是M8“落后于参照对象的演进”的典型形态：一段代码被用在了新的场景（热插拔），参照架构跟着改了，RISC-V没有。这说明M8不只能解释历史修复，也能指导在当前代码中找问题。

## 统计

不调用模型；构建0；新确认缺陷0；新疑点1条（RISC-V内存热插拔时页表分配失败直接崩溃，只记录，未运行验证），判断不了1条。
