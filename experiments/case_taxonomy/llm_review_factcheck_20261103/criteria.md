# 大模型复核规则标记：程序核对模型引用的代码事实（判据，实现之前写定）

## 这一轮要回答什么

前两轮发现，模型复核规则标记时，剩下的错误多是系统性的，其中一类是**说错材料里写着的代码事实**。例如，它说`arch_cpu_idle`“已带`__cpuidle`标注”，但给出的代码中并没有这个标注；又如，它说`die()`“只在用户态分支之外调用”。

本轮检验：让模型把判断所依据的代码事实写成程序能查的格式，由程序逐条核对；有不符的，把核对结果反馈给模型，请它重新判断。这样能否减少这类错误？

## 一、样本与提示词

- **样本**：与前两轮相同：
  - 新样本18个，标签见`llm_review_facts_20261103/heldout_labels.json`；
  - 原样本41个，标签见`llm_review_rule_flags_20261103/items.json`，按其修订1。
- **提示词**：在上一轮“加事实”的提示词（`H1_nn`、`O1_nn`）基础上，只把最后的输出要求换成带“事实声明”的格式，其余一字不改。

## 二、事实声明的格式

模型最多列出5条判断所依据的代码事实，每条是下列4种之一。`file`取提示词中给出的文件路径。

| 类型 | 字段 | 程序怎样核对（在该样本的快照版本上） |
| --- | --- | --- |
| `annotation` | `file`、`function`、`annotation`、`present`（真/假） | 函数签名中是否含该标注，例如`noinstr`、`__cpuidle`、`__init`、`notrace`、`inline`、`__always_inline` |
| `calls` | `file`、`function`、`callee`、`present` | 函数体中是否有对`callee`的调用 |
| `order` | `file`、`function`、`first`、`then` | 函数体中是否先出现`first`的调用，后出现`then`的调用 |
| `condition` | `file`、`function`、`callee`、`condition` | `callee`的每一处调用，其所在分支的条件中是否都包含`condition`。比较时去掉空白；否定条件写作`!(…)` |

以下几种情况记为“无法核对”，不算不符，单独报告：
- 文件或函数在快照中找不到；
- 格式不对；
- 类型不在上表中。

## 三、两步流程

1. **第一步**：每个样本问1次，共59次。
2. **核对**：程序逐条核对事实声明。
3. **第二步**：只对**至少有1条声明不符**的样本再问1次。提示词为：

   第一步的提示词 ＋ 模型第一步的回答 ＋ 程序的核对结果（哪几条不符、代码中实际是什么）＋ “请据此重新判断，按同样格式输出”。

4. **最终判断**：有第二步的，以第二步为准；没有的，以第一步为准。

**模型与参数**：Claude-Sonnet-5.5，凭据配置为`claude-sonnet55-20261103`，8路并行，不自动重试。

**调用量**：59次，加上第二步的次数，预计不超过约90次。

## 四、指标与事先写定的判定

**指标**：
- 新样本、原样本分别统计**最终判断**的保留率、去除率、复核后精确度；
- 同时报告**第一步判断**（尚未核对）的同样指标，作为对照；
- 事实声明的情况：总数、核对相符、不符、无法核对各多少；第二步改变了多少判断，改对了几个，改错了几个。

**成功标准**（看新样本的最终判断，同时满足）：
1. 保留率不低于90%；
2. 去除率不低于50%。

## 五、已知局限

- **能核对的事实只有4种。** 模型依据其他事实（例如对内核行为的一般性说法）判错时，程序无能为力。
- **条件核对是文本比较。** 写法不同可能被判为不符或无法核对。
- **误报的标签只来自第一标注人。** 有争议的几条（`memset_io`、`memcpy_toio`、`kvm_age_gfn`）仍按原标签计分。
