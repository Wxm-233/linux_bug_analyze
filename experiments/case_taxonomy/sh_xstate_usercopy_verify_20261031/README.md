# sh浮点上下文与加固用户拷贝：运行验证

## 要验证什么

模型判定试点（`ccp_judge_model_20261030/`）中，模型多标出了sh的`arch_task_cache_init`。研究者当时读代码后，判为“疑似真实问题”，理由如下：

- sh用普通的`kmem_cache_create`创建`task_xstate`缓存，这种缓存不允许与用户态互相拷贝；
- 发送信号时，sh用`__copy_to_user`直接从这个缓存的对象里拷出浮点寄存器状态；
- 因此在开启`CONFIG_HARDENED_USERCOPY`的内核上，理论上会触发`usercopy_abort`。

本轮在QEMU中实际运行验证。计划见`plan.md`（SHA `0f9d3126…`），运行前写定。

## 做法

- **构建**：交叉编译器`gcc-sh4-linux-gnu`由用户同意后安装。内核为终点版本`df2908090cda`，基于`rts7751r2dplus_defconfig`（QEMU的r2d板，SH7751R，带硬件浮点），初始文件系统编进内核。
- **测试程序**（`fpsig.c`）：作为`/init`运行，先做浮点运算，再给自己发`SIGUSR1`，然后打印结果。
- **运行**：`qemu-system-sh4 -M r2d`，三组如下。

| 组 | 内核 | 程序 | 结果 |
| --- | --- | --- | --- |
| 实验组 | 开启加固用户拷贝（`CONFIG_HARDENED_USERCOPY=y`，已核对配置） | 用浮点后收发信号 | **正常结束**，信号已处理，浮点结果正确（`g_milli=529142`），没有`usercopy`报错 |
| 对照1 | 开启加固用户拷贝 | 不用浮点 | 正常结束 |
| 对照2 | 关闭加固用户拷贝 | 用浮点后收发信号 | 正常结束，浮点结果与实验组相同 |

脚本`run.sh`，各组的控制台日志、构建日志和配置摘录在`logs/`。

## 结论：疑点被否定，不是问题

按计划，实验组正常结束属于“未复现”，需要排查原因。原因已经找到：

- 终点版本的`check_object_size`（`include/linux/ucopysize.h`）只在拷贝长度**不是编译时常量**时才做运行时检查：`if (!__builtin_constant_p(n) && ...)`。
- sh保存和恢复浮点上下文时，拷贝长度是固定的`sizeof(long)*(16*2+2)`，属于编译时常量。所以加固用户拷贝根本不检查这两次拷贝，也就不会报错。
- 编译时长度固定的拷贝，由其他编译期机制把关，例如`__bad_copy_from`、`__bad_copy_to`。

研究者之前读代码时漏看了`__builtin_constant_p`这个条件，模型同样如此。运行结果与这一解释完全一致：三组都正常，浮点状态在信号前后也正确保存和恢复了。

**这说明，读代码得到的疑点必须经过运行验证。** 本条从“疑似真实问题”改为“已排除”。原记录保留不改，并在`ccp_judge_model_20261030/README.md`末尾追加了更正。
