# 复核第2版（开发第2轮）：补充调用关系事实，每个样本跑2次（判据，实现之前写定）

## 这一轮要做什么

开发第1轮（`llm_review_v2_dev_20261104/`）中，有修复依据的真问题只保留6/8，开发目标是90%。
- **漏掉的两个**：
  - `setup_arch`：程序事实只给了`jump_label_init`在公共代码中的调用位置，没有给出它与`setup_arch`的先后；
  - `KVM_CAP_NR_VCPUS`：模型认为“建议值偏大不算错误”。
- **判错的一个误报**：`die`。模型以为它可能带着用户态寄存器被调用，而程序事实中没有给出`die`的调用位置。
- 当时只跑了1次。

本轮仍在同一批60个样本上开发，结论只作改进依据。

## 一、改动（其余与第1轮完全相同）

1. **CTX标记新增事实**：被标记函数在本架构目录中的调用位置，最多5处，带文件和行号。
2. **R10标记新增事实**：对每个缺少的被调函数X，在公共代码（init、kernel、mm）中找同时调用了被标记函数N和X的函数，最多2个，给出两者的行号和先后。
3. **`bug`的定义补一句**：“返回给用户态的值违反该接口的文档说明，也算错误的返回值。”这一句来自第1轮对`KVM_CAP_NR_VCPUS`的观察，属于针对开发样本的调整。
4. **每个样本跑2次**，提示词完全相同。

## 二、标签与核对

- 标签沿用第1轮的`labels3.json`（`553fdfb7…`），运行前核对SHA。
- 核对程序沿用第1轮的`factcheck2.py`，不修改。
- 追问规则不变。

## 三、两次结果的合并（写在调用之前）

- 两次都是`not_issue`，且依据都被接受，合并为`not_issue`；
- 否则，只要有一次是`bug`，合并为`bug`；
- 否则，只要有一次是`unsure`，或者一次`not_issue`、一次其他，合并为`unsure`；
- 两次都是`convention`，合并为`convention`。

这样合并，只有两次都能拿出依据，才会去掉标记。

## 四、指标与目标

与第1轮相同：
- 有修复依据的`bug`保留不低于90%；
- `not_issue`去除不低于50%；
- `convention`不被判为`bug`不低于50%。

每次的结果与合并结果都报告。合并结果达到三项目标后，才写独立检验的判据。

## 五、调用

60×2＝120次，另加追问。模型Claude-Sonnet-5.5，8路并行，不自动重试。调用前须征得用户同意。
