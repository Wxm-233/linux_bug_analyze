## 改了什么（其余与第1轮相同）

1. **CTX标记**：补上被标记函数在本架构中的调用位置。
2. **R10标记**：补上缺少的函数在公共代码中与被标记函数的共同调用者，以及两者的调用先后。例如“`start_kernel`中第959行调用`setup_arch`，第972行调用`jump_label_init`”。
3. **`bug`的定义补一句**：“返回给用户态的值违反该接口的文档说明，也算错误的返回值。”
4. **每个样本跑2次**，按事先写定的规则合并：两次都去掉才去掉；有一次判为`bug`就算`bug`。

**自测中发现的问题**：查共同调用者时，`git grep`的输出带版本前缀，第一版少切了一段，结果一律报告“没有”。已在调用之前修正。

## 标签更正（修订1，事后）

模型两次都把`KVM_CAP_NR_VCPUS`判为`convention`，理由是“NR_CPUS上限不超过KVM_MAX_VCPUS”。我核对v6.7的代码后确认模型说得对：
- NR_CPUS为`range 2 256`；
- `KVM_MAX_VCPUS`为256。

所以返回值不会超限，按三类定义属于`convention`。上游修复有意义，是因为后来NR_CPUS上限提高到了2048。原映射把“有修复”一律映射为`bug`，没有按快照时的配置核对，这是我的标注错误。

为了不只改模型反对的那一条，我按同一标准重查了其余7个，都维持`bug`。其中`setup_arch`（v6.1）：LoongArch选了`IRQ_FORCED_THREADING`，启动参数`threadirqs`的早期处理函数会在`jump_label_init`之前调用`static_branch_enable`，触发内核警告，所以确实是真问题。

## 分析（事后，只作描述）

- **补充的事实只修好了误报方面**：
  - `die`：调用位置事实给出后，第1次判为`not_issue`，第2次判为`unsure`，不再判为`bug`；
  - `not_issue`去除最好的一次达到19/23。
- **`setup_arch`仍然两次都漏。** 程序事实已经写明“`setup_arch`在`jump_label_init`之前”，模型仍然认为“`start_kernel`随后会调用，只是写法不同”。要判对它，需要知道“哪些早期参数会改静态键”，这超出了程序事实能直接给出的范围。
- **两次合并的规则太保守**：问题清单从9到11个变成22个，因为两次判断不一致的14个大多被记为`unsure`。
- **单次波动**：`not_issue`去除在16/23和19/23之间。

## 结论

- 更正标签后，开发样本上有修复依据的真问题两次都保留6/7（86%），离开发目标90%只差`setup_arch`一个，而它需要程序事实给不出的内核知识。
- `not_issue`去除70%～83%，违反约定类全部分流。
- 两次合并的规则让问题清单翻倍，不宜采用。
- 下一步待用户决定：
  - 带着单次运行的做法写检验判据，在独立样本上检验，即LoongArch未抽中的22个候选，加上第三个架构的新样本；
  - 或者继续开发。
