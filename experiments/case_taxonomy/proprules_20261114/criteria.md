# 判据：把“性质 → 检查”做成规则（proprules_20261114）

2026-11-14，Claude。用户：“做成规则试”（`x1loop_20261114` README 的下一步）。本文件在写检查程序、构建和运行之前写定，SHA 存入 `criteria_sha256.txt`。

## 一、要回答的问题

1. 依赖性质能不能按类别写成通用的判错规则，每条规则配一组从用户态触发的检查模板，而不是像 X1 那样每次手写？
2. 用这套规则，能不能自动复现 X1（阳性对照）？在当前版本的三个架构上，会不会发现新的违反？
3. 静态阶段（纵向信号）给出的候选里，有多少能自动映射到某条规则；映射不到的，分流到哪里？

## 二、规则表（写死）

每条规则只看“每个架构上性质是否成立”，不比较架构之间的差异（师兄新结论）。每个模板运行前都先“弄脏”：写 512 MiB 的 `0xA5` 再释放，并写 `drop_caches`（值 3）；每个模板放在单独的子进程里运行。

**R1 清零**：发布给用户的新内存，在用户第一次写之前读到的必须全是 0。对应静态效果类别 `mem`（清零或初始化）。模板：

| 编号 | 资源来源 | 做法 | 判错 |
|---|---|---|---|
| Z1 | 匿名页读缺页（零页） | 匿名映射 64 KiB，只读 | 有非零字节 |
| Z2 | 匿名页写缺页 | 每页写第 0 字节，读同页其余字节 | 其余字节有非零 |
| Z3 | 透明大页零页 | 2 MiB 对齐、`MADV_HUGEPAGE`，读 3 个大页（同 X1） | 有非零字节 |
| Z4 | 透明大页写缺页 | 同上，每个大页写第 0 字节，读其余字节 | 其余字节有非零 |
| Z5 | `MADV_DONTNEED` 后重读 | 写满 `0xCC`，`MADV_DONTNEED`，再读 | 有非零字节 |
| Z6 | 文件末尾之后 | 在 init 所在文件系统新建 100 字节的文件，`mmap` 一页，读第 100 字节之后 | 有非零字节 |
| Z7 | memfd 新页 | `memfd_create`、`ftruncate` 64 KiB、`mmap` 后读 | 有非零字节 |
| Z8 | brk 扩展 | `sbrk` 增加 64 KiB 后读新增部分 | 有非零字节 |
| Z9 | mremap 扩展 | 匿名 64 KiB 写满 `0xCC`，`mremap` 扩到 128 KiB，读新增部分 | 有非零字节 |

**R2 失效**：解除映射或去掉权限之后，旧的访问必须失败。对应静态效果类别 `tlb`、`pgtable`。模板：

| 编号 | 做法 | 判错 |
|---|---|---|
| T1 | 写一页（让 TLB 里有这一项），`munmap`，再读 | 没有收到 SIGSEGV |
| T2 | 写一页，`mprotect` 为只读，再写 | 没有收到 SIGSEGV |
| T3 | 两个线程：线程 B 不断读一页；线程 A `munmap` 这一页后通知 B，B 再读一次 | B 在收到通知后读成功（另一个 CPU 上的旧 TLB 项没被刷掉） |

**R3 指令一致**：往一页里写入新的机器码、改成可执行后，执行到的必须是新代码。对应静态效果类别 `cache`。

| 编号 | 做法 | 判错 |
|---|---|---|
| I1 | 匿名页写入“返回 1”的函数，`mprotect` 为可执行并调用；再改成可写，写入“返回 2”，改回可执行再调用 | 第二次调用不返回 2 |

各架构的机器码写死在程序里：riscv 是 `li a0,N; ret`，arm64 是 `mov w0,#N; ret`，x86_64 是 `mov eax,N; ret`。用户态不加任何显式的缓存刷新指令，依赖的就是 `mprotect` 时内核保证的一致性。

规则 R1～R3 和模板是我根据内核的公共语义（POSIX、mmap 手册、`madvise` 手册）写的，不来自任何一个样本的修复；只有 Z3 是照 X1 写的。

## 三、从静态候选到规则（写死）

- 输入：`effdep5_dev_20261113` 当前版本 riscv 的纵向候选（修订 2 后共 32 个），以及 X1 修复前的候选。
- 映射：
  - 候选的效果类别（`skipped_cats`）含 `mem`，并且共享资源或被跳过调用的实参里有名为 `page`、`folio`、`pte`、`vmf`、`vma`、`addr` 的变量，映射到 R1；
  - 含 `tlb` 或 `pgtable`，并且资源名同上，映射到 R2；
  - 含 `cache`，映射到 R3；
  - 都不满足的，记为“资源在内核内部，需要 ACTOR 或调试内核”，不生成检查。
- 要报告每个候选映射到哪里。映射只说明候选“可以用哪条规则检查”，不说明它是不是缺陷。

## 四、内核和运行（写死）

- X1 修复前、修复后：复用 `x1loop_20261114` 的 6 个内核（riscv、x86_64、arm64），arm64 另跑一组开 MTE 的。
- 当前版本（HEAD，7.3-rc2）：riscv、x86_64、arm64，defconfig 加 `TRANSPARENT_HUGEPAGE=y`，clang 18。
- QEMU：`-smp 2 -m 1024M`（同 x1loop 修订 1），每个“内核 × 运行方式”跑 3 次。

## 五、判定和要报告的数字

1. 每次运行、每个模板：是否违反。只有当模板的前置步骤都成功（映射成功、`madvise` 等返回 0）时，才算有效。
2. **阳性对照**：X1 修复前的 riscv、x86_64 上，Z3 必须违反，修复后不违反；arm64 不违反（x1loop 的结果）。做不到，说明规则化的检查程序有问题，要先查原因。
3. **当前版本**：任何模板在任何架构上违反，都列为疑点，按规则不对外报告。我会读相关代码，判断是真问题、QEMU 的行为，还是检查程序的问题。
4. **旧判错方式对照**：所有系统调用返回值修复前后是否一样。
5. 第三节的映射统计。
