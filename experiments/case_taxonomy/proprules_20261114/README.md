## 结论

1. **依赖性质可以写成通用规则。** 三条规则、13 个从用户态触发的检查模板，覆盖“清零”“失效”“指令一致”三类性质，写成一个检查程序 `propsuite.c`，三个架构共用。只有指令一致规则 R3 用到的机器码按架构写死。
2. **能自动复现 X1（阳性对照通过）。** 在 X1 的内核上，只有 Z3（大页零页）在修复前的 riscv、x86_64 上违反，3/3；修复后，以及 arm64 不管开不开 MTE，都不违反；其余 12 个模板在所有 X1 内核上都不违反。也就是说，规则检查只在该报的地方报，没有误报。
3. **当前版本没有发现违反。** riscv、x86_64、arm64（开 MTE 和不开 MTE）共 12 次运行，13 个模板全部通过。
4. **旧判错方式对照。** X1 内核上 312 个“模板 × 运行”（1823 次尝试）的前置系统调用全部成功，修复前后返回值看不出差别。
5. **从静态候选到规则的映射。**
   - 当前版本纵向信号的 32 个候选：6 个映射到 R1（清零），1 个到 R3，25 个的资源在内核内部，分流到“需要 ACTOR 或调试内核”。
   - X1 修复前的 27 个候选：X1 本身（`post_alloc_hook`）映射到 R1。
   - 映射只说明“可以用哪条规则检查”。这里的规则检查是对整个内核跑，不针对某个候选，所以映射和检查目前还没有一一对应起来，见下面的局限。

## 规则表（详见判据和修订 1）

- **R1 清零**：发布给用户的新内存，在第一次写之前读到的必须全是 0。模板 Z1～Z9，覆盖匿名页读缺页、匿名页写缺页、透明大页零页、透明大页写缺页、`MADV_DONTNEED` 后重读、文件末尾之后、memfd、brk 扩展、mremap 扩展。每个模板每次开机试 8 次，每次之前先弄脏 512 MiB 内存并回收缓存。
- **R2 失效**：解除映射或去掉权限后，旧的访问必须失败。模板 T1（`munmap` 后读）、T2（`mprotect` 只读后写），以及 T3（另一个 CPU 上的线程，在 `munmap` 返回后读，检查跨 CPU 的 TLB 刷新）。
- **R3 指令一致**：写入文件的新代码，重新映射后执行到的必须是新代码。模板 I1，做 100 次。

## 局限（如实写明）

- **规则和模板是我手写的。** 依据是内核的公共语义（mmap、madvise 手册等）。只有 Z3 是照 X1 写的，它能复现 X1，不是独立证据。其余 12 个模板在 X1 内核上都不违反，说明它们没有误报，但还没有一个独立的已知缺陷来证明它们能报出问题。
- **触发手法也是手写的。** 比如“先弄脏、回收缓存、重复 8 次”，是从 X1 的调试中学到的。第一次运行时 Z3 只试一次就测不出来（修订 2），说明触发强度对结果影响很大。
- **QEMU 的 TCG 把缓存模拟成一致的。** R3 只能发现内核逻辑上的错误，比如映射到了旧页，发现不了硬件缓存问题。R2 不受这个限制。
- **静态候选到规则的映射目前很粗。** 只按效果类别和变量名选规则，规则检查也是对整个内核跑，没有针对某个候选专门构造用例。真正要做到“针对候选”，需要知道候选所在的公共函数从哪个系统调用能走到（可以复用之前的可达性分析），再把模板限制在那条路径上。

## 下一步建议（还没做）

1. **找独立的阳性对照。** 从历史修复里挑“清零、TLB 刷新、指令缓存”类、能从用户态观察到的跨架构缺陷，比如开发集里的 A029、A042、A043（少刷 TLB），以及 A162（uprobe 少了 fence.i）。构建它们修复前、修复后的内核，看 R1～R3 能不能报出来。这才能检验规则本身的检出能力，而不只是复现 X1。
2. **把可达性接上。** 对映射到规则的静态候选，用已有的“从系统调用到函数”的可达性，选出能走到候选函数的模板，只报和候选相关的违反。
3. 内核内部的资源（25 个候选）需要 ACTOR 记录器或调试内核里的断言，移植 ACTOR 的评估见 `../actor_eval_20261113/README.md`。
