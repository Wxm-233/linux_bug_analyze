# N1.4a：从完整源码提取局部调用与条件事实

日期：2026-10-16。本轮是**已读 s390／x86 启动案例的开发实验**。目的在于把 N1 的一小段链条接起来：模型提出可核对的要求，程序从源码恢复事实，再由复核者区分局部事实与接口义务。不是独立检出实验，也没有新增内核启动。

## 输入与分工

- `protocol_pre.json`：执行前登记的范围。仅核对完整函数中的调用、分支和有条件的局部顺序；不声称调用效果或公共回调全链已经证明。
- `source_functions.json`：本地历史 Git 中的八个完整函数，保留版本、路径、原行号、整文件与函数指纹。旧版为 `88b604263f3d6eedae0b1c2c3bbd602d1e2e8775`，修复版为 `a052096bdd6809eeab809202726634d1ac975aa1`。旧包中的 x86 入口切片有缺行，本轮重新取完整函数；旧／修复文件清单仅有指纹，未被当作源码文本。
- 模型：Windows 原生 Claude Code＋`AWS-Claude-Sonnet-5`，只接收旧版源码与少量配置摘录，不给补丁、修复版、运行结果或先前检查卡；提出最多三项源码事实和另外的语义要求。原始响应、增量、最终正文及用量保存在外层忽略目录 `模型调用测试/2026-10-16/n1_source_conditions_01/`。
- 程序：`linux_bug_analyze/source_conditions.py` 从 C 语法树提取调用坐标、参数、条件及有限结构路径，并核对模型**未改写的**三项事实。核心不含架构名、函数名或特定 CPU 的答案。
- 研究者：选择已有案例中的对照问题，逐条审阅语义要求、接口依据和未证明项。五项研究侧问题单列在 `selected_query_results.json`，不能当作模型自动生成。

本轮源码来自已读案例，完整提取方法也尚未冻结，故“未提供补丁”不等于独立盲测。`source_facts.json` 是程序事实；`results.json` 是汇总。模型原始解释及逐项检查保留在忽略目录，没有整份复制入跟踪材料。

## 实现的确切范围

可处理完整函数里的顺序语句、`if/else`、早退和独立调用，保留目标调用**之前**的分支条件；每个条件求值位置独立，不把两次看起来相同的判断当作相同运行值。设置结构路径上限，超限拒判。只在未重赋值、未取地址逃逸、未被遮蔽的同一局部实参版本上标出很窄的身份联系；不等于指针指向内容相同或对象状态稳定。

循环、跳转、`switch`、间接调用、条件中的写入等超出本轮子集；能够解析时保留调用／条件清单，不给完整路径证明。缺头缺尾或非连续片段也拒判。函数类型形参、typedef 形参／局部对象作为 callee 时均按间接调用处理。调用隐藏宏展开、被调用者不返回、全局状态、并发及跨函数副作用没有被证明。

当前解析层明确为 **未预处理 C 的语法形态**。显式的 `bool`／`cpumask_t` typedef 桩只帮助解析，不代表真实类型、布局或有效配置；只允许白名单函数头注解的等宽遮罩。不能直接把这里的语法顺序升级为有效内核翻译单元的运行事实。第三方解析器的[官方说明](https://github.com/eliben/pycparser)也要求非简单 C 输入先行预处理，并说明 GCC 扩展支持有限。本项目后续需使用已有真实预处理证据，不能靠删除宏或补几个桩替代它。

## 本轮结果

| 完整函数材料 | 结构路径结果 | 能保留的事实与限制 |
| --- | --- | --- |
| 旧 s390 `smp_start_secondary` | 支持，2 个结构分支 | 通知在更新前；后面的 dedicated 分支不被当成前面通知的前提 |
| 修复 s390 `smp_start_secondary` | 支持，2 个结构分支 | 设置 setup 位、更新、通知的局部顺序；设置和通知使用同局部参数版本 |
| x86 `smp_callin` | 支持，1 个结构路径 | sibling-map 调用在通知前；不自动证明 getter 返回值与局部 `cpuid` 是同对象 |
| 公共 `sched_cpu_starting` | 支持，1 个结构路径 | core-starting、rq-starting 等调用的局部顺序和同参数版本 |
| 公共 `notify_cpu_starting` | 支持，1 个结构路径 | 局部调用清单；赋值表达式内的回调调用不是本轮独立调用事件，不补成已证明的分发链 |
| 旧／修复 s390 `cpu_thread_map` | 两项均不足 | 条件与调用清单可见，`goto`／循环不在路径子集；不能据此证明 mask 一定含当前 CPU |
| 公共 `sched_core_lock` | 不足 | 未展开的遍历宏导致解析失败，不能假装已经定位实际逐项锁消费 |

合计 **8 个函数材料，5 个可做局部路径核对、3 个不足**。它们来自同一已读案例，不是八条缺陷，也不据此计算检测召回率。

模型的三项事实均得到 `verified_local_structure`：x86 map 调用先于通知；旧 s390 通知先于更新；旧 s390 通知在函数内不被分支绕开。最终 JSON 仅剥离唯一外层 `json` 围栏，未修补字段、未重试。所谓“不被绕开”仍以不透明调用正常返回为前提，不证明实际启动成功、调用效果或并发可见性。

另有五项研究者选择的问题：旧 s390 的“更新在通知前”不成立，修复版成立；修复版 setup 调用在通知前、x86 map 在通知前、公共 core-starting 在 rq-starting 前均成立。其中仅两对参数满足“同局部版本”的窄判断，x86 两种 CPU 表达式没有自动合一。`not_established` 不等于自动确认缺陷或得到可执行反例。

### 两项语义要求均未直接采用

1. **把状态准备要求写成同一函数的调用布局要求。** 模型要求准备调用必须在同一个 bring-up 函数中排在通知前。准备也可能在先前阶段或别的函数完成；早调用也可能因资格守卫、错误对象或失败而没有效果。x86 的局部注释可以支持其实现意图，不能独自规定所有架构的代码布局。保留“在实际消费前，适用对象需满足必要状态”的假说，不能采用这个过强等价。
2. **从当前状态关系反推所有成员都执行过回调。** 模型推断其他 mask 成员都已完成 starting 回调。消费者检查的是当前 `rq->core` 和组关系，没有核对这段执行历史；初始 self 状态也可来自 `sched_init`。不能以 present／possible／online 或“完成回调”替代应有的状态关系。

两项经主智能体和独立方法角色复核，**自动采纳数为 0**。完整回答和局部三项正确事实，均不能掩盖这两项语义过推。当前完整契约判定仍 `insufficient`。
