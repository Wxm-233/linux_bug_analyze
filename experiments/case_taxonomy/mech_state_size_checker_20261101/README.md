# “表项状态—大小来源”机制的自动检查

## 这一轮要回答什么

RISC-V NAPOT清除缺陷是研究者按机制读代码找到的。本轮把这个机制写成自动检查，看程序能否自己标出它，并检查标记量和误标。

**事先声明**：用到的已知案例全部是开发数据，结果只说明机制能被自动表达和执行，不说明它在没见过的代码上有效。

## 做法

1. **找消费点**：在各架构大页文件中，找调用解码函数的位置。解码函数是事先列定的架构事实：arm64的`pte_cont`；RISC-V的`pte_napot`、`napot_cont_order`；sparc的`tte_to_shift`等。
2. **判本地保证**：消费点之前，路径上有“在内存”的判断，或者有“不在内存就提前返回”的写法。
3. **查调用者**：在公共代码中找所在函数的全部调用点，按路径条件或传入值的构造方式，分为三类：
   - NP：可能传入不在内存的表项；
   - P：保证在内存；
   - U：不受约束。
4. **判定**：
   - 有NP调用点，判为疑似违反（强）；
   - 只有U调用点，判为疑似违反（弱）；
   - 全部是P调用点，判为调用者保证。

### 正式运行前的实现修正（如实记录）

冒烟运行（只看终点版本的RISC-V部分）时发现，`named_spans`给出的范围从`{`那一行开始，不含函数头，参数表因此读错。改为用库函数`header_window`把函数头拼回第一行之后，再正式运行。判据没有改动。

## 结果

### E1 终点版本：三项都满足

| 标准 | 结果 |
| --- | --- |
| RISC-V的`huge_pte_clear`和`huge_ptep_get_and_clear`都被标记 | 是：前者**强**（3个调用点都是NP：解除映射的非present分支、mremap、uffd标记解除）；后者**弱**（mremap、vmalloc等调用点为U） |
| 12处正常对照中被标记的不超过2处 | 1处：RISC-V的`huge_ptep_clear_flush`，判为弱 |
| 终点版本标记总数不超过15 | 10处消费点：RISC-V 4处，sparc 6处 |

RISC-V其余位置判断正确：
- `huge_ptep_get`、`set_huge_pte_at`为本地保证；
- `huge_ptep_set_access_flags`、`huge_ptep_set_wrprotect`为调用者保证，传入的新值由`huge_pte_mk*`构造，或者调用点处在排除了各种不在内存情形的`else`分支里。

arm64在终点版本没有标记。

### E4 终点版本其余8处标记的人工核对

| 标记 | 归类 | 说明 |
| --- | --- | --- |
| RISC-V `huge_ptep_clear_flush`（2处，弱） | (b) | 调用者是`hugetlb_wp`（与在内存的表项做`pte_same`）和`try_to_unmap`/`try_to_migrate`（不带`PVMW_MIGRATION`的映射遍历只返回在内存的表项）。检查程序不认识这两种保证方式 |
| sparc `huge_tte_to_shift`、`huge_tte_to_size`（2处，弱） | (b) | 它们本身就是解码辅助函数，标记与调用它们的函数重复 |
| sparc `__set_huge_pte_at`（2处，强） | (c) | NP来自uffd写保护标记（sparc不支持，实际走不到）和`UFFDIO_POISON`标记（走得到）。推出的大小是错的，但写入和清除都只处理一项，前后一致，危害不明。与案例清点的U一致 |
| sparc `huge_ptep_get_and_clear`（2处，弱） | (c) | 同上 |

疑似问题(a)：0条。

## 判定

按事先标准：**E1三项全部满足，E2为3/4，记为“机制能被自动表达，并能复现开发数据上的问题”**。不能表述为“已证明能在未见代码上检测”。

## 局限

- **解码函数清单是人工列的架构事实**：漏掉了“从表项指向的页推大小”（`6f1bace9`）和powerpc 8xx的位判断。
- **调用者分类只认识写出来的条件判断**：`pte_same`、页表遍历接口这类隐含保证会被当成U，正是弱标记的主要来源。
- **只覆盖一个机制**：别的机制造成的缺陷，这个检查一概看不到。

## 统计

不调用模型；构建0；新确认缺陷0。
