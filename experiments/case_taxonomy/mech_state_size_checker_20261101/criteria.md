# “表项状态—大小来源”机制的自动检查（判据，实现前写定）

## 这一轮要回答什么

研究目标是验证共性机制能否**指导自动检测**。RISC-V NAPOT清除缺陷（`riscv_napot_clear_verify_20261101/`）是研究者按机制读代码找到的，不是程序找到的。本轮把这个机制写成自动检查，回答三个问题：

1. 程序能否在不给提示的情况下标出这个缺陷，同时不把已确认正常的位置标成疑似？
2. 在历史版本上，能否在修复前标出已知的同机制问题？
3. 在终点版本上一共标出多少条，人工核对后是什么性质？

**事先声明**：用到的已知案例全部是开发数据。RISC-V缺陷、A/B两组修复、12处正常对照都已被研究者读过，规则也是看过它们之后写的。所以本轮结果只能说明“机制能被自动表达和执行，并且标记量可控”，**不能**说明它在没见过的代码上有效。唯一的留出组C（`20156ce2`）照常检验，事先预计会漏：它的错因是空PMD槽，不是表项内容。

## 检查的三步

### 第一步：找消费点

**范围**：每个架构的大页实现文件，与案例清点的路径规则相同，即`arch/*/mm/hugetlbpage*.c`、`arch/*/mm/hugetlb*.c`、`arch/*/include/asm/**/hugetlb*.h`（目录深度不超过3层）、`arch/powerpc/mm/nohash/8xx.c`。

**消费点**：这些文件的函数里，调用了“从表项内容解码大小或是否成组”的解码函数的位置。解码函数是架构事实，事先列定如下：

| 架构 | 解码函数 |
| --- | --- |
| arm64 | `pte_cont` |
| riscv | `pte_napot`、`napot_cont_order` |
| sparc | `tte_to_shift`、`huge_tte_to_shift`、`huge_tte_to_size` |

其余架构没有以函数形式出现的解码，不检查。已知遗漏：powerpc 8xx用`_PAGE_HUGE`位直接判断。

### 第二步：本地保证

如果函数内满足以下任一情况，就判为**本地保证**，并且只要求在消费点之前出现：

- 消费点所在的路径条件中，有正向的“在内存”判断，例如处在`if (pte_present(x))`的分支内；
- 前面有提前退出的判断，例如`if (!pte_present(x)) { ...; return; }`；
- 同一个条件表达式里，前面有`!pte_present(x) ||`或`pte_present(x) &&`。

“在内存”判断包括`pte_present`和`pte_valid`。不核对变量是否同一，这是已知简化。

### 第三步：调用者

**找调用点**：对没有本地保证的消费点，取它所在的函数F。如果F只在本架构内部被调用（例如sparc的`__set_huge_pte_at`），就上溯一层到调用它的架构函数。然后在公共代码中找F的所有调用点，范围为`mm/`、`include/linux/`、`include/asm-generic/`、`fs/`下的`.c`和`.h`，并排除定义处。

**每个调用点按路径条件分类**：

| 类 | 判据 |
| --- | --- |
| **NP**（可能传入不在内存的表项） | 处在“不在内存”判断的分支内。这类判断包括`!pte_present`、`is_swap_pte`、`pte_is_marker`、`is_pte_marker`、`pte_marker_*`、`is_hugetlb_entry_migration`、`is_hugetlb_entry_hwpoisoned`、`softleaf_*`、`is_migration_entry`、`is_hwpoison_entry`、`pte_is_uffd_wp_marker`、`pte_swp_*`、`huge_pte_none_mostly`；或者传入的新值由`swp_entry_to_pte`、`make_pte_marker`、`make_*_entry`构造 |
| **P**（在内存） | 处在正向“在内存”判断的分支内，或者前面有提前退出的“不在内存”判断；或者处在一串判断“不在内存”各种情形的`if/else if`之后的`else`里（排除法）；或者传入的新值由`make_huge_pte`、`arch_make_huge_pte`、`pte_mk*`、`huge_pte_mk*`、`huge_pte_modify`、`huge_pte_wrprotect`、`mk_pte`、`pfn_pte`构造 |
| **U**（不受约束） | 以上都不是 |

### 判定

每个消费点给出以下一种结论：

| 结论 | 条件 |
| --- | --- |
| 本地保证 | 第二步成立 |
| **疑似违反（强）** | 至少一个调用点为NP |
| **疑似违反（弱）** | 没有NP，至少一个U |
| 调用者保证 | 全部调用点为P |
| 未知 | 找不到公共调用点，例如只经函数指针调用 |

疑似违反（强、弱）合称“标记”。

## 实现约定

- 语句结构用一个小型分析器解析：去掉注释、字符串和预处理行，识别`if/else`、循环、`switch`和代码块，计算每个调用点的路径条件，其中包括提前退出带来的反向条件。
- 函数切分用库函数`sibling_pairs.named_spans`。
- 源码一律用`git show <版本>:<路径>`读取，不改动`/root/repos/linux`。
- 不调用模型，不构建内核。

## 评价（事先写定）

1. **E1 终点版本（开发数据）**：
   - RISC-V的`huge_pte_clear`和`huge_ptep_get_and_clear`都应被标记；
   - 案例清点中的12处正常对照，标记数应不超过2；
   - 终点版本的标记总数应不超过15。
2. **E2 历史回溯（开发数据）**：在4个架构修复的父版本上（`6f1bace9`、`1de195dd`、`49c87f76`、`83d78ac6`），被修函数中修复所改动的消费点应被标记。标准是至少3/4。
   - `83d78ac6`之后门槛仍在，修复后仍被标记属于预期。
   - 另外报告留出组C（`20156ce2`）父版本的结果。
3. **E3 规模**：在`v4.14`、`v4.19`、`v5.10`、`v5.15`、`v6.1`、`v6.6`、`v6.12`、`v6.18`、`v7.0`、`v7.2`和终点版本上运行，报告每个版本按架构的标记数。
4. **E4 人工核对**：终点版本的标记，除RISC-V那两处以外全部人工核对，归为：
   - (a) 疑似问题；
   - (b) 有合理原因；
   - (c) 判断不了。

   (a)类只记录，不对外报告。

**判断标准**：E1三项全部满足，并且E2达到3/4，记为“机制能被自动表达，并能复现开发数据上的问题”。否则分析原因。无论结果如何，都**不得**表述为“已证明能在未见代码上检测”。

## 不做的事

不调用模型，不构建或运行内核，不对外报告。
