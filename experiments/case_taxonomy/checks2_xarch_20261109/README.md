# 检查二“跨架构实现对照”第一版（checks2_xarch_20261109）

## 这一轮要回答什么

检查二问：各架构对同一接口的实现，是否都完整提供了调用方需要的行为。这一轮只做靠“和其他架构的同名实现对照”能判断的部分，以 riscv 为目标，x86_64、arm64 为对照，共六种标记：

| 标记 | 方面 | 含义（只报 riscv 缺的方向） | 例子 |
| --- | --- | --- | --- |
| `stub` | ① | riscv 是空函数或只返回常数，对照方有真实实现 | 修复前 riscv 的 `arch_get_idle_state_flags` 用公共默认实现直接返回 0，arm64 有自己的实现 |
| `write-missing` | ② | 对照方直接写了某个共享资源，riscv 沿调用链 3 层都没写 | |
| `call-missing` | ② | 对照方直接调了一个会写共享资源的公共函数，riscv 3 层内都没调 | |
| `arg-diff` | ② | 调同一个公共函数时，同一位置的常数实参不同 | |
| `errno-diff` | ③ | 对照方返回的错误码，riscv 没有 | |
| `param-check` | ④ | 对照方在危险使用（下标、长度、移位、解引用）前检查了参数，riscv 没查 | |

要回答三个问题（判据 `criteria.md` 第一节）：
1. 以我们的边界全集为候选，能否报出上述失配？
2. 24 条可评估样本，在各自修复前的 riscv 代码上能否报出？
3. 当前版本报出多少，其中多少像真问题？

**参考线**（判据第六节）：
- 命中不少于 ⌈n/3⌉ 条，记为“检出能力达标”；
- 当前版本抽 40 条人工核对，疑似真问题不低于 25%，记为“噪声可接受”；
- 两条都满足，本轮才算达标。

判据写于实现之前（SHA 在 `criteria_sha256.txt`）。之后有两次修订，都只修我自己的脚本，判据、样本和参考线都没改：
- **修订 1**：去掉写依赖文件参数时漏了 `-Wp,-MD` 这种写法；
- **修订 2**：把修复目录和它的上级目录同时交给 make，A196 构建时两个目标互相抢，导致失败。

## 我做了什么

1. **事实抽取**（`archbound_ext/`）：
   - 复制师兄的 archbound，按判据第二节补了三处：每个单元的解析结果、调用的常数实参、函数返回的常数集合（`patch_ext.py`）；
   - 用 LLVM 18 编译。原压缩包没动。
2. **对照分析**（`xcmp.py`）：
   - **候选**：riscv、x86_64、arm64 三个修订边界池里“公共层使用、架构层提供”的函数的并集，共 1754 个；
   - **实现**：取所有非 static 的定义，加上头文件里的 static 定义，合并起来比较。这样修掉了师兄工具“每个架构只取第一个定义”的问题；
   - **传递**：写集合和调用集合沿直接调用展开 3 层，riscv 交给辅助函数做的事不算缺失。
3. **自测**（`selftest/`）：
   - 迷你内核树覆盖六种标记，以及多定义合并、传递抵消、方向、`.c` 中的 static、非候选这几种“不该报”的情况；
   - 第一次运行多出 1 条 `arg-diff`。按判据它应当报出，是我写期望集时漏了，记在 `expected_corrections.md`；
   - 反向检查（`reverse_check.txt`）：改成“每个架构只取一个定义”或“不展开调用”，自测都会失败。
4. **评估**（`eval_samples.py`）：
   - 对每条样本，导出修复前的源码，**只构建**判据范围内的目录和修复文件所在目录，每条约 3 分钟；
   - 收集事实，与当前版本的 x86_64、arm64 对照，再计分。
5. **人工核对**（`review_sample.py`，在结果出来之前写定，种子 20261109）。
6. **没命中的原因**（`miss_analysis.py`）和**降噪摸底**（`noise_exploration.py`），都在计分之后做，只作描述。

## 结果

### 当前版本：253 个不同问题

- **候选：** 1754 个。riscv 有实现的 855 个，构成可对照家族的 771 个；riscv 没有实现的 899 个；只有 riscv 实现、无从对照的 84 个。另有 2113 个只以宏提供的边界，本轮不覆盖。
- **标记：** 253 个不同问题。stub 109、write-missing 94、call-missing 28、errno-diff 15、arg-diff 7、param-check 0。按对照方分：对 x86 有 142 个，对 arm64 有 135 个。
- 三个构建的单元全部解析干净：riscv 963、x86 1084、arm64 1243。

### 人工核对 40 条：疑似真问题 1 条，噪声不可接受

| 原因 | 条数 | 例子 |
| --- | ---: | --- |
| 对照架构特有的功能 | 25 | `in_gate_area_no_mm`（x86 vsyscall）、`elf_core_extra_data_size`（arm64 MTE） |
| 对照方改写的是参数变量本身 | 6 | asm-generic 的 `arch_set_bit` 里 `p += BIT_WORD(nr)` |
| 错误码不同，但调用方不区分 | 5 | `apply_relocate_add` |
| riscv 配置没开相应功能 | 2 | `module_frob_arch_sections` 只在 RELOCATABLE 时才有 riscv 版本 |
| 公共代码已给默认值 | 1 | `kvm_arch_init_vm` 的 `max_vcpus` |
| 日志实参 | 1 | `arch_setup_dma_ops` 的 WARN |
| **疑似真问题** | **1** | 见下 |

**疑似真问题：`kvm_arch_vcpu_precreate`（#126）。**
- arm64 在中断控制器（vgic）初始化之后，拒绝再创建 vCPU（返回 -EBUSY）；riscv 恒返回 0。
- riscv 的 AIA 初始化（`aia_device.c` 的 `aia_init`）只给当时已有的 vCPU 分配 IMSIC 上下文。之后创建的 vCPU，`imsic_state` 为空。各入口都先判空再跳过，所以不会崩溃，但这个 vCPU 静默地没有 IMSIC，用户态也得不到任何错误。
- 需要动态验证；按规则只在本地记录，不对外报告。

### 24 条样本：命中 1 条，检出能力不达标

只有 **A274** 命中：修复前，riscv 的 `arch_get_idle_state_flags` 用公共默认实现直接返回 0，arm64 有自己的实现，`stub` 标记正好报在修复的函数上。

没命中的 23 条，卡在哪一步（`miss_analysis.json`）：

| 卡在哪一步 | 条数 | 样本与原因 |
| --- | ---: | --- |
| 修复函数不在候选集 | 15 | KVM 内部函数（A215、A225、A247、A336、A368、A380）、启动与资源（A085 `setup_bootmem`、A155 `init_resources`）、`.c` 中的 static（A026 `patch_map`、A039）、系统调用入口（A310 `do_trap_ecall_u`）、版本间改名（A288 `module_alloc`，当前对照方已改为 execmem）、kexec（A392）、驱动（B467 perf、B485 PCI MSI） |
| 比较了，报的类型不对 | 2 | A393、A398 报的是 `errno-diff`，缺陷属于输入检查，判据要求 `param-check` |
| 比较了，被过滤规则挡掉 | 2 | A043 漏调 `cpumask_clear`、A112 调 `early_ioremap` 而不是 `early_memremap`。被漏调的函数自己不直接写共享资源，而是交给别的函数去写，被 call-missing 的过滤条件挡掉 |
| 比较了，差别不在模型里 | 4 | A025（页表项取值位）、A143（表项是否存在）、A196（地址校验方式）、A387（写的是架构私有结构） |

**本轮结论：检出不达标（1/24），噪声不达标（疑似 2.5%），本轮不达标。**

## 看出的几点

1. **按“同名边界函数”对照，覆盖面太窄。** 23 条没命中里，15 条的修复函数根本不在候选里。样本里的缺陷大量出在架构内部的辅助函数、KVM、启动代码里，或者出在名字不同、作用相同的实现上。纯对照只覆盖了接口层的一小部分。
2. **单靠“比较差异”，分不清真缺陷和合理的架构差异。** 降噪摸底（`noise_exploration.json`，事后统计，不影响本轮结论）显示：
   - “去掉 riscv 只有公共默认实现、且只有一个对照架构有实现的家族”能把 253 条降到 98 条，可它**也正好去掉了唯一的命中 A274**。A274 的缺陷就是“arm64 有、riscv 退回公共桩”，和 25 条“arm64 特有功能”的误报长得一模一样；
   - 只有“去掉参数键 `p#N`”是安全的（253→213，命中保留）。
3. **由此引出下一步：用别的架构的补丁作证据（补丁引导）。** 如果对照架构是专门打补丁加上某个行为的，这个行为很可能是调用方真正依赖的。这能把真缺陷和架构特有功能区分开，而且不要求两边函数同名、也不要求修复的函数是边界函数。样本中 M8“落后于参照的演进”16 条、M10“同一约定、各自实现”24 条可以作为开发集。
4. **几处具体可改的地方**（下一轮先写进判据）：
   - call-missing 的过滤改为“被漏调的函数在 3 层内会写共享资源”（A043、A112）；
   - 去掉参数键；
   - 输入检查要覆盖“是否存在”“是否在区间内”这类语义判断，不只看参数在危险位置的使用（A143、A196）。

## 局限

- 对照方用的是当前版本（v7.3-rc2），目标是修复前的 riscv，属于跨版本对照，对照方的实现可能已经改过（如 A288）。
- x86_64 defconfig 没开 KVM，KVM 家族只有 arm64 一个对照。
- 人工核对由我一人完成。
- 样本都是我在分类阶段看过的，只能作开发集。下一步的留出集用 LoongArch 上的跨架构缺陷（用户 2026-11-09 决定），冻结规则后只跑一次。
