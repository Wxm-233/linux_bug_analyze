## 这一轮要做什么

第二部分的场景是：上游已经有了一个补丁（其他架构或公共代码中的修改），目标架构还没有对应的补丁，需要把它迁移过来。要评估迁移和迁移后的检测，需要一批**有标准答案**的历史样本：上游先出现的参照补丁，以及目标架构后来真实提交的跟进补丁。

## 二、回放配对的定义

目标提交T（池中的一个提交）和参照提交R，满足以下三条时，记为一个**回放配对**：
1. **R先进入上游**：R的提交日期早于T。R改动的是另一个架构的代码，或者公共代码。
2. **处理的是同一个具体条件**：R修复或实现了某个条件，T是把同样的处理带到目标架构。修改的是同名函数、同一约定或同一种修法。只是“其他架构也有类似代码”不算。
3. **R能用提交号指出**，并在仓库中用`git show`核实过。

找R的途径：
- T的说明中点名了R；
- T与R属于同一系列（作者相同、日期相近、标题模式相同，例如`x86/purgatory: …`与`riscv/purgatory: …`）；
- 在参照架构的对应文件中用`git log`查找T之前处理同一条件的提交。

**类型**：
- **A 跟进其他架构的修复**：R是其他架构对同一问题的修复；
- **B 跟进公共代码的改动**：R是公共代码的改动，T让目标架构适应它。若同时有其他架构适应同一改动的提交，参照取那个提交，它更接近迁移时可照的写法。

**不算配对的情况**：
- 只与目标架构自身有关的问题；
- 跨架构，但找不到具体的参照提交；
- 参照提交晚于T；
- T本身同时改动多个架构（这不是“跟进”）；
- 只修编译或链接错误的提交（编译器就能发现）。

## 三、标注字段

| 字段 | 内容 |
| --- | --- |
| `pair` | 是否为回放配对 |
| `kind` | A或B |
| `refs` | 参照提交号（可以有多个，例如系列中的前后几个） |
| `ref_arch` | 参照提交改动的架构，公共代码记为`common` |
| `mechanism` | 按`cross_arch_sample_set_20261102/catalog_v2.md`及修订2 |
| `simple` | T在目标架构上的改动不超过40行、不超过2个文件，记为简单 |
| `found_by` | 找到参照的途径：说明点名、同一系列、按文件查找 |
| `reason` | 一句话说明T与R处理的是同一条件 |

非配对条目只填`pair=false`和一句话理由。

## 五、回放材料（程序生成）

每个配对生成：
- `base`：T的父提交，即目标架构跟进之前的代码；
- `reference.diff`：R中参照架构或公共代码部分的改动；
- `truth.diff`：T的改动（标准答案，单独存放，不进入迁移的输入）；
- `target_files`：T改动的目标架构文件在`base`中的内容。
