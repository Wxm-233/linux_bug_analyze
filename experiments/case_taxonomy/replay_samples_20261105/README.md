# 第二部分的历史回放样本（第一批）

## 这一轮要做什么

第二部分的场景是：上游已经有了一个补丁（其他架构或公共代码中的修改），目标架构还没有对应的补丁，需要把它迁移过来。要评估迁移以及迁移后的检测，需要一批有标准答案的历史样本：
- **参照补丁R**：上游先出现的补丁；
- **跟进补丁T**：目标架构后来真实提交的补丁。

本轮从此前没用过的159个修复中找出这样的配对，逐条核实，冻结标签，并生成回放材料。没有运行迁移，也没有调用模型。

| 文件 | 说明 | SHA |
| --- | --- | --- |
| `criteria.md` | 判据，阅读提交之前写定 | `01337214…` |
| `candidates.py` → `candidates.txt` | 阅读辅助：说明中点名的提交、其他架构的同系列提交、其他架构同名函数的近期改动。第一次只在T的祖先中找同系列提交，漏掉了其他分支上的，结果保留为`candidates_attempt1.txt` | 见`delivery_manifest.json` |
| `labels.py` → `labels.json` | 逐条标注，参照提交都用`git show`核实过，并由程序检查R早于T | `f3735dc5…`（冻结） |
| `make_materials.py` → `replay/`、`truth/` | 每个配对的回放材料；标准答案单独放在`truth/` | 见`delivery_manifest.json` |

### 不算配对的边界情况

- **L080**（LoongArch BPF去掉返回值符号扩展）：说明写“像其他架构那样”，但其他架构从来没有做过这种扩展，所以没有具体的修复提交可作参照。
- **R000**（RISC-V把返回用户态的慢路径移到C）：arm64的`4d1c2ee2709f`做法相似，但那是没有功能变化的整理，不是同一问题的修复。
- **L118**（LoongArch TIF位冲突）：同一系列中其他架构编号正确，但T修的是LoongArch自己转换时的编号错误，不是跟进。
- **L120**：RISC-V有同名修复`d0bf7cd5df18`，但两者都只消除静态检查警告，原逻辑是正确的。

## 参考线：样本不够

按判据第六节，16对少于30对，**只能作描述，不够用于评估**。159个修复中只有约十分之一是“先有参照、后跟进”的配对。所以开发集与测试集还没有划分。判据规定划分时按`random.Random(20261105)`抽四分之一为开发集；扩大样本池之后再一起划分，以免开发集和测试集的标准前后不一。

扩大样本池的选择（需要先写修订再阅读，只数了个数）：

| 选择 | 个数 | 预计 |
| --- | ---: | --- |
| RISC-V `v5.15..v6.1`中带`Fixes:`的修复 | 123 | 按本轮约十分之一的比例，约十几对 |
| LoongArch `v6.1..`终点版本中，说明提到arm64、RISC-V或x86的提交（不要求`Fixes:`，也包括新功能） | 146 | 配对比例应明显更高 |
| RISC-V `v6.1..`终点版本中，说明写“like/similar to/same as arm64、x86、LoongArch”的提交 | 31 | 配对比例应很高 |
| LoongArch `v6.1..v6.6`中带`Fixes:`的修复 | 9 | 太少 |

后两项按“说明提到其他架构”来选，会偏向说明中直接点名参照的样本，迁移可能比实际情况容易，使用时要注明。它们还包括新功能的迁移，例如prog_pack这类，这与第二部分的场景更接近。
