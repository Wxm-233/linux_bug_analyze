# 跨架构缺陷的修复方式与机制对应（判据，标注之前写定）

## 这一轮要回答什么

跨架构缺陷样本集（`cross_arch_sample_set_20261102/labels_v2_1.json`，SHA前16位`cc863e18a00a87bd`）中，135条跨架构缺陷都来自上游的修复提交。每条已经标了机制（M1–M10）、对应物、修复时其他架构的状态（S0–S3）和掩盖方式。

本轮给每条补标“修复是怎么做的”，然后回答三个问题：
1. 每类机制的缺陷，通常怎么修？
2. 修复是否照着对应物的做法改？照搬时有没有只改一半？
3. 能不能据此为每类机制写出修复策略？策略要包括典型修法、适用条件和反例。

本轮只读提交、做标注和统计，不调用模型，不改动样本集原有标签。

## 一、材料

`collect.py`导出每条修复提交的说明和改动（`dump/`），并附上样本集原有标签供参考。

## 二、标注字段（第一标注人：模型Claude，逐条读改动后标）

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `action` | 修复动作，见第三节，可多选，第一个为主动作 | 改动实际做了什么 |
| `follow` | F1 照对应物补齐；F2 部分照搬；F3 另行实现；F4 无可照的对应物 | 修复后，RISC-V处理这个条件的方式与对应物的关系 |
| `layer` | A 架构代码；C 公共代码；AC 两者都改 | 按改动的文件判断，构建文件按其所在目录 |
| `cites` | Y / N | 提交说明是否明确提到其他架构或公共代码中的同类做法（如“like arm64”“as x86 does”） |
| `note` | 一句话 | 修复要点 |

`follow`的判断：
- **F1**：对应物处理同一条件的方式，修复后RISC-V在该条件上与它一致，允许名字、寄存器等架构差异。
- **F2**：修复只覆盖了对应物所处理条件的一部分，并且能在修复后的代码中指出遗漏的部分。
- **F3**：有对应物，但修复按RISC-V自身情况采用了不同做法。
- **F4**：没有可照的做法，包括对应物当时也错（S2），或其他架构没有这个功能（S3）。

## 三、修复动作（草稿，在开发集上试标后定稿）

| 代码 | 动作 | 例子 |
| --- | --- | --- |
| A1 补防护或检查 | 加`array_index_nospec`、边界或参数检查、能力或特性检查 | KVM下标钳住 |
| A2 调整顺序或时机 | 移动调用位置、调整初始化顺序、补齐“清空—刷新—写入”步骤 | 先初始化静态开关再解析启动参数 |
| A3 改执行上下文 | 开或关中断、把可能睡眠的操作移出锁区、换锁的种类 | `copy_*_user`移到锁外 |
| A4 补实现或覆盖默认实现 | 实现架构钩子、覆盖公共`__weak`默认实现、补缺失的处理分支 | 提供RISC-V自己的`is_trap_insn` |
| A5 换用正确的接口、属性或标注 | 换映射接口、改节区或`noinstr`等标注、改用正确的宏 | `early_ioremap`改`early_memremap` |
| A6 改配置或构建依赖 | Kconfig的select/depends、Makefile | kexec_file的依赖 |
| A7 改数值、类型、宽度或对齐 | 常量、类型宽度、符号扩展、对齐 | — |
| A8 补资源释放或清理 | 出错路径释放、恢复原状态 | — |
| A9 删除或回退错误代码 | 删掉多余处理、回退引入问题的提交 | — |
| A0 其他 | 以上都不合适，写明 | — |

**定稿规则**：
- 先在开发集27条上试标，可以合并、拆分或改名上述动作，但每个动作都要有明确定义。
- 定稿写入`criteria_amendment1.md`并记录SHA，之后才标测试集108条。
- 测试集标注中，如果遇到定稿分类放不下的情况，标`A0`并写明，不再改分类。

## 四、统计（全部135条报告，另分开发集、测试集）

1. 机制 × 主动作的分布表，每格给出条数和代表例子。
2. 机制 × `follow`，以及状态（S1/S2/S3） × `follow`。
3. `cites`的比例，以及`cites`与`follow`的关系。
4. 每类机制：给出典型修法；条件不满足时的反例（`follow`=F2、F3的情况）；以及与补丁迁移的关系（F1占多少）。

**修复策略的写法**：只对条数不少于5的机制写策略，少于5的只作描述。策略是对历史修复的归纳，不是经过独立验证的修复方法。

- 复核结果出来之前，结论注明“第一标注人的标注”。
