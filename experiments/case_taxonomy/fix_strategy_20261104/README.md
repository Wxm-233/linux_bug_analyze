# 跨架构缺陷的修复方式与机制对应

## 这一轮要回答什么

师兄建议：既然已经找出了很多语义失配的根因，可以看看这些缺陷的上游补丁，修复方式能否和失配的机制对应上，进而提出修复策略。

跨架构缺陷样本集（`cross_arch_sample_set_20261102/`）中的135条缺陷都来自上游修复提交，已经标了机制、对应物和修复时其他架构的状态。本轮给每条补标“修复是怎么做的”，回答三个问题：
1. 每类机制的缺陷通常怎么修？
2. 修复是否照着对应物改？
3. 能否为每类机制写出修复策略？

本轮只读提交、做标注和统计，不调用模型，不改样本集原有标签。

## 做法

第一标注人（模型Claude）逐条阅读修复提交的说明和改动，标注四个字段：

| 字段 | 含义 | 取值 |
| --- | --- | --- |
| 修复动作 | 修复实际做了什么 | 11类，见下 |
| `follow` | 修复后，RISC-V处理这个条件的方式与对应物的关系 | F1 与对应物一致；F2 只照搬了一部分；F3 另行实现；F4 修复时没有可照的正确做法 |
| `layer` | 改动在哪一层 | 架构代码 / 公共代码 / 两者都改 |
| `cites` | 提交说明是否明确提到“像某架构那样” | 是 / 否 |

**修复动作**的分类先在开发集27条上试标，再定稿。定稿时补了两类：
- “换信息来源”：例如大页大小不再从页表项内容推出，改用传入的参数；
- “补同步与内存顺序”。

定稿之后才标测试集108条。

## 修复策略（对历史修复的归纳，未经独立验证）

只对条数不少于5的机制写策略。

| 机制 | 典型修法 | 适用条件 | 反例或注意 |
| --- | --- | --- | --- |
| **M10 同一约定** | 找到参照架构处理同一条件的代码，照它用同样的接口、属性或顺序 | 参照架构当时已经正确（21/24） | 架构语义不同时要另写，如向量状态恢复按RISC-V向量规范处理 |
| **M7 边界与宽度** | 按目标架构的ABI修正数值：RV64的符号扩展、RV32的寄存器对、对齐和偏移；客体或用户可控的下标照x86、arm64加`array_index_nospec` | 参照架构或公共代码已有正确写法 | **加防护要覆盖同一文件中的所有同类下标**：PMU的修复给计数器下标加了防护，却漏了同一函数中的事件编号下标 |
| **M1 默认假设** | 在RISC-V覆盖公共默认实现，加入RISC-V特有的情况（如NAPOT大小），参照已自行实现的架构 | 公共默认按多数架构写，RISC-V有额外情况 | 问题出在只有RISC-V用的公共分支时，改为在公共代码中按配置区分（F4） |
| **M8 演进落后** | 公共代码改约定后，查各架构对同一约定的实现，照先跟上的架构改 | 有架构先改过 | 公共改动后各架构同时出错时，在公共代码统一修 |
| **M5 执行上下文** | 让操作符合场合限制：用户态异常先开中断、陷入处理中用raw锁、关中断时只刷本核TLB、空闲函数标`noinstr` | 参照架构的做法通常可照搬 | 非对齐陷入曾先改用不睡眠的拷贝函数，后来被回退，改为照对应物先开中断 |
| **M9 配置条件** | 在Kconfig或条件编译中表达依赖或能力（如ZACAS扩展、只有64位`time_t`的系统调用） | 多为公共代码中只有RISC-V或32位才走到的分支 | 8/14没有可照的做法 |
| **M3 映射步骤** | 补齐“清空—刷新—写入”和指令缓存维护，参照arm64的Break-Before-Make | 8/9可照arm64 | 指令缓存刷新出现过“修复再修复”：先补局部刷新，后又误删全局刷新，再补回来 |
| **M4 内存顺序** | 照参照架构或本架构已有的完全有序实现，补屏障或原子操作 | 弱序架构才暴露 | 公共驱动中的问题（如mlx5e）在驱动内统一修 |

## 与补丁迁移的关系（只作描述）

- **多数修复可以看成一次跨架构迁移**：修复时对应物已经正确的96条中，87条最终与对应物一致。样本集已经标出对应物的位置，所以“找参照、搬到RISC-V”正是补丁迁移要做的事。
- **迁移时只搬一半，会制造新缺陷**：
  - 样本集中有5条缺陷，起因就是照arm64加功能时漏了一部分，例如漏了禁止插桩、漏了auxv长度加一；
  - 修复本身也可能只照搬一半（F2）：NAPOT大页的修复保留了arm64已删除的门槛，后来经运行确认留下残留表项；PMU的修复漏了一处下标。
- **修复链**：样本集内有6条修复又引出了后续修复，例如指令缓存刷新连续修了三次、kfunc参数符号扩展先只处理了4字节。

所以迁移不能只搬改动的文字：要按机制列出需要成立的条件，在RISC-V上逐处核对。这与发现缺陷所用的是同一套条件。

## 局限

- 标注由第一标注人完成，GPT复核材料已准备好（30条），还没有复核。结论都是第一标注人的标注。
- 修复策略是对历史修复的归纳，没有在新缺陷上验证过。
- F2的判断依赖后续发现（例如后来的修复或运行确认），可能低估。
- 有3对是同一补丁的重复提交（A188/A197、A190/A191、B444/B445），按样本集原样各算一条。
