## 一句话结论

**这一步没有达到“有所提高”的目标。** 22 个样本上，契约挖掘只命中 3 个，和 P1 检查合起来是 5/22（基线 4/22），参考线是 8 个。当前版本按事先定的排序，前 30 条两人审下来没有一条“可能”。

**但它有一个有价值的产出**：不手写规则，它从数据里自动学出了“受限接口之前要查 present”这一组契约，报出的位置有 80 个和 P1 检查重合，两个已确认缺陷的位置都在里面。拖后腿的是另外两种契约带来的噪声，以及排序方法。

## 这一步想做什么（说人话）

原来的效果依赖只认一种写法：调用架构接口后把开关设成常数，跳过自己的工作（X1）。`depmine` 挖出的 22 个真实依赖缺失里，没有一个是这种写法，全都是“该做的根本没写”。

所以这一步改为统计“大多数调用点怎么用某个架构接口”，把偏离多数的地方报出来。分三种：

- **K1 前置条件**：例如多数代码在调用 `pmd_leaf(x)` 之前先查 `pmd_present(x)`，这里没查；
- **K2 返回值检查**：多数代码会检查某接口的返回值，这里没查；
- **K3 后置效果**：多数代码在调用 A 之后，会对同一对象再调用 E，这里没有。

守卫识别直接复用 P1 检查器已经验证过的那套逻辑，只是把“present 判断”推广成任意判断。不编译，直接读 git 对象，挖当前版本整个范围（4081 个文件、5 万个函数）只要 15～40 秒。

## 看出的几点

1. **“统计多数人怎么用”能自动学出 P1 规则**，不需要手写受限接口清单，以后可以用它发现其他同类前置条件。但它学到的契约比例只有一半左右，因为守卫常常写在调用者里，单靠比例分不清真偏离和合理偏离。
2. **K2、K3 在内核里噪声很大**。锁的配对被包装函数打破，取值接口天生不需要“检查返回值”。要用的话，K2 应只限于返回错误码或指针的接口，K3 要能识别“加锁后返回”这类包装。
3. **排序是瓶颈**。两个真缺陷的位置都被报出来了，但淹没在一百多条里。下一步（规划第 2 步）按各架构的位编码给每个偏离算“哪些架构、遇到哪种非 present 项会读错或改坏”，用它排序，应该能把它们提上来。B-1 在三个架构上都会读错位，B-2 在 arm64 上会改坏项，这两个都是按编码能算出来的。
4. P2～P6 这几类，不适合用“多数人怎么用”来描述，需要别的办法（例如 P2 看刷缓存的范围是否覆盖整个大页，P5 看调用时机）。
