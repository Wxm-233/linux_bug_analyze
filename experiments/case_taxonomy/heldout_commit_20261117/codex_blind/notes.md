## 最需要说明的边界项

### [1] 0f90b88dbcd1：是，c2a / P5

这不只是任意平台都可能发生的 NMI 时间戳竞态。修复时 `arch/x86/kernel/kvmclock.c:144` 的暂停检查会经 `pvclock_touch_watchdogs()` 改变 watchdog 状态，`include/asm-generic/kvm_para.h:12` 和 PowerPC 的同名函数则只返回 false。公共 watchdog 读取状态必须与该架构钩子的实际效果排序；完整补丁也同时处理了通用的单次读取问题。

### [3] d9807d60c145：是，a2c / P2

修复位置在架构初始化代码，但跨层依赖具体存在于 `sparse_init()` 返回后即调用 `zone_sizes_init()` 使用 vmemmap。RISC-V 的页表写入还要求 `sfence.vma` 才能保证地址翻译可见，不能把公共填充过程结束当成所需维护已经完成。`arch/riscv/mm/init.c` 中的 `vmemmap_populate()` 又委托给公共 `vmemmap_populate_hugepages()`，因此我没有把它仅归为无边界联系的架构内部错误。

### [5] 59f876fb9d68：是，c2a / OTHER

虽然说明里出现从 unsigned long 到 int 的转换，根本缺项是调用 `__ffs()` 前没有排除零。零输入不保证有效结果，ARM 的实际返回值暴露了公共内存初始化的错误假设。我没有把它归入 WIDTH，也没有把其中的 `MAX_ORDER` 误当成页缓存阶数上限 ORD。

### [7] e68b823ab0ba 与 [48] d8a719059b9d：分别不是、是

[7] 的直接问题是两个提交交互后调用了已删除的内部函数，内核无法构建；换用新 helper 时补刷新是保持原语义的配套改动。仅此不足以证明一个独立的跨层运行时缺陷。

[48] 则有独立运行时证据：公共层把“层级折叠”当成“该逻辑层级的大页操作必然不可用”，但 arm64 折叠后仍可在实际顶层装 block 条目，导致 huge-vmap 退化以及线性映射启动崩溃。PowerPC 8xx 的构建桩是同一补丁中的另一项配套工作，不抹去 arm64 的实质问题。

### [8] 8891b176d350 与 [12] 6510c78490c4：分别是、不是

[8] 有明确的对象布局边界：公共 fork 传来的 `init_task` 是静态大小，UML 的架构复制函数却按动态扩展大小读取源对象。[12] 只是 RISC-V 自身保存寄存器数组未初始化，说明与补丁没有显示公共层传入了不符合某项架构假设的对象或状态。不能仅因为函数叫 `copy_thread()` 就把所有架构上下文错误都算作跨层缺陷。

### [10] 56ae10cf628b 与 [24] b3f78e749865：是，c2a / P4

这两条没有止于“封装更好”的抽象理由，我额外核对了修复时的具体实现。

- [10]：`arch/powerpc/include/asm/nohash/32/pte-8xx.h:215` 在 16K 页配置下读取一个子项，再构造四项逻辑 PTE；裸解引用不等价于该读取接口。这里是基本页 PTE 访问语义，因此主类取 P4。
- [24]：`arch/arm/include/asm/pgtable-2level.h` 开头明确描述 Linux 软件 PTE 与硬件 PTE 分区保存；`arch/arm/mm/mmu.c:1800` 的 setter 经 `set_pte_ext()` 安装条目。x86 的 `set_pte_at()` 还执行页表检查。裸赋值没有普遍的完整安装效果。

我没有运行这些路径，也没有声称某个具体发行配置已经由此复现故障。

### [13] 546e42c8c6d9：是，a2c / P4；[14] edf2d546bfd6：不是

[14] 已有的刷新在热补丁内部太晚，架构补丁操作尚未返回就可能调用刚改写的函数。修复把刷新挪到实际写入之后，未显示公共调用者在接口允许的返回后使用时机上有错误假设，我按架构内部算法顺序问题判否。

### [57] e5dec38ac5d0 与 [60] 1690eeb0cb2b：不是
