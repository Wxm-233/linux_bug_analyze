## 结论

1. **提交级模式的“误报低”在留出集上站得住**：48 个正常提交只误判 1 个（2.1%），原因和开发集一样，是可以修的规则问题。
2. **召回受限于覆盖面**：开发集 58% 的对位召回，来自“样本正好是我们检查的类型”。在随机抽取的跨架构依赖缺陷上，92% 的缺陷类型我们还没做成检查，对位召回只有 11%，严格看是 7%。
3. **下一步最值得做的是扩覆盖面**。按留出集里的出现次数排：
   - **TLB/缓存钩子的语义**（P2、P4，约 6 个，多数是 riscv）：公共层以为“TLB 不缓存无效项”“建好映射就能用”，riscv 需要额外的 sfence。可以做成：公共层建立或修改映射后，必须经过 `flush_cache_vmap` 这类钩子；再结合架构横向信息，看哪些架构的钩子为空。
   - **大页页表项的读写方式**（P3，4 个）：hugetlb 的页表项要用 `huge_ptep_get` 等专门函数，公共代码直接用 `ptep_get` 或解引用就报。这是简单的词法规则，而且留出集里我们已经碰巧报到了出问题的那一行。
   - **架构实现那一侧的约定**（P1 的 a2c 方向）：架构对页表接口的实现里 `VM_BUG_ON(!pmd_present())` 这类假设，和公共层会传入的无效项类型对照。
4. **注意**：这批留出集样本一旦用于设计新规则，就变成开发样本了，之后要再取一批新的留出集。
