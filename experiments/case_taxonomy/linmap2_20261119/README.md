## 做法（`linmap2.py`）

只在第一版上加参数传播：
- 函数的第 `i` 个形参（或由它加偏移、做类型转换得到的局部变量）没经过守卫就流到接收者，就给这个函数建立参数摘要；摘要沿调用关系向上传递，最多 3 层；
- 调用处的实参如果是第一版认可的来源，就报出；
- 结构体字段和新的来源种类（栈数组、`dma_alloc_coherent`）都不加，留到后面。

`diag <n>` 给单个样本出断点表：修复改动的函数里每处接收者调用的参数形态（形参、字段、栈数组、全局、调用结果等）；如果是形参，再看摘要是否建立、调用处有几个、实参是什么形态。

## 结论

1. 参数传播这一环本身是通的：25 个里有 13 个建起了参数摘要。但它既没带来新对位，又在当前版本上引入了约 580 条误报。
2. 误报的大头是“同名函数在不同配置下各有一份定义”。不编译时，跨函数摘要会把这些定义混在一起。也就是说，做跨函数分析，就必须知道每个文件在哪些配置下参与编译。这是支持“先编译、再分析”的一条具体证据。
3. 如果保留参数传播，至少要修三处：
   - 同名函数有多份全局定义时，只在所有定义都满足时才建摘要，或者排除 `nommu.c` 这类按配置互斥的文件；
   - 局部名字遮蔽全局符号时不算镜像符号；
   - 路径条件（与标志相关的分支）。
4. 25 个样本的断点显示，下一步收益最大的是把 DMA 一致性内存作来源、做字段传播，或扩充镜像符号写法。参数传播不是主要的缺口。
