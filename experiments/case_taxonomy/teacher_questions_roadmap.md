# 两个研究问题的状态与验证路线（2026-09-26）

## 2026-10-12 方向调整

老师进一步要求每项Pattern解释架构差异、公共传播和A/B暴露原因。当前执行以[跨架构契约研究规划](cross_arch_contract_plan_20261012.md)为准：先重审原八项，优先die与shmem架构配对，再补生命周期/表示证据；局部模板与通用解析暂作技术支持。此前路线保留作历史参考，自动提取和权威裁定仍未全部解决。

老师提出的两个问题是：①怎样自动化提取应该添加的检查；②不同架构对同一接口的理解不一致时，以什么为准。**目前均未完全解决。** 八项接口证据矩阵已经人工给出适用条件、权威来源候选、消费者和正常反例；两条冻结蕴含式可对人工输入事实做确定性分类。但判定程序并不从未知源码发现接口边界或权威契约，cluster/文件 THP 的近邻试验也不能证明跨独立根因泛化。现阶段应把“提取候选事实”“裁定契约”“执行检查”作为三个可分别验收的步骤。

## 1. 从修复案例到候选检查

| 阶段 | 要得到的具体产物 | 通过与停止条件 |
|---|---|
| 确定接口边界 | 给定 Git 版本、架构、配置、入口与消费者，记录对外属性、选择点或首次读取点；按提交/独立因果链计数。 | 不能只凭关键词或修改目录；找不到消费路径时标 `insufficient`。 |
| 提取事实 | 自动从目标版本源码定位属性定义与注册、提供者声明及 fallback、预处理/Kconfig 守卫；输出每个事实的文件行号、推导路径和未知原因。后续再扩展到表示上限、状态时序。 | 先做 die/cluster topology sysfs 的**受限提取器**，保留 PPIN 运行时能力作边界对照；不能把缺失的宏误当作已证实的设备无能力，也不能把 fallback 当原生提供者。 |
| 确定契约候选 | 组合适用条件 A、权威来源 P、消费者 C、期望关系以及正常/不适用对照，保留来源类型与适用版本。 | 从代码关系只能提出候选；无文档、ABI 或消费者证据支持时不自动把它提升为通用规范。 |
| 检查与验证 | 旧版、完整修复、不完整修复、正常配置至少形成有意义的对照；分别记录源码检查、函数编译运行、历史内核启动与硬件证据。 | 规则输出 `hit/normal/not_applicable/insufficient`；配置网格不是独立缺陷数量。真实运行未完成时只报告静态或函数级结论。 |

本轮先实现 topology 家族的受限事实提取与已读样本校核。这一步若成功，解决的是**减少部分手工查源码**，不是自动判断未知缺陷。随后在新样本前冻结脚本、参数、预期、选样池文件及 SHA-256；保存首次标注和每次修订、人工时间。跨独立根因的验证要在不同接口/子系统进行，不能继续用同一 topology/sysfs 系列估计泛化。最终按**独立提交/因果链**报告人工事实一致性、拒判、误报和复核成本；样本量不足时不报总体精确率、召回率或提速比例。

## 2. 不同架构理解冲突时的裁定

不按多数架构实现投票，也不把补丁修改侧当作正确侧。先为**同一个接口、版本、配置和模式**建立证据卡：接口用途与适用边界、适用的磁盘格式/ABI/架构或硬件规范、消费者实际需要的输入范围和状态、各架构原生提供者及运行时能力、正常反例、冲突点。若已有适用的显式规范，就核对实现是否遵守；若文档缺失，则从消费者的可表示范围、首次读取时点和现有实现推导**暂定契约**，不能称已经裁定的规范。若架构差异是接口允许的能力差异，应把契约写成带条件的多分支，而非要求所有架构实现同一行为。规范与实测或不同版本约定冲突时保留两边证据，标 `insufficient/待领域裁定`，请领域人员确认后才生成强制规则。

每张证据卡至少标出 `authority_kind`（规范、格式、ABI、消费者约束或实现声明）、`authority_source`（可定位的位置）、`version/config/path`、`consumer`、`status`（有明确依据/暂定/冲突）和未解决理由。前两类事实可以用程序抽取；`status` 的提升须有适用的规范或领域复核，不由模型投票或提交标题决定。这也让检查器区分“源码关系正确推导”与“接口约定已经确定”。

例如 Btrfs 选项解析应使用磁盘 superblock 中真实扇区几何；普通文件 PMD 页选择受该版本 xarray 页缓存上限约束；历史 die/cluster sysfs 的两项原生宏是导出的源码门控依据，但只证明静态声明存在，不证明每台机器的拓扑值有效。PPIN 则依赖运行时单值，不能套双宏规则。VT-d 一级与二级页表对 WO 的表达能力、ACPI 规范与兼容策略、NUMA native/compat 接口边界，均需按模式或 ABI 分开裁定，不能从一个架构或修复补丁直接推向所有架构。

## 接下来可验收的工作

1. 受限提取器对已读 die/cluster 的旧版、修复版和正常/不适用配置输出带源码位置的事实，与人工矩阵逐字段对照；未知预处理条件和 PPIN 应拒判。
2. 用独立保存的选样快照选择不同子系统或独立根因，冻结后再阅读补丁并核查事实、真实适用条件和误报；需要人工确认权威来源的环节单列计时。
3. 将每个候选检查和权威裁定状态写回案例台账，再决定是否值得生成系统层前置断言、构建检查或跨配置回归测试。C1–C4 的五维分类及发现时间缺失仍并行保留，不以本路线替代。
