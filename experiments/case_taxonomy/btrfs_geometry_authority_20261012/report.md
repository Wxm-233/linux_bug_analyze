# Btrfs：从磁盘几何定义到消费前缓存检查

2026-10-12。接续[10/11局部字段链](../btrfs_first_consumer_20261011/report.md)，本轮补同版定义并进行有限字节/对象模型对照，回答检查应根据什么值、在哪里启用。不是新缺陷选样、真实内核或挂载验证。

## 新补齐的依据

父版`0d977e0eba234e01a60bdde27314dc21374201b3`与修复版`6f93e834fa7c5faa0372e46828b4b2a966ac61d7`的`ctree.h`相同，generic unaligned头也相同。共保存两个不同头文件，135319字节；批读取两版共270638字节。一个旧helper路径不存在，已记录取源脚本首次退出和已成功保存的generic原物；没有抹去失败或重复读取成功原物。

| 链上事实 | 同版源码依据 | 能说明什么 |
| --- | --- | --- |
| 磁盘扇区字段为`__le32` | ctree.h:245 | 该字段声明使用小端32位表示。 |
| 内存缓存为`u32` | ctree.h:984 | 缓存是CPU侧数值；完整typedef/布局编译未执行。 |
| `super_sectorsize`实例指向磁盘字段，位宽32 | ctree.h:2401–2402 | getter与字段匹配，而非按同名猜来源。 |
| STACK生成宏调用显式LE读取助手 | ctree.h:1623–1631 | 可见生成式是`get_unaligned_le32(&s->sectorsize)`。 |
| generic helper进行packed加载及`le32_to_cpu` | asm-generic/unaligned.h:12–15、30–33 | 一个同版参考实现含显式LE→CPU转换；不是直接字节移位实现。 |
| `btrfs_sb()`取回`s_fs_info` | ctree.h:1035–1038 | 取回当前superblock保存的指针。 |
| setter在`set_anon_super`成功时存入data | 既有super.c:1549–1554 | 存入是有条件的，不能机械认定所有路径都绑定同一对象。 |

`ctree.h`实际包含的是`<asm/unaligned.h>`；本轮没有解析具体架构的include/config，也没有追读`asm/byteorder.h`及`le32_to_cpu`底层。因此generic仅是参考定义，Python解码模型依据声明的LE语义，并非自动执行或认证真实架构上的C实现。

已有挂载路径显示分配/初始化、将fs_info交给sget、新superblock分支进入fill_super/open_ctree；复用旧superblock时新分配对象会释放。外部sget行为、完整别名/生命周期与CFG仍未知。不能把“setter与getter访问同一成员”升级成整条挂载路径的对象身份证明。

## 从定义生成的检查候选

本轮入口从10/11保存的字段候选出发，自动关联getter宏实例、所指磁盘字段、缓存字段类型和generic helper可见转换；字段/getter不由验收预期提供。两版均派生`conditional_template`，生成的属性为`cache_field == decode_le32(wire_field_bytes)`；对象取回与成功条件下的存入也被分别定位，但没有自动把对象链标成已成立。

首次运行退出码0，两版的定义关联符合事前预期。**同一组八项手工模型输入分别送入两版模板，共16次求值**；两版的格式定义相同，因此模型结果也相同。这不是自动重建旧/修复版实际缓存轨迹，更不能把修复模板输入的人为陈旧缓存误读成“修复版仍有错误”。

| 唯一模型输入 | 模型输出 | 本次裁剪是否不同 |
| --- | --- | --- |
| 真实4K、缓存4K、请求8192 | 缓存一致，裁剪4096 | 否 |
| 真实64K、缓存仍4K、请求8192 | 缓存失配，4096对8192 | 是 |
| 真实64K、缓存64K、请求8192 | 缓存一致，裁剪8192 | 否 |
| 真实64K、缓存仍4K、请求2048 | 缓存失配，两边均2048 | 否：小输入掩盖差异 |
| 零选项、未消费 | `not_consumed`，数值结论null | 不评价 |
| 准备失败、未消费 | `not_consumed`，数值结论null | 不评价 |
| 字段字节长度不足 | `insufficient` | 不评价 |
| 对象联系未证 | `insufficient` | 不评价 |

每版四项进入数值模型：两项一致、两项失配；两项未消费、两项不足另列。八项输出均符合预期，**不表示八项模型都通过**。缓存失配中的一项产生当次裁剪差异，另一项输出相同，说明缓存契约与当前输入的可见表现需要分开。64K情形假定受支持页/扇区配置和其余前置条件成立，验证函数及页面配置本轮未实际运行。

程序只执行新的Python入口一次，复用既有候选而未重跑旧提取器；源码审阅一次，未编译C、执行内核或挂载。真实路径、有效几何和对象联系三个模型标志由手工给定，不能从这些输入反推自动证明了路径。原始输出见`first_stdout.txt`/`first_stderr.txt`，机器结果见[results.json](results.json)，生成模板见[contract_template.json](contract_template.json)。

候选条件为：在确实到达正max_inline裁剪、适用几何已通过前置校验、对象联系成立且没有未建模改写时，缓存数值应等于本次磁盘字段的LE32解释。它是有条件的模型模板，不是可直接插入内核的已认证断言。

磁盘字段为LE32不等于需要再给缓存加一次端序转换；getter返回CPU数值后，消费端需要检查是否及时更新。也不能把4096一律判错：真实4K扇区时它恰好正确。这说明P2的数据表示依据与P3的消费时机检查需要衔接，但本例主要问题仍是P3，并关联P1的裁剪上限。
