# 候选覆盖率度量：结构对应与接口使用者（判据，计数前写定，2026-10-29）

按用户“量候选覆盖率”实施。不调用模型；只统计候选集是否包含目标，不判定也不排序优劣。

## 背景与数据

- P1′中B3（其他架构同一相对路径＋同名函数＋标识符重叠）召回@20为26/50。事后统计（刚补算、尚未记入笔记）：50对中19对的目标与S改动函数同名，而B3漏掉的24对中只有1对是同名目标。剩下的漏检看起来多是“不同文件、不同名，但使用了同一个通用接口或同一种用法”。
- **数据为P1′的50对，即开发集**。这些对已用于P1′的失败分析，研究者读过前20对，本度量只作开发报告，不计为检验，结果也不能用来宣称方法有效。

## 候选范围

同P1′：S没改过的`arch/<Y>/`下`.c/.h`文件中的顶层函数（`score_p1prime.universe`）。

## 两种候选来源

- **B3（结构对应）**：规则同`score_p1prime.b3`，但不截断，得到完整排序，报告前20、前40与全部候选池。前20应复现P1′的26/50；不一致时如实报告。
- **API（接口使用者）**：
  1. 取S增删行中的标识符（长度≥4、非C关键字，同`score_p1.idents`）；
  2. 保留在快照S中满足以下两条的标识符，称为“通用接口标识符”：至少在一个`arch/`之外的`.c/.h`文件中出现；全树出现文件数不超过500（排除过于常见的名字）；
  3. 候选为候选范围内函数体含有至少一个通用接口标识符的函数；
  4. 排序依次按：含有的通用接口标识符个数降序 → 所含标识符中最小的出现文件数升序（越稀有越前）→ 路径 → 行号。

  报告前20、前40与全部候选池。

## 指标

- 每种候选集是否包含该对的任一目标（覆盖），报告覆盖对数：
  - B3@20、B3@40、B3全部；
  - API@20、API@40、API全部；
  - 两个前20的并集（≤40个候选）；
  - 两个全部候选池的并集。
- 候选池大小（中位数、最大值），这决定逐项判定的成本。
- 在B3@20漏掉的对上，API@20、API@40能补回多少。

## 事先写定的解读规则（描述性，用于决定是否值得做M6）

- 两个前20的并集覆盖 ≥ 35/50（70%）：“结构＋接口使用者”生成约40个候选是可行的候选来源，值得在开发集上试M6的逐项判定。
- API@20在B3@20漏掉的对上补回 < 5对：接口使用关系对这批样本帮助有限。
- 两个全部候选池的并集仍覆盖不到的对，按“候选生成无法触及”报告，作为方法上限的说明。

## 输出

`coverage.json`：汇总计数与每对的覆盖标记（只含编号与布尔值、池大小），不打印目标或代码。
