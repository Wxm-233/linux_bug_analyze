# 在跨架构缺陷测试集上评估检测方法

## 这一轮要回答什么

用跨架构缺陷样本集的**测试集**，评估此前提出的四种机械检测方法：在RISC-V修复之前，它们能不能标出出问题的函数；对不是跨架构缺陷的修复，又会标出多少。按判据，每种方法在测试集上只运行一次。

| `criteria.md` | 判据，运行前写定 | `3596ba02…` |
| `run_methods.py` → `results.json`、`results_partial.jsonl`、`run.log` | 在每条修复的前一版上运行四种方法 | `a7bd2c12…` → `56f7e54c…` |

| `run_attempt1.log`、`停点.md` | 第一次运行在80条处按用户要求暂停的记录 | — |

标签用`cross_arch_sample_set_20261102/labels_v2_1.json`（`cc863e18…`）。不调用模型，不构建内核。

**运行情况**：第一次运行在428条中跑到80条时按用户要求暂停。当时程序只在全部结束后才写结果，所以这80条没有保存、也没人看过。之后把程序改为每条完成即保存、可续跑（判定规则未改），从头完整跑完一次：428条，0条出错。

## 四种方法

| 代号 | 方法 | 标出条件 |
| --- | --- | --- |
| F1 | 同名修复跟随 | arm64、x86、LoongArch中**同名函数**被带`Fixes:`的提交改过（不改RISC-V），之后RISC-V的同名函数没改过 |
| F2 | 公共改动牵连跟随 | 同时改公共代码和其他架构**同名函数**的提交（不改RISC-V），之后RISC-V的同名函数没改过 |
| R2 | 表项状态—大小检查 | 修复改动的函数中有M2规则的标记 |
| R5 | 关中断后睡眠检查 | 修复改动的函数中有M5规则的标记 |

## 结果

测试集正例（跨架构、非构建错误）102条，其中修复改动了RISC-V `.c`/`.h`函数的“可适用”正例45条；对照（非跨架构、非构建错误）286条，可适用93条。

| F1 | 4/102 | 4/45（8.9%） | 5/93（5.4%） | 0.47 | 无 |
| F2 | 6/102 | 6/45（13.3%） | 3/93（3.2%） | 0.058 | 无（比例差4倍，但p≥0.05） |

- **提前量**：F1命中中位数约3个月（6–413天）；F2中位数约4个月（23–1049天）。
- **命中的7条正例**：M8 3条、M7 2条、M5 1条、M9 1条（A039、A076、A086、A192、A195、A211、A278），其中5条集中在BPF trampoline相关函数。
- **未标出的95条正例**：57条不可适用（22条改的是RISC-V头文件中的宏或函数外内容，22条问题在公共代码或驱动、不在`arch/riscv/`，13条是汇编、Kconfig或Makefile）；38条可适用但未标出。
- **按参考线，四种方法在测试集上都没有对跨架构缺陷的区分力。**

## 事后分析（看到结果之后才做的，只作描述）

1. **命中多半是“热门函数”带来的巧合。** 逐条看命中所依据的参照提交：
   - 只有A039的参照提交（`2cd3e3772e41`，x86/cfi的BPF改动）正是引发该缺陷的公共改动；
   - A086、A211的参照属于同一函数的相关改动；
   - 其余（A076、A192、A195、A278）的参照与缺陷无关。
   - 对照中被标出的7条也是这类情况（BPF JIT、KVM vCPU、kgdb等函数在其他架构上经常改动）。

   也就是说，“同名函数近期被别的架构改过”主要反映函数改动频繁，不反映缺陷机制。
2. **“别的架构早已改好”的正例几乎都没抓到。** 测试集中掩盖方式为4的正例8条，只标出1条（A039）。A155、A202可适用却漏掉：参照修复在**名字不同**的函数里（arm64的`reserve_memblock_reserved_regions`对应RISC-V的`init_resources`；x86 unwinder对应RISC-V的`walk_stackframe`）。其余5条改的是汇编、头文件或公共代码。按名字对应是主要瓶颈。
3. **两条规则检查在测试集上没有用武之地**：测试集中没有M2正例，M5正例的写法（如在原子上下文中取`mmap`锁、`die()`用会睡眠的锁）超出了R5规则所列的调用。
4. **一半以上的正例不在RISC-V的C函数里**（57/102）。只看RISC-V函数的方法，覆盖面从一开始就被限制在45条以内。

## 结论

- 在独立的测试集上，**已有的四种机械方法都不能有效检测跨架构缺陷**：最好的F2在可适用正例中标出13%，与对照的差别不显著；四种合计只覆盖102条中的7条。
- 这与此前的发现一致，并且更明确了原因：
  - **按名字跟随**抓到的多是改动频繁的函数，而真正的参照修复常在名字不同的函数里；
  - **单一规则**只覆盖极少写法；
  - **一半以上的跨架构缺陷**在头文件宏、汇编、配置或公共代码中，函数级方法看不到。
- 对下一步的含义：
  - 机制要指导检测，需要按“**约定和条件**”而不是按名字把RISC-V与参照对象对应起来（例如约定级列点）；
  - 检测对象要覆盖头文件、汇编和配置。

  这两点都难以纯机械完成，可考虑让模型负责“找对应位置”这一步，再由规则或人核对；调用模型须另行征得同意。
