## 一、要回答的问题

师兄方向文档的第二阶段是“同一种子在多个架构的内核上运行，比较结果”。前三轮静态分析都卡在同一处：静态信息分不清“riscv 真的缺了必需的行为”和“对方架构特有、riscv 不需要”。这一轮搭一个最小的差分测试原型，回答：

1. 三个架构的内核在 QEMU 中运行同一组测试程序，结果能否稳定复现、能否比较？
2. 对一个从用户态可观察的已知跨架构缺陷（B467），修复前的 riscv 内核与修复后的 riscv、当前版本的 arm64 和 x86_64 相比，能否看出差异？修复后差异是否消失？
3. 当前版本上出现多少差异？其中多少是运行环境或架构能力造成的，多少像语义失配？

## 二、范围与安全边界

- **内核**：
  - 当前版本 v7.3-rc2 的 riscv、arm64、x86_64 defconfig 构建（`/root/work/boundary_build/<arch>_defconfig`，已有可启动镜像）；
  - B467 修复提交 `c625154993d0` 的父版本和修复版本，各做一次完整的 riscv defconfig 构建（`LLVM=1`）。
- **运行环境**：WSL 中已装的 QEMU 8.2（系统模式）、OpenSBI 1.7，TCG 软件模拟，单核，512 MB 内存，串口控制台。不安装任何软件。
- **测试程序**：同一份 C 源码，用各架构的交叉编译器静态编译，作为 initramfs 中的 `/init` 运行，跑完关机。
  - 只调用公开的系统调用，参数是普通、合法或明确不支持的取值，用来观察返回值和错误码；
  - 不做任何破坏内存、提权、绕过防护的尝试；也不在宿主机上运行这些内核。
- **第一版测试集**：
  - `perf_event_open`：类型取 HARDWARE、SOFTWARE、HW_CACHE、RAW、BREAKPOINT 以及一个不存在的类型，每种类型配若干支持和不支持的 config，记录成功或错误码。成功时立即关闭；
  - 对照组：`getpid` 是否成功、`uname` 的 `sysname` 字段、一个不存在的系统调用号（`syscall(-1)`）的错误码，用来检查测试框架本身。

## 三、定义

- **一次运行**：启动一个内核、运行全部测试、关机。输出中位于 `@@DT BEGIN` 与 `@@DT END` 之间的每一行是一条 JSON 结果，键为测试名和参数，值为结果（成功，或错误码名称）。
- **稳定**：同一内核重复运行 3 次，规整后的结果完全相同。
- **规整**：只保留“成功或错误码名称”，不比较返回的文件描述符数值、地址、时间。
- **差异**：同一测试键，在两个内核上的结果不同。
- **差异分类**（人工，逐条写理由）：
  - **环境**：由 QEMU 模拟能力造成，例如 x86_64 在 TCG 下没有模拟 PMU；
  - **能力**：架构本身就没有这一功能，例如某架构不支持硬件断点；
  - **疑似失配**：同一种“不支持”或“不合法”的情况，各架构给出的语义不同，例如错误码不一致，而公共代码依赖这个错误码；
  - **判断不了**。

## 四、参考线

- 每个内核 3 次运行必须稳定；不稳定的测试键单独列出，不参与比较。
- **B467 检出**：同时满足下面两条，记为“原型能看出该缺陷”：
  - 至少一个测试键，修复前 riscv 的结果与修复后 riscv 不同；
  - 在这些测试键上，修复后 riscv 与 arm64 一致。
- 当前版本的全部差异逐条分类，报告各类数量，不设阈值。
