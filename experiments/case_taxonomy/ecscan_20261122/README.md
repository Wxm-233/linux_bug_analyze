## 四、发现的新线索：mips32 XPA 的 `pfn_pte`

这是本轮唯一一处代码层面的新发现，盲审后判**平台不可达**，不报。

- `arch/mips/include/asm/pgtable-32.h:156-167`（XPA 分支）：`pte_high = pfn << PFN_PTE_SHIFT`（32 位），`pte_low = pfn >> _PAGE_PRESENT_SHIFT`（24）。`PFN_PTE_SHIFT = PAGE_SHIFT - 12 + _CACHE_SHIFT(5) + 3`，4K 页时为 8，`pte_high` 正好容下页帧号低 24 位、与 `pte_low` 无缝衔接。
- 但 `CPU_MIPS32_R5_XPA` 在 Kconfig 里 `depends on !PAGE_SIZE_4KB`（`arch/mips/Kconfig:1775`）。16K 页时 `PFN_PTE_SHIFT = 10`，`pte_high` 只容 22 位，**第 22、23 位（物理 64GB～256GB）两边都不存**；64K 页时第 20～23 位全丢。也就是 XPA 允许的页大小下，这段拆分都不连续；`MAX_POSSIBLE_PHYSMEM_BITS` 写的是 40。
- 引擎在 4 个保护常量下都给出截断，clang 对输入 2^22 折叠读回 0（36 条全部复现）。第一轮只在 `PAGE_KERNEL_NC` 下出现，是因为当时“其他”参加表决、其他保护常量形不成规律；第一轮 README 猜测的“缓存属性位与页帧号字段重叠”不对，已在该 README 追加更正。
- 可达性：树内能选 MIPS32 R5/XPA 的只有 `MIPS_MALTA` 和 `MIPS_GENERIC_KERNEL`（`arch/mips/Kconfig:167、589`），都没有 64GB 以上内存。Codex 独立得出同样的空档（“低段 22 位、高段从第 24 位接续，中间确有缺口”）和同样的不可达结论。

## 五、局限

- 映射族的多数表决仍然把三类“合理差异”报成偏离：**配置差异**（只有 4 个构建开了 THP、只有 s390 开了 MEM_SOFT_DIRTY）、**组合里缺调用方总会加的一步**（`pfn_pmd` 后不加 `pmd_mkhuge`）、**折叠层级/硬件限制**（i386 的 PUD）。34 行里约 30 行属于这三类。下一步可以自动识别：按构建配置把依赖未开配置的接口标为“不适用”；对 PMD/PUD 级只组合 `pfn_T → T_mkhuge → …`；跳过折叠层级。
- 求值只覆盖头文件；可达性（平台物理内存范围）仍要人判断。
- 只支持一个版本；多版本要先为其他版本生成头文件变体。
