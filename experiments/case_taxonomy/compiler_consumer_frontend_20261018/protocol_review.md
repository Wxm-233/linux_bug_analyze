# N2.11 编译器前端探查协议预审（2026-10-18）

本次仅读本阶段 `protocol_pre.json`，尚无命令计划或编译结果。协议把已知父版的完整 `core.i`、同版 `.config`、旧保存的 `.core.o.cmd` 绑定到一次生成汇编和 GCC dump 的探查；不改 N2.10 冻结方法，不构成内核运行或自动契约证明。该方向适合检查普通 C 解析器无法处理的真实配置源码是否能由原目标 GCC 表示。

执行前计划须逐项可审：

1. 验证两个既存 manifest 自身摘要、revision/profile、`core.i` 与 `.config` 的精确 SHA；原 `.core.o.cmd` 须指向同版 `kernel/sched/core.c` 且只有一个输入。以参数数组解析命令，不执行 Makefile 文本或 shell 展开。若发现响应文件、环境赋值、命令替换、多命令或无法解释的原参数，停止该 profile。
2. 列出原 argv 与新 argv 的逐项差异：仅目标编译器绝对路径、`.c`→已登记 `.i`、`-c`→`-S`、新输出/依赖参数及 `-x cpp-output` 改动。原目标、ABI、配置、优化、调试和影响 GIMPLE 的语义参数保持；未知输出参数或预处理附带输出不能默许写回旧 build。`-x cpp-output` 必须作用于精确 `.i` 输入，不能再包含宏预处理或手改源码。
3. 解析所有 `-o`、依赖文件、dump、临时文件可能去向；新路径须为已解析的 stage `raw/<profile>` 子路径。运行前检查目标输出不存在，运行后列出实际新文件并复查旧 `.i`、`.config` 摘要。只有一次目标编译器调用，超时/失败保留 stderr 与停点，不用改旗标重试。
4. 旧 s390 的编译成功应至少要求退出码 0、汇编/dump 文件可定位且身份与本次 argv 相符；若目标函数在 dump 中无法唯一完整提取，应报告“编译可行、函数提取不足”，不能把任意片段写作消费者证据。old_x86 的启动条件应在计划中明确，避免把仅退出码 0 升格成可审的前端材料。

任何 GIMPLE 分支、读写或源坐标只是该 GCC/该配置/该优化级别的编译器表示；它可能经过降级和优化，仍需与原源码、配置及语义要求复核。两个 profile 既有样本不能算独立新案例，函数抽取成功也不能解决 N2.10 别名门槛或证明首次消费期限。
