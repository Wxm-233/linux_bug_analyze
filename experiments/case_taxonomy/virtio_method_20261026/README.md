# virtio DMA布局与缓存隔离判定方法

2026-10-26。已读开发案例95c7b0ad6c69d1c0608ff0bbd358a546856beaf3，父版db191ba0c8564ff84877e5b1c9553e991feca239。本轮在WSL重新编译并执行16组布局探针，未运行内核或DMA设备，没有项目模型调用。独立正例/正常样本仍0/0。

## 消费用途与依据

virtio_input通过sg_init_one(evtbuf,sizeof(*evtbuf))及virtqueue_add_inbuf提交单个事件供设备写入。结构内evts邻接CPU可写字段。固定版本Documentation/core-api/dma-api-howto.rst解释DMA不一致缓存上共享维护单元可能覆盖数据，并说明DMA分组首尾标注保护两侧；修复给evts添加begin/end标注。规范依据与源码身份在source_audit.json中登记，不以测试断言或多数架构行为充当依据。

提供给设备的是单个8字节事件，测试检查的是整个数组与外部CPU字段之间的边界；不能误写成整数组一次DMA映射。数组内部多个事件的所有权与维护交互未由该布局测试证明。

## 条件、提供者保证与目标关系

窄布局命题的前提是：已知目标ABI、字段偏移、对象实际基址B和有效维护单元大小L。将数组记为[B+b,B+e)，最近前方CPU字段末端为B+p，后方CPU字段起点为B+n。两侧不共享单元分别要求：

- floor((B+p-1)/L) != floor((B+b)/L)。
- floor((B+e-1)/L) != floor((B+n)/L)。

这是按有序非空区间的边界字节判断，前提不是仅有“数组首地址对齐”。实际风险关系还要求设备真实写目标、CPU可写对象、DMA不一致性、维护路径、成功映射及相应所有权时段成立。布局共享提供候选，不能自动推出真实损坏。

对象由分配器提供，字段相对位置由ABI和类型决定，缓存维护由平台/DMA后端决定。ARCH_DMA_MINALIGN、运行时维护粒度、实际分配基址不是同一个事实，必须分别绑定。若实际DMA落在bounce缓冲区，原结构布局不直接描述设备写目标；回拷和所有权需另查。coherent模式可能不触发该不一致缓存机制，但不能因此证明所有DMA路径正确。

## 实验及对照

原virtio_dma_layout_probe.py未改。四种实现为旧版、只保留尾标注变体、只保留首标注变体、修复版；事件数64/63，假设粒度64/128，总计16组。63事件是构造输入，不是历史驱动配置或独立案例。spinlock等类型用替身，主机编译器产生布局；不是ARM64完整内核ABI认证。对齐宏在每组通过编译参数明确开启，未覆盖无ARCH_DMA_MINALIGN分支。

run.py保存实际编译C、编译参数/环境、原始偏移stdout和源文本。16组结果与历史JSON逐字段一致。重新取得的5份布局源码与归档全文/Git blob一致；固定版本DMA文档及事件提交语句也核Git blob和引文位置。audit.py从原始偏移单独计算边界关系，不使用旧结果布尔值作答案，随后才核对旧输出；关系本身仍由研究者登记。

| 实现 | 64事件、64/128粒度 | 63事件、64/128粒度 |
| --- | --- | --- |
| 旧版 | 首尾均共享 | 首尾均共享 |
| 仅尾标注 | 首共享、尾隔离 | 首共享、尾隔离 |
| 仅首标注 | 首尾均隔离 | 首隔离、尾共享 |
| 修复版 | 首尾均隔离 | 首尾均隔离 |

64×8字节恰好是所测粒度的整数倍，遮蔽了仅首标注的尾端问题；63×8字节改变这一关系。由此可复用的对照设计是选择长度跨越整粒度边界，程序应计算实际区间而非只搜索标注。此处是已读开发材料复核，未证明自动选配的前瞻收益。

额外对四个修复布局枚举B mod L的384种合成余数，确认相对偏移结论依赖基址条件。B mod L=0均成立；某些非零余数失效。这是反事实假设敏感性检查，失配基址可能违反C对象对齐要求，绝不是合法分配实例、正常对照或新Linux缺陷，不据此质疑已知修复。本轮未测真实分配地址。

## 自动检查流程与边界

1. 绑定版本、实际ABI/宏、字段区间、基址和维护粒度；未知保留不足。
2. 追踪event→SG→virtqueue→实际映射目标，登记方向、DMA API/后端和bounce等条件。
3. 在范围成立时分别判首/尾隔离，不能以标注存在、头部对齐或分配总大小代替。
4. 核CPU写入对象和设备所有权时段；只有布局而无执行链，不判真实损坏或完整安全。
5. 选择有区分力的长度/粒度边界；合成配置、功能绕过和合法正常对照分开统计。

程序本轮完成源码身份、布局编译、偏移提取、有限算术与结果核验；用途、规范、后端范围和所有权解释仍依赖人工。relation_audit.json对actual_base、actual_dma_target、ownership_interval及whole_path全部保留insufficient。无模型自动要求提取，无新增统一入口。

## 与其他接口的共性和不同

CPU拓扑需要对象资格、集合覆盖及阶段；Btrfs需要权威几何与消费裁剪；SMMU需要覆盖、编码及层级条件；virtio增加空间隔离、真实DMA目标和所有权时段的联合要求。可共享的是证据身份、条件关系和缺证处理，具体适配仍需字段布局、DMA后端及对象/时段追踪。不能把四类脚本放在一个入口就称通用自动分析。
