# RISC-V machine_shutdown 关中断后调用会睡眠的函数：运行验证

## 结论

**疑点成立：违反了约定，但这次运行没有造成可见后果。**

在终点版本`df2908090cda`的RISC-V内核上做kexec重启：
- `machine_shutdown()`先关中断，再调用`smp_shutdown_nonboot_cpus()`；
- 这个调用期间，当前任务**睡眠了16次**；
- 调用返回时**中断已被重新打开**。

所以函数注释说的“此后本hart不再有中断”实际上没有成立，而“关中断时不能睡眠”这条通用约定被违反了。第二个内核正常起来，日志中没有lockdep报告、WARNING或BUG。

这条疑点**不是人读代码找到的**：它是上一轮混合样本实验中，模型（只用模型、规则加模型两种做法都是）在一个“两年多未改动、按标签算无bug”的函数上标出来的，属于机制目录中的M5（执行上下文）。只记录，不对外报告；上游是否已有报告尚未查重。

## 方案

方案与判定标准见`plan.md`（运行前写定，SHA `a620d055…`），运行中没有修改。

**为什么不能只靠调试选项**：kexec调用`machine_shutdown()`时，系统已处于重启状态，`__might_resched()`在这个阶段直接返回，所以`CONFIG_DEBUG_ATOMIC_SLEEP`不会报警。因此改用只加打印的观测内核。

| 内核 | 改动 | Image SHA |
| --- | --- | --- |
| 观测内核 | `observe.patch`：只在调用前后打印`irqs_disabled()`和上下文切换次数，不改变行为 | `56215c14…` |
| 对照内核 | `control.patch`：同样的打印，再把`local_irq_disable()`移到调用之后 | `449f2fe6…` |

两者都由`git archive df2908090cda`解出，配置为`defconfig`，再开启`KEXEC_FILE`、`HOTPLUG_CPU`、`PROVE_LOCKING`、`DEBUG_ATOMIC_SLEEP`，构建后已核对`.config`。补丁由`make_patches.py`生成。

**运行**：QEMU 8.2 `virt`机型，4个hart。测试程序`kexec_test.c`作为`/init`：用`kexec_file_load`装入同一个内核，再kexec重启；第二个内核看到命令行标记后打印信息并关机。每个内核运行一次。

## 结果

| 观测项 | 观测内核（原样行为） | 对照内核（调用后才关中断） |
| --- | --- | --- |
| O2 调用前`irqs_disabled()` | **1**（中断已关） | 0 |
| O1 调用期间上下文切换次数 | **16** | 13 |
| O2 调用后`irqs_disabled()` | **0**（中断被重新打开） | 0；随后关中断，变为1 |
| O3 lockdep、WARNING、BUG | 0 | 0 |
| O4 第二个内核 | 正常起来 | 正常起来 |

原始输出在`logs/observe.log`和`logs/control.log`。

按事先标准：观测内核调用前中断已关，并且调用期间睡眠过；对照内核调用期间中断开着，第二个内核正常。**疑点成立。**

## 影响与边界

- **已确认**：
  - 关中断期间睡眠（16次）；
  - 函数返回时中断是开着的，和函数的意图相反。原因是睡眠时调度器重新打开了中断。
- **没有看到可见后果**：这次运行没有警告，也没有失败。原因之一是kexec阶段调度器跳过了这类检查。
- **可能的风险**（推测，未验证）：
  - 在这个窗口里，本hart会响应中断，而函数本意是此后不再响应；
  - 在其他配置、负载或真实硬件上，是否会出问题没有验证。
- **对照补丁**只用于确认原因，不是经过审查的修复。arm64的做法是根本不在这里关中断。
- 只在QEMU上运行过。

## 对研究的意义

- 这是**模型在机制目录指导下标出、再经运行确认**的第一个问题。它说明“机制目录加模型”能在规则覆盖不到的地方，找出真实的跨架构不一致：arm64不关中断，RISC-V关了。
- 它也说明了一种“被掩盖”的方式：违反约定的后果被重启阶段的检查豁免，以及调度器自动重开中断掩盖了，所以四年多来没有暴露。
- 但这只是一个例子。上一轮模型判有bug的36个样本中，有一半是错的，所以模型的标记仍然必须逐条验证。
