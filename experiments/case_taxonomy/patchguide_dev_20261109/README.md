# 补丁引导＋对照，开发轮（patchguide_dev_20261109）

## 这一轮要回答什么

用户 2026-11-09 提出：从其他架构的补丁出发，去发现 riscv 上的同类缺陷，这样或许能更好地定位。做法是：

- x86、arm64 修复某个问题时，往往补上一个调用、一次字段写入或一个错误码，我把这些叫作“补丁元素”；
- 去 riscv 对应的实现里找这个元素，找不到就报，并附上对方的修复提交作为证据。

例子：arm64 提交 `49c87f767774`（“arm64: hugetlb: Fix huge_ptep_get_and_clear() for non-present ptes”）在 `get_clear_contig` 里新增了 `pte_present` 判断。在 riscv 修复同一问题（A143）之前，我的工具就能指出：riscv 的 `get_clear_contig` 里没有 `pte_present`。

这一轮是**开发轮**（判据第〇节）：
- 现有样本作开发集，规则可以迭代，每次改动都记进 `iterations.md`；
- 数字只说明在开发集上调到了什么程度，不作为对外结论；
- 对外结论留给 LoongArch 留出集，规则冻结后只跑一次。

## 我做了什么

1. **开发集**：E1 中 M8（落后于参照的演进）、M10（同一约定、各自实现）的样本，加上检查二的 24 条，共 42 条。其中 18 条补建了修复前的 riscv 事实（`build_dev.py`，每条部分构建约 3–4 分钟）。修复只在汇编或宏里的 5 条扣除，评估 37 条。
2. **挖对照补丁**（`mine_patches.py`）：x86、arm64 自 2019-01-01 起带 `Fixes:` 的提交 7294 个。逐个改动块取出所在函数，抽取新增的调用、字段写入、错误码，抽取前先去掉注释和字符串。有新增元素的改动块共 4667 个。
3. **映射与查找**（`pguide.py`）：
   - 补丁改动的函数 h，在 riscv 上的目标有两种：同名函数（包括 `.c` 中的 static），以及对照架构上能到达 h 的候选接口在 riscv 上的实现；
   - 在目标及其 3 层被调函数的事实和源码文本里查找元素；源码文本直接从 git 读取，不用检出；
   - 严格卡时间：只用 riscv 修复作者日期之前提交的补丁。
4. **自测**（`selftest/`）：一个带日期的小 git 仓库，覆盖注释过滤、不带 `Fixes:` 的提交不挖、同名 static、经辅助函数映射到接口、间接已有的元素不报、时间截止。只修过一处样例错误（漏定义 `EINVAL`），之后一次通过。
5. **评估**（`eval_dev.py`）：
   - 宽松命中：标记的目标是修复函数，或者能在 3 层内到达修复函数；
   - 精确命中：在宽松命中的基础上，标记的元素正是 riscv 修复补上的那个元素。
6. **迭代 3 次**，逐次记录（`iterations.md`、`runs/iter0..2/`），然后做了上限估计（`ceiling.py`）。

### 上限估计：这条路本身能覆盖多少

在有修复元素的 24 条样本中，riscv 修复补上的元素，出现在截止日期前**同名函数**的对照修复里的，只有 2 条：
- **A143**：已精确命中；
- **A379**：arm64 提交 `8d09e2d569f6` 在 `patch_map` 里补了 `offset_in_page`。没命中的原因是，修复前 riscv 的 `patch_map` 别处本来就用过 `offset_in_page`。按元素查“有没有”，看不出“用在哪里”。

也就是说，在这个开发集上，规则调得再好，精确命中最多也只有 2 条。

## 看出的几点

1. **补丁引导一旦对上，非常准。** A143 的元素、位置都和 riscv 后来的修复一致，还附带对方的修复说明，能直接告诉后续的差分测试“该朝哪个方向变异”。
2. **但在我们的样本上，覆盖面很小。** 样本中的 riscv 缺陷，大多不是“别人修过、riscv 没跟上”：
   - M10、M7 居多，对方往往一开始就写对了。比如 A043 缺的 `cpumask_clear`，在 x86 的实现里从来就有；
   - 就连 M8，对方的演进也常常发生在公共代码里、没有 `Fixes:` 标签，或者函数不同名。
3. **噪声的性质和纯对照一样：** 绝大多数是对照架构特有的设计。对方修的是它自己才有的功能，riscv 不需要。“有修复补丁”这层证据，并没有像预想的那样把它们区分开。
4. **两条可以带到以后的改进：**
   - 要求元素在 riscv 上可用（迭代 1）；
   - 接口映射只看 1 层（迭代 2）。

   这两条让当前版本的报告从 1895 条降到 186 条，没有丢掉精确命中。

## 局限

- 只挖了 x86、arm64 的 `arch/` 目录中带 `Fixes:` 的提交；公共代码里的修复、不带标签的提交都没挖。
- 改动块的函数名取自 git 改动块的标题，是启发式的。
- 按元素查“有没有”，不看位置和条件。
- 人工核对由我一人完成；#169（`smp_send_stop` 的并发保护）没有查清。
- 样本都是我看过的，只能作开发集。
