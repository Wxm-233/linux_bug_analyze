# RISC-V NAPOT大页清除不在内存的表项：运行验证

## 结论

**疑点成立。** 在终点版本`df2908090cda`的RISC-V内核上：

- 一个64KB的NAPOT大页被写成中毒标记后，无论是解除映射还是用`mremap`移走，原地址只清掉了16个表项中的第1个；
- 之后在同一地址建立普通内存，第2到16个4KB页一读就收到SIGBUS，正确行为是读到零。

只去掉`pte_napot`门槛的对照内核上，同样的操作16页全部读到零。三条事先标准全部满足。

这是本项目第一个**按机制推出、并经运行确认**的RISC-V缺陷，来自上一轮的案例清点（`mech_state_size_inventory_20261101/`）。只记录，**不对外报告**，是否向上游报告由用户决定；上游是否已有修复尚未查重。

## 疑点是什么

RISC-V用NAPOT把16个连续的4KB表项合起来表示一个64KB大页。终点版本中：

- `set_huge_pte_at`写入不在内存的表项（中毒标记、迁移项等）时，按调用者给的大小**写满16个**（`1de195dd`修的）；
- `huge_pte_clear`和`huge_ptep_get_and_clear`清除时，先用`pte_napot(表项内容)`判断是不是NAPOT大页。不在内存的表项不带NAPOT位，判断为“不是”，于是**只清1个**。

arm64的`49c87f76`修同一问题时删掉了这道门槛；RISC-V照着修的`83d78ac6`只改了个数来源，门槛留了下来。

## 方案

方案与判定标准见`plan.md`（运行前写定，SHA `bc771b01…`），运行中没有修改。

- **内核**：
  - 原版：`git archive df2908090cda`，`defconfig`加`CONFIG_USERFAULTFD`，Image SHA `8e933a40…`；
  - 对照：同一源码打`control.patch`，只删掉两处门槛，Image SHA `5b3555e1…`。
- **运行环境**：QEMU 8.2，`virt`机型，`-cpu rv64,svnapot=on`，内核参数`hugepagesz=64K hugepages=16`。
- **测试程序**：`napot_test.c`，静态链接，作为`/init`，跑完关机。每个场景用单独的2MB区域，区域里先放一个已访问的普通页，保证页表页一直存在。

| 场景 | 做法 |
| --- | --- |
| C 对照 | 映射64KB大页并写入（大页真正在内存）→ 解除映射 → 同址建普通映射 → 读16页 |
| P | 映射64KB大页 → 用`UFFDIO_POISON`写成中毒标记 → 解除映射 → 同址建普通映射 → 读16页 |
| M | 同P，但用`mremap`把大页移走，而不是解除映射 |

## 结果

| 内核 | 场景C | 场景P | 场景M |
| --- | --- | --- | --- |
| 原版 | 16页读到零 | **第1页读到零，第2到16页SIGBUS** | **第1页读到零，第2到16页SIGBUS** |
| 对照（去掉门槛） | 16页读到零 | 16页读到零 | 16页读到零 |

前提检查全部通过：
- 64KB大页16个可用；
- 写入标记后读大页本身收到SIGBUS，说明标记生效；
- M场景中，移到新地址后读同样收到SIGBUS，说明标记被完整搬走。

两次运行的内核日志里都没有WARNING、BUG或Oops。日志中的调用栈信息，是内核按惯例记录1号进程收到的信号，属于预期内容。

原始输出：`logs/base.log`、`logs/patched.log`。

## 影响与边界

- **已确认的**：经过上面两条公共路径（解除映射，`mremap`），会留下15个残留的不在内存表项。之后在这里建立的普通内存会读到错误结果（SIGBUS）。
- **用到的条件**：硬件支持Svnapot；系统配置了64KB大页；进程能用userfaultfd（非特权进程可以用`UFFD_USER_MODE_ONLY`）。
- **没有验证的**：
  - 迁移项、uffd写保护标记走的是同一段代码。迁移项残留可能有更严重的后果，例如普通页按迁移项处理，但本轮没有构造；
  - 真实硬件上没有运行。
- **对照补丁**：只用于确认原因，不是经过审查的修复。

## 对研究的意义

- 这个缺陷是“表项状态—大小来源”机制的一个实例，而且在本项目已有的检查方法下都找不到：
  - 步骤比较：arm64和RISC-V这两个函数都“用了大小参数”；
  - 钩子覆盖：RISC-V覆盖了这两个钩子；
  - 多数比较：关键步骤类别相同。
- 它是按机制的**适用条件**去读才发现的：这条要求在什么状态下必须成立，判断时依据的是什么信息。不在内存的表项正是“内容不携带大小”的状态，而门槛恰好依据了内容。
- 它也说明了跨架构移植修复时的一种具体失误：照着另一个架构的修复改，却只改了一半，保留了与原问题同源的判断。

## 统计

不调用模型；构建2次（原版、对照）；运行2次；**新确认缺陷1个**（RISC-V，只记录、不对外报告，未查重）。
