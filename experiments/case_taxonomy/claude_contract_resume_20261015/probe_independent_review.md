# 公共消费者原型独立核对

2026-10-15。只读审查既有源码、生成 C、运行收据和说明；没有重新编译、执行、访问 API 或读取密钥。

**结论：未发现改变条件／循环来制造结果的实质问题；本轮结论在已说明的用户态逻辑模拟范围内成立。**

- 独立按 `source_packet.json` 的原始编号提取三个区间：240–248、250–258、5753–5794。去行号后的原文逐字存在于生成 C 对应 `#line` 后，三个函数 SHA 与收据一致。原判断、循环、跳转及告警条件未改。
- 五项输入及初值与驱动一致。空集合不锁任何成员，在5779告警；仅自身锁CPU1并提前退出；仅其他CPU锁CPU0但也因权重为1提前退出，因而没有告警；含自身但CPU0指向集合外CPU2时，第一轮跳过CPU1而找不到leader，在5779告警；正常双成员选择CPU0，第二轮把CPU1连接到CPU0。锁与解锁成员及最终指针均与现有输出一致。
- mock记录的是原函数实际发起的锁调用。四CPU以内、固定集合的这五项输入中，按位升序遍历与所需语义相符；WARN返回条件值并按源站点抑制重复记录。每项主动重置WARN状态已明确披露，不能当成一次内核生命周期的全局WARN计数。
- 原始 stdout 与结果 `cases` 一致，stdout、生成源码、packet、初次编译收据的SHA均核对一致。初次 `-Werror` 编译失败、执行0次；恢复编译命令仅移除 `-Werror`，生成C字节未变，第二次编译与唯一一次执行均返回0。可报告“两次编译、一次执行”，不能称为首次编译全部通过。

**可接受的解释边界：**这些输出说明“无WARN”不能替代集合成员契约检查，且 `containsSelf` 不能独自保证leader相关处理成功。`containsSelf` 的“必要性”仍是结合接口身份与调用条件提出的候选，不能仅凭这五项输入证明。尤其是 singleton-other 与缺leader输入的实际启动可达性尚未建立。

本原型不包含真实锁／IRQ／并发／硬件状态，不验证架构提供者初始化路径，也不解决取指针与稍后消费之间的对象／时刻等价。它是同一已读案例的五个逻辑输入，新增内核运行、独立缺陷案例与独立检测阳性均为0。现有 `probe_review.md` 已保留这些限制，没有把局部模拟写成完整跨架构验证。
