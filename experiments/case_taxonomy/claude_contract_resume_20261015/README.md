## 怎样联系跨架构机制

反例用于校准公共消费者的要求，架构差异仍须另证：x86在共同通知前准备组关系；旧s390的准备资格依赖online，而本地通知／公共回调发生更早。**应检查的是某个架构在共同消费期限前是否提供满足要求的状态，不是简单要求CPU先online，或仅扫描是否存在WARN。**

| 检查层次 | 当前可支持的结论 | 后续仍需的证据 |
| --- | --- | --- |
| 集合身份 | self是具有接口身份／消费依据的必要窄候选 | 不能只凭for_each语法推导所有集合都必须含调用者 |
| 组初始化／leader | 多成员路径需要其他有效leader和后续组一致性 | self并不充分；正常／异常构造的实际可达性另证 |
| 架构履约 | 提供者、资格、准备顺序及配置可以分别定位 | 不把最早为零或较晚update直接当消费时必空 |
| 真正消费点 | 5755取指针、callee取指针、内容遍历、旧采样各有位置 | 旧pre_irq_disable采样不是精确遍历原子快照；中间写入／并发未证 |
| 权威依据 | 版本／配置下消费者实现和实际接口用途能约束候选 | 源码推断、规范与防御策略分级，不按多数架构投票 |

当前仍是已读案例的机制开发；已有历史四格运行不在本轮重跑，也不升级为本轮新检测或泛化证据。
