# 方向4第三轮：“跟随arm64修复”推广到全部家族

## 这一轮要回答什么

方向4前两轮在大页家族上发现：以arm64为参照，能解释RISC-V大部分机制性的大页问题；而且有一条独立证据——arm64修好的问题，三周后RISC-V也在同名函数上修了一遍。

这一轮检验这个机制能不能推广到所有家族：

> arm64的一次修复给某个函数**新加了一个调用**，即新加了一步；RISC-V有同名函数，当时还没有这一步。那么RISC-V后来会不会也补上？

如果大多会补上，这就可以做成一个简单的提醒工具：每当arm64合入一个修复，就自动检查RISC-V的同名函数。

## 做法

- **样本**：v5.10以来arm64带`Fixes:`的修复3681个。同时改了`arch/riscv/`的17个排除在外，因为它们已经顺带改了RISC-V，不算“跟随”。
- **提醒**：修复前后，比较arm64函数调用了哪些函数或宏，取修复后新出现的调用。只保留RISC-V也能用的名字。如果RISC-V的同名函数当时没有这个调用，就记一条提醒。
- **结果判定**：到终点版本时，RISC-V的同名函数里有没有出现这个调用。
- **基线**：同一批函数中，arm64在修复之前就有、而RISC-V一直没有的调用，统计RISC-V后来补上的比例。
- **复制检验**：x86修复→RISC-V；arm64修复→LoongArch。

| `follow.py` → `follow.json` | 扫描与结果，8路并行 | 见`criteria_sha256.txt`；`6029ca70…` |

冒烟时，脚本复现了上一轮的独立证据：arm64在`get_clear_contig`中新加了`pte_present`，RISC-V以`83d78ac6`跟进（带`Fixes:`）。

## 结果

| 配置 | 修复数 | 提醒条数（涉及修复数） | 新加步骤的跟进率 | 基线跟进率 | 终点时仍未跟进 |
| --- | ---: | ---: | ---: | ---: | ---: |
| **arm64 → RISC-V** | 3681 | 62（31） | **4.8%**（3条） | 5.3% | 52 |
| x86 → RISC-V | 2348 | 34（20） | 2.9%（1条） | 5.9% | 31 |
| arm64 → LoongArch | 3116 | 28（18） | 0% | 4.7% | 28 |

**按事先定的标准：无用。** 跟进率远低于15%，也没有高于基线，三种配置都是如此。“arm64新加了一步”这个信号放到全部家族上，对RISC-V没有指导作用。

### 为什么

1. **能产生提醒的修复很少**：3664个arm64修复中，只有31个同时满足“新加的调用RISC-V也能用”和“RISC-V有同名函数”。
2. **大多数是arm64自己的事**：例如大端序内核的uprobes、MTE、NMI、休眠恢复时屏蔽DAIF、BPF arena。这些修复新加的步骤，对RISC-V没有意义。
3. **“跟进”的3条中，有2条是同一个系列补丁**：KVM客户机进出逻辑的重写，arm64和RISC-V相隔一天分别合入。这不是RISC-V看到arm64修复后的跟随。真正的“跟随”只有大页那一条。
4. **很多新加步骤是通用的加固写法**，例如`WARN_ON_ONCE`、`READ_ONCE`、`guard`，不代表RISC-V缺了什么约定。

所以，前两轮在大页上观察到的“跟随arm64”，依赖的是NAPOT与arm64连续页在**结构上高度相似**。它不是一个在所有家族都成立的规律。

### 事后查看（看过结果之后，判据不要求，未登记）

仍未跟进的提醒里，有几条看起来和RISC-V相关。研究者查看了其中一条：

- **arm64 `a77644d0`（2026-08-28）修复了`show_pte()`中的无锁页表遍历**：遍历过程中，页表页可能被并发释放；上层表项可能在检查之后被清空，再用`pXd_offset()`重读，就会得到错误的下层指针。修复改用`*_offset_lockless`，并在遍历期间关中断。
- RISC-V的`show_pte()`（`arch/riscv/mm/fault.c`）仍然是旧写法：读出上层表项后，又用`p4d_offset(pgdp, addr)`等从指针重读，而且没有关中断。RISC-V在多核且有MMU时同样选择`MMU_GATHER_RCU_TABLE_FREE`，arm64的修复理由正是建立在这一点上。
- **结论：疑似RISC-V存在同样问题**，只影响打印崩溃信息的路径。没有运行验证，只记录，不对外报告，由用户决定。

另外几条看起来可能相关的，例如arm64 `650768c5`“限制页表拆除以避免误报警告”涉及`pmd_free_pte_page`和`pud_free_pmd_page`，本轮没有查看。

## 结论

- “跟随arm64修复”**不能作为通用的提醒机制**：在全部家族上，跟进率和基线一样低。
- 它的有效范围，是RISC-V与arm64**结构相似的家族**，例如多表项大页、页表遍历。在这些家族里，按机制逐个深挖（前两轮的做法）比全局扫描更有效。
- 全局扫描并非全无价值。它给出了少量值得人看的线索，例如`show_pte()`那条。但从52条仍未跟进的提醒中挑出这样的线索，需要人工判断，也就是说需要理解语义。

## 可能的下一步（未登记）
