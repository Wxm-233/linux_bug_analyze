## 改了什么

`reach_20261115` 的 F4（内核页表）有一条规则：函数体里只要出现 `init_mm`、`pte_offset_kernel` 这类标识符，函数里所有调用点都滤掉。本轮把这一条换成看**这次调用的值从哪来**：

- 取第一个实参的来源，例如 `ptep_get(pte)` 的来源是 `*pte`，根变量是 `pte`；
- 局部变量：本函数里对它的每次赋值右边都来自内核页表（`pte_offset_kernel(...)`、`pgd_offset_k(...)`、`init_mm` 或已判为内核页表的变量），才算内核页表；右边有 `?:` 的不算（可能一边是用户页表）；
- 参数：所有调用者在这个位置传的都是内核页表指针，才算，跨函数最多 3 遍。

按文件、按函数名前缀（`vmemmap_`、`kasan_`）的两条规则不变，其余过滤和排序也都不变（只读导入 `reach.py`）。

## 看出的几点

1. **按“函数里出现什么”判断很容易判反**。`init_mm` 既可能是“在走内核页表”，也可能是“遇到内核页表就跳过”。看值从哪来，两种情况都能分清。
2. 新放出来的 9 条虽然都不是缺陷，但原因从“内核页表”变成了“有守卫但不认识”：守卫写在架构函数 `*_user_accessible_page()` 里。把这两个函数加进 F1 的守卫名单，就能再滤掉 8 条。这是 F1 名单不全，不是 F4 的问题。
3. 代价是可达候选多了 9 条，新疑点 3 从第 25 名降到第 28 名，仍在前 30。

## 局限

- 根变量只取第一个标识符：`pvmw->pte` 看的是 `pvmw`；如果结构体的某个字段来自内核页表、其他字段不是，会判不准。这次的当前版本里没碰到。
- 参数只看扫描范围内的调用者；架构代码里的调用者、函数指针回调（例如 `apply_to_page_range` 的回调）看不到，这类仍靠“按文件”的规则兜底。
- 函数里没有赋值、不是参数的根变量（例如全局变量）一律当作非内核页表。
