# N2.10冻结挑战：关系来源链不足

本诊断只读冻结结果与现在获准披露的9份挑战源码。未修改冻结v2、v1、测试、oracle或baseline，未改写输入或重跑；不新增v3普通C补丁。本批源码已被实现角色阅读，后续只能作为已见开发材料。

## 实际结果与前端已通过的部分

预登记支持的6份K0—K5全部不足，3726条参考记录全部因源码不足而跳过。实际求值、返回值比较、check_observations比较均为0。零mismatch不能解释为正确，3726条也不是3726个新问题。

与N2.9不同，实际错误不再是注释或CRLF。9份均保留原文与解析视图身份；K2原字节含CRLF，仍进入了同样的后续结构核对。K0—K5实际理由一致：`check_not_search_object_and_witness_linked`。因此词法桥与普通C解析已越过此前首因，但整条条件提取/行为比较没有完成。

## 缺的是值来源追踪，不是注释格式

K0的精确链条是：第16行`entry = sequence[scan]`，第17行`earlier_relation = parent[entry]`，第20行搜索谓词才比较`earlier_relation == entry`；第33行另一遍直接比较`parent[inspected_unit] != selected`。K2同样先在第17行读取`route[element]`到局部量，再在第20行使用该量。

v2允许并保存这些循环局部声明，有限解释器也能计算普通整数别名；但实际分类门禁仍对**谓词自身**调用`v1.array_reads`，与后续检查中的数组根做直接语法交集。搜索谓词只有两个局部ID，未沿声明追到数组读取，集合为空，于是拒判。K0—K5共有这个来源链形式，这解释了6份同因不足。

这不是变量重命名或数组不存在，也不是实际执行发现契约错误。它暴露了“能够解析/解释局部别名”和“能用该别名建立来源依据”之间的断点。保守门禁没有凭相似名字强行宣称同一来源，但目前不支持协议预期的这类简单来源链。不能删除门禁、手工内联局部量或只换写法重跑后追认成功。

K0的空域、K1的单成员短路也未得到新行为比较：当前先核完整函数结构，提前被同一来源门禁挡住。K5的参数化提名、首命中是否仍等于sentinel，以及其他前/后检查和continue变体，同样尚未运行核对。不能从共同首因推出这些后续语义一定正确或一定错误。

## 三项拒判对照的限度

- Z0实际为`unsupported_search_control_or_write`，来源于搜索期间额外条件改写界；这是不支持搜索控制/写入的门禁，不是完整动态界分析证明。
- Z1实际为`monotone_flag_only_conditional_set_one`，拒绝检查后把flag重置0。
- Z2实际为`unsupported_statement:While`，拒绝非规范while。

三项均按预期保留不足，且与N2.9的通用注释拒绝不同，已到相应结构边界；它们没有参考执行记录，不能扩大成任意不安全控制或副作用均可识别的结论。

## 对研究方向的影响与下一步

旧9份已读开发回归的7份提取、2754次return匹配仍只属于开发结果。本次新输入6份预期支持却0份提取，说明当前方法依赖窄语法形状，不能声称自动消费者条件已经稳定。15项组件测试通过也不能替代实际独立比较。

下一步不继续新增普通C模板或围绕这批失败修v3，而应有界核对真实Linux的编译器前端：先确认现有精确版本/配置/编译命令能否提供保留源位置的完整公共消费者AST或IR，再检查局部值经load、赋值和分支传到实际检查位置的来源链。目标是为“架构提供的数据经过公共接口后实际被怎样使用”建立可靠证据，而不是让更多手写形状匹配。

探查只限既有消费者和现有材料，保留原源、配置、工具及产物身份；若编译产物不匹配、位置/宏来源无法绑定或值流超范围，就记录不足并停止，不沿helper树持续补源。编译器IR本身也不会自动解决对象别名、真实准备效果、架构规范与全路径证明，这些仍需分别验证。本次冻结失败与边界全部保留。
