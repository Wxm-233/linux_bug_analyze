# 从标量写入到字节交接：本轮机制实验

日期：2026-09-30。延续 D2/D3，验证如何从源码提取应该检查的表示边界，以及用什么证据裁定接口格式。旧 v4、历史输出和统计分母均保持原样。本轮无付费模型调用。

## 本轮支持到哪里

1. 自动取证现在能在受支持形状下，从同版源码取得直接标量取址、长度、声明和 HCI 到 `memcpy` 的复制链；指针自身赋值也能与端序元素写入分开。
2. 已读两项的大小端缩小原型说明：主机计算与对外字节交接是不同的表示域，检查必须放在实际跨域处。TI 适用型号的官方文档补足了命令格式的外部依据。
3. 冻结后的两个新输入仍未检出目标：结构体字段与直接缓冲区 API 超出当前形状。**没有建立独立同机制检出或通用检测能力。**本次如实停止，不按输出换样。

## 共性机制与检查方向

P2“数据表示不一致”继续有效，进一步细化为**数值域与字节域之间的交接必须有适用的编码/解码关系**。

- 进行比较、长度计算和主机 API 调用时，使用主机数值。
- 进入明确要求某种格式的设备命令、持久化或共享字节格式前，按该格式编码；读入后按相同契约解码。
- 只有生产者/消费者与适用契约确定后，才能判断是否缺转换或转换过早。普通 `void *`、同名字段或补丁里新增转换都不足以单独裁定问题。
- 内部同主机读写可能保持同一种表示；应先检查配对是否自洽和是否真的跨越格式域，不能仅见主机字节复制就计为跨架构缺陷。

检查建议的当前自动部分是源码事实提取与保守分类，外部协议含义、支持型号及完整运行条件仍需要证据卡和复核。不是由模型直接生成断言后无条件插入内核。

## 已读契约与运行对照

### 设备命令与主机 API 分流

历史 hci_ll 的速率值一边发给设备、一边交给串口 API。父版发 `&speed`，复制链不改变 payload；修复只对发送侧建立 `__le32 speed_le`，主机 API 仍接收原数值。

[TI 官方 SWRU442B](https://www.ti.com/lit/ug/swru442b/swru442b.pdf)第 6 页给出低字节在先的传输规则，第 13 页规定 `0xff36` 速率参数为四字节。该指南 2015-10 初版、2017-10 修订，与 2017-12 的修订时间相容；协议依据限于所查 WiLink 8/WL18xx，未外推到所有 TI compatible 或所有 HCI 命令。

缩小原型中，速率 3000000 在 s390x 旧版复制为 `00 2d c6 c0`，修复为协议要求的 `c0 c6 2d 00`；x86_64 旧新相同。115200 亦有该大小端差异。零值是字节不变对照，但实际 `if (speed)` 不发送零值，不能把它算作走通了正常命令路径。

### 主机比较前的过早编码

历史 mpt3sas 在比较前把主机长度编码成小端，随后按主机整数与 16384 比较。s390x 原型中，4096/16384 分别被解释成 1048576/4194304，误选另一分支；65536 变成 256，又产生相反方向的误选。修复删除比较前的转换。

x86_64 的选择旧新一致；SGE 数为 3 时另一条件遮蔽该差异，旧新均走 PRP。原型合计分别运行 3 个速率、5 个长度×2 个 SGE 数，**输入数量不当独立缺陷数**。它只验证表达式与存储字节，没有固件交互、历史内核运行、DMA 或真实设备故障。

详细 A/P/C、源码行与完整输出见 [契约卡](authority_review.md)、[原始结果](authority_results.json)。

## 两个自动取证模块

### 指针层级 v5

v5 包装冻结 v4，解析原始左值和同版成员的指针/数组层级。mpt3sas 的 `reply_free = NULL` 与分配结果赋值单列为 pointer-object；`reply_free[i]` 元素写入仍保留局部 normal，不把过滤数当正常数据点。复杂层级、条件声明、数组整体赋值或类型不一致保守拒判。

| 已读开发输入 | v4 candidate/normal/insufficient | v5 candidate/normal/insufficient | 指针自身另列 |
|---|---|---|---|
| mpt3sas 旧/新 | 0/1/2 | 0/1/0 | 各 2 |
| hisi_sas 旧 | 1/15/38 | 同 v4 | 0 |
| hisi_sas 修复 | 0/16/38 | 同 v4 | 0 |
| dw_mmc 旧/新 | 0/5/6 | 0/1/10 | 0 |

**旧 v4 解释勘误：**dw_mmc 同函数先在 64 位模式声明 `idmac_desc_64addr *p`，后在另一个分支重用名字为 `idmac_desc *p`。旧提取器汇总全函数类型，后部声明覆盖了前部，导致四处原生 `u32` 写点被错误关联成 `__le32` 的 normal。v5 校验写点前声明后拒判这四处。它们的零值本身仍字节不变，既不是四项新错误，也没有证明 64 位模式存在缺陷。原结果保留，旧 normal 的类型依据不能再用于模式验证。精确行号见 [v5 开发说明](../representation_v5_development.md)。

### 出站标量 v1

只支持 `__hci_cmd_sync()`/`hci_req_add()` 上直接 `&固定宽标量`、`sizeof(同变量)`；复制链从同版函数取证，遇到别名改写、参数变换或不支持形状时拒判。输出原始主机声明标量字节、匹配转换形式、证据不足三类事实，opcode 格式默认未知。

默认开发回放中 hci_ll 两版均有两项 insufficient。内核源语境明确假设 `__KERNEL__=true`，但 `CONFIG_SERIAL_DEV_BUS` 未指定，所以不能裁定完整适用性；保留的局部表示事实为旧 speed 多次赋值不足、修复 speed_le 匹配转换形式且源值路径未证明。没有为了回放命中悄悄打开配置，也没有把声明为 `__le32` 就当完整正确。

新模块 46 项与 v5 16 项测试通过；根执行者连同旧 v4 重跑 **87 项测试执行全部通过**。只读方法审计另外核对显式已编码 host 临时变量、二次转换、consumer alias/cast 修改与条件成员等指定边界。测试覆盖不是独立样例准确率。

## 老师两个问题的当前答案

**怎样自动提取应添加的检查：**从类型/值来源开始，定位第一次主机运算或字节交接，追到真实消费者，再对照有适用范围的格式约束。现在已实现部分声明、调用和复制链取证；值路径、结构体字段与读写配对仍有缺口。检查条件可以表达为“该命令在此配置下复制四字节，因此发送端应满足其四字节格式”，而不是“凡出现硬件 API 都加转换”。

**不同架构解释不同时以什么为准：**以版本、设备模式、路径和实际消费者适用的契约为准。外部设备命令可用厂商规范；内部格式先核对同版生产者/读端及共享范围；类型声明还要来自正确作用域。没有依据或存在冲突时只给复核线索。本轮一条 TI 契约得到适用外部规范支持，尚未解决所有旧案例的接口争议。
