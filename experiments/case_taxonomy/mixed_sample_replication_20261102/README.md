### 与上一轮合并（次要结果，363个样本）

L F1 0.488，RL F1 0.502，差0.014，95%置信区间 [−0.049, 0.074]；McNemar 51对39，p = 0.25。合并后也看不出显著差别。

## 事后分析（看到结果之后才做的，只作描述）

1. **两种做法的F1都和“全部判有bug”差不多。** 本轮样本中三分之一有bug，全部判有bug时查准率1/3、查全率1，F1正好是0.5（上一轮样本构成相同，也是0.5）。L的0.507、RL的0.488都在这个水平。所以F1在这个样本设计下区分不了“会检测”和“乱猜”，上一轮0.429→0.545的差别，很可能主要是小样本的波动。
2. **真正说明问题的是配对区分。** 91对中，L只有21对、RL只有17对做到“修复前判有bug、修复后判无bug”；两个版本都判有bug的，L 37对、RL 36对。也就是说，模型多数时候并没有认出“那个”bug，而是在代码里找出了别的可疑之处。
3. **机制目录对未改动函数的误报有稳定的降低，但不显著。** 本轮32→25，上一轮13→8，两轮方向一致；只看本轮91个未改动函数，仅L误报13个、仅RL误报6个，事后McNemar p = 0.17。代价是查全率也下降（58→53）。
4. **模型给出的机制大多是一般缺陷类。** RL判有bug的126个中，归为M7（边界）55个、M6（生命周期）30个，这两类本来就标为“一般缺陷”，不是跨架构特有的；归为M1–M5、M8、M9的合计31个。这说明在“随便一个RISC-V函数”上，机制目录主要起的是一般检查清单的作用，跨架构机制本身用上的不多——这与样本的来源一致：这些修复大多不是跨架构缺陷。

## 结论

- **上一轮“机制目录让模型检测更好”的结论没有在新样本上复现**，应撤回为“未见显著差别”。本轮是事先写定标准的复核，结论以本轮为准。
- 机制目录对“少误报”有两轮一致、但不显著的作用。
- 让模型逐个函数判断“有没有bug”，在修复前后版本上几乎分不开，这种做法本身不适合作为检测方法的主体。结合约定级试点与同名函数跟随的结果，机制更适合用在**先确定检查点**（列出某个约定的全部实现位置，或找出参照架构刚修过、RISC-V未跟进的同名函数），再让模型或人只回答具体问题，而不是直接对任意函数问“有没有bug”。
- 样本以`Fixes:`标签为准，多数修复不是跨架构缺陷，这限制了机制目录能起的作用；要检验跨架构机制本身，需要以跨架构缺陷为主的样本。
