# 新方向：三类检查的精炼与有保障的静态分析

## 方向调整

依据《跨架构缺陷bug Fuzz》，研究方向收窄为**跨架构缺陷发现**：
- 去掉修复与迁移；
- 去掉大模型辅助，只用静态分析；
- 静态分析的结果交给文档中的第二步，即差分模糊测试。

**约束：检查保持三类，不再增加类别**。本轮的做法是把每一类的范围补全、说清楚，使三类合起来覆盖所有边界语义失配。

本轮要回答四个问题：
1. 原三类检查为什么覆盖不全；
2. 三类各自应该包括什么；
3. 十类机制落在哪一类，有没有漏掉的情况；
4. 每一类怎样做静态分析，能保障到什么程度。

另外，静态分析结果有两种用法：一是指定目标点位，二是不设点位、只作为变异提示（hints）。本轮先列出判断哪种可行要看哪些数字，做完边界枚举后再定。

本轮不调用模型，不改代码，只做分类与设计。

| 文件 | 说明 |
| --- | --- |
| `labels.py` → `labels.json`、`stats.json` | 135条跨架构样本逐条归类（取自`cross_arch_sample_set_20261102/labels_v2_1.json`中跨架构为C的样本）：所属检查、检查中的方面、原三类检查能否覆盖 |

## 一、原三类检查的问题

问题不在类别数量，而在**每一类的范围定得太窄**。三类都是按症状写的，即“代码长什么样会可疑”：
- 类型一致性只比C类型的宽度和符号；
- 实现完备性只找空实现和常量返回；
- 调用上下文只找写缺失、调用缺失和检查条件不同。

我把135条跨架构样本逐条对照，原三类只能覆盖其中30条（22%）；去掉15条构建与工具链问题后，是30/120（25%）。没覆盖到的情况主要有：

| 缺口 | 例子 |
| --- | --- |
| 边界只算函数调用，漏了架构提供的宏、常量、数据对象、Kconfig符号 | RISC-V把`TASK_SIZE_MAX`设成`LONG_MAX`（A171）；`AT_VECTOR_SIZE_ARCH`少算了一项（A027） |
| 只看“公共代码调用架构”这一个方向 | 公共`kexec_buf`新增了字段，架构栈上的结构没有初始化（A190） |
| 值只看C类型，漏了取值范围、编码、单位、地址类别 | 公共默认实现只认PMD/PUD大小，不认NAPOT大小（A036）；`__pa`只接受线性映射地址，传入的却是fixmap地址（A328） |
| 实现只看是否为空，漏了实现应提供的维护和保证 | 改写代码后没刷指令缓存（A087）；xchg缺屏障（A081） |
| “调用上下文”名不副实，没有真正的执行上下文 | 关中断时取mutex（A327）；资源在CPU上线阶段之后才提供（A091） |

## 二、三类检查的精炼

### 先把“边界”定义全

**边界符号**指在一侧使用、在另一侧定义的符号，包括函数、宏、常量、类型、全局变量与数据对象、Kconfig符号。两个方向都算：
- 公共代码使用、定义在`arch/<架构>/`中，或者由`asm-generic`回退、`__weak`默认实现提供；
- 架构代码使用、定义在公共代码中。

**边界点**指一处跨边界的使用：一次调用、一次宏展开或一次读写。

### 三类检查的划分依据

一次跨边界的交互可以分成三部分：
- **传了什么**：数据；
- **对方做了什么**：实现；
- **在什么状态下发生**：上下文。

失配一定出在其中某一部分。三类检查分别对应这三部分，所以不用增加类别，就能把交互方式覆盖全。

| 检查 | 回答的问题 | 包括的方面 | 样本数 |
| --- | --- | --- | ---: |
| **一、数据一致性**（原“类型一致性”） | 跨边界的值，在各架构、各配置下的含义是否一致 | ① 位宽与符号 ② 取值域：架构常量的取值，架构可能产生的取值是否在公共代码或默认实现能处理的范围内 ③ 编码与布局：字节序、符号扩展约定、结构或栈布局 ④ 单位、基准与对齐 ⑤ 地址与输入的类别：线性映射、fixmap、vmalloc地址，标志的含义 | **37** |
| **二、实现完备性** | 各实现是否都完整提供了调用方需要的行为 | ① 存在与选用：定义缺失、Kconfig依赖、能力只在部分配置下才有、退回空实现或常量桩 ② 副作用：写缺失（共享状态、寄存器、标志位）、公共调用缺失或实参不同 ③ 返回值：可能返回的取值集合 ④ 输入检查：同一接口的各实现对同一输入的检查不同或缺失 ⑤ 维护与保证：TLB与指令缓存维护、先清后写、原子性与内存序 ⑥ 实现内部步骤的先后 | **57** |
| **三、调用上下文** | 调用发生时，所处的状态是否满足被调用方的要求 | ① 执行上下文：中断、抢占、可否睡眠、RCU、可否插桩、MMU开关 ② 所处阶段：相对启动、initcall、CPU热插拔等公共阶段的先后 ③ 对象与资源是否就绪：被读取的字段是否已初始化，对象是否已构造或需要重置 | **26** |
| 不属于三类 | 构建与工具链（构建脚本、编译选项、汇编指令布局），不是运行时语义失配，由构建矩阵编译发现 | | 15 |

原文中“调用上下文”的内容（写缺失、调用缺失、检查不同）是“实现做了什么”的问题，移到检查二。检查三改为名副其实的“调用发生时的状态”。原文提到的“公共侧依赖未保证的副作用（如假定缓冲区已清零）”属于检查二②。

文档中的四类失配模式也都包含在内：
- 配置边界对应检查一②④；
- 表示失配对应检查一③；
- 时序失配对应检查三②③；
- 能力误判对应检查二①。

**完备性检查结果**：135条中，120条落入三类，15条属于构建与工具链，没有归不进去的。

**十类机制不能直接当作检查类，因为它们混合了三个维度：**
- **失配的内容**：M2–M7、M9，基本各自落在一类检查里。
- **失配的成因**：M8，指实现照着参照的旧版本写，参照后来又改了。它的样本分散在三类里。
- **对照基准**：M10，指同一约定由各架构各自实现。它说明可以拿其他架构的实现作对照。

所以在三类检查中，M8、M10不单列，只决定拿谁作对照。见下面“对照基准”一节。

## 四、静态分析策略与保障

### 保障指什么

在给定的内核版本、给定的“架构×配置”集合（构建矩阵）、给定的检查定义下，程序报出的结果包含所有符合定义的位置，也就是不漏报；允许误报。

成立的前提：
- 调用图与指针分析取保守近似：函数指针按类型匹配，所有可能的目标都算上；
- 分析不了的代码（汇编、JIT生成的指令）不跳过，整体报出。

| 保障等级 | 含义 |
| --- | --- |
| 精确 | 结果直接取自编译器，没有近似 |
| 保守可靠 | 在有限的抽象上做数据流分析，不漏报，可能误报 |
| 相对规格可靠 | 先写一份有限的规格表，相对这份表不漏报 |

**保障不了的情况**：
- 所有架构同时漏了，又没有规格可对照，例如缺页重试时所有架构都漏了`FAULT_FLAG_TRIED`（A032）；
- 不经过任何架构接口、只是隐式依赖x86强内存序的公共代码（B584）；
- 构建矩阵之外的配置。

### 公共部分：构建矩阵与边界枚举（精确）

- **构建矩阵**：每个架构（先做RISC-V、arm64、x86）取defconfig，再翻转影响边界的Kconfig选项，例如RV32/RV64、页大小、`PREEMPT_RT`、`KASAN`、扩展开关。用clang编译，导出AST和宏展开记录。
- **边界枚举**：对每个“架构×配置”，记录每一处跨边界引用解析到的定义位置，包括宏，两个方向都算。每个边界符号得到一张表，写明每个配置下它是架构自定义、公共默认，还是不存在。

### 检查一：数据一致性

| 方面 | 做法 | 保障 |
| --- | --- | --- |
| ① 位宽与符号 | 在每个配置的AST中找边界点上的整数转换：实参到形参、返回值到接收变量、写入边界全局变量。某配置下变窄或改变符号就报，并沿数据流追到来源赋值 | 精确 |
| ② 取值域 | 常量和宏在每个配置下求值。默认实现中`switch`/`if`处理的常量集合，与架构能产生的取值集合（例如支持的大页大小）比较，后者不被包含就报。公共函数新增了返回值，而架构处理返回值的分支不含它，也报（A313）。各架构对同一边界常量的取值全部列出 | 判断部分精确；列表精确 |
| ③ 编码与布局 | 字节序：对`__le32`等注解类型，在大端、小端两种配置下用sparse各查一遍。扩展约定：BPF到本机、compat到原生、MMIO模拟等跨ABI传递，按psABI规格表核对是否做了扩展。布局：汇编和跳板按偏移访问`pt_regs`等结构的地方，对照`asm-offsets`，硬编码的偏移一律报 | 相对规格 |
| ④⑤ 单位与类别 | 给地址类变量推断类别：物理地址、线性映射虚拟地址、fixmap、vmalloc、页帧号、字节数。以`__pa`、`PFN_DOWN`、`virt_to_page`等转换函数为种子，沿数据流传播。类别混用，或与被调用方要求的类别不符，就报 | 相对种子表 |

### 检查二：实现完备性

**对照基准**：拿什么作对照，按以下顺序取。
1. 其他架构对同一接口的实现，对应M10；
2. 公共默认实现；
3. 参照对象的当前版本，对应M8：目标实现当年参照的那个实现，今天是什么样子；
4. 规格表，用在前三者都没有的时候。

| 方面 | 做法 | 保障 |
| --- | --- | --- |
| ① 存在与选用 | 构建矩阵中编译、链接，记录未定义引用。Kconfig转成逻辑公式，做可满足性分析。列出公共代码用到的能力（`cmpxchg128`、ISA扩展、编译器内建）在哪些配置下由谁提供，使用处没有被相应能力检查支配就报。列出空实现、只返回常量的实现和公共桩 | 精确；能力判断保守 |
| ② 副作用 | 每个实现计算may-write集合（全局变量、参数可达字段、per-cpu变量、`pt_regs`字段），以及调用的公共函数和常量实参。调用方在调用后、重新写之前要读的位置记为post-read。目标实现may-write不含、而对照基准必定写的位置，以及公共调用或实参不同的地方，都报 | 保守可靠；调用比较精确 |
| ③ 返回值 | 比较各实现可能返回的常量集合（错误码等），对照调用方区分的取值 | 精确（常量部分） |
| ④ 输入检查 | 对每个实现，列出参数及其可达字段的危险使用：下标、拷贝长度、解引用、移位量、地址转换、传给公共函数。求支配这些使用的检查条件，包括调用方已经建立的条件。没有检查，或与对照基准的检查条件不同，就报 | 使用点精确，“无检查”判断保守 |
| ⑤ 维护与保证 | 规格表一次写定，表示成状态机：改页表后在返回或被依赖之前须刷TLB；改代码后在执行之前须刷指令缓存；拆分映射须先清、刷，再写（取自`cachetlb.rst`）；原子接口各变体要求的顺序（取自`atomic_t.txt`）；membarrier等要求的屏障。检查所有路径，包括内联汇编和JIT发出的指令 | 相对规格 |
| ⑥ 步骤先后 | 求同一接口各实现中边界可见操作（公共调用、共享状态写）的先后偏序，顺序相反就报 | 精确比较 |

### 检查三：调用上下文

| 方面 | 做法 | 保障 |
| --- | --- | --- |
| ① 执行上下文 | 上下文抽象为有限个状态：中断开关、可否抢占、可否睡眠、RCU是否在看、可否插桩、是否在异常入口、MMU开关。从系统调用、中断入口、启动入口、热插拔回调等入口出发，在调用图上做过程间数据流，求每个调用点可能的上下文。被调用方的要求由它内部的调用推出，例如沿`mutex_lock`、`GFP_KERNEL`、`might_sleep`的传递闭包。可能的上下文超出被调用方允许的范围就报。已有的CTX规则和M5扫描可作为起点 | 保守可靠 |
| ② 所处阶段 | 公共阶段有全序：MMU开启前后、initcall级别、CPU热插拔状态、`sparse_init`等关键初始化点。对每个边界资源，求使用者最早所在的阶段与提供者所在的阶段，提供晚于使用就报 | 相对阶段表 |
| ③ 对象就绪 | 被调用方可能读取的字段（过程间may-read），与调用方在调用前必定写过的字段（定值分析）比较。对象在下次使用前须重置的情况同样处理 | 保守可靠 |

## 五、两种使用方式与判断方法

| | 策略一：作为提示，不设点位 | 策略二：精化静态分析，给出点位 |
| --- | --- | --- |
| 静态分析做什么 | 只做边界枚举，所有边界代码一视同仁；三类检查只提取信息、不下判断，作为变异和检查结果的提示 | 三类检查各自报出点位，第二步以点位为目标 |
| 检查一给出 | 各架构的位宽、取值域、类别 → 优先变异高位、符号位、取值边界 | 转换变窄、取值超出范围的具体位置 |
| 检查二给出 | 各实现的写集合、返回值集合、检查条件 → 作为执行结果检查项（比较哪些变量和返回值） | 写缺失、检查缺失的具体位置 |
| 检查三给出 | 被调用方的上下文要求 → 构造调用序列，例如让调用发生在原子上下文、早期阶段或热插拔期间 | 上下文不满足的具体调用点 |
| 保障落在哪里 | 静态阶段不排除任何边界代码；能否找到取决于模糊测试能否走到并触发 | 静态阶段对每个检查给出不漏报的点位 |
| 主要风险 | 边界代码太多，定向测试顾不过来，退化成普通的覆盖率引导 | 有些方面很难做精确，误报多 |

**判断哪种可行，要看以下三组数字，都在边界枚举做完后才能得到：**
1. **边界规模**：RISC-V与arm64、x86之间的边界符号、边界点各有多少，被系统调用可达的有多少。定向模糊测试一次通常只盯一个或少数目标；边界点如果上万，策略一只能退化成普通测试加提示。
2. **点位数量与误报**：策略二各检查报出的点位数，以及抽样核对的误报率。
3. **模糊测试能不能看到后果**：
   - 样本集中有16条的后果被执行环境遮住，例如现有硬件不缓存非叶表项、x86强内存序遮住了缺屏障、推测执行越界。在QEMU上做差分测试，很可能看不到两个架构的输出差异。这16条中，检查二有12条，其中9条是⑤维护与保证；检查一有3条；检查三有1条。
   - 另有32条只在某些架构走得到出问题的状态。
   - 这说明至少检查二⑤这一部分，后果在差分测试中看不到，只能靠静态分析直接报出。

所以我预计结果可能是两者结合：
- 模糊测试看得到后果的方面（检查一，检查二①②③④，检查三）可以只给提示；
- 看不到后果的方面（检查二⑤，以及部分检查三①）由静态分析给出点位。

这个预计要等上面三组数字出来才能确认。

## 六、流程

1. 构建矩阵：各架构×关键配置，用clang编译，导出AST。
2. 边界枚举：两个方向，所有符号种类。两种策略都需要这一步。
3. 三类检查：策略一只提取信息，策略二报出点位。
4. 差分模糊测试：按文档原设计。

**评估：**
- 在120条样本各自修复前的版本上，看对应检查是否报出该点位，或给出能触发的提示，按检查统计查全率；样本集原有的开发集与测试集划分照用。
- 在当前版本上抽样核对误报。
- 对照组是文档原三类检查，它们在这批样本上最多覆盖30/120。

## 七、建议的下一步

1. 写判据，实现构建矩阵与边界枚举，并统计边界规模。这是两种策略共同的第一步，也是判断哪种可行的依据。
2. 按样本数和已有基础实现检查：
   - 检查三①执行上下文（17条，已有CTX规则）；
   - 检查二②③④（对照类，28条，文档已有初版结果，可以按新定义重新过滤）；
   - 检查一①②⑤；

## 局限

- 归类由我一人完成，依据是样本集中每条的一句话理由，没有重读补丁。每条只取一个主要方面；有的样本同时涉及两类，例如A188既是检查二⑤（须原子），也是检查二①（选用了通用的非原子默认实现）。
- 样本都是已修复的缺陷。归得进去只说明已知情况被覆盖，不能证明未知情况都被覆盖。“传什么、做什么、在什么状态下”这一划分给出的是理论上的完备性，实际能不能找到，取决于各方面的分析能否实现。
- 15条构建与工具链问题在范围之外。构建矩阵编译能发现其中的编译、链接错误，但vDSO编译选项一类的问题，编译通过了也发现不了。
- JIT生成的代码（BPF相关11条）和汇编（跳板、入口代码）是静态分析的难点，目前只能整体报出。
