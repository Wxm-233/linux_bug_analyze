## 一、astra 的要点

1. **根本原因在候选生成之前**：九个引擎大多从一组已知操作出发（页表访问器、阶数宏、64 位表达式、弱定义的效果调用……），只能找“已知操作用错”。分析器没有一份**独立于代码差异的“使用约定”**作输入，所以判定不了另一种错误。比如“32 位调用者传进来的数组，元素步长是多少”“运行时才确定的能力”，在现有引擎里都变不成可比较的值。多加调用深度、多加 typedef 都解决不了。第二个瓶颈是事实能否正确关联到对象、路径和生效的构建：规则 A 第二版追参数，新对位 0，却多出 580 条误报。
2. **构建覆盖是前提，但不能折算成召回**：缺构建的 9 例补齐构建，也不会自动长出规则。
3. **对“合并漏报、补全规则”**：同意合并，但**按“同一对象、同一种使用约定、取得约定的证据、可复用的反证”四项合并**，不按表面形态。判定“错”的方式不同就拆开。先只批两天做样本和证据盘点，过线才实现。
   - **第一顺位：类型一致性中的“兼容 ABI 元素宽度”**。例子是 `move_pages`：32 位程序交给 64 位内核一个指针数组，约定的元素宽度和内核取元素的步长不一致。登记表里只有 1 例，但它的好处是遮住补丁也能从“接口约定”和“编译后的类型”分别读出两个数，独立判断是否相等。
   - 第二顺位：实现一致性中的“运行时能力前置条件”（hugetlb、secretmem、CPPC，3 例）。三例需要的证据并不相同；规则 B 已经在这一类上独立 1/10。
   - 暂缓：指令可见性、KASAN 清零、SIMD、原子区睡眠，以及其余 5 种单例形态。另外 7 例（并发、运行时硬件、间接分派、修复才引入的钩子）目前没有静态见证。
4. **计划（8～10 个工作日）**：
   - 第 1～2 天，**供给盘点**：独立评分者从本地 git 历史建 compat/ABI 修复池，分设计侧和后期侧，并备好合法对照。过线条件：设计侧 ≥ 3 个根因、≥ 2 个接口族、≥ 6 个合法对照；后期侧 ≥ 5 个根因、≥ 2 个接口族，其中至少 1 族没参与设计。不过线就结束，只交盘点。
   - 第 3～5 天，**做一个按构建解释类型的小检查**：从系统调用入口表找兼容入口和本机入口，追到共同消费同一用户数组的函数。一边从 ABI 布局或兼容类型取“约定宽度”，一边从生效翻译单元的类型、读取和下标取“实际宽度和步长”，两个数不能由同一处强转推出。用编译器类型信息和基本块判断兼容路径能否到达；读不到就记未知。
   - 第 6～7 天，冻结后由评分者一次回放，和九项基线、简单对照比较。继续线：后期集比九项基线净增 ≥ 2 个严格命中的根因、覆盖 ≥ 2 个接口族；10 个合法对照至多误报 1 个。

## 二、我的方案

### 采纳 astra 的诊断和合并原则

它说中了我们一直没讲清的一点：**现有检查是“已知操作 → 找用错的地方”，没有“接口约定”这一侧的输入**。所以每补一条规则只能覆盖一种操作，对没见过的缺陷召回为 0。用户提的“合并漏报补规则”方向是对的，但要按“约定”合并，不按表面形态。

### 第 1 步（约 2 天）：compat ABI 元素宽度的供给盘点

照 astra 的第 1～2 天做，调整三处：

- **调整 1：独立评分者用 Codex**。我写判据和取样规则，Codex 按规则从本地 git 历史建池、标注、分设计侧和后期侧；我只看设计侧，后期侧只看数量和哈希。这和 effsupply 那一轮的做法一样。
- **调整 2：取样规则写成可机械执行的**。在 git 历史里找改过 `compat_*`、`in_compat_syscall`、`compat_ptr`、`COMPAT_SYSCALL_DEFINE`、`get_compat_*`/`put_compat_*` 的修复提交（带 `Fixes:` 或明确修复描述），再由 Codex 人工标注是否属于“共享入口下数组元素宽度或步长不一致”。不用新检查的报警来选样。
- **调整 3：先查独立性**：去掉分析集、封存集、晚期 4 例和设计样本里已有的提交（由 Codex 核对，我只看重合数量）。

门槛照 astra：设计侧 ≥ 3 个根因、≥ 2 个接口族、≥ 6 个合法对照；后期侧 ≥ 5 个根因、≥ 2 个接口族，至少 1 族没参与设计。**不过线就停**，只交盘点，这也是结论（说明这一类在历史上太少，不值得专门写检查）。

### 第 2 步（过线才做，约 3 天）：兼容 ABI 宽度检查

照 astra 的第 3～5 天做。我补充三点：

- **类型信息来源**：用 clang 对相关翻译单元输出 JSON 格式的语法树，取类型和下标表达式。不建全内核中间表示，只解析入口能到达的那几个文件。
- **构建**：三个 defconfig 都开了 `CONFIG_COMPAT`（x86_64 还开了 `IA32_EMULATION`；arm64 是 aarch32 兼容，riscv 是 rv32 兼容，已在 v7.4-rc3 的 `.config` 核对），现有构建可以直接用。历史回放每个父树最多补两组构建，超出预算的记未知。
- 实现前先抽查 clang 语法树在宏展开后的调用位置、类型和步长是否保真；读不到类型就降为未知。
