# N2.13：把公共条件接到编译器明确的控制范围

2026-10-19。接续N2.12，仍是同一项已读调度拓扑案例的开发补证，不是新增两个架构案例或独立检测。范围与命令见`protocol_pre.json`、`command_plan.json`；取证经过`plan_review.md`和`execution_review.md`核对。

## 取得了什么

复用非观测的历史配置、精确core.i、已安装GCC及N2.11最终参数，只重定位三个输出并增加CFG转储。s390一次39.679秒、x86一次33.815秒，均exit0；每配置六项旧保护路径未变。只生成新汇编和转储，没有重新生成.i、完整内核构建、启动或付费模型调用。s390原有头文件警告保留，x86 stderr为空。

两份portable consumer record保留完整函数头、循环和successor表、正文及源码位置。各22个实际基本块，控制后继表相同；GCC的Loop0是根区域，不能将“3 loops”算成三个源码循环。原始全单元转储留在被忽略的`raw/`中，record和binding可携带；源文件、dump行、基本块号分别记录。

## 程序化结果与检查

新增`linux_bug_analyze/gimple_cfg_facts.py`按实际GCC格式解析metadata、块、显式分支和循环；边只来自successor表，极性须与正文目标一致。循环分支控制仅采用本次判断到首次共同块的单后继前缀，不把下一次迭代可达写入当成本次条件控制。未知call/asm效果保留；支持范围见`method_notes.md`。

14项新方法测试、15项原局部方法回归共29项通过。复核补齐了两类跨表示歧义：旧记录缺少可比discriminator标记，以及两个旧事件对应一个新事件，均不算精确绑定。方法审查完成后才运行两份已读真实输入；测试记录保存当时代码SHA，方法说明随后落盘，**没有另行生成事前方法基线，不称独立冻结评估**，不回填或重跑原输出。

两配置均得到22块、32条正常边、10个显式条件分支。每份63个旧事件可双向唯一对应，原37条局部依赖中25条的两端都能落到同一真实基本块，包括两条关键字段读取→比较关系；这是语法来源关系的块定位，不是值/别名证明。s390另有116个旧事件不足（89项缺支持形状/精确位置、27项discriminator不可比）；x86为119项（89＋30），不足不是新错误数。

程序自动列出了搜索命中边的循环出口与赋值、唯一目标条件store及诊断asm分支的正常汇合。诊断分支在旧表示中的discriminator不可比，故该旧事件不强接，直接使用新CFG的自身结构；builtin值关系仍未知。程序结果见`program_results.json`，25条已绑定局部边及分母见`results_summary.json`；没有改动N2.12事实或比较结果。

## 三段关系及其含义

|问题|编译器显示的正常控制|能支持的限定解释|仍未证明|
|---|---|---|---|
|候选比较到见证和搜索退出|bb9真→bb10赋值→bb12；假→bb11继续迭代|命中一个合适候选后选见证并离开搜索；不是先证明所有成员均正确|实际存在候选、迭代集合与对象身份|
|目标条件到字段写入|bb17真→bb18写→bb19；假直接bb19|本次目标条件控制这次写入；其他成员绕过写入仍接受后续检查|跨CPU地址/alias、实际写入与可见性|
|后续读取和诊断继续|bb19分支真→bb20诊断asm→bb21，假直接bb21，再到bb22迭代|诊断块有正常继续边，不能套成直接return模型|expect值摘要、asm/call必返回、运行路径可满足|

完整源码与真实记录核对见`actual_source_review.md`。最后一项保持两段证据：字段读取→比较、builtin返回临时量→诊断分支；本轮不把未知调用结果补成“字段不一致必诊断”的自动链。CFG尾部物化void return也不回填旧GIMPLE事件数。

## 与跨架构研究的关系

本轮检查的是同一公共消费者，公共控制结构对应本身不能说明哪种架构违反要求。它补齐的是：接口消费者究竟在哪条分支、对哪个候选和哪次写入提出要求。后续才能用这些条件约束架构侧的准备效果，避免把“更新函数在前面”或“所有成员都应先写过”当成充分依据。

既有10/13带观察运行中，旧s390在首次消费得到空集合，修复s390与两版x86包含当前CPU；这是历史运行证据，**不是本轮新增运行，也不是当前非观测CFG已经自动绑定的状态**。见[历史对照](../s390_arch_contract_20261013/runtime/README.md)。已有提供者分析还表明，准备资格被拒绝时可能复制空集合，资格通过且非HW时才在显式前提下形成单目标集合；其前提仍未自动求真。见[提供者条件效果](../preparation_effects_20261017/README.md)。

尤其不能从本函数单独推出“所有成员在入口前均准备完成”或完整的“mask必须包含当前CPU”契约。前者混淆搜索见证与后续检查；后者还需要首次锁消费、对象和阶段依据。正常CFG不解决别名、准备资格或并发稳定性。
