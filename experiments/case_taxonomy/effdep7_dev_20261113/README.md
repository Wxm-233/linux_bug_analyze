## 纵向信号这三轮（effdep5～7）的总体判断

1. **能复现师兄的例子，清单也足够短。** X1 一直排第 1；每棵树的候选从几百上千条（横向比对）压到了 2～7 条，专家几分钟就能看完。人工建议里写出的依赖性质（“page 发布前必须已清零”）也符合师兄新结论的要求。
2. **但除 X1 外，还没有找到第二个例子。** 当前版本最后剩下的 6 条全是普通控制流；中间找到的唯一一条真实依赖（`pte_modify` 保留 uffd 位），被“同一资源”条件筛掉了。效果过滤和同一资源这两条规则，都是在 X1 和当前版本上看着设计的，只能说明它们不会伤到 X1，说明不了它们能抓到别的缺陷。
3. **这种缺陷本身少见。** “公共层相信架构接口已经产生效果、于是跳过自己的工作”在当前版本里本来就不多；一旦出问题，往往很快被修掉。要检验召回率，需要更多这种形态的历史样本，而我们 120 条开发集里只有 X1 这一条是这种形态。

## 下一步建议（还没做）

1. **扩样本，检验召回。** 在内核历史中按修复补丁的形态机械地筛出更多“公共层跳过自己工作”类的修复。例如修复补丁删掉了“调用某个架构接口后把开关变量设为常量”这样的语句，或者把它改成了用返回值决定是否跳过（X1 的修法就是这样）。对每个修复的父提交跑纵向信号，看能否命中。这需要每个样本做一次部分构建，约 10～14 分钟。
2. **上下文对象不算资源。** 在函数里传给大多数调用的变量（如 `env`、`desc`）不计入共享资源。这只改分析脚本。
3. **字段级的资源关系。** 像 `pte` 存进 `vmf->orig_pte` 这种经由字段的联系，需要抽取器记录赋值去向，才能让 `pte_modify` 那类依赖不被误删。
