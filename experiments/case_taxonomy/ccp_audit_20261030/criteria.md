# 约定变化跟进：30对抽检（判据，抽样与标注前写定）

承接`ccp_feasibility_20261030/`：新样本238对的全部候选覆盖为45%，略低于50%的判据，且漏覆盖集中在“T的改动不含C接口名”的一半。本轮抽检用来回答：这些配对中，有多少是真正的“使用方没跟进C的约定”；在真实例中，候选覆盖是多少；没覆盖到的原因是什么。不调用模型。

## 抽样

- 对象：`ccp_feasibility_20261030/ccp_pool.json`中与已有兄弟数据集不共用提交的238对。
- 方法：按(C, T)哈希排序后，用`random.Random(20261030)`打乱，取前30对。
- 被抽到的30对从此转为已接触。

## 标注（盲于覆盖结果）

标注者为Claude，只读C与T的标题、说明和`.c/.h`差异，以及T的目标函数；标注时不看任何覆盖、排名或候选池信息。结果写入`audit_30.json`并记录SHA，之后才读取覆盖结果。

`follow_up`（T是否属于“使用方没跟进C的约定”）：

| 取值 | 标准 |
| --- | --- |
| `yes` | C改变了公共层约定（改名、改签名、新增必须设置的字段或状态、新增断言或使用要求、删除钩子等），T在C没改过的架构里，把某个使用方改为符合这一新约定 |
| `partial` | T与C的约定改变有关，但不是直接跟进；例如为满足新约定而做了别的调整，或修的是新约定带来的间接后果 |
| `no` | T修的是C带来的另一类问题（逻辑错误、性能问题等），或与C的约定改变无关；也包括C本身不是约定改变的情况 |

同时记一个`contract_kind`（重命名/签名、新增必须字段或状态、新增断言或锁要求、删除或替换钩子、语义或行为改变、其他），以及一句理由。

## 计算（标注SHA记录之后）

1. `yes`、`partial`、`no`的数量与比例。
2. 在`yes`中，全部候选、前50与前20的覆盖率，以及候选池大小；同时报告`partial`与`no`的对应数字作为对照。
3. 对`yes`中没被全部候选覆盖的对，逐个记录漏覆盖原因。可能的原因包括：T改动的位置不含C的任何接口名（约定是语义上的）；接口名因全树出现文件过多被过滤；C没有可用的接口标识符；目标所在文件不在候选范围内；其他。这一步在看到覆盖结果之后进行，属于事后分析。

## 解读规则（描述性，样本只有30对）

- 如果`yes`占比低，而`yes`中的覆盖明显高于45%：说明整体覆盖不足主要来自配对噪声，后续方法登记时应先做配对过滤或人工确认。
- 如果`yes`中的覆盖仍明显低于50%：说明仅靠接口名生成候选不够，需要按漏覆盖原因补充候选来源，再考虑方法登记。
