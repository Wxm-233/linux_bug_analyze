## 改进了什么

| 编号 | 改进 | 针对的问题 |
| --- | --- | --- |
| I1 | 锁、关中断、陷入入口、可插桩区间都**按分支跟踪**。对每个调用，只看同一分支或外层分支上更早的获取和释放 | A122漏报：提前返回分支里的unlock截断了区间 |
| I2 | 跨核调用的`_async`版本不算违规 | 关中断时调用异步版本是允许的 |
| I3 | **按问题合并**：同一规则、同一违规操作、同一最终函数算一个问题 | `die()`一个问题被重复标出9次 |
| I4 | R10不标记桩函数，也不标记在RISC-V上不会启用的配置功能 | 误报多是“RISC-V还没实现这个功能” |
| I5 | R7只看客体可控（KVM）和用户可控（ptrace、信号、系统调用等）的地方，并排除所有调用点都传常量的下标 | kgdb、KVM内部常量等误报 |
| 修订1 | 可插桩区间的开始和结束，也认在`__always_inline`辅助函数内部完成的情况 | A068漏报：`ct_cpuidle_enter()`内部调用`instrumentation_end()` |
| 修订1b | 评分时函数范围包括签名行 | A068的修复改的是签名行 |

### 评估窗口`v6.1`（只算一次）

| 规则 | 标记 | 问题 | 位置命中 | 原因一致的命中 |
| --- | ---: | ---: | --- | ---: |
| CTX | 5 | 4 | 2：`130aee3fd998`、`0b1d60d6dd9e` | **0** |
| R7 | 0 | 0 | — | 0 |
| R10 | 0 | 0 | — | 0 |

- **两个位置命中，原因都不一致**：
  - `130aee3fd998`修的是`die()`用`spin_unlock_irq`会意外重新开中断，而规则说的是在`die_lock`区间里可能睡眠；
  - `0b1d60d6dd9e`修的是`cpu_relax`里的静态分支导致`-Os`编译失败，而规则说的是noinstr约定。
- **4个问题的人工核对**：
  - (a) 2个：`machine_shutdown`，本项目已确认；`arch_cpu_idle`缺noinstr，上游2024-03修复，在窗口之外；
  - (b) 1个：`die()`中的`console_lock`；
  - (c) 1个：`cpu_relax`。
- **参考统计**：标记函数在窗口内被修过的2/4，未标记函数的抽样中是31/200，Fisher p=0.12。

**按判据判定**：
- 原因一致的命中为0个，要求不少于3个，**未达到**；
- 问题中(a)类占50%，要求不低于30%，满足。
- 两条须同时满足，所以**本轮未达到成功标准**。

## 为什么在新窗口上几乎没有结果（事后分析）

1. **`v6.1`时，这些规则针对的代码大多还不存在。**
   - R7的检查点是KVM的AIA中断控制器、PMU和ONE_REG扩展，在`v6.1`时还没有或很简单，所以没有标记。
   - R10在`v6.1`上也没有满足条件的钩子。
2. **陷入入口规则依赖入口框架。** RISC-V在`v6.6`之前没有用通用入口框架，旧的`entry.S`会在调用C处理函数之前按情况开中断，所以“陷入处理时中断关闭”在`v6.1`上并不成立。检查器在`v6.1`上没有标出陷入类问题，这本身是对的；但这说明，CTX在`v6.12`窗口上命中的A118、A158、A175等，都属于“改用通用入口框架之后才出现”的一批缺陷。
3. **规则是从近两年的缺陷中总结出来的，对更早的代码覆盖有限。** 两年前的RISC-V修复，多数属于其他类型，例如编译错误、早期启动、页表细节，不在这三条规则的范围内。

## 结论

- 按判据，**第2版规则在新窗口`v6.1`上未达到成功标准**：没有原因一致的命中，标记也很少，只有4个问题，其中2个是真问题。
- 改进本身在调试窗口上是有效的：
  - 按分支跟踪抓到了A122和A068；
  - 按行范围对应补上了A158；
  - `v6.12`窗口的M5命中从2/6提到4/6。
  
  但这两个窗口用于调试，不能作为证据。
- **对研究的启示**：
  - 这些规则检查的是**特定时期的代码结构**，例如通用入口框架、KVM AIA。它们能有效发现“同一批结构”中的同类问题：`die()`、未对齐陷入、APLIC、PMU都是成批出现的。但对更早的代码，没有可检查的对象。
  - 要可靠地评估“规则能否提前发现缺陷”，评估窗口应该紧接在规则所依据的代码结构出现之后，而不是更早。目前样本集中，这样的窗口都已经用来调试过了。
- 下一步的可选方向（未执行）：
  - 等`df2908090cda`之后的新修复出现后，在当前代码上做真正“向前”的评估：现在就把第2版规则在终点版本上的标记冻结下来，之后看哪些被修；
  - 或者把规则用到其他与RISC-V代码结构相近的架构上（如LoongArch），看能否发现同类问题。
