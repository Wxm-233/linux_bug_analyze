# 配置局部开发的机制收束建议

2026-10-11。独立机制审阅；仅根据指定综合报告、接口矩阵、老师问题路线和当前代办提出建议。未独立核对 Git、Linux 源码、真实配置或硬件，未运行模型或配置实验。本文件是机制层建议，不是覆盖对照结果审计。

## 1. 建议保留的共用检查

将本轮机制写为一条带证据门控的义务：

> 在同一接口、版本、架构、配置和模式下，经独立核实且适用的环境要求，应在要求传递及合法合并后被保留，并在首次真实消费前由有效状态满足。

必须分别记录三个对象：环境要求 `E`、合并后的请求 `R`、实际供消费的状态 `S`。`R` 与 `S` 一致，并不能证明 `R` 覆盖了 `E`。也不能从“一个默认值被覆盖”直接推导违反了 `E`。

完整候选至少有三项：

1. **环境依据及适用性**：要求来自适用的规范、格式、ABI、消费者约束或实现声明；记录版本、模式、配置和路径。依据存在不等于已获得领域裁定。
2. **要求传递**：在提供、解析、合并和覆盖后，核实必须保留的要求仍在有效请求中。合法覆盖和遗漏硬性要求应分开。
3. **首次消费满足**：有效配置或状态在实际消费前满足要求；路径未进入、构建/核验失败、实际状态未知都不计成功。

三项是检查义务与证据字段，可以共用；不是一条已实现的通用源码分析器，更不是新增第五类 Pattern。

## 2. 默认值、用户选择、硬性要求的区别

| 对象 | 本轮可据材料陈述 | 不能自动推出的结论 |
| --- | --- | --- |
| 架构默认 | KUnit 架构配置提供初始条目，同版合并按键覆盖，基础请求可覆盖默认。 | 架构默认一定是平台不可违反的要求；覆盖就是缺陷。 |
| 用户选择 | 用户条目改变最终请求；六组以内的对照可验证保存函数的合并与匹配行为。 | 改变合法/非法；用户选择已被真实 Kconfig 接受，或已在内核启动中生效。 |
| 硬性环境要求 | 只有经核实、适用且有来源的约束才能作为“必须保留”的条件。 | 因架构名、端序符号名、提交增加一行，或合成结果更符合预期，就认定硬性要求。 |

若硬性要求与用户选择冲突，需先裁定接口是否允许该选择，以及是否应拒绝、保留、转换或另选模式。当前材料不足以替接口选择统一政策。多用户文件的冲突检查，不能迁移成“架构默认也不可覆盖”的证据。

## 3. 源例支持什么、不支持什么

| 源例 | 支持的机制 | 证据边界 |
| --- | --- | --- |
| I3C 配置谓词局部投影 | 回读正确反映请求执行，仍可能与注入 CPU 属性不符；选择依据与执行核验必须分开。 | 同版 Kconfig 支持 CPU 属性的含义；人工 autoconf、寄存器模型和 wrapper 末尾不证明真实配置、硬件支持或完整初始化成功。实际 PIO/DMA 首个消费者未确认。 |
| 有限 C 候选提取器 | 可自动保存受支持配置 guard、同载体/寄存器/mask 操作、词法顺序和复核位置；没有模式操作时模板不适用。 | 人工目录提供属性—模式关联；共现不证明 CFG、数据流或设备契约。三项已读/合成输入不是检测准确率。 |
| KUnit 配置消费链 | 已写入的正向请求可通过真实解析/子集匹配核验；父版不写该条约束，就可接受三种合成状态。 | 六组空基础请求仅说明请求完整性边界。父版接受小端/缺符号不证明历史内核如此；提交版请求不证明最终生效。`validate_config()` 是配置复核位置，本轮未确认它就是模式的真实首个消费者。 |
| KUnit 用户覆盖边界 | 静态合并链支持检查最终请求的来源和变化；覆盖对照能够补足空基础请求的行为缺口。 | 对照只能证明合并函数行为。无适用权威时输出“请求变化/依据待复核”，不能判“违背平台要求”。构建/启动、独立新输入检测仍未完成。 |
| 八项接口矩阵 | 首次消费时状态就绪、边界处可表示、按真实能力导出，都可纳入有条件的依据—传递—满足卡。 | 每例对象、单位、生命周期和权威来源不同，不能直接共享正则或跨接口强制断言。原型证据层级不能相加。 |

迁移范围阶段对 Python 输入为不适用，对另一输入为材料不足；候选数是 `null`，未运行检测，不能解释成零命中、漏检或正常通过。

## 4. 与 P1–P4 的关系

按当前代办中的代表例，P1 是 shmem 大页边界，P2 是磁盘/协议等表示关系，P3 是 s390/Btrfs 首次使用顺序，P4 是 die 导出/VT-d 模式能力。

- **P2/P4 是本轮直接交接点**：环境属性决定模式/表示，执行成功仍可能依据不足或请求不完整。
- **P3 提供检查放置原则**：应落在实际首次消费前，不能只在局部函数结束检查最终状态。本轮没有新增真实消费时序验证。
- **P1 可复用证据卡结构**：要求、对象、单位和允许范围都要明确；本轮配置覆盖未展示新的数值范围机制。

因此保留四类框架，将这一机制作为检查的共同前提和 P2/P4 交接说明。不得声称已用配置例验证所有四类，或认为名称相似就能复用同一实现。

## 5. 自动提取与人工裁定的边界

| 可自动提取/执行的有限部分 | 仍需人工或领域裁定的部分 |
| --- | --- |
| 受支持的配置字面量、条目、guard、同版局部声明及文件行号。 | 接口实际要求、适用环境、支持模式与权威证据的语义。 |
| 保存函数的解析、按键合并和子集匹配；记录每次覆盖的来源与最终值。 | 默认与硬性要求的区别、覆盖优先级是否合法、冲突应如何处理。 |
| 有限操作链的共现和词法顺序；已经提供的事实对候选蕴含式的分类。 | 完整跨文件因果链、CFG/数据流、真正首个消费者及可靠检查位置。 |
| 原文及身份一致性、未知字段和拒判原因。 | 实际生成配置可达性、真实运行路径、硬件/ABI符合性与正式纳入。 |

“机器已抽出一条声明”和“声明足以约束接口”必须用两个字段。补丁改动位置、局部对照、模型意见都不能代替权威裁定。

推荐机制卡明确区分：`architecture_default`、`user_request`、`authoritative_requirement`、`effective_request`、`observed_state`、`validation_position`、`first_real_consumer`。最后两个字段不得合并；未知者保持 `unknown`。

建议判断状态保留：`not_applicable`、`insufficient`、`request_changed`、`requested_requirement_rejected`、`candidate_requirement_lost`。只有经核实硬性要求、完整适用条件和真实消费证据齐备后，才讨论消费契约违例；局部验证拒绝错误配置也不能直接计作新缺陷。

## 6. 一个真正有限的下一项

完成至多六组覆盖对照及机制卡后，停止 I3C/KUnit 局部网格开发。下一项固定为 **D3：NUMA native/compat 的单接口权威争议包**，先使用已有材料，限定两个入口和两个已有冲突主张，不运行新网格、不扩标题池。

一次完成：列出适用 ABI 文本、已保存的入口/实测证据及各自版本；核对它们是否描述同一对象和长度边界；形成一张“明确依据/暂定/冲突”的裁定卡和一个待领域确认的问题。确切运行内核源码或适用 ABI 仍缺时，写明 `insufficient` 并结束该有界任务，不能用更多局部输入消除权威缺口。本建议只要求形成审阅包，不授权向外部人员发送消息，也不要求将 D3 整体勾选。

这一步直接推进老师第二个问题：以接口、版本、模式和消费者约束为准；保留冲突证据，不以多数架构或补丁侧投票。独立同机制的自动提取验证仍另列 D2 待办，不能以本项代替。

## 7. 收尾必须保持的口径

原 12 条仍为 6 条源码确认、5 条核心范围外、1 条条件兼容。新增确认和独立同机制阳性仍为 0。九项旧原型、八项机制矩阵、配置网格和已有目的性选例不能相加为缺陷总数。首次发现日期仍缺，两个目标时间间隔不得用代码来源/主线修复跨度替代。D2 整体泛化、D3 完整裁定、C1–C4 专家纳入及时间、D4/NUMA均未完成。
