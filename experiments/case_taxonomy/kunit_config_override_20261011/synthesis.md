# 配置覆盖边界：请求满足不等于环境要求完整

2026-10-11。本轮完成六项非空用户请求的离线覆盖对照，收束I3C/KUnit配置局部开发。没有新增Git源物，没有构建或运行内核。

## 实验结果

六项与事前源码预期一致，78个适配字段核对通过。4项请求满足、2项不满足；两处同名异值产生覆盖合法性复核候选，**不是两项缺陷**。无冲突也不表示环境正确。六个记录是同一例的合成对照，不是六个独立样本。

结果说明：基础请求覆盖架构默认后，既有核验按最终请求检查，不再保证原默认被保留。该优先级是否正确，需要核实目标环境允许的模式。我们尚未取得“此环境必须保持y且禁止用户选择n”的完整权威证据，不能将覆盖判为错误。

`conflicting_options()`是本轮wrapper增加的诊断调用；真实历史`make_arch_config()`只解析和合并，没有在该处先拒绝冲突。本轮没有修改该流程，也没有新增实际门禁。合成输出不是生成的`.config`，不证明Kconfig可达、真实端序或启动结果。

## 共性机制的收束

将三个对象分开：经核实且适用的环境要求E、合并后的有效请求R、实际供消费的状态S。

- I3C的回读确认模式操作结果，不确认选择依据；宏注入和寄存器模型也不确认真实配置或设备契约。
- KUnit的子集核验能确认已写请求被满足，不能补出遗漏的环境要求；本轮进一步说明，核验的对象会随覆盖后的请求变化。
- 因此，检查候选应分别定位依据、要求传递与实际消费。`R`被`S`满足，不足以推出`R`完整保留了`E`。

这属于P2数据表示与P4能力/模式的交接说明。P3提供“在真正消费前检查”的放置原则；P1可复用要求、对象和单位的证据结构。本轮不增加第五类Pattern，也未用配置例验证全部四类。

程序可提取受支持的配置字面量和条目、记录按键覆盖及最终值、运行已提供请求的匹配。真实环境要求、覆盖政策、跨文件链和首个真实消费者仍需人工或领域裁定。源文件行号和局部复核位置不能直接当成实际检查插入点。详见[机制卡](mechanism_card.md)及其结构化记录。
