# N2.9：消费条件抽取原型及未通过的独立挑战

日期：2026-10-18。**本轮完成了限定原型、独立参考和实际评价，但独立挑战没有通过；真实Linux消费条件仍未自动抽取。** 原方法、源码、预期与失败记录保持原样，没有删注释、改写源码或针对挑战修规则后追补成绩。

## 研究目的与实现

上一轮模型曾将“找到一名合适成员”扩张为“所有成员此前都已准备”，程序只核对引用和词法顺序，未发现这种语义过推。本轮尝试从公共消费者的搜索、更新和检查中直接提取条件，区分找到首个成员的条件、更新之后实际抵达的逐成员检查，以及单成员提前返回。这是N1架构准备义务与N2对照条件的一个组件，不是通用C解释器，也尚未连接架构提供者或证明接口义务。

新增 `linux_bug_analyze/consumer_obligations.py`：从完整普通C函数的AST得到受限IR，保留分支、首个匹配、break/continue、写入及检查顺序；有限执行对未初始化、越界和未知效果返回不足。仅支持局部整数、固定小数组及限定循环结构，无指针、外部调用、GNU表达式。返回值和分支名称保持中性，不由正负返回码判定系统是否出错。

冻结前15项开发测试通过，包括存在与全称的区别、先写后检查、首个匹配后退出、单成员/空域、continue限制检查域、重命名及不足处理。这些是方法开发测试，不是Linux案例或独立准确率。初轮11项记录也保留。冻结身份见 `method_baseline.json`，支持边界见 `method_notes.md`。

## 独立参考与实际结果

独立角色在未读实现及输出的条件下编写合成C源和Python顺序参考；冻结后才向实现者揭示。这里的“独立”指组件开发角色隔离，不是新Linux问题或人类专家裁定。冻结记录中 `Human-authored` 的措辞实际指助手手工编写、非由提取器生成，**不能解释为人类专家编写或金标准**。

| 统计项 | 实际结果 | 含义 |
| --- | --- | --- |
| 开发测试 | 15项通过 | 只覆盖已公开开发形状 |
| 独立合成源码 | 9份：7份预期支持、2份预期不足 | 各种源码形式，不是9个缺陷 |
| 基础有限域 | 3888条枚举记录，1296组去重输入 | 三成员集合、目标、关系和遍历顺序；不代表案例数量 |
| 原生C/Python返回值对照 | 含源码变体共2754次，一致 | 仅校验参考侧返回值；见证、最终数组和轨迹来自Python，未由原生C观测 |
| 提取器支持覆盖 | 预期支持7份中实际提取0份 | 全部停在源码解析层 |

九份挑战源码的实际首因一致：合法C注释直接传入 `pycparser.CParser`，而该入口要求注释已处理，因而在第1行停止。两份负对照也被相同前置错误挡住，未实测可变循环边界及while的专门拒判能力。

只读源码诊断还发现循环内局部声明、循环中累计标志后统一返回、先检查后更新等形状与当前模板不符。这些是**未越过首个解析错误的静态缺口**，不是另一次执行结果。不能据此断言修好注释后即能通过，也未这样修后重跑。

## 与跨架构研究的关系及当前边界

有限条件抽取要回答的是：公共代码究竟要求一个见证、每个实际使用对象的关系，还是某个特定分支下的状态；再将它与不同架构的准备资格和时机对齐。合成输入暂不包含CPU架构差异，故本轮没有证明新的跨架构契约、跨架构逃逸检测、端到端收益或泛化能力。真实Linux原文还未打通，旧历史运行证据也未冒充新自动提取结果。

新付费模型调用、新Git源码获取、新预处理、内核构建、内核运行和确认缺陷均为0；仅编译运行了合成C参考。正式独立同机制正例/同用途正常仍为0/0；N1/N2、R5/R6整体未完成，R3继续暂缓。
