# 判据：三处改动合并运行（merge_dev_20261111）

2026-11-11，Claude 在生成用例和运行之前写定，SHA 存入 `criteria_sha256.txt`。对应 `汇报/2026-11-11/下一步规划.md` 的 0.4、0.5（用户同意先做完阶段零）。

## 一、目的

前几轮分别验证了三处改动：接口常数按架构换算（`anyarch`）、上限提示值改成相对值（`relhint`）、易变输出归一化（`stability`）。它们从来没有合在一起跑过。本轮把它们合起来，再加上规划 0.4 的两点调整，看合并之后检出有没有变差、噪声有没有变少。合并后的版本就是准备冻结、拿去跑留出集的方法。

## 二、用例组（写死）

- **G3d**：`diverse_dev_20261110` 的“定向＋提示值”组，原样。作为对照。
- **G3c**（合并版）：由 G3d 派生，预算相同（3 个种子各 1000 个）。
  1. **相对提示值**。G3d 里含“上限提示值”的用例，用以“组名/rel/用例编号”为种子的随机数决定：一半保持原样，一半换成相对版本（与 `relhint` 轮同一枚硬币，所以被选中的原用例与那一轮相同，另外多出只含第二种写法的用例）。与 `relhint` 轮相比有两点调整（规划 0.4）：
     - 相对值只用“能映射的最高地址”一种（`mmap_top`），不再用“指针检查上限”；
     - 第二种写法的提示值也换：`o:*:52`（缓冲区地址或上第 52 位，52 来自 arm64 的 2^52）换成 `o:*:b`，b 是使 2^b 不小于该内核 `mmap_top` 的最小整数。
     上限提示值的定义：整数参数等于 s − 1、s、s + 1（s 的取法同 `relhint` 判据第二节），或参数是 `o:*:52`。
  2. **接口常数换算**。对 G3c 的全部用例，按 `anyarch` 轮确认的两处（`openat` 的 flags、`pipe2` 的 flags）做按架构换算。换算表只在当前版本上算过；这四个打开文件标志的取值多年未变，本轮直接用于五个样本组的旧版本内核，这一点没有另行验证，如实注明。
- 相对值按内核取（`rtprobe_dev_20261110/probes.json`），所以每个内核一份清单。

## 三、运行与判定（写死）

- 每组的清单 = G3d 与 G3c 用到的全部用例（去重），同一批运行。6 组、23 个内核各 3 次。
- 工具全部用默认工具 `difftest_tools_20261111`：`run.sh`（显示内核警告）、`compare.py`（归一化、超时单独成类）、`score.py`、`warnings.py`。易变清单沿用 `stability_dev_20261111/volatile.json`（本轮的用例只是把已有用例的个别参数换了值，系统调用和输出槽位没有变）。
- 人工确认：原有用例沿用 `relhint_dev_20261110/confirm.json`（它包含 `diverse` 轮的全部结论）。**新出现的、构成检出而尚无结论的用例，由我逐个确认并写明理由**，写入本轮的 `confirm.json`。

## 四、要报告的数字

1. G3d 与 G3c 的确认合计、每条缺陷在几个种子中检出、至少 2 个种子检出的缺陷条数。
2. 当前版本上两组三个方向“与众不同”的用例数和簇数。
3. 被换成相对版本的用例数（两种写法分别计）、被常数换算改动的用例数。
4. 内核警告：有没有。

## 五、参考线（事先写下）

- **合并版可以作为冻结的方法**：G3c 的确认合计不低于 G3d 减 1，覆盖的缺陷条数不少于 G3d；当前版本上 G3c 三个方向的簇数合计不多于 G3d。
- 否则指出是哪一处改动造成的（必要时拆开重算），不冻结。
- 5 条缺陷、3 个种子，1 分以内的差别不作结论。
