本目录以 `analysis_out/stratified-20260921/manifest.json` 的 500 条固定样本为选例池。`pilot_500_20260926.tsv` 在源码复核前冻结 12 条**目的性样本**，覆盖不同优先级分层、表示/能力/几何/生命周期线索及多个子系统。短判定的 `related`/`uncertain` 仅记录选例背景，不是人工确认标签；该组不能用来估计总体相关率。

每项案例以独立缺陷因果链为计数单位。复核先读提交说明和补丁，再追踪接口提供者、消费者及适用配置；只有能说明接口两侧预期及可观察后果时才纳入机制统计。`case_reviews.md` 记录新 12 条的逐项证据与未解决问题。旧九项原型的证据层级见 [`../CONTRACT_MATRIX.md`](../CONTRACT_MATRIX.md)，来源与纳入口径复核见 [`historical_inventory.md`](historical_inventory.md)。九项原型不等于九项已确认、持久修复且在受支持配置可达的缺陷，也不与新选例混成“已完成内核复现”。

2026-09-26 进一步做了七组特化核查：历史 `shmem_is_huge()` 函数的旧/新编译对照、die sysfs 架构宏配置矩阵、x86/qemu-s390x 上的 perf 消费者函数运行、virtio input DMA 布局的旧版/完整修复/不完整修复对照、ARM SMMU 范围命令的编码契约对照、arch_topology 热插拔的历史函数执行，以及 ARM64 Hyper-V CPUHP 状态的源码顺序投影。运行脚本、机器结果与限制见 [`prototype_results.md`](prototype_results.md)。s390 perf 候选因先前测试修复和资源提供条件被改列“条件性兼容改动”；调度 NUMA 案例因缺少架构语义差异证据改列“核心范围外的边界对照”。两者不计独立跨架构缺陷。冻结 12 条现为六条源码确认、五条核心范围外、一条条件性兼容改动。

老师提出的五维字段统一按下列口径记录：触发架构/平台、触发子系统、纵向或横向、**错误引入侧**、引入→发现与发现→修复时间。纵向指公共层与架构/平台实现之间的语义不一致；横向需有“架构 A 的变化→共享行为→架构 B 的回归”证据。修改文件所在侧不自动等于错误引入侧。时间须有可核实的引入提交、发现时间与修复提交日期；仅有 `Fixes:` 时最多计算引入→修复，不能替代两个目标间隔。尤其要区分**代码初现、可触发配置形成与实际发现**，旧代码行的 blame 日期可能只是字段迁移或重构。缺失字段写“待核实”。

下一步在不同机制下尝试自动抽取候选检查条件：从接口定义、提交补丁和调用关系定位生产者与消费者，提取输入范围、表示、能力与状态时点，随后用旧版、完整修复、不完整修复、正常配置四类对照检验。不同架构对接口的理解不一致时，先找 ABI、硬件/架构规范及内核文档中的适用条件；证据冲突保留待领域人员裁定。
