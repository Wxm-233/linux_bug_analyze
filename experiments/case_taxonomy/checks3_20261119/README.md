## 做了什么

规则和引擎一条不改，在外面加一层，按三类检查分组：

| 检查 | 引擎 | 查什么 |
|---|---|---|
| **类型一致性检查** | WT | 32 位架构上的位宽截断 |
| | ORD | 页大小推出的 order 超过页缓存上限 |
| **实现一致性检查** | P1 | 用页表接口前没确认表项在位 |
| | XV | 同上，按各架构编码差异排序、上提到辅助函数 |
| | TLB | 改了页表后该刷 TLB/缓存却没刷 |
| | WK | 覆盖实现在某些路径上跳过了通用实现的工作 |
| | XA | 页表接口的原子性层级不一致；少数架构断言表项在位 |
| **调用上下文检查** | CTX | 原子或关中断上下文里调用了会睡眠、会发 IPI 的架构实现 |

每个引擎“新引入候选”和“对位”的判断，都直接调用这个引擎接入提交级模式那一轮的函数（CTX 是照搬 `ctxeval.score()` 里的那几行）。输出统一为：检查类、引擎、文件、函数、行号、签名。

代码 `checks3.py`：
- `score`：开发集和留出集的分组结果，写 `results.json`，并与各轮存下的结果对照，写 `verify.json`；
- `commit <提交号>`：单个提交的分组报告，缺缓存时调用各引擎自己的入口补跑，写 `commits/<提交号>.json`。

## 结论

1. 三类检查现在在代码和报告里都有了明确的结构：每一类由哪几个引擎组成、各自贡献多少，一目了然。
2. 效果与之前完全一样（1084 组 0 处不一致），没有任何规则被改动。
