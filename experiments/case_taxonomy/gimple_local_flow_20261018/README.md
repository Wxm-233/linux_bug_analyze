## 实现与实际输出

新增 `linux_bug_analyze/gimple_local_flow.py`。状态扫描隔离GCC位置注解、引号、注释和整段多行asm，保留原文区间及来源；`D.123`、`cpu.358_1`作为完整临时名，不把文件路径或asm点号统计为成员。语句分为字段/索引读取、写入、标量赋值、调用、分支、goto、标签、声明、结构及opaque等。

依赖只连接同一直线区域中的定义和使用，每次重赋值产生新版本。label、分支、调用、写入、asm及作用域等边界切断环境；未解决的使用单列。取址操作与值使用分开，不能把 `helper(&flags)` 当作读取flags旧值；调用结果也保持未知，不从未知helper推值等价或内容效果。cast及表达式边仅是语法上的可能依赖，不证明运行时短路读取或值等价。

## 确认的局部联系与边界

两版均恢复了两项关键联系：搜索中的 `rq->core` 读取进入紧接的候选比较；后续 `rq->core` 读取进入与 `core_rq` 的比较。它们来自程序的定义—使用边，不是人工补进结果。程序也保留首个候选赋值之后的显示goto、目标分支及真实标签；这仍不等于自动证明循环存在性、全称要求或条件写入支配关系。

取得掩码指针不等于读取掩码内容；lock/helper体仍未知，不能将可见字段读取称为全局首次实际消费。后续WARN/asm也未被改写为return。调用、per-CPU地址、跨区域同对象、其他writer和稳定性均不足。

## 原始核对与工程后继分别保存

独立角色事前整理20项已读源码事实查询。原冻结比较为 **2匹配、2不匹配、16不足**，见 `source_check_results.json`。其中参照使用 `field_load/field_store/condition/assignment`，实现使用 `load/store/branch/scalar_assign`，词汇未接线使已有事实无法定位；两项不匹配不能解释为方法漏掉store或生成假源码事实。这个交接问题没有在冻结前统一清楚，原结果不回改。

本轮随后在 `schema_bridge/` 单独登记工程后继，只转换已输出事件的类别名称，保留原类别；不增加/删除事件、边、region或源位置，不重跑分析器，不改预期和原比较器规则。该20项已读回放为 **12匹配、8不足、0不匹配**。这是表示接线修正，不能作为独立检出、准确率或方法能力提升；`condition/assignment`的类别含义仅限这份参照，桥接并非任意GIMPLE语义转换器。

剩余8项是两版各4项计数受到全局opaque策略影响：`void unlock = <<< error >>>;` 被保守记录为opaque，因此成员读取总数、调用总数、零return和零假字段查询均未获完整计数认证。即使原事件中已存在12个调用，也未为了追求全通过而修改这条策略。工程桥还不对未来同时含field/indexed元数据的未知packet提供保证；本轮绑定packet没有该形状。

## 研究意义与下一步

本轮将真实源码入口推进到了可程序化核对的局部来源联系，开始为“消费者的条件究竟依赖哪次内容读取”提供依据。尚不能仅凭这些边推导架构准备义务，更不能据两版同用途函数认定运行状态相同或取得新的跨架构检出。

下一N2.13优先取得编译器的明确基本块/控制表示，将局部来源链连接到条件写入、搜索退出和诊断后继续，减少人工按文本顺序补控制关系。再与已有架构提供者的资格、对象及首次消费对齐。具体边界见 `next_step.md`，不继续为了全通过扩格式与opaque处理。
