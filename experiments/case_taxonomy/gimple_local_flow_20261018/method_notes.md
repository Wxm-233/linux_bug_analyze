# N2.12 local GIMPLE facts — developer method

This method exposes partial, source-bound syntax and same-region scalar dependencies from a GCC GIMPLE dump. It does not derive a normative consumer obligation, execute GIMPLE, prove a CFG, solve aliases, or verify a cross-architecture contract. The two existing Linux fragments are known development material; neither event counts nor the independent source-fidelity questions are new defects or a held-out Linux accuracy denominator.

## Interface and coordinates

`analyze_gimple(document)` accepts `id`, `path`, `revision`, and exact `text`. Output includes the SHA-256 of UTF-8 text, document identity, `events`, `dependencies`, `unresolved_uses`, `control_edges`, `barriers`, `unknowns`, and `coverage`. Input file/binding validation belongs to the separately frozen root adapter. This module hashes supplied text; that alone does not certify its provenance or truth.

Status is `partial_local_facts` after lexical segmentation, or `insufficient_lexical_input` if quotes, comments, asm, parentheses, brackets or scopes cannot be delimited. Unsupported well-delimited statements remain visible as `opaque` with raw ranges. No supported suffix facts are emitted after a whole-input lexical failure. A partial status never means complete function coverage or correct behavior.

Each event has `id`, `kind`, `raw`, normalized `code`, `start_offset`, exclusive `end_offset`, inclusive `dump_line_start/end`, `source_locations`, `defines`, `uses`, `region`, and `barrier`. Ranges include leading raw whitespace/annotations/comments associated with the unit. Offsets count Python Unicode characters, not UTF-8 bytes; lines count LF, preserving CRLF characters and tab characters in raw text. `source_locations` holds `{path,line,column}` only for actual GCC `[path:line:column]` annotations on a statement code line. A preceding comment-only annotation or an unannotated label is not assigned an inherited exact location. Annotation text inside opaque asm remains in the raw asm span, not an instruction source claim.

The public kind vocabulary is `function`, `declaration`, `scalar_assign`, `load`, `store`, `call`, `branch`, `goto`, `label`, `return`, `asm`, `scope`, `try`, `finally`, `clobber`, and `opaque`. Dotted GIMPLE temporaries such as `D.123` and `cpu.358_1` are whole identifiers, never member expressions. Pointer-member facts have `field={base,field,access}`; exact array access has `indexed={base,index}`. These facts describe syntax and do not establish pointer target identity or memory validity.

## Bounded local facts

The scalar subset accepts identifiers, decimal/`0B`-style integer tokens and a limited balanced operator grammar. A supported leading cast carries `assignment_kind=cast` and `cast_value_equivalence_proved=false`. Copy/pure/constant classes describe syntax only. Empty expressions, quoted literals, increment/decrement, unknown dereference, nested/indirect calls and unsupported expression forms stay opaque rather than being simplified away.

Labels and exact displayed conditional target pairs/unconditional gotos produce edges with `source_event`, `target_label`, `target_event`, `branch`, `resolution`, and `reachability_proved=false`. An edge resolves only when its displayed label is unique. Adjacency, loop visitation, try/finally reachability, and return of an opaque call are not proved.

Each visible scalar definition has a version within a straight-line region. `dependencies` contain `{use_event,variable,definition_event,definition_version,region}`; only an existing definition in that exact region can bind. An unbound use is `{use_event,variable,region,reason:live_in_or_barrier_cleared}`. Labels, branches, gotos, returns, scopes, try/finally, opaque statements, asm, clobbers, calls, and memory writes clear bindings. A declaration kills a previous same-name binding; it does not establish an initialized value.

Call value arguments can bind to preceding supported scalar definitions. An exact `&identifier` operand is recorded separately in `address_operands`; it does not produce a value-read dependency on that scalar's previous contents. Calls expose their syntactic result in `defines` and `result_unknown=true`, but **this version does not install that result into the new environment**. A later use of a call result remains unresolved, so an argument-to-result or callee-result-to-condition value chain is unsupported. Store uses can bind preceding values, then the memory write clears all scalar bindings. A subsequent textual read of the same field does not prove the same object, unchanged memory, or store dominance.

Asm is scanned as one opaque parenthesized statement, including the existing GCC dump's raw multiline assembler text and internally unescaped quoted assembler directives. It is never parsed for fields, labels, or returns. The scanner requires a balanced detectable terminal, otherwise the input is insufficient. This finite scanner is not a general GCC dump grammar; uncertain forms must remain insufficient. No CPU, runqueue, scheduler, contract, or field name is hardcoded.

## Development record and limits

The first targeted run passed **14 unittest methods**; exact command, output, exit code and module/test hashes are saved in `development_tests_initial.json`. It includes a source-hash-bound extraction of one existing real s390 multiline asm block as a component fixture, not a complete real-input run. Other tests cover source/comment/string contamination, whole GIMPLE identifiers, redefinitions, local read/compare/cast chains, target binding, branch joins, call/store/asm/scope barriers, diagnostics versus return, malformed input, and Unicode/CRLF coordinates. There was no model call, compiler invocation, boot, new Git source, independent-reference read, or complete two-fragment analysis in this developer run.

Before freezing, authority review identified that passing `&identifier` had been counted as reading that scalar's stored value. The correction separates address operands from value uses and adds one targeted method test. The first 14-method record is retained; `development_tests_review_fix.json` records the subsequent **15-method** targeted run and exact revised module/test hashes. This is a pre-freeze method correction, not a change after full-input/reference outcomes.

The next root-controlled evaluation freezes this method/adapter, analyzes the two full exact fragments once, and compares finite independently registered source-fidelity checks. Successful local links still do not establish existential/forall consumer requirements, a globally first content read, architecture-provider readiness, alias equivalence, or an effective new-issue detector. Those remain later research questions.
