## 要注意的地方

1. **很多是同一架构内的差异**：设计侧 19 个根因里，有不少是同一架构的不同 CPU 型号、物理机和虚拟机之间的差异（和 x86 有关的占 11 个：arch/x86 下 8 个，另有两个 Intel 平台驱动和一个 Intel 热管理）。按判据第二节的定义，这些都算（能力随“架构、CPU 型号或平台固件”变化），但它们和“公共代码默认了某个架构的行为”不完全是一回事。写检查时，要把“公共代码里的能力依赖”和“架构代码内部的 CPU 型号差异”分开统计。
2. **样本够，不等于检查写得出来**：规则 B 在这一类上失败过（独立召回 1/10，当前版本 11 条全是误报）。这次的样本说明这类缺陷常见，但写检查前要先解决 astra 指出的问题：从修复前的代码里证明“这个操作依赖哪项能力”。规则 B 只认 `if (!X()) return 0` 和同文件同函数，太窄。
3. **修订 1 会影响判断口径**：设计侧有 3 个根因（M5、M6、M16）靠修订 1 的第 2、3 条才算主族。去掉它们，设计侧仍有 16 个根因、10 个族。晚期因修订 1 而多算或少算了几个，我看不到。
