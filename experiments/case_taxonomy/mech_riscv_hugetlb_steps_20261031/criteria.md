# 方向4第二轮：比较RISC-V与arm64多表项大页函数的实现步骤（判据，实现前写定）

## 背景

第一轮（`mech_riscv_hugetlb_20261030/`）发现：

- 用“arm64覆盖了、RISC-V没覆盖的钩子”作检查，能在修复前标出4/5个机制案例；
- 但RISC-V大页修复中最常见的是另一种情况：**RISC-V已经覆盖了钩子，自己的NAPOT实现却写错了。** arm64的连续页实现在对应位置本来就是正确的写法。

本轮把“参照arm64”从“有没有覆盖”推进到“**实现步骤是否一致**”，检验这一机制能否指导检查：

> arm64与RISC-V都用一组连续表项表示一个大页。处理这类大页的同名函数，在arm64中做了的关键步骤，RISC-V也应当做。缺了某一步，就是候选问题。

## 比较对象

- arm64的`arch/arm64/mm/hugetlbpage.c`与RISC-V的`arch/riscv/mm/hugetlbpage.c`中，**同名**的非static函数（例如`set_huge_pte_at`、`huge_ptep_get`、`huge_ptep_get_and_clear`、`huge_ptep_set_wrprotect`、`huge_ptep_set_access_flags`、`huge_ptep_clear_flush`、`huge_pte_clear`）。
- 每个函数的“步骤”取函数体，加上它直接调用的、同一文件内的函数体，只展开一层。

## 步骤特征（每项都用固定的正则，在展开后的文本上判断）

| 特征 | 含义 | 判断方法 |
| --- | --- | --- |
| S1 清空表项 | 先把表项清空或读出并清空 | 出现`ptep_get_and_clear`、`__ptep_get_and_clear`、`pte_clear`、`__pte_clear`、`ptep_clear`之一 |
| S2 刷新TLB | 修改后或修改前刷新TLB | 出现`flush_tlb_range`、`__flush_tlb_range`、`flush_tlb_page`、`flush_tlb_mm`之一 |
| S3 整组处理 | 按表项个数循环处理一组表项 | 出现`for (`或`while (`循环，且循环附近出现表项个数的变量（如`ncontig`、`pte_num`）；或调用名字含`contig`的同文件函数 |
| S4 区分是否在内存 | 处理前检查表项是否在内存 | 出现`pte_present(` |
| S5 合并脏位和访问位 | 把一组表项的脏位、访问位合并 | 出现`pte_dirty(`或`pte_young(`，并且出现`pte_mkdirty(`或`pte_mkyoung(` |
| S6 按大小参数确定个数 | 表项个数由调用者传入的大小参数推出，而不是从表项内容推出 | 出现`num_contig_ptes`、`find_num_contig`，或出现`sz >>`、`(sz,`等对参数`sz`的使用；同时不以`napot_cont_order(`、`napot_pte_num(`作为唯一的个数来源 |

**标记条件**：同名函数中，arm64有某项特征而RISC-V没有。每个“函数×缺失特征”记一条。

## 检验

### 1. 回溯（设计数据，只作“能否表达”的检验）

第一轮中归为“RISC-V自身NAPOT实现错误”的4个修复：

- `83d78ac677b9`：不在内存的表项取错个数；
- `1458eb2c9d88`：`set_huge_pte_at`没有先清空并刷新；
- `1de195dd0e05`：`set_huge_pte_at`写swap项时个数不对；
- `835e5ac3f98e`：`huge_ptep_set_wrprotect`逐项改写。

在每个修复的父版本上运行比较，arm64与RISC-V都取父版本中的代码，看被修复的函数是否因与修复相关的那一步缺失而被标记：

| 修复 | 期望缺失的特征 |
| --- | --- |
| `1458eb2c` | S1或S2 |
| `835e5ac3` | S1或S2 |
| `1de195dd` | S6 |
| `83d78ac6` | S4 |

这4个案例启发了特征的设计，所以命中不能算独立证据，只说明这些步骤能被这样表达。同时报告每个父版本上的标记总数。

### 2. 用arm64自己的修复作独立参照（描述性）

- 取NAPOT支持合入（`82a1a1f3bfb6`，2023-02）之后、改动`arch/arm64/mm/hugetlbpage.c`的带`Fixes:`的arm64修复。
- 对每个修复，看它修改的函数在RISC-V中是否有同名函数。若有，看修复前后arm64的步骤特征有什么变化，以及在arm64修复时，RISC-V的同名函数是否已经具备修复后的那一步。
- 再看RISC-V后来有没有对应的修复。
- 这部分回答的问题是：arm64修过的连续页问题，RISC-V是否也会出现，以及能否借arm64的修复提前发现。

### 3. 当前代码

在终点版本`df2908090cda`上运行比较，列出全部标记，由研究者逐条人工核对，归为：

- (a) 疑似问题；

疑似问题只记录，不对外报告。

## 事先写定的判断标准（描述性案例研究）

- **能表达**：回溯的4个案例中，至少3个在父版本上因期望缺失的特征被标记。
- **可用**：各父版本与终点版本上的标记都不超过15条，可以全部人工核对。
- **有独立支持**：第2部分中，至少有1个arm64修复满足两点——RISC-V有同名函数，并且在arm64修复时缺少同样的步骤。

三条都满足：下一轮把“同名函数步骤比较”推广到其他结构相似的家族（例如页表遍历、TLB刷新），并在其他架构对上检验（例如powerpc与arm64）。不满足的，如实记录并分析原因。
