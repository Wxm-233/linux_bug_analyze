# 方向4第二轮：比较RISC-V与arm64多表项大页函数的实现步骤

## 这一轮要回答什么

第一轮发现，RISC-V大页修复中最常见的不是“该覆盖的钩子没覆盖”，而是**RISC-V覆盖了钩子，自己的NAPOT实现却写错了**；arm64的连续页实现在对应的地方本来是对的。

这一轮检验这个机制能不能指导检查：

> arm64和RISC-V都用一组连续表项表示一个大页。处理这类大页的同名函数里，arm64做了的关键步骤，RISC-V也应该做；少了一步就是候选问题。

## 做法

- **比较对象**：`arch/arm64/mm/hugetlbpage.c`和`arch/riscv/mm/hugetlbpage.c`中同名的非static函数。每个函数的内容包括函数体，以及它直接调用的同文件函数的函数体（只展开一层）。
- **步骤特征**：每一项都用固定的正则判断。

| 特征 | 意思 |
| --- | --- |
| S1 清空表项 | 修改前先把表项清空，或读出并清空 |
| S2 刷新TLB | 调用TLB刷新 |
| S3 整组处理 | 按表项个数循环处理一组表项 |
| S4 区分是否在内存 | 处理前检查表项在不在内存（`pte_present`） |
| S5 合并脏位和访问位 | 把一组表项的脏位、访问位合起来 |
| S6 按大小参数确定个数 | 表项个数由调用者给出的大小推出，而不是从表项内容推出 |

- **标记条件**：同名函数中，arm64有、RISC-V没有的特征，每个“函数×缺失特征”算一条。

| 文件 | 说明 |
| --- | --- |
| `criteria.md` | 判据，实现前写定（SHA `b5dd1364…`） |
| `steps.py` → `steps.json` | 步骤提取与比较（SHA见`criteria_sha256.txt`；输出`01076c98…`） |
| `steps_run1_named_spans_defect.json` | 第一次运行的原始结果，因函数识别缺陷作废，原样保留 |
| `manual_review.json` | 当前代码6条标记的人工核对（`04dc96c3…`） |

### 运行中发现的工具缺陷（重要）

第一次运行的回溯结果是0/4。排查后发现，原因是项目共用的函数识别工具`sibling_pairs.named_spans`只往`{`前面看4行去找函数名。参数列表写得长一些的函数，名字就认不出来，整个函数被丢掉。这次被丢掉的包括：

- arm64：`clear_flush`、`get_clear_contig`、`get_clear_contig_flush`；
- RISC-V：`set_huge_pte_at`、`get_clear_contig`、`clear_flush`。

判据没有改动。本轮在脚本里换用往回找到分号、右花括号、空行或预处理行为止的识别方式（最多15行）后重跑。第一次的结果原样保留。这个缺陷是看过第一次结果才发现的，已如实记录。

**这个缺陷可能也影响了此前使用`named_spans`的各轮**，例如兄弟数据集、候选生成v1和v2、程序规则判定。凡是参数列表较长的函数，都可能被漏掉。影响多大需要另行评估。

## 结果

### 1. 回溯（设计数据，只说明这些步骤能被这样表达）

| 修复 | 问题 | 期望缺失 | 修复前是否被标出 | 父版本标记数 |
| --- | --- | --- | --- | ---: |
| `1458eb2c` | `set_huge_pte_at`修改NAPOT表项前没有先清空并刷新 | S1或S2 | 是 | 9 |
| `835e5ac3` | `huge_ptep_set_wrprotect`逐项改写，没有整体清空并刷新 | S1或S2 | 是 | 10 |
| `1de195dd` | `set_huge_pte_at`从表项内容推个数，写入swap项时出错 | S6 | 是 | 10 |
| `83d78ac6` | 表项不在内存时取错个数 | S4 | 是 | 7 |

4/4，标准是至少3个；每个父版本的标记数在7到10条之间。

### 2. 用arm64自己的修复作独立参照

NAPOT支持合入之后，arm64大页文件共有8个带`Fixes:`的修复。其中1个满足“RISC-V有同名函数、在arm64修复时缺少同样的步骤”：

| arm64修复 | 新增的步骤 | 当时的RISC-V | 后来 |
| --- | --- | --- | --- |
| `49c87f76` arm64: hugetlb: Fix huge_ptep_get_and_clear() for non-present ptes（2025-02-26，v6.14-rc5） | S4 区分是否在内存 | `huge_ptep_get_and_clear`同样缺这一步 | RISC-V在2025-03-17（v6.15-rc1）以`83d78ac6`修复同一问题 |

RISC-V那次修复的提交说明写道：arm64的修复同样适用于RISC-V；**某些大页函数不能用表项的值推出映射大小，因为表项可能不在内存中**。这是社区自己对这一机制的表述。如果arm64修复时就按“arm64刚补上的步骤、RISC-V同名函数还没有”去比较，可以提前约三周发现。

其余7个arm64修复：有的修复前后步骤特征没有变化，例如修的是地址对齐或TTL提示；有的是公共签名修改；有的对应函数RISC-V没有。

### 3. 当前代码（终点版本）

共6条标记，研究者逐条核对：

| 函数 | 缺失 | 归类 | 说明 |
| --- | --- | --- | --- |
| `huge_ptep_clear_flush` | S6 | **(c) 判断不了** | RISC-V仍从表项的值推个数，arm64已改为用大页大小；这正是RISC-V自己的修复说明里提醒不要做的事。但现有的三个调用点（写时复制、解除映射、迁移）传入的都是在内存的表项，大概率无害。值得进一步确认，不对外报告 |
| `huge_ptep_get` | S6 | (b) | RISC-V先检查表项在内存，再从表项推个数，这样做是对的 |
| `huge_ptep_set_access_flags` | S4、S6 | (b) | S4的缺失是只展开一层造成的，这一步在更深一层的`get_clear_contig`里；该函数只对在内存的表项调用 |
| `huge_ptep_set_wrprotect` | S4、S6 | (b) | 原因同上；fork时只对在内存的表项调用，迁移项和标记项另行处理 |

## 结论（按事先标准）

| 标准 | 结果 | 是否满足 |
| --- | --- | --- |
| 能表达：回溯4个中至少3个被标出 | 4/4 | 满足 |
| 可用：父版本与终点版本标记都不超过15条 | 7–10条；终点6条 | 满足 |
| 有独立支持：至少1个arm64修复，RISC-V同名函数当时缺同样步骤 | 1个（49c87f76→83d78ac6） | 满足 |

- “与arm64比较实现步骤”这一机制，能解释第一轮中占多数的“RISC-V自身NAPOT实现错误”。它有一条独立的历史证据：arm64修过的问题，三周后RISC-V也修了同一个，而且修复说明直接引用了arm64的修复。
- 加上第一轮“参照arm64找该覆盖未覆盖的钩子”，**“以arm64为参照”能覆盖RISC-V大页修复中的大部分机制性问题**：第一轮的5个，加上本轮的4个。
- 局限：
  - 回溯的4个案例同时也是设计数据；
  - 独立证据只有1个；
  - 特征用正则判断，只展开一层，会产生假标记，例如S4。

## 下一步建议

1. **先评估`named_spans`缺陷对此前各轮的影响**：统计各轮用到它的地方被漏掉了多少函数，判断哪些结论需要重算。
2. 按事先规则，把“同名函数步骤比较”推广到其他结构相似的家族，例如页表遍历、TLB刷新；并在其他架构对上检验，例如powerpc与arm64。
3. 做成“跟随arm64修复”的提醒：arm64的大页、页表相关修复一旦合入，就自动比较RISC-V同名函数是否缺少arm64刚补上的步骤。

## 统计

不调用模型；构建0；新确认缺陷0。疑似但大概率无害的1条（`huge_ptep_clear_flush`），未对外报告。
