# 判据第二版：调用上下文检查（ctxcheck2_dev_20261112）

2026-11-12，Claude。用户 11-12：“写新版判据”。本文件在挑样本、写代码、构建和运行之前写定；SHA 存入 `criteria_sha256.txt`。第一版（`ctxcheck_dev_20261112`）的判据作废，它的结果只作为本版改动的来由。

## 一、为什么改、改什么

第一版在 A175 上跑通了，但按当时的规则判为未检出：arm64 在断点用例上报了首行相同、内容不同的告警。看结果后发现规则有三处问题，本版改正：

1. **按用例比，不按整次运行比**。第一版把一次运行里出现过的告警首行汇总后再跨架构比较，不同用例上的告警混在一起。
2. **签名太粗**。第一版只取告警首行；本版加上状态行（`in_atomic()`、`irqs_disabled()`、`preempt_count` 的取值）。
3. **“几个架构都报”要单列**。第一版直接丢弃；本版记为“部分架构告警”，单独报告。

另外三处小改：异常种类补到 7 种；系统调用提示先去掉“不适合测”的系统调用再取前 20；把用户态异常入口的规则移植到 arm64、x86_64、LoongArch，使静态部分不只适用于 riscv。

**这三条规则改动是看了 A175 的结果才定的**，所以 A175 在本版下的结果只作开发集参考，不计入第五节的评估。

## 二、静态部分（流程第 6 步，写死）

1. **检查器**：沿用 `checks_v1_20261108` 的执行上下文检查器，即 `ctx_extract.py`、`ctx_analyze.py` 的性质闭包和状态数据流；在标记上去掉已知误报来源，规则同第一版判据第三节第 1 条。
2. **按架构移植“用户态异常入口”**：每个目标架构写一张表，把处理函数名映射到异常种类（表在实现时写成 `trap_tables.json`，写完记 SHA，之后不改）：
   - riscv：`do_trap_*`、`do_page_fault`（同第一版）；
   - arm64：`el0_*` 系列及其调用的 `do_el0_*` / `do_*` 处理函数（`arch/arm64/kernel/entry-common.c`、`traps.c`、`debug-monitors.c`、`mm/fault.c`）；
   - x86_64：`DEFINE_IDTENTRY*` 生成的 `exc_*` 处理函数（`arch/x86/kernel/traps.c`、`mm/fault.c`）；
   - LoongArch：`do_*` 异常处理函数（`arch/loongarch/kernel/traps.c`、`mm/fault.c`）。

   检查器的抽取范围随目标架构改为 `arch/<目标>/` 和公共目录。在某个架构上移植失败（抽取报错或入口表为空），如实记录，该架构的样本只做动态部分，单独报告。
3. **系统调用入口**：先去掉 `rank_policy.json` 中“不适合测”的系统调用，再按可达标记位置数取前 20（第一版是先取前 20、再发现大多不能测）。
4. **产出**：`hints_ctx_<样本>.json`，记录有标记的异常种类和系统调用前 20，以及例子。

## 三、用例（写死）

1. **异常用例 7 种**，同一份源码在四个架构上编译：
   - 断点；
   - 非法指令；
   - 非对齐读；
   - 非对齐写；
   - 读未映射的用户地址；
   - 写只读页；
   - 跳到不可执行的页。

   每种 3 个用例，间隔 1.2 秒。**七种全部都跑**，不按提示筛选，因为数量很少；但要报告每个检出用例所属的种类是否在静态提示里，以此衡量静态部分。
2. **系统调用用例**：从第二节第 3 条的前 20 个系统调用中，按现有生成器的 G3g 做法生成，每个系统调用 50 个用例，共约 1000 个。
3. 每个内核，异常用例和系统调用用例各跑 3 次；内核命令行显示警告级别消息。

## 四、判定（写死）

1. **调用上下文告警**：正文含以下之一：`sleeping function called from invalid context`、`BUG: scheduling while atomic`、`inconsistent lock state`、`possible circular locking dependency`、`suspicious RCU usage`、`Invalid wait context`。
2. **归属**：告警归到之后打印的第一个用例（同第一版）。
3. **签名** = 首行（去掉地址、进程号、时间、行号）+ 状态行（保留 `in_atomic()`、`irqs_disabled()`、`preempt_count` 的取值）。
4. **每个内核、每个用例的状态**：
   - 3 次运行中至少 2 次有调用上下文告警，记为“报”；
   - 0 次，记为“不报”；
   - 恰好 1 次，记为“不稳”，这个用例不判。
5. **每个用例的跨架构判定**，只在三个架构都“报”或“不报”时进行：
   - **与众不同**：只有一个架构报，另外两个不报；
   - **部分架构告警**：两个架构报，一个不报；
   - **全部告警**：三个都报；
   - **一致**：都不报。
6. **检出一个样本**：
   - **强检出**：存在一个用例，修复前的目标架构内核上是“与众不同”且目标架构在报，修复后的内核在这个用例上“不报”；
   - **弱检出**：同上，但是“部分架构告警”且目标架构在报的一方。

   两种都要人工核对告警的调用栈经过修复改动的函数，才算数。强、弱分开计数，主数字是强检出。
7. **噪声**：
   - 当前版本三个调试内核（`dbgassert_dev_20261111`）上，所有“与众不同”和“部分架构告警”的用例数；
   - 每个样本修复后的内核上，仍然报的用例数。
