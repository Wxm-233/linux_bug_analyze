# 修订2：L组与开发样本的重叠单独报告（标注L组之后、看MIPS候选之前、调用之前写）

## 起因

标注L组时发现，L组的候选与开发样本有大量重叠：
- **同一函数、同一修复**：L组3个有修复依据的`bug`全部属于这种情况：
  - `do_ale`（v6.2）与开发样本28；
  - `kvm_eiointc_regs_access`与开发样本52；
  - `kvm_eiointc_sw_status_access`与开发样本53。

  它们只是同一函数中另一处调用被另一条规则标出，例如开发样本标的是`copy_from_user`，L组标的是`copy_to_user`。
- **同一函数**：L组中还有很多标记落在开发样本出现过的函数上，例如`do_bp`、`do_watch`、`do_bce`、`die`、`do_page_fault`。

原因是开发样本是从同一个候选池中随机抽的，同一函数的多个标记可能分到两边。这样L组的`bug`保留率主要反映开发时已经见过的问题，不能说明推广。

## 改动（只增加报告内容，不改指标和目标）

1. **另外报告**：去掉“与开发样本有相同修复提交”的样本之后，各项指标的结果。判断依据是`labels3.json`中的`fix`字段，是否出现在开发样本有修复依据的提交中：

   `69cc6fad5df4`、`47256c4c8b1b`、`62f11796a0df`、`01a8e68396a6`、`8dc5245673cf`、`ea68d444a658`、`bb0511d59db9`、`b3e31a6650d4`
2. **另外报告**：L组中“函数名与路径出现在开发样本中”的样本数，及其上的结果，只作描述。
3. **结论的写法**：
   - 有修复依据的`bug`能不能推广，以去掉重叠之后的结果为准。
   - 如果去掉之后分母少于5个，就写明“bug保留没有得到独立检验”。
