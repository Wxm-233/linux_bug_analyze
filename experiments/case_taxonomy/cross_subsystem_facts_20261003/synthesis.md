# 跨子系统的表示事实、契约与实际消费对照

2026-10-03。按事前协议，停止继续扩大 HCI 同例网格，复用未改的单修订读入/写出工具，对两项**已读接口**整理机器事实与人工契约。本轮是开发材料回放和源码审阅，不是独立新样本验证，也没有新增确认缺陷。

## 两项结果

| 接口与主观察点 | 机器结果（父版→修复版） | 人工补齐的事实 | 当前能支持的结论 |
| --- | --- | --- | --- |
| ocfs2 `ocfs2_dinode_has_extents()` 的 `i_flags` | 候选→局部正常；字段为 `__le32`，旧表达式直接与主机掩码相与，修复增加 `le32_to_cpu` | 同版头文件明确这是磁盘 inode，掩码为普通整数；直接消费者是文件检查修复入口，返回值决定是否按 extent list 处理 `id2` | 条件性表示失配及修复符合本地格式约束有源码支持；不代表真实大端挂载或 I/O 后果已复现 |
| Raspberry Pi PoE PWM `get_property()` 的 `msg.reg` | 候选→局部正常；`u32 reg` 写入 `__le32`，修复增加 `cpu_to_le32` | 唯一可见调用位于 probe，传入 `RPI_PWM_CUR_DUTY_REG=0`；固件封装层复制请求与响应载荷，不做逐字段转换 | 类型域不匹配可作为复核线索，但当前调用的零值大小端字节相同，不能认定实际请求因这一写入出错 |

全文件回放背景分别为 ocfs2 的 3 候选/10 局部正常→0/13，以及 PWM 的 1/2→0/3。它们是访问或赋值站点数，**不是缺陷数量或准确率**。ocfs2 的另两处候选没有追加为本轮 primary。

ocfs2 中 `i_size` 非零测试和 `i_clusters == 0` 是已有源码的正常反例：单独判断零与非零不因端序改变。修复版显式转换也符合该读取的局部约束。父版同一条件中的 `i_mode` 是另一个运算，不能因这两个正常读取就称整条条件正确。PWM 的 `set_property()` 已对 `reg`、`val` 作显式转换，是正常写出对照；不能因此认证整个请求、返回协议或固件实现。

## 为什么还要追调用与消费

ocfs2 的目标不处在任意 inode 读取的无条件快路径。文件检查修复过程先经过验证失败、只读与 journal 等检查、签名和 VALID 标记检查；`ocfs2_iget` 的 `I_NEW`、缓存及验证分支也影响回调是否执行。直接消费者在条件成立时才解释 extent list，并可能调整元数据、重算校验和、标记脏缓冲。这里记录的是**源码上的条件后果**，没有观测到实际损坏，完整大端构建和运行路径仍未知。

PWM 表明，只从“主机类型值写入小端字段”生成诊断会混入值域例外。当前零值即使未转换，也没有请求字节差异；不能添加一个不存在的非零调用来制造阳性。类型检查仍可表达接口风格或未来调用风险，但应与当前路径的行为判断分栏。固件本地封装层的 `memcpy` 证明本地载荷没有逐字段转换，不能认证外部固件的历史规范。其 Kconfig、设备树和 `COMPILE_TEST` 分支也不能单独证明大端真实设备可达，更不能套用另一平台的大小端政策。

## 对四类 Pattern 和自动检查的启发

本轮深化的是 P2“表示不一致”，也说明它与 P3“实际消费时机”及 P4“支持条件”有关，不能把四类标签当成四套互不相干的检测器。可以把候选检查写成：

> 在确定版本和支持路径内，某值具有已审阅的表示约束，且确实到达相应运算或复制边界；当其实际值域足以使表示差异改变结果时，检查两侧是否满足同一约束。

系统层可先保留字段表示类型、集中转换的访问函数和静态类型诊断，再在磁盘运算或请求复制边界按契约检查。零值、同域比较、未到消费点和配置不适用应有各自状态，不能统一算“通过”。目前没有把这套条件装进真实内核，也没有实现自动跨过程值域、调用条件和配置求解。

对老师的两个问题，本轮的局部答案更清楚了：

- **怎样提取应该添加的检查：**工具可定位声明、表达式和部分传参形状；还需人工补出值源、真实消费点、值域和启用条件。先提出带条件的复核建议，再验证是否能升级为系统检查。本轮调用与磁盘链来自人工审阅，不包装成自动提取。
- **接口理解冲突以什么为准：**按同版本的格式声明、实际消费者、适用平台及外部规范分别保留依据。磁盘小端字与主机整数的转换有本地源码依据；PWM 固件的外部约定和实际大端支持尚缺，不能依据最终补丁或多数架构裁定。

## 方法限制与下一步

原工具为受限文本规则，不是完整 C 语义分析。consumer 的转换识别在整条条件内匹配同文本字段，同域掩码及零比较也有前缀匹配边界；本轮逐站人工核对简单表达式，不证明复杂表达式可用。producer 的 `u32` 形参不独自证明运行值的语义，后续 `&msg` 调用只是文本边界。`normal` 仅表示当前站点符合该规则。

不从这两项目的性材料计算泛化准确率或时间提升。下一步先把支持形状、值域与消费条件写成有限验证协议，再固定最多两项独立输入；区分仅元数据见过和源码参与开发，父版输出保存后才解封补丁，不按结果换例或扩池。若没有合格输入就记录停止；若值域/消费证据不足，保持不足。状态路线、专家纳入、首次发现日期、外部接口争议与 NUMA ABI 仍另列待办。
