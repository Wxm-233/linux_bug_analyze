# 判断小测：位置给对时，模型能不能判对（开发集）

## 这一轮要回答什么

第二版框架（`../framework_v2_design_20261103/README.md`）把检测分为四段：找候选、配证据、判断、复核。本轮只测**判断**：
- 把开发集中**确实有缺陷的RISC-V函数**（取修复前一刻的版本）交给模型，同时给出程序配好的参照实现；
- 混入**之后没被修过的函数**作为反例；
- 看模型能查出多少、误报多少。

同时比较两种问法：
- **V0**：第一版的问法，直接问参照中有没有RISC-V也应满足、但没做到的要求；
- **V1**：第二版的问法，额外给出逐条差异、参照中这些差异是哪个提交为什么引入的，以及RISC-V的编译条件和调用者；要求逐条记账、引用证据，并打0至3分。

## 构建结果（不调用模型）

- **正例**：27条全部取到目标函数，其中19条按程序规则找到了参照实现。只有11条配到了标注对应物所在的文件。
  - 有的配得很牵强。例如`do_trap_misaligned`被配到x86 `traps.c`中的int3处理，因为两者调用集合的相似度刚好超过0.25。
  - 8条没找到参照，只给了RISC-V代码。
- **反例**：找到54个，抽了50个。其中有3对是同一个函数在不同快照中各被抽到一次，例如`ftrace_modify_call`，这是判据允许的。

## 调用

- 154个目录全部完成，没有截断，约254万token。
- 第一次运行因会话结束而中断：36次完成，8次进行到一半。这8次的半截输出已归档到调用目录下的`_interrupted_attempt1/`，然后从断点续跑，所以**实际发出162次调用**。
- 判据规定“不自动重试”。这8次是因中断而重新调用，不是因为失败而重试，这里如实记录。

## 结果

| | V0（第一版问法） | V1（第二版问法） |
| --- | ---: | ---: |
| 正例被标记（/27） | 11 | 8 |
| 其中问题与真实修复一致 | 3 | 3 |
| 其中不一致，但指出了同一函数里另一个之后被修的真问题 | 1 | 1 |
| 反例被标记（/50） | 7 | 6 |
| V1分数的AUC（正例对反例） | — | 0.59 |

- V1的分数**几乎只有0和3两档**：正例中19个0分、8个3分；反例中44个0分、1个2分、5个3分。模型没有用打分来表达不确定。
- 正例上V0与V1的配对比较：只有V0标记的5条，只有V1标记的2条，McNemar p = 0.45，**两种问法没有显著差别**。

**按判据判定：三条都没有达到。**
- V1标记的正例8条，要求不少于11条；
- 反例误报6个，要求不超过5个；
- 问题与修复一致的3条，要求不少于8条。

结论是**判断仍是瓶颈**。按事先写定的规则，下一步不扩大找候选。

## 人工核对（第一标注人为模型Claude）

两种问法中**与真实修复一致**的都是3条：
- A301：BPF跳板保存返回值的顺序（两种问法都对）；
- A398：内存槽在GPA上界处的差一错误（两种问法都对）；
- A328：对fixmap地址使用`__pa()`（只有V0对）；
- A379：内核正文分支应直接用`__pa_symbol`得到物理地址（只有V1对）。

不一致的例子：
- A305、A321：真实修复是让原子操作完全有序，模型两次都说成零扩展问题。RISC-V的BPF由校验器插入零扩展，模型说的多半不是问题。
- A344：真实修复是开中断，V0说成缺少插桩标记。
- A327：真实修复是早期启动时不能拿`text_mutex`，V1说成缺少指令缓存同步。

另有一条值得注意：A359的目标函数中，模型（两种问法）指出“结束在GPA上界的内存槽被`>=`错误拒绝”。这不是A359本身修的问题，而是**之后A398修的真问题**。快照里它已经存在。

反例中被标记的13个（V0 7个、V1 6个）没有逐个核对。“之后没被Fixes修过”不等于没有问题，其中可能有真问题。

## 事后分析（只作描述）

1. **模型看到的问题往往不是真正的问题。** 即使把有缺陷的函数直接交给它，它也只在3/27条上说中。它倾向于挑一个“看起来缺了什么”的地方，比如零扩展、插桩标记、`__kprobes`，而不是真正违反的约定。
2. **V1提供的证据没有带来改进。** 原因可能有三点：
   - 程序配对质量差，19条中只有11条配到标注对应物所在的文件，有的完全配错；
   - 列出的差异多为两边写法不同，与缺陷无关，模型逐条否定后，整体打了0分；
   - “来历”提交说明往往讲的是参照自己的历史，比如重构、优化，而不是“为什么必须这样做”。
3. **打分没有起作用。** 模型只给0分或3分，无法用来排序。
4. **说中的几条有共同特点。** A301、A328、A379、A398要么缺陷就在函数内部、一眼可见（保存顺序、差一错误、`__pa`用错），要么参照实现里有几乎同样的写法可以直接对照（A379）。需要知道函数之外的上下文的，例如早期启动阶段不能拿锁、需要完全有序、缺少权限复位，模型都没说中。

## 结论

- 按判据，**位置给对时，这个模型（DeepSeek-V4.1-Flash）也判不准**：说中3/27，误报6/50或7/50。第二版问法没有比第一版更好。
- 下一步的选项（未执行）：
  - 换一个更强的模型，在同一批77个用例上重跑V0和V1（约154次），判断瓶颈是在模型能力还是在问法；
  - 改进配证据：用标注的对应物代替程序配对，作为上限对照，看配对质量对判断的影响有多大；
  - 把需要函数外上下文的缺陷（执行上下文、内存序）交给专门的程序检查（如M5扫描），模型只处理函数内部可见的问题。
