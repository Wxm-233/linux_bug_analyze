## 二、判定：复用引擎原有的判断

- **P1**：
  - 对任务所在的文件，按 P1 原来的方式做词法分析（`S.analyze_all`）。P1 原有范围是 mm/、kernel/、lib/、fs/proc/ 和 include/linux/；任务落在别处的，按 P1 原有的 `extra` 机制把所在顶层目录加进来；
  - 对每个任务，找到 P1 分析出的同一处调用（同文件、同函数、同行、同接口），用 P1 原有的判断（`S.classify`、`softleaf_excluded`、`dead.dead_branch`）得出结论：
    - 没被过滤 → **候选**；
    - 被过滤 → **满足**，并附上过滤理由；
    - P1 的词法分析里找不到这处调用 → **未知**。
- **ORD**：
  - 按 ORD 原来的方式（`O.analyze`）分析任务所在的文件；
  - 对每个任务函数：
    - ORD 有这一行，并且 guarded → **满足**；
    - 没有 horizontal → **不适用**（各架构取值相同）；
    - 否则 → **候选**；
    - ORD 没有这一行，说明 F 不在页缓存上下文 → **不适用**；
    - F 所在文件没有被分析 → **未知**。
  - 报告位置沿用 ORD 原来的函数起始行。
- **EC**：
  - 用 EC 在 df 上已有的规律表（laws）和偏离表（deviations），不重算；
  - 由任务发起的规律：
    - 某个 EC 构建上有偏离 → **候选**；
    - 有规律、没有偏离 → **满足**；
  - T 里的接口如果不出现在任何规律里，就是 EC 没覆盖，记为 **不适用**；
  - 候选行沿用 EC 原有的 cands（按接口、类别、构建汇总），只保留规律由任务发起的那些；
  - **EC 的实现矩阵（20 个构建）和边界的 5 个构建分开记账**：报告每个 EC 候选的偏离构建是不是在 5 个边界构建里，以及它的公共消费者来自哪些构建的边界记录。

**每一行新候选**都附上证据链：发起它的边界记录（构建、编译单元、F、行、接口、绑定定义），以及守卫和 `#if` 条件。
