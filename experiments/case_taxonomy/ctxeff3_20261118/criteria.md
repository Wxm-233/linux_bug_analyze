# 调用上下文检查第三版：横向条件（判据，写代码之前定下）

2026-11-18，Claude。用户：“做横向条件”。

来源：第二版（`ctxeff2_20261118`）当前版本的 10 条少数派候选里，第一版裁定“不可能”的还剩 6 条。原因都是架构实现里的条件，或者调用点、路径上的条件，横纵两面的规则都没看这些条件。

第二版代码只读导入（`ctxeff2.py`，它又只读导入第一版）。纵向区间和传播规则不变；X1、X2、少数派标记不变。只增加下面五条“排除”规则。每条规则只会**去掉**候选，不会新增候选。

## 一、需要的结构信息

对架构实现的函数体和公共代码的函数体，额外记录：
- **每个调用所处的条件**：包住这次调用的 `if (条件)`（带花括号的块，或者不带花括号的单句）里的条件文本；`else` 分支不记录。
- **提前返回**：函数体最外层的 `if (条件) return …;` 或 `if (条件) goto …;`，也包括块内含 `return` 或 `goto` 的 `if (条件) { … }`。记下它的位置和条件文本。

## 二、五条排除规则

**H1 上下文守卫提前返回（横向）**
- 沿架构实现计算效果时，函数 F 里某次调用（睡眠原语、IPI 原语，或者通向它们的下一层函数）之前，如果有一个提前返回，其条件文本含下列任一记号，这次调用带来的效果就不计入：
  `kfence`、`debug_pagealloc`、`in_atomic`、`irqs_disabled`、`in_interrupt`、`in_task`、`preemptible`、`oops_in_progress`。
- 含义：实现作者已经针对“原子上下文”或“调试功能会在原子上下文调用”做了避让。
- 已知风险：条件是多个子条件“或”起来的时候，可能把与当前路径无关的守卫也算进去。

**H2 常量空表项让路径不可行（横向）**
- 沿架构实现向下追一层调用时，如果这次调用的实参里有常量空表项（`__pte(0)`、`__pmd(0)`、`__pud(0)`、`__p4d(0)`、`__pgd(0)`），那么被调函数里，所有条件文本含 `_present(` 的调用都不计入效果。
- 含义：传入的是空表项，`p?d_present()` 一定为假，这些分支走不到。

**H3 调用点前的架构宏守卫（公共侧）**
- 公共代码函数 F 调用钩子 I 之前，如果有提前返回，条件是 `!宏`（宏名全大写），而且架构 a 的头文件里有这个宏的某个定义，值为 `0`，那么（I，a）这条候选不报。
- 含义：在 a 的某种配置下，宏为 0，调用点直接返回，不会走到钩子。

**H4 单 CPU 上下文（纵向）**
- 上下文来源函数（区间所在的函数）里，如果调用了下列任一函数：`hibernate_resume_nonboot_cpu_disable`、`pm_sleep_disable_secondary_cpus`、`suspend_disable_secondary_cpus`、`freeze_secondary_cpus`、`disable_nonboot_cpus`，那么从它出发的关中断上下文降为原子上下文：对 X1 仍然有效，对 X2 不再有效。
- 含义：其他 CPU 都已下线，发 IPI 不会等待。

**H5 只在高端内存分支（路径）**
- 上下文来源函数里，区间内的调用所处的条件含 `PageHighMem` 或 `is_highmem`，就把这条上下文链标为“需要 HIGHMEM”，沿传播保留这个标记。
- 某个架构上，`HIGHMEM` 按 archsig 的配置可行性判为不可能，那么经由这类链的候选，在这个架构上不报。
