# 方法一：以公共钩子为锚，比较所有架构的实现

## 这一轮要回答什么

方向4的结论是：参照另一个架构检查RISC-V，要求对应关系落实到同一个钩子或同一个函数。公共代码要求各架构实现的钩子，本身就是天然的函数级对应。本轮把参照从“只看arm64”扩展为“所有实现了这个钩子的架构的多数做法”：

> 一个钩子，如果多数架构的实现都调用了某个函数或宏（即都做了某一步），而RISC-V的实现没有，就是候选问题。

## 做法

- **钩子**：RISC-V和另外至少3个架构都定义了同名函数，并且公共代码会用到它。终点版本共494个，v6.6共425个。
- **步骤**：实现里调用的函数或宏，只展开一层同文件被调函数，并且只保留RISC-V也能用的名字。
- **多数做法**：其他实现架构中，至少一半、且不少于3个架构的实现都做了的步骤。
- **评价**：
  1. 回溯：v5.10以来，RISC-V给某个钩子的实现新加了一步的修复。在修复前，这一步是否已经是多数做法？
  2. v6.6时标出的多数做法，后来RISC-V补上了多少？与“只有1到2个架构做了”的少数做法对照。
  3. 终点版本的标记，抽20条人工核对。

## 结果

| 指标 | 结果 | 事先定的标准 |
| --- | --- | --- |
| 回溯召回 | **10/100条**（46个修复中有6个被标出） | ≥30%为有用，<15%为无用 |
| v6.6多数做法后来被RISC-V补上 | **9/123（7.3%）** | ≥10%，且至少是对照的2倍 |
| 对照：少数做法后来被补上 | 91/4162（2.2%） | — |
| 终点版本的标记 | 163条，涉及93个钩子 | — |
| 人工核对20条 | 有合理原因19条，判断不了1条，疑似问题0条 | — |

**按事先定的标准：无用**（召回<15%）。

### 有用的信号

- 多数做法的补上率是少数做法的3.3倍，说明“多数架构都做的事”确实更可能是RISC-V后来要补的。
- 召回到的几条都是真问题，而且与前几轮独立得到的结果吻合：
  - 大页`set_huge_pte_at`缺`pte_present`（方向4第二轮的案例）；
  - `huge_ptep_set_wrprotect`缺`pte_wrprotect`；
  - kexec的`arch_kimage_file_post_load_cleanup`缺`vfree`（即完备性对比中那个内存泄漏）；
  - `kprobe_ftrace_handler`缺防递归加锁；
  - ACPI表映射缺`early_memremap`；
  - vdso映射缺`mmap_write_lock_killable`。

### 为什么不够

1. **多数修复加的不是“多数做法”。** 例如KVM里RISC-V特有的向量上下文处理、BPF arena的新能力、RISC-V自己的指令缓存刷新方式。这些问题本来就不在“别人都做了”的范围里。
2. **噪声很大。** 163条标记中，大量是写法差异而不是缺了约定，例如内联汇编`__volatile__`、`pte_val`、`kfree`、32位与64位的重定位宏。还有只展开一层造成的假标记：RISC-V把该做的事放在更深一层的函数里，或者放在汇编里，例如`machine_kexec`的关中断写在`kexec_relocate.S`中。
3. **“步骤”这个特征太粗。** 只看调用了哪些名字，分不清“必须的约定步骤”和“实现细节”。

## 结论

- 以钩子为锚、看多数做法，**对应关系确实有保证**，也不依赖arm64走在前面；信号方向也是对的，补上率是对照的3.3倍。但只按调用名字比较，召回太低、噪声太多，达不到“能指导检测”的标准。
- 与方向4的结论一致：大页上有效，是因为比较的步骤是有语义的少数关键步骤，例如“先清空并刷新”“区分是否在内存”；这里直接拿全部调用名来比，混进了大量实现细节。

## 可能的下一步（未登记）

1. 只比较少数**有语义的关键步骤**，而不是全部调用名。例如：
   - 内存屏障与原子操作；
   - TLB与缓存刷新；
   - 是否在内存与有效性检查；
   - 加锁与关中断；
   - 释放与引用计数。

   先人工定义这些“约定步骤”的词表，再看召回与噪声。
2. 展开更深的调用层次，并且把汇编里的关键指令也算进来（例如关中断、屏障），减少假标记。
