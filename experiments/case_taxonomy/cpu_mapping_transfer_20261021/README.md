## 有价值的分析与边界

I把持久的`cpuid_to_apicid`与热拔时可被清除的per-CPU APIC映射区分开，J则连接了固件硬件编号、逻辑槽、PACA/索引存储及thread-group消费。这些是模型在固定研究focus下找到的具体关系；命名空间、选择域和阶段等一般原则已由研究者提供，不能把复述先验算作从零自动提契约。

两组都说明不能直接迁移“原始ID集合保持”这个表面公式。SPARC旧例直接把固件身份用作公共位图索引，本例可用显式映射形成逻辑编号；CPU可预留为possible，也不代表此刻必须present或已有可供每个用途消费的物理身份。要求需要落实到实际操作的对象域和阶段。

父版独立审阅指出以下尚未被程序发现的语义问题：

- I对present与有效映射关系的概括遗漏boot CPU初始化例外；要求每个present CPU都调用同一primary marker也过强，调用事件不等于分类内容已正确准备。
- J的容量公式缺少实际索引实现依据；不能只凭集合计数推出所需容量，也不能在缺分配器语义时断言分配/释放必须采用同一表达式。
- J要求准备与使用时守卫取值全程相同，是比实际安全条件更强的假说。真正应核对的是发生读取时对象已有效准备；登记拓扑回调也不是实际首次读取。

这些是有限源码审阅，不是专家金标准、已证运行误报或新增缺陷。所有22项引文即使绑定成功，仍不能自动证明要求成立。

## 实际修改的核对

I提交说明将目的写为：已知可热插拔CPU数量后，初始化时即可分配CPU号，使更多代码进入`__init`、相关映射及计数成为`__ro_after_init`。修改将未present的已登记APIC映射分配提前，热插拔改为只查找已分配编号。

现有证据没有建立一条修复前已适用要求被破坏、经公共消费导致错误的完整因果链。因此I不计作确认缺陷或独立同机制阳性；这不等于证明历史版本在所有配置无缺陷。父版提到的未收齐`topo_assign_cpunr`定义，后续虽被删除，也不能追认为程序找到了真实构建故障。

J支持同用途的源码参考，但尚未证明实际活动配置、固件条件和目标消费者均满足要求，不能计独立正常样本。模型提出的其他待核问题也不算新发现。

独立角色在不读当前模型答案、程序结果或父版回答审阅的情况下，先保存[修复oracle](repair_oracle.md)；主任务记录该版本后才允许其读取模型，比较另存，原预测不按oracle修改。oracle仍是助手源码审阅，不冒称专家金标准。其循环概括也须保留已初始化boot0的例外，不能扩为present与映射/物理位的无条件等价。

[后验比较](prediction_oracle_comparison.md)已完成：模型找到了具体双映射和集合用途，但没有提出实际修改的“初始化预绑定＋映射初始化后只读＋热插拔不再新分配”的组合。提出缺失helper与删除调用的字面重合，不当作缺陷因果命中；两个词法支持项也不覆盖该预绑定效果。不将这项尚未确认缺陷的提交计入检出率分母来计算准确率。
