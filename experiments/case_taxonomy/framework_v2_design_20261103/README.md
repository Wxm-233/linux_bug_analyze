# 检测框架第二版（设计，尚未实现、未调用模型）

## 一句话

第一版只看最终“命中没有”，分不清是**没找到位置**还是**找到了却判错**。第二版把检测拆成四段，每一段都单独评估：先在开发集上把每段调好，测试集最后只跑一次。最先要做的是一个小测，验证模型在**位置已经给对**的情况下能不能判对。

---

## 一、第一版的问题出在哪里

### 1. 位置找得少：51条里只找到7条

测试集中，快照之后才被修复的跨架构缺陷共51条。按修复改动的位置分：

| 修复改在哪里 | 条数 | 第一版能不能覆盖 |
| --- | ---: | --- |
| RISC-V的C函数 | 22 | 能，但只覆盖到其中一部分 |
| RISC-V的头文件（宏、内联函数） | 9 | 基本不能 |
| RISC-V的汇编 | 4 | 不能 |
| RISC-V的Makefile | 2 | 不能 |
| 公共代码（不在RISC-V目录里） | 14 | 不能 |

**例子**：A215把`array_index_nospec`加进了KVM的APLIC中断处理。它在arm64里的对应物叫`vgic_get_irq`，**名字完全不同**。第一版只靠同名函数、公共钩子来配对，所以找不到它。

按“对应物是什么”分：在别的架构里职责相同的实现（K2）24条，公共钩子（K1）13条，公共代码本身（K3）14条。

### 2. 位置找对了也判错：7个全部被放过

第一版问模型的是比较抽象的问题，例如“RISC-V的这些特点会不会让这个默认实现不成立”，并且附了一张通用的特点清单。模型对7个位置都回答“没有问题”。原因有两点：
- **没告诉模型参照为什么那样写。** 例如arm64为什么要自己重写`pgprot_dmacoherent`。不知道理由，模型就无从判断这个理由在RISC-V上是否同样成立。
- **说“没问题”不需要证据。** 模型只要给出一个听起来合理的理由就可以放过。

### 3. 差异本身区分不了真假（开发集上的程序估算）

失败分析中发现，51条里约17条有一个明显特征：参照里职责相同的文件有某个写法，RISC-V没有，修复正是把它补上。例如：
- A118补上raw自旋锁；
- A195补上`sign_extend`；
- A215、A225补上`array_index_nospec`；
- A202补上`READ_ONCE_TASK_STACK`。

我在**开发集**（27条）上用程序验证了这个思路能不能直接用来找缺陷，结果不行：

| 做法 | 定位到的（27条中） | 每个文件的候选数 |
| --- | ---: | ---: |
| 只看“参照有、RISC-V没有、且常在修复中出现”的写法 | 0 | 约19 |
| 看“参照有、RISC-V没有”的全部公共写法，按几个参照都有来排序 | 4（排名多在第29至111） | 约300 |

**结论**：差异只能用来缩小范围。真正能区分缺陷的，是“参照为什么这样写，这个理由在RISC-V上是否成立”。

> 说明：第1、2点用到的是已经结束的那一轮在测试集上的结果，属于诊断；第3点只用了开发集。新方法的任何参数都不会用测试集来调。脚本和结果在`probes/`中。

## 二、第二版框架：四段，每段单独评估

```
找候选（程序）  →  配证据（程序）  →  判断（模型）  →  复核（人工或运行）
  量：定位查全/候选数    量：证据是否齐全     量：查出率/误报率     量：前K个中的真问题
```

### 第1段：找候选（程序，不调用模型）

把三个来源合并起来：
1. **机制模块**：沿用第一版的M1、M5、M8、M10和M2，把检查点从C函数扩展到头文件宏、内联函数、汇编符号、Makefile和Kconfig。
2. **职责配对**：解决名字不同的问题。配对依据包括：同名；实现同一个公共钩子；在同一个子路径下（如`kvm/`、`net/`）且调用的公共函数最相似；被赋给同一个操作表字段。配对以**函数**为单位，不按整个文件比，避免一个文件出几百个差异。
3. **参照修复事件**：即已设计好的“参照驱动线”。arm64、x86或loongarch修了一个公共约定时，回头检查RISC-V。

### 第2段：配证据（程序，不调用模型）

对每个候选，程序准备三样东西：
- **逐条差异**：RISC-V函数和参照函数之间多了什么、少了什么，每一条单独列出。
- **差异的来历**：对参照中多出来的那一行，用`git blame`找到引入它的提交，把提交说明附上，作为“为什么要这样写”。
  - 例：arm64 `vgic_get_irq`里的`array_index_nospec`，来自一次防推测执行越界的修复，提交说明会写明“下标来自用户”。
- **按位置给出的RISC-V事实**：不再用一张通用清单，而是按候选所在的子系统或默认实现，给出相关的RISC-V事实，例如这个文件在哪些配置下编译，以及Svpbmt、非一致DMA、RV32、ACPI等哪些与它相关。

### 第3段：判断（模型）

- **逐条记账**：模型对每一条差异回答“参照的这个理由，在RISC-V上成立吗”，三选一：
  - 成立，而且RISC-V缺少相应处理；
  - 不成立：**必须引用RISC-V的具体代码行或配置**；
  - 不确定。
- **没引用事实的“不成立”，一律记为“不确定”。** 这是针对第一版“放过太容易”的问题。
- **输出0至3分**，用于排序，而不是只给一个“是”或“否”。这样可以按人工核对的能力取前K个。

### 第4段：复核

按分数取前K个人工核对。能在QEMU中运行验证的，就运行验证（machine_shutdown就是这样确认的）。

## 三、评估方式也改

1. **分段评估**：
   - 第1段用程序在开发集上画出“定位查全对候选数”的关系，不调用模型。
   - 第3段用“位置已给对”的小测，量查出率和误报率。
2. **开发集调参，测试集只跑一次。** 开发集27条，按每条修复的前一个版本取快照。
3. **命中按文件和行范围算**，不再按函数名。第一版因为函数被重构，漏算了一个真问题。
4. **主指标**：定位查全，加上前K个中人工确认的真问题数，同时报告误报。

## 四、建议的下一步：判断小测（只用开发集）

**要回答的问题**：位置已经给对时，模型能不能判对？如果连这都做不到，前面找得再准也没有用；如果能做到，就值得投入去扩大第1段。

| 项目 | 内容 |
| --- | --- |
| 正例 | 开发集27条：用修复的前一个版本，取被修复的RISC-V函数或代码段 |
| 反例 | 约50个：同样配好对，但之后两年内没有被Fixes修过的RISC-V函数 |
| 对应物 | 正例和反例都用同一套程序配对规则来找，不使用标注里的对应物说明 |
| 对比 | V0：第一版的问法；V1：第二版的问法（逐条差异＋来历＋事实，引用约束，打分） |
| 调用量 | 约77×2≈154次（DeepSeek-V4.1-Flash）。可选：V1再换一个更强的模型，约77次 |
| 事先写定的判定 | V1查出≥11/27，且反例中误报≤5/50，才继续扩大第1段；否则说明这个模型做判断是瓶颈，先换模型或改问法 |

**需要说明的风险**：开发集中的修复都是公开提交，模型可能见过，查出率会偏高。反例用来控制误报，但对“见过”这一点只能部分缓解。这一点会写进判据。

**暂缓**：约1300次调用的参照驱动线。它将作为第1段的来源3并入。在第3段被证明能判对之前，先不跑。
