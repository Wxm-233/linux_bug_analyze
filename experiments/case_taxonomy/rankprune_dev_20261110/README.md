# 提示点的排序与裁剪（rankprune_dev_20261110）

## 这一轮要回答什么

上一轮（`static2_dev_20261109`）把静态渠道补全以后，提示点涨到 7～10 倍。“点位集合” T 几乎覆盖全部系统调用，定向失去了选择性，动态检出从 5、7 掉到 3、2。这一轮给提示点打分，只留得分最高的 K 个系统调用，每个参数只留 V 个取值，看两件事：

- 含修复点的系统调用排在第几；
- 动态检出能不能恢复。

判据 `criteria.md` 在计算任何排名之前写定。

## 打分规则

一个提示点的得分由五个因子相乘：

| 因子 | 含义 | 取值 |
| --- | --- | --- |
| 边界项证据 e | 这个守卫用到的边界项，有多大把握在各架构上不一样 | 3：常量，至少两个架构上能算出值且值不同（例如修复前的 `TASK_SIZE_MAX`：riscv 是 `LONG_MAX`，arm64 是 2^52）；2：实现写在 `arch/riscv/` 或 riscv 驱动里；1：其他 |
| 稀有度 | 到处都出现的边界项（如 `current`）不值钱 | 1 / log2(1 + 含该项的系统调用数) |
| 深度 | 越深越难从参数控制 | 1 / (1 + 深度/4) |
| 回调 | 经过回调的路径不确定 | 每经过一次回调边 ×0.5 |
| 补丁证据 | x86/arm64 修过同名函数，说明这里容易出错 | 命中 ×1.5；只用 riscv 修复日期之前的补丁 |

- 系统调用的得分取它所有提示点的最高分；入口渠道 raw_nr 记 2 分。
- 裁剪参数：K = 40（约为全集 208 个的 1/5），V = 6；每个系统调用只保留 3 个提示点。
- 取值按以下顺序保留：先取高分提示点的，同一提示点内先取“常量确证分歧”导出的值。

## 结果

### 静态：修复点排第几（T 从 138～170 裁到 40）

| 样本 | 含修复点的系统调用及排名 | 进前 40 | 修复点相关取值保留 |
| --- | --- | --- | --- |
| A101 `arch_get_mmap_end` | `mremap` 5、`remap_file_pages` 11、`shmat` 17、`brk` 21 | 是 | 是 |
| A310 入口渠道 | raw_nr 1 | 是 | 是 |
| A171 `TASK_SIZE_MAX` | 102 个系统调用都含它，前 40 里有 30 个；`futex` 第 8 | 是 | 是 |
| A181 `__put_user` | 31 个系统调用含它，前 40 里有 25 个 | 是 | 是 |
| B467 | 没有含修复点的提示点 | 不可评估 | — |

A171、A181 的修复点在所有拷贝用户数据的路径上都会出现，“进前 40”对它们几乎是必然的，**区分不出排序的好坏**。真正能说明排序作用的只有 A101（从 138 个里排到第 5）和 A310（第 1）。

排在前面的大多说得通。当前版本的前几名是：raw_nr、`perf_event_open`（`perf_reg_validate`，riscv 实现）、`mprotect`（经 riscv 的 hugetlb 实现 `arch_make_huge_pte`）、`getcpu`、`sendmmsg`/`recvmmsg`/`recvmsg`（`__put_user`）、`futex`、`munmap`（`TASK_SIZE`）。但只用到 `put_user`/`get_user` 的系统调用分数完全相同，并列挤占了不少名额（例如当前版本第 10～16 名都是 0.5676）。

### 动态：检出恢复了

| 组 | 确认检出合计（3 个种子相加） | 检出的缺陷（种子数） |
| --- | --- | --- |
| 第一轮 G0 / G1 / G2 / G3 | 0 / 3 / 5 / 7 | G3：A101 2、A310 2、A171 3 |
| 上一轮 G2' / G3'（全开、不裁剪） | 3 / 2 | G2'：A101 1、A171 2；G3'：A310 2 |
| **本轮 G2r**（裁剪后点位，通用取值） | **5** | A310 2、A171 3 |
| **本轮 G3r**（裁剪后点位，裁剪后提示） | **6** | A310 3、A171 3 |

- 按参考线（G2r > 3 且 G3r > 2），记为**“裁剪恢复了定向效果”**；
- 和第一轮相比：G3r 的 A310、A171 两条每个种子都检出，比第一轮 G3 更稳定（第一轮 A310 只有 2 个种子）；但 A101 没检出。第一轮 G3 的 A101 是区间模板碰巧暴露的，这次 `mremap` 等调用虽然排进了前 5，满足触发条件的用例仍然没有出现；
- 34 个检出用例我逐条确认（`confirm.json`），形态与前两轮相同：
  - A310：`syscall(-1)` 修复前返回第 0 个参数；
  - A171：指针落在 [TASK_SIZE, LONG_MAX] 时，修复前后返回的错误码不同。其中 `mincore` 修复后在范围检查处返回 ENOMEM，符合 mincore(2)。

当前版本 9 个与众不同的聚类全部核对（`manual_review_current.json`），**疑似失配 0 个**：
- 测试自身问题 4 个：`get_robust_list` 写回指针 2 个，区间模板撞上测试程序 2 个；
- riscv 合法差异 2 个：调用号位宽；
- 判断不了 2 个：rseq；
- 环境/能力 1 个：cpumask 配置。

## 看出的几点

1. **排序本身是有效的，而且代价很低。** 同样的静态信息，裁剪到 40 个系统调用后，动态检出从 3、2 回到 5、6。上一轮“信息越多越差”的问题，主要是稀释，不是信息错了。
2. **但这一轮的检出仍然只有 A310、A171 两条。** 它们的症状宽，或者有专门的入口渠道。A101 的关键调用已经排在前列，卡在“随机 flags 很少合法、区间状态很少恰好满足”，也就是用例模型；A181、B467 同样卡在用例模型。**静态侧继续优化的边际收益在下降，瓶颈已经转到动态侧的用例构造。**
3. **证据 e = 3（常量确证分歧）太少**，每组只有 1 个边界项（就是 `TASK_SIZE_MAX`）。原因是大多数边界常量在三个架构上要么都不是编译期常量，要么值相同。“取值分歧”这条证据要扩展到运行时的值，例如由差分测试读出各架构的实际取值。
4. **同分并列是下一处可改进的地方**：`put_user`/`get_user` 一类通用边界并列占了许多名额，可以按“该系统调用独有的边界项数”打破平局。

## 局限

- K、V 和各个系数是事先拍定的，没有做敏感性分析。在开发集上调它们，会把已知答案带进去，应留到能用留出集检验的时候。
- e = 3 的规则偏向 `TASK_SIZE_MAX`（A171），判据中已注明；补丁证据按日期截止，没有使用修复之后的信息。
- 动态复测只有 G2r、G3r，与前两轮不是同一批运行，只作描述；数字仍然很小。
- 本轮没有新建内核。
