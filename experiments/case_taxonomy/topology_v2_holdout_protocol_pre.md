## 目标与范围

- 目标一：检查扩展后的受限源码提取器能否在更早的 book/drawer 历史修订中追到属性、守卫、原生 ID/CPU-map、fallback、Kconfig 和 sysfs 注册的源码证据，或者恰当地拒判。

- 不以补丁标题或“修复版”标签充当真值。这里的两项目标修订是功能血缘内的历史变更，不是两项已确认缺陷，也不能衡量对独立根因的召回率。

## 冻结与判读

1. v2 提取器、规则和 runner 完成后，记录四个文件的 SHA-256：本 protocol、`topology_contract_extract.py`、`contract_check_pilot_v1.py`、`topology_v2_holdout_runner.py`。选样 JSON 同时记录候选池查询、目标哈希、网格和代码哈希。冻结后再运行 runner；runner 先核哈希，再读取 Git 历史源码并保存原始输出。任何异常保留 `runner_error`，不伪装成 `insufficient`。
2. 程序结果只按既定规则解释：`hit` 为该条件下有源码支持的导出且缺所需原生提供者；`normal` 为已证实适用且满足条件；`not_applicable` 为接口或构建路径可证实不启用；`insufficient` 为源码形状、宏条件或权威条件无法判明。若顶层通用理由与 `unknown_reasons` 不同，以源码证据和具体拒判原因说明，不据顶层文案虚构故障。
3. 原始机器输出保存并计算哈希后，才阅读目标提交源码、对应版本的文档和配置；逐条复核是否漏掉相关路径或误判，记录人工开始与结束的墙钟时间及工具等待局限。源码复核可能发现机器规则缺陷，但**不回写冻结代码或改动原始输出**；后续修复应另建版本与新留出。
4. 报告分母以两项历史修订计；24 个条件记录只展示适用边界，不当作 24 项独立案例或准确率。若两个修订共享同一功能血缘，只能说明历史形式迁移，不声称跨子系统泛化或总体提速。静态宏不能证明运行时拓扑值正确；没有历史内核启动验证时只称源码层判断。
