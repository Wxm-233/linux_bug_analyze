## 内核补丁的工作方式

- 用法和 KCOV 一样：一个按任务开关的记录器。用户程序打开 debugfs 文件，用 ioctl 初始化并开启，再用 mmap 拿到缓冲区；之后，这个任务在系统调用里产生的事件都写进缓冲区。
- **事件**有四种：堆分配、堆释放（挂在 `mm/kasan/common.c` 的 slab 钩子上）、堆读、堆写（挂在 `mm/kasan/generic.c` 的访问检查上）。只记录这次跟踪期间分配过的对象；中断上下文里的事件不记。每个事件带调用栈。
- **没有架构相关代码**。`evtrack.c` 里没有 x86 专有的东西。x86 相关的改动只有两处：
  - 3 个测试用系统调用的表项，我们不需要；
  - `traps.o`、`fault.o` 关掉 KASAN 插桩，防止缺页处理里递归出错。riscv 需要做对应的处理。
- **依赖通用 KASAN**。riscv64 支持通用 KASAN。

## 和我们需求的差距

按师兄的新结论，动态阶段要回答两个问题：资源被谁写、被谁读（用来造多步用例），以及读到时是否满足性质。

1. **不记录值**：事件里只有地址、大小、调用栈。
   - 读事件可以在 KASAN 检查时顺手读出内存当前的值，最多 8 字节，也就是“将被读到的值”。
   - 写事件只能拿到写之前的旧值。
   - 判断“读到的是否已清零或已初始化”，用读事件的值就够了。
2. **只覆盖 slab 堆对象**。页分配器分出的页面不在其中，X1（页面清零）这类资源要另外在页分配和映射给用户的位置加钩子。
3. **版本差距**：补丁基于 v6.2-rc5，我们是 7.3-rc2。KASAN 的钩子函数从那以后改过名、改过签名，需要手工移植，不能直接打补丁。
4. **类型插件**是 clang-14 的，我们用 clang 18，要适配新版 pass 接口。可以先不用。

## 结论和工作量估计

- **需要，但只要内核记录器这一部分，并加两项扩展**：读事件记录值；页面级资源加钩子。
- 估计移植 evtrack 到 7.3 并在 riscv、arm64、x86_64 上调通约 1 天（主要难点是 riscv 缺页、陷入路径关插桩，以及 KASAN 钩子改名）；加记录值和页面钩子约半天到 1 天；在执行器里加读缓冲区约半天。
- **建议时机**：等 `effdep5_dev_20261113`（纵向信号）出结果，确定要检查哪些资源和性质，再移植，免得做出来的记录器跟要查的东西对不上。移植时打开 KASAN 的内核要重新构建，每个架构一次。
