# 属性来源—模式操作的有限检查候选

2026-10-11。本轮把上一阶段“执行结果符合请求，并不保证请求依据正确”的机制，整理成机器可读的来源复核候选。没有重跑16格，没有新的Git取证、C编译或模型调用。

## 已完成的行为

复用10/10的词法提取器，在屏蔽注释和字符串后查找直接正向、带花括号的配置guard。有限模板核对同一载体、模式mask和寄存器的设置／清除、写入、回读、后续位检查及错误返回；这些只是源码共现和先后位置，不证明控制流、数据流或实际执行。

程序自动保存配置引用、同版局部声明、操作原文、行号、复核位置和未知项，再提出条件性检查义务：**实际进入并成功离开模式选择路径时，最终模式应符合已经独立核实的环境属性；错误返回和未执行不算成功。** 具体断言位置、首个真正消费者及完整接口语义尚未自动确定，未生成或部署内核断言。

## 哪些部分自动，哪些仍由人提供

| 部分 | 当前能力 | 尚未证明的部分 |
| --- | --- | --- |
| 配置与源码位置 | 提取CONFIG引用、支持形式的guard、操作原文与行号 | 完整预处理、外围条件、有效配置绑定 |
| 声明依据 | 从两份同版Kconfig中提取局部声明、依赖和help | 全Kconfig语义、生成autoconf、可构建配置 |
| 操作关联 | 同carrier／register／mask的全行简单形式与词法顺序 | CFG支配、值源、检查与错误路径的真实归属 |
| 接口属性关联 | 按人工审阅目录限定host_data_ordering与CPU属性的复核范围 | 不能从名字或实验结果自动推导设备规范 |
| 检查建议 | 生成条件、义务、源码复核位置和证据缺口 | 首次消费者、可靠断言位置、可直接部署的检查 |

人工目录 `control_catalog.json` 依据同版源码意图、控制符号及CPU属性声明形成，另有独立原文审查。它是条件性关联，不是领域专家金标准或硬件权威。若未补该关联，程序不能仅凭名称含endian就判断两个接口必须一致。

两个候选都保留 `effective_configuration_binding=unknown`、路径与设备/消费者契约未知、`automatic_replacement=null`，CFG、运行及编译错误认证均为false。声明已见与声明未见的来源状态不同，但都不足以直接判断真实构建是否出错，或自动把宏换成另一个名字。

## 本轮对老师两个问题的推进

“怎样自动提取应该添加的检查”：当前已有一条有限路线——先明确接口与属性关联，再自动定位供给/判断、受控操作和复核位置，将应满足的条件及证据缺口输出成候选。自动化降低了定位与记录工作，但没有自动解决契约发现和可靠放置检查的问题。

“不同架构理解不一致时以什么为准”：程序应保存同版本、同配置、同消费路径的来源证据和未决状态，不能用多数架构、一个修复的改动位置或局部测试通过作唯一标准。本轮两项候选没有被升级为已正确/已错误，正是因为实际配置、设备规范和消费者还未裁定。

四类Pattern仍有效。本轮细化P2表示和P4模式/能力之间的条件：执行机制可以正常工作，而控制它的属性来源不足。这是既有框架的交接机制，未增加第五类或新的确认案例。
