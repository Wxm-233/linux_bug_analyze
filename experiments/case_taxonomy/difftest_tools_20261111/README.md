统计行：模型调用 0；构建 0；新确认缺陷 0；新疑点 0。

## 为什么做

前几轮各自改了一部分：`anyarch` 轮让比较不再写死 riscv，`stability` 轮让稳定性判定不再被时间类输出干扰，`relhint` 轮需要每个内核一份用例清单。这些改动散在三个目录里，原来的比较脚本（`diverse_dev_20261110/compare.py`）仍然写死 riscv，也没有归一化。用户同意把新规则接进默认流程。旧轮次的文件不能改，所以新建这个目录。

## 两个脚本

### `run.sh`（WSL）

```
bash run.sh <配置文件>
```

按配置文件里的内核表运行，每个内核 3 次，日志压缩后放进配置指定的目录。脚本里没有任何架构名或内核名。用例清单的路径是一个模式，可以按架构给（`{arch}`），也可以按内核给（`{name}`）；清单相同的内核共用一个启动镜像。执行器、打包和启动方式沿用旧轮次，没有改。

### `compare.py`（Windows 或 WSL，只读日志）

```
python compare.py <配置文件>            # 默认做归一化
python compare.py <配置文件> --raw      # 不做归一化，等同旧规则
python compare.py learn <配置文件>... -o volatile.json   # 从这些日志里学易变清单
```

每个内核都作为“被检查内核”算一遍，与其他架构的内核比较。判定有这几种：

| 判定 | 含义 |
| --- | --- |
| `same` | 全部一致 |
| `odd_<架构>` | 只有这个架构与其余不同 |
| `split` | 不止一个架构不同，或同一个参照架构的两个内核不一致 |
| `weak_same` / `weak_diff` | 能比的参照架构只剩一个（其余因缺少硬件能力被剔除），相同 / 不同，分不出是谁的问题 |
| `excluded` | 被检查内核自己缺少用例需要的硬件能力 |
| `no_ref` | 没有可比的参照 |
| `unstable` | 某个内核的 3 次运行不一致（归一化之后） |
| `timeout` | 被检查内核超过了执行器给单个用例的时限 |

与旧脚本（只看 riscv）的对应关系：旧的 `consistent` = `same` 或 `weak_same`；`odd_strong` = `odd_riscv`；`odd_weak` = `weak_diff`；`ref_split` = `odd_<别的架构>` 或 `split`。`weak_*` 是为了保住旧的 `odd_weak`：B467 的检出靠的就是它（x86 的模拟环境没有硬件性能计数器，只能和 arm64 一家比）。

### 配置文件

```json
{"group": "名字",
 "cases": "逻辑用例的 json", "cases_txt": "清单路径模式，含 {arch} 或 {name}",
 "logs": "日志目录", "out": "比较结果目录",
 "volatile": "易变清单的路径；不写或 null 表示不归一化",
 "kernels": [{"name": "...", "arch": "...", "image": "WSL 里的内核镜像"}]}
```

例子见 `smoke/kernels_smoke.json`。

## 11-11 之后的三处更新

1. **超时单独成类**（`compare.py`）：被检查的内核超时判为 `timeout`；超时的参照内核不参与该用例的比较。`--no-timeout-class` 恢复旧行为。回归见 `regress_timeout.py`、`regress_timeout.json`：五个样本组构成检出的用例集合不变；调试内核轮 arm64 方向 49 簇 → 17 簇。
2. **默认显示警告级别的内核消息**（`run.sh` 改用本目录的 `harness/run_qemu.sh`，内核命令行 `loglevel=5`）；`QUIET=1 bash run.sh …` 恢复旧的静默方式。验证见 `kwarn_dev_20261111`：判定差别在底噪内，检出集合不变。
3. **内核告警的提取**：`python warnings.py <日志目录>`，输出每次运行的告警事件、归属的用例和签名（规则见 `dbgassert_dev_20261111/criteria.md` 第四节）。
4. **内核消息的清理规则**：改为去掉所有带时间戳的内核消息行（显示警告后，内核消息会成串插进执行器的一行输出中间）。旧日志的四项回归不受影响。

5. **计分**：`python score.py <配置>`，读新格式的比较结果、用例清单和人工确认结论，给出每组的确认合计等。配置格式见脚本开头，例子见 `regress/score_diverse_cfg.json`。在 `diverse` 轮日志上与原评价脚本的结果逐项相同。原“使用时要注意”里说的“计分脚本还读旧格式”已不再成立。

## 整条流程的试跑（`smoke/`）

用 `anyarch` 轮的 160 个校准用例，在当前版本三个内核上用 `run.sh` 跑一遍（9 次运行，7 秒），再用 `compare.py` 比较；与用同一脚本比较 `anyarch` 轮当时的日志相比，判定和观测值完全相同（arm64 与众不同 36 个、相同 124 个）。

## 使用时要注意

- **易变清单要跟着用例集走**。现在的清单（`stability_dev_20261111/volatile.json`）是从 `diverse` 轮的用例学出来的。用例集变了，先用新日志 `learn` 一次；为了不让“学习”和“评价”用同一批数据，最好用一批单独的运行来学。
- 归一化之后，清单里那些输出的内容差异不再可见，见 `stability_dev_20261111/README.md` 的“代价”。
- 检出的计分脚本（`diverse_dev_20261110/evaluate_d.py`）还读旧格式的比较结果，没有改写。需要计分时可以按上面的对应关系把判定换回去；本目录没有提供这个转换。
- 硬件能力的剔除规则目前只有一条（`perf_event_open` 需要硬件计数器），沿用旧脚本的函数。
- 四个及以上架构的路径没有数据可测。
- 接口常数换算（`anyarch`）、相对提示值（`relhint`）属于生成器一侧，不在本目录。
