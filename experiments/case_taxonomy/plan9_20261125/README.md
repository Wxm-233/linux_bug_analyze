## 一、astra 的要点

1. **点位分三层，各由一方决定**：
   - 边界在哪：由构建感知的边界提取器决定；
   - 哪个操作值得查：由资源传播和性质分派决定，要同时匹配资源、操作和使用方式，光知道“这是数值”不能发起 ORD；
   - 在哪一行报告：由原有的性质检查器决定。

   每一行候选都要能沿证据链回到发起它的那条边界。
2. **①、② 是同一项依赖的两端**：一次公共调用按构建绑定到某个实现 G，多个构建对同一公共接口的绑定组成“实现对照组”。真正跨层的，是接口所承载的值、状态或效果约定。所以 EC、WK、XA 并不脱离边界：任务由公共接口发起，在实现处报告。
3. **边界不只有函数调用**：公共代码对架构常量、类型布局、ABI 位宽的依赖也算边界，用宏展开来源、构建绑定后的类型作证据。但“只是个窄化赋值”“同函数里有个架构调用”“路径在 arch/ 下”都不足以证明存在依赖。旧候选里找不到可追溯依赖的，留在迁移对照表里，不为了保住行数而把边界定义放宽。
4. **四种记录**：边界、资源、性质任务、判定。判定分满足、候选、未知、不适用四种，未知不能算通过。展示仍用 outfmt 的三列。
5. **每个引擎改动最小的接法**：只换任务从哪里来，判断规则不动。最先接 ORD（常量依赖）、P1（调用处的值）、EC（实现组）三种形态；WT、CTX、TLB 最容易损失，要先列出迁移差异。gstate2、setbefore 和“能力判断”这类没有可靠触发条件的检查，先不进主表。
6. **分析深度**：
   - 全树建一个轻索引，只对命中边界的编译单元建函数内控制流图，双向追定义和使用；
   - 默认只跨一层包装，用函数摘要表示，例如“第 2 个形参传到返回值”；
   - 别名、逃逸、间接调用造成的缺项要显式输出；
   - 按构建求事实，再按公共接口合并。
7. **它指出的一个问题**：`scan12.py`（以及 `scan11.py`）在非 df 版本缺 EC 缓存时，会把 df 的 EC 结果复制成那个版本的文件名。所以“能输出一张表”不能证明真的扫描了那个版本。新入口必须逐项核对版本和配置，缺了就生成，或者明确报缺。
8. **五轮安排**：
   1. 可换版本的驱动；
   2. 全树边界和资源（带阳性、阴性小夹具）；
   3. ORD、P1、EC 纵向打通；
   4. 接其余六个引擎；
   5. 父版本整版扫描和净收益。

   门槛见 `astra_plan.md` 第六节。核心要求：已确认的命中一个都不能丢；新表里每条报警都能重建出上游路径；替换旧入口还需要有净收益，即至少 1 条独立复核的新增真线索，或者审查工时降低 25%。

## 二、我的综合方案

**采纳 astra 的框架**。它和我的草案方向一致，在三处比我更严谨：
- ①、② 合成一项依赖；
- 边界包括常量、布局这类非调用依赖；
- 判定要有“未知”。

我补三点：

1. **我核对过它说的 scan12 复制问题**：`scan12.table()` 第 28～29 行确实会在缓存缺失时复制 `df.json`。目前用到的父版本结果都不是经过 scan12 出的（R4 用的是 scan3 的 `rows_of`，只有 8 个引擎、不含 EC；EC 召回走的是 ec10 自己的父版本缓存），所以已有结论不受影响。但以后对非 df 版本出表前，必须先修这个问题，这也是第 1 轮要做的事之一。
2. **第九轮“扩构建”照常做完**：它就是 astra 第 2 轮的输入之一（5 个构建的边界）。做完后按 astra 的意见，只认它覆盖了什么，不急着往下游接。
3. **把 WT 的预期说在前面**：WT 当前 746 行，其中 728 行是优先级二的窄化写法。按“必须有可追溯的跨层依赖”这条规定，大部分会离开主表，进入对照表。这是预期之中的“候选数下降”，不是退化；但要逐簇抽查被删掉的行（astra 第 4 轮的门槛）。

**接下来的顺序**（每轮先写判据）：

| 轮 | 做什么 | 关键门槛 |
|---|---|---|
| 1 | 可换版本的驱动：输入版本 + 构建矩阵，从空目录跑完，缺缓存就生成或明确报缺；修 scan12 的复制问题 | df 的 978 行逐字段一致；用别的版本的缓存冒充，必须被拒绝 |
| 2 | 全树边界和资源：调用、实现绑定、常量和布局依赖、一层包装摘要；配小夹具 | 夹具全对；按固定种子抽 30 条链，至少 27 条对；跨版本、跨构建错绑为 0 |
| 3 | ORD、P1、EC 改由资源任务发起 | 三项的冻结命中全部保留；每条报警都能重建上游路径 |

### 补充：第九轮扩构建带来的一条输入（第 2 轮要处理）

扩到 5 个构建后，加了 32 位 arm，于是 `NUMA`、`COMPAT`、`64BIT`、`SECRETMEM` 等配置项变成了“只在部分架构上有”。按第一轮的规则，这些配置项下的代码都被算成了架构层，mm/ 里有 618 个函数从公共层变成了架构层。secretmem、compat `move_pages` 也因此掉出了边界。

所以第 2 轮重写边界时，分层要改成“相对于编进它的那些构建”来判断：
- 只在一部分构建里编译、但在这些构建里源码相同的代码，记为“公共层（部分架构）”，它对架构的调用仍然算边界，只在这些构建之间比较；
- 只有在编进它的构建之间源码确实不同，才算 A1。

详见 `widebuild_20261125/README.md`。

## 三、输出：候选表 + 动态验证任务单（用户 11-25 追加）

用户的要求：“点位 / 关键资源 / 要观察的性质”这三项，对静态分析器来说可能还不够；交给动态分析的内容要更详细，原来整版扫描候选表里的一些内容也可以保留。

### 1. 整版扫描候选表（所有候选都有）

- **原有列全部保留**：序号、检查类、引擎、优先级、文件、行、函数、受影响架构、特征、关键资源、要观察的性质、不算失配的条件；
- **师兄流程加的列**：挂接、边界边、跨层资源、文档分类、常量性质；
- **新加**：判定（满足 / 候选 / 未知 / 不适用）、证据链编号（指向边界记录、资源记录、性质任务）。

### 2. 动态验证任务单

只给审查后留下的候选，或者优先级一的候选生成，每条一份 JSON。“半自动”指静态给出草稿，人可以补充。

| 字段 | 内容 | 来源 | 自动程度 |
|---|---|---|---|
| 定位 | 版本、出问题的构建、报告行、公共消费点、架构实现 | 边界记录、判定 | 自动 |
| 资源与性质 | 同候选表；另加期望值和实际值（例如“多数架构为真，这个构建为假”） | 资源记录、性质任务、引擎输出 | 自动 |
| 触发配置 | 这几行编进去所需的配置项：`#if` 条件，以及 Makefile 里的 `obj-$(CONFIG_…)` | 第一轮的预处理和 Makefile 条件 | 自动 |
| 到达路径 | 从系统调用或其他入口到点位的调用链 | 第七轮调用图的反向遍历 | 自动（近似；经函数指针的标“未知”） |
| 运行时开关 | 控制这条分支的启动参数和 sysfs 开关 | 守卫条件里的全局变量，以及写它的 `__setup`、sysfs store 函数 | 半自动 |
| 前置状态 | 需要什么对象或状态（1GB PUD 映射、迁移项、`PROT_NONE`……） | 资源种类加性质推出 | 半自动 |
| 观测点 | 路径上的断言和告警（`VM_WARN_ON`、`BUG_ON`、`pr_err` 一类），以及要打开的调试配置 | 在到达路径上查找 | 半自动 |
| 差分对照 | 应该正常的构建（多数架构）；已知修法时给出 kbuild 变异写法 | 实现对照组 | 对照构建自动；变异由人写 |
| 平台需求 | QEMU 设备和参数（vfio 加 ivshmem、`memmap=`、大内存……） | 驱动配置项能推出一部分 | 人工补 |

### 3. 怎么接进各轮

- **第 2 轮**：资源记录多存三样：配置条件、守卫、包装摘要。
- **第 3、4 轮**：每接一个引擎，同时输出它的任务单字段。
- **第 6 轮**：标准答案是已确认缺陷的动态实验，例如 `p1dyn_20261115`、`s3dyn_20261116`、`s4dyn_20261116`、`s6dyn_20261116`、`lpaeqemu_20261122`、`rvpud_20261124`。在各自缺陷还在的版本上生成任务单，逐字段对照实验里实际用到的配置、入口、开关、观测现象和对照构建。
  - 门槛事先定：触发配置和对照构建必须全对；到达路径里要包含实验用的入口；观测点至少对上一半；平台需求只报告。
  - 自动程度不够的字段，在任务单里标成“需人工”，不能空着装成齐全。
