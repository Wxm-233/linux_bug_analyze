# 第九次规划｜从跨层边界到三类检查的整版扫描

**建议先做一条能验收的纵向链路，再切换正式入口。** 输入是内核版本和构建矩阵。脚本先找公共代码依赖架构实现、架构配置或架构数据表示的位置，再沿控制流和数据流找出跨层的对象、值和效果。只有这些记录能发起性质检查。现有引擎保留性质判断、三类归属和报告位置。旧扫描在迁移期间充当独立对照。新入口如果覆盖不了已经确认的缺陷，正式入口仍用旧版，并公布具体缺口。

## 一、点位分三种，分别交给谁决定

| 点位 | 谁决定 | 例子 |
|---|---|---|
| 边界发生在哪 | 构建感知的边界提取器 | 公共函数 F 在某个翻译单元调用接口 I，当前构建选中架构实现 G。另有公共表达式使用架构常量、类型布局或配置值的非调用边界。 |
| 哪个操作值得检查 | 资源传播和性质分派 | 同一页表项进入仅对特定状态有定义的操作，或者同一架构常量从定义点传到分配尺寸。性质表须同时匹配资源、操作和使用方式。仅知道“这是数值”还不能发起 ORD。 |
| 哪一行报告 | 性质检查器 | 可以是 F 中的最终消费点、包装函数内的操作、G 的定义或某一架构的覆盖实现。每行都要能沿证据链返回发起任务的边界。 |

草案里的①和②是同一依赖的两个端点。一次公共调用按构建绑定到 G，多个构建对同一个公共接口的绑定再组成实现对照组。**实现是被选择的端点，真正跨层的是接口所承载的值、状态或效果约定。** EC 可在 G 的定义行报告，WK 可在特定覆盖实现报告；二者都能交代哪个公共接口需要这项性质。库内保留各引擎原有的符号索引、文本匹配和位向量求值器。索引可以找某个已绑定接口的实现或消费者，不能独立生成候选后按同文件或同函数补挂边界。

例如，公共路径 change_pud_range 使用 pud_leaf 的布尔返回值选择怎样处理页表项。边界记录保存公共调用、实参来源、条件用途和各构建选中的定义。EC 由此得到接口及适用的 PUD 实现组，沿用现有规则和组内比较，在异常实现的位置报告，并列出公共消费点。同一个定义被多个调用点用到，只求值一次，保留多条来源。一个架构未编入这条公共路径时，保留缺项及原因。这个例子也适合做反向验收：撤掉全部有效发起记录后，原来对应的 EC 任务必须消失。

**两类难点应在边界定义里说清。** 一是公共层对架构常量、布局和 ABI 位宽的依赖没有函数调用，可用宏展开来源、构建绑定后的类型或实际接口参数作证。二是仅有一个通用窄化赋值、同函数有个架构调用、或路径位于 arch/，都不足以建立依赖。对这类旧候选逐条记“有可追溯路径／索引范围不足／传播中断／当前定义无适用边界”。其中最后一类留在迁移对照表。若某个已知真缺陷确实在范围外，明确列为架构目标与边界定义的冲突，停止替换；切勿为保行数把所有赋值都定义成边界。

## 二、从现有材料能得出什么

- 第一轮的分层和直接边提取已经利用整批翻译单元，窄的是后面的资源分析。三架构记录有直接边 20,600 条，计入宏后 47,387 条。配置项是否只在部分架构出现取决于比较矩阵；实际是否启用、某个调用实际绑定谁，还须查该构建。头文件里的函数不能凭名字跨翻译单元合并。见 [layerbound](../layerbound_20261124/README.md)。
- xprop 的 978 行中，57 行同行、38 行同函数、83 行在分析范围内却没有对应边界、800 行在范围外。这四个数衡量旧表与小范围索引的空间关系。特别是 38 行没有证明读写了同一个对象，800 行也不能用来估算全树失配率。xconst 已经展示一种值得保留的扩展：47 行 ORD 校准材料中有 44 行能挂到架构常量来源。见 [xprop](../xprop_20261124/README.md)、[xconst](../xconst_20261124/README.md)。
- setbefore 的 9 个候选复核后均排除，原因包括 EFI 守卫、不可行的 panic 链和合法初始化。仅从资源类别推出“先设后读”会再次付出这笔审查成本。capcheck 的 0/19 也说明同树多数写法不足以推出运行时能力前置条件。性质表应记录已编码的触发条件和证据要求。尚无可判性质的资源只做缺口统计。见 [setbefore](../setbefore_20261125/README.md)、[capcheck](../capcheck_20261121/README.md)。
- scan12 是候选表汇总入口。它在部分非 df 输入缺文件时会从 df 结果复制出目标版本名；因此“能输出一张表”不能证明已扫描那个版本。新入口要以清单逐项验版本和配置，缺数据则自动生成或返回缺项。见 [scan12.py](../outfmt_20261124/scan12.py)。九项旧基线是八项共 938 行加 EC 40 行，合计 978 行。宽构建轮有 [判据](../widebuild_20261125/criteria.md)，本规划把五构建结果作为待验输入。

## 三、公共接口和每个引擎的改动

建议在新的整版驱动里保存以下四种记录。展示仍用 outfmt 的“关键资源、要观察的性质、不算失配的条件”三列，同时保留可机器核验的证据键。

| 记录 | 最少字段 | 它防止哪类错误 |
|---|---|---|
| 边界 | 版本、配置指纹、翻译单元、F、调用或依赖表达式、公共接口、实际定义 G、展开点与定义点、依赖种类、绑定依据 | 避免错用同名函数、错误宏分支和其他版本缓存 |
| 资源 | 边界键、方向、参数序号／返回／出参／全局／隐含效果、对象或字段及其定义版本、生产点、消费点、守卫、配置条件、传播链、已知程度；一至十类沿用原资源分类 | 区分同一行的两个值、重赋前后的对象、同名的不同全局；上下文和副作用也可表示 |
| 性质任务 | 性质编号、三类归属、发起资源、操作及使用条件、可比实现组、适用输入域、免报条件、缺少证据时的处理 | 避免“数值都查位宽”“页表函数都参加同一投票” |
| 判定 | 任务键、报告位置及所属函数、证据链、具体构建、满足／候选／未知／不适用、理由及证据强度 | 可按修复函数评分；规则启发式提示与有反例的违反分别呈现，未知不能算通过 |

**逐项适配。** 下表的免报依据只在相应规则已能观察到时使用。迁移只改任务从哪里来；需要新增证明能力时单立性质版本、单做对照，避免同时更换入口和裁判。

| 检查类别、引擎 | 发起记录 → 复用的判断 → 报告位置及边界情况 |
|---|---|
| 类型一致性检查 · ORD | 架构常量的来源链 → 按原有阶数相关操作与消费模式判断 → 报告最终公共表达式。对象式宏依赖可直接用 xconst。出现常量但未进入相应操作就不发任务。 |
| 类型一致性检查 · WT | 构建绑定的源值、目标类型和窄化转换 → 原 WT 规则；已证明可表示的另列 → 报告转换。与某个边界值没有定义－使用链的普通赋值留在对照表。类型大小随架构变化时须指出具体类型依赖与实际转换；不能把全树 WT 事后挂到“32 位”边界。 |
| 实现一致性检查 · P1 | 页表项值进入相应访问操作 → 复用原有词法判定，另存同一对象在到达该操作时的 present 等守卫证据 → 报告操作点。调用处与被查对象相同才可用守卫解释。 |
| 实现一致性检查 · XV | 返回或参数经页表包装接口传到消费点 → 以端口绑定原有包装器、操作和筛选条件 → 报告原消费函数；不同包装层的同名参数需靠实参与形参对接。 |
| 实现一致性检查 · EC | 有公共用途的接口及配置选中的实现组 → 复用 EC 规则 1～5、输入域、位求值和原有可比组 → 报告实现或旧规则指定位置。边界构建与 EC 实现矩阵分别记账；保留原比较条件，例如 PUD 与 PMD 的比较总体不同，不能把五个边界构建直接当作全部 EC 对照。 |
| 实现一致性检查 · TLB | 页表修改效果和相关映射范围进入公共更新路径 → 以该效果为起点复用现有刷新及路径搜索 → 报告产生或消费该义务的旧规则位置。路径看不全要标未知，不能据此断言漏刷。 |
| 实现一致性检查 · WK | 被公共代码使用的接口、弱默认定义、构建实际选中的强覆盖 → 复用默认与覆盖实现的效果比较 → 报告覆盖实现。找不到公共用处的弱符号只能记入索引。 |
| 实现一致性检查 · XA | 公共操作传入的对象、体系结构实现和访问方式 → 复用原子操作相关模式 → 报告具体实现。对象或并发条件缺证据时保留原候选强度，不提升为确认。 |
| 调用上下文检查 · CTX | 跨层调用所携带的执行上下文、具体下游调用目标 → 复用原引擎到可睡眠操作的链搜索 → 报告原有链上位置，并附边界到该链的连接。边界既可在链中间，也可通过包装入口被调用；缺一跳时记录断点。 |

最早接 ORD、P1、EC，分别验证常量依赖、调用处的值、实现组这三种形态。XV 和 WK 可复用这些接口；WT 的覆盖面、CTX 和 TLB 的路径连接最容易损失，应优先列出迁移差异。gstate2、setbefore 保留为已有实验性质，按所查状态效果或调用上下文归回已有三类，分别报告原结果。没有可靠触发条件的能力判断、兼容 ABI 性质不因填表而上线。

## 四、控制流、数据流和构建做到哪里

1. **整版建轻索引，按边界按需深查。** 从当版源树、Kbuild 选择和构建矩阵枚举可见翻译单元；索引直接调用、宏与类型依赖、公共入口和实现绑定。对命中的翻译单元才建函数内 CFG，追参数、返回值、直接字段、可定位的出参和全局读写。函数内沿定义－使用关系双向追踪；在分支合流保留多来源。把“守卫支配消费点且对象未被改写”与“附近出现过检查”区分开。
2. **默认只跨一个包装层。** 对可解析直接调用保存摘要，例如“第 2 个形参传到返回值”“写入第 1 个指针指向的字段”，在实际调用点替换为实参。别名不明、指针逃逸、间接目标不唯一、递归或内联汇编导致的缺项显式输出。保留 TLB、CTX 已有的专用多跳搜索，通用提取器无需为它们建立全内核深度调用图。若召回差异确实来自第二层包装，先记录丢失的具体链，再决定是否扩摘要。
3. **先按构建求事实，再按公共接口合并。** 头文件中的同一行可在不同翻译单元展开成不同操作。复用键至少包含版本、实际配置、目标架构、编译器和命令、翻译单元及提取器版本。跨构建比较只在规则声明的适用组内进行。归并报告时保留每个构建的守卫、绑定和未覆盖原因。
4. **按版本计算成本。** 已有记录中，三份 defconfig 构建分别约 7 分 37 秒、19 分 32 秒和 5 分 29 秒，顺序合计约 33 分钟；355 个 mm/kernel 翻译单元、940 次预处理约 2 分 16 秒。已有构建上跑原分层约 20 分钟，小范围资源提取约 3 分钟；另有 i386 allmodconfig 约 40 分钟的案例。这些是不同范围的实测参照，不能相加当作新五构建全树耗时。父版本首跑的五构建耗时、磁盘峰值和缓存命中耗时目前为 null。逐版分别记录配置准备、命令枚举、预处理、CFG、EC、汇总的 CPU／墙钟和磁盘。见 [增量扫描记录](../incscan_20261120/README.md)、[EC 构建记录](../ecbuild_20261122/README.md)。
5. **省掉链接可以，省掉范围须标出来。** 优先用 kbuild 已有的同版本同配置产物；冷启动先生成必要头文件、取得真实翻译单元清单和编译参数，再仅预处理或生成分析所需的 AST。单做 prepare 不会自动给出可靠的全树命令库。某些老版本会静默关掉所请求选项，要检查最终配置。先用旧版完整产物验证轻构建的单元集合、宏绑定和性质结果；不一致就为该构建补真实对象编译。只做 mm/ 和 arch/*/mm 可调试，遗漏调用者、头文件消费点和 kernel/，不能进入整版评测。整版的含义是对指定矩阵下的全树自动枚举，未编入的代码仍报覆盖缺口。

## 六、五轮安排及事先冻结的门槛

每轮开头写 criteria.md、记录 SHA256，冻结代码依赖、版本矩阵、抽样种子和分母。下面的数值是建议验收线。每轮可交付一份机器可查的结果；人工和 Codex 只在自动候选生成后审查。输入端不提供修复函数、修复差异、按版本挑的约定或人工选的疑点。

| 轮 | 输入和工作 | 交付、门槛和停止条件 |
|---|---|---|
| 一 · 可换版本的驱动 | 冻结 df 九项结果和回归项；另取预先指定的非 df 版本，从空结果目录用版本＋矩阵驱动。复用真实同版构建，登记来源。 | 交付运行清单、旧表逐行对照、冷／热成本。df 旧基准 978 行逐字段一致；非 df 每项结果均能追溯到自己的版本，缺缓存能生成或显式失败。故意提供异版缓存必须拒绝。任何静默复制、缺项伪装零候选即停。 |
| 二 · 边界和资源 | 在整树索引上自动产生调用、实现绑定、常量／布局依赖和包装摘要；冻结阳性及阴性小夹具，包括同名异实现、同函数不同值、重赋后失去守卫。 | 交付边界清单、资源链、按构建和目录的覆盖漏斗。夹具期望全部满足，删去所有有效边界后对应任务全部消失；自动候选生成后按固定种子核对 30 条链，至少 27 条端点、对象、方向均对，跨版本或跨构建错绑为 0。样本不足按实际数报告，不能宣布过线；错绑先修提取器。 |
| 三 · ORD、P1、EC 纵向打通 | 只从新任务入口运行三项，用同版旧扫描作旁路对照。保留 EC 实现组和原规则。 | 交付逐规则的发起记录→判定→报告、旧有而新无及新有而旧无的原因。三项各自已有冻结命中全保留，所有新表报警均有可重建的上游路径。缺实现组、靠同函数猜链、或仍靠旧候选列表发起任务则停。 |
| 四 · 接其余六项 | 接 XV、WK、XA、WT、TLB、CTX；专门核对 WT 的普通赋值、上下文跨多跳、弱覆盖与映射效果。 | 交付九项差异表和按引擎的缺性质／缺传播／无适用边界清单。九条旧报警回归断言全部保留，主表旁路候选为 0；每个消失的已知命中能定位首个断点。有真缺陷丢失便不切正式入口；仅候选数下降可以接受，但必须列原因、抽审被删簇。 |
| 五 · 父版整扫与净收益 | 在同一批修复父版本对新旧入口分别整扫，冻结输出后才连接修复函数标签。同时在一个冻结的当前版本比较原生队列和旧队列。 | 交付逐例配对表、覆盖分母、审查工时及新增证据。新入口不得损失任何同口径旧命中。两队列各按冻结种子及排序抽至多 12 个独立根因簇，各限两人时、同一裁决标准，另盲核被删簇。替换还须至少有 1 个独立复核的新增真线索，或等量正确线索下人工分钟下降至少 25% 且被删抽样未发现真线索。双方均零线索时只能报告链路和覆盖增量，不能宣称发现效率提高；保留原入口，决定是否继续投入。 |

## 七、评测怎样算数

**历史召回只用修复父版本整版扫描。** 先扫描全部目标，再由独立评分步骤将报告函数与冻结的修复函数标识匹配。比较同版同矩阵的新旧结果，列出逐例得失，按独立根因去重。构建失败、接口未编入、没有边界、传播断裂、有资源无性质、性质未报分列；总分母保留失败项，另列可评子集。修复补丁、修改行和修复后消失均不参与检测或筛选。规则开发用过的集合只能报告开发回归。保持原分析集 3/21、其中干净子集 0/12、EC 开发集 5/8 的原定义和出处；若旧 EC 的命中还依赖修复后消失，先并列重算父版单侧基线，再冻结逐例不得丢。既有 0/23 保留为此前另一口径；新数据不得与这些分母拼接。12 个干净漏报的“4／4／4”只是 df 上的粗分，须在各自父版定位才算数。下一份独立数据应按预先冻结的纳入准则由评分方保管，开发方冻结后整批评一次；封存材料继续隔离。

**当前版本分三本账。** 第一，记录旧表、新入口原生表和仅旧表有的回归记录，以独立缺陷 ID、性质、规范化报告点和证据来源去重。recallprobe 的九条断言中 DAX 有 P1、XV 两项；shmem 的邻近线索也需与直接命中修复函数分开。登记册另有 AMD、arm32 DMA 等不同发现路径，逐个标明适用引擎和覆盖，不能用九断言代替登记册。第二，报“单元覆盖→边界绑定→有资源→有适用性质→已判／未知→候选→独立复核”的分母；接口定义、实现组、配置格和根因数分别统计。第三，报告每个审查队列的确认、排除、未决、新证据及人时；将首次发现、旧问题新增可核验证据和仅重排分列。抽样未审、未完成构建、尚未产生的净收益均记 null。这样可以分别回答链路是否真实、是否保住召回，以及审查者有没有因此更快找到新的真问题。
