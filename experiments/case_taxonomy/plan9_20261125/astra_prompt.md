## 我先想的一个“一条线”的草案（请你批评、改写）

1. **边界**：第一轮扩到全树，作为唯一的点位来源。① 是公共层的调用点；② 是架构实现，按构建区分。
2. **跨层资源**：在每个边界调用点上做函数内的数据流，必要时再往外一层，得到资源记录：
   - 下行：入参的来源和种类；
   - 上行：返回值、出参、被 G 写的全局，在 F 里是怎么被使用的（条件、解引用、传给谁）；
   - 常量和常量性质；
   - 各构建里的实现。

   每条记录带上“常见资源”的分类（一～十）。
3. **失配候选**：资源种类 × 性质，用一张“性质表”来连接。比如：
   - 页表项 → 交给只对 present 项有定义的接口之前要是 present（P1、XV）；
   - 编码 → 往返不变（EC）；
   - 数值 → 位宽（WT）、取值范围（ORD）；
   - TLB → 改完要刷（TLB）；
   - 执行上下文 → 能否睡眠（CTX）；
   - 全局状态 → 设定之后才读（第七轮）；
   - 弱符号、原子性 → WK、XA。
4. **判定**：原有引擎改成“性质检查器”。性质判断逻辑不动，只把“自己找点位”换成“接收边界资源”。三类检查的分组不变。
5. 原有引擎找到、但不在边界上的点位（例如 EC 在 arch/ 头文件里的行、WT 的非边界赋值），先保留在表里并标成“非边界候选”，保证不退化；以后再看要不要并进边界的定义。
6. 没有检查器的资源种类（能力判断、compat ABI 宽度……）单独列出来，作为“有资源、缺性质”的缺口清单。
