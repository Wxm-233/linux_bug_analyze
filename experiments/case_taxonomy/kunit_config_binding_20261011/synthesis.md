# 从配置请求到配置核验：模式依据的第二个有限实例

2026-10-11。接续[真实输入范围核查](../config_mode_transfer_scope_20261011/synthesis.md)，本轮改用真实配置消费接口研究机制，不把Python材料交给C寄存器模板。

## 本轮结论

KUnit已经检查生成配置是否满足请求，但请求自身必须先覆盖经核实的环境要求。一次配置核验成功，不能证明请求完整，也不能证明运行模式正确。用户配置还可覆盖架构默认请求，必须先判断覆盖是否合法，再评价合并后的有效要求。

这与前一I3C局部试验的机制相通：读回模式位只能确认执行结果，不能确认选择依据；KUnit的子集匹配也只能确认已有要求被满足。它们支持把P2/P4交接处的候选检查拆成“依据正确且适用”“要求被完整传递”“消费时实际满足”三部分，尚不证明跨接口自动检测已泛化。

## 同版源码链

只取得09ea90e5988df98ef58d61ae5af4834e64596d9e的四份消费源物，一次Git batch。完整身份、原始收据与引文见`raw/`、`retrieval_manifest.json`、`source_quotes.json`及`audit_authority/review.json`。

1. `QemuArchParams.kconfig`是字符串载体；QEMU操作类保存该字符串，`make_arch_config()`解析它，再将基础请求合并进去。
2. 合并按键覆盖，基础请求可以覆盖架构默认。多用户文件之间另有冲突检查，不能把那处检查当成架构请求合并也受保护；覆盖本身不必然是缺陷，应结合允许模式和优先级裁定。
3. `build_config()`合并请求、写配置、调用olddefconfig，随后`validate_config()`读取生成的`.config`并调用`is_subset_of()`；`build_kernel()`构建后还复验。
4. 常规`run_tests()`遇配置/构建失败会返回，不启动测试；单独exec入口直接执行，不能说所有入口均自动完成配置核验。这只是源码顺序审阅，本轮没有调用这些流程。

运行前固定真实提供者、四份同版源物、六项合成输入、runner和独立源码预期。唯一一次runner在Windows加载保存的`kunit_config.py`，从提供者AST中取字符串，调用真实解析、空基础请求合并、子集匹配。未导入构建/QEMU主流程，未调用make或启动内核。

## 可以怎样指导自动检查

- 先形成经审阅的版本/环境要求卡：何种模式必须满足什么属性，依据来自哪里，哪些覆盖是允许的；依据不清就给复核候选。
- 程序定位配置提供者、合并顺序和最终请求，检查经审阅的要求是否被遗漏或被合法性未知的覆盖消去；不能仅凭新增补丁或架构名称生成强制要求。
- 将最终请求和生成配置比较，并在真实消费前确认实际模式。已有子集核验可复用，但要保留没有实际配置、未进入核验路径等拒判。

自动部分目前是配置字面量和条目提取、真实解析/匹配；跨文件链、模式要求与覆盖政策由人工源码审阅确定。本轮没有实现通用消费者分析器或新增内核断言。对老师两个问题的进展是明确检查可拆解的位置与裁定依赖，仍需独立同机制样本及领域确认。

下一项有限核查覆盖边界：另冻至多六组架构请求与用户请求合并对照，复用保存函数，区分“默认值允许覆盖”和“环境要求必须保留”。没有可追溯模式依据时只报告请求变化，不判缺陷。完成后收束配置局部开发，将该检查义务归入共性机制台账，不继续扩同例网格。
