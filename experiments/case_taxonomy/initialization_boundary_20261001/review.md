# 初始化入口条件下，表示检查何时适用

日期：2026-10-01。本轮使用已读 HCI 父版 `cef456cd354ef485f12d57000c455e83e416a2b6` 和修复版 `727ea61a5028f8ac96f75ab34cb1b56e63fd9227`，不新增案例、不读取新池，不调用模型。保留原源码条件，验证前轮提出的表示检查在什么时候应该启用。

## 原始条件和投影边界

该版本的四阶段同步入口实际叫 `__hci_init`，不是 `hci_init_req`。生成的 C 保留两个版本的完整 `__hci_init`、`hci_init3_req`、`hci_init4_req` 和本地完成读端 `hci_cc_le_write_def_data_len` 原文；同版 `HCI_PRIMARY`、`HCI_AMP`、`HCI_LE_DATA_LEN_EXT`、`LMP_LE`、`lmp_le_capable` 等宏与相关命令参数结构也从真实所属头文件摘取。`source_evidence.json` 保存全部引用的 revision、blob、全文件 SHA-256、行号和原文。

必须区分两个条件：init3 的读取最大长度命令在 `lmp_le_capable(hdev)` 及 `DATA_LEN_EXT` 下加入；init4 的写默认长度命令只检查 `DATA_LEN_EXT`，没有重复检查 LE。实验没有替原代码补一个 LE 判断。

矩阵中的 `lmp_le_capability` 是 `features[0][4] & LMP_LE` 的能力位，**不是** `HCI_LE_ENABLED` 配置标志。后者及 SETUP、CONFIG、SSP 等配置标志统一由 false-returning 桩模拟。命令支持数组、其他特性位和 `max_page` 为零；扩展功能、设置、debugfs 等 helpers 显式桩化并计数。数据长度来源使用同版分配函数的默认值 27/328，init3 请求不模拟真实响应更新。

同步请求桩直接调用各阶段回调，没有真实请求队列、超时、控制器或锁。在“早期错误”格中，仅在 init1 的同步调用返回 `-EIO`，发生于该阶段桩回调之前；这不代表所有阶段错误。`stages` 数组记录同步请求的**尝试顺序**，所以错误格只记 `[1]`。init1/init2 本身均为无命令桩。

`hci_req_add` 桩在目标 opcode、确切 4 字节大小验证后原样复制参数，记录目标 add 尝试及所有 opcode；这是命令构造时的字节快照，没有执行队列。原内核 `hci_req_add_ev` 还可能因 `req.err` 或 `ENOMEM` 拒绝实际入队，本轮只模拟复制成功，因此 `target_add_attempt_count` 与 `simulated_target_copy_count` **不是原内核已入队数**。仅有目标快照时注入成功完成状态，将快照交给原本地读端。端序契约检查由 Python 在程序结束后独立复算，**不是**已经嵌入 C 的运行时诊断或阻断机制。未知布局不降格成 normal：本投影的 4 字节布局断言失败会中止实验。

## 64 格有限实验

每个版本、每个目标包含 16 格：primary/AMP × LMP_LE 能力开/关 × DATA_LEN_EXT 开/关 × init1 同步成功/错误。现有 GCC 13.3.0 编译 x86_64 和 s390x 用户态程序；后者由 QEMU s390x 8.2.2 运行，程序实际读取内存字节核对目标端序。

| 版本/目标 | 有目标 add 尝试及模拟复制 | 未触达目标 add、检查不适用 | 模拟复制的字节不符 |
| --- | --- | --- | --- |
| 父版 / x86_64 小端 | 2/16 | 14/16 | 0/2 |
| 修复版 / x86_64 小端 | 2/16 | 14/16 | 0/2 |
| 父版 / s390x 大端 | 2/16 | 14/16 | 2/2 |
| 修复版 / s390x 大端 | 2/16 | 14/16 | 0/2 |

构造时适用的条件为 primary、DATA_LEN_EXT 开、init1 同步无注入错误，且桩固定复制成功。primary 成功格尝试 `[1,2,3,4]`，AMP 成功格只尝试 `[1,2]`，错误格只有 `[1]`。init3 的读长度命令 add 尝试也按保留的 LE 能力条件出现，另由运行器核对。

每组两格中的一格为 **LMP_LE 关但 DATA_LEN_EXT 开** 的不一致注入状态。原 init4 确实仍会尝试目标 add，但这个结果只显示该局部条件没有再次检查 LE，不能推出真实设备可达或新的缺陷。另一格的能力组合较一致，真实发现流程与配置状态同样未证。表内网格不是两个新案例。

在模拟目标复制点，父版大端字节为 `001b0148`，同版小端参数/本地 LE 读端要求的字节为 `1b004801`；原读端从父版大端快照得到 6912/18433，而非来源 27/328。修复在两目标都写出 `1b004801` 并读回 27/328；小端父版字节也相同。

没有目标 add 尝试的 56 格全部是 `not_applicable`，字节符合与否、本地读端数值符合与否均存为 null；保持预置本地成员 51/801，也没有伪造目标成功完成。不能把未走到观察点的配置叫 normal 或当作修复通过的数量。

## 对自动检查的意义与未完成部分

检查应同时绑定三个条件：具体 opcode、参数布局/大小及实际到达观察/消费点。即便有来源—写出—读端契约，也不能无条件把同一个数值检查放到所有配置上。对于未触达目标 add 的配置应明确不适用；对于能力组合矛盾或真实可达未证的情况，要报告条件性源码投影，不能按大端结果直接推真实故障。真实入队还需满足请求和分配条件。

本轮补充了检查适用边界，未验证真实历史内核、控制器、全部阶段错误、响应时序、配置发现和完整初始化副作用。未覆盖 `req.err/ENOMEM`、同步阶段 4 失败，也未执行更外层 `ret==0`、非 UNCONFIGURED、非 USER_CHANNEL 等入口条件。它不填补独立同机制留出空缺，也不提高案例确认层级或外部历史规范权威。

`results.json` 保存完整编译/运行命令与 stdout、逐格状态、桩假设、工具版本、可执行文件哈希，以及 runner/C 执行前后哈希相同的记录。Git 查询保存命令、blob 和全源 SHA，关键精确摘录在证据文件。两项开发提取/编译修正在 `development_failures.json` 中单列；正式运行全部成功。
