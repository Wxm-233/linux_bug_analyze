## 新补的材料和有限结论

1. **通用对象交接。** 父版`fs/super.c:577–635`与修复版字节相同。598–609匹配到已有superblock会直接返回，不调用setter；614–617分配新对象后重试；620–633把原`data`传给setter，成功后返回该`s`。结合既有`fs/btrfs/super.c:1549–1554`（setter成功时保存`s_fs_info`）及`ctree.h:1035–1038`（`btrfs_sb`），选定新建成功分支的挂载`fs_info`身份联系得到直接补证。已有superblock复用、失败及remount应分别处理，不由该分支外推完整生命周期和并发关系。

2. **真正文件消费有额外门禁。** 新保存的完整`fs/btrfs/inode.c`在父/修复版字节相同。普通写回1100–1103仅在`start==0 && fs_info->sectorsize==PAGE_SIZE`时尝试inline；压缩路径692–705也有相等限制，493–495排除subpage压缩。因此64K页/4K盘不能作为“应当inline”的布局正常对照。它只能按合法挂载条件检查参数与普通文件行为。旧`validate_super`的只读注释与实际其他条件仍须结合核对，不能仅凭该注释断定读写可用性。

3. **可区分输入只是条件性设计。** 在64K页/64K盘、首段覆盖完整文件、无压缩、实际路径可达且元数据/资源足够时，6144字节满足`4096<L<8192<65536`；8192字节可作为等号边界。341–368的门禁会比较`data_len`与`max_inline`。两版在文件写回时`sectorsize`均应已经更新为64K，遗留差异是选项先前是否被裁成4096，不能把旧版写回扇区仍为4K当作原因。以上是源码推演，不是实测layout。

4. **成功写文件不证明inline成功。** 403–406调用`insert_inline_extent`；275–279写入`BTRFS_FILE_EXTENT_INLINE`，299–307复制无压缩页内容；436返回结果，1104–1133仅在返回0时按inline完成处理。410–412及420–422将`-ENOSPC`转换为1而回退。因此需分别保留上限门禁、资源回退和提交后的实际extent类型；不能仅凭write/fsync、读回一致或参数日志归因。

5. **对象链仍不完整。** 新文件路径6764取得目录root，6783传给新inode构造，6487保存`btrfs_grab_root(root)`；消费端347–348再取得`inode->root->fs_info`。还没有完整核对root取得、引用生命周期、实际写回入口及运行对象联系。未来运行需核对挂载对象和消费对象、start/end/isize、各门禁及返回原因，不能称自动身份证明已完成。
