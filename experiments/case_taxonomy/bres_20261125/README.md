## 做了什么（说人话）

**1. 分层改成“相对于编进它的那些构建”来判断。** 一段代码只在部分架构上存在（比如受 `NUMA`、`SECRETMEM` 这类功能配置控制），但在这些架构上内容完全一样，就记为“公共层（部分架构）”，仍然算公共代码。只有两种情况才算架构层：
- 函数体里的内容因架构而不同；
- 函数是通用默认实现，架构可以拿自己的实现替换它（例如 `#ifndef ptep_get`）。

这样，第九轮加了 32 位 arm 之后掉出去的 secretmem、`do_pages_move` 又回到了边界上。

**2. 边界由 clang 在每个编译单元里实际解析出来，不再按名字猜。** 对 5 个构建的全部约 1.6 万个编译单元，凡是公共函数，它体内每一处跨层依赖都记一条，分五种：
- **调用**：被调函数的定义（或声明）在架构层；
- **宏**：函数式宏由架构定义；
- **常量**：对象式宏一层层追到 arch/ 或架构相关配置项，带来源链；
- **布局**：`sizeof` 作用在 arch/ 下定义的类型上，多数是经宏引入的，比如 `PTRS_PER_PTE = PAGE_SIZE / sizeof(pte_t)`；
- **包装一层**：调用的公共 static inline 函数里直接调用了架构函数，记下“包装函数的形参对应架构调用的哪个实参”。

每条都记下这个构建实际绑定到的定义（文件:行）和绑定依据，以及该构建 `.config` 的 SHA256。

**3. 资源记录比第二轮多了五项**，供以后的性质检查和动态验证任务单使用：
- 数据的方向（下行、上行，或者是出参）；
- 返回值赋给局部变量以后，在后面哪几处被用到；
- 守卫：外层的 `if`、前面的提前返回，以及守卫之后变量有没有被重新赋值；
- 包住这一行的 `#if` 条件；
- 被调函数读写了哪些全局变量。

例如 DAX 缺陷所在的 `insert_page_into_pte_locked`：两处 `pte_pfn` 都绑定到各架构自己的定义，守卫记成“包在 `!pte_none(pteval)` 里”和“`!mkwrite` 时提前返回”。这正是那个缺陷的形态：“不是 none”不等于“是 present”。

## 局限

- 只跨一层包装，不跟踪函数指针。经操作表进入的架构实现（例如 `x86_init.*`），在边界上看不到。
- 守卫来自宏内部的 `if`（例如 WARN 宏）时，条件原文显示的是宏调用本身。
- WARN、BUG 一类宏也算作“宏”边界（它们由架构实现），数量不少，但本身不是要检查的资源。第 3 轮分派性质任务时，不会给它们分派。
- “常量”沿用第五轮的定义，包括 `current` 这类运行时的量；第六轮的常量性质，到第 3 轮再接上。

## 补记（第 3 轮发现的漏洞，已修复并重跑）

第 3 轮发现提取器有漏：头文件里的公共函数，只在“包含它的编译单元中按名字排第一的那个”里处理。可排第一的那个单元，可能正好是第一轮排除的单元（boot、vdso 等），这时这个头文件里的公共函数一条记录也没有。例如 x86 的 `include/linux/pgtable.h` 就被指定到了 `arch/x86/boot/compressed/ident_map_64.c`。
