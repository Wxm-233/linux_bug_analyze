# 判断小测加上下文事实（Claude-Sonnet-5.5，开发集）

## 这一轮要回答什么

前两轮判断小测中，两个模型说中的都是函数内部一眼可见的缺陷，需要函数外规则的都没说中。本轮检验：**由程序把函数所处的上下文和要遵守的约定算出来交给模型，能不能说中更多？**

做法是在Sonnet的V0问法上，只增加一节“上下文事实”和一句提示，形成V2。用例、代码、参照实现、标记规则都与V0相同。

| --- | --- | --- |
| `criteria.md` | 判据，实现之前写定 | `da19210d…`（见`criteria_sha256.txt`） |
| `build_v2.py` → `context.json`、`prompt_index.json` | 计算上下文事实，并在V0原文上插入，生成V2提示词 | 见`delivery_manifest.json` |

模型输出在`模型调用测试/2026-11-03/judge_bench_context_20261103/`。

## 上下文事实（程序算出，不调用模型）

对每个目标函数，程序列出四类事实：
1. **谁调用它，在什么状态下调用**：调用者及其`__init`等标注、是否在关中断区间内、调用前已拿着哪些锁、路径条件；
2. **作为函数指针登记**的位置；
3. **再上一层调用者**；
4. **约定的文字说明**：钩子在`include/`中的注释，以及所调用接口的kernel-doc，取含`Context`、`must`、`sleep`、`irq`、`order`等词最多的6个。

77个用例中：
- 68个找到了调用者；
- 7个有函数指针登记；
- 7个有钩子说明；
- 35个有接口说明。

核对确认，V2与V0的提示词只差插入的两处。

**例子**：A327（`arch_jump_label_transform_queue`）的事实写出：
- 它在`jump_label_init`（`__init`）中被调用；
- 再上一层是`setup_arch`、`start_kernel`；
- 列出了`mutex_lock`的说明“可能睡眠”。

**瑕疵**：调用者搜索把`drivers/s390/`等驱动目录也算了进来。判据只排除了`arch/`下的其他架构目录，这些驱动不在`arch/`下。

## 调用

77次全部完成，没有截断，约21万token。

## 结果

| | Sonnet V0 | **Sonnet V2（加上下文）** |
| --- | ---: | ---: |
| 正例被标记（/27） | 8 | **2** |
| 其中与真实修复一致 | 2 | **0** |
| 反例被标记（/50） | 1 | 1 |

- V2标记的2条正例（A288、A387）说的都是**以前就判过“不一致”的同样说法**：KASAN影子内存、未知调试标志。
- V0说中的A392、A398，在V2中都被判为“没有问题”。
- 与V0的逐条比较：只有V0标记的6条（A305、A344、A359、A392、A393、A398），只有V2标记的0条，McNemar p=0.031。
- 回答分布：正例27条中21条`no`、4条`unsure`、2条`yes`；反例50个中48个`no`。

**按判据判定**：
- **可行性**：三条都没有满足。标记2条，要求不少于11条；误报1个，满足不超过5个；一致0条，要求不少于8条。
- **上下文是否有帮助**：要求“一致”不少于5条，实际0条。所以**加入这些上下文事实没有帮助，反而让结果更差**。

## 为什么更差（事后分析，只作描述）

1. **注意力被引开了。** 加入的提示句要求模型判断“是否违反调用者状态或接口约定”，它就主要去回答这个问题，不再逐行比对参照实现。
   - A392：V0指出漏排除`crashk_low_res`；V2认为“满足`crash_exclude_mem_range`的约定，arm64多出的部分属于其自身功能”。
   - A398：V0指出上界差一；V2讨论的是锁是否配对、参照多出的功能，漏掉了`>=`。
2. **近似的事实出错，把模型带偏了。**
   - A327的事实写着“调用时不在关中断区间内”。但早期启动阶段，在`start_kernel`开中断之前，中断本来就是关着的；程序只按调用序列看`local_irq_disable`，看不到这一点。
   - 模型据此推理：“早期启动时mutex无竞争，可以正常使用”，恰好错过了真实缺陷：早期启动时中断关闭，此时不能拿`text_mutex`。
3. **真正需要的事实没有算出来。**
   - A344（陷入处理中应开中断）的调用来自汇编入口，程序找不到上一层；
   - A309（kexec崩溃路径死锁）需要知道崩溃路径上别的CPU可能持有中断描述符的锁，调用序列里看不出来。
4. **对框架的启示**：
   - 上下文事实如果不准，比不给更糟。早期启动、陷入入口这类全局状态，应该由专门的规则明确给出，不能靠调用序列近似；
   - “检查代码差异”和“检查上下文”最好分成两次独立的提问，而不是塞进同一个问题里互相挤占。

## 人工核对

- 第一标注人（模型Claude）：2条都不一致。
- 这两条的说法，与上一轮GPT已判为不一致的条目相同，A288对应G02/G22/G24，A387对应G10/G15。按判据仍准备了`gpt_review/`，共2条，可交GPT复核。
- 反例N_027（`kasan_populate_pud`中`memblock_alloc`未检查返回值）没有核对。

## 结论

- 按判据，**这种近似的上下文事实没有帮助**：说中从2条降到0条，误报持平。
- 判断这一段至今最好的结果，仍然是“只给代码和参照”的V0：DeepSeek说中3条，Sonnet说中2条且误报1个。
- 下一步的选项（未执行）：
  - 把“代码对比”和“上下文检查”拆成两个独立的提问，各自标记，取并集；
  - 对少数全局状态（早期启动、陷入入口、关中断的崩溃路径）写专门的规则，给出确定的事实，不用近似；
  - 或者暂停判断这一段，回到程序规则检查。M5扫描这类规则，已经找到过machine_shutdown和未对齐陷入的真问题。
