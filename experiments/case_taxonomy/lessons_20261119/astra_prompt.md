## 研究目标

Linux 的公共代码（mm/、kernel/、fs/、drivers/）通过接口调用各架构自己的实现（arch/<架构>/）。公共代码常常默认了某个架构（通常是 x86 或 arm64）的行为，这个假设在别的架构上不成立，就产生**跨架构缺陷**。目标：给一个内核版本（或一批提交），自动找出尽可能多的跨架构缺陷，同时误报少。约束：

- 方法是**静态分析 + 多架构差分测试**（QEMU 里同一测试在 riscv、arm64、x86_64 等内核上跑）；
- 检测流水线里**不用大模型**；
- 静态检查按论文的三类组织：类型一致性（位宽、地址类别、编码）、实现一致性（各架构实现是否做了公共代码依赖的事）、调用上下文（关中断、原子上下文等）。

## 现状

- 现有 8 项静态检查，大多是词法级、不编译，直接读 git 对象：
  - 页表接口调用前没判断 present（加可达性过滤、各架构编码表、辅助函数上提）；
  - 32 位位宽截断；
  - 页大小推出的阶数超过页缓存上限；
  - TLB/缓存钩子；
  - `__weak` 通用实现与架构覆盖实现的差异；
  - 页表接口原子性与断言；
  - 关中断时调用会睡眠或等待 IPI 的架构实现。
- 用这套方法确认了 5 个新缺陷，2 个已报给社区并被维护者确认（shmem 补丁有 2 个 Reviewed-by；DAX+uffd-wp 由维护者修复，带我们的 Reported-by）。
- **问题是召回**：
  - 新评测集上，在缺陷修复前的版本上整版扫描，没参与设计的 24 个跨架构缺陷，**一个都没报到**（0/24）。漏报分属约 8 种形态：线性映射地址误用、能力判断缺失、SIMD 可用性、compat 指针、标志要求的效果被跳过、无锁页表遍历、并发、PMU 等。
  - 今天按漏报补了两条规则：
    - A“线性映射地址”：`virt_to_phys`/`virt_to_page` 用在镜像符号、vmalloc、kmap 地址上；
    - B“能力判断”：架构实现在 `!can_set_direct_map()` 这类能力不满足时静默返回成功；或同一文件里有的路径查能力、有的不查。
  - 两条规则在开发样本上都能报出。但从历史挖出的同类缺陷（两人盲判后 A 25 个、B 10 个）上，召回只有 **0/25 和 1/10**。原因：
    - 同类缺陷的写法差别很大，A 里约 18 个的地址是从参数或字段传入；
    - 有些缺陷的判断函数是修复时才加的，修复前按定义就看不出；
    - 规则照着一两个样本写，被样本牵着走。

## 我（另一个助手）目前想到的方向

1. **从修复补丁出发找同类漏网之处**：把每个历史修复的“修复前写法 → 修复后写法”机械提取成模板，在当前代码里找仍保留修复前写法的地方。可以用“时间回放”检验：只用修复 F 当时的模板，去 F 当时的版本找，看找到的位置后来是否被别的修复改掉。依据：我们报给社区的 shmem 缺陷，正是两次同类修复漏掉的位置。
2. **多架构差分测试，用内核自带的调试检查当判定器**：DEBUG_VIRTUAL、DEBUG_VM、PAGE_TABLE_CHECK、lockdep、KASAN 等在不同架构上严格程度不同，只在某个架构上出现的警告就是线索。A 的 25 个样本里至少 5 个是 arm64 上 DEBUG_VIRTUAL 报出的。
3. **编译后做真正的跨函数数据流分析**（libclang 或 CodeQL），解决“地址从参数、字段传入”的问题。
4. **先在全部历史修复上统计各形态的数量**，先做数量最多的几类。
