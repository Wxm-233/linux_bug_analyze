# 提交级模式：判据（写主程序和统计之前定下）

2026-11-17，Claude。用户：“做提交级模式”。对应 `analyzer_plan_20261116.md` 的计划 A。目的：让分析器能直接回答“这个提交有没有问题”，并在开发集上量出提交级的召回和误报。

## 一、提交级模式的定义

输入一个提交 X（只看第一父提交 X^）。

1. **引擎**：四条检查线各算一个引擎，每个引擎只读导入该线的正式版本，在单独的进程里运行（`engines.py`）：
   - P1：效果依赖，直接调用（`reachgap_20261116`）；
   - XV：效果依赖，横向编码域（`xvdom_20261116`），加上接口提升（`xvlift_20261116`）；
   - ORD：页大小派生的阶数 × 页缓存上限（`orddom_20261116`）；
   - WT：位宽截断（`widthtrunc3_20261117`）。

   各引擎的扫描范围不变。P1、XV 另外把 X 改动的、范围外的 `.c` 文件所在目录加进来（与各线 recall 的做法相同），X^ 和 X 用同一个范围。
2. **候选的签名**：每个候选记为（文件，函数，特征）。特征不含行号：
   - P1：接口名、对象；
   - XV：编码域候选为接口名、对象，提升候选为辅助函数和参数位、接口名、对象；
   - ORD：来源集合；
   - WT：形态、位置、去空白的表达式。
3. **重命名**：X 里被重命名的文件（`git diff -M` 的 R 记录），X^ 一侧的候选先换成新路径。
4. **新引入的候选**：同一签名在 X 上的个数多于 X^ 上的个数，多出来的部分算新引入。**不限于 X 改动过的函数**：例如 X 改了结构体字段的类型，截断会出现在没改动的架构代码里，也算。
5. **提交级判定**：两种口径，事先都定下：
   - **口径甲（全部）**：任一引擎有新引入的候选，就判“可疑”；
   - **口径乙（去掉 A 形态）**：不计 WT 的 A 形态（窄化，已知精度约 17%），其余同口径甲。
6. **输出**（`report/<提交>.json`）：是否可疑，以及每条新候选的引擎、位置、特征。
7. 引擎在某个版本上出错时，记为“引擎出错”，这个引擎在该提交上不计新候选，并在统计里单列。

## 二、开发集（`dataset.py`，只用于开发和调参，不是正式评测）

1. **正样本**：各检查线历史样本（共 31 个修复提交，`fixes_raw.json`）的 `Fixes:` 标签所指的提交，去重后 24 个（不含 Linux 初始导入）。
2. **负样本**：对每个正样本 P，在 P 改动过的、属于扫描范围的文件上，取 P 之前和之后时间最近的各一个提交，要求：
   - 不是合并提交；
   - 前后不超过 365 天；
   - 没有被 HEAD 历史里任何 `Fixes:` 标签指向（按哈希前 8 位）；
   - 不是正样本。

   共 44 个。
3. **局限**：“没有被 `Fixes:` 指向”不等于“没有缺陷”；正负样本都偏向 mm 和文件系统；样本是开发集，判据之后的调参都要在这批样本上，正式评测要等用户的样本。

## 三、指标

1. **提交级召回**：正样本中判“可疑”的比例（口径甲、乙各报一次）。
2. **对位召回**：正样本中，新引入的候选里至少有一条落在“修复改动过的函数”上的比例。函数按名字比较，名字取引用该提交的所有修复在修复前、修复后两侧改动的函数；WT 的 A 形态另外按“调用实参的被调函数”比较，即第二版的口径二。
3. **误报率**：负样本中判“可疑”的比例（口径甲、乙各报一次）。
4. **按引擎分解**：每个引擎各自贡献的召回、对位命中、误报。
5. **漏报分类**（正样本没有对位命中的）：
   - 缺陷在没改动的旧代码里（X 引入了一种新状态，旧代码没处理）；
   - 改动不在扫描范围；
   - 引擎在旧版本上出错；
   - 规则没覆盖。
6. **误报审查**：对判“可疑”的负样本，逐条看新候选：
   - 是这次改动真的引入了值得看的写法；
   - 签名没对上，属于位置移动、重构等假的新候选；
   - 规则本身的噪声。

   我一个人看，不请第二标注人（这一步只用于找改进方向，不出精度数字）。

## 四、参考线（第一次量，预期写在这里，达不到也如实报告）

- 对位召回（口径甲）≥ 12/24；
- 误报率（口径乙）≤ 30%；
- 引擎出错的版本 ≤ 10%。

## 五、不做的事

- 不改各检查线的规则和打分，只做提交级的比较和统计；
- 不构建内核，不做动态验证；
- 不调用第二标注人。
