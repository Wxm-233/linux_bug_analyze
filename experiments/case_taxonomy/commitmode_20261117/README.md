## 做法

1. **四个引擎**（`engines.py`）。每个引擎在单独的进程里，只读导入一条检查线的正式版本：
   - P1：效果依赖，受限接口的直接调用（`reachgap`）；
   - XV：横纵两面（`xvdom`）加接口提升（`xvlift`）；
   - ORD：页大小派生阶数 × 页缓存上限（`orddom`）；
   - WT：位宽截断（`widthtrunc3`）。

   在当前版本上，四个引擎的候选数和各自的正式版完全一致：P1 53、XV 56（33 + 23）、ORD 59、WT 746。

   单版本耗时：ORD 约 20 秒，WT、P1、XV 各约 2.5 分钟；P1、XV 各约 2GB 内存。结果缓存在 WSL 的 `/root/work/commitmode_cache/`。
2. **比较**（`commitmode.py`）：
   - 对提交 X，在 X^ 和 X 上各跑一遍；
   - 候选签名为（文件，函数，特征），不含行号；
   - X 里重命名的文件先换成新路径；
   - 同一签名在 X 上的个数多于 X^ 的部分，算“新引入”。

   **不限于 X 改动过的函数**：例如 X 改了结构体字段的类型，截断会出现在没改动的架构代码里，也算。
3. **开发集**（`dataset.py`、`dataset.json`）：
   - 正样本 24 个：各检查线 31 个历史修复的 `Fixes:` 标签所指的提交；
   - 负样本 44 个：每个正样本改过的同一批文件上，前后时间最近、没被 HEAD 历史里任何 `Fixes:` 标签（共 91249 个）指向的提交；
   - 时间跨度 2006～2026 年。
4. **运行**：534 个引擎任务，重进程并行 5 个、轻进程并行 3 个，共 2 小时 37 分钟。

### 4. 引擎出错

全量运行后有 3 处缺缓存，日志里也没有输出或报错。推测是扫描范围扩大后内存变大，又同时跑 5 个重任务，进程被系统杀掉了（没有直接证据）。之后单独补跑（`rerun.log`）：

| 提交（都是负样本） | 引擎 | 补跑结果 |
|---|---|---|
| 5bd2c0650a90 mm: 更新剩余 mmap_prepare 用户（扫描范围外 12 个目录） | XV（父版本） | **补跑成功**，241 秒，候选与提交后相同，没有新候选 |
| cb787f4ac0c2 [整树] 去掉 no_llseek（扫描范围外 105 个目录） | P1、XV | 单独跑父版本仍未生成缓存，期间 WSL 一次连接超时；提交后版本跑到一半被我停掉。**记为引擎出错**：整树改动会把扫描范围扩到上百个目录，超出单个引擎的内存 |

所以最终引擎出错 2/272（同一个提交的 P1、XV）。这个提交的 ORD、WT 都正常，没有新候选。要支持整树改动，P1、XV 的扫描范围扩展要设上限，例如只加入改动里真正碰到受限接口的文件。

## 对分析器的启示

1. **提交级的误报很低，主要靠“前后比较”本身**：一个正常提交很少引入新的危险写法。3 个误报里 2 个是可以修的规则问题（认识旧的守卫写法、调用者都已判断），1 个是签名设计问题（代码挪到新函数）。
2. **签名改进**：函数改名或代码挪到新函数时，签名对不上。可以在函数名之外，再按“去掉空白的语句文本”匹配一次：父版本里有同样的语句，就不算新引入。
3. **最大的漏报类别是“新增状态”**（4/24）：提交新增了一种无效项、一个约束或一个高位标志，出错的是别处没改的旧代码。要补这一类，需要“提交改了接口语义 → 重新检查所有使用者”。例如提交新增了一种交换项类型，就把所有对这类项调用受限接口、但没排除它的地方都报出来。
4. **规则覆盖**：
   - 受限接口表补上 hugetlb 的 `huge_pte_*`；
   - 阶数族的“上限”不能只看宏名，要看它在各架构上的实际值（横向常量表已经有，直接用）。
5. **评测口径**：对位按函数名比较会低估。用户的正式评测如果按“提交是否可疑”打分，口径甲的召回是 79%、误报 6.8%。
