# 启动时探测各内核的实际边界值（rtprobe_dev_20261110）

2026-11-10，Claude。判据 `criteria.md` 和三份修订（SHA 见 `criteria_sha256.txt`）。

统计行：模型调用 0；构建 0；新确认缺陷 0；新疑点 0。

## 为什么做

有些边界值在编译期求不出来，要到启动时才定。最典型的是用户地址上限：静态常量表里三个架构只有 arm64 是常数（2^52），riscv 和 x86 的值拿不到。这带来两个麻烦：提示值只能用 arm64 的那个数；arm64 方向有一批“地址空间大小不同”的固有差异，只能靠人工认。本轮在运行的内核里把这些值直接测出来，再看能拿它做什么。没有构建内核，没有改原执行器。

## 一、探测

`harness/rt_probe.c` 是一个独立的小程序，启动后测几项值就关机。两个主要的值：

- **用户指针检查的上限**：用长度为 0 的 `read` 调用。长度为 0 时内核只检查指针合不合法，不访问内存，所以可以逐位试出上限。
- **能映射的最高地址**：在指定地址映射一页，逐位试出最高能映射到哪里。

另外测了“是否忽略地址最高字节”（分用户指针检查和内存管理类调用两种）、页大小、硬件能力位等。

23 个内核各启动 2 次，**46 次启动共 15 秒**。全部完整，两次的值全部相同，抽查全部通过。

| 内核 | 用户指针检查的上限 | 能映射的最高地址 | 内存管理调用忽略最高字节 |
| --- | --- | --- | --- |
| 当前版本 riscv | 2^56 + 1 | 2^56 | 否 |
| 当前版本 arm64 | 2^52 + 1 | 2^52 | 是 |
| 当前版本 x86_64 | 2^56 − 4095 | 2^56 − 4096 | 否 |
| A171 修复**前** riscv | **2^63** | 2^56 | 否 |
| A171 修复**后** riscv | 2^56 + 1 | 2^56 | 否 |
| A101、A310、B467 的 riscv（修复前后） | 2^63 | 2^56 | 否 |
| A181 的 riscv（修复前后） | 2^56 + 1 | 2^56 | 否 |
| A101、A310、B467 的 x86_64 参照 | 2^63 | 2^56 − 4096 | 否 |
| A171、A181 的 x86_64 参照 | 2^56 − 4095 | 2^56 − 4096 | 否 |
| 全部 arm64 参照 | 2^52 + 1 | 2^52 | 是 |

说明：

- “+1”是因为探测用的是长度 0，这几个架构的检查含等号。两个值差 1 以内就算对上了。
- riscv 和 x86 的值是静态分析拿不到的，现在有了；它们与 arm64 的 2^52 确实不同。
- **A171 的现象被直接测出来了**（判据第六节，只记录）：修复前的 riscv 内核，指针检查的上限是 2^63，而实际能映射的最高地址只有 2^56，两者差了 128 倍；修复后对上了。A101、A310、B467 的 riscv 内核版本更早，同样是 2^63，与“它们早于 A171 的修复”一致。
- 但“两个上限对不上”**本身不能当作缺陷判据**：三个较早的 x86 参照内核也是 2^63，那是 x86 当时的设计（只检查符号位，靠别的机制兜底），不是缺陷。

## 二、用探测值自动认出“地址空间大小不同”

在上一轮 `anyarch_dev_20261110/runs/CURt` 的结果上做，没有重新运行用例。规则：如果用例里某个可能当地址用的值，在三个内核上“合不合法”的结论不一样，就给用例打上 `addr_cap` 标签。只打标签，不剔除。

对照上一轮人工核对过的 17 个簇（arm64 11 个、x86 6 个）：

| 规则 | 与人工一致 | 说明 |
| --- | --- | --- |
| 第一版：每个整数参数单独看 | 12 / 17 | 漏了 5 个：地址本身合法，地址加长度才越界 |
| 修订 2：再看两两之和，以及加 1、加一页 | 17 / 17 | 看了第一版的结果后改的，**不是独立验证** |

按修订 2 的规则，当前版本各方向的情况：

| 方向 | 簇数 | 整簇带标签 | 不带标签 |
| --- | --- | --- | --- |
| arm64 与众不同 | 12 | 8 | 4（`prctl` 2、保护位 1、时间 1） |
| riscv 与众不同 | 12 | 0（另有 1 簇部分带） | 11 |
| x86_64 与众不同 | 6 | 0 | 6 |

也就是说，arm64 方向三分之二的簇可以由程序直接归为“地址空间大小不同”，不用人看。代价：全部 8107 个用例里有 487 个（6%）带标签，其中 461 个的结果是“三者相同”。所以这个标签只适合用来给已经出现的差异分类，不能反过来用它预测哪里会有差异。

## 三、提示值改成“本架构实际上限的前后”

当前版本 8107 个用例里，有 280 个用了 2^52 − 1、2^52、2^52 + 1 这三个提示值（都来自 arm64 的常数）。把它们换成各架构自己探测到的上限前后：riscv 换成 2^56 附近，x86 换成 2^56 − 4096 附近，arm64 不变（自检：arm64 的清单逐字节相同）。这 280 个用例在三个内核上各跑 3 次，10 秒。

| | 换算前 | 换算后 |
| --- | --- | --- |
| 三者相同 | 266 | 279 |
| arm64 与众不同（用例 / 簇） | 14 / 6 | 1 / 1 |
| 其他 | 0 | 0 |

13 个用例从“arm64 与众不同”变成“三者相同”，没有任何用例反向变化，没有新簇。剩下的 1 个用例用的是另一种写法的提示值（“缓冲区地址或上第 52 位”），本轮没有换算。

道理很简单：以前三个架构都拿 2^52 去试，这个数对 arm64 是“刚好越界”，对另外两个是“普通的合法地址”，测的根本不是同一件事。换算后三个架构都在测“刚好越界”，结果自然一致。

## 说明什么

1. **运行期探测可行，而且几乎不花时间**。静态拿不到的 riscv、x86 地址上限，15 秒就测出来了，并且稳定。
2. **地址类的固有差异可以机械处理**。两种办法都有效：事后打标签（认出来），或者事前把提示值对准各架构自己的边界（不让它产生）。后一种更干净。
3. **“每个架构对准自己的边界”和“三个架构用同一个数”是两种不同的测试，都要保留**。前者测的是“各架构在自己的边界上行为是否一致”；后者测的是“同一个输入各架构怎么处理”，A171 当初就是靠后者测出来的。只用前者会漏掉 A171 这一类：它的问题恰恰是 riscv 自己的边界定错了。
4. **探测值之间的对照是一种新的线索**。A171 修复前，“指针检查的上限”和“能映射的最高地址”差了 128 倍，不需要任何测试用例就能看到。但它不能单独当判据（旧版 x86 也这样），需要和跨架构比较结合：同一版本上别的架构对得上、只有某个架构对不上，才值得看。这一点本轮只是观察，没有做成规则。

## 没做的、不确定的

- 第二节的修订规则是看了结果后改的，17/17 不能当作准确率。样本组的簇没有人工结论，没法独立检验。
- 第三节只在当前版本上做。样本组里 A101、A171（修复前）、A310、B467 的 riscv 内核两种上限对不上，按修订 3 不能换算。
- “缓冲区地址或上某一位”形式的提示值没有换算。
- 只探测了地址上限这一个边界值。常量表里编译期求不出值的边界项有几百个，其余的没有做。
- 没有用启动参数切换同一架构的不同模式（例如 riscv 的三级、四级页表）。
- 人工结论都出自 Claude 一人。
