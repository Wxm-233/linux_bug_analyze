# 复核第2版（开发轮）：三类判断、去掉须有核对依据、程序算出架构事实

## 这一轮要回答什么

`llm_review_expand_20261103/`在LoongArch 60个样本上没有达标，暴露出三个问题：
1. “真问题”的标准没定清；
2. 模型缺少目标架构的知识；
3. 模型凭无法核对的理由就能去掉标记。

本轮在同一批60个样本上针对这三点改进复核做法。这批样本已经看过结果，所以本轮**只是开发轮**，结论只作改进依据。

## 改了什么

1. **三类判断**：
   - `bug`：会出实际错误；
   - `convention`：违反写法约定，但不出错；
   - `not_issue`：标记不成立，或只是缺少功能；
   - 另可答`unsure`。

   `bug`和`unsure`进入问题清单，`convention`单独列为“写法不一致”。
2. **去掉标记须有可核对的依据**：判`not_issue`时，`refute`中至少要有一条核对相符的声明，或程序给出的事实编号；否则改记为`unsure`并追问。
3. **程序算出的事实**，按标记类型给出：
   - 是否为异常入口登记的处理函数，函数中开关中断和加解锁的位置与条件；
   - 当时Kconfig中是否选了`ARCH_SUPPORTS_RT`和`HAVE_NOINSTR_VALIDATION`；
   - R7：函数的调用位置；
   - R10：缺少的被调函数在公共代码和本架构中的调用位置。

   另有手写的LoongArch架构事实2条：进入异常时硬件关中断；处理函数按PIE决定是否开中断。
4. **新增声明类型`config`**：核对Kconfig中是否select某个选项。

## 结果

61次调用（第一步60次、追问1次），全部完成，约22万token。

| 指标 | 结果 | 开发目标 |
| --- | --- | --- |
| 有修复依据的`bug`保留（最终为`bug`或`unsure`） | **6/8 = 75%** | ≥90%，**未达到** |
| `not_issue`去除 | **16/23 = 70%** | ≥50%，达到 |
| `convention`不被判为`bug` | **27/27 = 100%** | ≥50%，达到 |

逐类的最终判断：

| 标签 \ 最终 | bug | convention | not_issue | unsure |
| --- | ---: | ---: | ---: | ---: |
| bug（10，含2个无修复依据） | 8 | 2 | 0 | 0 |
| convention（27） | 0 | 18 | 9 | 0 |
| not_issue（23） | 1 | 2 | 16 | 4 |

其他：
- 2个无修复依据的`bug`，即LoongArch KVM两处缺`array_index_nospec`，都判为`bug`。
- 事实声明145条，相符144条、不符1条。不符那条是条件写法问题，追问后判断没变。
- 25个`not_issue`判断全部附了核对相符的依据，没有被改为`unsure`。依据多为程序事实，例如`F3`“不能开启PREEMPT_RT”，或者模型自己写的声明。
- 4个模型自己答了`unsure`，并说明“没有可核对的反驳依据”。这4个本应去掉，例如`machine_crash_shutdown`、`fixup_exception`，现在保留在问题清单里交给人看。

**问题清单的构成**：最终`bug`或`unsure`共13个，其中真问题8个（6个有修复依据、2个无修复依据），误报5个。
- 只算有修复依据的：6/11 = 55%；
- 上一轮同一批样本3次取多数后，留下的27个中只有5个是真问题，即19%。

## 漏掉和判错的（事后分析）

- **漏掉的2个`bug`都被判为`convention`**：
  - `setup_arch`：模型认为`start_kernel`随后会调用`jump_label_init`，所以只是写法不同。它没有联系到LoongArch在`setup_arch`中先解析早期参数，而早期参数处理可能修改静态键。程序事实中给了`jump_label_init`在`init/main.c`中的调用位置，但没有给出它与`setup_arch`的先后。
  - `KVM_CAP_NR_VCPUS`：模型认为“只是建议值偏大，不会造成实际错误”。按定义，“错误的返回值”算`bug`，但这一条确实处在`bug`和`convention`的边界上。
- **误报判为`bug`**：`die`。模型认为`die`可能带着用户态寄存器被调用，然后在持raw锁时调用`get_user`。核对v6.1的代码，`die`只经由`die_if_kernel`和`fault.c`中内核态的`no_context`调用，所以原标签保持不变。
- **`convention`与`not_issue`的边界不清**：
  - 9个noinstr类被判为`not_issue`，依据是“没有选`HAVE_NOINSTR_VALIDATION`”；
  - 2个“等价写法”被判为`convention`。

  这两种都不影响问题清单。

## 结论

- 三项改进使复核明显变好：
  - 违反约定类全部分流出去；
  - 标记不成立的去掉70%；
  - 问题清单中有修复依据的真问题占比从19%升到55%；
  - 理由拿不出依据的标记保留下来交给人看，没有被直接去掉。
- 但有修复依据的真问题只保留了6/8，**没达到开发目标（90%）**。漏掉的2个都被判为“违反约定但不出错”。
- 只跑了1次，单次结果有波动。
- 下一步待用户决定：再调一轮开发（例如给R10补充“公共代码中调用先后”这类程序事实），或者带着现在的做法进入独立样本检验。
