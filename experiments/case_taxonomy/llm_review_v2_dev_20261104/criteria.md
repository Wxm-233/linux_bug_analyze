# 复核第2版（开发轮）：三类判断、去掉须有核对依据、程序算出架构事实（判据，实现之前写定）

## 这一轮要做什么

`llm_review_expand_20261103/`在LoongArch 60个样本上没有达标，问题有三：
1. “真问题”的标准没定清；
2. 模型缺少目标架构的知识；
3. 模型凭无法核对的理由就能去掉标记。

本轮针对这三点改进复核做法，并在**同一批60个样本上调试**。这60个样本已经看过结果，所以本轮只是**开发轮**，结论只作改进依据；能否推广要在下一轮的独立样本上检验，判据届时另写。

## 一、三类判断

模型对每个标记给出以下之一：

| 类别 | 定义 |
| --- | --- |
| `bug` | 在该版本某个能选到的配置、能走到的路径下，会造成实际错误：崩溃、死锁、“在原子上下文中睡眠”一类的警告、错误数据或返回值、安全问题（含推测执行越界） |
| `convention` | 违反内核的写法约定，或与其他架构写法不一致，但在该版本的配置和路径下不会造成实际错误 |
| `not_issue` | 标记本身不成立，例如路径走不到、状态不成立、已有等价处理、该版本选不到相关配置；或只是缺少某项功能或优化 |
| `unsure` | 判断不了 |

**流程上的处理**：
- `bug`和`unsure`进入问题清单；
- `convention`进入单独的“写法不一致”清单，不算缺陷；
- `not_issue`去掉，但须满足第二节。

## 二、去掉标记须有可核对的依据

模型判`not_issue`时，必须在`refute`中写出推翻这个标记的依据。每条依据是以下之一：
- 一条事实声明：沿用原有的4种，即annotation、calls、order、condition，另加第5种`config`，见第三节；
- 提示词中程序给出的一条架构事实的编号，例如`F2`。

**判定规则**：
- 至少一条依据核对相符，才接受`not_issue`；
- 否则改记为`unsure`，标记保留，并按原格式追问一次；
- 追问后仍然没有相符的依据，就保持`unsure`。

依据是否真能“推翻”标记，程序判断不了，只核对事实本身。这是已知局限。

## 三、程序算出的事实

**按标记类型给出的事实**：由`facts.py`在该快照的代码上计算，只给能确定准确的事实，每条编号`F1`、`F2`……

| 标记类型 | 事实 |
| --- | --- |
| CTX，陷入入口（B类、N1、N2） | 该函数是否由异常入口登记表调用；函数中各处`local_irq_enable`/`local_irq_disable`的行号和所在条件 |
| CTX，rt类 | 该版本该架构的Kconfig中是否有`select ARCH_SUPPORTS_RT` |
| CTX，noinstr类 | 该版本该架构的Kconfig中是否有`select HAVE_NOINSTR_VALIDATION` |
| R7 | 该函数在该架构目录中的调用位置，最多5处，带文件和行号 |
| R10 | 每个缺少的被调函数在公共代码和该架构中的调用位置，各最多3处 |

**架构事实表**：每个架构手写不超过3条与异常和中断有关的硬件行为，并注明代码出处，对该架构的所有CTX标记相同。LoongArch：
1. 进入异常时硬件关闭中断（清`CSR.CRMD.IE`），原来的中断状态保存在`CSR.PRMD.PIE`；
2. 内核的异常处理函数按`PIE`决定是否重新开中断，见`traps.c`中各`do_*`的`if (regs->csr_prmd & CSR_PRMD_PIE) local_irq_enable()`。

这张表是在看过上一轮的漏判之后写的。下一轮检验用到新架构时，在看样本之前先写好它的表。

**新增声明类型`config`**：`{"type": "config", "arch": "loongarch", "symbol": "ARCH_SUPPORTS_RT", "selected": false}`。核对方法：该快照`arch/<arch>/`下的Kconfig文件中是否有`select SYMBOL`。

## 五、做法与调用

- **提示词**：
  - 在原提示词的基础上，把判断要求换成三类定义，加入程序事实、架构事实表和`refute`要求；
  - 不加RISC-V的`facts.md`；
  - 其余材料（规则说明、代码、调用链、参照实现）不变。
- **核对**：`factcheck2.py`，直接导入原`factcheck.py`，新增`config`类型；先用已知结论的声明自测。
- **调用**：每个样本1次，加追问。模型Claude-Sonnet-5.5，8路并行，不自动重试。调用前须征得用户同意。

## 六、开发轮的指标（只作改进依据）

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| bug保留率 | 8个有修复依据的`bug`中，最终为`bug`或`unsure`的比例 | ≥90% |
| not_issue去除率 | 23个`not_issue`中，最终为`not_issue`的比例 | ≥50% |
| convention分流率 | 27个`convention`中，最终不为`bug`的比例 | ≥50% |
