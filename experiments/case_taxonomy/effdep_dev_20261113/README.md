## 结论（先说结果）

- **没达到参考线。** 主样本 10 条中，函数级定位命中 3 条（参考线 5 条）；命中的候选经横向比对后定性成立的为 0 条（参考线 3 条）。当前版本 40 条人工核对，疑似真问题 2 条，是同一个根因，占 5%（参考线 10%，实验二为 2.5%）。
- **主要原因有三个，都不是调参能解决的：**
  1. **实现摘要只认“写内存”这一种效果。** 命中的 A043（`arch_tlbbatch_flush`）、A025（`set_direct_map_default_noflush`）的效果是刷 TLB、改页表属性，摘要判断不了，都记成“判断不了”，所以定性不成立。
  2. **横向比对用的是当前版本的 arm64/x86。** 师兄的例子 X1 的修复把 `tag_clear_highpage` 改名成了 `tag_clear_highpages`，当前版本里没有同名实现，这个接口连接口集合都没进。另外，`page` 出现在后面 `if (... kasan_unpoison_pages(page, ...))` 的条件里，被当成“检查过”，F3 也被压掉了。
  3. **很多缺陷不是“公共代码调用架构接口”这个方向。**
     - A032：架构的缺页处理函数调用公共代码，方向相反。
     - A243：效果通过结构体字段的初始化产生。
     - A254：修复在汇编里。
     - A274：返回值用在一个更大的表达式里，F1～F3 都不覆盖。
- **定性成立的候选大多是“设计如此”。** 某个架构没有这项硬件特性（缓存一致、MTE、保护键、contpte、硬件单步、vsyscall），所以对应的钩子本来就是空的。横向比对“有的架构有效果、有的没有”这一条，本身区分不了“漏写”和“不需要”。

## 人工核对（`out/review_CUR_riscv.md`）

40 条：疑似真问题 2 条，“不是”38 条，判断不了 0 条。

- **疑似真问题**（第 7、20 条，同一根因）：riscv64 默认开启 `COMPAT`（支持 32 位用户态），但 `syscall_get_arch` 对 32 位任务也返回 `AUDIT_ARCH_RISCV64`，`asm/seccomp.h` 也没有定义 `SECCOMP_ARCH_COMPAT`。arm64 在这里会区分 compat 任务。审计和 seccomp 可能把 32 位任务当成 64 位处理。
  - 需要专业人员确认：这可能是已知的取舍（riscv 上 32 位用户态很少用），本轮不做动态确认，也不对外报告。
  - 工具把 arm64 判成“无效果”其实是摘要误判（它的返回值依赖任务），但它指向的差异是真的。
- **“不是”** 的 38 条里：
  - 36 条是“该架构没有这项特性”，设计如此。其中 `flush_dcache_*` 有 9 条；`pte_batch_hint` 有 4 条，是同一个 inline 函数因为路径写法不同（`kernel/../mm/internal.h` 与 `mm/internal.h`）被重复计数。
  - 2 条是摘要误判：`ptep_set_access_flags` 的资源是按值传入的参数；`perf_reg_validate` 返回的是常量，但取哪个常量依赖输入。

## 这一轮说明了什么，下一步可以怎么改（还没做，等和师兄讨论）

1. **“定位”这一步能找到位置，但排名靠后。** 3 个命中都在第 80～815 位，前 50 条人工建议里一个都没有。
2. **“定性”这一步目前主要在挑“哪个架构没有某项特性”，不是在找漏写。** 可以考虑三点改动：
   - 加一条“特性开关”过滤：架构没有选这个特性的 Kconfig，就不算“无效果”；
   - 把“效果”扩展到刷 TLB、改页表、屏障这类副作用；
   - 横向比对改用同一时间点的其他架构，而不是当前版本。
3. **一部分缺陷的方向本来就不在这个检查里。** 架构调用公共代码、结构体字段初始化、汇编，这三类缺陷按分流应该交给别的出口，或者直接作为人工建议。
4. **这轮找出的唯一疑点 `syscall_get_arch` 是“返回常量 vs 依赖任务”的差异，实质上更接近值依赖。** 也就是说，类型一致性检查和效果依赖检查的边界需要重新划。
