# 时序代码编辑候选 v2：新留出选样前方案

日期：2026-09-26。仅使用已读的 Btrfs、s390、RISC-V、i915、sched、dax、perf 与 x86 命名案例开发。`temporal_rule_v2.py` 解析 Git 零上下文补丁的变更行，再回到父版/修复版**完整 C 源码**定位覆盖这些行的语句；只比较同文件、同文的完整单行或多行调用/赋值，并借 hunk 函数上下文区分“同函数搬移”“跨函数搬移”“函数上下文不足”“未命中”。这避免 v1 将 i915 多行调用尾部误作完整调用。`temporal_rule_v2_known.json` 固定八项已读训练预期。

四类输出都只是**候选代码编辑**。尤其跨函数搬移不等于状态时点变化，更不等于缺陷；没有同文语句搬移也不证明不存在时点变化（dax）。语句/函数定位失败必须输出证据不足，不能静默归为正常。针对具体候选，仍须人工验证同一状态 P/C、路径条件 A、Kconfig/设备能力、失败分支与正常配置；旧版 P 在其他函数时不能因当前函数找不到 P 就判旧版违例。本版不自动提取这些语义角色，`CONFIG_SMP` 守卫等另作证据，不能被搬移检测替代。

训练通过后冻结脚本和配置 SHA-256，再从固定 500 条中 `lifecycle` 层排除已看案例，按 `SHA256("20260926-v2:<hash>")` 排序，依次取同函数候选 1 条、跨函数候选 1 条、未命中 2 条；任何桶不足则记录短缺，不临时改变规则。标题不参与排序。人只在选定后读说明和补丁，逐条记录真实时序变化、跨架构范围、人工 P/C 标注数及耗时；不按留出结果改 v2。若代码需要修复，保留 v2 原始结果另建 v3。四条样本不足以估计总体精确率/召回率。
