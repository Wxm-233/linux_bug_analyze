# 任务：给一个静态分析器做“覆盖面评测”的第二标注人（盲判）

## 背景（请先读）

这是一个防御性的研究项目：我们在开发一个**静态分析器**，用来在 Linux 内核源码里提前发现“公共代码默认了某种架构行为、换个架构就不成立”的问题。为了知道这个分析器**为什么没能报出**一些已经被修复的缺陷，我们把评测集里 21 个**已公开、已修复**的上游提交逐个分类：分析器在哪一步做不到。

你的工作只是**给分析器的能力打标签**，判断每个样本对静态分析来说“可比、可绑定、可表达”与否。不需要写任何利用、复现或测试代码，也不需要描述怎么触发问题。所有样本都是 Linux 主线里已经合入的公开修复。

第一标注人（Claude）已经标过，**请独立判断，不要看他的结果**。

`collected.json` 里每项是一个样本：修复提交（`fixes[].fix`）、修复前的父版本、修复改动的文件和函数，以及两项机械结果：`S2`（修复改动的 `.c` 文件在三个 defconfig 编译数据库里是否编入，r/a/x 表示 riscv、arm64、x86_64）和 `S5`/`S6`（分析器在父版本上是否已经在修复函数上报了候选）。

## 每个样本只需要打这几个标签

照 `criteria.md` 第二节第 4、5、6 条：

- **S1 可比对象**：修复前的源码里，这个问题是否落在一个“跨架构可比”的点上（多份按架构或配置选择的实现，或者一个对不同架构含义不同的性质，如地址类别、位宽、能力判断、上下文约束）？只是普通逻辑错误的，记“否”。
- **S2 构建覆盖**：在机械结果基础上判断。问题所在的实现属于不在 riscv、arm64、x86_64 三个构建里的架构的，记“否”；只改头文件的，看包含它的 `.c` 是否编入。
- **S3 可绑定**：静态上能否确定用的是哪个实现、哪个对象（直接调用或按构建选择 → 是；要经 ops 表、函数指针、运行时分派才知道 → 否）。
- **S4 性质可表示**：能否只用**修复前已有**的名字和信息，把这个问题表达成三类检查（类型一致性、实现一致性、调用上下文）之一？必须用修复才引入的函数或标志才能表达的，记“否”。并发竞争、内存模型这类，记“否”。
- **first_break**：S1～S5 里第一个“否”或“未知”；都为“是”填 `S6`。
- **auto**：`具备`（S1～S4 都是）/ `只能人工核验`（S1 是，但 S3 或 S4 否）/ `非跨架构可比`（S1 否）/ `其他`（例如只有 S2 不满足，请写明）。

每个标签附一句证据（引用修复前源码的文件和行号即可）。
