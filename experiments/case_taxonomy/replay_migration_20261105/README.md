# 历史回放实验：迁移与迁移后的检测

## 这一轮要回答什么

第二部分的流程是：上游有了一个补丁 → 找到目标架构对应的位置 → 迁移 → 两项检查 → 调用第一部分的检测 → 编译、运行。本轮用42个历史配对（开发集10、测试集32，见`replay_samples_more_20261105/`）回答三个问题：
1. 模型能否写出正确的迁移补丁；
2. 修复策略有没有帮助；
3. 迁移后的检测能否发现迁移补丁中的问题。

| 文件 | 说明 | SHA |
| --- | --- | --- |
| `criteria.md` | 判据，实现之前写定（初稿直接把真实补丁改过的文件给模型，实现之前发现泄露位置，已改） | 见`criteria_sha256.txt` |
| `criteria_amendment1.md`、`criteria_amendment2.md` | 开发阶段对“能否应用”检查的两处修订：忽略hunk行数；按hunk内容重算行数后再模糊匹配 | 同上 |
| `build_prompts.py` → `candidates_*.json`、`prompt_index_*.json` | 迁移提示；候选文件只按参照补丁挑选 | 进入测试阶段时冻结，见`criteria_sha256.txt` |
| `run_calls.py` | 调用，调用记录在`模型调用测试/2026-11-05/replay_migration_20261105/` | 见`delivery_manifest.json` |
| `evaluate.py` → `patches/`、`eval_*.json`、`blind_*.md`、`blind_key_*.json` | 应用检查、定位、改动重合度；隐去条件的比对表 | 同上 |
| `dev_judgement.json`、`test_judgement.json` | 我对“修法一致”的盲判 | 同上 |
| `make_commits.py`、`run_rules.py`、`compile_riscv.py` | 把补丁做成本地提交；RISC-V的程序规则；RISC-V编译检查 | 同上 |
| `build_detect.py`、`detect_sheet.py`、`detect_judgement.json` | 迁移后的模型审查与逐条核对 | 同上 |

## 怎么做的

- **迁移提示**：给模型参照补丁（标题、说明、改动），以及目标架构在跟进之前的**候选文件**。候选文件由程序只根据参照补丁挑选（换架构名后的同路径文件；含参照补丁中函数名、宏名、配置符号的文件；最多5个）。不给真实补丁的任何内容。
- **两种条件**：条件S附修复策略表和两项检查，条件N不附，其余逐字相同。
- **开发阶段**：10对。看了结果后只改了评估中的应用检查，提示没有改。
- **测试阶段**：32对，提示冻结后各运行一次。修法是否一致由我在不知道条件的情况下判断。
- **迁移后的检测**：对能应用的补丁，做一次模型审查（沿用补丁审查第2版：程序收集代码事实，要求引用依据，检查项改成通用写法）；RISC-V的补丁另跑第4版规则和P1、P2第2版。

## 结果

### 1. 开发阶段（10对，20次调用）

- 两种条件都是8/10修法相同。另外2对两种条件都只对一部分：
  - A032照RISC-V只保存FP寄存器，漏了LoongArch特有的LSX/LASX向量寄存器；
  - A052的候选文件没有选到`relocate.c`，漏了处理RELR的核心代码。
- **补丁格式问题很多**：严格应用只通过7/20，失败多是hunk头的行数数错，或者在截取的文件上把行号写成`-1`、`xxx`。为此加了两级检查（修订1、2）：忽略行数后13/20能应用；按内容重算行数后再模糊匹配，又通过7个，20个全部能应用。

### 2. 测试阶段：迁移（32对，64次调用）

| | 条件S（给修复策略） | 条件N（不给） |
| --- | ---: | ---: |
| 修法与真实补丁相同 | **11**（盲判12，事后更正1） | **14** |
| 只做对一部分 | 12 | 11 |
| 不同 | 9 | 7 |
| 能应用（忽略hunk行数） | 15 | 16 |
| 能应用（加上重算行数后模糊匹配） | 20 | 22 |
| 给出了补丁 | 28 | 29 |

- **按参考线**：
  - “迁移能用”要求条件S的“同”不少于60%，实际为34%，**没有达到**；能应用的也只有约一半；
  - “策略有帮助”**不成立**：S比N少3对。1对S对N错（A103），3对N对S错（A104、L121、R014），再加上事后更正的R012。
- **分批**：
  - 第一批11对（按修复筛选），S对2对（更正后）、N对5对；
  - 第二批21对（说明点名参照），两种条件都对9对。

  说明点名参照的样本并没有更容易。
- **定位**：候选文件完全覆盖真实补丁改动文件的只有15/32对。没有候选文件时，模型只能凭记忆写。

**出错原因**（两种条件合计39个补丁，按更正后计）：

| 原因 | 次数 | 例子 |
| --- | ---: | --- |
| 漏改一部分 | 14 | A028漏了Makefile，新文件不会被编译；V011把锁改为读写锁后漏改一处`cond_resched_lock`，无法编译；R012（条件S）没有判断跳转目标是否在替换块内 |
| 程序没有选到要改的文件 | 10 | R014、V007、L082没有候选文件，模型凭记忆写，或者认为不需要改；R014还凭记忆说RISC-V“已经是正确写法”，实际基线正是错误写法 |
| 照搬参照做法，但前提在目标架构上不同 | 7 | L147照RISC-V用`kfree`，但LoongArch的`ctx.offset`由`kvcalloc`分配，应为`kvfree`；L128照RISC-V只扩展`int`参数，漏了按符号标志处理`char`、`short`；A060照arm64在设置页表项时加屏障，LoongArch的真实修复是改用原子写页表项和原子更新PGD/ASID |
| 判断不需要迁移 | 4 | A073认为LoongArch没有x86那种“写内存唤醒”机制；R077把基线中早已完成的通用crashkernel转换又做了一遍 |
| 改在基线中不存在的代码上 | 4 | L081、A077、A087：意图对，但没有候选文件，改的那几行在基线中不存在 |

**修复策略中的两项检查，正对应前两类主要错误**：“同类位置是否都覆盖”对应漏改，“参照前提是否成立”对应照搬。条件S的提示里写了这两项检查，但模型没有照做，条件S的结果也没有更好。

### 3. 测试阶段：迁移后的检测（42次调用）

**程序规则**：RISC-V能应用的9个补丁，第4版规则和P1、P2第2版都没有新标记。漏改造成的编译错误（V011）不在规则的范围内。

**模型审查**（逐条核对见`detect_judgement.json`）：

| | 结果 |
| --- | --- |
| 修法“部分/不同”的补丁中，检测指出了出错原因 | **9/20（45%）** |
| 其中“漏改一部分” | **9/13** |
| 其中“照搬前提不成立” | **0/7** |
| 修法“同”的22个补丁上的不成立标记 | 3条，平均每个补丁0.14条 |

- 按参考线，查出率45%，**略低于50%**；误报每个补丁平均不超过1条，**达到**。
- **检测擅长发现漏改**：
  - A028漏改Makefile（2/2）；
  - V011漏改的`cond_resched_lock`（2/2）；
  - A018改了函数签名但没改调用处；
  - L121、A103补丁为空；
  - A104漏了`bpf_jit_inlines_helper_call()`。
- **检测发现不了照搬前提不成立**：L147的`kfree`/`kvfree`、L128的`char`/`short`、A060的屏障做法、L132的旧接口，7个都没有指出。原因是判断这类错误要知道目标架构自己的事实，例如`ctx.offset`在别处由`kvcalloc`分配，而按固定规则收集的代码事实里没有这些内容。这与第一部分复核中的经验一致：缺了一条架构事实，模型就判断不了。
- **检测还指出了我盲判漏看的问题**：R012（条件S）没有判断跳转目标是否在替换块内。核对代码后成立，事后把该补丁从“同”更正为“部分”。
- **检测指出了补丁格式带来的错误**：A029（条件N）的hunk行数写少了一行，按格式应用后少了最后的右花括号；A103（条件S）的hunk起始行写成1，模糊应用时被放进了文件头注释。修法本身对，但应用后的代码是错的，检测正确指出了。

### 4. 编译检查（RISC-V）

RISC-V能应用的9个补丁（`compile_test.json`）：在`defconfig`加`KVM`、`KEXEC_FILE`的配置下，编译补丁改动的目标文件，打补丁前后都没有错误。

但“只编译补丁改动的文件”会漏掉问题：
- V011的两个补丁改了`mmu.c`，编译通过；
- 检测指出`gstage.c`中漏改的`cond_resched_lock`。我另外编译了整个`arch/riscv/kvm/`目录：
  - 基线通过；
  - 两个补丁都在`gstage.c:417`报错：`passing argument 1 of '__cond_resched_lock' from incompatible pointer type`。

  检测的这条判断成立。这也说明，编译检查要覆盖受补丁影响的整个目录或整个内核，而不只是补丁改动的文件。这次额外的编译不在判据之内，只作核实。

## 看出的几点（只作描述）

- **迁移是可行的，但离可靠还远**：约三分之一的补丁与真实补丁相同，三分之一只对一部分。一半以上的错误不在于“会不会写”，而在于“改哪里”和“目标架构有什么不同”：程序选文件、判断是否需要迁移、核对前提。
- **把修复策略写进提示没有用**：两项检查以文字形式给模型，它并不会照做。要让检查起作用，需要由程序执行：
  - 程序按机制列出同类位置，逐个对照补丁；
  - 程序收集目标架构的相关事实（例如被释放对象的分配方式、寄存器宽度），交给检测。
- **迁移后的检测有用，但分工明显**：漏改这一类，模型审查能发现大部分（9/13）；照搬前提不成立这一类，完全发现不了（0/7）。后者正是第一部分中“由程序给出事实”这条待办要解决的问题。
- **定位是第二部分的第一个瓶颈**：只按名字找候选文件，一半的配对都没选全。

## 局限

- “修法一致”和检测的核对都由我一人完成，有一处盲判错误是检测指出后才更正的。
- 目标架构以LoongArch为主（测试集25/32）。RISC-V只有7对，编译检查也只对RISC-V做。
- 每种条件只运行一次。
- 补丁只在本地使用，没有提交，也没有对外报告。

## 统计

模型调用106次（开发20、测试迁移64、测试检测42，全部完成）；构建：RISC-V 5个基线和9个补丁版本的目标文件编译，另加V011三个版本的kvm目录编译（见第4节）；新确认缺陷0；新疑点0。
