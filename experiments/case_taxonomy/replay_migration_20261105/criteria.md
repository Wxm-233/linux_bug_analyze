# 历史回放实验：迁移与迁移后的检测（判据，实现之前写定）

## 这一轮要回答什么

第二部分的流程是：上游有了一个补丁 → 判断目标架构对应的位置 → 迁移 → 两项检查 → 调用第一部分的检测 → 编译、运行。本轮用`replay_samples_more_20261105/labels_all.json`中的42个历史配对（开发集10、测试集32）回答：
1. **模型能否写出正确的迁移补丁**：给它参照补丁和跟进之前的目标代码，它写出的补丁与目标架构真实的跟进补丁是否一致，能否应用、能否编译；
2. **修复策略有没有帮助**：给修复策略和两项检查（条件S）与不给（条件N），结果有什么差别；
3. **迁移后的检测能否发现迁移补丁中的问题**：对生成的补丁调用检测，检测的标记是否对应真实的错误。

## 一、两个阶段

| 阶段 | 样本 | 做什么 | 调用量 |
| --- | --- | --- | --- |
| **开发** | 开发集10对 | 设计并调整迁移提示的格式；条件S、N各1次 | 20次 |
| **测试** | 测试集32对 | 提示冻结后只运行一次：条件S、N各1次迁移，再对每个生成的补丁做一次检测 | 迁移64次，检测64次 |

开发阶段可以改提示，每改一次写修订并记SHA。进入测试阶段之前，提示冻结。两个阶段的调用量都先报给用户，用户说“开始调用”之后才调用。

## 二、迁移提示

**输入**：
- 目标架构；
- 参照提交的标题、说明（去掉`Signed-off-by`等尾注）和改动（参照架构或公共代码部分，即回放材料中的`reference.diff`）；
- 目标架构在跟进之前（`T^`）的**候选文件**。回放材料中的`target_files`正是T改过的文件，直接给出等于告诉模型改哪里，所以不用；候选文件由程序只根据参照补丁选出：
  1. 参照补丁改动的参照架构文件，把路径中的架构名换成目标架构后，在`T^`中存在的；
  2. 参照补丁中被改的函数名，以及被增删的宏名、Kconfig符号，在`T^`的`arch/<目标架构>/`中出现的文件，按出现的名字个数排序；
  3. 合计最多5个文件。单个文件超过1500行的，只给出包含这些名字的函数，以及文件开头的包含和定义部分，并注明已截取；
  4. 另附这些文件所在目录的文件名列表，以便模型新建或改名文件。
- 定位本身也是迁移的一部分，所以另评“定位”：生成的补丁改动的文件与T改动的文件的重合。

**不给**：真实跟进补丁T的任何内容（标题、说明、改动、改过哪些文件），也不给我标注的机制。

**说明**：判据初稿直接使用`target_files`，在实现之前发现它泄露了T的位置，改为上面的写法；SHA以改后为准。

**条件S额外给出**：`fix_strategy_test_20261105/strategy_table.md`（按机制的修复策略和两项检查），原样附上。

**要求模型输出**：
1. 目标架构需要做哪些修改，各对应参照补丁的哪一处；
2. 统一格式的补丁（`diff --git a/... b/...`），路径相对于内核源码根目录；
3. 需要核对的前提，即参照做法在目标架构上成立所依赖的条件。

两种条件的提示除策略段落外逐字相同，程序检查。模型：Claude-Sonnet-5.5，8路并行，不重试。

## 三、评估

| 指标 | 怎么算 |
| --- | --- |
| **能否应用** | 在`T^`上`git apply --check`；失败的再用`patch -p1 --fuzz=3 --dry-run`试一次，分别报告 |
| **能否编译** | 只对目标为RISC-V的配对：在`T^`加补丁的源码上，用`defconfig`加补丁涉及的配置，编译补丁改动的目标文件；与不加补丁的编译结果比较新增的错误。目标为LoongArch的配对，本机没有LoongArch交叉编译器，安装需要下载，由用户决定；不安装则不报告 |
| **修法一致** | 我对照真实补丁T判断：**同**（改的是同一处、同一种做法，细节可以不同）、**部分**（方向对，但漏了T中的一部分，或多改了T没有改的内容且会造成错误）、**不同**。判断时隐去条件：程序把两种条件的输出打乱顺序、隐去条件名，答案单独存放，判完再合并 |
| **定位** | 生成补丁改动的文件中，T也改动的比例；T改动的文件中，生成补丁也改动的比例（程序）。候选文件中是否包含T改动的文件，单独报告，用来区分“程序没选到”和“模型没改对” |
| 改动重合度（辅助） | 生成补丁与T的增删行，在去掉空白和注释后的重合比例（程序） |

R、L两批分开报告，再报告合计。条件S与N按同一配对比较，报告“S同N不同”“N同S不同”的个数。

## 四、迁移后的检测（只在测试阶段）

对测试阶段每个生成的补丁做一次检测：
- **模型审查**：沿用`patch_rules_v2_20261105/`的L2提示（代码事实、依据要求），把其中的架构和检查项改为通用写法（RISC-V或LoongArch），并附上参照补丁；
- **程序检查**：目标为RISC-V的，另外运行第4版规则和P1、P2第2版（`patch_check`接口）。LoongArch没有对应的补丁场景规则，只做模型审查。

**评估检测**：以“修法一致”的判断为依据。修法为“部分”或“不同”的补丁中，检测指出了导致不一致的那个问题的比例（查出率）；修法为“同”的补丁中，检测报告了真问题以外的标记的比例（误报）。真假逐条由我核对。

## 五、参考线（看结果之前写定）

- **迁移能用**：条件S下“同”不少于60%，且能应用的不少于80%。
- **策略有帮助**：条件S的“同”比N高出不少于10个百分点；不足记为“帮助不明显”。
- **检测有用**：在“部分/不同”的补丁中，查出率不少于50%；在“同”的补丁中，平均每个补丁的不成立标记不超过1个。
- 开发阶段的结果只用于调整提示，不按参考线下结论。

## 六、其他规定

- 生成的补丁和编译结果只在本地使用，不提交，不对外报告。
- 测试阶段每种方法只运行一次。
- 收尾用`round_close`。
