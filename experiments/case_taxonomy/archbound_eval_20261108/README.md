# 师兄静态分析器 archbound 的试用与对照（2026-11-08）

## 这一轮要回答什么

用户把师兄的静态分析器放在主文件夹的 `tool.zip`（SHA256 见 `tool_zip_sha256.txt`），要我查看、试用，比较它与我们目前的工具有什么区别，好用的地方拿过来。具体是三个问题：

1. 它能不能在我们的环境、我们的内核版本（v7.3-rc2）上跑通？
2. 它和我们的边界枚举、检查器在思路和结果上有什么区别？
3. 哪些做法值得拿过来，哪些地方不一定对？

这一轮只做描述性的试用和对照，没有预先设参考线，所以不写 `criteria.md`。数字都只用来描述，不作为“检出率”。

## 它是什么

archbound 是用 C++ 和 LLVM libTooling 写的插件，分两步：

- **collect**：对一个架构的一次构建，逐个解析编译单元，记下函数定义、调用关系、值的流动（赋值、初始化、返回）、共享资源的读写、`__HAVE_ARCH_*` 宏等“事实”，存成一个 JSON。
- **analyze**：把几个架构的事实放在一起，按**同名函数**跨架构比较，输出“测试点位”。测试点位就是给后续定向模糊测试用的目标位置，每个点位带一个类别：
  - `width/param`：公共侧实参类型与架构侧形参类型的宽度不一致，例如 `u64` 传给 `unsigned long`；
  - `width/global`：全局变量在固定宽度类型与架构宽度类型之间赋值；
  - `empty-impl`、`const-ret`：同一函数在某架构是空实现或直接返回常数，另一架构有真实实现；
  - `call-context/resource-missing`：同一函数在架构 A 写了某个共享资源，架构 B 没写；
  - `call-context/call-missing`：同一函数在架构 A 调了某个会写共享资源的公共函数，架构 B 没调；
  - `call-context/param-check`：危险用法（下标、长度、移位、解引用）之前，A 检查了参数、B 没查。

它正好对应师兄方向文档里的三类检查，文档结果表里的数字（1075、2235、133/136、248、1、158）就出自它，当时用的是 v6.1 和 x86、i386、arm64、riscv 四个构建。

## 我做了什么

1. **编译**（`scripts/build_archbound.sh`）：
   - 原 Makefile 写死了师兄机器上的 LLVM 15 路径，我没有改它，另写脚本，用 WSL 里已装的 LLVM 18 编译；
   - 只改了一处 API 名：`clang::InternalLinkage` 在 LLVM 18 里改名为 `clang::Linkage::Internal`；
   - 改动只在 WSL 的副本 `/root/work/archbound` 里，压缩包没动。
2. **自带样例**（`scripts/fixtest.sh`）：
   - `_fix` 样例的点位与师兄的 `p.json` 类别、数量完全一致（5 个：width/param 1、width/global 1、empty-impl 2、resource-missing 1）；
   - 他附的 `r.txt` 是更早版本的报告，当时还没有 `call2.c`，所以文字对不上。
3. **真实内核**：
   - 用我们已有的三个构建：riscv defconfig、x86_64 defconfig、RV32（`closure_20261108_rv32_abi`）。RV32 的作用相当于他用的 i386，用来暴露 32 位上的截断。
   - **第一次不限范围**（`scripts/collect_kernel.sh`）：三个构建都在写结果时被系统按内存不足杀掉。它把整个构建的事实放在内存里，峰值 14.6 GB，WSL 只有 15 GB。
   - **改成只收集判据范围内的 `.c` 单元**（`scripts/scope_list.py`、`scripts/collect_scope.sh`）。范围与 `checks_v1_20261108` 判据第二节相同：`arch/<架构>/`、`kernel/`、`mm/`、`lib/`、`init/` 和几个与架构相关的驱动目录，三个构建分别是 963、1084、728 个文件。峰值内存 7.1–8.3 GB，每个构建用时 2.5–4.5 分钟。
   - **解析错误的核对**：这次几乎每个单元都报 1 个错误，内容全是 `error opening '…/.xxx.o.d'`。原因是内核编译命令里的 `-Wp,-MMD,<依赖文件>` 是相对构建目录写的，多线程运行时进程当前目录不对，依赖文件写不进去。我做了一份去掉这个参数的编译数据库副本（`scripts/nomd.py`），重跑 riscv：错误降到 0，定义、调用、值流等 7 项计数与之前**完全相同**。所以这类错误不影响收集到的事实，三份数据都有效。
4. **分析**（`scripts/analyze_kernel.sh`）：三份事实一起分析，峰值内存 7.9 GB。
5. **样本对照**（`scripts/compare_samples.py`、`scripts/scope_fair.py`、`scripts/inspect_hits.py`）：
   - 用 `boundary_closure_20261108/sample_match_v2.json` 里每条样本修复改动的实体（函数、宏、对象），以及它们在当前内核中的行范围；
   - 点位里的函数名、全局变量名与实体同名，或者点位位置落在实体的行范围内，就算点位“碰到”这条样本。

| 检查 | 样本数 | archbound 点位碰到 | 我们的边界（riscv） | 我们的边界（三架构并集） | 只有 archbound 碰到 |
| --- | ---: | ---: | ---: | ---: | ---: |

| 二、实现完备性 | 57 | 17 | 34 | 35 | 0 |

只比较实体落在同一范围内的 108 条样本：我们的边界命中 73 条，archbound 碰到 29 条，这 29 条我们的边界全部覆盖。我们命中、但实体完全在范围外的样本只有 2 条（B485、B584）。

碰到的 29 条里，23 条是被 `width/param` 碰到的。

## 看出的几点

1. **“碰到”大多是巧合，不是对准缺陷。**
   - A118（`die()` 里在原子上下文中拿 RT 锁）：碰到它的是 `die` 在 riscv 与 x86 之间调用了哪些公共函数的差异。x86 的 `die` 结构不同，没有直接调 `add_taint`、`bust_spinlocks`。这与缺陷无关。
   - B494（cpuidle 只给在位 CPU 初始化）：碰到的是同一文件里 bool 全局变量被赋了 int 值。
2. **类别与缺陷对得上的例子也有。**
   - A274（riscv 缺了 ACPI LPI 上下文丢失标志的处理）：修复后，`arch_get_idle_state_flags` 出现 const-ret 不对称。x86 用 `include/linux/acpi.h:1594` 的公共默认实现返回常数，riscv 在 `arch/riscv/include/asm/acpi.h:80` 自己实现。这正是“实现完备性”要找的形态。
   - A123、A303（`setup_bootmem` 地址越界）：碰到 `phys_addr_t` 与 `unsigned long` 之间的全局赋值（`max_pfn`、`memory_limit` 等），在 RV32 上与“数据一致性”相符。
3. **它只看当前代码。** A192（clone_flags 截断）是它文档里的标杆。在 v7.3-rc2 上已经修好，它的位宽点位也随之消失，只剩一个无关的 `pt_regs.a0` 写不对称。这说明它表现符合预期；但用“修复后的版本”对照样本，本身就测不出检出能力，我们的样本匹配也有同样的局限。
4. **两者是互补的。** 它是跨架构对照，我们是单架构穷举加保障。它碰到的样本全在我们的边界里，说明我们的边界可以作为它的“候选全集”；它的对照规则，正是我们还没实现的检查二。

## 好用、值得拿过来的

1. **按同名函数跨架构对照的框架**：直接覆盖师兄定义的“调用上下文”（写缺失、调用缺失、检查差异）和“实现完备性”（空实现、常量返回）。
2. **共享资源与架构私有资源的判定**：结构体定义在 `arch/` 下算私有（如 `pt_regs`），在 `include/linux/` 下算共享（如 `task_struct`）。简单，能滤掉寄存器类噪声。
3. **调用缺失的降噪办法**：只报“漏调的公共函数会写共享资源”的。他用它把 1308 条降到 158 条，`printk` 一类全部滤掉。我们检查三①的噪声主要来自 printk，可以借用这个思路。
4. **用 32 位构建暴露截断**：我们已有 RV32 构建。
5. **点位 JSON 格式**：每个点位只属一类，只带该类需要的字段，已经考虑了怎么接 SyzDirect，可以作为我们输出的统一格式。

## 不一定对、要改的

1. **同名家族每个架构只取第一个定义**（`Analyze.cpp` 的 `byArch` 首次写入后不再覆盖）。同一架构有几个同名函数时，只比较其中一个，会漏，也可能比错。
2. **只按名字归组**：名字不同、作用相同的实现归不到一组，我们的边界枚举里有这层对应关系。
3. **常量返回只认“函数体只有一句 return”**，多一行就算正常实现。
4. **不统计单元解析失败**：出错只打印，结果照样输出。这次的 `.o.d` 错误碰巧无害，但真有致命错误时不会提示。
5. **汇编文件也当 C 解析**：不限范围时，`.S` 文件会产生大量错误。
6. **内存占用大**：事实全放在内存里；全构建要 14.6 GB 以上，WSL 跑不下。

## 局限

- 只用了 riscv、x86_64、RV32 三个构建，没跑 arm64；范围限定在判据第二节的目录。
- “碰到”只看名字或位置重合，不判断类别是否对应缺陷；上面的逐条判断只抽查了 7 条。
- 都是在修复后的当前版本上对照，不是在修复前的代码上检测，不能当作检出率。
