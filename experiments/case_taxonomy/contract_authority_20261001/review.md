# 契约依据补全：表示域交接的源码链与证据门控

2026-10-01，继续 D2/D3。本轮完成已读案例的来源和本地读端补证、原响应/读端函数的大小端投影，以及证据门控的有限开发。没有新确认缺陷，也没有可运行的独立同机制留出。

## 本轮补齐的机制证据

`source_authority/` 核对 HCI 父版 `cef456cd354ef485f12d57000c455e83e416a2b6` 的五个源码文件、Git blob、全文件 SHA、原文行号与全树直接引用。父版及已选修复提交的 committer 日期为 2019-10-16，不能以此代替缺陷实际发现日。

来源成员不仅声明为 `__u16`：默认值为数值常量 `0x001b/0x0148`，成功读取最大数据长度的响应经 `le16_to_cpu()` 存入主机成员；失败则保留此前值。全树八处直接字符串引用支持这一有限审阅，不是全程序数据流或别名证明。init3 读取、init4 写出受设备类型/LE/数据长度特性等源码条件约束；同步初始化有阶段顺序，但本轮没有证明真实控制器的响应和执行路径。

写入 `HCI_OP_LE_WRITE_DEF_DATA_LEN` 的参数声明为 packed `__le16` 两字段，构造器原样复制参数。实际 Linux 命令完成读端从保存的已发参数取值，再用 `le16_to_cpu()` 更新默认长度。故本轮的局部源码契约比只靠字段名称更充分：**来源已是主机数值，字节参数及本地读端要求小端解释**。外部设备仍是另一证据层，不能由本地回调自证。

系统层可在这个主机数值→固定格式交接处集中检查/转换；检查落点要在原样复制前，并受具体接口和适用条件限制。不能看到主机整数复制就一律要求 LE：内部同主机 host/host 仍是必要正常对照。

## 原源码局部链的运行结果

`provider_projection/` 保留完整原响应函数和原命令完成读端，发送赋值来自上一轮冻结生成计划。注入三组有限响应值后，核对响应解码、主机成员、发送字节和实际 Linux 本地读端；采用现有 x86_64 GCC 和 s390x GCC/QEMU 用户态环境。

| 三组响应输入 | 小端原型：格式不符 | 大端原型：格式不符 |
| --- | --- | --- |
| 原响应解码＋父版发送赋值＋原完成读端 | 0/3 | 3/3 |
| 原响应解码＋修复版发送赋值＋原完成读端 | 0/3 | 0/3 |

三组来源成员均先还原正确主机数值；旧发送在大端写出主机字节，本地 LE 读端因而还原不同值。Python 分别由输入值计算实际生产关系、所需字节及读端解释，没有用 C 的 pass 标签反推预期。另有响应非零状态、写完成非零状态、缺少已发数据三个对照，两端均保留此前成员。失败响应后不模拟发送，避免假设未知请求调度路径可达。

两目标各六条正常链结果加三条分支控制，不是新增九个案例。原型使用投影后的 `hci_dev/sk_buff`、转换桩和注入的已发命令上下文；没有执行初始化请求队列、真实控制器、原历史内核或完整配置，也未证明所有值域、别名或生命周期。

## 接口权威的状态与自动化边界

`authority_gate.py` 重新核对冻结生成计划、卡的修订/函数/对象/完整字段绑定，以及精确原文、行号、文件 SHA 和版本元数据。语义结论必须归属于审阅者，不能从引用匹配自动推出。门控不给自动修复或新样本真值，不改冻结提取器的 candidate/matched 标签。

锁定版 17 项测试通过，最终记录为 `root_test_final_lock.json`；早期 16 项测试原样保留。已读真实材料的最终运行在 `development_final_lock/`，五项有限状态对照为：

| 输入依据 | 门控输出 |
| --- | --- |
| 已归属的同版来源/本地读端/源码条件审阅 | `source_contract_ready`：仅局部审阅材料齐备 |
| 外部历史规范未核对 | `conditional` |
| 缺字段来源引用 | `insufficient` |
| 已报告证据冲突 | `conflict` |
| 没有审阅卡 | `insufficient` |

所有机器契约已证、运行可达、完整内核、外部协议已证标志都保持 false。`source_contract_ready` **不是**全自动证明接口正确，也不是领域人员确认。独立审计把某字段引文换为另一字段的真实同版引文，引用仍能匹配；这暴露门控不能认证引文是否足以支持逐字段语义。因此引用完整性、字段绑定与语义审阅分别报告，不能把它称为自动提取权威真值。

同版源码和本地读端已得到支持；Bluetooth SIG 较新 5.4 文本提供小端及命令版本的旁证，但历史 Core 5.1 正文未得到核对。当前规范不能无说明替代历史适用文本，外部历史格式保留条件性。来源、消费者与版本/模式冲突时标冲突或不足，不按架构多数、修复补丁或“往返成功”裁定。

## 有限独立验证为何未运行

`selection/` 先固定 2016—2022 Bluetooth/HCI 标题和路径元数据，39 条，最多选择两条；未读目标补丁、commit body 或父版源码。优先 hci_core 的标题匹配仅三条，唯一明确端序项已用于开发。全池七条明确端序/转换标题中六条 SHA 已见于此前材料，剩下一条是 Makefile 端序检查标志；其他 convert 标题主要为 API 迁移，不能合理预期同一直接字段写出形状。

因此 `selected=[]`，独立检测执行零次，按协议停止。它只说明这个关键词、版本和路径池没有适配未读材料，不能说明其他案例不存在、检测器得到真阴性或泛化已经成立。未依据检测输出换例，也未扩大池获取阳性。

这里采用保守的“此前任何 SHA 提及即排除”标准，标题/元数据提及并不等于源码参与过开发。因此零项也受该排除口径影响；未来若重新设计独立试验，应事前区分元数据暴露和实际源码/补丁暴露，不能追改本轮选样或将其解释为真实样本耗尽。

## 当前结论与下一步

四类初步 Pattern 仍保留；本轮为“表示不一致”补出一个具体机制：一个接口先把外部格式转成主机数值，后续另一个接口误把该数值直接当成固定格式字节。可检查的应是表示域交接及其真正读端，而不是单独看类型名或只验证写读自洽。

老师的两个问题有实质进展：受限源码形状能自动生成条件检查；局部契约可追到来源及实际读端。但依赖审阅的证据门控不等于自动语义证明，外部历史规范与通用独立泛化仍缺。固定 12 条保持 6/5/1；C1–C4 的专家纳入/发现日期、D3 全部争议、D4 NUMA 边界状态不变。

下一轮不继续扩大同一标题池。优先做一次有限的初始化入口/特性关闭对照：保留真实条件分支，验证候选检查在参数消费前何时应启用、何时不适用，区分源码投影和实际内核路径。同时保留历史规范或领域裁定的缺口，得到材料前不把门控升级为外部强制规则。
