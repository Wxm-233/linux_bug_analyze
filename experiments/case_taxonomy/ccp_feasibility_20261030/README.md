## 设定

公共层改动C改变了约定，后来的修复T（`Fixes:`指向C）在C没改过的架构目录中，修改了一个已有函数的函数体。检查任务是：给定C，找出这些需要跟进的架构位置。

候选的生成方式：在C合入时的代码树中，取C没改过的架构目录下、函数体含有C的接口标识符的函数。接口标识符取自C在公共层增删行中的名字，要求全树出现的文件数不超过500。

冒烟测试用一个已读案例（kexec约定`KEXEC_BUF_MEM_UNKNOWN`）：候选池116个函数，x86漏改的函数排第2位。

- 覆盖不足几乎全部来自“T没有提到C的任何接口名”的那一半。
- 可能的解释：这些T修的并不是“使用方没跟上C的约定”，而是C带来的其他后果。这与此前人工标注的观察一致：“从引入点出发”的36对中，真兄弟只有15对。
- 但这一点没有经过核实。用“是否含有接口名”来定义任务会形成循环论证，不能直接把这一半排除。
- 命中的配对候选池较大（中位数300），未命中的较小（中位数60）。候选池大时更容易“碰上”，所以覆盖率里也含有池大小的影响。
