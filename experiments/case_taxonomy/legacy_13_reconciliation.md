# 旧称“13 条源码案例”的清单与原型对应关系

整理日期：2026-09-28。来源是 Windows 每日单份日志：`日志/2026-09-12.md` 的 C1–C8、`日志/2026-09-14.md` 的 C9–C13，以及 `日志/2026-09-15.md` 对九项原型和四项未做原型的汇总。本表是**找回原始卡片身份并按提交去重**，不是对每项重新阅读 Linux 源码、领域专家确认或安全漏洞统计。

| 原卡 | 当时的核心提交 | 旧原型对应 | 目前纳入口径及仍缺证据 |
|---|---|---|---|
| C1 Btrfs | `6f93e834fa7c` | 有，同一修复提交 | 参数就绪/磁盘几何的源码与顺序原型；真实挂载、首次故障日期未核实。 |
| C2 mlx5 SHAMPO | `d8a7ed9586c7` | 无 | 页大小×MTU/WQE 粒度的源码分析；未做历史驱动运行或设备验证。 |
| C3 NUMA compat | `e130242dc351` | 有，同一修复提交 | native/compat 字宽与边界原型；剩余输入与完整入口契约未裁定。 |
| C4 s390 回溯 | `88b604263f3d` | 无 | 栈帧起点与公共回溯消费者的源码分析；未做历史执行原型。 |
| C5 s390 拓扑 | `a052096bdd68` | 有，同一修复提交 | 热插拔通知时序/掩码原型；真实内核通知链未运行。 |
| C6 ARM SMMUv3 | `8c73c32c83ce` | 有，同一修复提交 | 域状态转换原型；真实设备可见 DMA/并发未验证。 |
| C7 VT-d | `6f5dc7658094` | 有，同一修复提交 | 页表权限原型；真实设备 DMA/IOTLB 后果未验证。 |

| C9 parisc | `d97180ad68bd` | 有，同一修复提交 | 函数级原型曾完成，但该修复后来被撤销；**不能计持久有效修复缺陷**。 |
| C10 fbnic | `4bd451f4c285` | 有，同一修复提交 | 描述符片段原型；大页触发条件在历史支持配置外，补丁说明为防御性改进。 |
| C11 perf | `aa6a6a2d16c1` | 有，同一修复提交 | s390x 大端用户态工具原型；与内核核心缺陷分层。 |
| C12 pata_falcon | `8847d42d7a02` | 无 | 同 CPU 下不同介质格式的兼容能力扩展；不称已确认回归。 |
| C13 ACPI | `aa06e20f1be6` | **相关但不同锚点**：九项原型台账使用 `adbf61cc47cb` 及历史状态 | 同一 ACPI CPU 条目/能力主题下的多阶段修复；需按独立根因、入口与版本进一步排重，不能把两个提交静默当成一个缺陷。 |

因此，“13 条”是 **13 张原始源码卡片**；2026-09-15 所说的“九项已有原型”中，八项可与本表同一修复提交直接对应，ACPI 是**主题相连、锚点不同**的一项历史链原型。其余四张（mlx5、s390 回溯、fw_devlink、pata_falcon）当时未做原型。九项原型的验证层级与后续修正见 [`historical_inventory.md`](historical_inventory.md)；固定 500 中另选的 12 条及其 6/5/1 是**后来的另一批目的性样本**，见 [`case_reviews.md`](case_reviews.md)，不能把两批原始数字直接相加成不重复缺陷总数。

下一步需要逐条补“是否纳入已确认跨架构缺陷”的领域裁定，并对 ACPI 多阶段修复、可能共用根因的同子系统样本做因果排重。当前仅找回原始 13 卡的提交清单和原型映射，没有补出首次发现日期；老师要求的引入→发现、发现→修复两个时间段仍按可核实来源逐项留空。新发现的 bcachefs 大端字段名案例也另列，不追溯塞回这 13 卡。
