# “以arm64为参照”检查RISC-V的适用条件（方向4机制结论）

## 一句话结论

**当RISC-V与arm64处理的是同一种数据形态，并且对应关系落实到同名的钩子和函数时，“以arm64为参照”能在修复之前标出RISC-V的问题，而且每次只需人工看几条；离开这个条件，这个参照就不起作用。**

## 要回答的问题

研究目标是从已确认的跨架构缺陷中提炼共性机制，并检验这些机制能否指导自动检测，当前以RISC-V为重点。

方向4试的是一种很直接的机制：RISC-V是较新的架构，arm64是成熟的架构，而且两者在不少地方很像。那么能不能拿arm64作参照，找出RISC-V该做而没做的东西？

前后做了五轮，下面汇总结果，并归纳它在什么条件下有效。

## 证据汇总

| 轮次 | 怎么用arm64作参照 | 结果 | 有效吗 |
| --- | --- | --- | --- |
| 接口完备性对比 | arm64提供了、RISC-V没提供的约定接口（配置开关、宏、可覆盖函数） | RISC-V补接口的20个修复中，修复前已在清单上的：只看arm64作参照为12个（60%），要求x86和arm64都提供为6个（30%）。但每个版本的清单约有一百条，多数是可选功能 | 部分有效：召回不低，准确率低 |
| 大页第一轮 | arm64覆盖了、RISC-V没覆盖的大页钩子 | 两类机制的5个修复中，4个在修复前被标出；每次只标出4–5条；当前代码7条标记均不是问题 | 有效 |
| 大页第二轮 | 同名函数中，arm64做了的处理步骤，RISC-V有没有做 | 4个“RISC-V自身NAPOT实现错误”全部能在修复前标出（这4个同时是设计数据）。另有一条独立证据：arm64修了`huge_ptep_get_and_clear`，三周后RISC-V在同名函数上修了同一个问题，修复说明直接引用了arm64的修复 | 有效 |
| 第三轮：推广到全部家族 | arm64修复新加了一步，RISC-V同名函数有没有 | 跟进率4.8%，基线5.3%；x86→RISC-V、arm64→LoongArch同样无效 | 无效 |
| 第四轮：页表遍历家族 | 钩子覆盖＋步骤比较 | 7个机制案例只标出1个；每次最多标出32条 | 无效 |

## 函数层对应率（看过上述结果之后补测，描述性）

| 家族 | RISC-V函数中arm64有同名定义的比例 | 机制案例中，修复当时arm64有同名函数的 |
| --- | ---: | ---: |
| 大页 | **83%**（19/23） | **8/9** |
| 页表遍历 | 54%（178/333） | 3/7 |

大页家族里，RISC-V的NAPOT大页和arm64的连续页一一对应：钩子同名，处理函数也同名，例如`set_huge_pte_at`、`huge_ptep_get`、`get_clear_contig`。页表遍历家族虽然也是“多级页表”，但RISC-V的很多函数在arm64里没有同名对应，例如：

- 内存热拔：RISC-V的`remove_pud_mapping`在arm64中叫`unmap_hotplug_pud_range`；
- `vmalloc_fault`：arm64根本没有这个函数；
- 运行时决定页表级数相关的宏和判断，arm64也没有对应。

## 适用条件

把五轮放在一起看，“以arm64为参照”要起作用，需要同时满足以下几点：

1. **数据形态相同。** 两者偏离的是公共代码的同一个默认假设。大页上，公共代码默认“一个大页对应一个页表项”；RISC-V的NAPOT和arm64的连续页都用“一组表项”表示一个大页，所以都得覆盖同一批钩子、做同样的处理步骤。如果只有RISC-V偏离，例如运行时决定页表级数，arm64就没有可供参照的写法。
2. **对应关系落实到函数这一层。** 同名的钩子、同名的函数要真实存在，检查才能逐个对照。只是“都属于页表相关代码”这种家族层面的相似是不够的：页表遍历家族的函数同名比例只有54%，机制案例中只有3/7有对应。
3. **arm64走在前面。** arm64的连续页大页早在2017年前后就有了，RISC-V的NAPOT是2023年才加入的。arm64已经踩过的坑，RISC-V后来又踩了一遍，例如“不能用表项的值推出映射大小，因为表项可能不在内存”。时间差越大，参照越有用。
4. **问题出在“该做的事”上，而不在硬件或平台特性上。** 以下这些arm64修复对RISC-V没有意义：
   - arm64专有的硬件特性：MTE、NMI、各种CPU勘误；
   - RISC-V专有的机制：运行时页表级数、SBI；
   - 通用的加固写法，例如加`WARN_ON_ONCE`、`READ_ONCE`。

   第三轮之所以无效，主要原因就在这里：arm64的修复大多属于这几类。

**不满足时的表现**：

- 第三轮全局扫描中，提醒的跟进率与基线没有差别；
- 第四轮页表遍历家族中，机制案例很少能被标出，标记也多；
- 完备性对比中，清单很长且多为可选功能。

## 和早期结果是一致的

- **P1/P1′**（让模型读修复、写搜索规则去其他架构找）失败，原因之一是规则带着原架构的函数名和写法，换个架构就对不上。这正好从反面说明，函数层的对应关系是关键。
- **结构基线**（去其他架构的同一相对路径找）只在各架构有平行实现目录时有效：层内约三分之二命中，层外为零。这也是“对应关系要落到具体位置”的体现。
- **接口完备性对比**中，只用arm64作参照的召回（60%）比要求x86和arm64都提供（30%）高一倍。这说明对RISC-V而言，arm64是比x86更合适的参照。

## 能转化成什么检查

1. **同形态家族的“钩子覆盖”检查**：arm64因为某种数据形态覆盖了的公共钩子，RISC-V若也有这种形态，就应该覆盖。大页上回溯4/5，每次只有几条。
2. **同形态家族的“步骤比较”检查**：同名函数中，arm64做了的关键步骤，RISC-V也应该做。大页上回溯4/4。
3. **“跟随arm64修复”提醒，限定在同形态家族**：arm64在这些家族里合入修复时，自动比较RISC-V的同名函数。全局用无效，限定后有一条独立的历史证据。

使用前要先判断某个家族是否满足条件1和2。函数层对应率可以作为一个简单的初筛指标：大页83%有效，页表遍历54%无效。不过这只有两个点，阈值定不下来。

## 局限

- 有效的证据都来自大页一个家族；独立的历史证据只有1条。
- 大页第二轮的4个回溯案例同时是设计数据。
- 函数层对应率是看过结果之后补测的，只有两个家族，说明不了阈值。
- 疑似问题没有一条经过运行验证：`show_pte()`、`huge_ptep_clear_flush`、`pud_free_pmd_page`。

## 对研究目标的意义

- 这是方向4对“机制能否指导检测”这个问题的回答：**能，但有明确的前提**。机制要落实到“同一种数据形态、函数一一对应”的层面，指导才有效。
- 这也解释了此前几条路线失败的共同原因：要求、模式或参照停留在笼统的层面，没有落实到具体的对应位置。
- 写进论文时，可以作为一个有正例、有反例、有边界的机制结论：大页上有效，全局扫描和页表遍历上无效，原因是对应关系的粒度。
