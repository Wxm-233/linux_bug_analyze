# 检查三①“执行上下文”第一版（checks_v1_20261108）

## 这一轮要回答什么

三类检查里，第三类“调用上下文”在 11-06 被我精炼为“调用发生时的状态”。这一轮先做其中第①项：**执行上下文**，即在原子上下文中做了不该做的事。具体找三种失配：

- **S 类**：在原子上下文里调用了可能睡眠的函数。原子上下文指关中断、持自旋锁、禁抢占这些不允许调度的状态。
- **I 类**：在硬原子上下文（关中断或持 raw 自旋锁）里发 IPI 并等待其他 CPU 完成。IPI 指处理器间中断。
- **R 类**：在硬原子上下文里拿 `spinlock_t`。它在 PREEMPT_RT 内核里会变成可睡眠的锁。

要回答三个问题（判据 `criteria.md` 第一节）：
1. 能否用纯静态分析，保守地把这类失配找出来？
2. 6 条已知样本，在各自修复前的代码上能否报出？
3. 当前版本 v7.3-rc2 上报出多少，其中多少像真问题？

**参考线**（判据第六节）：
- 6 条样本命中不少于 4 条，记为“检出能力达标”；
- 从当前版本随机抽 40 条标记人工核对，疑似真问题不低于 25%，记为“噪声可接受”；
- 两条都满足，本轮才算达标。

判据写于实现之前，SHA 记在 `criteria_sha256.txt`。之后写了三次修订，都只修我自己的工具、加防护，没有改判据、阈值、样本或期望集：
- **修订 1**：实现前补了 7 处宏展开上的疏漏；
- **修订 2**：抽取器没切到编译目录，导致配置宏全部丢失，第一次评估作废；
- **修订 3**：分析器没按判据 3.3 停止展开原语和前缀函数；续跑时防护误把缓存单元当成不干净。

## 我做了什么

1. **抽取**（`ctx_extract.py`）：用 libclang 把范围内每个函数体转成结构化的中间表示，按单元缓存，可以断点续跑。范围是 riscv 的 `arch/riscv/`、`kernel/`、`mm/`、`lib/`、`init/` 和几个与架构相关的驱动目录，当前版本共 764 个单元。
2. **分析**（`ctx_analyze.py`）：
   - 在调用图上求“可能睡眠 / 可能发 IPI / 可能拿 RT 锁”三个性质的闭包；
   - 在每个函数里做结构化数据流分析，跟踪 `(关中断, raw 锁, 普通锁, 禁抢占)` 计数，覆盖 if/else、循环、switch、goto；
   - 函数入口状态有三个来源：陷入入口（RISC-V 进入异常时中断已关）、IPI 回调、调用者传播。在调用图上迭代到不动点；
   - 最后在每个调用点判断，报出 S/I/R 标记。
3. **自测**（`selftest/`）：迷你内核树，11 条期望标记必须完全一致。修订 2、3 各加了一项检查，并做了反向检查：把修正去掉，自测就会失败。
4. **评估**（`eval_samples.py`）：对当前版本和 6 条样本修复前、修复后的版本，各自导出源码、构建（共 13 个内核）、抽取、分析，再计分。
5. **人工核对**（`review_sample.py`，结果出来之前写定，种子 20261108）：从当前版本抽 40 条标记，逐条回内核源码判断。

## 结果

### 6 条样本：按判据 6/6 命中，检出能力达标

我逐条看了命中标记里有没有真正对应该缺陷的一条（`sample_hit_review.json`）：

| 样本 | 缺陷 | 对上缺陷的标记 | 修复后 |
| --- | --- | --- | --- |
| A076 | DEBUG_PAGEALLOC 在原子上下文中拿 init_mm 写锁 | `__set_memory → mmap_write_lock`，来源链 `__kernel_map_pages < debug_pagealloc_map_pages < post_alloc_hook` | 消失 |
| A118 | 陷入中 `die()` 拿 RT 下会睡眠的锁 | `die → spin_lock_irqsave(die_lock)`（R） | 消失 |
| A122 | kfence 关中断时刷 TLB 发 IPI | `kfence_protect_page → flush_tlb_kernel_range → … → on_each_cpu_mask`（I） | 消失 |
| A158 | 未对齐陷入中关中断调 `copy_from_user` | `handle_scalar_misaligned_load → copy_from_user` | 消失 |
| A175 | 用户态 `ebreak` 陷入时关中断调 `force_sig_fault` | `handle_break → force_sig_fault` | 仍在 |
| A344 | 同 A158 一族，修法是开中断 | `do_trap_load_misaligned → do_trap_misaligned` 等 4 条，对应较弱 | 仍在 |

- 4 条有真正对上的标记，而且修复后消失，说明分析确实抓到了这些缺陷。
- A175、A344 的修复是“如果来自用户态就开中断”，这是一个 `user_mode(regs)` 的条件分支。我的分析不区分路径，内核态那一支仍然关中断，合并后还是“可能关中断”，所以修复前后分不出来。
- 每条样本的“命中标记”有 4 到 234 条，真正对上缺陷的只是其中少数，其余只是性质链或来源链恰好经过修复改动的函数。

### 当前版本：30584 条标记，噪声不可接受

| 项 | 值 |
| --- | --- |
| 单元 | 764，全部解析干净 |
| 函数 | 42078；陷入入口 22 个；IPI 回调 49 个 |
| 可能睡眠 / 可能 IPI / 可能 RT 锁的函数 | 13933 / 13410 / 13915 |
| 标记 | 30584（按调用位置去重 30314）；S 10760、I 9736、R 10088 |
| 状态来源 | 函数内 5039，入口传播 25545 |
| 不在保障内、已计数 | 间接调用 2268，内联汇编 10351 |

人工核对 40 条（`manual_review.json`）：**疑似真问题 0 条**、不是 38 条、判断不了 2 条。疑似占比 0%，远低于 25%。误报原因按次数：

| 原因 | 次数 | 例子 |
| --- | ---: | --- |
| 早期启动阶段关中断 | 12 | `start_kernel` 调 `workqueue_init_early`，此时单线程，内核允许拿睡眠锁 |
| 性质链经过 `preempt_schedule*` | 11 | 它只在抢占计数降到 0 时才被调用，那时已不在原子上下文 |
| 性质链经过 printk | 9 | `_printk → … → console_unlock`，原子上下文里 printk 只会 trylock 或推迟输出 |
| 入口状态由别的调用者合并而来 | 6 | `kthread_unuse_mm` 在 `task_unlock` 之后才 `mmdrop`，却被标成持 raw 锁 |
| 运行时条件没有建模 | 4 | `__xas_nomem` 只在 gfp 允许阻塞时才先解锁再分配 |
| 其他 | 3 | 锁配对建模不准；`smp_call_function_single_async` 不等待；riscv 的 CPU 定时器在 RT 下走任务上下文 |

（一条标记可以有多个原因。）

**本轮结论：检出达标，噪声不达标，本轮不达标。**

## 看出的几点

1. **方向上可行**：执行上下文类缺陷能用纯静态分析抓到。6 条样本里 4 条精确对上，并且修复后消失。
2. **噪声来自几处判据层面的缺口，都能对症处理**，但按规则只能放到下一轮，先改判据：
   - 前缀规则漏了宏展开后的名字：`pr_warn` 展开成 `_printk`、`WARN` 展开成 `__warn_printk`；
   - `preempt_schedule*` 不应算作“可能睡眠”链的一环；
   - 早期启动阶段（`start_kernel` 开中断之前）不应算原子来源；
   - 陷入入口规则 (a) 收进了 `ret_from_fork_user`、`schedule_tail` 这类不是陷入处理的函数；
   - 入口状态在调用者之间合并，丢掉了调用路径，需要按调用上下文区分；
   - `user_mode(regs)` 这类分支不区分，导致修复前后分不出来。
3. **这一项是单架构检查，跨架构的成分只在陷入入口规则上**。它和师兄方向文档里的“调用上下文”（跨架构的写缺失、调用缺失、检查差异）不是一回事。那部分可以借用师兄的 archbound，见 `../archbound_eval_20261108/README.md`。

## 中途作废的两次结果

- `invalid_run1_autoconf/`：抽取器解析前没切到编译数据库的 `directory`，相对的 `-I./include` 失效，`generated/autoconf.h` 找不到，配置宏全部丢失，所有单元都是 fatal。修订 2 修正。
- `invalid_run2_opaque/`：分析器在调用点仍用原语和 `trace_` 等函数自己的闭包报标记，与判据 3.3 不符。修正后，当前版本的标记从 33628 降到 30584。修订 3 修正。

## 局限

- 范围外的调用者带来的原子上下文会漏；间接调用、内联汇编、跨函数持锁、softirq/NMI 等不在保障内，已计数。
- 没有构建 PREEMPT_RT 配置，R 类按原语识别。
- 样本只有 6 条，都在 riscv 陷入和内存管理路径上。
- 人工核对由我一人完成；“判断不了”的 2 条没有追查到底。
