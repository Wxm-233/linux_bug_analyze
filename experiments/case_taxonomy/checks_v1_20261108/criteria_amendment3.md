# 判据修订 3（2026-11-08 15:10，Claude，写于样本目标分析之前）

续跑第二次评估时，我在人工核对当前版本的抽样标记过程中，发现分析器 `ctx_analyze.py` 有一处没有按判据 3.3 实现。这是我自己代码的错误。按失败规则，本修订只修工具，**不改任何判据、阈值、样本或期望集**。

## 发现的问题

判据 3.3 规定了两类函数“不向下展开”：

- 原语函数，即 3.2 原语表里的函数，包括睡眠种子和 IPI 种子；
- 以 `pr_`、`printk`、`trace_`、`WARN` 等前缀开头的被调函数。

代码只做到了一半：它不让这些函数的性质沿调用边往上传给调用者，但还有三处没挡住。

- **调用点照样报。** 在调用这些函数的地方，代码仍然用被调者自己的闭包来报标记。
- **函数体照样分析。** 这些函数的函数体照样接收入口状态，也照样参加分析。
- **函数体照样产生性质。** 这些函数体里的调用照样作为种子，产生“可能睡眠/可能 IPI/可能 RT 锁”的性质。

抽样里的真实例子：

- `tmigr_update_events` 调用 `trace_tmigr_update_events`，报出 S 类。性质链是 `trace_tmigr_update_events > __warn_printk > …`，说明 `trace_` 函数的函数体被展开了。
- `riscv_iommu_queue_send` 调用 `__might_sleep`，报出 I 类。性质链是 `__might_sleep > __warn_printk > … > on_each_cpu`，说明睡眠原语的函数体被展开了。
- `perf_event_init_context` 调用 `mutex_lock`，报出 I 类。原因相同。

## 修订条目

1. 新增 `is_opaque(name)`：原语（`is_primitive`）、睡眠种子名（`SLEEP`）、IPI 种子名（`IPI`）、`NO_DESCEND` 前缀，都算“不展开”。
2. 不展开的函数：
   - 函数体不产生种子；
   - 不接收入口状态，函数体不分析，也就不会在它的函数体里报标记；
   - 调用边和入口传播都不进入它。
3. 在调用点，被调者如果是不展开的函数，只按它自己作为原语的类别报（例如 `mutex_lock` 只算 S），不再查它的闭包。
4. 分配函数（`kmalloc*` 等）只在实参含 `GFP_KERNEL` 等时才是原语，按原样处理，不列入“不展开”。这一条维持原实现，不扩大。
5. 自测 `selftest/verify.py` 加第三个单元 `selftest/src/kernel/opaque.c`：
   - 里面有一个函数体会睡眠的 `trace_` 函数、一个函数体会发 IPI 的 `mutex_lock` 定义，以及在关中断时调用 `trace_` 函数的调用者；
   - 按判据，这个文件不应产生任何标记，所以期望集 `EXPECTED` 一条不改，只把“单元全部干净”从 2 个改成 3 个；
   - 结果：修正后自测通过（`selftest/rerun_after_am3.log`）；
   - 反向检查：用修正前的分析器副本跑同一自测会失败，多出 `I cb→mutex_lock`、`I mutex_lock→on_each_cpu`、`S opq_caller→trace_opq_event` 三条，正是这个错误的表现。
6. 已用修正前代码分析的只有当前版本。它的 `results/current.json` 和据它抽的 `review_sample.json` 移到 `invalid_run2_opaque/` 留档，不参与统计。抽取缓存不受影响，只重做分析。之后用同一个已写定的 `review_sample.py`（SHA 不变，种子 20261108）重新抽样。
7. 样本目标的分析都在本修订之后进行。修订时后台续跑正在抽取 A076_pre，还没有任何样本目标进入分析。

8. （15:20 追加，仍在任何样本目标分析之前）续跑防护修正。
   - 续跑时，抽取器把之前已抽好的单元记为 `cached`。`eval_samples.py` 的防护（修订 2 第 4 条）只认 `ok`，于是 A076_pre（191 cached + 467 ok）被误停。
   - 改法：统计里出现 `cached` 时，逐个读该目标缓存里的单元文件，按分析器同样的规则（`error` 字段 / 非空 `fatal`）重算状态；只要有一个不是 `ok`，照样停下。防护的严格程度没变。

## 本修订不处理、留给下一轮的判据缺口

人工核对中还看到大量噪声，来自判据本身。按规则，这些不能在本轮改：

- **前缀规则漏掉宏展开后的名字。** `pr_warn` 宏展开后的被调者是 `_printk`，`WARN` 展开后是 `__warn_printk`。它们不以判据列的前缀开头，所以仍然展开。
- **`preempt_schedule*` 被当成“可能睡眠”链的一环。** 运行时它只在抢占计数降到 0 时才被调用，也就是说那时已经不在原子上下文了。
- **陷入入口规则 (a) 收进了不是陷入处理的函数。** 例如 `ret_from_fork_user`：它在 `entry.S` 中出现，但并不是在 SIE 清零时进入的。
- **trylock 失败分支仍按“可能持锁”处理。** 路径条件没有建模。

## 不变的部分

判据第 5、6 节和修订 1、2 全部不变。
