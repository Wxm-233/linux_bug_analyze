# GPT盲复核与第一标注人的一致性（10份材料，300条）

## 这一轮要回答什么

此前各轮的标签都由第一标注人（模型Claude）给出。用户把10份盲复核材料交给GPT（每份一个新对话），GPT不看我们的标签，按各份的复核说明独立判断。本轮做三件事：
1. 计算两位标注人的一致性；
2. 逐条看分歧，对照代码核实；
3. 确认我们的标签哪些要更正，以及更正对已有结论的影响。

各轮原有的标签文件不改动，更正记录在`label_corrections.json`中。

| 文件 | 说明 |
| --- | --- |
| `agreement.py` → `agreement.json`、`disagreements.json` | 一致性与逐条分歧，读各轮的`gpt_review/answers.csv`和原有标签 |
| `label_corrections.json` | 核实后的事后标签更正和证据 |

**两点比较方式的说明**：
- 旧材料中，`real`的定义包含“违反内核约定”。所以凡是我们已有三类标签的轮次，比较时都把“违反约定”算作`real`。
- GPT的10份答案都核对过格式：表头、编号、顺序都与答题表一致。

## 核实后的更正（事后）

| 更正 | 涉及 | 依据 |
| --- | --- | --- |
| **PMU `fevent_code`缺防护是真问题** | RISC-V规则标记4条、终点版本规则标记4条；规则第4版剔除的4个标记；修复演示中“剩下5处为误报”的说法 | `cfg_match`走`SKIP_MATCH`时不检查计数器类型。客体可以把非固件事件号存进固件类型的计数器，之后启动、停止、读取时的`fevent_code`就是客体可控的。我们原以为它是“配置时已校验的保存值” |
| **新疑点**：客体可触发宿主的`WARN_ONCE` | RISC-V KVM `pmu_fw_ctr_read_hi`（终点版本） | 同上路径存入越界的事件号后，读计数器高位会触发`WARN_ONCE("Invalid firmware event code")`。只记录，未运行验证 |
| **硬中断中panic时`smp_call_function`会报警告** | 独立检验L02、M02；开发样本20 | `smp_call_function_many_cond`中有无条件的`WARN_ON_ONCE(!in_task())`，不受`oops_in_progress`影响。arm64、RISC-V停核用专门的IPI，不走这条路径 |
| **kfence在v6.6走不到** | RISC-V新样本中的`kfence_protect_page` | v6.6中能用IPI刷新TLB的只有CLINT，而它只在无MMU时选上，KFENCE又要求MMU。与此前的NR_VCPUS同属“有上游修复就当真问题”的错误 |
| `__acpi_unmap_table`不是问题 | 2条 | `early_memunmap`本身就调用`early_iounmap`，问题只在映射一侧 |
| v6.12执行上下文规则中，6条标记的调用链走不到 | 6条 | 已核对其中1条：标记的调用位于“来自用户态”的分支，`do_trap_error`只发信号，不会调用`die`。相关的两个问题本身仍成立，由其他标记代表 |
| MIPS `die`改为判断不了；MIPS `do_mcheck`改为真问题 | 2条 | `die`：我们的理由有误，NMI路径会带用户态寄存器调用`die`，但睡眠检查被抑制。`do_mcheck`：入口关中断，用户态机器检查时会报睡眠警告 |

## 结论

- **后期的标注较可靠**：
  - 修复方式的主动作kappa为0.92，改在哪一层全部一致；
  - LoongArch开发样本kappa为0.86；
  - 修复主线的结论有第二位标注人支持。
- **早期规则轮的标注可靠性低**：其中“判断不了”较多，引用这些轮的精确度数字时要注明。
- **GPT纠正了几处实质错误**，其中两处值得写进论文：
  - **PMU**：规则标出的位置是对的，被第一标注人和规则第4版误判为误报；
  - **kfence**：再次出现“有上游修复就当真问题”的映射错误。
- 由此得到一条做法上的教训：**按“当时版本能否选到出错的配置和路径”判断，而不是按“后来有没有修复”判断**。
