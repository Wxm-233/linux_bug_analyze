## 资源长什么样（说人话）

在每个“公共函数直接调架构函数”的地方，看四样东西：

- **传过去什么**（入参）：类型和来源，例如“页表项，来自局部变量 `pud`，它的值是 `pudp_get()` 读出来的”；
- **拿回来什么、怎么用**（返回值）：例如“bool，直接当 `if` 条件”“页帧号，拿去和另一个页帧号比较”；
- **用了架构定义的哪些常量**：例如 `PAGE_NONE`、`PUD_SIZE`、`PAGE_SHIFT`；
- **架构函数里偷偷读写了哪些全局变量**：例如 riscv 的 `pmd_page` 读 `vmemmap_start_pfn`、`pgtable_l4_enabled`。

再按《常见资源及其需要满足的性质》的分类归类（四、页表项；七、指针和地址；六、数值；三、内存里的数据；五、TLB 和缓存；十、能力判断）。

**最值得往下做的是“全局状态”和“能力判断”**：它们天生就是架构相关的运行时状态，例如 riscv 的页表级数开关 `pgtable_l4_enabled`/`pgtable_l5_enabled`、`vmemmap_start_pfn`，现在没有任何检查看它们。

**三个架构间资源不一致的调用点 248 个**（`result.json`）。其中有真实差异，例如同一个 `follow_huge_pmd → pmd_page`，只有 riscv 的实现读了全局变量；也有假象：arm64 上一部分宏版本（如 `pmd_present`）的返回值没抽出来，见局限。

## 局限和已知问题

- **`current` 这类“写成对象式宏、实际是函数调用”的宏被当成常量**（`#define current get_current()`），新抽查里错的 2 条都是它。下一轮要排除宏体是函数调用的对象式宏。
- arm64 上一部分**宏版本接口的返回值没抽出来**（找不到宏展开的最外层表达式），造成部分“架构间不一致”是假象。
- 只做了 mm/ 和 `fs/proc/task_mmu.c` 里的调用者；头文件里的 `static inline` 调用者、其他子系统没做。
- 只做直接边，不含公共宏展开的边。所以 D2 riscv `pte_leaf_size` 不在本轮里。
- 数据流只在单个函数内：局部变量只追到“初值和赋值来自哪个调用”，不跨函数。
- “虚拟地址”“页帧号”部分靠变量名判断（例如名字含 `addr`、`pfn`）。
