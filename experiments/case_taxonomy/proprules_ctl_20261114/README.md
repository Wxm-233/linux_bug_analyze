## 在历史中找替代样本

范围：v6.1 以来，带 `Fixes:`、改了 riscv、arm64、x86、LoongArch 的 mm 和页表相关文件，提交说明里有用户态可见后果的关键词（用户态、崩溃、数据错、过期、清零、泄漏等）。共约 50 个，标题见本轮对话记录。其中看起来最可能的 3 个：

| 提交 | 修的是什么 | 为什么不能用 |
|---|---|---|
| `e3ba51ab24fd` | arm64 TLBI RANGE 操作数算错，TLB 没刷干净 | 后果只在 KVM 虚拟机热迁移时出现，我们没有嵌套虚拟化环境 |
| `82dd33fde026` | riscv 的 ASID 分配留下过期 TLB 项，应用读到错误数据 | 要求硬件 TLB 按 ASID 区分条目。QEMU 的 riscv 每次写 `satp` 都会刷掉整个 TLB，过期条目留不下来 |
| `6a288a4ddb4a` | 开启 `init_on_free` 时，大页零页暴露了未清零的 MTE 标签 | 只涉及 arm64 MTE 一个架构的硬件特性；性质是“标签为 0”，现有 R1 只查内容。要测就得照它新写模板，就不独立了 |

其余的多是启动、内存热拔插、KVM、调试、性能或构建相关，或者后果需要特定硬件。

## 这说明什么

1. **TLB 和指令缓存这两类跨架构缺陷，大多数要靠真实硬件的缓存行为才会表现出来。** 比如非叶子翻译缓存、按 ASID 区分的 TLB、不一致的指令缓存，QEMU 的 TCG 都不模拟。R2、R3 在 QEMU 上能查的，只剩“内核逻辑上漏了叶子 TLB 刷新”或“映射到了旧页”这类错误。
2. **清零这类缺陷在历史中很少**，主要就是 X1 这一族。
3. 所以，用真实历史缺陷给 R1～R3 做独立阳性对照，在现有环境下做不成。

## 可选的替代做法（还没做，等用户定）

1. **人工注入缺陷（变异测试）**：在当前版本的内核里，按规则覆盖的效果，有意删掉一处操作，作为已知答案的阳性对照，看 R1～R3 能报出几个。这是缺陷样本不足时检验检测能力的常用做法。例如：
   - 删掉某个架构 `flush_tlb_page` 或 `flush_tlb_range` 中的刷新；
   - 删掉 `clear_user_highpage` 中的清零；
   - 让 `do_anonymous_page` 跳过清零；
   - 删掉 `flush_icache_pages` 或 `set_pte_at` 里的指令缓存刷新。

   每个变异只改一处，在 riscv、x86_64、arm64 上分别构建（增量构建，每个几分钟）。“叶子 TLB 没刷”在 TCG 里看得到，因为 TCG 的软件 TLB 要靠内核发出的刷新指令才会失效。缺点是注入的缺陷是人造的，只能说明规则能查出什么样的错，不能说明真实缺陷长什么样。
2. **换一个更严格的模拟环境**：比如用 QEMU 插件模拟页表遍历缓存、不一致的指令缓存。工作量大，属于研究性质。
3. **只在真实硬件上验证**：需要 riscv 开发板（例如 Spacemit K1），不在当前条件内。
