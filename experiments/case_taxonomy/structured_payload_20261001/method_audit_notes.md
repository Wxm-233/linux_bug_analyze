# 结构字段—复制—读端实验：事前方法审计

日期：2026-10-01。此文只使用已经解封的 2026-09-30 两条源码复核、冻结 v5 和 outbound scalar 模块。未读取本轮新留出提交的正文、补丁或源码；下列两例只能作为开发数据，不能再次计算独立验证成功。

## 应当由程序分开保存的证据

1. **声明绑定**：同一修订的对象声明、字段声明、位宽与指针层级；局部变量要绑定到具体声明，不能按整个函数中最后一次出现的同名变量选类型。声明来自头文件时同时保存路径、blob/内容哈希、行号和配置假设。
2. **写入事实**：字段真正接收的是主机数值、已经编码的值，还是未知表达式；保存最后写入与发送调用的关系，地址逃逸、后续覆盖和无法证明的控制流单列不足。声明为 `__le16` 并不保证其中已存入小端字节。
3. **复制事实**：发送长度与实际对象相同，经过的函数在同一修订，参数和长度未经改变，并最终原样复制。调用名本身不能替代参数取证。
4. **读端契约**：区分同机主机数值读取、明确的小端/大端读取，以及外部消费者但编码未证。消费者缺失时只能输出表示复核线索，不能把主机字节一律判成错误。
5. **适用性**：版本、模式、目标设备/架构和配置。只保存到 `memcpy` 的路径不足以证明设备使用该命令；声明证据不能替代实际触发证据。

建议输出分别记录 `declaration_binding`、`producer_representation`、`copy_chain`、`reader_or_schema`、`applicability`，最后再给 `candidate/local_match/insufficient`。`local_match` 表示所查表示关系相符，不等于完整命令、驱动或内核正常。零站点只表示范围没有覆盖。

## 两条已读案例提供的权威区别

`727ea61a5028` 的父版：`hci_core.c:841–848` 将 `hdev->le_max_tx_len/time` 直接写入 `cp.tx_len/time`。同版 `hci_core.h:271–272` 的源字段为主机 `__u16`，`hci.h:1547–1551` 的命令字段为 `__le16`，命令通过 `hci_req_add`、`hci_prepare_cmd`、`skb_put_data` 原样复制。**同版命令字段声明构成内核生产者应满足的表示契约**，足以支持条件性“大端主机直接写入小端字段”的源码候选；修复前后字节差异可以由缩小原型验证。它不自动证明具体控制器的格式、运行可达性或真实故障。这里的判断不能由“修复加了转换”反向充当唯一权威。

`0ab905c3be8c` 的父版：`coredump.c:432–447` 写入主机 `u32 dump_size`，同机工作队列最终在 `:181–209` 重新按主机 `u32*` 读取。其旧版写入—读取在大小端各自都能还原同一个数值；修复成对使用 `put_unaligned_le32/get_unaligned_le32` 后也是自洽的内部表示。**同一主机的实际读端决定这条链的数值解释**；缺少外部格式或其他消费者证据时，不能要求旧内部链必须采用小端。旧读取的对齐/有效类型/对象生命周期是另一个问题，本轮数值往返不能证明其安全。

因此“以什么为准”宜采用可追踪的版本和消费者契约：先确定接口属于外部序列化边界还是同机内部往返，再查看同版声明、规范/设备文档及实际读取。如果依据冲突或未找到读端，保留冲突和未知，不用架构多数实现、单一类型名字或补丁内容替代权威。

## 编译器核对能够证明什么

- 常规 GCC/Clang 内核编译通常将 `__bitwise` 检查标记展开为空；`__le16` 和 `__u16` 都可成为同一个基础无符号整数类型。**编译通过、赋值兼容或 AST 的 desugared type 不能证明端序编码正确**。若试验自行提供 typedef，应明确这些替身没有恢复 Sparse 的语义检查。
- 编译器的实际声明引用、成员声明引用、位宽、对象层级与词法作用域可用于核对提取器的绑定。必须保留 typedef 原始拼写及其来源，不能只看基础类型宽度。仅在 AST 中看到不同 typedef 名字也不等于已证明物理字节格式。
- 若从历史源码截取声明和函数、补最小 typedef/stub 后编译，结果只验证该缩小翻译单元。它不能证明原内核完整预处理、真实配置、头文件依赖、宏展开、控制流可达性或设备执行。原始片段与补入部分应分别记录哈希和来源。
- 本机小端执行只能确认小端原型。大端字节若来自公式，应写作模型结果；如在 s390x 用户态程序和 QEMU 中运行，应写作大端用户态原型，仍不是历史内核或 Bluetooth 控制器验证。

## 最少正常反例与必须拒判的情况

| 输入关系 | 合理的有界结果 | 要防止的误判 |
| --- | --- | --- |
| 主机值经匹配 `cpu_to_le16` 写 `__le16`，随后原样复制 | 局部表示匹配；外部适用性仍待证 | 把修复后的匹配事实写成整个接口正常 |
| 同机 host 写出、同机 host 读回；以及 le 写出、le 读回 | 两种同端表示均自洽 | 只见 `skb_put_data(&host)` 就报跨架构错误 |
| 已为 `__le16` 且来源编码已证的字段直接写入另一 `__le16` 字段 | 匹配或在来源不充分时不足 | 再加转换造成二次编码 |
| 大端/小端表示混用但值为零或字节对称数 | 正常控制输入不能解除一般表示冲突 | 用零值样例通过推断所有值正常 |
| 同名变量位于两个作用域、字段只是指针对象、长度不是对应对象大小 | 具体绑定未证时不足；已证指针对象另列 | 复用旧 v4 的全函数类型缓存、把地址值当内容 |
| 字段被多次写、分支写、未知调用修改，或地址在复制前逃逸 | 来源/最后写入/可达路径未证则不足 | 文本顺序被当成所有运行路径的证明 |
| 宏或 CONFIG 影响声明、长度、发送入口和转换函数；头文件重复定义 | 编译绑定或配置未证则不足 | 简单声明搜索替代真实预处理 |
| 未找到读端，或者读端会额外转换、按字节组装 | 外部格式或读端语义未知 | 从原样复制直接推导消费者期望 |

字节对照至少含非零且不对称值（16 位如 `0x001b`、`0x0148`，32 位如 `0x12345678`）、零值控制与两种主机端序。对结构体还应核对字段偏移、总尺寸和 packed/对齐假设；不能把多字段站点数当成多个独立案例。
