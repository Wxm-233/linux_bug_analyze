# 已读表示案例的编译器与大小端原型核对

日期：2026-10-01。本轮是**开发验证**，使用已读的 HCI 结构体命令、内部 coredump 往返和 dw_mmc 同名变量例，未读取新留出样本、未调用模型。网格中的输入和变体不是新增缺陷或独立检出样本；不修改已确认案例统计。

## 取证与复现

`run_probe.py` 从 `/root/repos/linux` 的固定历史修订号读取 9 份文件，自动摘出原始声明、赋值、发送调用和内部读端。`source_evidence.json` 保存 revision、blob、全文件 SHA-256、摘录起止行和原文。生成的 `runtime_projection.c` 保留 HCI 原始结构体和两条赋值表达式，用最小 `hci_req_add` 的 `memcpy` 模型代替真实内核队列；内部 coredump 使用对应的主机/小端编解码投影。

使用现有 GCC 13.3.0 编译 x86_64 和 s390x 静态用户态程序；后者由 QEMU s390x 8.2.2 运行。`results.json` 保存每个命令、退出码、标准输出/错误、编译器版本、生成源码与可执行文件 SHA-256，以及逐输入数值。没有安装编译器或依赖。Clang 和 Sparse 未安装。

## 表示检查结果

每条路线使用两组非对称的非零输入及一组零值对照。下表只统计两组非零输入的字节/数值不一致，不表示硬件失败或案例数。

| 路线与变体 | x86_64 小端 | s390x 大端 |
| --- | --- | --- |
| HCI：原始两个字段均直接赋值 | 0/2 与声明的线格式不同 | 2/2 不同 |
| HCI：只转换 `tx_len`，`tx_time` 保留原赋值 | 0/2 不同 | 2/2 不同 |
| HCI：两个字段均转换 | 0/2 不同 | 0/2 不同 |
| coredump：原始 host 写、host 读 | 0/2 数值不同 | 0/2 不同 |
| coredump：完整 le 写、le 读 | 0/2 不同 | 0/2 不同 |
| coredump：只改写端或只改读端 | 每个变体 0/2 不同 | 每个变体 2/2 不同 |

HCI 的第一组值为 `tx_len=0x001b`、`tx_time=0x0148`。大端原始发送字节是 `001b0148`，只改单字段是 `1b000148`，完整转换是 `1b004801`，与同版打包结构体的两个 `__le16` 字段要求一致。第二组 `0x1234/0xabcd` 得到同样结论。三个变体在小端字节相同，因此只做默认小端测试容易漏掉该条件性的表示问题。零值变体的字节也相同；它只显示问题依赖值，不能当作路径正确性或实际控制器接受的证明。

coredump 的原始生产者和消费者都在同一主机内：将 `0x12345678` 原样写入，再按主机数值读取，在两端序目标上均得到原值。完整显式小端编解码也得到原值。大端上只转换一侧则得到 `0x78563412`。所以“原样复制主机整数”本身不能推出跨架构错误，必须查实际读端是否要求不同表示；这个内部往返正常反例应保留。本投影用 `memcpy` 代替旧指针解引用，**未证明原始访问的对齐、别名、队列或生命周期安全**，也未证明有外部固定线格式消费者。

## 编译器如何帮助确定应检查的位置

`scope_projection.c` 从 dw_mmc 父版 `40dfdd8d1449382cae3db2cefb1f5521ce19259b` 摘取成员声明，并保留两个分支各自的原始根声明。原文件第 505 行的 `p` 是 `struct idmac_desc_64addr *`，对应第 521–524 行的四个 `u32` 成员写；第 533 行另一个分支的 `p` 是 `struct idmac_desc *`，对应 `__le32` 成员。GCC 正确块绑定的静态断言编译通过；故意按全函数最后一个同名 `p` 绑定，第一个分支的静态断言编译失败。额外的合成嵌套同名变量得到 `-Wshadow=local` 诊断。

`scope_tree_original.txt` 是 GCC 原始树，`scope_bindings.json` 从该小投影函数的声明图自动取得两个不同 `var_decl`、指针记录类型、对应成员写及 typedef 拼写。它说明检查生成前应按**具体声明和词法作用域**关联左值，不能按变量名建立一个全函数类型缓存。这是一个有界编译器图试验，还不是可解析任意内核翻译单元的自动检测器。

GCC 原始树在这里保留 `u32` 与 `__le32` 的 typedef 拼写，但普通 GCC 将它们视为兼容的基础整数型，**不会检查端序语义**。HCI 投影也用编译通过的静态断言明确记录 `__u16` 与 `__le16` 在普通 GCC 下类型兼容。编译成功只能验证宽度、结构布局和作用域绑定，不能证明端序转换正确；表示契约仍需同版声明及实际读端的依据，Sparse 若以后可用只能补充一部分静态约束。

据此，可自动提取的检查方向是：先找到具体声明的字段与来源表示，再追踪字节复制到读端，生成“写出后按消费者格式解释是否还原预期数值”的条件检查，并覆盖完整修复、单字段修复与单端修复。若实际读端或格式权威没有被证明，应输出材料不足，不能把缺少转换直接判成缺陷。HCI 此处依据的是同版 `__le16` 命令声明；外部控制器规范符合性与实际运行仍未验证。内部 coredump 则以同主机两端的实际读写链为边界，不能强加与已读链无关的外部格式。

本轮验证了“绑定具体声明”和“同时检查生产者与消费者”的必要性。没有真实内核、控制器或设备运行，没有新的独立泛化成绩，也不据此提高两例的确认层级。

复现命令（输出目录默认是本目录）：

```bash
python3 run_probe.py --linux-dir /root/repos/linux
```
