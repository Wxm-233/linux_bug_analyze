## 做法（说人话）

编码表能算出“如果这里拿到非 present 项，会在哪些架构上出错”，但很多调用点根本拿不到非 present 项。本轮把这些机械地滤掉，再按编码表排序。

| 过滤 | 含义 | 滤掉 |
|---|---|---|
| F1 已守卫 | 本函数或所有调用者（跨函数入口事实）已经查过 present、`trans_huge` 或 `access_permitted` | 148 |
| F2 布尔守卫 | 有名字含 `present` 的变量或参数为真，例如 `is_present && pmd_young(x)` | 2 |
| F3 现造的值 | 值不是从页表读出来的，也不是参数 | 69 |
| F4 内核页表 | 函数里用到 `init_mm`、`pte_offset_kernel` 等，或在 vmemmap、KASAN、vmalloc、ptdump 这类文件里 | 19 |
| F5 约定只传 present 项 | 函数名含 `present` | 5 |
| F6 测试代码 | `debug_vm_pgtable` 等 | 8 |
| 留下 | 可达候选 | **65** |

分析器复用契约挖掘的（含跨函数传递），编码表用上一轮的。不构建，当前版本全量跑完约 1 分钟。

裁定：12 条正式条目里，**可能 2、说不清 1、不可能 9**。

**可能（新疑点 3，同一处代码）**：`mm/memory.c:2494-2495` 的 `insert_page_into_pte_locked()`。这是 Codex 找到的路径，我核实了关键几步：

1. 对 ext4 DAX 的共享可写映射注册 userfaultfd 的**异步写保护**（WP_ASYNC）。`vma_can_userfault()` 写明，只开 WP 模式且是 WP_ASYNC 时“允许任何内存类型”；
2. 在还没填充的位置装上 uffd-wp 标记，这是一种非 present 项；
3. 进程写这一页，缺页处理经 `pte_marker_handle_uffd_wp()` → `do_pte_missing()` 进入 DAX 的缺页，最后以 `write=true` 调用 `vmf_insert_page_mkwrite()`；
4. 这时页表项里还是标记，不为空。代码默认“非空就是已经映射的页”，对它调用 `pte_pfn()`，读出的值和 DAX 页的页框号对不上，于是触发 `WARN_ON_ONCE`、返回 `-EFAULT`，**进程收到 SIGBUS**。

我原来判“不可能”，理由是 DAX 页不会换出或迁移，漏了 uffd 标记也是非 present 项。另外，这条在各架构上都会出错，`pte_pfn` 对标记读出的都是无意义值，所以它不算典型的跨架构缺陷，属于公共层没查 present 的一般性错误。还没有动态验证。

**说不清**：`mm/mprotect.c:733`。Codex 给出的路径要求 L1TF CPU、`l1tf=off`、超过 256G 的交换区，以及 FUSE DAX 私有页被换出，条件太苛刻，没有核实。

**附加的两条 MGLRU 路径**：两人都判“不可能”。`get_pte_pfn()` 先查了 `pte_present`，非 present 时返回 -1，调用者直接跳过。所以 B-2 那种问题只在经典 LRU 路径上出现，和 p1dyn 关掉 MGLRU 才复现的情况一致。

## 看出的几点

1. **“编码表 + 可达性过滤”是一个可用的组合**：编码表回答“在哪些架构上、怎么出错”，过滤回答“这里会不会拿到非 present 项”。两者合起来，已知缺陷都排进了前 5，而人要看的条目从几百条降到 65 条。
2. **过滤里最有效的两项是跨函数守卫（F1）和现造的值（F3）**，加起来滤掉了 217 条。
3. **新疑点 3 说明非 present 项的种类要考虑全**。uffd 标记、guard 标记这类“软件标记”，即使页本身不会换出或迁移，也会出现在页表里。人判断时很容易漏掉，我这次就漏了。
4. 唯一被误筛掉的样本，是因为 F4 只看函数里有没有出现内核页表的标识符。`try_to_unmap_one` 很大，里面有个别地方涉及 `init_mm`，就被整个当成了内核页表函数。F4 以后应该看实参的来源，而不是看整个函数。

## 局限

- F4、F5 是按名字判断的，会误伤（见上）；
- 跨函数只传入口事实，像 `get_pte_pfn()` 这种守卫写在被调函数返回值里的情况看不到，这次是人工排除的；
- 新疑点 3 还没有动态验证，严重程度、上游是否已修都不知道；
- 可达候选 65 条里，只审了前 30 条和两条附加。
