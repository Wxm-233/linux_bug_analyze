# 判据：带调试断言的内核（dbgassert_dev_20261111）

2026-11-11，Claude 在构建和运行之前写定，SHA 存入 `criteria_sha256.txt`。用户 2026-11-11 同意构建 3 个内核。

## 一、目的

三类检查里，调用上下文检查一直没有接进动态测试：它关心的是“调用时能不能睡眠、是否持锁、中断是否关闭”这类运行时状态，系统调用的返回值看不出来；静态标记又太吵（30,584 处，抽查 40 处没有真问题）。

`anyarch_dev_20261110/runtime_requirements.md` 第四类指出：这类要求内核自己已经写成了运行时断言，只是默认配置不打开。本轮构建打开这些断言的内核，回答三个问题：

1. 能不能构建、能不能启动、运行慢多少？
2. 在没有已知缺陷的当前版本上，断言会不会乱响（噪声有多大）？
3. 断言触发能不能作为一种新的判据：同一个用例，断言只在某个架构上响。

本轮只做当前版本的 3 个内核，不构建旧版本，所以**不评价对已知缺陷的检出能力**。

## 二、构建（写死）

- 源码 `/root/repos/linux`（HEAD `df2908090cda`，不改工作树），`LLVM=1`，输出到 `/root/work/dbgassert/build/<架构>`。
- 配置 = 各架构默认配置 ＋ 打开下列选项，再 `olddefconfig`：
  `DEBUG_KERNEL`、`DEBUG_ATOMIC_SLEEP`（不能睡眠的地方睡眠）、`PROVE_LOCKING`（锁的使用规则，连带中断状态和 RCU 检查）、`DEBUG_VM`、`DEBUG_VM_PGTABLE`（启动时自检各架构的页表函数）、`PAGE_TABLE_CHECK`、`PAGE_TABLE_CHECK_ENFORCED`、`DEBUG_LIST`、`DEBUG_SG`、`DEBUG_VIRTUAL`、`SCHED_STACK_END_CHECK`、`DEBUG_IRQFLAGS`。
- 构建后逐项核对 `.config`，记录每个架构上哪些选项实际生效；某个架构不支持的选项如实记录，不算失败。
- 不打开内存越界检查（KASAN）：模拟器里太慢，且与调用上下文无关。
- 只构建内核镜像。构建完成并跑完后删除目标文件，只留镜像和 `.config`。

## 三、运行（写死）

- 启动方式与此前各轮相同，只有一处不同：内核命令行的 `quiet` 换成 `loglevel=5`，否则警告级别的内核消息不会出现在控制台上。为此在本轮目录里放一份启动脚本的副本，只改这一处。
- **启动自检**：三个内核各用探测程序（`rtprobe_dev_20261110/harness/rt_probe.c`）启动 2 次，只看启动到关机期间的内核告警。
- **用例**：`diverse_dev_20261110` 的当前版本用例全集（8107 个），清单原样。三个内核各运行 3 次。
- 若调试内核上单次运行超过 60 分钟，改为只跑 G3d 的用例（2779 个），并在 README 里说明。

## 四、从日志里取什么（写死）

- **告警事件**：控制台上匹配下列任一开头的内核消息，连同其后的同一段调用栈：`WARNING:`、`BUG:`、`kernel BUG`、`INFO: possible`（锁检查的报告）、`INFO: suspicious`、`Unable to handle`、`Oops`、`Call Trace` 之前的 `------------[ cut here ]------------`。
- **归属**：一个告警事件归属于它之后打印的第一个用例结果（即触发时正在执行的用例）；出现在第一个用例之前的归为“启动阶段”，出现在最后一个用例之后的归为“关机阶段”。
- **签名**：告警的第一行去掉时间戳、CPU 号、进程号、地址后的文本，加上调用栈里前 3 个函数名。同一签名在一次启动里通常只报一次（内核的一次性告警），所以按“签名 × 内核”统计，不按次数。
- 每次运行另记：执行器报告的“污染标志是否变化”、是否完整结束、用时。

## 五、要报告的数字

1. 三个内核：是否构建成功、镜像大小、每个选项是否生效、构建用时。
2. 运行用时，调试内核对默认内核的倍数；是否全部完整结束。
3. 启动阶段、用例阶段、关机阶段各有哪些告警签名，分别在哪些架构上出现、几次运行中出现。
4. **只在一个架构上出现的签名**：全部人工核对，结论分三种——能解释（合理的架构差异或环境原因）、不能解释（疑点，只记在本地，不对外报告）、未核对。
5. 功能对照：调试内核上用默认工具（`difftest_tools_20261111/compare.py`，归一化）得到的三个方向“与众不同”的簇，与默认内核上的结果（`anyarch_dev_20261110/runs/CURt` 用同一工具重算）相比，簇的集合差多少。预期基本相同；差异如实报告。

## 六、解读规则（事先写下）

- 没有任何告警：说明在当前版本、现有用例下断言不会乱响，噪声为 0；但**不能**说明这条路能发现缺陷，只说明它可用。
- 有只在一个架构上出现的告警：它是一条线索，不是结论；要人工看调用栈判断是内核问题、配置问题还是模拟器问题。
- 三个架构都出现的告警：与跨架构无关，单独列出，不深究。
- 本轮不构成“调用上下文检查已接入”的证据；要证明有用，需要在带断言的旧版本内核上重现开发集里属于调用上下文类的已知缺陷，那需要另外的构建，留给下一轮并先征求用户同意。

## 七、规则

只构建用户同意的 3 个内核；不安装、不联网、不调用大模型、不对外报告、不改旧轮次文件、不改内核源码工作树；内核只在 QEMU 中运行。统计行：模型调用 0；构建 3；新确认缺陷 0；新疑点 N。
