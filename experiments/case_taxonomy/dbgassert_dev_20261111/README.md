# 带调试断言的内核（dbgassert_dev_20261111）

2026-11-11，Claude。判据 `criteria.md`（SHA 见 `criteria_sha256.txt`），在构建和运行之前写定，没有修订。用户同意构建 3 个内核。

统计行：模型调用 0；构建 3；新确认缺陷 0；新疑点 0。

## 为什么做

三类检查里，调用上下文检查一直没接进动态测试：它关心“调用时能不能睡眠、是否持锁、中断是否关闭”，这些从系统调用的返回值看不出来。但内核自己已经把这类要求写成了运行时断言，只是默认配置不打开。本轮把它们打开，看这条路走不走得通。

只做了当前版本的 3 个内核，所以本轮**不评价对已知缺陷的检出能力**，只回答：能不能用、会不会乱响。

## 一、构建

当前版本，默认配置上加 12 个调试选项：不能睡眠处睡眠的检查、锁的使用规则检查（连带中断状态和 RCU 检查）、内存管理的调试断言、启动时的页表函数自检、链表和栈溢出检查等。

| 架构 | 结果 | 用时 | 镜像大小（默认 → 调试） |
| --- | --- | --- | --- |
| riscv | 成功 | 237 秒 | 25 MB → 30 MB |
| arm64 | 成功 | 411 秒 | 42 MB → 49 MB |
| x86_64 | 成功 | 275 秒 | 15 MB → 16 MB |

选项全部生效，只有一处例外：riscv 上“页表检查”（`PAGE_TABLE_CHECK`）没有生效，因为它还依赖另一个默认配置里没开的选项。其余 10 个选项在三个架构上都生效了。

## 二、启动自检

三个内核各启动 2 次，只看启动到关机期间的内核告警。

- riscv、x86：没有告警。页表函数的启动自检没有报任何问题。
- **arm64：1 条告警，两次启动都出现**。内容是：某个驱动定义的跟踪事件，输出格式里写了一个二次解引用，内核启动时的自查把它标了出来。

这条告警我核对了，**不是跨架构差异**：

- 涉及的驱动（一个 USB 控制器驱动）只在 arm64 的默认配置里编译，riscv 和 x86 的默认配置里没有它；
- 这个自查不是调试选项带来的，默认内核上也会触发，只是以前的内核命令行是静默的，警告级别的消息被挡住了，我们一直没看到。

所以它说明的是另一件事：**此前所有运行都看不到警告级别的内核消息**。这条告警本身只记在本地，不对外报告。

## 三、在调试内核上跑用例

当前版本的全部 8107 个用例，三个内核各 3 次，全部完整结束。

| 架构 | 单次用时 | 用例阶段的告警 | 关机阶段的告警 | 污染标志变化 |
| --- | --- | --- | --- | --- |
| riscv | 约 330 秒 | 0 | 0 | 无 |
| x86_64 | 约 283 秒 | 0 | 0 | 无 |
| arm64 | 约 1580 秒 | 0 | 0 | 无 |

**8107 个用例 × 3 个架构 × 3 次，没有触发任何一条断言。** 断言不会乱响，噪声为 0。

用时：默认内核上三个架构一起跑大约 3 分半；调试内核上 riscv 和 x86 是 5 分钟左右，慢得不多；arm64 要 26 分钟，慢了好几倍。

## 四、功能对照：调试内核和默认内核的结果一样吗

用默认比较工具（归一化）分别算调试内核和默认内核上三个方向“与众不同”的簇：

| 方向 | 默认内核 | 调试内核 | 两边都有 |
| --- | --- | --- | --- |
| riscv | 10 簇 | 10 簇 | 10 |
| x86_64 | 3 簇 | 3 簇 | 3 |
| arm64 | 11 簇 | 49 簇 | 11 |

riscv 和 x86 完全一致。arm64 多出 38 簇，原因查清了，都不是内核行为的差异：

- **32 簇是超时**。执行器给每个用例设了时限；arm64 的调试内核太慢，有 66 个用例超时，而另外两个架构只有 26 个（那 26 个是本来就会阻塞的调用，三个架构都超时）。多出来的 40 个只在 arm64 上超时，于是被判成“arm64 与众不同”。
- 3 簇是 `openat`：本轮用的是没有做接口常数换算的原始清单，这 3 簇在 `anyarch` 轮已经解释过。
- 剩下 3 簇（`getpeername`、`set_tid_address`、`times`）没有逐个分析，看形态与超时或易变输出有关。

## 说明什么

1. **这条路可用**：三个架构都能构建、能启动、能跑完全部用例；断言在没有已知缺陷的版本上一条都不响。以后只要有一条断言只在某个架构上响，就是很干净的线索。
2. **还不能说它有用**：本轮没有任何已知缺陷可测，“一条都不响”也可能只是因为现有用例碰不到这类问题。现有用例是为“参数检查”类缺陷设计的，本来就不针对调用上下文。
3. **两个顺带的发现，对现有流程有用**：
   - 以前的运行看不到警告级别的内核消息。把内核命令行从静默改成显示警告，不需要重新构建，默认内核上就能多一路信号。
   - “超时”应当单独成一类判定。现在它被当成普通的返回值参与比较，只要某个架构明显更慢，就会凭空多出几十簇。
4. **arm64 的调试内核太慢**，单独拖长了整轮时间。原因没有查，可能与模拟器里 arm64 用的 CPU 型号有关。

## 下一步需要什么

要证明这条路能发现缺陷，需要一个“断言应该响”的例子。开发集里有 26 条属于调用上下文类的已知缺陷，可以挑其中能由用户程序走到的几条，构建它们修复前、修复后的调试内核，看断言是否只在修复前响。这需要另外的构建（每条 2 个 riscv 内核），本轮没有做，要先征求用户同意。

## 没做的、不确定的

- 没有打开内存越界检查（模拟器里太慢，且与调用上下文无关）。
- riscv 上页表检查没生效，没有去补它依赖的选项。
- 启动自检“没有告警”是按“没有出现告警消息”判断的；通知级别的消息（自检开始、通过）在本轮的日志级别下不显示，所以没有正面确认每一项自检都执行了，只确认了相应选项已编入内核。
- arm64 多出的最后 3 簇没有逐个分析。
- 告警的归属规则（归给之后打印的第一个用例）本轮没有机会检验，因为用例阶段没有告警。
