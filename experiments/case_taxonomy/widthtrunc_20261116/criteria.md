## 一、问题

`unsigned long`、`long`、`size_t`、`pgoff_t` 这些类型，在 64 位架构上是 64 位，在 32 位架构（arm、i386、riscv32、mips32 等）上只有 32 位。公共层或架构层把一个**在所有架构上都是 64 位**的值（`u64`、`loff_t`、`sector_t` 等），交给这类“随架构变宽”的类型，32 位上就会悄悄截断。x86_64、arm64 上测不出来。

## 二、横向：类型位宽表（写死）

沿用探针方法（各架构头文件和编译选项，编成 LLVM IR，读常量），求下列类型的 `sizeof × 8`：`int`、`long`、`unsigned long`、`size_t`、`ssize_t`、`pgoff_t`、`uintptr_t`、`phys_addr_t`、`dma_addr_t`、`resource_size_t`、`loff_t`、`u64`、`sector_t`、`blkcnt_t`、`time64_t`、`ktime_t`。

组合：
- 已有 64 位目录：x86_64、arm64、riscv、loongarch、powerpc、s390、mips（64r6el）；
- 已有 32 位目录：arm（multi_v7）；
- 新建 32 位目录：i386（`i386_defconfig`）、riscv32（`rv32_defconfig`）、mips32（`32r2el_defconfig`）。只做 `modules_prepare`。

某个组合编不过的类型，记为“不可用”。

**随架构变宽的类型 N**：在至少一个组合上小于 64 位，在至少一个组合上等于 64 位。
**恒 64 位的类型 W**：在所有有结果的组合上都是 64 位。

## 三、纵向：三种形态（写死）

**扫描范围**：`mm/`、`kernel/`、`lib/`、`fs/` 下的 `.c`；`include/linux/` 和 `mm/` 下的 `.h`；另加 `arch/*/kernel/*.c`、`arch/*/mm/*.c`（截断常发生在架构层接收公共层值的地方）。

**类型推断**（词法）：
- 变量的类型来自函数参数、局部声明（`T v` 或 `T v = …`，不带 `*` 的才算标量）；
- 结构体字段的类型来自扫描范围内的 `struct S { … }` 定义，`x->f`、`x.f` 按 x 的结构体类型查；
- 函数返回类型来自定义或原型；
- `typedef` 递归展开到基本类型名；
- 显式转换 `(T)e` 的类型是 T。

**三种形态**：
- **A 窄化**：目标类型在 N 中、源类型在 W 中：
  - 赋值或初始化（目标是变量或字段）；
  - 实参传给形参；
  - `return` 返回值。
  
  源表达式里出现 `>>`、`&`、`%`、`/`、`min`、`clamp`、`lower_32_bits` 这类缩小范围的运算时不报。
- **B 移位溢出**：`X << S` 的左操作数 X 是 N 类型（变量、字段或调用返回值，没有先转成 64 位），并且结果被赋给、或返回为 W 类型。
- **C 掩码截断**：`A & ~(B …)` 或 `A & ~B`，A 是 W 类型，B 是 N 类型，并且 B 没有先转成 64 位。

**守卫**：函数体里出现 `BITS_PER_LONG`、`CONFIG_64BIT`、`upper_32_bits`、`overflows_type`、`ULONG_MAX`、`SIZE_MAX`、`check_*_overflow` 之一，算作有守卫，不报（函数级规则；已知会漏掉分支级的问题，见 orddom 的教训）。

**候选**：每个“函数 + 形态 + 语句位置”是一条候选。横向成立的条件是：所涉及的 N 类型在至少一个组合上小于 64 位。

**排序**：形态 C、B 在前，A 在后（C、B 几乎一定出错，A 常是值本来就小）；同一形态里，先按“受影响组合数”多少，再按文件、行号。
