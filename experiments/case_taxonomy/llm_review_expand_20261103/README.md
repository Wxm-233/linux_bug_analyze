## 样本怎么来的

1. **RISC-V上凑不够**：第2版规则在20个快照上共标出624个位置，去掉以前复核过的只剩4个。原因是规则标出的位置在各版本之间基本不变，已经被前几轮用完。
2. **改用LoongArch**，按用户选择：
   - 把三条规则的检查对象换成LoongArch，参照换成arm64、x86、RISC-V，只替换与架构有关的常量；
   - **等价性自测**：把移植版的检查对象设回RISC-V，在v6.12上运行，50个标记与冻结版**逐条完全一致**；
   - 在v6.1–v7.2共22个快照上运行，去重后82个候选，按种子`20261103`抽60个。修订中误写为21个快照，实际是22个。
3. **标签**：在生成提示词之前定好。

| 标签 | 数目 | 内容 |
| --- | ---: | --- |
| a（有上游修复依据） | 9 | 见下 |
| b（误报，第一标注人判断） | 48 | 见下 |
| a2（疑似真问题，无修复） | 2 | `kvm_get_vcpu_by_cpuid`、`kvm_set_cpuid`：下标来自客体或用户，检查上界后没有`array_index_nospec`，到终点版本未加 |
| c（判断不了） | 1 | `on_thread_stack`：后来作为功能提交的一部分改成了`__always_inline` |

a类9个：
- KVM中4个函数持自旋锁时调用`copy_*_user`，共5个标记（`47256c4c8b1b`、`62f11796a0df`、`01a8e68396a6`、`8dc5245673cf`）；
- `setup_arch`：没有像其他架构那样在`parse_early_param`之前调用`jump_label_init`（`ea68d444a658`）；
- v6.2的`do_ale`：不开中断就可能走到`get_user`（`69cc6fad5df4`）；
- `KVM_CAP_NR_VCPUS`：没有像其他架构那样用`min_t`限制上限（`b3e31a6650d4`）；
- `regs_irqs_disabled`：被noinstr代码调用却不是`__always_inline`（`bb0511d59db9`）。

b类48个：
- noinstr类25个：入口函数中调用可插桩函数时没有`instrumentation_begin/end`，但调用都在`irqentry_enter`之后；
- rt类10个：快照时LoongArch还不能开启PREEMPT_RT；
- R10类8个：缺少的只是功能，或用了等价的写法；
- 其他5个。

## 结果

249次调用：第一步180次、对照60次、追问9次，全部完成，约73万token。

| | 保留真问题（9） | 去除误报（48） | 复核后精确度 |
| --- | ---: | ---: | ---: |
| 第1次 | 5/9 = 56% | 27/48 = 56% | 19% |
| 第2次 | 5/9 = 56% | 27/48 = 56% | 19% |
| 第3次 | 5/9 = 56% | 31/48 = 65% | 23% |
| **3次取多数** | **5/9 = 56%** | **26/48 = 54%** | **19%** |
| 对照：直接问（1次） | 5/9 = 56% | 36/48 = 75% | 29% |

复核之前，a类在a、b中的占比为9/57＝16%。

**按判据判定：未达到成功标准。** 3次取多数的保留率为56%，要求不低于90%；3次中没有一次单独达标。

其他指标：
- 稳定性：57个a、b问题中，44个的3次判断完全一致。
- 事实声明：
  - 共663条，相符654条、不符9条、无法核对0条；
  - 只有5次回答没写声明，比RISC-V那一轮多得多（那一轮72次中49次没写）。
- 追问：9次，**没有改变任何判断**。9条不符都是核对程序的写法问题：模型只写了条件的一部分，或者两个调用在不同分支上，程序判为先后不符。不是模型说错了事实。
- a2的2个疑似真问题：3次和对照都判为真问题。

## 事后分析（只作描述）

**按标记类型细分**（3次取多数 / 对照）：

| 类型 | 个数 | 保留 | 去除 |
| --- | ---: | --- | --- |
| noinstr（N2） | 25 | — | **3/25** / 15/25 |
| noinstr（N1，a类） | 1 | 0/1 / 0/1 | — |
| rt | 10 | — | 10/10 / 9/10 |
| 关中断或持锁中睡眠（A） | 9 | 5/5 / 5/5 | 4/4 / 3/4 |
| 陷入中睡眠（B） | 2 | 0/1 / 0/1 | 1/1 / 1/1 |
| R10 | 10 | 0/2 / 0/2 | 8/8 / 8/8 |
| **去掉noinstr类后** | 31 | 5/8 / 5/8 | 23/23 / 21/23 |

1. **去除率低，几乎全来自noinstr类，本质是“什么算真问题”的分歧。**
   - 要求写事实时，模型核对到“入口函数是noinstr、调用了可插桩函数、中间没有`instrumentation_begin`”，这些事实都对，于是判为“违反noinstr约定”；
   - 直接问时，模型更常说“只是缺少标注的形式问题”。
   - 我的标签按“是否会出实际错误”判为误报：上下文已建立，LoongArch不做这项校验，上游也一直保留这种写法。
   - 这一类的标签本身有争议，GPT复核说明中“违反内核约定”也算真问题。所以需要等GPT复核结果。
2. **漏掉的4个真问题，3次和对照都漏，是系统性的**：
   - **缺少LoongArch特有的知识**：
     - `do_ale`：模型认为“用户态来源时可以睡眠”，没有意识到进入异常时硬件已关中断，而当时的`do_ale`没有重新打开；
     - `setup_arch`：模型认为“LoongArch早期参数不依赖静态键”。
   - **把影响小的修复判为不算缺陷**：
     - `regs_irqs_disabled`：模型说“会被内联”；
     - `KVM_CAP_NR_VCPUS`：模型说“只是建议值”。
   - RISC-V的复核提示词有一份从早先误判中总结的背景事实（`facts.md`），LoongArch没有对应的一份。
3. **要求写可核对事实的问法，在LoongArch上没有帮助。** 去掉noinstr类后，保留率两种问法相同，都是5/8；去除率23/23对21/23，差别很小。程序核对没有纠正任何判断。
4. **RISC-V上的100%不能推广**。可能的原因：
   - 那18个样本与设计做法时用的样本同源；
   - 有`facts.md`补上了RISC-V特有的知识；
   - 样本中没有noinstr这类有定义争议的标记。

## 结论

- 按判据，**本轮未达到成功标准**：LoongArch上3次取多数，保留真问题5/9、去除误报54%，比直接问还差（去除75%）。
- RISC-V上“要求写出可核对事实＋程序核对＋追问”的100%结果**不能推广**。目前不能把它当作复核这一步的定论，第十节的说法需要修改。
- 两个主要问题：
  1. 模型缺少目标架构特有的知识，例如进入异常时的中断状态、早期启动顺序；
  2. “违反约定但不出实际错误”算不算真问题，判断标准需要先定清楚，并写进提示词。
- **新疑点（只记录，不对外报告）**：LoongArch KVM的`kvm_get_vcpu_by_cpuid`和`kvm_set_cpuid`中，下标来自客体或用户，检查上界后没有`array_index_nospec`。到终点版本还没加；模型6次判断都认为是真问题。

## 统计

模型调用249次（Claude-Sonnet-5.5，约73万token）；构建0次；新确认缺陷0；新疑点1组（LoongArch KVM两处Spectre-v1）。
