# 设计侧回归的实现调整记录（effzero_20261120）

每次按开发样本改实现都记在这里：改了什么、为什么、改前改后的结果。判据第一节的定义要改就另写修订。

1. （运行 X1 父版本之前发现）请求位正则 `REQBIT` 会把 `INIT_LIST_HEAD(...)`、`INIT_WORK(...)` 这类宏调用当成请求位。判据写的是“请求位”，宏调用不是位，改为：只算后面不跟 `(` 的标识符。这是按判据原意修实现，不改定义。
2. 按修订 1 改实现：成员调用只在成员名对应唯一结构体类型时成组；对象被写入（下标/成员赋值、memcpy 一类）后记为“已写”，按未知处理；E2 的接口条件改为“至少一个实现在某条路径上清零”。改了第一阶段，X1 父版本的缓存作废重跑。
3. 按修订 2 改实现（D1、D3 父版本跑完、其余 4 个未完成时停下，结果作废）：请求位收窄；E1 报来源函数；E2/E3 穿过最多 2 层包装找实现组；E3 补 R1。另有不改定义的修正：同文件 `static` 函数优先解析、空指针分支跟踪（`if (!x)` 等）、展开含 `__GFP_ZERO` 的宏、摘要加“混合”状态。自测加一例 `if (ret) memset; return ret;`（空分支不算正常返回）。
4. E3 实现收紧（D1 父版本重跑后，E3 37 条以 `copy_from_user` 21 条为主）：原来把“路径上清零了”（R1）和“用到了请求位”记成同一个标志，清零的实现都被当成了“用请求位的实现”。现在分开记；并且要求调用方带请求位的那个实参，对应到实现里一个确实和请求位一起出现过的参数（判据原文“测试它或把它传下去”的“它”）。被报实现本身也要满足这一条（后面确实用了请求位，只是提前返回的路径没用到）。
