# 判据：显示内核警告后在已有内核上重跑（kwarn_dev_20261111）

2026-11-11，Claude 在运行之前写定，SHA 存入 `criteria_sha256.txt`。对应 `汇报/2026-11-11/下一步规划.md` 的 0.2（用户同意先做 0.1、0.2）。

## 一、目的

此前所有运行的内核命令行都带 `quiet`，警告级别的内核消息到不了控制台（`dbgassert_dev_20261111` 发现）。本轮把它换成 `loglevel=5`，在已有的 23 个内核上把 `diverse_dev_20261110` 的用例原样重跑一遍，回答：

1. 默认配置的内核上，现有用例会不会触发内核警告？在哪些内核上？
2. 5 条已知缺陷的修复前内核上，有没有“修复前有、修复后没有”的警告？这相当于白捡的一路信号。
3. 换命令行之后，原来的判定和检出会不会变？不变才能把它设为默认。

不构建内核。

## 二、运行（写死）

- 工具：`difftest_tools_20261111/run.sh`（默认已改为 `loglevel=5`）、`compare.py`（归一化、超时单独成类）、`warnings.py`。
- 六组（当前版本和五个样本组）、23 个内核，用例清单是 `diverse_dev_20261110/gen` 的原清单（每组约 8000 个），每个内核 3 次。
- 告警事件的取法、归属、签名：沿用 `dbgassert_dev_20261111/criteria.md` 第四节。

## 三、要报告的数字

1. 每个内核：启动阶段、用例阶段、关机阶段各有哪些告警签名，几次运行中出现。
2. **修复前有、修复后没有**的签名（同一样本组内比较两个 riscv 内核）：全部人工核对，判断是否与该样本的缺陷有关。
3. **只在某个架构上出现**的签名（同一组内，按架构比较）：全部人工核对，结论分“能解释 / 不能解释（疑点，只记本地） / 未核对”。
4. 与 `diverse` 轮（`quiet`）的对比：用同一工具、同样的归一化和超时规则，分别比较两批日志，报告
   - 每个被检查的 riscv 内核上判定不同的用例数；
   - 五个样本组“构成检出的用例”集合是否相同（修复前为 `odd_riscv` 或 `weak_diff`，修复后为 `same` 或 `weak_same`）。
   参照：`stability` 轮测得两次独立运行之间的底噪是每组 0～6 个用例。

## 四、解读规则（事先写下）

- 判定不同的用例数在底噪范围内、检出集合相同（或只差在底噪用例上）：把 `loglevel=5` 设为默认。否则查明原因再定。
- “修复前有、修复后没有”的警告：只有在调用栈或消息内容能与该样本修复的代码对上时，才记为“与缺陷有关”；否则记为“无关或不明”。它不计入原有的检出得分，单独报告。
- 默认配置没有打开调试断言，所以没有警告不说明没有调用上下文类的问题。

## 五、规则

不构建、不安装、不联网、不调用大模型、不对外报告、不改旧轮次文件；日志入库后删除 WSL 里的临时目录。统计行：模型调用 0；构建 0；新确认缺陷 0；新疑点 N。
