统计行：模型调用 0；构建 0；新确认缺陷 0；新疑点 0。

## 为什么做

此前所有运行的内核命令行都带“静默”选项，警告级别的内核消息到不了控制台。上一轮构建调试内核时才发现这一点。把它改成显示警告不需要重新构建，所以在已有的 23 个内核上把上一批用例原样重跑一遍，看三件事：有没有内核警告；5 条已知缺陷的修复前内核上有没有“修复前有、修复后没有”的警告；换了命令行之后原来的判定和检出会不会变。

## 做法

用默认工具（`difftest_tools_20261111`）。六组（当前版本和五个样本组）、23 个内核，用例是 `diverse_dev_20261110` 的原清单（每组约 8000 个），每个内核 3 次，共 69 次运行，约 21 分钟，全部完整结束。

## 结果

### 一、内核警告：没有

23 个内核、69 次运行，启动阶段、用例阶段、关机阶段都**没有出现任何一条内核警告或错误报告**（`WARNING`、`BUG`、锁检查报告、崩溃信息都没有）。执行器记录的“污染标志”也没有变化。

所以“修复前有、修复后没有的警告”也没有。这一路信号在默认配置的内核上是空的。这符合预期的一半：默认配置没有打开调试断言，内核不会主动检查调用上下文；而这 5 条缺陷的表现都是返回值或输出不对，不是内核报错。

### 二、顺带看了其他内核消息（判据之外的观察）

除了警告，控制台上还有一些普通的内核消息。我按“去掉数字后的模板”比较了各内核在用例阶段打印了什么：

- **五个样本组里，修复前和修复后两个 riscv 内核打印的消息模板完全相同，条数也相同。** 没有任何消息能区分修复前后。
- 只在 riscv 上出现的：用户进程因非法访问被终止时，riscv 会把全部寄存器打印出来（每次运行约 15 次，每次十来行），arm64 和 x86 不打印这些。这是各架构打印习惯不同，不是缺陷。
- 只在 x86 上出现的：时钟源不稳定的提示。这是模拟器环境造成的，与内核行为无关。

### 三、换命令行不影响判定和检出

用同一套工具和规则，把这次的日志与上一批（静默）的日志分别比较：

| 组 | 判定不同的用例 | 构成检出的用例（静默 → 显示警告） |
| --- | --- | --- |
| 当前版本 | 3 | — |
| A101 | 2 | 3 → 3，集合相同 |
| A310 | 2 | 14 → 14，集合相同 |
| A171 | 3 | 19 → 19，集合相同 |
| A181 | 4 | 2 → 2，集合相同 |
| B467 | 3 | 3 → 3，集合相同 |

判定不同的都是进出“不稳定”，每组 2～4 个，落在两次独立运行之间的底噪范围内（上一轮测得每组 0～6 个）。五个样本组里构成检出的用例一个不差。

按事先写下的规则：**把“显示警告”设为默认**。

### 四、一个需要修的地方（已修）

显示警告以后，内核消息会成串地插进执行器某一行输出的中间（例如 x86 的时钟源提示，一次三四行）。原来的清理规则只处理“插进一行中间的单条消息”，遇到这种情况会解析失败。已经把默认比较脚本的清理规则改成“去掉所有带时间戳的内核消息行”，被打断的那一行就能重新接上。改完后旧日志的四项回归全部通过。

## 说明什么

1. 默认配置的内核在现有用例下不报任何警告，修复前的内核也一样。想靠内核自己的报错来发现调用上下文类的问题，必须用带调试断言的内核，默认内核不行。
2. 显示警告没有副作用，可以作为默认；以后如果某个用例真的让内核报错，不会再被悄悄挡掉。
3. riscv 在用户进程出错时会多打印很多寄存器信息。它不影响结果，但会让日志变大，也是“内核消息插进输出行”最常见的来源。
