# 架构接口完备性对比：以RISC-V为对象

## 这一轮要回答什么

前面“从一次公共改动出发、去找要跟着改的函数”这条路线走不通；而且RISC-V的历史修复里，多数是“需要**新加**东西”，比如补一个宏、打开一个配置开关。

这一轮换个角度。公共代码允许或要求各架构提供一些东西，我们把这些东西列成清单，比较哪些是**x86和arm64都提供了、RISC-V却没有**的。这类接口称为“缺口”。要回答两个问题：

1. RISC-V真正修过的“缺东西”的bug，在修复之前有多少已经出现在缺口清单里？
2. 缺口清单有多长？里面有多少是真问题？

不调用模型，不构建内核。

## 比较哪些东西

| 类别 | 是什么 | 例子 |
| --- | --- | --- |
| K：配置开关 | 架构在Kconfig里`select`的`ARCH_HAS_*`、`HAVE_*`等配置，公共代码会根据它决定是否启用某个功能 | `ARCH_HAS_NON_OVERLAPPING_ADDRESS_SPACE` |
| M：约定宏 | 架构定义的`__HAVE_ARCH_*`、`__ARCH_WANT_*`等宏，告诉公共代码“我有自己的版本”或“我需要这个系统调用” | `__ARCH_WANT_NEW_STAT` |
| S：“已提供”标记 | 架构写`#define 名字 名字`，告诉公共头文件“这个函数我自己提供了，别用默认版本” | `#define tlb_flush tlb_flush` |
| W：可覆盖函数 | 公共代码里用`__weak`标记的默认函数，架构可以写一个同名函数替换它 | `crash_smp_send_stop` |

只统计公共代码确实会用到的接口。

## 结果

### 1. 回溯召回（主指标）

v4.15以来，带`Fixes:`标签、并且新增提供了某个接口的RISC-V修复，共20条（19个提交）。

| 缺口定义 | 修复之前已是缺口 |
| --- | ---: |
| **x86和arm64都提供（主定义）** | **6/20（30%）** |
| 仅看arm64 | 12/20（60%） |
| x86、arm64、powerpc、s390中至少3个提供 | 6/20（30%） |

主定义召回到的6条都是名副其实的“RISC-V缺了别人都有的东西”：

| 修复 | 缺的接口 | 后果 |
| --- | --- | --- |
| RISC-V: Request newstat syscalls | `__ARCH_WANT_NEW_STAT` | 公共代码把旧的stat系统调用移出默认集合后，RISC-V没再申请，相关系统调用就没有了 |
| riscv: Fix ftrace syscall handling which are now prefixed with `__riscv_` | `ARCH_HAS_SYSCALL_MATCH_SYM_NAME` | 系统调用符号改名后，ftrace匹配不上系统调用 |
| riscv: fix kprobe `__user` string arg print fault issue | `ARCH_HAS_NON_OVERLAPPING_ADDRESS_SPACE` | kprobe打印用户态字符串参数时出错 |
| RISC-V: kexec: Fix memory leak of fdt buffer | `arch_kimage_file_post_load_cleanup` | kexec加载后，设备树缓冲区泄漏 |
| RISC-V: Fixup schedule out issue in machine_crash_shutdown() | `crash_smp_send_stop` | 崩溃关机流程中出现调度问题，修复改为由架构提供这个函数 |
| riscv: Select ARCH_USE_MEMTEST | `ARCH_USE_MEMTEST` | 内存测试功能没打开 |

其中3条在修复之前最近的那个长期支持版本里，就已经是缺口了。

漏掉的14条主要分三种：

- **只有部分参考架构提供（10条）**：这些接口对应的功能，RISC-V只和某一两个架构相同。例如：
  - RISC-V的NAPOT大页与arm64的连续页类似，相关接口`huge_ptep_get`、`arch_hugetlb_migration_supported`、`hugetlb_mask_last_page`、`arch_get_idle_state_flags`只有arm64有；
  - `arch_clear_hugepage_flags`只有arm64和s390有；
  - `pudp_huge_get_and_clear`只有x86和powerpc有（两个标题相同的提交，算2条）；
  - `pmdp_collapse_flush`只有powerpc和s390有；
  - `is_trap_insn`和membarrier的内存屏障开关只有powerpc有。
- **本身不是“缺接口”（4条）**：
  - 一次cacheinfo的公共重构，改动顺带落在RISC-V上，算了2条；
  - 一次配置改名与RISC-V的新代码撞车；
  - 一次把宏改写为inline函数。

### 2. 缺口清单有多长，后来怎样

| 版本 | 缺口数 | 到终点已补上 | 其中由带`Fixes:`的修复补上 | 仍是缺口 | 接口已不存在或不再满足定义 |
| --- | ---: | ---: | ---: | ---: | ---: |
| v5.10 | 130 | 55 | 3 | 36 | 39 |
| v5.15 | 105 | 39 | 3 | 43 | 23 |
| v6.1 | 114 | 42 | 3 | 49 | 23 |
| v6.6 | 90 | 27 | 1 | 52 | 11 |
| v6.12 | 79 | 16 | 0 | 62 | 1 |
| 终点 | 83 | — | — | — | — |

- 缺口数中位数为105，后来被补上的占34.6%。但补上缺口的几乎都是**加功能**的提交，由修bug的提交补上的，每个版本只有0到3个。
- 反过来看：v4.15以来RISC-V所有“新增提供某个接口”的提交共397条，其中179条（45%）在提交之前就是主定义下的缺口。缺口清单能较好地预测“RISC-V接下来会移植什么功能”，但大多数并不是bug。

### 3. 当前缺口的人工抽查（终点版本，20个）

| 归类 | 个数 | 例子 |
| --- | ---: | --- |
| (a) 疑似RISC-V该补而没补 | **0** | — |
| (b) 硬件没有对应特性，或按设计不适用 | 5 | 内存保护键；资源监控与分配；`gethostname`、`getpgrp`、`pause`等旧系统调用（新架构的系统调用表本来就不包含） |
| (c) 用别的方式实现了，或通用默认版本就够用 | 7 | CPPC的`cpc_read_ffh`实现在`drivers/acpi/riscv/`（程序只看`arch/`，这是检测范围的局限）；函数图追踪走`ftrace_graph_func` |
| (e) 可选功能尚未实现，不影响正确性 | 8 | BPF即时编译的几项能力、`HAVE_STATIC_CALL`、ACPI APEI |

(e)类是人工查看时新增的，因为判据原定的a–d四类装不下“可选功能还没做”这种情况。

### 4. 与此前24对RISC-V案例的对应

24对中只有2对的修复新增提供了接口，分别是`__ARCH_WANT_NEW_STAT`和`arch_get_idle_state_flags`。前者在主定义下是缺口；后者只有arm64提供，不是。

## 结论

- 按事先定的规则：召回30%，处在“介于两者之间”。缺口数中位数105（≤150）、后来补上的比例34.6%（≥20%）都满足要求，但召回刚好落在下限上。按规则要先分析漏掉的修复，分析见上。
- **完备性对比能抓住一类真实的问题**：RISC-V缺了x86和arm64都有的约定接口。召回到的6条都是真bug，其中一半在修复前的长期支持版本里就已经能看到。
- **但作为找bug的工具，它的准确率很低**：每个版本有约一百个缺口，后来由修bug提交补上的只有几个。人工抽查的20个当前缺口，没有一个像是该补没补的。缺口清单更像是一张“RISC-V还没移植的功能清单”。
- 漏掉的修复，多是RISC-V只与某一两个架构共享的功能，例如NAPOT大页之于arm64的连续页。用“x86和arm64都提供”做参照抓不到这一类；只用arm64做参照能召回60%，但清单会长将近一倍。

## 可能的下一步（未登记）

1. **按“公共代码在不提供时会不会出错”给缺口分级**，而不是一视同仁。例如：
   - `__ARCH_WANT_*`系统调用开关，缺了就会少系统调用；
   - `__weak`默认实现为空、但语义上必须由架构完成的函数，例如崩溃时停止其他CPU。

   这样可以把“可选功能”和“必须提供”的接口分开，有望提高准确率。
2. **按功能相近的架构选参照**：例如大页相关的接口用arm64作参照，而不是固定用x86和arm64。
3. 把检测范围从`arch/`扩大到`drivers/*/riscv/`等架构专属目录，减少类似`cpc_read_ffh`的误报。
