## 这一轮要回答什么

效果依赖检查到现在只有 X1 一个样本。`vrecall` 按“删掉了调用后的开关赋值”去筛，近五年只找到 X1。师兄结论第 18 条说，更常见的是“缺失的操作根本没有对应语句”，修复时是**新增**一项检查或工作。

本轮按三种“新增”形态，在 v5.10 以来的修复里机械筛选，抽样读补丁，回答三个问题：
- 这类“跨边界的隐式依赖缺失”大约有多少？
- 它们长什么样？
- 能不能给效果依赖检查攒出足够的开发样本？

只读 git 历史，没有构建，没有运行内核。

## 三种形态

- **A：公共侧新增对架构接口结果的检查**。例如新增 `if (!pmd_present(pmd))`，或者像 X1 那样改成 `init = !tag_clear_highpages(...)`，再由条件判断。
- **B：公共侧在调用架构接口附近新增一项工作**：清零、写页表项、刷 TLB、刷缓存或内存屏障。例如在调用某个架构接口后补一个 `flush_dcache_page()`。
- **C：架构实现里新增一项效果**。所在函数是架构接口，补丁在里面新增了上述效果。

“架构接口”指在当前版本里有架构自己的定义，并且还有通用定义或至少两个架构定义的名字（共 4868 个），去掉字符串、位操作、原子操作这类库函数。

## 16 个“是”长什么样

按依赖的方向分：公共层依赖架构接口的有 11 个，架构实现不满足公共层约定的有 5 个。**没有一个是 X1 那种“先写了再用开关跳过”**，全部是“根本没写”或者“用错了”。这就是纵向信号一直找不到第二个例子的原因。

按内容归成六类：

| 类 | 个数 | 例子 | 说人话 |
|---|---|---|---|
| **P1 没查 present 就用了只对 present 条目有定义的接口** | 3 | `26e7888a0c89`：公共层对非 present 的 PMD 调 `pmd_leaf()`。loongarch 的 `pmd_leaf` 只看 `_PAGE_HUGE` 位，交换项恰好总带这一位，于是误判成大页。`43e7f189769c`：对交换项调 `pmd_write()`，x86 上软脏位和可写位是同一位。`49c87f767774`：arm64 的 `huge_ptep_get_and_clear` 假设条目是 present，公共层却会对迁移项调它 | 页表项有“在内存里”和“不在内存里（交换、迁移、标记）”两种状态。很多架构接口只对前者有意义，但原型里没写这一点。哪个架构会出错，取决于它的位编码 |
| **P2 只在缓存有别名的架构上需要的刷缓存，被漏掉或范围不对** | 3 | `19b482c29b6f`：shmem 漏了 `flush_dcache_page()`。`7f9c9b607dc2`、`9add2cc22de6`：对大页只刷了一页 | 这些钩子在 x86、arm64、riscv 上是空函数，所以在这些架构上永远测不出来 |
| **P3 公共层对大页级别或形式的假设** | 2 | `fac35ba763ed`：以为 hugetlb 只在 PMD/PUD 级，arm64 的 CONT-PTE 大页用错了锁。`cb0f01beb166`：mprotect 没处理 PUD 大页，只有 x86_64、ppc64 会走到 | 有的架构多支持了一种页表形式，公共代码没想到 |
| **P4 架构接口有原型里没写的副作用，或效果范围不同** | 3 | `8c5b3a8adad2`：arm64 的 `set_pte_at()` 会顺带设一个页标志。`f0293cd1f4fc`：riscv 的 `flush_tlb_range()` 不清缓存的非叶子页表项。`f64c723741c9`：arm64 要求页表项先清空再写新值 | 同一个接口，各架构做的事多一点或少一点 |
| **P5 架构实现违反公共层的调用顺序或时机约定** | 4 | `496e0f706b8a`：s390 以为 `kvm_arch_vcpu_postcreate()` 一定先于运行。`213aa670153e`：parisc 在公共层约定的时间之前就写保护了 `__ro_after_init`。`8cfe148a7136`：arm64 KVM 违反了 RCU 的约定。`1037d186edfc`：openrisc 去掉了公共 earlycon 依赖的 early ioremap | 公共层“什么时候调、调之前保证什么”没写进原型 |
| **P6 架构特有的地址区域** | 1 | `ce732a7520b0`：KMSAN 不认识 x86 的 CPU entry area | 公共代码只认识通用的地址布局 |

另外有两个“不是”值得一提：`6455b6163d8c`（arm64）和 `175e476b8cdf`（MIPS64）是内存屏障太弱，只在弱内存序的架构上出错。它们是跨架构缺陷，但不是边界上的依赖，所以没算进“是”。

## 看出的几点

1. **依赖缺失的样本是有的，而且不少。** 按形态 C 筛出的修复里约三分之一是这一类，形态 A、B 约四分之一到五分之一。效果依赖检查可以有开发集了。
2. **它们几乎都是“根本没写”，不是“写了再跳过”。** 现在的纵向信号只认后一种，所以一个也抓不到。下一版静态形态要改成找“缺了什么”。
3. **P1 最适合马上做成静态检查。** 规则很机械：调用只对 present 条目有定义的页表访问函数（`pmd_leaf`、`pmd_write`、`pte_dirty` 等）之前，同一路径上必须先查过 `p?d_present`。它正好是师兄说的“一侧写、另一侧不检查就直接使用”，而且三个例子分别落在 loongarch、x86、arm64 上，不只是 riscv。动态上也有办法触发：迁移项、交换项、uffd 标记都能从用户态造出来。
4. **P2 在我们的架构矩阵（riscv、x86、arm64）上测不出来**，那些钩子都是空的。要测，得加 arm32、mips 或 parisc 这类缓存有别名的架构。
5. **P4、P5 的“约定”目前不在任何原型里**，静态上只能靠横向比较各架构实现做了什么（例如 `f0293cd1f4fc`：riscv 缺了自己的 `pmdp_collapse_flush`），或者靠动态的性质检查。
