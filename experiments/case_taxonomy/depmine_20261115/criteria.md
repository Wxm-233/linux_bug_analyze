## 三、三种形态（写死，机械）

在同一个补丁块（hunk）里判断。“新增”指 `+` 行；“修复后代码”指上下文行加 `+` 行；“修复前代码”指上下文行加 `-` 行。

- **形态 A：公共侧新增对架构接口结果的检查**（公共侧文件）。满足任一条：
  - A1：某个 `+` 行含 `if (` 或 `while (`，条件里调用了架构接口 I，并且 I 在这个补丁块 `+` 行里出现的次数多于 `-` 行；
  - A2：某个 `+` 行形如 `v = ...I(...)...;`（I 是架构接口，`v` 是变量名），I 的次数条件同上，并且 `v` 在修复后代码的某个 `if (` 或 `while (` 行里出现。
- **形态 B：公共侧在调用架构接口附近新增一项工作**（公共侧文件）。某个 `+` 行调用了效果调用 E；在修复后代码里，这一行之前 8 行以内调用了架构接口 I（I ≠ E）；并且 E 在这个补丁块 `+` 行里出现的次数多于 `-` 行。
- **形态 C：架构实现里新增一项效果**（架构侧文件）。补丁块所在的函数是架构接口：取补丁块头 `@@ ... @@` 后 git 给出的函数上下文里的函数名，没有就取补丁块内第一个函数定义行。某个 `+` 行调用了效果调用 E，E 在这个补丁块 `+` 行里出现的次数多于 `-` 行。

一个提交可以同时属于几种形态。

## 五、判断（逐条读提交说明和匹配的补丁块）

每个抽中的提交判为下面三种之一：

- **是**：修复补上的检查、工作或效果，是因为边界一侧对另一侧有**函数原型里没写明的假设**（某效果已经做了、某性质成立、某返回值不会出现），而这个假设在**部分架构**上不成立。必须能从提交说明或代码里看出和架构差异有关：提到具体架构、某些架构的实现不同、某配置只在部分架构上有。
- **不是**：
  - 与架构无关的普通逻辑错误、竞态、泄漏、错误处理；
  - 纯重构；
  - 只是架构内部的问题，与公共层的约定无关。
- **说不清**：如实写。

对判为“是”或“说不清”的，再记下：
- 依赖方向：公共层依赖架构接口，还是架构依赖公共层；
- 缺的是什么：检查返回值、效果（清零、刷 TLB、刷缓存、屏障、页表项）、顺序，或别的；
- 修复前公共层是否“写了再跳过”（`vrecall` 的形态），还是“根本没写”；
- 涉及哪些架构。

判断时只能看提交本身（提交说明、补丁、必要时修复前后的源码），不看任何静态分析结果。
