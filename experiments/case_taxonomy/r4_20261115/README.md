## 为什么要加 R4

`rulemap2` 发现，静态候选 `move_ptes`（`mm/mremap.c`）依赖的是：搬移页表时，有效的表项被正确搬到新位置，空的表项保持为空。

这一点很重要。如果某个架构的相关接口出错，mremap 之后用户在新地址看到的就是零，原来的数据丢了。但现有的三条规则（R1 清零、R2 旧翻译失效、R3 指令缓存一致）都不检查这一点。

## R4 和两个模板

**R4**：用 `mremap` 把一段用户内存搬到新地址后，搬过去的内容必须与原来一致，没访问过的页必须读到零。

| 模板 | 做法 |
|---|---|
| P1 | 64KB 匿名内存，第 i 页写满 `0x30+i`；用 `MREMAP_FIXED` 强制搬到另一个地址；逐字节核对 |
| P2 | 同上，但只写 `i % 3 != 2` 的页，其余页保持没访问过（页表项为空）；搬移后写过的页要等于原值，没写过的要全为零 |

两个模板加在 `propsuite4.c` 里（= `propsuite3.c` + P1、P2），原有 13 个模板没有改动。

## 怎么验证

1. **变异**：在架构头文件里定义一个有缺陷的 `move_pte`。这个接口本来就允许架构覆盖，sparc 有真实的实现，而且只在 `move_ptes` 里被调用，所以变异只影响搬移这一条路径。
   - **R4a**：搬移时丢掉所有有效表项；
   - **R4b**：只丢掉页号为奇数的表项。
   - 在 riscv、x86_64 上各构建一个。
2. **阴性对照**：未改动的 HEAD 内核，riscv、x86_64、arm64。
3. **覆盖**：在 `kcov_pa` 的当前版本 KCOV 内核上，确认 P1、P2 真的走到了 `move_ptes`。

## 中途出的错（修订 1）

第一批变异只定义了 `move_pte`。但通用头文件的保护条件是 `#ifndef __HAVE_ARCH_MOVE_PTE`，不是“架构有没有定义 `move_pte`”：

- x86 开了 `-Werror`，重复定义直接报错，构建失败；
- riscv 只报警告，结果通用定义把变异覆盖了，变异没生效（第一批 riscv 上 P1、P2 都是 0/3）。

改为同时定义 `__HAVE_ARCH_MOVE_PTE`（和 sparc 的做法一样）后重建，构建日志里“macro redefined”出现 0 次。第一批阳性运行移到了 `runs/pos_invalid1/`。

这次失误正是新写的构建复用工具里要加“预检”的原因：打上变异后，先预处理一个文件，确认变异真的生效。

## 局限

- **变异打在 `move_pte` 上，而静态候选的接口是 `pte_none`。** `pte_none` 在全内核到处被用，直接改坏它内核起不来。两者在这条路径上的可观测后果相同：有效映射在搬移中丢失，新地址读到零。但 R4 还没有直接针对 `pte_none` 出错验证过。
- 只验证了“丢映射”这一类错误。“空表项被当成有效的搬过去”在 `move_ptes` 里不会发生（空表项在调用 `move_pte` 之前就被跳过了），P2 的空洞检查只是兜底。
- X1 的两棵树没有 P1、P2 的判错结果，没有重跑流水线。
