# 补丁场景的检查：第2版

## 这一轮要回答什么

上一轮（`patch_rules_20261105/`）补了三项程序检查和模型审查补丁，结果有三个问题：
- P1（反向执行上下文）、P2（变体接口完整性）在开发样例上按预期报告，但在终点版本全架构上误报过多：27条中26条不成立，1条判断不了；
- 模型审查补丁（L）以错误理由推翻了正确的K1标记（0/6）；
- L在已知缺陷都已修正的第8步上，报出的问题大多不成立。

本轮收紧P1、P2，并给模型审查加上程序收集的代码事实和依据要求。

**性质说明**：收紧的依据来自上一轮在同样版本上看到的误报，所以本轮在这些版本上的结果都是**调参，不是独立评估**。

## 改了什么

**P1第2版**：
1. 陷入处理函数中，第一次打开中断之前的调用，算作已固定在当前CPU上；
2. 处在“在线CPU少于2个”条件下的调用，算作已固定；
3. **要有可能被迁移的正面证据才报告**：调用链上某个函数调用了会睡眠的函数，或者断言自己持有互斥锁。能睡眠就一定能被迁移，没有这种证据的链不报告；
4. 追溯深度由3层改为4层。

**P2第2版**：只在“两个变体共用的文件调用了这个接口”时报告。

**L2**：
- 由程序按固定规则收集代码事实：被改函数直接调用的函数的实现（宏展开一层），另一个变体中的同名函数，以及被改函数在仓库中的调用点；
- 报告问题、否定程序标记，都必须引用材料中的代码，否则只能写“判断不了”；
- 程序检查结果改附P1、P2第2版。

## 结果

### 1. P1、P2第2版

| | 开发样例 | 终点版本全架构 |
| --- | --- | --- |
| P1 | K1仍在模型系列第2–5步、上游迁移3步、上游修复前报告，在模型系列第6–8步、上游修复后不报告 | 13条 → **3条**，3条都不成立 |
| P2 | K3（`bpf_arch_text_copy`）仍在第4–6步报告，第7–8步不报告 | 14条 → **0条** |

- 按参考线，P1、P2都“开发样例通过”。P2在终点版本上没有标记；P1剩下3条都不成立，仍记为“误报过多”，但数量已从13条降到3条。
- P1剩下的3条属于同一种情况：本核刷新之后，紧接着还有一次全核刷新，或者之前已经全核刷新过。例如`flush_icache_all`先刷本核，再刷所有CPU；`thead_errata_patch_func`在模块阶段已经经`patch_text_nosync`做过全核刷新；`machine_kexec`调用时其他CPU已经下线。所以迁移到别的CPU也不影响结果。
- 代价：P2第2版不再报告`bpf_arch_text_invalidate`。RV32缺少它其实也是问题，但它只被公共代码调用，不在新条件的范围内。

这一轮把核对结果分为三类：
- **真问题**：所审查的代码中确有错误；

- **不成立**。

**已知缺陷**：

| 缺陷 | L1 | L2 |
| --- | --- | --- |
| K4 JIT漏了可执行的运行地址 | 3/3 | 3/3 |

**变化的原因**：
- **不成立的问题从10个降到0个**：上一轮误报的指令缓存、finalize失败泄漏、RV32 PC相对计算等，这次材料里有`patch_text_nosync`、`bpf_jit_binary_pack_finalize`、RV32 `emit_call`的实现，模型都没有再报。
- **K1从“错误否定”变成“判断不了”**：依据要求起了作用。K1的关键事实是`__set_fixmap`只刷本核TLB，它在第三层调用里，按固定规则没有收进材料，所以模型如实写了判断不了。要发现K1，代码事实还要再往下收一层，或者对宏展开后的函数再展开一层。
- **“与参照一致”的问题变多了**：finalize失败后`jited`已置位、收敛循环中出错时泄漏pack、`bpf_jit_free`中finalize失败后重复释放。这些都是真实存在的代码问题，但上游RISC-V迁移`48a8f78c50bd`的写法完全相同，不是这次迁移引入的。

### 3. 模型审查发现的一个新疑点（已有代码，属于第一部分）

L2在第4步3次中有2次、第8步有1次指出：`patch_map`只在`CONFIG_STRICT_MODULE_RWX`开启时，才对vmalloc地址做fixmap映射，否则直接返回原地址；而BPF的pack已经被`set_memory_rox`设成只读，所以写入会失败。

我核对后，认为这是**终点版本上游RISC-V中也存在的问题**（按代码推断，未运行验证，只记录）：
- 上游提交`2c9e5d4a0082`去掉了`BPF_JIT`对`MODULES`的依赖。`STRICT_MODULE_RWX`依赖`MODULES`，RISC-V上还可以由用户关闭（`ARCH_OPTIONAL_KERNEL_RWX`）。
- arm64因此出过问题：开启`BPF_JIT`、关闭`MODULES`时，`bpf_arch_text_copy`写只读区失败，释放时报警告。arm64的修复`b1480ed230ac`（Fixes: `2c9e5d4a0082`）把判断改为`CONFIG_EXECMEM`。
- 终点版本`df2908090cda`中，RISC-V的`patch_map`仍然用`IS_ENABLED(CONFIG_STRICT_MODULE_RWX)`判断，而`bpf_arch_text_copy`会把写入失败变成`ERR_PTR(-EINVAL)`返回。所以关闭`MODULES`时，RISC-V的BPF JIT应当无法把代码写进pack，每个程序都会JIT失败。
- 这是典型的M8（演进落后）：公共代码改了约定，arm64跟上了，RISC-V没有跟上。可以在QEMU中用`MODULES=n`、`BPF_JIT=y`的配置运行验证，列入待办。

此前的模型迁移结果、上游的迁移都继承了这个问题。

### 4. 在模型迁移结果中再次确认的问题

`bpf_arch_text_poke`的锁断言（L2中6/6）和整块`kzalloc`（6/6）与上一轮相同。L2都引用了调用点作为依据：trampoline和arraymap的调用者都不持有`text_mutex`。

## 看出的几点（只作描述）

- **给出代码事实、要求引用依据，能大幅减少模型审查的误报**：不成立的问题从10个降到0个，同时没有丢掉K3、K4和两处真问题，还多发现了一个上游已有的问题。这与第一部分复核第2版的经验一致。
- **依据要求能让模型不再凭印象否定正确的程序标记**，但它也只能做到“判断不了”。要让模型确认K1，必须把关键事实（`__set_fixmap`只刷本核TLB）放进材料。下一步可以让P1在报告时，把它沿调用链看到的“只刷本核”的那段代码一起附上。这正是“由程序给出事实”。
- **第二部分的审查也能发现第一部分的问题**：`patch_map`的问题存在于已有代码中，是在审查迁移补丁时被带出来的。
- **程序检查收紧之后误报降到个位数**，但这些都是在同样版本上调出来的，需要在历史回放样本上独立评估。

## 局限

- 只有一个迁移案例，K1–K4和上一轮的误报都用来设计本轮的修改，不是独立评估。
- `patch_map`疑点和两处模型迁移问题都没有运行验证。
- 三类核对由我完成。“与参照一致”的判断依据是上游迁移`48a8f78c50bd`中同一处代码的写法。
- 每个版本只审查3次。

## 统计

模型调用9次（全部完成）；构建0次；规则运行16个版本；新确认缺陷0；新疑点1（RISC-V `patch_map`在`STRICT_MODULE_RWX`关闭时直接写只读的BPF pack，arm64已修，只记录、未运行验证、未上报）。
