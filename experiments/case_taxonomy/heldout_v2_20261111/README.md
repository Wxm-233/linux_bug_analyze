### 说明什么

1. **符合事先写下的预期**（第一版判据第七节）：开发集里能从系统调用带着参数走到修复位置的只占 13%，“10 个候选里可能只有 1～2 个够得着，确认合计可能是 0”。实际是 0 个够得着，所以 0 分说明的是**方法的适用面**，而不是“方法在够得着的缺陷上失败了”。这批数据**回答不了** G3g 和 G3c 谁更好。
2. **LoongArch 的修复和开发集的五条缺陷性质不同**：开发集挑的是“架构边界常量 / 架构实现在系统调用参数上表现不同”的缺陷；LoongArch 这 10 个是普通的架构维护修复（调试设施、BPF JIT、vDSO、页表位、泄漏）。按日期等距抽样抽到的就是这样的分布。
3. **暴露出的方法盲区**（下一版要考虑，不在本轮修改）：
   - 静态分析的范围只有 `arch/<目标>/kernel/`、`arch/<目标>/mm/` 和公共目录，`arch/<目标>/net/`（BPF JIT）不在内；
   - 执行器只发单个系统调用，看不到需要多步状态的问题（L04、L09）和 vDSO 路径（L06）；
   - 默认配置覆盖不到的代码（L02）测不到，这一点只能如实报告。

## 暂停时发现并修好的两个脚本问题（不涉及方法文件）

暂停前 L02 已经走完了构建、静态分析、探测、清理，但在生成用例一步失败。查下来是两个基础脚本的问题，第一版也有、只是第一版没有候选走到这一步：

1. `static_group.sh` 抽事实时把源码根目录写成了主仓库，而候选的编译数据库指向导出的源码副本，结果事实是空的（0 个编译单元），后面的词表、排序也都是空的。已改为传入候选自己的源码目录，并加了检查：抽出的函数为 0 就报错停止。
2. 运行脚本里 S 为空时没有加引号，生成脚本少了一个参数。已加引号。

L02 的所有步骤标记已清除，接着跑时从头重新构建。这两处只改了调度脚本，31 个方法文件的校验值不变。

另外记下一个观察：L02 打上修复后做增量构建，**一个文件都没有重新编译**，修复前后的内核镜像逐字节相同。也就是说，按默认配置，L02 修改的代码根本没有编进内核，动态测试不可能检出它。这是要如实报告的结果（“默认配置覆盖不到”），不是失败。没有为此去读补丁。

以前每个候选跑完 `clean` 就把源码副本和三个构建目录全删了，只剩内核镜像，以后要重跑静态分析或做动态定位都得重新构建。恢复运行前改成：

这些只改了调度脚本（`build_cand.sh` 多了 `keep` 一步，`save`、`fix` 多拷 `vmlinux`），方法文件校验值不变。
