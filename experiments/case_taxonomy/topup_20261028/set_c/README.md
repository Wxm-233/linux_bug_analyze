## 事后复核（输出保存后读修复，描述性，非登记指标）

20个样本中**5个是跨架构相关的真修复**，E4全部漏掉，原因各不相同：

| 样本 | 修复 | 为什么E4没抓住 |
| --- | --- | --- |
| s01 | net/smc：非s390架构上禁用SEID | 按`CONFIG_S390`开关的行为契约，无对应模板 |
| s07 | sched/arm64：最后兜底选rq时考虑CPU隔离 | 可覆盖钩子及其公共回退是修复**新增**的，父版不存在，无法从父版枚举实例 |
| s10 | perf：`order > MAX_ORDER`改为`>=` | 运行时变量与开区间上限的语义；F2只比较两个宏常量 |
| s15 | drm/r128：修复UML构建 | `__x86_64__`编译器预定义与`CONFIG_X86`不一致；UML不在上下文中，且追踪失败 |
| s18 | memcg：`socket_pressure`改u64 | 32位字长下的撕裂；无字长模板 |

另有5个主题相关但非缺陷修复（s05、s14、s16、s17、s19：架构宏改名、重构、清理），10个范围外（网络、驱动、tracing、新功能等）。s09为选样误中（include guard名`_TOUCH_OVERLAY`不以`_H`结尾）。

## 结论

- 按diff形态抽样确实把跨架构相关的修复带进了样本（真修复5/20），但从die、shmem、s04提炼的检查族在这些未接触修复上**命中为0**。五个漏检分属五种机制：配置开关行为、修复新增的钩子、运行时值对上限语义、预定义宏对Kconfig、字长原子性——没有一个与F1/F2/F3的形态相同。
- 这说明E4的问题不在噪声或执行细节，而在**覆盖面**：每个检查族都是单个案例的形态，未接触缺陷的形态多样，逐个加模板难以追上。
- 零误报也没有多少说服力：对照与样本一样几乎不产生实例。

## 冻结后记录的局限（不回填）

追踪上下文为三个defconfig，驱动类文件常不构建，致追踪全部失败（样本4、对照3）；S-F1.1的include guard排除只认`_H`结尾；F2对“上限按设计不超过几何量”的配对方向会误报。
