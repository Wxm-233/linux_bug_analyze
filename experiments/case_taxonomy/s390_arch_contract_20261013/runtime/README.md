## 架构因果链与检查启示

旧s390在CPU上线后才更新拓扑，更新函数又排除未上线CPU。它先通知共同CPUHP入口，因此公共调度初始化首次使用时得到空集合；实际锁循环执行零次，原消费者找不到core_rq而告警。上线后mask变为正常单CPU集合，最终sysfs也正常，不能替代首次消费观察。

x86在通知之前按“已准备”集合建图，CPU虽未上线，self已存在。修复s390也先加入setup集合、更新拓扑，再通知公共代码。两种架构不需要相同内部实现，但交接时必须满足同一消费者要求。这补齐了“架构差异来源→公共接口→共同首次使用→不同暴露结果”的窄运行链。

适合提取的检查候选是：**在通知边界或公共首次消费点，确认该架构的拓扑已经准备，集合包含当前CPU，并记录状态的提供者和资格来源。** 直接要求cpu_online=true会误报这三格正常路径；只检查最终mask会漏掉旧s390。检查更新语句在前也不够，还要检查更新函数是否按错误资格集合过滤。完整SMT兄弟集合仍需另证。
