| 入口 | 原文能支持的关系 | 仍缺什么 |
|---|---|---|
| `cpu_init_topology`，195–220 | 将形参c放入局部tscan.c，调用parse_topology；把tscan.dom_shifts交给memcpy写入x86_topo_system.dom_shifts，再由这些shift计算dom_size，随后调用topo_set_ids | parse_topology如何取得/写出信息、依赖哪个CPUID叶、实际配置和对象值均未知 |
| `cpu_parse_topology`，166–193 | 创建另一个局部tscan，调用parse_topology；核对APIC及局部/系统dom_shifts，随后调用topo_set_ids | 比较时的实际值、helper语义和两次执行的对象关系均未证明 |

这补充了“架构/厂商准备影响读取结果后，信息可能进一步固化为共享派生状态”的源码去向。后来的能力重采不应直接当成这些派生字段已经重算；但仅凭本轮两定义，也不能断言它们必然保留错误值。硬件可见范围、c->cpuid_level、能力位、两个不同的局部tscan与共享派生字段分别记录，不用同一个“准备状态”代替。

后续CPU比较不匹配时只记录日志，不是调用topo_set_ids的阻断门槛。告警或无告警均不能直接充当完整契约的判定依据。

## 怎样转成检查候选

研究侧形成`dependency_candidate.json`：**若某个派生结果确实依赖提供方的准备效果，应在该次派生前建立必要输入状态；或者另证受影响结果在首次使用前已经重新计算。** 检查位置应落在真正依赖输入的读取/分支，不能要求所有CPUID读取先解锁，识别厂商和型号本身可以在前。

此候选的依据、适用条件、准备效果和准确期限尚未完整建立，状态保持`insufficient`。它由研究者在读过修复后归纳，不是新模型自动输出，也不是已经自动生成的通用检测规则。它对大方向的作用是明确N1下一步需要取得的数据关系，并帮助N2以后区分可比路径；本轮没有实施配置选择。

## 三类不足分别记录

- **输入仍缺**：新两定义均把实际解析交给parse_topology，topo_set_ids也未展开；尚未定位真正CPUID依赖读取。这里按范围停止，不沿helper/include继续递归。
- **工具尚不支持**：旧完整函数定位器不支持`void __init`，保留失败后仅按已定位原行和括号取得完整原文，未改冻结方法。程序对初始化函数可保留200/203/213三处调用，但循环阻止完整局部流程结论；另一函数因FW_BUG字符串宏未展开而解析不足，前向提取又不支持该__init头形态。没有删宏/循环或补桩制造通过。
- **旧模型未提出的关系**：原A回答没有提出解锁与拓扑依赖消费的主要关系。新增源码在原输入中不存在，因此不能拿本次人工补证回算旧模型漏报率，亦不能预言加材料后一定改善。旧六项claim和结果未改。
