## 程序纠错起作用的一次

本轮4次运行共写出52条事实声明：
- 相符51条；
- 不符1条；
- 无法核对0条。

那1条不符正好是设计这个做法时设想的情形：
1. **第5次运行的第一步**：模型对`arch_cpu_idle`写了声明“函数签名带`__cpuidle`”，并据此判为**误报**。
2. **程序核对**：签名是`void arch_cpu_idle(void)`，不带`__cpuidle`，判为不符。
3. **把核对结果反馈给模型后**：它改判为**真问题**，理由是“它被`__cpuidle`的`default_idle_call`调用，自身却没有`__cpuidle`或`noinstr`标注，可被插桩；x86和arm64都有该标注”。这正是上游修复的内容。

没有这一步，第5次运行会把这个真问题去掉。

## 事后分析（只作描述）

1. **“要求写出可核对的事实”使判断更准、更稳。** 同样的18个问题、同样的模型，不要求写声明时，单次保留率在75%～100%之间浮动；要求写声明后，5次都是100%。
2. **程序核对是一道保险。** 大多数时候模型写出的事实是对的，51/52；偶尔说错时，核对加追问能把判断纠正过来。
3. **模型并不总写声明。** 72次回答中有49次没写任何声明，所以程序核对能覆盖到的判断有限。
4. **样本少。** 只有18个问题、8个真问题，结论需要在更多独立样本上验证。另外，其中10个误报的标签来自第一标注人，GPT复核材料已备好。

## 结论

- 按判据，**本轮达到成功标准**：在新样本上，“要求写出可核对代码事实＋程序核对＋不符时追问”的复核做法，5次运行都留住了全部真问题、去掉了全部误报。
- 这一做法可以作为流程中“大模型复核规则标记”这一步的当前做法。
- 下一步需要：
  - 在更多独立样本上验证；
  - 让模型更稳定地写出声明，例如把声明设为必填；
  - 扩展可核对的事实类型。
