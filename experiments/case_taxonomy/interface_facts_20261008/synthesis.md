# 格式载体与实际使用的有界开发结果

日期：2026-10-08。完成 10/3 待办中“四个已读接口的格式载体与真实使用”有限开发。这次补的是自动事实与检查建议的依据，不是新的全量筛选，也不是独立未知缺陷发现。

## 本轮改变

新增 `interface_fact_extractor.py`，接收预先指定的同版源文件、目标函数和成员，按受支持的简单源码形状定位事实。`run_development.py` 从已封存 manifest 读取原字节，核对 SHA-256 与 Git blob，分别处理四接口的父版和修复版。分类函数不接收父/修复标签或补丁内容；目标的选择仍来自已读材料，不能称自动发现目标。

输出分为五层：

1. **格式载体**：字段注解、API 第几个格式参数、本地 helper 实现以及另列的人工格式依据。`u64` 只证明声明类型，不证明硬件数据是主机序。
2. **具体操作**：掩码读、零判断、指定字段初始化、API 输出缓冲区、位域读，以及固定标量的 sizeof 类型/大小引用。局部正常不认证整个条件、函数或接口。
3. **可见值域**：限定 static 函数在同一保存文件中的直接引用，以及唯一简单整数宏。参数额外引用/改写、地址逃逸、条件预处理和歧义均拒判；这里仍不是实际运行输入或可达性证明。
4. **模式和适用性**：硬件交换标志的源码引用可以定位，实际 ring flags 继续未知。filecheck 门槛、固件 handle/DT/Kconfig、输入长度及 descriptor 来源等仍归属旧人工审阅；程序记录其来源和剩余未知，不把引文匹配变成语义认证。
5. **有条件检查建议**：指出在哪里核对格式/值域/消费者，以及哪些缺失条件会阻止升级为错误判断。工具不自动修改源码，也不部署内核断言。

## 解析审阅与保留下来的失败

首轮开发遗漏多行 mask 与 SMB 的真正声明路径，原输出保存在 `development_initial_results.json`。第一次修正回放保存在 `development_before_audit_results.json`。独立审阅又发现括号化参数改写、opaque/数组/多声明符阴影、源位宽及已编码值二次转换、API selector 遮蔽、局部宏覆盖、helper 后续覆盖与 GNU 非求值上下文等边界；对不支持的形状收紧为不足，具体探针和早期报告原样保留在 `audit_source_shape/`。

加固后的第一次根验收还发现：多声明符拒判把 switch 的 case 分支调用误当声明。该轮输出与收据保存在 `development_case_guard/`，随后修正控制关键字边界并加入正常对照。最终 `run_checks.py` 的 47 项边界测试通过，八修订回放成功；代码执行前后哈希一致。`verify_stage.py` 核对源码、逐行引用、原审阅卡、最终执行代码及事先审阅的有限验收条件。它检验保存材料的一致性，不是语义正确率。

最终结果核对还将接口计数字段改为 `development_interfaces`，避免把四个已读接口误称未知独立样本；仅计数命名改变的上轮输出保存在 `development_schema_label/`。分类工具未因此改变，最后根目录输出与执行收据已重新保存。独立语法审阅对同 32 个合成输入复核，最终三个探针脚本均退出 0，执行前后提取器哈希一致；初轮及中间审阅原样保留。该 32 项仍是语法/语义边界探针，不是新增源码案例。

## 共性机制和系统层落点

四类 Pattern 保留为交叉分析维度。本轮主要增强表示类：**应检查具体值如何在格式边界被解释，而不是只搜索是否有端序转换。**接口的格式可以由字段类型、API 参数或外部消费者/硬件模式承载；未求值引用不消费字段值，零值域也可能使表示差异不产生当次错误。

系统层的候选方向仍是保留表示类型、集中访问/序列化，并在真实消费边界启用有条件检查。启用需要格式权威、来源值域和路径条件；拒判/未执行与正常分别记录。老师的两个问题因此有了更多可执行的事实提取，但复杂控制流、跨过程值域、外部规范和实际配置仍需审阅，尚不能称通用自动检测已完成。
