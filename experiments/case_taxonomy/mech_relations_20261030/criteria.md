# 方向1：公共代码明写关系的跨架构核算——第一轮（挖掘计数＋取值试点）（判据，实现前写定）

## 背景与机制

研究目标（2026-10-30确认）：从已确认的跨架构缺陷案例中提炼共性机制，并验证这些机制能否指导自动检测，当前以RISC-V为重点。

本方向对应的机制是**数值关系**：公共代码假定某些由架构提供的常量之间满足某种数值关系，某个架构或配置却不满足。已确认的案例包括：

- **shmem**：大块内存的阶数不能超过页缓存上限，只有arm64在64KB页配置下不满足（13＞11）；
- **Btrfs**：页大小与扇区大小的关系；
- **SPARC**：CPU数量与位宽的关系。

这几个案例里的关系，当初都是人工整理出来的。本方向换一个要求来源：**公共代码自己已经把很多这样的关系写成了检查**，例如`BUILD_BUG_ON(A > B)`、`static_assert(...)`、`WARN_ON(x >= LIMIT)`。这些要求不需要推导，直接读出来即可。读出后交给已经验证可靠的编译期事实层，在不同架构和配置下计算真实取值。

本轮只回答两个可行性问题：

1. 这样的明写关系有多少？
2. 用取值探针能否在几种架构配置下把它们算出来？

## 第一部分：挖掘与计数（零成本，终点版本`df2908090cda`）

### 检查点的范围

在`arch/`、`tools/`、`Documentation/`、`samples/`、`scripts/`以外的`.c`和`.h`文件中，找出以下检查的调用：

- `BUILD_BUG_ON`、`BUILD_BUG_ON_MSG`、`static_assert`、`_Static_assert`；
- `WARN_ON`、`WARN_ON_ONCE`、`WARN`、`WARN_ONCE`；
- `BUG_ON`、`VM_BUG_ON`、`VM_WARN_ON`、`VM_WARN_ON_ONCE`。

取出括号中的第一个参数，即被检查的条件，按括号配对提取，允许跨行。

### 分类

| 名称 | 含义 |
| --- | --- |
| 含比较 | 条件中出现`<`、`>`、`<=`、`>=`、`==`、`!=`之一 |
| 纯常量 | 条件中除数字、运算符外，只有全大写的宏名，以及`sizeof`、`offsetof`、`sizeof_field`、`__alignof__`、`ARRAY_SIZE`、`BIT`、`BIT_ULL`、`GENMASK`、`ilog2`、`order_base_2`、`is_power_of_2`；这些函数式写法括号内的内容不检查 |
| 与架构有关 | 条件中至少有一个宏名在某个`arch/<架构>/include/`中有`#define`，或者条件中含有`sizeof`、`offsetof`、`sizeof_field`、`__alignof__`（结构体布局因架构而异） |
| **候选关系** | 同时满足“含比较”“纯常量”“与架构有关” |

### 报告

- 检查点总数、各分类的数量，按检查类型拆分；
- 候选关系所在的文件数，以及`.c`与`.h`的分布。

## 第二部分：取值试点

### 配置

| 架构 | 配置 |
| --- | --- |
| x86_64 | `x86_64_defconfig` |
| arm64 | `defconfig` |
| arm64（64KB页） | `defconfig`，加`CONFIG_ARM64_64K_PAGES=y` |
| riscv | `defconfig` |
| s390 | `defconfig` |

### 样本与方法

- 从候选关系中只取位于`.c`文件里的，因为取值探针需要一个能编译的编译单元。用`random.Random(20261030)`抽30个检查点。
- 用`linux_bug_analyze.kernel_facts collect`在该文件的编译单元中求值。每个检查点求三个表达式：
  - 整个条件的值；
  - 比较运算符左边的值；
  - 比较运算符右边的值。

  比较运算符取顶层第一个；条件中没有顶层比较的，只求整个条件。
- 每个“检查点×配置”的结果记为以下之一：
  - 算出值；
  - 该文件在此配置下不参与编译（Kbuild未选中）；
  - 编译失败；
  - 探针失败（例如表达式依赖函数内的局部定义）。

### 报告

- **取值成功率**：算出值的“检查点×配置”数，除以该文件参与编译的“检查点×配置”数。
- 在各配置之间取值不同的检查点数。
- **检查被触发的情况**：
  - `BUILD_BUG_ON`、`WARN*`、`BUG*`类的条件取值为真；
  - `static_assert`类的条件取值为假。

  前者按理会导致编译失败，正常情况下不应出现。
- 对含比较的检查点，两边的差值，即余量，在各配置下的大小，特别关注riscv。

## 事先写定的决策规则

- **候选关系≥50个，且试点取值成功率≥60%**：本方向可行。下一轮登记完整核算，覆盖：
  - 全部候选关系，其中头文件里的关系借用包含它的`.c`文件求值；
  - 更多RISC-V配置，例如32位、不同的虚拟地址位数；
  - 余量分析与历史回溯检验。
- **候选关系<50个，或取值成功率<30%**：明写关系这个来源太薄，或者取值手段不适用。转而考虑隐含关系，例如数组下标、移位量和架构常量之间的关系。
- **介于两者之间**：先分析失败原因，再决定。

## 不做的事

- 不调用模型。
- 不把任何取值结果直接当作缺陷。检查被触发、或者余量很小，都只记为候选，需人工核实，也不对外报告。
