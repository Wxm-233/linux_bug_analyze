# 用修复策略为新疑点写出修复（演示）

## 这一轮要做什么

上一轮（`fix_strategy_20261104/`）从135条历史修复中，为8类机制归纳出修复策略。本轮把这些策略用到此前记录的8个疑点上，演示“按机制定修法”的过程：
1. 确定疑点所属的机制；
2. 按该机制的策略找到对应物；
3. 照对应物写出修复；
4. 用程序检查修复是否完整。

这是演示，不是对策略的独立验证：疑点都是我此前分析过的。补丁只记录在本目录，不向上游提交，也不对外报告。

**编译**：
- 用交叉编译器编了RISC-V的6个、MIPS的2个目标文件，打补丁前后都没有错误或警告；
- RISC-V的配置开启了KVM、KEXEC_FILE、HOTPLUG_CPU、HUGETLBFS、SVNAPOT；
- MIPS配置中KVM没有被选上，`vz.o`是按目标单独编译的。

### D7：照搬参照架构的修复会引入新错误

LoongArch的修复是把`jump_label_init()`提前到`parse_early_param()`之前。照搬到MIPS（在`arch_mem_init`中提前调用），补丁能应用、能编译，但读代码发现**这样启动很可能崩溃**：
- 在MIPS上，`jump_label_init()`要改写代码：`arch_jump_label_transform_static`就是`arch_jump_label_transform`；改写之后要调用`flush_icache_range()`刷新指令缓存；
- `flush_icache_range`是一个函数指针，要等`setup_arch`中更后面的`cpu_cache_init()`才设置好；
- 所以提前调用`jump_label_init()`时，这个指针还是空的。

也就是说，修复所依赖的前提“改写代码时缓存操作已经可用”，在LoongArch上成立，在MIPS上不成立。要修好MIPS，需要另作设计，例如先初始化缓存，或者推迟改写静态开关的那些早期参数。本轮没有给出可用的修复，`D7.patch`只作为反例保留。

**这个疑点本身仍然成立**（按代码推断，未运行验证）：
- 静态开关在`jump_label_init()`之前被打开时，内核会报警告；
- 而且之后`jump_label_init()`只把应为空操作的位置改写为空操作，已打开的开关对应的位置不会被改写，所以`threadirqs`可能不起作用。

## 看出的几点（只作描述）

- **策略能直接指向修法。** 8个疑点都能按机制找到对应物，写出的补丁都很小（D4最大，新增约40行）。其中4个修法在本架构内就有现成的写法：
  - D3：辅助函数已经存在；
  - D4：按范围遍历的写法已经存在；
  - D5、D8：同一文件中已有同类防护。
- **“覆盖同一文件的同类位置”这一条起了作用。** 用检测规则复查，发现MIPS的读取处同样缺防护。只修原来记录的那一处，就会重演PMU修复“漏一处”的情况。
- **照搬之前，要检查参照做法的前提在目标架构上是否成立。** D7能应用、能编译，但前提不成立。这类问题编译发现不了，要按机制列出前提，到目标架构上逐条核对。这与发现缺陷用的是同一套条件。
- **能证明修复有效的，只有D1、D2的运行结果。** 其余补丁只做了应用、编译和规则复查。

## 局限

- 演示所用的疑点都是我此前分析过的，不能说明策略在新问题上的效果。
- 只有D1、D2有运行验证，而且是此前用同样做法的对照补丁做的；其余补丁没有运行。
- LoongArch补丁没有编译；MIPS的KVM文件是在未开启KVM的配置下单独编译的。
- 临时工作树和编译目录已删除；补丁提交留在内核仓库中，没有引用，之后会被git清理。

## 事后更正（GPT复核之后）

D5所说“剩下5处标记的下标来自配置时已校验的保存值，为误报”是错的。

`kvm_riscv_vcpu_pmu_ctr_cfg_match`走`SKIP_MATCH`时不检查计数器类型，客体可以把非固件事件号存进固件类型的计数器。之后启动、停止、读取时的`fevent_code`就是客体可控的。所以这几处同样需要`array_index_nospec`，D5只修了1处，**没有覆盖全**。这正好又是“漏一处”的例子。

同一路径上，读计数器高位时客体还可以触发宿主的`WARN_ONCE`，已记为新疑点。
