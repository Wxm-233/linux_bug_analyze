## 结论

- **7 个变异检出 6 个，达到参考线（≥5）。** 6 个都由事先预期的那一项检查报出，3 次运行全中。
- **没有误报。** 15 种“变异内核 × 运行方式”中，除了预期的那一项，其余检查全部通过。
- **没检出的 M7，是因为系统坏得太厉害，检查跑不起来。** riscv 用户地址空间的范围刷新完全不做时，fork 的写时复制失效，每个检查的子进程都被 SIGABRT 终止（glibc 检测到堆被破坏）。按判据算运行无效、不算检出。这说明性质检查本身依赖“进程能正常 fork 运行”，系统级的严重损坏要靠别的信号发现，比如运行完整性、进程崩溃。
- **arm64 的 M3 印证了“横向差异只用来定向”。** 变异让 arm64 在没有 MTE 时谎称“已经清零”。结果只有不开 MTE 时 Z3 报错，开 MTE 时不报，和 X1 是同一类依赖错误。

## 这说明了什么，还有什么没说明

- **说明了**：
  - R1 的 Z3、Z4、Z7 和 R2 的 T3，对本模板对应路径上“删一处清零”“少刷远程 CPU”这类缺陷能稳定检出，而且三个架构通用，不误报。
  - 再加上 `proprules_20261114` 的 X1 阳性对照，Z3 已经有两个独立的阳性例子：真实缺陷 X1，以及注入的 arm64 M3。
- **没说明的**：
  - 变异是人造的，而且是我看着模板选的注入点，每个变异都正好落在某个模板走的路径上。这只说明“路径对上了就能查出来”，不说明真实缺陷落在模板路径上的比例。
  - T1、T2（本 CPU 上的失效）这次没有得到有效检验：本来指望 M7 来检验它们，M7 却把系统弄坏了。
  - R3 没有变异，原因是 QEMU 的指令缓存永远一致（判据已写明）。
  - Z1、Z2、Z5、Z6、Z8、Z9 这次没有对应的变异。

## 下一步建议（还没做）

1. 补一个“只影响本 CPU 刷新、不破坏 fork”的变异，比如只在 `mprotect` 路径（`change_protection` 的 `flush_tlb_range`）不刷，用来检验 T1、T2。再给 Z1、Z2、Z5 等补变异。
2. 把规则检查接回整体流程：静态（纵向信号或其他检查）给出“资源 + 性质 + 位置”，按效果类别选规则，分流到动态。规则检查当作动态阶段的判错方式，替代或补充原来的“比较返回值”。
3. 把“运行完整性”（子进程异常退出、内核警告）也当作一种判错信号，用来覆盖 M7 这类系统级损坏。
