## 一、要回答的问题

1. 调用上下文检查能不能像前两类检查一样，作为静态分析的一步（流程第 6 步），产出“该去触发哪些入口”的提示？
2. 用这些提示造出的用例，在打开内核自检断言的调试内核上，能不能检出开发集里的调用上下文类缺陷：修复前的目标架构内核报警、修复后不报、参照架构不报？
3. 噪声有多大：参照架构和修复后的内核上会不会有调用上下文类的告警？

## 二、可行性检查得出的前提（写判据前已做，见 `harness/trap_probe.c`、`README.md` 第一节）

- 开发集 26 条调用上下文类样本里，补丁说明表明能由用户程序触发、调试断言能抓到的只有 A158（用户态非对齐访问）和 A175（用户态 `ebreak`/`unimp`，需 PREEMPT_RT）。其余发生在启动、kexec、KVM、插桩、CPU 热插拔、调试分配器等处。
- 在本机 QEMU（OpenSBI 1.3）上，用户态非对齐访问不进入内核（对齐错误计数为 0，`PR_UNALIGN_SIGBUS` 也不触发）。**A158 在本环境不可复现**，记为环境限制，不构建。
- 用户态断点、非法指令在三个架构上都进入内核（子进程分别收到 SIGTRAP、SIGILL）。
- 所以本轮唯一的动态样本是 **A175**（修复 `969f028bf2c4`，父提交 `e3f16d63d54e`）。结论只能是“这条路走得通/走不通”，不能当作检出率。

2. **用户态入口**：
   - 异常入口：标记的调用者或来源链中出现以下处理函数之一，就归到对应的异常种类：`do_trap_break` → 断点；`do_trap_insn_illegal` → 非法指令；`do_trap_load_misaligned` / `do_trap_store_misaligned` → 非对齐读/写；`do_trap_load_fault` / `do_trap_store_fault` / `do_trap_insn_fault` → 访问错误；`do_page_fault` → 缺页。

3. **产出**：`hints_ctx.json`：{异常种类: 标记数及前 5 条例子}，{系统调用: 得分及例子}。

## 六、判定（写死）

- **调用上下文告警**：告警正文含 `sleeping function called from invalid context`、`BUG: scheduling while atomic`、`inconsistent lock state`、`possible circular locking dependency`、`suspicious RCU usage`、`Invalid wait context`、`BUG: Invalid wait context` 之一。
- **与众不同**：某告警签名（正文首行去掉地址、进程号、时间后）在被检查内核的 3 次运行中至少 2 次出现，并且在任一参照架构内核的任何一次运行中都没有出现。
- **检出 A175**：修复前的 riscv 内核在异常用例上出现与众不同的调用上下文告警，修复后的内核上同一签名没有出现；再人工核对告警的调用栈，确认经过修复改动的处理函数（`do_trap_break`、`do_trap_insn_illegal` 或同一宏生成的处理函数）。
- 同时报告：每个内核上全部调用上下文告警（启动阶段、异常用例、系统调用用例分开）；静态提示的规模；用时。

## 七、事先写下的预期（不是通过条件）

- 静态部分应当把断点、非法指令列为有标记的异常种类（`checks_v1` 在 A175 修复前、修复后都有 `handle_break → force_sig_fault` 一类标记，因为它不区分 `user_mode(regs)` 分支）。所以静态提示在修复后也会存在，静态部分本身分不出修复前后，这要靠动态判定。
- 如果 PREEMPT_RT 调试内核在启动阶段就有大量告警，判定会受干扰，如实报告。
