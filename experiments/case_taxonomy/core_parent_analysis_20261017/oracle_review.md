## C：启动期注解整理，不构成所求违约或合格正常对照

`repair_C.txt:7–9` 的动机是给两个启动期函数添加 `__init`，说明仅为“No point in keeping them around”。补丁把 x86 钩子注释从 runtime 改为 boottime，并给公共弱实现、x86 实现及 `bringup_nonboot_cpus` 加同一注解（23–59）。没有改参数、分支、准备效果或消费内容，也没有报告某架构发生错误。

父版可见的公共用途是真实的：`kernel/smp.c:897–929` 的启动参数钩子，以及943–963经 `bringup_nonboot_cpus` 启动其他 CPU；`kernel/cpu.c:1505–1515` 在数量和 present/online 条件下调用 `cpu_up`。但这不证明存在跨架构失配。`__init` 宏、最终节布局和 init 内存回收并未在本包闭合；不能反过来凭修复注解声称已验证全部调用者都只在启动期。

**资格裁定**：C 是注解/驻留范围整理的研究范围对照，本轮不计已修复的跨架构缺陷；也不能仅因补丁没有行为修改，就计为“同用途且契约已证明满足”的真正正常对照。没有有证据的跨架构 A/B 暴露链、首次内容读取前的准备要求或错误传播结果。此前跳过付费分析的资格不足决定不变。

## D：空间范围与层级保留契约，具有防护意图，未证实当前跨架构逃逸

### 修复改变什么，哪些要求来自父版

`repair_D.txt:9–29` 说明：当 cluster 信息被填充、`CONFIG_SCHED_CLUSTER` 启用时，CLS 可进入调度层次。补丁在公共 `cpu_clustergroup_mask` 内检查 `cpu_coregroup_mask(cpu)` 是否为 `cluster_sibling` 的子集；若是则返回当前 CPU 的单元素掩码，否则返回原 cluster 掩码（44–54）。

这是**范围/层级语义约束**，不是把准备调用移到首次读取前的时间顺序修复。补丁作者提出“CLS 不应覆盖等于或大于 MC 的范围”，并希望相同范围时保留既有 MC、移除 CLS。必须区分两级依据：

1. 父版公共消费者已有的较弱要求：`kernel/sched/topology.c:2188–2198` 要求经过 `cpu_map` 求交后的子 domain span 包含于父 span；2211–2241要求非重叠同层掩码相等或不交。这些可在不看修复时提出。
2. 修复明确选择的更强策略：MC/CLS 范围相同时保留 MC 而不是 CLS，并在 provider 侧抑制该 CLS。这是修复说明中的设计选择，不能倒灌为父版已有的、对所有架构都明确生效的严格禁令。父版 `arch_topology.c:675–682` 的注释反而明确接受扩展 MC 后让调度器去掉 MC；因此仅据相等就把父版判断为违反其现存明文契约，会过推。

补丁谓词是 `MC ⊆ cluster`；它不是通用“cluster 必须严格包含于 MC”的完整集合证明，不单独处理部分重叠形态。后续检测必须保存真实集合关系、配置和选中层次，不能仅凭大小、名称或一句严格层次口号判错。

### 架构差异怎样可能进入公共代码

父版 ARM64 选择公共拓扑接口（`arch/arm64/Kconfig:123`、`arch/arm64/include/asm/topology.h:17`）。公共 MC 提供者结合 NUMA 节点、core/LLC 和 cluster 条件返回范围；CLS 返回 `cluster_sibling`（`drivers/base/arch_topology.c:660–690`）。x86 同用途 getter 分别返回 LLC/L2 掩码（`arch/x86/kernel/smpboot.c:688–696`），且可按 NUMA-in-package 或 hybrid 条件替换层次表（1480–1490）。两边接口相似但范围来源不同，这是值得检查的架构相关边界。

共同消费者在 `kernel/sched/topology.c:1654–1668` 的条件层次表引用这些接口，1540–1597读取掩码并与 `cpu_map` 求交，随后构建层次。因此潜在传播链可写成：**架构/固件形成的 cluster、LLC、NUMA 关系 → 架构选中的 getter/层次表 → 公共调度域范围、层级与标志选择**。这仍是带前提的源码机制，不等于已证明 ARM64 暴露而 x86 正常；x86 L2/LLC 关系、实际配置和最终表也未运行核对。

### 旧父版实际可达性的关键限制

修复说明开头明确说当前 DT 平台尚未填 `cluster_id`，全部默认 -1，后续正确赋值后才会生成多 CPU cluster（`repair_D.txt:9–14`）。父版 DT 解析499–650只写 package/core/thread，`reset_cpu_topology:744–756` 把 cluster ID 设为 -1；`update_siblings_masks:712–717` 仅在相同且非负 cluster ID 时增加 cluster 兄弟位，clear735–736先置自身位。这里变量/节点名中的 cluster 不能冒充 `cpu_topology[].cluster_id` 已赋值。

所以本包**不支持声称旧 DT 路径已经发生该多 CPU cluster 失配**。未展开的架构 ACPI 实现、实际固件 ID、特定硬件/NUMA 几何和运行配置仍未知。作者预期的拓扑后果可登记为历史修复意图/条件模型；本轮没有架构真实暴露、告警、吞吐变化或修复后运行结果。也不能由 NUMA 节点范围参与 getter 就声称作者在此提交报告了已复现的 NUMA 故障。

### 内核已做的检查与补救不是本项目新机制

父版已经有：子父 span 不包含时告警并取并集修补（2188–2198）；非 NUMA 同层部分重叠检查，并在构域循环中失败退出（2211–2241、2271–2272）；按 span、标志和组结构清除退化父层及单 CPU 底层（169–204、712–737）。相同范围不一定触发前两项错误，它可能通过退化规则选择保留哪一层；具体删层受标志、组结构和构域提前终止等条件影响，不能只看一次集合相等就宣称所有配置都走同一删层步骤。

本例对研究的价值是要求 N1 区分**已存在的结构健全性检查**与**接口希望保留的层级行为**，再比较不同架构提供者在相同公共用途下能否满足该条件。不能把现成调度器断言、补救或本补丁 provider 门禁归功为本项目新发现的系统机制。

**资格裁定**：D 是源码已接触的、公共 CPU 拓扑到公共调度的空间契约开发例，可支撑局部候选与策略边界研究；不纳入本轮“首次准备”机制的独立正例，也尚不足以计已确认完整跨架构逃逸。不能以材料不足标记为正常或模型漏检。
