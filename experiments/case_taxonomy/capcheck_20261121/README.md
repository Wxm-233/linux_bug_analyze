## 做了什么（`capcheck.py`，一个版本约 40 秒、3GB 内存）

全树约 3.3 万个 `.c` 文件、410 万个调用处，逐函数算出每个调用处被哪些能力判断保护：
- 正向 `if (P)` 分支；
- `if (!P)` 的 else 分支；
- 前面有 `if (!P) return`；
- 静态函数的所有调用方都被保护；
- 模块初始化函数已挡住整个文件。

能力判断按“身份”归一，例如 `boot_cpu_has(X)`、`static_cpu_has(X)` 都算能力 `X`。然后做两种推断：
- **A 操作多数保护**：同一个操作（被调函数，或被调函数加常量首参数，如 `wrmsrl(MSR_X)`）有 ≥ 3 处、且 ≥ 60% 的调用处被同一项能力保护，其余调用处是候选；
- **B 同类入口多数检查**：同一目录、同一种注册方式的入口有 ≥ 4 个，其中 ≥ 60% 一开头就检查能力，其余完全不查能力的入口是候选。

自测通过。在 `df2908090cda` 上：推断出“依赖关系”783 条，A 类候选 686 条，B 类 0 条。

## 诊断（`diag.py` → `diag_run1.json`）

对每个根因，找出修复版本里被新判断保护起来的调用，再看它们在父版本里的统计（n = 全树调用处，g = 其中被同一项能力保护的）：

| 情况 | 根因 | 例子 |
|---|---|---|
| 被保护的操作在父树里 g = 0 | 大多数 | M2 `writex_c0_entrylo0` n=2、g=0；M9 `fpsimd_preserve_current_state` n=5、g=0；M12 `irq_work_queue` n=43、g=0；M18 只是改了写入的位 |
| 有部分保护，但保护它的是另一项能力 | M5 | `wrmsrl(MSR_IA32_SPEC_CTRL)` 6 处里 3 处被 `MSR_SPEC_CTRL` 保护（50%），修复补上的却是 `SSBD`/`AMD_SSBD` |
| 同一类操作每处用不同的能力 | M11 | `kvm_cpu_cap_check_and_set(X)` 每处各查各的能力 |
| 修复补的是入口检查（属于 B 的范围） | M1、M13、M14、M17 | 加密模块、kvmclock、两个平台驱动的初始化 |
| 修复没有可对应的调用 | M3、M10、M16 | 改的是位掩码、断言条件或宏 |

**B 类为什么一条都没有**：234 个 ≥ 4 个入口的组里，“一开头就查能力”的比例最高只有 0.38（arch/x86 的 module_init，主要是加密模块），其次 0.33、0.28。60% 这个门槛在内核里达不到。M14、M17 所在的 drivers/platform 组比例不到 0.12；也就是说，大多数平台驱动本来就不查“是否在虚拟机里”，这两个修复是个别驱动出事后补的。

**为什么没用那一次修订**：按诊断，即使把 A 的门槛放到最低、把 B 降到 0.3，能有实质证据的也只有 M5 和 M1 两个左右，到不了 4 个。看着开发答案去调门槛，结论也不可信。所以直接结项。

## 这说明什么

1. **“从多数写法推断约定”这条路，对能力前置条件走不通**。规则 B（只认同文件）失败，这次把范围扩到全树、加上调用方和模块级保护，仍然 0/19。证据不是被漏看了，而是本来就不在代码里。
2. **需要外部的“接口约定”**，这正是 astra 诊断的那个缺口。对能力前置条件，可能的约定来源包括：
   - **x86 MSR 和 CPUID 特性的对应关系**：哪个 MSR 需要哪个特性。内核里 `arch/x86/kvm` 的 MSR 处理和 `cpufeatures.h` 有一部分，完整的在 Intel/AMD 手册里；
   - **指令和 ISA 扩展的对应关系**：riscv 的 `ALTERNATIVE` 和 `RISCV_ISA_EXT_*`、arm64 的 `cpucaps` 已经把一部分写成了机器可读的形式；
   - **“只能在物理机上用”的驱动**：可以从访问的 MSR 或固件接口间接推出。
   有了这类约定表，检查就变成“某操作需要能力 P，这条路径上没有 P 的判断”，不再依赖多数写法。
3. 这和兼容 ABI 那一族的结论相呼应：两族都卡在“约定从哪来”。区别是兼容 ABI 的约定能从代码里读出来，但样本太少；能力前置条件样本多，但约定不在代码里。
