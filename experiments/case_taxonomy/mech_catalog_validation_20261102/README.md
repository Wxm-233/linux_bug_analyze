# 共性机制的逐条核验

## 这一轮要回答什么

在等待复核实验期间，不调用模型，核验机制目录（M1–M9）：
1. **覆盖面**：真实的RISC-V修复有多少能归入这些机制，其中多少是真正的跨架构问题；
2. **M5能否像M2一样写成自动检查**，并找出跨架构共性。

## 第一部分：121个单函数修复的归类

| 类 | 个数 | 其中跨架构（C） | 例子 |
| --- | ---: | ---: | --- |
| M1 默认假设不适用 | 3 | 1 | 页表级数名按编译期级数写，RISC-V运行时可以降级 |
| M2 表项状态与信息来源 | 0 | 0 | 这批样本里没有大页修复 |
| M3 修改映射的步骤 | 1 | 1 | KVM脏页记录时，写保护要覆盖整个大页块 |
| M4 原子性与顺序 | 5 | 2 | BPF原子操作要完全有序；RV32分两次写64位CSR |
| M5 执行上下文 | 4 | 3 | 早期启动关中断时取了mutex；用户态陷入处理中访问用户内存要先开中断 |
| M6 生命周期与出错路径 | 19 | 2 | 泄漏、释放后使用、状态未初始化；卸载模块要恢复线性映射权限 |
| M7 边界、宽度、对齐 | 20 | 3 | 差一、整数溢出、移位越界、RV32地址 |
| M8 公共接口变化未跟上 | 5 | 5 | 公共代码新增`VM_FAULT_SIGSEGV`；vfio改变`vm_pgoff`含义；`sparse_init`后移；crashkernel低端区间；IMA产生空缓冲区 |
| M9 特性与配置条件 | 9 | 2 | 没有Supm扩展；替代补丁生效前就做扩展检查 |
| X1 RISC-V自身逻辑 | 40 | 6 | SBI返回码、AIA寄存器语义、指令解码 |
| X2 其他 | 15 | 0 | 注解、缩进、日志级别 |

- **覆盖率**：M1–M9合计66条，占54.5%；去掉X2后占62.3%。按参考线，记为“目录覆盖较好”。
- **但真正跨架构的只有25条，占21%。** 大量M6、M7是普通的编码错误（泄漏、越界），只是恰好发生在RISC-V代码里，没有其他架构共同承担的对应约定。所以“能归入目录”不等于“是跨架构缺陷”。
- **M8全部是跨架构的**（5/5），而且多数提交说明里直接写了“arm64已经这样做”。这类问题最符合“一个架构先改、另一个架构滞后”的模式。
- **目录之外还有6条跨架构问题**，可以归纳为一种新的机制：**公共约定由每个架构各自实现，RISC-V的实现与其他架构不一致**。例如：
  - 系统调用号为-1时返回`-ENOSYS`；
  - BPF trampoline的运行统计；
  - KVM脏页记录时强制使用页粒度；
  - `KVM_SET_GUEST_DEBUG`的语义；
  - 创建perf计数器时先禁用；
  - 信号返回时恢复向量状态的顺序。

  它和M8的区别是：公共接口本身没有改变。建议在目录中补为M10。
- **证据是否足够**（参考线：每类至少5条）：M4、M6、M7、M8、M9达到；M1、M3、M5不到。M2、M3在这批样本里少，是因为样本按“只改一个函数”抽取，又不含大页代码；它们在此前的大页实验中有专门证据。

**说明**：归类由研究者一人完成，理由逐条留在`labels.py`中，便于复核。

## 第二部分：M5的自动检查

在终点版本所有架构中含关中断调用的405个`.c`文件中，标出5条：

| 架构 | 函数 | 关中断后调用 | 归类 |
| --- | --- | --- | --- |
| RISC-V | `machine_shutdown` | `smp_shutdown_nonboot_cpus` | (a) 开发样例，已运行确认 |
| arm | `machine_crash_shutdown` | 经`crash_smp_send_stop`调用`smp_call_function_single_async` | (b) 异步调用不等待；崩溃路径 |
| LoongArch | `machine_crash_shutdown` | 经`crash_smp_send_stop`调用`smp_call_function` | (b) 崩溃路径的有意写法 |
| MIPS | `default_machine_crash_shutdown` | 经`crash_kexec_prepare_cpus`调用`smp_call_function` | (b) 同上 |
| powerpc | `oops_begin` | 经`pmac_backlight_unblank`调用`mutex_lock` | (c) 关中断的oops路径中取互斥锁，只在老式PowerMac背光配置下编译；oops期间检查会被跳过 |

- **E1**：RISC-V `machine_shutdown`被标出。
- **E2**：标记总数5条，噪声很小。
- **E3**：
  - (a)：1条（开发样例），新疑似问题0条；
  - (b)：3条，都是崩溃路径；
  - (c)：1条（powerpc，只记录，不对外报告）。
- **E4 跨架构共性**：`machine_shutdown`中调用`smp_shutdown_nonboot_cpus`的只有arm、arm64和RISC-V三个架构，**只有RISC-V先关中断**。崩溃关机函数`machine_crash_shutdown`在arm、arm64、LoongArch上都关中断，这是崩溃路径的共同做法。

**结论**：M5能写成噪声很小的自动检查。按“同名函数在其他架构上的做法”对照，能把RISC-V的偏离和各架构的共同做法区分开。不过开发样例之外没有找到新问题，所以这只说明“能表达、噪声小”，不能说明它找得到新bug。

## 对机制目录的修订建议（记录，未改动正在使用的`catalog.md`）

1. **新增M10**：公共约定由各架构各自实现，RISC-V的实现与其他架构不一致，而公共接口本身没有改变。
2. **把M6、M7标注为“通用缺陷类”**：它们覆盖面大，但多数与跨架构无关。在研究“跨架构机制”时，应分开统计。
3. **M8是最典型的跨架构机制**：提交说明里常有“arm64已这样做”。可以据此做一个自动提醒：arm64合入了某类修复后，检查RISC-V是否需要同样修改。此前“跟随arm64”的试验中，按名字匹配效果不好，需要改为按机制匹配。

正在运行的复核实验仍使用原`catalog.md`，以保证与上一轮可比。
