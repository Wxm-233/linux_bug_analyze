# 剩余疑点的核查（读代码，未运行）

用户要求运行验证剩余疑点。研究者先逐条核对了触发路径，以判断哪些值得运行、怎样运行才有意义。以下全部是**读代码得到的结论**。sh那次的教训说明，读代码可能漏看条件，所以每条都附上了依据，便于复核。

| 疑点 | 来源 | 结论 | 依据 |
| --- | --- | --- | --- |
| x86 `sgx_vepc_fault`在只持VMA锁时调用`mmap_read_unlock` | 模型判定试点（RISC-V案例组） | **排除** | 终点版本`mm/memory.c`中，`do_read_fault`、`do_cow_fault`、`do_shared_fault`在调用`->fault`之前都先调用`vmf_can_call_fault()`。只要VMA的操作表没有`map_pages`，并且当前持有VMA锁，它就直接`vma_end_read()`并返回`VM_FAULT_RETRY`，不会调用`->fault`。sgx vepc的`sgx_vepc_vm_ops`只有`.fault`，所以`sgx_vepc_fault`不会在只持VMA锁时被调用 |
| RISC-V `pud_free_pmd_page`把每个非空PMD表项都当页表页释放 | 页表遍历家族 | **排除** | 它只在`vmap_try_huge_pud`中被调用，前提是PUD已指向PMD表。解除vmalloc映射时，`vunmap_pmd_range`先用`pmd_clear_huge`清掉大页叶子，留下的非空PMD表项只可能指向页表页，按页表页释放是正确的。只有同一地址段还挂着活跃大页映射时才会出错，而vmalloc不会在使用中的地址上再建映射 |
| RISC-V `huge_ptep_clear_flush`从表项的值推出表项个数 | 方向4第二轮 | 大概率无害 | 三个调用点（写时复制、解除映射、迁移）传入的都是在内存中的表项 |
| RISC-V `kprobe_fault_handler`把单步状态下的任何缺页都当作单步引起 | 方法一第二版（单独记录） | **写法与arm64、x86修复前相同，但未找到可触发路径** | 见下 |
| RISC-V `show_pte()`无锁遍历页表 | 方向4第三轮、第四轮 | 仍是疑点，**无法运行验证** | 只在内核致命错误打印信息时执行；要触发，需同时让该进程的页表被并发释放，在模拟器中构造不现实；影响限于崩溃信息打印 |

## kprobe_fault_handler的详细分析

- **跨架构背景**：
  - arm64在2026-07-10（v7.2-rc5）以`879a6754`修复：单步窗口内，性能采样或追踪代码可能在调试异常路径上运行，并自己触发缺页；若一律当作单步缺页处理，就会把PC改成探针地址，破坏真正缺页的恢复上下文。复现条件是“perf加preemptirq追踪点加DWARF调用栈，同时在频繁执行的函数上装kprobe”。
  - 该修复说明写明，是照x86的`6381c24cd6d5`做的。
  - RISC-V当前的实现仍是修复前的写法，属于一个跨架构不一致。
- **RISC-V上为什么看起来触发不了**：
  1. RISC-V进入单步前，`kprobes_save_local_irqflag`清掉`SR_SPIE`，单步窗口里不会来中断，性能采样中断也进不来。
  2. 单步结束靠`ebreak`陷入内核，入口走`irqentry_nmi_enter`。其中的`trace_hardirqs_off_finish`只在中断原本开着时才会进入追踪逻辑，而且在NMI上下文中明确跳过`irq_disable`追踪点（`if (!in_nmi())`）。arm64复现中引发缺页的那段追踪代码，在RISC-V上不会在这个窗口里运行。
  3. RISC-V的模拟执行探针只模拟跳转类指令，不访问内存，不会缺页。
- **结论**：RISC-V存在与arm64、x86修复前相同的写法，但研究者没有找到能在RISC-V单步窗口里触发“非单步指令缺页”的路径。它更像一个**潜在的跨架构不一致**，而不是当前可触发的缺陷。这是研究目标中“同一约定在一个架构下被掩盖”的一个例子：在RISC-V上，它被单步窗口关中断和NMI入口的写法掩盖了。

## 可运行的验证

只有一项运行实验有意义：验证kprobe一条的“不可达”判断。

- 在QEMU的RISC-V上，启用kprobes与中断追踪；
- 用测试模块在一个需要单步执行的指令上装kprobe，并在中断追踪点上挂一个计数探针；
- 在负载下统计单步窗口内追踪代码是否运行过。

预计约一小时，是否进行由用户决定。
