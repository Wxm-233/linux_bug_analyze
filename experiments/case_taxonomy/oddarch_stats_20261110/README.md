## 为什么做

用户 2026-11-10 修正目标：不单找 riscv 的缺陷，而是尽可能找到所有跨架构缺陷。此前的比较只统计“riscv 与另外两个架构不同”。本轮不构建、不运行内核，只在 `diverse_dev_20261110` 已入库的运行记录上，补算 arm64、x86_64 各自与众不同的用例。

## 做法

`oddarch.py`：沿用旧比较脚本的解析、稳定性和 PMU 剔除规则；对每个三元组（riscv、arm64、x86_64 各一个内核）的每个用例，判为 三者相同 / 某一个与众不同 / 三者互不相同。回归：算出的“riscv 与众不同”与旧 `compare.json` 的 `odd_strong` 逐用例相同，不稳定集合和 PMU 探测结果也相同（脚本内断言，全部通过）。

## 当前版本的人工核对（`review_CUR.json`）

arm64 14 簇、x86_64 6 簇、三者互不相同 5 个用例，全部核对，**全部能解释，疑点 0**。原因分五种：

| 原因 | 涉及 | 说明 | 核对方式 |
| --- | --- | --- | --- |
| 用户地址空间大小不同 | arm64 7 簇（listmount 1、mincore 5、remap_file_pages 1） | arm64 默认配置是 52 位地址，2^52 及以上的地址被第一道检查拒绝；riscv、x86 的上限更高。其中 3 簇只是执行器“在指定地址预先映射一页”成败不同 | 读了 `.config`（`ARM64_VA_BITS=52`）和 `mm/mincore.c`、`fs/namespace.c`；x86 是否启用五级页表没有单独确认 |
| arm64 忽略地址最高字节 | arm64 1 簇（mlock2） | 地址第 63 位被置 1；arm64 的带标签地址约定会去掉最高字节，于是调用成功 | `.config`（`ARM64_TAGGED_ADDR_ABI=y`） |
| 同一个数字在各架构含义不同 | arm64 6 簇（openat 3、prctl 2、mprotect 1） | arm64 的 `O_DIRECT`/`O_DIRECTORY` 取值与通用定义互换；`prctl` 63、64 是 arm64 专有功能；保护位 0x10 是 arm64 专有的 | 读了三处头文件 |
| 环境或输出内容不同 | x86_64 6 簇 | `stat` 结构体在 x86 上布局不同（newfstatat）；输出内容随时间、设备号变化（clock_gettime、statx）；64 号进程只在 x86 上存在（getpriority、setpriority）；可读内存的长度不同（pwrite64） | 按观测值推断，没有逐字节确认 |
| 系统调用号的宽度 | 三者互不相同 5 个 | 调用号为 2^63：riscv 按 64 位判断越界返回 ENOSYS；arm64、x86 截成 32 位后执行 0 号系统调用，而 0 号在两者上是不同的调用 | 读了 `arch/riscv/kernel/traps.c`、`arch/arm64/kernel/syscall.c` |

## 说明什么

1. **数量级相同**：在没有已知缺陷的版本上，三个方向的噪声都是十簇上下（10、14、6），人工可以核对完。把比较改成“对每个架构都统计”，不会让结果多到看不过来。
2. **提示值对别的架构同样起作用**：arm64 的 24 个用例里 16 个来自“定向＋提示值”那一组，用的正是 2^52 附近的值。这个值本来就是静态分析从 arm64 的地址上限算出来的。也就是说现有流水线已经在顺带探测 arm64 的边界，只是此前没有统计。
3. **要面向所有架构，需要先处理两类固有差异**，否则它们会一直占着结果：
   - 各架构取值不同的接口常数（如 `O_DIRECT`）：生成器现在给三个架构传同一个数字，应当像系统调用号那样按架构换算；
   - 各架构专有的功能（如 arm64 的 `prctl` 63、64 和保护位）和地址空间大小：应当在比较时按“能力不同”单独归类，而不是算作与众不同。
4. **不能说明的**：用例是按 riscv 的边界和提示生成的，对 arm64、x86 没有定向；arm64、x86 上也没有已知缺陷的样本。所以本轮只说明噪声水平和可行性，不说明对这两个架构的检出能力。
