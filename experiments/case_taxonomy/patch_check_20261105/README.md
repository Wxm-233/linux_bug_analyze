# 对补丁调用检测：接口与第一次衔接

## 这一轮要回答什么

研究分为两部分：
- **第一部分**：在已有的迁移上检测缺陷。按共性机制写成程序规则，再由大模型复核。
- **第二部分**：上游有新补丁、RISC-V还没有对应补丁时，做迁移与修复。迁移完成后，调用第一部分的检测。

本轮做第二部分的前两项：
1. 把第一部分的检测做成可以对“基线版本＋一组补丁”调用的接口；
2. 用它检查此前的prog_pack迁移结果，同时检验它能否发现迁移中实际出现过的缺陷。

| 文件 | 说明 | SHA |
| --- | --- | --- |
| `criteria.md` | 判据，实现之前写定 | `6c661835…` |
| `input/prog_pack_series/` | 此前prog_pack迁移的最终8个补丁及索引，从原项目复制，此后不再依赖原项目路径 | 见`SHA256SUMS` |
| `patch_check.py` | 接口：应用补丁、运行规则、比较、统计覆盖 | 见`delivery_manifest.json` |

## 接口做了什么

`patch_check.py`分三个命令：
- `series`：在内核仓库的临时工作树中，从基线开始依次应用补丁（或挑入上游提交），每步提交一次，得到每一步的版本。工作树用完即删。
- `run`：在基线和每一步的版本上运行冻结的第4版规则（执行上下文CTX、推测执行越界R7、同一约定R10），然后比较：
  - 哪些函数被改了；
  - 哪些标记是基线没有的；
  - 哪些标记落在被改的函数或其调用链上。
- 覆盖情况：对最终版本中每个被改的函数，写出每条规则是否检查到它。这样“没有标记”就能区分两种情况：检查过、没问题；或者根本不在规则范围内。

## 结果

### 1. 接口能用

三组共12个版本全部完成了应用、检测和比较。每个版本约2.5–4分钟，其中同一约定规则R10占大部分时间。没有任何步骤需要人工处理。

### 2. 没有新标记

| | 被改的函数（最终版本） | 新标记 | 落在被改函数上的标记 |
| --- | ---: | ---: | ---: |
| P 每一步 | 3→18 | 0 | 0 |
| U 每一步 | 2→13 | 0 | 0 |
| Ufix | 2 | 0 | 0 |

基线原有的标记也一个没少：迁移既没有引入规则能看见的问题，也没有顺带修掉什么。所以按判据第五节，**不需要调用模型复核**。

### 3. 原因：被改的函数大多不在规则范围内

| | 被改的函数 | 至少一条规则检查到的 |
| --- | ---: | --- |
| P 最终版本 | 18 | **2**：`patch_insn_write`（CTX，第6步加了关抢占区域之后才进入范围）；`bpf_int_jit_compile`（R10） |
| U 最终版本 | 13 | **1**：`bpf_int_jit_compile`（R10） |
| Ufix 修复后 | 2 | 2（修复加了关抢占区域，两个函数因此进入CTX范围） |

- R7只看KVM、ptrace、信号等少数文件，BPF JIT和代码改写都不在内。
- CTX只看三类函数：自身含关中断、加锁或关抢占的函数，陷入入口和跨核回调，以及公共代码在原子上下文中调用的钩子。
- R10只看arm64、x86、LoongArch都实现、并且被公共代码调用的函数。

这些规则是为“在已有代码中找同类问题”设计的，对一个新功能的补丁，大部分改动都落在它们之外。

### 4. 已知缺陷一个都没发现

| 编号 | 缺陷 | 机制 | 发现了吗 | 为什么 |
| --- | --- | --- | --- | --- |
| K1 | 用fixmap改写代码时没有关抢占（P第2–5步、U都有；P第6步、上游`a370c2419e46`修正） | M5 执行上下文 | 否 | CTX查的是“原子上下文里调用了会睡眠的函数”。K1正好反过来：某个操作**必须**在不可迁移的上下文中做，却没有。现有规则没有这个方向 |
| K2 | 调用基线中不存在的接口 | 构建错误 | 不计 | 编译器就能发现 |
| K3 | RV32缺少共用的文本拷贝和失效接口（P第7步补上） | M10 同一约定 | 否 | 要比较同一架构下64位和32位两个变体是否都提供了公共代码需要的接口，R10只比较不同架构 |
| K4 | JIT只保存可写的构造地址，漏了可执行的运行地址（P第8步修正） | M10 同一约定 | 否 | 要知道“运行时计算用的地址必须取可执行映像”，需要对照arm64、x86 JIT的写法，现有规则没有 |

### 5. 规则之外看到的一点（人工观察，未验证）

模型系列第3步的`patch_text_set_nosync`先用`kzalloc(len, GFP_KERNEL)`申请与填充长度一样大的缓冲区，再整体写入。上游的做法（`cad539baa48f`）是按页用fixmap直接填充，不申请内存。
- 在这个基线上，`BPF_PROG_PACK_SIZE`在支持大页vmalloc时为`PMD_SIZE`（2MB）乘以节点数；
- 释放程序时，公共代码调用`bpf_arch_text_invalidate(hdr, hdr->size)`，长度最大接近一个pack；
- 所以可能要申请约2MB的连续内存。内存碎片多时会失败，公共代码会报`WARN_ONCE`，被释放的区域也不会填成非法指令。

这只影响此前的迁移结果，记录在这里，没有运行验证。它和K1一样，属于“照着参照做法时漏了参照的前提”：上游不申请内存，正是因为这条路径不应依赖大块分配。

## 看出的几点（只作描述）

- **衔接本身是通的**：第二部分的结果可以直接交给第一部分检查，不需要人工介入，一个版本几分钟。
- **但现有规则对迁移补丁几乎看不见**：18个被改的函数中只有2个在任何一条规则的范围内，4个已知缺陷一个都没发现。现有规则是从“已有代码中的同类问题”出发写的，而迁移补丁大多是新功能代码。
- **没发现的缺陷仍然落在已有的机制里**：K1是M5，K3、K4是M10。缺的是机制在“补丁场景”下的检查方向，而不是机制本身。具体有三个方向，本轮不写新规则，只作描述：
  1. **反向的执行上下文检查**：某些操作必须在不可迁移或关中断的上下文中做，例如fixmap、本核TLB刷新、per-CPU映射。检查它们的每个调用点，是否处在这样的区域里，或者由`stop_machine`调用。
  2. **同一架构不同变体的接口完整性**：公共代码需要的钩子，在RV64、RV32等配置下是否都有实现。
  3. **对照参照架构的补丁做逐项比对**：迁移的输入本来就有参照补丁，可以逐个比较参照补丁中每处改动在目标架构上有没有对应。K4这类问题，在x86的prog_pack补丁中都有对应的写法。
- **模型判断在补丁场景中更必要**：规则覆盖不到的改动，需要模型按机制条件逐项检查补丁本身，而不只是复核规则的标记。这需要调用模型，留到下一轮，先报调用量。

## 局限

- 只检查了一个迁移案例（prog_pack），而且是代码改写和BPF JIT这类规则本来就较少覆盖的领域。
- 覆盖情况中CTX的第三类（公共代码在原子上下文中调用的钩子）是按规则的写法重新计算的近似值。
- 第5节的观察没有运行验证。
- 临时工作树已删除，补丁提交留在内核仓库中，没有引用，之后会被git清理。

## 统计

模型调用0次；构建0次；规则运行12个版本加3个基线；新确认缺陷0；新疑点0。模型迁移结果中的一处人工观察记在第5节，因为只涉及本地的迁移结果，不计为内核的新疑点。
