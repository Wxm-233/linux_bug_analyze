# 方向4第四轮：RISC-V页表遍历家族深挖

## 这一轮要回答什么

在大页家族上，“以arm64为参照”效果很好：检查有没有覆盖该覆盖的钩子、比较实现步骤，都能在修复之前标出问题。第三轮发现它不能推广到所有家族，有效范围限于和arm64结构相似的家族。

页表遍历看起来就是这样一个家族：两者都是多级页表，公共代码用同一组辅助函数遍历。本轮按大页轮次的方法检验：

1. 读懂已确认的修复，归纳机制；
2. 按机制写检查，回溯检验；
3. 用在当前代码上，人工核对。

事先假设三类机制：

- **层级折叠**：RISC-V在运行时决定用3、4还是5级页表；
- **叶子与坏表项判断**；
- **读取与并发**。

## 结果

### 1. 35个已确认修复的归因

| 类别 | 个数 | 例子 |
| --- | ---: | --- |
| **层级折叠** | 3 | 内存热拔时，`remove_pud/p4d_mapping`在被折叠的层级上照常加索引，越界遍历；3级页表模式下`P4D_SHIFT`写错；ptdump按编译期级数给层级起名 |
| **叶子与坏表项判断** | 2 | `kernel_page_present()`、`vmalloc_fault()`逐级下行时没有先判断是不是大页叶子 |
| **读取与并发** | 2 | 解除映射与页表遍历竞争；调用`walk_page_range`前没有持mmap锁 |
| 公共约定改变 | 3 | 例如`for_each_mem_range`改为给出物理地址 |
| RISC-V自身逻辑错误 | 8 | 多为KASAN映射建立、直接映射权限 |
| 其他 | 17 | ptdump显示、缺页处理、kprobes黑名单、编译问题 |

三类机制合计7个，占20%。按文件筛选出的修复里，大量与“遍历”本身无关。

### 2. 回溯检验（7个机制案例）

只有`kernel_page_present`一例在修复之前被标出（检查B）。其余6例没有标出，原因各不相同：

| 案例 | 为什么没标出 |
| --- | --- |
| 层级折叠3例 | 这是RISC-V特有的机制，arm64长期是编译期固定级数，没有可对照的写法；`P4D_SHIFT`是宏，不在比较对象内 |
| `vmalloc_fault` | arm64没有这个函数 |
| 内存热拔的`remove_pud_mapping` | arm64对应的函数叫`unmap_hotplug_pud_range`，名字不同，同名比较对不上 |
| 加锁两例 | 修的是加锁约定，不在六项遍历步骤的特征里 |

此外，各父版本上的标记最多有32条，超过了事先定的20条。

### 3. 当前代码（终点版本）

检查A标出12条，检查B标出16条，共28条，研究者逐条核对：

| 归类 | 条数 | 说明 |
| --- | ---: | --- |
| (a) 疑似问题 | 2 | `show_pte`缺“无锁偏移”；`die_kernel_fault`那条由只展开一层带入，是同一问题。与第三轮事后发现的是同一条：RISC-V的`show_pte()`从指针重读上层表项、不关中断，arm64的`a77644d0`已经改掉 |
| (b) 有合理原因 | 23 | 多为arm64连续页优化或硬件勘误；也有RISC-V用原子操作、arm64需要读表项的情况；还有只展开一层造成的假标记 |
| (c) 判断不了 | 3 | `pud_free_pmd_page`：RISC-V对每个非空PMD表项都当作页表页释放，没有先确认它是表而不是大页叶子，arm64会先判断。另有终点版本新加的两个公共接口`ptep_try_set`和`ptep_modify_prot_transaction`，需细读后才能判断 |

疑似问题与判断不了的条目只记录，不对外报告。

## 结论（按事先标准）

| 标准 | 结果 | 是否满足 |
| --- | --- | --- |
| 机制成立：至少一半案例属于三类机制 | 7/35（20%） | 不满足 |
| 检查有指导作用：机制案例至少一半在修复前标出，且标记不超过20条 | 1/7；最多32条 | 不满足 |

- **“以arm64为参照”在页表遍历家族上不起作用。** 这个家族里最典型的机制是RISC-V运行时决定页表级数，而arm64长期没有对应的做法。两边对应的函数名字常常不同，有的函数arm64根本没有。
- 这与大页家族形成对照。大页上RISC-V的NAPOT与arm64的连续页一一对应，同名钩子、同名函数都在。“结构相似”需要具体到函数这一层，而不能只看“都是多级页表”。
- 本轮再次标出了`show_pte()`那条疑似问题，它来自两条独立的路线：第三轮的“跟随arm64修复”和本轮的“步骤比较”。

## 可能的下一步（未登记）

1. **针对“层级折叠”做RISC-V内部的一致性检查**，不参照arm64。RISC-V的遍历代码中，凡是直接用`base + pXd_index(addr)`计算下一级位置、却没有考虑`pgtable_l4_enabled`/`pgtable_l5_enabled`的地方，都与内存热拔那个修复同类。可以用程序把这类写法全部列出来人工核对。
2. 核实`show_pte()`疑似问题，以及`pud_free_pmd_page`，例如构造场景运行验证。
3. 回顾方向4的四轮结果，整理“以arm64为参照”的适用条件，作为论文中的一个机制结论：哪些家族有效、为什么。
