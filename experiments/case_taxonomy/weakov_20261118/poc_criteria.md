# PoC 阶段判据（在把任务派给 Codex 之前写下）

2026-11-18，Claude。用户：“你可以调用 codex 的 gpt6.2-sol-max 来生成”。

## 一、谁生成，给它什么

- 生成者：Codex，模型 gpt-6.2-sol，推理强度 max，新会话（`-New`），无沙箱（可进 WSL）。
- **给它的**：
  - 静态分析器对这条候选的输出：接口、架构、效果、三条缺失路径的行号和条件、公共调用点；
  - 有缺陷版本 `arch_unregister_cpu` 的源码，以及 `acpi_processor_post_eject`、`unregister_cpu` 的源码；
  - 环境说明：QEMU 8.2 的 virt 机型（aarch64）、UEFI 固件路径、iasl 路径、交叉编译器、内核配置要点（ACPI_TABLE_UPGRADE、ACPI_CONFIGFS 已开），以及“QEMU 8.2 的 arm virt 不支持 vCPU 热插拔”；
  - 有缺陷的内核镜像（变异 W1）。
- **不给它的**：修复提交和它的说明、修复版内核镜像、我想到的触发办法。提示里要求它不要查 git 历史。
- 允许它在有缺陷的镜像上自己试跑，最多 10 次启动。

## 二、我怎么判（固定下来，不随 Codex 的说法改）

拿 Codex 交付的 PoC，在两个镜像上各跑 3 次。两个镜像同一棵源码树、同一配置：
- 缺陷版：df2908090cda + 变异 W1（恢复修复前的三处提前返回）；
- 修复版：df2908090cda 原样。

**“触发”**：PoC 走到移除 CPU 的流程，移除完成后：
- (a) `/sys/devices/system/cpu/cpuN` 仍然存在，也就是 sysfs 设备没注销；或者
- (b) 再次添加同一个 CPU 时失败，表现为报错、卡住或内核告警。

**参考线**：缺陷版 3/3 次触发，修复版 0/3 次触发，并且修复版确实走到了移除流程（日志里能看到 CPU 被移除、目录消失）。缺陷版触发但修复版也“触发”，算 PoC 不区分，不算成功。

## 三、修正轮次

第一次交付不满足参考线时，我把运行日志发给同一个 Codex 会话，最多再修 2 次。总共最多 3 轮，每轮前后记录额度。
