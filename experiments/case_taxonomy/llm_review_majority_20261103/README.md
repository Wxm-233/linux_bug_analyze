## 做法

- **样本**：新样本18个、原样本41个，都用上一轮“加事实”的提示词，一字不改。
- **次数**：上一轮的那一次算第1次，本轮每个问题再问4次。236次调用全部完成，约68万token。
- **多数规则**（事先写定）：5次中至少3次判为“误报”才算去掉，否则保留。

## 逐条看错在哪里

**新样本**：
- `arch_cpu_idle`（真问题）：5次中3次判为误报，取多数后被去掉。每次的理由都是“已带`__cpuidle`标注”，但给出的代码中并没有这个标注。
- `memset_io`（标为误报）：5次都判为真问题。这一条的标签本来就有争议。
- `kvm_riscv_aia_aplic_inject`：5次中有1次判错、1次不确定，多数判对。

**原样本**：
- `machine_shutdown`：5次中4次判对。上一轮单次判错，确实是偶然的。
- `die()`在陷入处理中拿普通锁（真问题）：**5次全部判为误报**，理由都是“标出的是用户态分支，不会进入`die()`”。而上一轮不加事实时，这一条是判对的。说明背景事实在这一条上稳定地起了反作用，大概是事实2让模型去区分用户态和内核态分支，结果看错了。
- `arch_ftrace_update_code`（真问题）：5次全部判为误报。
- `memcpy_toio`（标为误报）：5次都判为真问题，与`memset_io`同类，有争议。
- `kvm_age_gfn`：5次中2次判为真问题，多数判为误报。上一轮核对时，第一标注人已认为它其实是真问题（新疑点），只是按判据仍以原标签计分。

## 事后分析（只作描述）

1. **模型的判断大体是稳定的。** 新样本5次判断中只有3%与多数不一致，原样本为5%。上一轮看到的“倒退”，一部分是偶然（`machine_shutdown`），另一部分是稳定的（`die()`那一条）。
2. **剩下的错误多是系统性的，取多数纠正不了。** 被判错的真问题，大多5次都错，例如`die()`、`arch_ftrace_update_code`，或者多数是错的，例如`arch_cpu_idle`。要纠正它们，需要：
   - 让程序核对模型引用的代码事实，例如“函数是否带某标注”；
   - 补上模型缺的知识；
   - 并检查事实清单是否会把模型带偏。
3. **取多数的作用是让结果更可预期。** 单次运行的保留率在75%到100%之间浮动，取多数后稳定在88%。原样本上，多数结果比第1次单次高（86%对79%）。
4. **有争议的标签影响结论。** `memset_io`、`memcpy_toio`模型每次都判为真问题，而第一标注人判为误报；`kvm_age_gfn`第一标注人已改判为真问题。等GPT复核结果回来后，结论可能会变：如果把`memset_io`算作真问题，新样本上的保留率会变为8/9=89%。

## 结论

- 按判据，**本轮未达到成功标准**：取多数后，新样本保留率仍为88%。
- 取多数让结果更稳定，在原样本上略有提高，但纠正不了系统性的错误。
- 模型复核在新样本上的表现稳定在“保留88%、去除90%、精确度87.5%”。剩下的问题需要靠**程序核对模型引用的代码事实**来解决，而不是多问几次。
