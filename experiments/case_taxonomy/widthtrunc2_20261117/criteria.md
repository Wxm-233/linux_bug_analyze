## 一、改什么（写死）

### 1. 按“这段代码实际在哪些位宽上编译”取位宽（降噪的主要手段）

一处候选如果属于下列任一种，就认为它**只在 64 位上编译**，不报：

- **架构**：文件在 `arch/X/` 下，而 X 只有 64 位。判定方法是读 `arch/X/Kconfig`：
  - `config 64BIT` 是不带条件的 `def_bool y`，算只有 64 位；
  - 没有 `config 64BIT`，算只有 32 位；
  - 其余算 32、64 位都有。
- **文件名**：文件名以 `_64.c` 结尾。
- **构建条件**：文件由 Makefile 的 `obj-$(CONFIG_X)`、`<模块>-$(CONFIG_X)` 引入（目录逐级向上也算），而 X 依赖 64 位。
- **预处理条件**：候选所在行处在 `#if`、`#ifdef` 的正向分支里，条件含 `CONFIG_X`（X 依赖 64 位）或 `BITS_PER_LONG == 64`；或者处在 `#ifndef CONFIG_64BIT`、`#if BITS_PER_LONG == 32` 这类块的 `#else` 分支里。

**“X 依赖 64 位”的判定**：
- 读全树的 Kconfig，初始集合是 `64BIT`、`X86_64`、`PPC64`、`SPARC64`；
- 某个符号的 `depends on`（包括外层 `if … endif` 带来的条件）里，用 `&&` 连接的某一项是集合里的符号（不带 `!`、不在 `||` 里），它就加入集合；
- 迭代到不再变化。

### 2. 掩码函数（C 形态）

`~` 后面是名字含 `mask` 的函数调用（例如 `~huge_page_mask(h)`），不报。这种写法取的是页内偏移，本来就不需要高位。

### 3. 修规则毛病（C 形态）

`&` 的左操作数如果是函数调用，按调用的返回类型判断，不再看调用的实参。

### 4. `>>` 的细化（A 形态）

第一版只要出现 `>>` 就不报。改为只在下列情况才认为“范围已经缩小”：
- 移位量是 ≥ 32 的字面常量；
- 移位量含 `PAGE_SHIFT`，并且目标类型是 `pgoff_t`（内核允许把文件偏移换算成页号）。

其他 `>>` 不再挡住报告。`&`、`%`、`/`、比较、`min`/`clamp` 等仍按第一版处理。

### 5. 扫描范围

在第一版的范围上，加入 `fs/` 下所有 `.h` 文件。
