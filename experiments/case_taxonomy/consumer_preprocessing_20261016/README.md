# N1.4b：真实配置下公共消费者的表达式与来源

2026-10-16。本轮补齐上一阶段无法从原始宏直接处理的消费者表达式，复用旧／修复×s390／x86四格已有 Kbuild 预处理。**仅限同一已读案例的开发取证**，没有新编译、内核启动或模型调用；没有独立检出或新增确认案例。

## 本轮解决什么

上一阶段只能核对部分函数的局部调用顺序。公共 `sched_core_lock` 含未展开的遍历宏，不能把原始片段当完整路径；`cpu_smt_mask` 又是通用接口，单看名字无法确认各架构实际读取的存储。此次从已绑定的完整 `core.i` 中提取真实展开区域，回答：**在所查配置下，共同消费者取得哪个掩码、后续在哪个表达式使用它？**

`protocol_pre.json` 在提取前固定四格、三个查找目标、无新增运行以及不能升级的结论。程序只提取区域、标识符坐标和 GCC 行映射；下文对接口连接的说明来自源码复核，不是程序自动证明的语义契约。

## 输入与产物身份

使用原 `s390_arch_contract_20261013/profiles/` 的非观测对象构建产物，**不是**随后 `runtime/` 下的带观测完整内核。两版分别为：

- 旧版 `88b604263f3d6eedae0b1c2c3bbd602d1e2e8775`。
- 修复版 `a052096bdd6809eeab809202726634d1ac975aa1`。

每格重新核对既有账本中的10份指定材料：结果、命令、Windows 配置／生成配置、两份摘录、WSL 实际 `.config`／生成配置、`kernel/sched/core.i`／`core.o`，共40份。不是对旧88份产物或全仓库重做封存。实际 SMP、SCHED_SMT、SCHED_CORE、HOTPLUG_CPU、SYSFS 均启用、NR_CPUS=4；s390 另启用 SCHED_TOPOLOGY。同架构旧／修复配置仅 LOCALVERSION 不同，跨架构配置不相同。

针对五个相关源码文件的两版引用，共10项，另从历史 Git 核对当前缓存源码一致；保留整文件指纹和有限行摘录。未核全源树。`.i` 与 `.o` 仍留 WSL 缓存，Windows 只保存所需原始区域及身份，避免复制大型产物。

## 提取和源码复核结果

| 位置 | 四格实际内容 | 本轮能确认的范围 |
| --- | --- | --- |
| 公共 `sched_core_lock`，`kernel/sched/core.c:240` | `cpu_smt_mask(cpu)` 结果赋给 `smt_mask`；保留 IRQ 保存；循环条件含 `cpumask_next(t, smt_mask)`；循环体用 `t` 对应的 runqueue 锁 | 取得指针与后续读取集合是不同位置；没有删掉宏展开后的循环、GNU 表达式或汇编 |
| 公共 getter，`include/linux/topology.h:203` | s390 返回 `&cpu_topology[cpu].thread_mask`；x86 返回包含 `cpu_sibling_map`、`__per_cpu_offset[cpu]` 的每 CPU 存储表达式 | 同一公共接口背后是不同架构存储。x86 汇编／指针表达式原样保留，不当作完整别名或内容证明 |
| 迭代助手，`include/linux/cpumask.h:209` | 四格均只有 `unsigned int ... cpumask_next(int n, const struct cpumask *srcp);` | 只取得外部声明，没有取得该翻译单元内的函数体，不能宣称其实现已分析 |
| 旧／修复同架构比较 | 以上三个区域原文逐字相同 | 与既有提供者修复位置相符，不说明两架构全部机器行为相同 |

s390 展开后的锁助手是 `__raw_spin_lock`，x86 是 `_raw_spin_lock`。两者名称不同，原文均保留，不能因为公共 C 相同就忽略这些差异。

合计 **8个完整函数定义＋4个外部声明**，来自四个已有配置单元；不是12个样例或12项缺陷。全部区域保留原始文本、UTF-8字节跨度／字符跨度、正文指纹、物理行号和 GCC 原文件行映射。预处理列号仅表示 `.i` 的列号，GCC 行标记没有给出原始 C 列号。

源码复核还核对了同版通用 getter 中的 `topology_sibling_cpumask`、架构头中的对应宏，以及 `for_each_cpu` 的不同条件分支。**GCC 把 getter 映射到通用 `topology.h`，不等于记录了宏定义的展开栈。** `source_references.json` 保存的是候选定义及局部上下文，不能把头文件出现或源文件中的某个定义，单独当作“该宏在本配置必然生效”的证明；实际展开结果在四格 `.i` 区域中另行保存。

## 对跨架构研究的意义与边界

本轮把原先“架构 getter 可能不同”的缺口收紧为有配置依据的表达式来源：公共锁消费者经相同接口访问，s390／x86 接口背后的存储不同。结合此前已完成的启动与准备证据，后续应核对的是**各自提供者能否在共同使用期限前，为传入的那个 CPU 提供满足要求的集合**。不是要求两个架构的内部布局或原始输出相同。

但本轮没有得到实际集合值，也没有证明准备生效。取得指针发生在后续循环读取前；不能把先前关中断前的采样升级为 `cpumask_next` 读取时的内容，更不能推出整个区间稳定。源码中的循环仍不属于上一阶段的有限路径子集，`control_flow_proved=false`、`runtime_content_proved=false`，完整契约继续 `insufficient`。资格守卫、跨函数写入效果、其他 writer、动态回调、精确消费和并发仍未闭合。

## 开发失败、修正与验证

首次按三个目标都应有函数定义查找，在旧 s390 的 `cpumask_next` 处停止。错误原样保留在 `first_attempt_error.json`。检查源码和实际编译片段后确认，当前配置选择外部声明；另一个条件分支虽有内联版本，**没有把它复制进来冒充当前实现**。随后仅对显式允许的此名字保存唯一外部声明，定义／声明分类分开，默认严格定义查找不变。这是事后明确的范围修订，不把首次失败改写成成功。

提取器测试还暴露了 Windows 文件名反斜杠转义问题，已修复；独立复核发现聚合返回类型前缀可能截掉、相同后缀可能混用源树，均已补对应处理和测试。执行器使用精确绝对源码路径，并拒绝将混合 token 来源归为单一头文件。循环、IRQ 与锁操作没有为解析方便而删除。

最终新增18项边界测试通过；上一阶段源码条件27项、最小协议28项回归共55项通过。独立方法角色只读抽查旧 s390 的三个区域、10项身份记录与汇总，未见阻断问题；没有独立重新读取全部 WSL 缓存，不能称专家金标准或全缓存审计。
