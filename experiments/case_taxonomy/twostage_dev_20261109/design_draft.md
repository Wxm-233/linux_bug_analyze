# 设计草稿：两阶段衔接开发轮（twostage_dev_20261109）

2026-11-09，Claude。这是**草稿**，交给 Codex 独立审查后定稿为 `criteria.md`（定稿时记 SHA）。定稿前没有任何测试运行。

## 背景（前几轮的结论）

- **静态阶段**：检查二（`checks2_xarch_20261109`）以“公共层使用、架构层提供”的边界函数为候选，与 x86/arm64 的同名实现对照，当前版本报出 253 个标记（`flags_current.json`）。人工核对 40 条，疑似真问题只有 1 条，24 条样本只命中 1 条。它不覆盖只以宏提供的边界（2113 个）。
- **动态阶段**：`difftest_known_20261109` 证明，只要测试从用户态触发了缺陷，跨架构多数比较就能稳定地看出来：5 条已知缺陷修复前全部检出，修复后消失，误报为 0。基于 sysfs 和 `.config` 的环境、能力自动剔除，与人工分类 8/8 一致。**但那一轮的测试是我照着修复说明写的。**
- 这 5 条缺陷是：A101（mmap 提示地址当上限，宏 `arch_get_mmap_end`）、A310（`syscall(-1)` 不设 -ENOSYS，入口函数 `do_trap_ecall_u`）、A171（`TASK_SIZE_MAX` 宏为 LONG_MAX，futex 接受高位别名地址）、A181（`__put_user_nocheck` 宏在非对齐时按值类型写，`put_cmsg` 的 `cmsg_len` 写错）、B467（riscv perf 驱动对不支持事件返回 EINVAL 而非 ENOENT）。

## 这一轮要回答什么

1. **桥接**：静态点位能否自动找到触达它的系统调用？
2. **生成**：不看修复说明，按“参数类型”机械生成测试，并用静态点位决定在哪些系统调用上加大力度。这样在 11 个 riscv 内核上能检出几条已知缺陷？当前版本冒出多少“与众不同”，其中多少像真问题？
3. **诊断**：每条没检出的缺陷，卡在哪一环：静态点位没指向它、桥接不到，还是生成不出触发它的参数？

## 流水线

### 1. 静态点位
- 检查二当前版本 253 个标记所在的 riscv 函数（`family` 名）。
- 诊断用的“理想点位”：5 条已知缺陷修复所改的函数。如果是宏或入口代码，记为“不可跟踪”。

### 2. 通用生成器（不看任何修复说明）
- **系统调用**：riscv/arm64 通用表与 x86_64 表的交集，共 326 个，去掉黑名单。黑名单是会影响全局、挂起或杀进程的调用：reboot、kill 系列、exit 系列、execve 系列、clone 系列、mount 系列、swapon/off、kexec、模块加载卸载、改时间、acct、quotactl、syslog、sethostname/setdomainname、ptrace、process_vm_writev、prlimit64、rt_sigsuspend、pause 等。
- **参数签名**：从当前版本源码的 `SYSCALL_DEFINEn` 机械解析。
- **参数类**（按参数名和类型的规则，写死）：

| 类型 | 默认值 | 变异类 |
| --- | --- | --- |
| 指针 | 有效的清零缓冲区（页对齐，2 页） | NULL、有效地址+1（不对齐）、有效地址 \| 2^62（高位别名）、内核地址 -65536 |
| 路径字符串 | `/tmp/f`（已有的普通文件） | NULL、空串、`/tmp/nonexist`、`/tmp/d`（目录） |
| fd | 普通文件 fd | 目录 fd、非阻塞管道读端、非阻塞 unix dgram 套接字、eventfd、-1、1000（未打开）；名为 dfd 的另加 AT_FDCWD |
| 大小/长度 | 64（`sigsetsize` 固定为 8） | 0、1、4096、2^31、全 1 |
| 标志/模式/命令 | 0 | 1、2、4、0x40、2^31、全 1 |
| pid | 自身 | 0、-1、99999 |
| uid/gid | 0 | -1、65534 |
| 地址型整数（addr、start 等） | 0 | 有效地址、有效地址+1、高位别名、内核地址 |
| 其他整数 | 0 | 1、-1、INT_MAX、INT_MIN |

- **种子**：在参照内核 `cur_arm64` 上，对每个系统调用试“全默认”和 64 个由固定随机种子生成的参数组合，最多保留 2 个成功（返回非错误）的组合作种子；一个都没成功就用全默认。
- **第 0 层（全量，不定向）**：每个种子本身，加上它的全部单参数变异；另加系统调用号边界用例（-1、100000，参数全 0）。
- **第 1 层（定向）**：对第 0 层中触达至少一个静态点位的系统调用，再做种子的全部双参数变异，每个种子最多 300 个（固定随机抽样）。
- **执行**：每个用例在新的子进程里运行；运行前重建 `/tmp/f`、`/tmp/d`；限时 0.3 秒，超时记 `timeout`。结果规整为 ok、错误码名、`timeout` 或 `killed_SIGxxx`。

### 3. 桥接（只用于确定“哪个系统调用触达哪个点位”）
- 另建一个开了 FUNCTION_TRACER 的当前版本 riscv 内核，只用于桥接，不参与比较。
- 跑一遍第 0 层：把静态点位函数中 `available_filter_functions` 里有的写入 `set_ftrace_filter`，记录每个用例命中了哪些点位函数。
- 某个点位被触达：至少一个用例命中它。某个系统调用触达某个点位：它的某个用例命中了这个点位。不在可跟踪列表里的点位（内联、static 被内联、宏），计数为“不可跟踪”。

### 4. 内核与参照
- **riscv**：当前版本 1 个，加上 5 条样本的修复前、修复后各 1 个，共 11 个（全部已建好）。
- **参照**：当前版本 riscv 用当前版本的 arm64/x86_64；每对样本内核用**该样本修复提交版本**的 arm64/x86_64（新建 10 个），避免参照比 riscv 新造成的版本差异。
- 每个内核运行 3 次，只比较 3 次结果完全相同的用例。

### 5. 判定（沿用上一轮，加一类剔除）
- **能力/环境**：`perf_event_open` 的用例需要 `hw_pmu`（上一轮的探测规则）；
- **版本**：系统调用不在该内核版本的系统调用表里，剔除；
- 剔除之后按多数规则判定：两个参照一致而 riscv 不同为“强”与众不同，只剩一个参照为“弱”，参照之间不一致为“参照分歧”。

### 6. 评价
- **检出缺陷 X**：存在用例 c，在 X 修复前的内核上与众不同，在 X 修复后的内核上不是。前后两个内核只差 X 的修复提交，参照也相同，所以这个差别只能来自 X 的修复。
- **交叉检出（描述性）**：按 git 真值，X 也存在于其他内核时，上面的用例在那些内核上是否同样与众不同。
- **当前版本的疑点**：当前 riscv 上全部与众不同的用例，按第 0 层、第 1 层分开计数。用固定种子抽 40 条（不足就全看）人工核对，分为：疑似失配、环境/能力、版本、riscv 合法差异（规范允许的实现差别）、测试自身问题、判断不了。
- **定向的作用**：比较第 0 层和第 1 层的疑点密度，以及已知缺陷的检出来自哪一层。
- **诊断**：对 5 条缺陷，逐条说明卡在哪一环。

### 7. 参考线（开发轮，宽松）
- **桥接**：报告可跟踪、已触达的点位比例，不设阈值。
- **通过**：检出至少 3/5，并且当前版本抽查的疑似率不低于 25%（与检查二同一标准）。不通过就写清楚瓶颈在哪一环。

## 我自己知道的风险
- 我知道这 5 条缺陷长什么样，参数类里的“高位别名”“不对齐”“系统调用号 -1”都可能受此影响。开发集上的检出数偏乐观，真正的盲测要等留出集（LoongArch）。
- 单参数变异很可能触发不了需要“多个参数同时特定”的缺陷，比如 A101 要“提示地址已被占用＋长度很大＋MAP_PRIVATE”。
- 很多系统调用在全默认参数下直接返回 EINVAL，走不到深处。
- 用例之间的状态残留，会造成不稳定或连锁差异。
