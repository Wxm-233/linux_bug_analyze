# 约定变化跟进：逐项判定第二层——模型判定小规模试点

## 这一轮要回答什么

公共代码改了约定以后，程序会列出一批“可能要跟着改”的架构函数（候选）。上一轮试过用程序规则判断哪些候选真的需要改，一个都没判对。这一轮换成让大模型来判：把公共改动C和30个候选函数交给模型，让它逐个回答“这个函数需不需要跟着改，为什么”。

这和以前失败的“让模型凭空写出要求”不一样：约定改了什么，C的改动里已经写清楚了，模型只需要对照着读。我们想知道：在这样一个问得很窄的问题上，模型能不能把真正需要改的函数挑出来。

## 做法

- **样本**：从没用过的208对中，取“真正被修的函数排在候选前30名以内”的60对，随机抽20对。另外加3对RISC-V案例，只作展示。
- **输入**：C的标题、说明和完整改动，加上30个候选函数的全文。候选顺序打乱，模型看不到程序原来的排名，也看不到后来的修复T。
- **输出**：每个候选判为“需要改”“不需要改”或“不确定”，各附一句理由，最后再给出排序。
- **盲核**：调用全部保存后、判分之前，研究者在不看模型输出的情况下，逐对判断这20对是否真的是“架构没跟上约定”。结果是：是10对、部分6对、否4对（`audit_20.json`，SHA `3689debf…`）。

| 文件 | 说明 |
| --- | --- |
| `criteria.md`、`prompt_template.md` | 判据与提示模板，调用前写定（SHA `94f72dcf…`、`3ee314dd…`） |
| `select.py` → `sample.json` | 抽样 |
| `build_prompts.py` → `prompt_index.json` | 生成23份提示；每份都包含目标函数，其中5份的候选不足30个（候选池本身小，最少2个） |
| `run_calls.py` | 23次Kimi调用 |
| `labels_20.tsv` → `audit_20.json` | 盲核 |
| `score.py` → `results.json`、`stats.json` | 判分 |

各脚本的SHA见`criteria_sha256.txt`。模型输出在`模型调用测试/2026-10-30/ccpj_01`到`ccpj_23`。

## 结果（主样本20对）

| 指标 | 模型 | 对照 | 事先定的标准 |
| --- | ---: | ---: | --- |
| 真正要改的函数被判为“需要改” | **3对** | 取程序原排名的前几名（个数与模型标记数相同）：4对 | 有效需≥12对；<8对为无效 |
| 每对标为“需要改”的个数（中位数） | **0** | — | ≤5 |
| 真正要改的函数排在前3名 | 4对 | 程序原排名：10对 | — |
| 只看盲核判为“是”的10对 | 3对 | 1对 | — |

- 23次调用全部正常完成，没有失败。模型可见输出合计约56万token，其中主样本约43万。
- **按事先定的规则：无效（命中不到8对）。** 这种形式的模型判定不可行，下一步转向其他方向。

### 模型错在哪里

模型非常保守，20对中有13对一个候选都没标“需要改”。真正要改的函数，大多被它判成了“不需要改”，而且理由听起来都很合理。例如：

| 公共改动 | 真正要改的架构函数 | 模型的判断 |
| --- | --- | --- |
| virtio加固中断：设备就绪之前到达的中断会被丢掉 | UML的`um_pci_init_vqs`，需要在probe中调用`virtio_device_ready()` | 不需要改：它只是加了接收缓冲区 |
| 内核要求`ro_after_init`区域在`mark_rodata_ro()`之前保持可写 | parisc的`mark_rodata_ro`，写保护做得太早 | 不需要改：它只计算并打印大小 |
| 公共代码新增了`timer_setup()` | UML自己有一个同名的静态函数，会冲突 | 不需要改：调用的是本文件里的初始化函数 |
| 公共的`rodata=`处理函数改为返回1，arm64自己的处理函数因此不再被调用 | arm64的`parse_rodata` | 不需要改：它用`early_param`注册 |

模型判对的3对，都是能在代码里直接看到冲突的情况：
- 改了名字的futex辅助函数；
- 普通slab缓存不再允许与用户态拷贝（powerpc的`rtas_flash`）；
- `set_huge_pte_at`要处理新的非present页表项。

要判断上面那些例子，需要知道代码之外的内核运行规律，例如“probe必须先让设备就绪”“同名的`__setup`只会执行第一个”“写保护的时机”。只读C的改动和候选函数本身，模型给不出判断。提示中“只有能指出具体冲突才判需要改”这句话，可能也让模型更保守。这一点没有单独检验。

### RISC-V（3对，只作展示）

3对的目标函数全部被判为“不需要改”，其中包括抽查里那个`cpumask_next()`的例子：模型认为`*pos - 1`是“标准用法”。

### 模型多标出的函数

主样本中，模型把6个非目标函数标为“需要改”。其中4个后来改过或删除了，2个到样本终点版本仍然没变。研究者人工查看了这2个：

1. **sh的`arch_task_cache_init`（疑似真实问题，未运行验证）**：公共改动让普通slab缓存默认不允许与用户态拷贝。sh用普通的`kmem_cache_create`创建`task_xstate`缓存，信号处理时却用`__copy_to_user`/`__copy_from_user`直接拷贝其中的浮点寄存器。按终点版本的代码，`__copy_to_user`会做`check_object_size`检查，SLUB对不在允许范围内的拷贝会`usercopy_abort`。因此在开启`CONFIG_HARDENED_USERCOPY`、使用硬件浮点的sh内核上，带浮点上下文的信号处理理论上会触发这个检查。到终点版本，这段代码仍未改变。**只记录，不对外报告，由用户决定后续处理。**
2. sh的`hw_breakpoint_handler`：模型认为可能会重复发送SIGTRAP，研究者看来证据不足，判为误报。

RISC-V案例组里，模型还标出了x86的`sgx_vepc_fault`。它在-EBUSY时调用`mmap_read_unlock`并返回RETRY。如果它会在只持有VMA锁的缺页路径下被调用，这样做就是错误的。是否真会走到这条路径，尚未核实，记作待查。

## 结论

- 模型能认出“代码里看得见的冲突”，但多数约定改变需要了解代码之外的内核运行规律。在逐个候选的判定上，模型非常保守，召回只有3/20，不如直接取程序原排名的前几名。
- 按事先规则，“候选生成＋模型逐项判定”这条路线在当前形式下不可行。
- 意外收获是：模型多标出的函数里，有1个看起来是至今仍存在的真实问题（sh），另有1个待查（x86 sgx）。这说明模型的“过度怀疑”有时有用，但样本太小，不能据此得出结论。
- 建议的下一步：转向**架构接口完备性对比**。统计公共代码要求架构提供哪些东西（钩子函数、宏、`ARCH_HAS_*`配置），看RISC-V缺了哪些、哪些是后来才补上的。这一方向不依赖逐个候选的语义判定，正好对应RISC-V历史样本里占多数的“需新加代码”一类。

## 统计

Kimi调用23次（全部完成，可见输出约55.9万token）；构建0；新确认缺陷0。另有疑似问题1个（sh）、待查1个（x86 sgx），均未运行验证，未对外报告。
