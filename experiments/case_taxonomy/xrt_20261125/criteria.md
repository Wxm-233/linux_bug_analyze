# 判据：把“编译期常量”和“运行时才确定的量”分开（xrt_20261125，师兄流程第六轮）

2026-11-25，Claude。用户：“区分运行时的量”。本判据写于任何实现和运行之前。接第五轮 `xconst_20261124`，其文件只读不改。

## 一、问题

第五轮把“追到架构定义”的对象式宏都记成了“架构常量”，一共 2230 条记录。但其中有一部分其实要到运行时才确定，例如：
- riscv 的 `VMALLOC_START` 展开后是 `kernel_map.page_offset - …`，读的是全局变量；
- x86 的 `VMALLOC_START` 是 `vmalloc_base`；
- `cpuset_current_mems_allowed` 是 `current->mems_allowed`，要经函数 `get_current()` 取得。

这两种量要查的性质不同：
- **编译期常量**：要查“在哪些架构、哪种页大小下取值不同”，属于 ORD/WT 那类逐配置求值；
- **运行时的量**：还要查“在它被设定之前是否已经被读了”“启动后会不会再变”，属于第四轮全局状态那类检查。

所以必须先把两者分开。

## 二、定义

对第五轮的每条架构常量记录（构建 b、文件 f、宏 M），在 f 的编译单元末尾问编译器一个问题：**M 能不能作为文件作用域静态变量的初始值**，即 `static __typeof__(M) v = (M);` 能否通过编译。这正是 C 语言里“编译期常量表达式”的标准，由 clang 自己判定，不靠我们解析宏。

分类：
- **编译期常量**：能通过。包括由常量拼成的结构体字面量，例如 `__pgprot(常量)`。
- **运行时**：不能通过。再在函数体里放一份 `(void)(M);`，从语法树里找原因：
  - 引用了哪些全局变量，标出该变量是不是 `const`、`__ro_after_init`，是否声明在 `arch/` 下；
  - 调用了哪些函数（`__builtin_*` 除外）；
  - 有没有内联汇编。

  按原因分成：
  - **运行时·变量**：只读到全局变量；
  - **运行时·调用**：有函数调用或汇编，可同时读变量；
  - **链接时地址**：只引用了全局符号的地址（取地址或数组），没有读它的值。
- **依赖使用处**：文件作用域里报“未声明的标识符”，也就是宏引用了使用处的局部变量或参数。
- **未判定**：不能通过，但找不到上述原因；或者探针本身失败（例如宏到文件末尾已被 `#undef`）。

宏在同一编译单元里被定义多次的，按文件末尾生效的定义判断，并单独计数报告。

## 三、做法

- 输入：第五轮 `/root/work/xconst/consts_<构建>.json.gz`，三个 mglru 构建，用同样的编译命令。
- 每个（构建，文件）只解析一次：用 libclang 的 unsaved file，把探针追加在源文件末尾，加 `-ferror-limit=0`。
  - 每个宏一行静态初始化探针，外面包 `#ifdef M`；
  - 每个宏另加一个函数探针。
- 诊断按行号对回探针。
- 产出：
  - 每条记录加上分类和原因；
  - 统计**同一个宏在不同架构上分类不同**的情况；
  - 在第五轮候选表上加一列“常量性质”。新表放在本目录，不改第五轮的表。
