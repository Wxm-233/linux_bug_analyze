## mpt3sas：存储表示与主机运算要分别检查

父版为 `cd5897eda27dc155146f25ddf4b0dd9967b3e2bb`。

- `drivers/scsi/mpt3sas/mpt3sas_base.c:1440–1441` 的 PRP 指针原先声明为 `u64 *`，修复改为 `__le64 *`；`:1458–1468` 等相应转换类型一起调整。旧版实际写 PRP 的 `:1519`、`:1532`、`:1552–1553`、`:1565`、`:1575` 已使用 `cpu_to_le64`。另一个 PRP 构建函数的 `:1705`、`:1710` 也已转换。这里的改动补齐了端序类型信息，不能据此认定旧版这些写入均未转换或在大端下必然写错。
- 真正改变长度判断的地方是 `base_is_prp_possible()`：`:1739` 定义主机变量 `u32 data_length`，`:1743` 先做 `cpu_to_le32(scsi_bufflen(scmd))`，`:1749` 却直接与主机整数阈值比较。`include/scsi/scsi_cmnd.h:188–190` 的 `scsi_bufflen()` 返回 `cmd->sdb.length`，没有线格式转换；`mpt3sas_base.h:144` 定义 `NVME_PRP_PAGE_SIZE=4096`。修复只删除这里的 `cpu_to_le32`，保持长度运算为主机表示。
- 源码推导示例：长度为 4096、SG 数为 1 时，主机语义应满足 16 KiB 门槛；在大端数值解释下，小端编码后的 32 位值为 `0x00100000`，会改变该比较。这个例子是表达式推导，未执行新测试，也不证明随后会崩溃、损坏数据或在特定设备上产生可观测故障。
- `_base_check_pcie_native_sgl()` 的 `:1789–1799` 使用上述判断决定是否构建 native NVMe PRP，说明比较并非无用赋值。`drivers/scsi/mpt3sas/Kconfig:43–49` 要求 `PCI && SCSI`，面向 PCIe SAS 控制器。构建条件没有限定某个 CPU 架构，但这不等于已经证明大端机器上存在对应硬件并实际走通该路径。

原始报告的定位噪声必须单独记录。`mpt3sas_base.h:1305` 是 `__le32 *reply_free`；旧版 `mpt3sas_base.c:3771` 给指针赋 `NULL`，`:4295–4296` 给指针赋 DMA 分配结果，并不是向小端标量写主机数值。两条 `insufficient` 是指针层级识别不足。`:5819` 的 `reply_free[i] = cpu_to_le32(reply_address)` 才是数组元素写入，局部 `normal` 有依据，但与本次修复位置无关，不能替代修复目标的结论。

## hci_ll：形式相同的 void 指针掩盖了命令表示

父版为 `7c6ca1201e5e87513b27196138f06df9cbd09a7a`。

- `drivers/bluetooth/hci_ll.c:670` 定义 `u32 speed`，`:701–707` 从当前串口工作速率取得值，`:712–713` 将 `sizeof(speed)` 和 `&speed` 交给 `__hci_cmd_sync()`。旧版没有在发送边界建立小端表示。
- 调用链不是隐式转换器：`net/bluetooth/hci_request.c:187–190` 转发到 `__hci_cmd_sync_ev()`，`:134` 添加请求，`:337` 调用 `hci_prepare_cmd()`，`:311–312` 用 `skb_put_data()` 添加参数；`include/linux/skbuff.h:2046–2051` 最终直接 `memcpy`。`:308` 只转换命令头 opcode，不能据此推断 payload 自动转换。
- 修复版 `hci_ll.c:710` 新增 `__le32 speed_le = cpu_to_le32(speed)`，`:713–715` 发送其地址，`:718` 仍把主机变量 `speed` 交给串口配置。提交正文和这组修改支持“设备命令参数使用小端、主机串口 API 使用主机数值”的局部契约判断。本轮没有核对 TI 外部协议原文，也没有验证真实控制器收发。
- 实际入口条件包括 `ll_setup()` 中 serdev 非空（`:669–673`）、固件下载成功（`:690–699`）和速率非零（`:709`）。`drivers/bluetooth/Kconfig:145–154` 的 `BT_HCIUART_LL` 依赖 `BT_HCIUART_SERDEV`，后者在 `:91–94` 依赖 `SERIAL_DEV_BUS && BT_HCIUART`，UART 驱动在 `:77–80` 依赖 TTY；设备范围为 TI BRF 系列。配置不写端序限制，仍不能声称大端硬件执行已验证。

## 对实验和下一步的含义

这两项支持 P2“数据表示与使用语义不一致”的源码讨论，却不属于本轮要验证的“已声明端序结构体字段上的宏整数写入”正例。应记录为两个新范围边界，不能用零 candidate 推导准确率、泛化成功或无问题。也不能把这次复核计作新增硬件/真实内核原型实验。

后续可分别研究两条检查：编码后的值是否被继续用于主机比较或运算；主机整数是否通过取地址和字节复制进入明确要求某种表示的命令参数。两条都需要消费者/接口依据，不能仅看到 `cpu_to_le*` 或 `void *` 就判断错误。指针自身赋值与指针指向的端序元素也需要在定位阶段区分。本轮仅记录这些发现，冻结 v4 和原始报告保持不变。
