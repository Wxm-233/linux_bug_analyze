# E1候选→事实查询桥接（N1→E2链路第一版）

2026-10-28。设计见[design.md](design.md)。试点只用已接触、不计评价的试点2提交（`arch/x86/kernel/cpu/amd.c`父版）。

## 实现

- `linux_bug_analyze/candidate_bridge.py`：①候选的提供者/消费者引用→所在顶层函数、被引用行中的标识符、候选文本中的`CONFIG_*`→命名查询与**不含值**的事实词表；②形式化提示（只给事实名/含义/类型，要求只用这些事实在v2 DSL中写scope/relation，或声明不可表达）；③`evaluate_candidate`：先用`validate_contract`校验，再由共享构建器生成v2契约交核心。未审核时要求/依据声明来源记为`model_proposal`，核心按既有规则判不足；研究者审核后才以`researcher_review`重评，两次分别保留。
- `kernel_facts`：被内联函数在预处理文本中找调用者（`callers`），新增查询`may_reference`（自身或其内联进的调用者有该符号重定位；语义只是“可能经内联引用”）。
- 测试：`tests/test_candidate_bridge.py`4项、`tests/test_kernel_facts.py`仍3项通过；WSL全量454项，仍为原有2个pycparser导入错误；SPARC通用位宽回归仍4/4。

## 试点2全链路

| 环节 | 结果 |
| --- | --- |
| 查询生成 | 5候选→9个函数、61条查询 |
| 事实回答 | 58/61（defined 9/9、may_reference 22/25、expansion_contains 25/25、config 2/2）；内联归属使原先不可答的被内联函数大多可答 |
| 形式化（1次Kimi调用） | 完整交付，130秒，13,577 token；**5/5声明不可表达** |
| 核心判定 | 无可判定契约；未进入研究者审核 |

模型给出的不可表达理由一致：候选要求的是**数值一致性**（如性能值与硬件范围、APIC ID位宽与核心数）、**初始化时序**（BSP初始化后、外部查询前已设置）与**跨CPU/热插拔/resume的取值一致性**（如MSR），而现有函数级事实只回答“是否引用/是否包含文本/配置值”。

## 结论

桥接在机械层面已贯通（候选→查询→事实包→形式化→校验→核心），但对真实候选的表达能力为0/5。缺口不在桥接本身，而在事实词表：E2需要比“函数是否引用符号”更接近要求语义的事实。按候选要求的类别，下一步需要的事实种类是：

1. **全局对象的读/写端点**（哪个函数写、哪个函数读某全局/每CPU变量）——静态，可用现有GIMPLE写入分析扩展到读；
2. **初始化阶段与调用可达**（`__init`/initcall级别、BSP/AP路径、调用图上是否先于消费者）——静态，需要调用图；
3. **运行时取值**（每CPU变量、MSR派生值、拓扑字段）——需要真实guest观测适配器（已有ARM64/x86 QEMU与PID1框架），成本高。

另一个选项是在E1提示中要求候选用可观测事实表述要求，以缩小语义差距；这会改变E1输入，需另起协议版本。

## 统计

1次Kimi调用（完整交付），1个x86_64事实包；0内核启动；独立正例/正常0/0。评价方法冻结仍过期。
