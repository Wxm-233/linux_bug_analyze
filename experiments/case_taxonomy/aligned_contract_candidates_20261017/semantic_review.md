# N2.5 模型候选的独立语义核对

本评审先保存 `source_oracle.md`，后才阅读已完成的 `模型调用测试/2026-10-17/n25_aligned_contract/final.md`。仅结合原11个区域、披露的1个事后补充区域及对应元数据，不读旧运行结果、不补源码、不改模型原文。以下“采纳”均指局部或条件候选，不是确认违约、满足或检测成功。

## 总体判断

回答提出了有研究价值的消费前提和架构资格差异，并主动保留通知外链、目标身份及稳定性缺口。它没有把词法顺序直接等同于完整CFG，也区分了getter取指针与mask内容使用。但**R1仍需收窄用途前提，T2的“等价”不成立，R3的存在量词不能升级为整组语义**。因此不将任何路线升级为完整跨架构履约结论。

引用身份/行号合法性由另行程序结果报告；合法引用只能证明引用来自输入，不能证明推理正确。输入确实没有预填人工契约结论，但保留了 `o->self` 和 `cpumask_test_cpu` 等观测代码，可能提供线索；不能称完全无答案暗示的自动发现或独立泛化。

## 三项要求

| 要求 | 决定 | 原因与采用边界 |
|---|---|---|
| R1：内容消费时包含目标CPU | **采纳为有条件必要候选** | 公共锁循环只锁mask成员，后续起始函数操作目标rq，确有“本次遍历若须保护该rq，则应覆盖该CPU”的用途依据。模型也承认外部锁规则未给出、通知外链缺失。不能把statement泛化成所有weight读取都必须self，或不带锁覆盖/合法目标/实际执行前提的全局接口定理。self也不充分保证leader、完整硬件组、稳定性或整条初始化正确。 |
| R2：锁定至解锁期间mask不变 | **保留假说，不注册为已证明要求** | 多次读取共享mask提示需要快照或协调机制，模型正确指出unlock和串行化缺源。但“全程完全不变、排除所有写者”是一种较强策略；合法快照/协调方案不一定要求物理对象全程不可变。现包不能证明lock/unlock集合不同、存在并发故障或必须采用该策略。 |
| R3：weight!=1时存在另一self-core leader | **仅采纳代码分支条件，降级语义说明** | 源码确实搜索一个 `t!=cpu && rq(t)->core==rq(t)`，找不到则WARN并退出。该存在条件是避免此分支告警的代码条件，不自动成为完整接口规范。模型“即掩码成员是已建立core关系的同核兄弟”过强：存在一个候选leader既不证明全部成员，也不证明实际同核；`core==self`也可能只是初始化时的自身状态。正常退出/合法失败语义仍未知。 |

空mask导致weight0、无leader并告警的局部推理可保留；singleton-other可能weight1直接退出，说明“非空/无WARN”不能替代锁覆盖；这些是源码逻辑边界，不是本轮新运行或实际可达输入。

## 六条架构路线

### R1：s390

提供对象 `cpu_topology[cpu].thread_mask`、possible目标循环、`cpu_thread_map` 的online资格及notify后再set_online/update的局部顺序，与材料一致。模型将其标为conditional_mismatch，且明确最后写者、入口online值、其他准备和实际通知回调均未证明，方向可采纳。

但“只有online时update才可能包含自身”应限定于**本mapper在合法目标、有效存储、循环覆盖、原语效果和无干扰等前提下的这次写入**；不能排除包外其他writer，也不能把old guard固定成公共接口必须要求。仅由set_online位于后面，不能证明到达notify时CPU必然offline。

### R1：x86

per-CPU `cpu_sibling_map`、先加入setup集合以及 `smp_callin` 中先调用建图后notify，均有本包原文。模型列出了CPU身份、目标上限/迭代覆盖、并发清除和通知外链前提，并明确不能推出R2/R3，适合保留为**局部条件满足候选**。

这不是“x86已证明正常”。setup位出现只说明某处设置该资格位；函数在首部set setup，不能单凭集合名或成员资格证明所有准备步骤均完成。两次读取当前CPU号的身份及per-CPU最终对象亦未由本包闭合。

### R2：两侧

s390可见possible循环调用mapper，x86可见向其他CPU sibling map的写入位置；可作为潜在writer清单。模型的insufficient状态正确。但“任何调用都会改写所有possible CPU，包括正在被其他CPU消费的掩码”只能改读为正常迭代/原语前提下可能写这些目标，不能断言实际同时消费或并发重叠；其他写者和串行化未给出。x86向“已在线兄弟”写入中的online也不是这段源码显式资格，应保留未知。

### R3：两侧

s390 HW分支的present/online筛选、x86 setup迭代及match条件是可见形状；模型保留模式、match语义和rq状态未知，insufficient结论合适。setup成员不能自动等于已经完成全部建图/调度准备；两侧都不能从集合来源直接证明leader或真实SMT关系。

## 局部顺序与推荐检查

| 项目 | 处理 |
|---|---|
| L1 update应在notify前 | 模型已在limits明确实际after、expected before，不是抄错顺序。程序可判该**候选期望未建立**，不能将其算确认缺陷。已有准备可能使移动非必要；旧online guard也使只提前调用仍可能copy空mask，不能当完整修复。 |
| L2 set_online在update前 | 局部顺序真实，能解释旧mapper资格；这是旧实现兼容性事实，不是公共消费者必须等待online的规范。不能用它否定合法的online前准备方案。 |
| L3 x86建图在notify前 | 局部源码关系可采纳；缺效果、身份、覆盖与稳定性，因此不等于准备完成。 |
| T1 在真实内容使用边界核self/对象 | **保留candidate**。应绑定实际被遍历对象、目标CPU及用途；循环前检查仍需检查至使用间无变化的依据，不能自行宣布精确消费验证完成。 |
| T2 最后写者/online状态检查 | **降级，尤其拒绝“等价”作为程序规则**。online为真只是旧mapper接受资格之一，尚需目标覆盖、原语效果、HW最终交集、无干扰等条件；其他writer和保留状态未知。最后写入的来源也不能代替消费时成员关系，更不能把旧online限制升格为未来所有实现的接口义务。可保留为待查的旧提供者状态来源问题。 |
| T3 比较lock/unlock快照并排除writer | 保持insufficient；可以登记一致性假说，不接入当前正式特征或新增并发结论。当前不为此递归补unlock/helpers。 |

模型正确区分D06探针读与原循环；评审进一步保留：core257–259的bits/self/weight采样在关中断264之前，原mask遍历为265。即使对象表达式一致，也不能把该采样等同于精确遍历值、全局首读或全区间稳定。`r4_note`标签、常量及事后打印均不充准备/失配真值。

## 本轮真正有用的三点

1. **可提炼出连接两架构的窄消费要求**：在共同锁覆盖用途下检查目标成员资格，比“有无调用准备函数”“是否已经online”更接近接口实际需要；本轮只验证该要求能被模型提出并经人工限定，尚未证明自动检测有效。
2. **准备资格与消费要求必须分开**：old s390采用online筛选，x86采用setup集合；顺序正确与资格正确需要共同满足。把old guard当规范或只移动调用，都会丢掉这一架构相关机制。
3. **程序核对与语义裁定承担不同任务**：词法顺序/引用绑定能固定模型究竟说了什么，不能替模型证明原语效果、完整调用链或规范权威。T2和R3即使引用正确仍需降级，体现了保留未知的实际作用，而非准确率提升证明。

## 下一阶段建议

先把本轮可采纳的R1/T1与L1–L3保存为一张**限定候选卡**：分开模型提出的要求、程序确认的局部事实、研究者采用的用途前提及待证项；R2/R3与T2/T3不升格为正式N2履约特征，whole_contract继续不足。不要为填满当前案例继续扩helper、writer或配置网格。

随后冻结这条方法路线，按接触/家族记录寻找未参与开发的同机制问题与同用途正常对照，再做同材料、同预算的直接模型与组件方案比较；找不到合格材料就报告资格不足，不以当前已读回放代替独立评价。本轮没有新增内核/缺陷或独立正正常样本，不计算检测率或N2增益。
