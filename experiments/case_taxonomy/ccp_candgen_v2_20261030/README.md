# 约定变化跟进：候选生成v2

## 这一轮要回答什么

公共代码改了约定以后，我们要在其他架构里找出“还没跟着改”的函数。具体做法是先让程序列出一批可能要改的函数，称为**候选**，然后看后来真正被修的函数是否在这批候选里，这个比例称为**覆盖率**。

上一轮的v1只用一条规则：公共改动里出现过的名字，哪个架构函数的函数体里用到了，哪个函数就是候选。v1在新样本上的覆盖率是45%，没达到事先定的50%。人工抽查30对后，归纳出了它漏找的几类原因。这一轮按其中四类修改候选生成规则（v2），在**没用过的208对**上重新测量。

## v2加了什么

| 补充 | 解决的问题 | 例子 |
| --- | --- | --- |
| 函数自己的名字也算 | v1只看函数体里用了哪些名字，没看函数本身叫什么；而架构对某个接口的实现，名字往往就是接口名 | 公共代码开始在新场景调用`set_pmd_at()`，要改的正是x86自己的`set_pmd_at()` |
| 公共改动所在函数的名字也算 | 公共改动只改了函数内部或函数头，接口名本身没出现在改动行里 | 公共代码收紧了`cpumask_next()`的内部检查，改动行里没有`cpumask_next`这个词 |
| 常见名字改按“`->名字`”匹配 | `interface`这类名字全内核有五千多个文件在用，v1直接丢掉；按结构体成员的写法匹配，范围就小多了 | `plat->interface`改为`plat->phy_interface` |
| 多看一层调用 | 公共改动所在函数又去调用某个架构函数，出问题的是被调用的那个 | 公共改动在`timekeeping_update()`里调整了顺序，受影响的是它调用的架构函数`update_vsyscall()` |

这四项都是从抽查的30对里总结出来的，所以那30对只作参考，评价只看另外208对。

**实现阶段的修正**：冒烟测试中发现，如果公共改动改在函数头上（例如在返回类型那一行加`__must_check`），程序没把它算作“改动所在的函数”。原因是程序识别的函数范围从`{`开始。判据写的是“改动行所在函数”，所以补上了函数头。这个修正在记录脚本SHA、跑正式评价之前完成。

## 结果（未用过的208对）

| 指标 | v1 | v2 | 事先定的标准 |
| --- | ---: | ---: | --- |
| 被修的函数出现在全部候选中 | 44.2%（92对） | **51.4%（107对）** | ≥50% |
| 出现在前50个候选中 | 29.3% | 34.1% | — |
| 出现在前20个候选中 | 23.6% | 26.9% | — |
| 每次给出的候选函数个数（中位数） | 143 | **174** | ≤200 |
| 候选个数的上四分位 | 358 | 390 | — |

- v2比v1多找到15对，原来找到的一对也没丢。
- v1部分由程序重新算了一遍，208对与上一轮记录逐对一致。
- **按事先定的规则，候选生成可用，下一步是设计“逐项判定”。**

但要如实说明，这个“通过”很勉强：

- 51.4%只比标准高1.4个百分点。按统计区间估算，真实值大约在45%到58%之间，有可能低于50%。
- 候选数量偏多。中位数174个，有96对（接近一半）超过200个。前50个候选里只能找到34%，所以候选的排序目前帮助不大。
- 208对里并不全是真正的“没跟上约定”。按抽查比例，大约有三成是间接后果或无关的。因此覆盖率既可能被低估，也可能有一部分是碰巧找到的。

## RISC-V方向

v4.0版本以来，“公共代码改了、RISC-V没跟上、后来补修”的历史配对只有**24对**：

- **6对**改的是RISC-V里已有的函数，可以用候选来评价。v1覆盖2对，v2覆盖3对。新增的那一对就是抽查里的`cpumask_next`例子：显示`/proc/cpuinfo`时，到最后一颗CPU要提前结束。
  - 没被覆盖的3对都没用过，而且都是“语义上”的约定改变，公共改动和RISC-V函数之间没有共同的名字：
    1. 工作队列新增了CPU亲和范围，要求处理器间中断在更早的时候就能用；
    2. RISC-V的时钟事件在CPU休眠期间会停，需要准备一个“广播”时钟；
    3. BPF的内存分配方式改了，RISC-V的BPF即时编译要依赖某个原子指令扩展。
- **18对**的修改不在已有函数里。从标题看，多数是在头文件里补宏或声明，或者按公共代码的新参数改写RISC-V自己的实现。例如`huge_ptep_get_and_clear()`和`set_huge_pte_at()`都新增了页大小参数，此外还有`MAX_POSSIBLE_PHYSMEM_BITS`、`tlb_flush()`的定义、newstat系统调用。这一类目前的候选生成完全看不到，需要“拿已经改过的架构做参照”的找法。

RISC-V的样本太少，以上只作案例，不计算比例。

## 下一步建议

1. **设计“逐项判定”**（事先规则给出的下一步）：给定公共改动和一个候选函数，判断这个函数是否需要跟着改。由于每次候选有一百多个，判定成本很重要。可以先在少量配对上看判定的准确率和花费，再决定是否需要先改进排序。
2. **“参照已改架构”的候选来源**：公共改动的作者通常已经改了几个架构，可以把这些改动当作模板，到没改的架构里找对应位置，例如同名的函数或宏、同一个头文件。这正好对应RISC-V那18对需要新加代码的情况，可以用它们做设计材料。

## 补记（2026-10-31，函数识别缺陷评估）

`named_spans`只回看`{`前4行识别函数名，会漏掉函数头较长的函数。用修正实现重算（候选与目标）：未接触208对的v2全部候选覆盖由51.4%变为51.9%，池中位数由174变为175，v1不变（44.2%），结论不变。RISC-V方向24对中“改已有函数”由6对更正为8对（新增KVM的kvm_arch_prepare_memory_region与BPF的__arch_prepare_bpf_trampoline）。原数字保留，见`spans_defect_audit_20261031/README.md`。
