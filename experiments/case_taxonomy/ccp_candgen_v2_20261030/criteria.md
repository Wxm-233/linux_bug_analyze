# 约定变化跟进：候选生成v2（判据，实现前写定）

承接`ccp_audit_20261030/`：30对盲核中`yes`占21对，但v1候选只覆盖其中7对（33%）。14个漏覆盖对里，有7对属于可以通过改候选生成补上的四类。本轮按这四类修改候选生成，在**未接触的208对**上重算覆盖。不调用模型。

用户安排重点关注Linux公共层到RISC-V的跟进。按现有规则，RISC-V方向的历史配对只有24对，不够单独统计：其中6对改的是已有函数，18对需要新增代码。所以本轮评价仍用全架构，RISC-V单独列案例。

## v2的四项补充（来自抽检的事后漏因，设计数据是那30对）

v1：取C在公共层`.c/.h`增删行中的标识符（长度≥4，不是C关键字，全树出现文件数≤500）。在C没改过的架构目录下，函数体含有任一标识符的函数即为候选。

v2在v1基础上补充四项：

1. **函数名匹配**：候选函数的函数名本身属于C的标识符集合时，也计为命中（v1只看函数体）。
2. **C改动所在函数的名字**：C在公共层`.c/.h`中改动行所在函数（以C合入后的代码为准，用`named_spans`定位）的函数名，加入标识符集合。同样要求全树出现文件数≤500。
3. **成员访问形式**：C增删行中以`->name`或`.name`形式出现、但因全树出现文件数>500被v1过滤的名字，改为只按成员访问形式匹配（`->name`或`.name`）。要求成员访问形式的全树出现文件数≤500。
4. **一层调用关系**：第2项中C改动所在的那些函数，在C合入后的函数体里调用到的函数名（`name(`形式），只作为**函数名匹配**使用：架构目录下同名函数的定义计为命中，但不按函数体匹配。同样要求全树出现文件数≤500。

排序：按命中的不同键（标识符、函数名、成员名）个数降序，再按路径与行号排序，与v1相同。候选范围仍为C没改过的架构目录下、C合入时已存在的函数。

## 评价样本

- **主样本**：`ccp_pool.json`的238个新样本中，去掉抽检用过的30对，剩下的208对。研究者此前只看过这208对的汇总覆盖，没有读过逐对内容。
- **参考**：抽检的30对，以及其中的21个`yes`，同时报告v2的覆盖。这30对是设计数据，不作评价。
- 208对中预计有约30%不是真正的跟进（抽检比例为9/30）。所以覆盖是对“真实例覆盖”的保守估计。

## 指标

在208对上，分别报告v1与v2的以下指标：

- 前20、前50与全部候选的覆盖；
- 候选池中位数与上四分位数；
- 消融：只加一项补充时全部候选的覆盖。

## 事先写定的决策规则（主样本208对，v2）

- 全部候选覆盖≥50%，**且**候选池中位数≤200：候选生成可用，下一步设计并登记“逐项判定”。
- 全部候选覆盖≥50%，但池中位数>200：覆盖够但候选太多，下一步先做排序或过滤，以前50的覆盖为目标。
- 全部候选覆盖<50%：本轮的补充仍不够，转向“同类位置对比”候选来源（针对需要新增代码的一类）的设计。

## RISC-V案例（描述性）

- 列出RISC-V方向的24对：T在`arch/riscv/`，`Fixes:`指向没改过RISC-V的公共层改动C。
- 对其中改已有函数的6对，报告v1与v2是否覆盖。
- 对需要新增代码的18对，本轮只列出哈希和标题，留作“同类位置对比”的设计材料。这些对从此转为已接触。

`v2_pool.json`：每对的v1/v2覆盖、池大小，以及目标被哪类补充命中。`stats.json`：汇总。`riscv_cases.json`：RISC-V的24对。
