## 三条规则

| 规则 | 约定 | 写法 |
| --- | --- | --- |
| R1 | 跟踪器可能把调用号改成-1，所以返回值必须在跟踪钩子之前、无条件地预置为`-ENOSYS` | 在调用`syscall_enter_from_user_mode`等锚点的函数中，锚点之前必须出现`ENOSYS`，且它的路径条件不多于锚点的路径条件 |
| R2 | 开启脏页记录时，二级页表只能按页粒度映射 | `arch/*/kvm`中大页调整函数的调用点，路径上必须有与脏页记录有关的判断，或者被调函数里有这类判断 |
| R3 | 恢复惰性扩展状态时，先放弃已持有的状态，再拷贝 | 在RISC-V、x86、arm64的信号代码中，“拷入当前任务状态”的调用之前，必须先有“放弃”调用（两者都是事先列定的架构事实） |

## 判定

按事先标准：
- **规则可用**：E1为3/3，E2的(a)加(c)为0/8。
- **不能泛化**：E3召回1/4，不到一半。

## 解读：M10需要“约定级”而不是“位置级”的规则

- 每条规则都是从RISC-V的一个案例写出来的，抓住的是这条约定在RISC-V上的**一个实现位置**：系统调用入口、缺页时的大页调整、恢复函数内的顺序。
- 但同一约定在不同架构上，分散在**多个实现位置**：
  - R1：入口函数或跟踪钩子；
  - R2：缺页时调整，或者清除脏页记录时拆分；
  - R3：每个恢复函数内，或者调用者里尽早处理。
- 所以留出样本中的违反大多发生在规则没看的位置。误报也来自同一原因：约定在别的位置已被满足，比如汇编、调用者、被调函数。

**改进方向**：M10规则要先列出“这条约定在各架构上的全部实现位置”，再在每个位置上检查条件或顺序。这正是M2规则里“保证来源”的推广：
- 不仅要问“保证在哪里”；
- 还要问“约定在哪些地方需要被保证”。

这一步需要对约定本身建模，比如沿公共接口的调用图找出所有相关位置，可以由模型辅助列出候选位置，再由规则逐一核对。
